## 1. DB (스크립트는 사용자가 실행)

DB 확인: `s-erp-postgresql-readonly` MCP로 `tb_purchase_request_hd/dt`, `tb_purchase_confirm_hd`, `tb_item_partner_price`, `tb_warehouse`, `tb_customer_info`를 조회했다.
`tb_purchase_request_dt`에 이미 `order_type`, `use_type`, `order_close_at`(발주대기 마감), `purchase_confirm_id`가 있다.

## 2. 계산 규칙

잔량 = `확정수량 − SUM(order_qty)` (대상: 유효한 발주 헤더(`use_at='Y'`)의 행). 행이 삭제되면 잔량이 자동 복원된다.

부가세(행 단위, 반올림은 영업 `roundSalesOrderAmount`와 동일):

| 구분 | 공급가 | 세액 | 합계 |
| --- | --- | --- | --- |
| 과세 + 미포함 | 수량 × 단가 | 공급가 × 10% | 공급가 + 세액 |
| 과세 + 포함 | 수량×단가 ÷ 1.1 | (수량×단가) − 공급가 | 수량 × 단가 |
| 영세·면세 | 수량 × 단가 | 0 | 공급가 |

- 세액은 영업처럼 직접 수정할 수 있고, 수정하면 합계를 다시 계산한다(영세·면세는 0 고정).
- 헤더 금액은 행 합이다. 서버가 같은 규칙으로 다시 계산해 저장하고, 화면 값과 다르면 서버 값을 사용한다.

## 3. API (`/api/v1/materials/purchase-orders`)

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/candidates` | 확정 행 후보. 조건: 확정 유효, `order_close_at='N'`, 잔량 > 0. 쿼리: 확정일 기간, 검색어, 구매처명 |
| POST | `/` | 발주 저장 |
| GET | `/material-default` | 직접 발주 품목의 계정·검사대상 기본값(`inspectAt`) |
| GET | `/{purchaseOrderId}` | 저장된 발주 조회(헤더 + 행) |
| GET | (기존) `/purchase-request-confirms/unit-price` | 기본 단가 재사용 |

### 3.1 후보 응답 행
`purchaseRequestDetailId`, `confirmNo`, `confirmDt`, `supplierId/Name`, `materialId/Code/Name/Spec/Unit`, `materialTypeName`, `inspectAt`(품목마스터 `inspect_type`), `confirmQty`, `orderedQty`, `remainQty`, `confirmDeliveryDt`, `warehouseId/Name`, `unitPrice`, `currencyCode`, `orderType`, `useType`, `requestNo`, `stockQty`(null), `remark`.

### 3.2 저장 요청
```
{
  "sourceType": "CONFIRM" | "DIRECT",
  "orderDt", "supplierId", "currencyCode", "warehouseId",
  "taxType", "vatIncludedAt", "remark",
  "orderType", "useType",              // DIRECT일 때 필수, CONFIRM이면 무시
  "details": [{
    "purchaseRequestDetailId",         // CONFIRM일 때 필수
    "materialId",                      // DIRECT일 때 필수
    "orderQty", "unitPrice", "deliveryDt", "warehouseId",
    "inspectAt", "vatAmt", "remark"
  }]
}
```

### 3.3 저장 규칙
1. 인증·테넌트 확인. 행 1건 이상.
2. `CONFIRM`: 대상 확정 행을 `FOR UPDATE`로 잠그고, 모두 존재·확정 유효·`order_close_at='N'`·동일 구매처(`supplierId`)인지 확인한다. 요청 구매처가 확정 구매처와 다르면 **발주 구매처(헤더)를 기준**으로 저장한다. "확정과 다름" 표시는 서버가 판단하지 않고 화면이 확정 기준값과 발주값을 비교해 행에 표시한다(구매처·단가·수량 초과·납기일·창고). 한 발주서의 모든 행 구매처는 같아야 한다(헤더 구매처). 확정 행과 통화가 다르면 400.
3. `DIRECT`: 품목 계정이 RAW/SUB/SUPPLY인지, 발주구분·사용용도 공통코드가 유효한지 확인한다. MR 1건(`MR-…`, 요청자=로그인 사용자, 요청일=발주일)과 MC 1건(`MC-…`, 확정값=발주 입력값)을 만들고 각 행을 연결한 뒤 `purchase_request_detail_id`로 발주 행에 기록한다. 요청 상태는 `CONFIRMED`로 계산한다.
4. 출처 혼합 거부(행에 `purchaseRequestDetailId`와 직접 품목이 섞이면 400).
5. 입력 검증: 수량 > 0(소수 2자리), 납기일·창고 필수, 단가 ≥ 0 또는 null, 부가세 조합(영세·면세에서 포함 선택 거부), 창고·구매처 사용 가능 여부.
6. 금액 재계산 후 저장, 번호 `PO-YYYYMMDD-NNNN` 발급. 하나라도 실패하면 전체 롤백.
7. 응답: 저장된 발주(헤더 + 행), 잔량 초과 행 목록(경고용).

### 3.4 기존 확정 취소 보강
`POST /purchase-request-confirms/{id}/cancel`: 해당 확정의 행이 유효한 발주 행에 연결돼 있으면 409(`이미 발주된 확정은 취소할 수 없습니다. 발주를 먼저 취소해 주세요.`).
단, 직접 발주가 자동 생성한 MC는 발주 취소 때 함께 취소되므로 직접 취소는 막는다(같은 검증이 적용됨).

## 4. 화면 (`frontend/src/pages/materials/order/create`)

- 구성: `OrderCreatePage`, `components`(헤더 폼, 행 그리드, 확정 불러오기 창, 직접 품목 선택), `services`, `types`, `data`(컬럼), `hooks`. 라우팅은 `AppRouter.tsx`에 추가.
- 헤더: 발주일(기본 오늘), 구매처, 입고창고, 부가세구분, 부가세여부, 사용용도·발주구분(직접 발주일 때만 표시), 비고, 금액 3종(읽기 전용).
- 버튼: [확정 불러오기], [품목 추가](직접 발주), [선택 행 빼기], [저장], [초기화].
- 확정 불러오기 창: 컬럼 = 선택, 확정번호, 확정일, 구매처, 품목계정, 품목코드, 품목명, 규격, 단위, 재고량(비어 있음), 확정수량, 기발주, 잔량, 요청납기일, 확정납기일, 사용용도, 비고.
  첫 체크 행의 구매처를 상단 칩으로 고정한다. F1Grid는 행 단위 비활성을 지원하지 않으므로, 다른 구매처 행을 체크하면 **선택에서 자동 제외하고 안내 문구를 표시**한다(구현 시 확정한 차이). 칩 ✕로 선택 초기화. [선택 불러오기]로 그리드에 누적 반영한다(같은 구매처·같은 통화만, 이미 담은 확정 행은 건너뜀).
- 그리드 행: 수량, 단가, 납기일, 창고, 검사대상, 비고 편집. 공급가·세액·합계는 계산, 세액은 수정 가능(영세·면세 잠금). 확정과 다른 행은 경고 아이콘.
- 출처 제한: 확정 불러오기 행이 있으면 [품목 추가]를 막고, 직접 품목이 있으면 [확정 불러오기]를 막는다(안내 문구 표시).
- 로딩·에러·저장 중 중복 방지를 확인한다. 저장 성공 시 발주번호 안내 후 화면을 초기화한다.

## 5. 검증 항목
- 같은 구매처 제한과 칩 초기화, 분할발주 후 잔량·후보 제외.
- 부가세 3가지 조합의 계산과 영세·면세에서 포함 컨트롤 비활성.
- 직접 발주 저장 시 MR·MC 자동 생성과 연결, 실패 시 전체 롤백.
- 발주 행이 있는 확정의 취소 거부.
- 행 빼기(저장 전)와 출처 혼합 차단.

## 6. 확정한 사항 (구현 시점)
- 반올림: 영업 수주 `roundSalesOrderAmount`와 같이 소수 둘째 자리 반올림(HALF_UP). 서버 `PurchaseOrderAmountCalculator`와 화면 `calculateOrderAmounts`가 같은 규칙이다.
- `inspect_type`은 `Y`만 검사대상으로 보고 그 외(빈값 포함)는 `N`으로 처리한다.
- 헤더 구매처를 바꾸면 확정 행은 "확정과 다름"만 다시 계산하고 단가는 바꾸지 않는다. 직접 발주 행은 새 구매처의 기본 매입 단가로 다시 조회한다.
- 통화는 확정 행의 통화를 따르며 화면에서 수정하지 않는다. 직접 발주는 첫 품목 단가의 통화 또는 KRW다.
- 세액은 서버가 화면 값을 받아 저장한다(영업과 같은 직접 수정 허용, 영세·면세는 0만 허용). 헤더 금액은 서버가 행 합으로 다시 계산한다.
- 직접 발주 시 자동 생성되는 MR/MC의 비고는 `직접 발주 자동 생성 (PO번호)`이다.
