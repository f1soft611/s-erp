## 범위와 기존 계약

- 프론트엔드 수주등록·현황, 수주 전용 공통코드 조회 서비스, F1-Grid 문서와 테스트를 변경한다.
- 수주/상세 API 주소, payload field(`status`, `lineStatus`, `deliveryMethod`, `deliveryDt`), 현황 검색 query key(`status`, `lineStatus`), 권한은 유지한다.
- DB 테이블이나 컬럼, CHECK, FK를 변경하지 않는다. 공통코드 그룹/항목은 테넌트별 seed SQL을 제공하되 실제 DB에는 적용하지 않는다.
- 레이아웃은 기존 수주등록·수주현황과 공용 검색/알림 컴포넌트를 유지한다. 반응형은 375/768/1280px에서 확인한다.

## 공통코드 계약

| 공통코드 그룹 | 사용 화면 | 활성 itemCode | 활성 itemNm |
|---|---|---|---|
| `SALES_ORDER_STATUS` | 수주상태 및 진행상태 | `수주등록`, `생산대기`, `생산중`, `출하완료`, `취소`, `대기` | 각각의 표시명 |
| `SALES_DELIVERY_METHOD` | 배송방법 | `택배` (기본 seed; 관리자가 추가 가능) | `택배` (기본 seed; 관리자가 수정 가능) |

- 그룹/항목은 기존 공통코드 service를 사용해 조회한다. 그룹 `useAt='Y'` 및 항목 `useAt='Y'`만 사용하며 항목은 `sortOrder` 오름차순이다.
- 저장/API 값은 `itemCode`, 화면의 일반 표시값은 `itemNm`이다. 기존 수주상태 DB CHECK에 따라 header 상태 code는 현재 허용된 다섯 값 그대로 둔다.
- `대기`는 현행 `tb_sales_order_dt.line_status` 기본값이므로 진행상태 표시/필터에 포함한다. 수주상태 selector/search에서는 제외한다.
- 신규 그룹/항목이 비어 있으면 고정 목록으로 대체하지 않는다. 사용자가 알 수 있도록 오류/누락 안내와 재시도 UI를 보여준다.
- 수정/조회 데이터의 코드가 현재 활성 항목과 일치하지 않으면 해당 원문을 비활성 legacy 선택지/표시 fallback으로 보존한다. 선택을 바꾸기 전 기존 값을 빈 값이나 다른 코드로 치환하지 않는다.
- delivery method는 선택형 TextField다. 코드 조회 중·오류·항목 없음이면 비활성화한다. 기존 nullable 저장 정책을 유지하므로 코드가 없을 때 다른 입력/저장을 막지 않는다.

## 수주등록

1. 수주상태 필드는 현재와 같이 읽기 전용이다. 신규 기본값과 조회 수주의 상태 코드를 `itemNm`으로 표시한다.
2. 배송방법은 `SALES_DELIVERY_METHOD` select이며 `itemCode`를 기존 `deliveryMethod` payload에 저장한다.
3. 상세 F1-Grid 첫 행 번호 헤더를 `행`에서 `No`로 바꾼다. 상세 row number나 API 데이터는 변경하지 않는다.
4. 헤더 납기일은 필수 입력이다. 저장 전 빈 값 및 잘못된 날짜를 거부하고 기존 날짜 입력 검증 메시지 패턴을 사용한다.
5. 상세행을 추가하는 시점의 헤더 납기일을 새 행 `deliveryDt`에 넣는다. 이후 상세 납기일은 편집 가능하며 기존 상세 날짜는 헤더 변경만으로 덮어쓰지 않는다.
6. 상세 `lineStatus` 표시명을 `진행상태`로 바꾸고 공통 상태명으로 표시한다. 이 입력/상태전이는 현재와 같이 읽기 전용이다. `대기` 등 미등록 기존값은 원문 표시한다.
7. 시스템 계산 지원 범위를 넘는 수량/단가 입력은 행에 적용하지 않는다. 기존 행 값을 유지하고 오류 문구(예: `계산된 공급가 계산 결과가 지원 범위를 초과했습니다.`)를 기존 페이지 오류 영역에 표시한다. 오류를 콘솔로만 보내거나 성공처럼 무시하지 않는다.

## 수주현황

1. `lineStatus`의 컬럼/상세검색 라벨을 `업무상태`에서 `진행상태`로 변경한다. 기존 `lineStatus` query key는 유지한다.
2. 기존 작업지시서 008의 현황 그리드 `status` 숨김은 유지한다. 수주상태 상세검색 select는 공통코드 항목 label을 사용하고 기존 `status` query key로 전송한다.
3. 진행상태 상세검색도 같은 `SALES_ORDER_STATUS` 그룹의 활성 항목을 label/value로 사용한다. line-level `대기`도 선택 가능하다.
4. 상세 패널의 수주상태 Chip과 행별 진행상태도 `itemNm`을 표시한다.
5. 견적번호 `quotNo` 컬럼은 표시 상태로 유지한다. 검색 파라미터와 응답 필드는 변경하지 않는다.

## Seed와 롤백

- `docs/database/20261117/20261117_015_seed_sales_order_common_codes.sql`을 `backend/DATABASE/20261117`에 동일 사본으로 둔다. 스크립트는 명시적 `target_tenant_id` psql 변수와 대상 테넌트 존재 확인을 요구한다.
- 신규 그룹 두 개를 만들고 수주상태 5개, line default `대기` 1개, 현재 fixture에서 확인된 배송방법 `택배` 1개를 추가한다. 기존 그룹/항목 및 관리자의 이름·정렬·사용 여부는 덮어쓰지 않는다. 충돌 값은 그대로 보존한다.
- verification SQL은 선택된 대상 테넌트의 그룹별 활성 항목 수만 확인한다. tenant 행/사용 데이터는 결과 문서에 복사하지 않는다.
- rollback은 seed marker와 초기값이 모두 그대로인 seed item/group만 삭제하고, 수주 헤더·상세의 상태 및 배송방법 문자열 참조를 확인해 사용 중인 항목은 보존한다. 다른 소비자의 참조와 운영자 관리 변경을 완전히 추론할 수 없으므로 업무 적용 후 롤백하지 않는다.
- 변경 이력에는 2026-11-17, 대상 테이블, 데이터 영향 범위, schema 변경 없음, 미적용 상태, rollback 제한을 기록한다. 실제 DB 적용은 하지 않는다.

## 오류·검증 기준

- 코드 로딩 실패/누락은 등록·현황에서 알림 및 재시도 가능하며 hard-coded fallback options는 없다.
- 과거 값이 활성 코드에 없더라도 변경하지 않고 조회/수정에서 원문으로 보존한다.
- 공통코드 service test: active group/item만 포함, sortOrder, itemCode/itemNm 대응, 오류 전파.
- 등록 test: 수주상태 표시명, 배송방법 코드/이름, 로딩 실패/재시도, 납기 필수/저장 차단, 행 추가 납기 기본값과 행별 수정, No label, 계산 overflow 거부와 메시지.
- 현황 test: status/progress dynamic options, label, query key 호환, 견적번호 표시, 상세 수주상태/행 진행상태 표시.
- DB scripts: tenant 인자 필수, no existing data overwrite, seed idempotency, conservative rollback, docs/backend 사본 동일성.
- Vitest 대상 실행, TypeScript/Vite build, 변경 영역 lint, 실제 브라우저 375/768/1280px을 확인한다. 테스트 서버가 새로 시작되면 종료한다.
- 결과/스크린샷: `docs/result/20261117/sales-order-common-codes/`.

## 데이터베이스 확인 근거

- 기본 `s-erp-postgresql-readonly`: `list_tables`에서 공통코드·수주 테이블을 확인했다.
- `describe_table`: `tb_common_code_group`, `tb_common_code_item`, `tb_sales_order_hd`, `tb_sales_order_dt`의 현재 컬럼을 확인했다. `tb_sales_order_hd.status`는 문자열이며 현행 CHECK 허용값은 저장소 스키마 이력과 DDL에서 확인했다. 상세 납기 컬럼은 nullable, `line_status` 기본값은 `대기`다.
- 그룹 부재 확인은 제안 그룹명에 대한 단일 aggregate `EXISTS` 결과로만 확인했다. 행별 tenant 데이터는 조회하거나 기록하지 않았다.

## 제외

- DB 변경 적용, backend Java/Mapper/API 변경, 상태 전이 기능, 화면 재설계.
- 현재 확인되지 않은 배송방법 항목을 추측하여 추가 seed하는 행위. 추가값은 공통코드 관리에서 운영한다.
- 수주현황 status 컬럼을 다시 노출하거나 `status`/`lineStatus` API 필드명을 바꾸는 행위.
