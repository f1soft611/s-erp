# 출하계획 API 전환 상세사양서

**계획:** [출하계획 API 전환 계획](../../plan/20261117/20261117_001_출하계획_API_전환_계획서.md)

## 1. 결정

- 구버전 API 소비자 호환은 사용자 결정에 따라 유지 대상에서 제외한다.
- API 버전 분리는 하지 않는다. 현재 API 주소 `/api/v1/sales/delivery-plans`와 저장소의 현재 계약을 유지한다.
- 배포 대상은 서로 호환되는 현재 프론트엔드·백엔드 빌드로 구성하고 같은 변경 창에서 전환한다.
- 확인 시점 HEAD `45c5669d`는 저장소 기준점일 뿐 실제 운영 artifact가 해당 SHA라는 증거가 아니다. 배포 담당자는 배포할 빌드와 SHA를 확정해야 한다.

## 2. 현재 계약과 소비자

- 등록·수정 요청은 `details` 목록을 사용하고 각 상세에 `salesOrderId`, `salesOrderDetailId`를 전달한다.
- 현황 목록은 계획 헤더 단위가 아닌 계획 상세 행 단위다. AUTO 수주별 단건 조회 경로는 현재 코드에 남아 있으며 MANUAL 사용은 허용하지 않는다.
- 현재 프론트엔드 직접 호출은 `frontend/src/pages/sales/shipment/deliveryplan/services/salesDeliveryPlan.service.ts` 한 곳에서 수행한다. 백엔드 경로는 `SalesDeliveryPlanApiController`에 선언되어 있고 서비스 테스트도 존재한다.
- 검색 결과는 저장소 내 호출자만 설명한다. 운영 중인 외부 클라이언트·브라우저 캐시·장기 열린 탭의 수나 버전은 이 작업에서 확인되지 않았으며, 구버전 유지 보장은 배포 요구사항이 아니다.

## 3. DB 스키마 근거 및 제한

- 기본 `s-erp-postgresql-readonly` MCP의 현재 메타데이터에서 `tb_sales_delivery_plan_hd`에는 `sales_order_id`가 없고, `(sales_delivery_plan_id, tenant_id)` 고유키가 있다.
- `tb_sales_delivery_plan_dt`는 `sales_order_id`, `sales_order_detail_id`를 필수로 보유하고 헤더 복합 FK와 원 수주상세 복합 FK를 가진다. 확인한 구조는 `20261112_009` 다중수주 변경의 목표 형태와 일치한다.
- 이 결과는 해당 세션의 기본 MCP 연결 DB에 대한 현재 구조일 뿐, 운영 대상 DB의 식별·마이그레이션 이력 또는 운영 앱 버전을 증명하지 않는다.
- 배포 직전 운영 대상 DB의 테이블 컬럼·제약을 확인한다. 현재 형태면 009 전방 스크립트를 다시 적용하지 않는다. 구 형태라면 백업, 선행 스키마와 제약 검증, 운영 승인 후 적용 여부를 결정한다.

## 4. 배포 순서

1. 배포 담당자가 대상 환경, 배포할 백엔드·프론트엔드 artifact와 SHA, 대상 DB를 기록한다.
2. 운영 DB가 현재 상세 사양과 일치하는지 확인한다. 009 스크립트가 아직 적용되지 않은 구 스키마라면 승인된 점검 시간, 백업 및 선행조건 확인을 거친 뒤 한 번만 적용한다.
3. 출하계획 쓰기를 일시 중지하고 진행 중 요청을 배출한다. 구 스키마 DB에 구버전 백엔드를 남겨 둔 채 스키마를 바꾸거나, 현재 프론트와 구버전 백엔드를 혼합하지 않는다.
4. 현재 계약에 맞는 백엔드와 프론트엔드를 같은 배포 변경으로 전환한다. 브라우저 정적 자산 캐시를 갱신하고 사용자가 열린 화면을 새로고침하도록 한다.
5. 합성 데이터로 MANUAL 다중수주 계획 등록·수정, 계획 상세별 현황, AUTO 수주별 조회, 납품 생성 시 계획 상세 연결을 확인한다.
6. API 오류와 DB 제약 위반을 점검하고 통과 후 쓰기를 재개한다. 실패하면 쓰기를 계속 차단하고 원인을 복구한다.

## 5. 롤백 및 중단 기준

- 새 스키마에서 구버전 백엔드를 실행하지 않는다. 구버전 SQL은 제거된 헤더 `sales_order_id`를 참조할 수 있다.
- 애플리케이션 문제 발생 시 DB 상태와 생성된 데이터를 먼저 보존한다. 호환성이 확인되지 않은 이전 artifact를 자동 재배포하지 않고, 원칙적으로 현재 스키마를 유지한 채 수정 빌드로 복구한다.
- 스키마 롤백은 `20261112_009_rollback_multi_order_sales_delivery_plan.sql`의 가드를 통과하고 운영 승인·백업이 있을 때만 별도 결정한다. 빈 계획, 다중수주 계획 또는 한 수주를 공유하는 복수 계획이 있으면 롤백을 중단한다.
- 대상 DB, 적용 상태, 배포 artifact SHA 중 하나라도 확인되지 않으면 배포를 시작하지 않는다.

## 6. 검증 범위

- 문서/코드 계약 대조 및 DB 메타데이터 확인을 기록한다.
- 본 작업에서는 코드·화면·DB를 변경하지 않으므로 애플리케이션 테스트, 브라우저 검증, 스크린샷은 적용하지 않는다.
- 운영 배포 후 검증은 위 5단계의 합성 데이터 시나리오를 사용하며 실제 업무 데이터를 테스트에 복사하지 않는다.
