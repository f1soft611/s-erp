## API 계약

- 경로: `POST /api/v1/groupware/approvals/{electronicApprovalId}/references`
- 인증: 기존 전자결재 인증 principal `LoginVO`를 사용한다.
- 요청 JSON:

  ```json
  {
    "participantUserIds": ["42", "73"]
  }
  ```

- 요청 DTO는 `participantUserIds`만 받는다. 요청자가 보낸 tenant, 행위자 ID/이름, 참조자 이름, 결재 단계/순서 및 시각은 신뢰하지 않는다.
- 빈 목록, 빈 ID, 중복 요청 ID는 `400`으로 거부한다. 현재 이미 문서에 참여 중인 사용자 ID는 신규 참여자로 추가하지 않으며 기존 상태를 보존한다.
- 응답은 기존 `ResultVO` envelope를 사용하며 성공 시 `item`은 `{ "electronicApprovalId": number, "addedCount": number }`, `message`는 `참조자를 추가했습니다.`이다. 선택 대상이 모두 이미 참여 중이면 `addedCount`는 `0`이고 이력은 생성하지 않는다.
- 잘못된/없는 문서 ID는 `400`/기존 비공개 문서 `404`, 접근 불가·삭제 문서는 기존 관련 문서 권한 검증의 `404`, `DRAFT`는 `409`로 거부한다. 활성 사용자 조회에서 누락된 대상이 하나라도 있으면 요청 전체를 `400`으로 거부한다.

## 서버 검증 및 저장 규칙

1. 인증 principal을 검증하고 `DocumentApprovalAccessService.requireRelatedDocument`로 요청자가 문서 열람 권한을 갖는지 확인한다.
2. 인증 사용자의 tenant 범위로 `selectDocumentApprovalForUpdate`를 실행해 삭제되지 않은 문서를 잠그고, 상태가 `DRAFT`가 아니어야 한다.
3. `selectActiveParticipants`로 요청의 모든 ID를 동일 tenant 내 활성 사용자 및 활성 로그인 계정에서 조회한다. 요청 전체 대상이 조회되지 않으면 어떤 쓰기도 하지 않고 실패한다.
4. `selectApprovalLines` 결과에서 이미 참여하는 사용자 ID를 찾는다. 기존 사용자는 그대로 유지하고 새 사용자만 추가한다. 신규 대상이 없으면 성공 0건을 반환하며 SYSTEM 이력을 생성하지 않는다.
5. 새 `REFERENCE` 행은 기존 참조자의 stage를 이어 사용한다. 참조자가 아직 없다면 가장 큰 승인/합의 stage 바로 다음 stage를 사용한다. `participant_order`는 그 참조 stage에서 현재 가장 큰 순서 다음부터 부여한다.
6. 이름/부서는 활성 사용자 조회 결과를 사용한다. `action_status`, `pending_at`, `action_at`, `action_comment`는 모두 NULL이다. 각 insert 건수가 1이 아니면 예외 처리한다.
7. 모든 신규 참여자를 삽입한 뒤 한 건의 SYSTEM 이벤트를 기록한다. `event_type`은 `REFERENCE_ADDED`; content는 행위자와 실제 신규 참조자 이름을 식별할 수 있어야 한다. 공통 `insertSystemEvent`가 인증 principal의 행위자/생성 시각을 기록한다.
8. 삽입과 SYSTEM 이력은 하나의 `@Transactional(rollbackFor = Exception.class)` 작업이어야 한다. 참여자 또는 이력 저장 오류가 발생하면 실패를 반환하고 전체를 롤백한다.

## DB 확인 결과와 변경

- 기본 `s-erp-postgresql-readonly`에서 `list_tables`를 실행하고 `tb_electronic_approval_main`, `tb_electronic_approval_line_info`, `tb_common_comment`, `tb_user`, `tb_login_account`의 메타데이터를 조회했다. 행 데이터는 조회하지 않았다.
- `tb_electronic_approval_line_info`의 `uq_electronic_approval_line_participant`는 `(tenant_id, electronic_approval_id, participant_user_id)`를 유일하게 제한한다. `uq_electronic_approval_line_position`은 문서 내 `(stage_order, participant_order)`를 유일하게 제한한다. 참조 상태 CHECK는 미확인 시 모든 action 필드를 NULL로, 확인 시 `CONFIRMED` 및 `action_at` 존재를 허용한다.
- `tb_common_comment.chk_tb_common_comment_event_type`는 SYSTEM event 목록에 `REFERENCE_CONFIRMED`는 포함하지만 `REFERENCE_ADDED`는 포함하지 않는다. 날짜별 migration에서 허용 목록을 확장하고 역변경 SQL을 함께 둔다. 실제 DB에는 적용하지 않는다.
- 같은 기존 SQL 계약에서 `selectActiveParticipants`는 tenant 및 활성 `tb_user`/`tb_login_account`를 제한한다. `selectIsDocumentParticipant`의 `documentReadAccess`는 기안자 또는 결재 참여자를 통해 읽기 권한을 확인한다. `selectDocumentApprovalForUpdate`는 tenant 및 삭제 여부를 제한하고 문서 row를 잠근다.
- INSERT는 기존 `insertDocumentApprovalLine`을 재사용하고, 시스템 이력은 `DocumentApprovalDraftSupportService.insertSystemEvent`를 재사용한다. 별도 참여자/ACL 테이블이나 컬럼은 만들지 않는다.

## 프론트엔드 및 메뉴 동작

- 문서 상세의 기존 더보기 메뉴에 `참조자 추가하기`를 추가한다.
- 메뉴 순서는 `문서 공유하기`, `참조자 추가하기`, 조건부 구분선, 기존 `문서 수정`/`수정 후 재상신`, `삭제`다. 수정/삭제 권한 및 상태 조건은 기존 그대로 둔다. 양 그룹 중 관리 메뉴가 모두 숨겨진 경우 구분선을 렌더링하지 않는다.
- 메뉴 항목을 선택하면 먼저 메뉴를 닫은 후 작업을 시작한다.
- 선택 다이얼로그는 기존 `UserSelectEditor` 다중 선택 UX를 재사용한다. 현재 결재선 참여자는 선택 대상에서 제외한다.
- 성공 시 참조자와 SYSTEM 타임라인을 다시 조회하고 문서 목록/페이지 갱신을 트리거한다. `addedCount=0`인 경우 사용자에게 중복 제외를 성공으로 오인시키지 않는다. API 실패 시 다이얼로그를 유지하고 오류를 표시한다.
- 사용자 옵션은 문서 상세에서 이미 사용하는 활성 `fetchDraftFormUsers` 경로를 재사용하며 동일 목록을 중복 요청하지 않는다.
- `REFERENCE_ADDED`는 기존 SYSTEM 타임라인 표현을 사용하고 서버 event content를 가공/대체하지 않는다.

## 회귀 검증

- 백엔드: 요청자 인증/열람 권한/문서 상태/삭제 상태, 빈·중복 요청, 없는·비활성·타 tenant 대상, 기존 참여자 보존, 미확인 신규 참조, SYSTEM 이력 생성, 이력 실패 시 트랜잭션 오류를 검증한다.
- 프론트엔드: endpoint/body/envelope 검증, 메뉴 순서/조건부 divider/callback 순서, 기존 참여자 제외, 요청 실패 메시지와 재선택 가능 상태, 성공 후 상세 및 타임라인 refresh를 검증한다.
- 통합: 새 참조자는 기존 참여자 조회 및 미확인 참조 목록에서 해당 문서를 즉시 볼 수 있고 기존 결재 상태/단계/대기 건수/참조 확인 상태가 변하지 않아야 한다.
- 브라우저: 합성 데이터로 375px, 768px, 1280px 확인 및 스크린샷 저장. 실행 가능하지 않은 검증은 결과 문서에서 사유와 함께 구분한다.

## 승인된 후속 수정 사양

- 문서현황 상세에서 참조자를 추가하면 목록 재조회 및 상세 재조회는 수행하되, 상세 패널은 계속 열린 상태로 유지한다.
- 검색 조건 변경으로 새 목록 조회가 시작되면 기존 상세 패널은 닫는다. 재시도/데이터 갱신과 검색 조건 변경은 서로 다른 동작으로 취급한다.
- `REFERENCE_ADDED` SYSTEM 이벤트 내용은 `행위자님이 참조자(이름1, 이름2)를 추가했습니다.` 형식이며, 괄호 안 이름은 해당 요청으로 실제 저장된 신규 참조자만 쉼표로 구분한다.
- 검증은 문서현황 통합 테스트의 상세 유지 assertion 및 백엔드 서비스 테스트의 정확한 이벤트 content assertion으로 수행한다. 데이터베이스 구조/API 계약은 변경하지 않는다.
- 참조 추가 성공 후 목록/상세/타임라인 갱신은 기존 화면 데이터를 유지한 조용한 백그라운드 조회로 처리한다. 목록 그리드의 전체 로딩 표시, 상세 초기 로딩 화면, 타임라인 로딩 표시는 새로 띄우지 않는다. 재조회 실패 시에는 stale 데이터를 지우지 않고 기존 페이지/상세/타임라인 오류 UI를 통해 실패를 알린다. 참조 추가 성공 토스트는 그대로 표시한다.
- 조용한 갱신은 참조 추가 성공 경로에만 적용하고, 사용자가 검색 조건을 바꾸거나 명시적으로 재시도하는 조회는 기존 로딩 표시를 유지한다.
