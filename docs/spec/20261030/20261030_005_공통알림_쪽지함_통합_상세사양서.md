# 공통 알림·쪽지함 통합 상세사양서

기준: [작업지시서](../../directions/20261030/20261030_005_공통알림_쪽지함_통합_작업지시서.md), [승인 설계](../../superpowers/specs/2026-10-30-unified-notifications-design.md)

## 1. 도메인 분리

### 공통 알림

- 이벤트 발생원은 `APPROVAL_COMMENT_MENTION` 또는 `DIRECT_MESSAGE_RECEIVED`다.
- 각 이벤트는 수신자별 알림 레코드로 저장되어 읽음 상태가 수신자마다 독립된다.
- 필드 계약: `notificationId`, `eventType`, `sourceType`, `sourceId`, nullable `targetId`, `title`, `summary`, `createdAt`, nullable `readAt`.
- 댓글 알림의 `sourceId`는 댓글 ID, `targetId`는 문서 ID다. 쪽지 알림의 `sourceId`는 메시지 ID이며 `targetId`는 null, 대화 ID는 메시지에서 조회한다.
- 사용자/tenant ID와 원본 이동 URL을 요청에서 신뢰하지 않는다. 응답은 타입화된 source 정보로 이동을 구성한다.

### 쪽지 대화와 메시지

- 하나의 대화는 같은 tenant의 서로 다른 두 명을 참여자로 가진다.
- 대화에는 선택 제목(최대 120자), 생성시각 및 마지막 메시지 시각이 있다.
- 메시지는 대화 ID, 발신자 ID, 수신자 ID, 일반 텍스트 본문(1~5,000자), 생성시각과 nullable `readAt`을 가진다.
- 새 쪽지 작성은 대화와 첫 메시지를 생성한다. 답장은 기존 대화에 메시지를 추가하고 상대방을 수신자로 지정한다.
- 참여자는 대화 생성 시 정해진 두 사용자로 고정하며, 참가자 추가/변경은 지원하지 않는다.
- 메시지 단위 삭제, 보관, 전달, 첨부, 임시저장, 그룹 쪽지는 제공하지 않는다. 대화방 단위 삭제는 본인에게만 숨기는 방식으로 제공한다(5장 "대화방 삭제" 참고).

## 2. DB 스키마

### `tb_notification`

수신자별 이벤트 알림을 저장한다.

| 컬럼 | 타입/규칙 | 설명 |
|---|---|---|
| notification_id | BIGSERIAL PK | 알림 ID |
| tenant_id | BIGINT NOT NULL, tenant FK | 테넌트 |
| recipient_user_id | BIGINT NOT NULL, user FK | 알림 수신 사용자 |
| event_type | VARCHAR(40) NOT NULL | `APPROVAL_COMMENT_MENTION`, `DIRECT_MESSAGE_RECEIVED` |
| source_type | VARCHAR(30) NOT NULL | `APPROVAL_COMMENT`, `DIRECT_MESSAGE` |
| source_id | BIGINT NOT NULL | 댓글 또는 메시지 ID |
| title | VARCHAR(200) NOT NULL | 목록 제목 |
| summary | VARCHAR(500) NOT NULL | 최소 정보 알림 요약 |
| read_at | TIMESTAMP NULL | 읽음 시각 |
| created_at | TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP | 생성 시각 |

- unique: `(tenant_id, recipient_user_id, event_type, source_type, source_id)`로 재시도 중복을 방지한다.
- index: `(tenant_id, recipient_user_id, read_at, created_at DESC, notification_id DESC)`.
- 원본은 polymorphic이므로 source FK는 만들지 않는다. 읽음/이동 시 해당 업무 서비스가 source 접근을 재검증한다.

### `tb_direct_message_thread`

| 컬럼 | 타입/규칙 | 설명 |
|---|---|---|
| thread_id | BIGSERIAL PK | 대화 ID |
| tenant_id | BIGINT NOT NULL, tenant FK | 테넌트 |
| participant_a_user_id | BIGINT NOT NULL, user FK | 참여자 A |
| participant_b_user_id | BIGINT NOT NULL, user FK | 참여자 B |
| subject | VARCHAR(120) NULL | 대화 제목 |
| created_at | TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP | 생성 시각 |
| updated_at | TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP | 마지막 메시지 시각 |

- `participant_a_user_id < participant_b_user_id` 및 두 참여자 상이 조건을 둔다.
- unique `(tenant_id, thread_id)`는 메시지의 tenant 복합 FK 대상이다.
- index는 tenant와 참여자별 updated_at 내림차순 목록 조회를 지원한다.
- 개별 사용자는 여러 대화를 같은 상대와 만들 수 있다.

### `tb_direct_message`

| 컬럼 | 타입/규칙 | 설명 |
|---|---|---|
| message_id | BIGSERIAL PK | 메시지 ID |
| tenant_id | BIGINT NOT NULL | 테넌트 |
| thread_id | BIGINT NOT NULL | 소속 대화 |
| sender_user_id | BIGINT NOT NULL, user FK | 발신자 |
| recipient_user_id | BIGINT NOT NULL, user FK | 단일 수신자 |
| content | TEXT NOT NULL | 일반 텍스트 본문 |
| created_at | TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP | 발송 시각 |
| read_at | TIMESTAMP NULL | 수신자 읽음 시각 |

- `(tenant_id, thread_id)`는 `tb_direct_message_thread`의 동일 tenant 대화에 FK로 연결한다.
- 발신자와 수신자는 서로 달라야 한다. 같은 대화의 두 참여자 중 한 명이 발신자, 다른 한 명이 수신자인지는 서비스에서 검증한다.
- index: `(tenant_id, thread_id, created_at, message_id)`, `(tenant_id, recipient_user_id, read_at, created_at DESC)`, `(tenant_id, sender_user_id, created_at DESC)`.

### 인덱스 및 동시성

- 알림·메시지 쪽지함 목록은 cursor/페이지 단위로 조회하고 사용자/tenant 필터가 선행되도록 인덱스를 사용한다.
- 동일 메시지 발송을 재시도할 때는 요청 idempotency key 대신 DB 트랜잭션과 message_id 기반 알림 unique 제약을 사용한다. 클라이언트가 네트워크 타임아웃 뒤 새 POST를 다시 보내면 새 쪽지로 취급되므로 클라이언트 중복 제출을 막는다.
- 대화의 updated_at 갱신과 메시지/알림 추가는 한 트랜잭션으로 수행한다.

## 3. API 계약

모든 API는 로그인 principal에서 tenant/login identity를 해석하고 user ID를 DB에서 확인한다. 아래 path는 신규 계약이다.

### 공통 알림

| Method / path | 요청/응답 |
|---|---|
| `GET /api/v1/groupware/notifications/summary` | `{ unreadCount }` |
| `GET /api/v1/groupware/notifications?limit=20&beforeNotificationId=&unreadOnly=false` | `{ resultList, hasNext, nextBeforeNotificationId }` |
| `PUT /api/v1/groupware/notifications/{notificationId}/read` | 현재 사용자 소유 알림을 읽음 처리하고 최신 알림을 반환 |

- 목록은 최신순 `(created_at DESC, notification_id DESC)`이며 limit는 1~50 범위로 제한한다.
- 동일 읽음 요청은 성공적으로 반복 가능하되 다른 사용자의 알림 ID는 404 처리한다.
- 읽음 API는 쪽지 읽음 상태를 변경하지 않는다.

### 1:1 쪽지

| Method / path | 요청/응답 |
|---|---|
| `GET /api/v1/groupware/messages/summary` | `{ unreadCount }` |
| `GET /api/v1/groupware/messages/threads?folder=ALL\|INBOX\|SENT&limit=20&beforeUpdatedAt=&beforeThreadId=` | 대화 요약 페이지와 전체 건수 (folder 생략 시 `ALL`) |
| `POST /api/v1/groupware/messages/threads` | `{ recipientUserId, subject?, content }`; 생성된 대화 및 첫 메시지 반환 |
| `GET /api/v1/groupware/messages/threads/{threadId}?beforeDate=YYYY-MM-DD` | 참여자 확인 후 하루치 메시지 페이지 `{ resultList, messageDate, hasPrevious }` 반환 |
| `POST /api/v1/groupware/messages/threads/{threadId}/read` | 해당 참여자의 받은 미읽음 메시지 및 연결된 새 쪽지 알림을 함께 읽음 처리 |
| `DELETE /api/v1/groupware/messages/threads/{threadId}` | 현재 사용자에게만 대화방을 숨긴다(`participant_a/b_hidden_at` = 현재 시각). 받은 미읽음 메시지·새 쪽지 알림도 함께 읽음 처리. 비참여자/타 tenant는 404. 메시지 row는 삭제하지 않음 |
| `POST /api/v1/groupware/messages/threads/{threadId}/messages` | `{ content }`; 참여자 두 사람 사이 답장 생성 및 수신자 알림 반환 |

- `ALL`(기본): 현재 사용자가 참여자 A/B 중 하나인 모든 대화. 쪽지함 화면은 `ALL`만 사용한다.
- `INBOX`: 현재 사용자가 recipient인 메시지가 하나 이상 존재하는 대화(API 호환용).
- `SENT`: 현재 사용자가 sender인 메시지가 하나 이상 존재하는 대화(API 호환용).
- 대화 요약의 마지막 메시지와 unread count는 해당 사용자 기준으로 계산한다.
- 대화 메시지 GET은 하루 단위로 페이지한다. `beforeDate`가 없으면 메시지가 있는 가장 최근 날짜(활동 중이면 당일)를, 있으면 `beforeDate` 이전 중 가장 최근 날짜를 반환한다. `messageDate`는 반환한 날짜(메시지가 없으면 `null`), `hasPrevious`는 그 날짜 이전 메시지 존재 여부다. 날짜 경계는 DB `created_at`(timezone 없는 local timestamp)의 `[day 00:00, day+1 00:00)`이다.
- 대화 진입 GET은 side effect가 없다. 프런트엔드는 GET 성공 후 read endpoint를 호출한다.
- 상대 읽음 상태는 발신 메시지의 `readAt`으로 표시한다.
- 대화 조회, 읽음, 답장은 현재 사용자 principal이 참여자 A/B 중 하나인지 검증한다.

### 댓글 멘션

- 기존 `POST /api/v1/groupware/approvals/{electronicApprovalId}/comments`에 `mentionedUserIds: number[]`와 `mentionAll: boolean`을 추가한다.
- 기존 content/parentCommentId 계약은 유지한다.
- 멘션 수신자 ID는 현재 tenant의 활성 사용자 및 활성 계정, 해당 문서 접근 권한을 검사한다. `mentionAll=true`이면 문서 접근 대상자 집합을 서버에서 계산하며 요청 ID 목록만으로 수신자를 정하지 않는다.
- `mentionAll`과 명시적 사용자가 겹치거나 중복 ID가 있으면 하나의 알림만 만든다. 작성자는 제외한다.
- 댓글 최초 저장과 멘션 알림 생성은 동일한 `@Transactional` 처리다. 수정 API에서는 멘션 재발행을 하지 않는다.
- `GET /api/v1/groupware/approvals/{electronicApprovalId}/comments/mention-users` → `{ resultList: number[] }`: 문서 접근 대상자(기안자 + DRAFT가 아니면 결재/참조 라인 참여자) 중 작성자를 제외한 사용자 ID. 문서 접근 권한이 없으면 404다. 프런트엔드는 멘션 후보를 이 목록으로 제한한다.
- 저장 시 프런트엔드는 편집기 본문에 `@이름`/`@ALL` 토큰이 실제로 남아 있는 선택만 전송한다(삭제된 멘션의 stale ID 제외).

## 4. 쪽지와 알림 상태 전이

| 사용자 동작 | 쪽지 read_at | 알림 read_at |
|---|---|---|
| 쪽지 도착 | NULL 유지 | 새 `DIRECT_MESSAGE_RECEIVED` 행 생성 |
| 알림 팝오버 열기 | 변화 없음 | 변화 없음 |
| 공통 알림 선택 | 변화 없음 | 선택한 알림 read_at 기록 |
| 쪽지 대화 열기 및 읽음 호출 | 현재 사용자의 받은 메시지 read_at 기록 | 해당 대화의 해당 수신자 `DIRECT_MESSAGE_RECEIVED` 알림 read_at 기록 |
| 상대가 내 쪽지를 읽음 | 상대 메시지 read_at은 상대만 기록 | 발신자 알림 생성 없음 |

알림을 먼저 읽은 뒤 쪽지를 나중에 열거나, 쪽지함에서 대화를 직접 열어도 최종 상태는 동일해야 한다. 메시지 읽음과 연결 알림 읽음은 한 트랜잭션이다.

## 5. 화면 사양

### 헤더

- 기존 알림 아이콘에 최근 5개 팝오버, 미읽음 뱃지(최대 표기 `99+`), 알림함 더보기를 제공한다.
- 별도의 쪽지 아이콘은 받은 미읽음 개수를 보여 주고 쪽지함으로 이동한다.
- 두 개수는 다른 API와 다른 상태에서 산출한다.
- 카운터 뱃지는 공통 `headerCounterBadgeSx`로 높이·최소폭 16px, 글자 10px의 작은 크기로 표시한다.
- 375px 너비에서도 프로필/검색/테마 컨트롤과 겹치지 않게 아이콘 간격과 팝오버 너비를 조정한다.

### 공통 알림함

- 전체/미읽음 전환, cursor 페이지, 발생시각/읽음 상태/제목/요약을 제공한다.
- 댓글 멘션은 문서 상세로, 쪽지 도착은 쪽지 대화로 이동한다.
- 팝오버를 열기만 한 경우 읽음 처리하지 않는다.
- 읽음 API가 실패하면 항목은 미읽음 상태를 유지하고 오류를 표시한다. 알림 선택은 탐색을 계속 허용한다.

### 쪽지함

- 받은함/보낸함 구분 없이 대화 상대별 단일 대화 목록(카카오톡 채팅 목록형), 사용자 검색 선택기, 제목(선택), 본문 입력, 대화 메시지 목록과 답장 입력을 제공한다.
- 대화는 생성시각 오름차순으로 표시한다. 수신 메시지의 미읽음 강조는 서버 상태를 사용한다.
- 목록은 상대가 보낸 읽지 않은 메시지 수를 강조하고, 대화 내 내가 보낸 메시지는 상대 읽음 상태(`1`)를 보여 준다.
- 쪽지 본문은 React text node로 표시하며 `dangerouslySetInnerHTML`을 사용하지 않는다.
- 반응형 검증은 375px, 768px, 1280px에서 수행한다. 모바일 목록→상세 전환은 페이지 내 패널 전환을 사용한다.
- 새 쪽지 작성은 공통 `CommonDialog`(xs, 모바일 전체 화면)를 사용하고 하단 버튼은 `보내기`(주 버튼) → `취소` 순서로 배치한다.

### 알림함·쪽지함 공통 디자인

- 두 페이지는 `groupware/shared/components/InboxPageLayout`의 공통 셸(제목/설명/우측 액션), 필터 토글(알림: 전체/읽지 않음; 쪽지함은 단일 목록으로 토글 없음), 외곽선 패널, 목록 항목을 사용한다.
- 목록 항목은 미읽음 점 표시·굵은 제목·배경 강조, 요약 1줄 말줄임, `YYYY. MM. DD. 오전/오후 HH:mm` 형식 일시를 동일하게 표시한다. 쪽지는 미읽음 개수 뱃지를 추가 표시한다.

### 후속 요청: 쪽지 대화 스크롤/전송 영역

- 쪽지함은 대시보드 콘텐츠 영역의 전체 가용 높이를 사용하며, 메시지 수와 무관하게 페이지 자체의 세로 스크롤이 생기지 않도록 한다.
- 데스크톱에서 좌측 대화 목록은 좌측 패널 내부에서 스크롤한다. 우측 채팅 패널은 가용 높이에 고정하고, 대화 헤더 및 답장 작성/전송 폼은 스크롤 밖에 둔다.
- 우측 메시지 내역만 내부 스크롤을 사용한다. 메시지가 많아도 답장 입력과 전송 버튼은 계속 보이고 사용할 수 있어야 한다.
- 모바일의 기존 목록↔상세 화면 전환은 유지한다. 각 화면은 가용 높이를 채우며, 선택된 상세 안에서는 메시지 내역만 스크롤한다.
- 검증은 선택된 대화의 panel height/minHeight/overflow, 메시지 내부 스크롤 및 전송 폼 고정 레이아웃을 확인하고 375/768/1280px 브라우저에서 페이지 가로·세로 넘침과 버튼 접근성을 확인한다.

### 후속 요청: 메신저형 쪽지 UI

- **대화 목록(`MessageThreadListItem`)**: 프로필(사진이 있으면 사진, 없거나 로드 실패 시 이름 첫 글자 `ProfileAvatar`), 굵은 상대 이름, 최근 내용 2줄 말줄임, 우측 상단 축약 시각(오늘 `오전/오후 h:mm`, 어제 `어제`, 올해 `M월 D일`, 그 외 `YYYY. MM. DD.`), 미읽음 개수 원형 뱃지(`99+` 상한)를 표시한다.
- **대화 내역(`MessageChatView`)**: 내가 보낸 메시지(`senderUserId !== thread.otherUserId`)는 우측, 받은 메시지는 좌측에 상대 프로필/이름과 함께 표시한다. 같은 발신자·같은 분·같은 날짜의 연속 메시지는 한 그룹으로 묶어 프로필/이름은 첫 메시지에만, 시각은 그룹 마지막 메시지에만 표시한다. 상대가 읽지 않은 내 메시지에는 `1`을 표시한다. 날짜가 바뀌면 날짜 구분선을 표시하고, 대화를 열거나 메시지가 추가되면 맨 아래로 스크롤한다.
- **색상**: 카카오톡 색상을 따르지 않고 S-ERP 테마를 사용한다. 대화 배경은 `primary.main` 저농도 alpha, 보낸 말풍선은 `primary.main`/`primary.contrastText`, 받은 말풍선은 `background.paper`와 옅은 테두리, 전송 버튼은 기본 primary contained 버튼이다.
- **답장 입력**: 문서 댓글 입력과 같은 테두리 박스 구조로 상단 여러 줄 입력(`메시지 입력`, 최대 5,000자), 하단 우측 `전송` 버튼을 배치한다. Enter는 전송, Shift+Enter는 줄바꿈이며 한글 조합 중 Enter는 전송하지 않는다. 첨부 등 좌측 도구는 아직 지원하지 않는다.
- **조용한 로딩**: 답장 전송 후 목록·메시지 재조회는 로딩 표시를 바꾸지 않는 silent 모드로 수행한다. 새 쪽지 전송 후에는 전체 대화 목록과 대화를 미리 함께 조회한 뒤 한 번에 전환해 빈 화면/스피너 깜빡임이 없도록 한다.
- **프로필 사진 API**: `GET` 대화 목록 응답의 각 대화에 `otherUserProfileImage`(nullable 문자열)를 추가한다. 서버는 상대 사용자 `tb_user`의 `tenant_id`, `login_id`로 `tb_login_account.profile_image`를 LEFT JOIN한다. 스키마 변경은 없다.

### 후속 요청: 대화 일자별 페이징·헤더 프로필·쪽지함 통합

- **일자별 페이징**: 대화를 열면 가장 최근 메시지 날짜(당일) 하루치만 조회한다. 메시지 영역을 상단(48px 이내)까지 올리면 `beforeDate=현재 가장 오래된 날짜`로 이전 하루치를 조회해 앞에 붙이고, 기존에 보던 메시지 위치가 유지되도록 `scrollTop`을 높이 증가분만큼 보정한다(맨 아래로 이동하지 않음). 조회 중에는 상단에 높이를 차지하지 않는 작은 스피너만 표시하고 중복 요청을 막는다. `hasPrevious=false`이면 더 조회하지 않는다. 하루치가 짧아 스크롤이 생기지 않으면 화면이 찰 때까지 이전 날짜를 자동 조회한다.
- 답장 후에는 최신 날짜 페이지만 다시 조회해 이미 불러온 이전 날짜 메시지와 병합한다.
- **헤더 프로필**: 대화 상세 헤더의 상대 이름 왼쪽에 `ProfileAvatar`(40px, 사진 있으면 사진, 없거나 로드 실패 시 이니셜)를 표시한다.
- **받은함/보낸함 통합**: 1:1 대화는 이미 양방향 메시지를 한 대화에 담으므로 화면 토글을 제거하고 `folder=ALL` 단일 목록(최근 활동순)으로 표시한다.

### 후속 요청: 댓글 멘션 필터·강조

- `@` 입력 시 표시되는 후보 목록은 편집기 포커스를 빼앗지 않는 `listbox`(Popper)로 표시하여 `@관리`처럼 이어서 입력하면 이름·부서 기준으로 즉시 필터한다(접두 일치 우선). `@ALL`은 검색어가 없거나 `all`/`전체`의 접두일 때만 표시한다.
- 키보드: ↑/↓ 이동, Enter/Tab 선택, Esc 닫기. 편집기 포커스가 벗어나면 목록을 닫는다.
- 저장된 댓글의 `@사용자`/`@ALL`은 primary 계열 배경·굵은 글자 `.comment-mention`으로 강조 표시한다.
- 댓글 멘션 알림 링크는 실제 메뉴 경로 `/groupware/doc/write?approvalId={targetId}`로 이동한다.

### 후속 요청: 대화방 삭제(본인에게만 숨김)

- **삭제 방법**: 대화 상세 헤더 우측 `대화방 삭제` 아이콘 버튼 → 공통 다이얼로그 확인(`삭제`, `취소`) → `DELETE /messages/threads/{threadId}`. 성공 시 목록에서 제거하고 선택을 해제하며 헤더 쪽지 카운터를 갱신(`s-erp:message-read` 이벤트)한다. 실패 시 오류 알림을 표시하고 목록을 유지한다.
- **범위**: 본인 쪽 `*_hidden_at`에만 현재 시각을 기록한다. 상대방 목록·메시지에는 영향이 없고 메시지 row는 물리 삭제하지 않는다(DB `20261030_009`).
- **재활성화**: 숨김 시각 이후 메시지가 생기면(상대방이 새 쪽지를 보내거나 본인이 같은 대화에 보내면) 목록에 다시 나타난다. 이때 숨긴 사용자에게는 숨김 시각 이후 메시지만 표시하고(카카오톡 나가기 후 재초대와 유사), 이전 날짜 페이징도 숨김 시각 이전은 조회하지 않는다.
- 숨긴 대화의 이전 메시지에 연결된 알림 링크(`/messages/{messageId}/thread`)는 404로 처리한다.
- 새 쪽지 작성은 기존처럼 매번 새 대화를 만든다(같은 상대와의 기존 대화 재사용은 미적용).

### 후속 요청: 새 쪽지 받는 사람 검색·프로필

- `받는 사람`은 검색 가능한 Autocomplete(`MessageRecipientSelect`)로 표시한다. 이름 또는 부서로 필터하며 이름 접두 일치 → 이름 포함 → 부서 포함 순으로 정렬한다. 결과가 없으면 "검색 결과가 없습니다."를 표시한다.
- 각 후보와 선택된 값 앞에 `ProfileAvatar`(28px)를 표시한다. 사진(`/api/v1/co/workflow/forms/users`의 `profileImage`)이 있으면 사진, 없거나 로드 실패 시 이름 첫 글자를 표시한다. 후보 하단에는 부서명을 표시한다.
- API/스키마 변경은 없다.

### 후속 요청: 화면 복귀 시 대화방 조용한 갱신

- 쪽지함에서 다른 탭·창으로 갔다가 돌아오면(`document` `visibilitychange`가 visible일 때, window `focus`) 헤더 알림·쪽지 배지처럼 스피너 없이 갱신한다.
- 대화 목록(`folder=ALL`)을 다시 조회하고, 열린 대화가 목록에 있으면 최신 일자 페이지를 기존 메시지와 병합한다(이미 불러온 이전 일자·스크롤 유지, 중복 제거).
- 열린 대화에 안 읽은 쪽지가 있으면 읽음 처리 후 `s-erp:message-read` 이벤트로 헤더 배지를 갱신한다.
- 동시 갱신은 1건으로 제한하고 실패는 조용히 무시한다. 실시간 푸시/폴링이 아니라 화면 복귀 시점 갱신이며 API/스키마 변경은 없다.

### 후속 요청: 채팅방 문서·공지 공유 링크와 OG 미리보기

- 쪽지 본문(평문)의 `http(s)` URL을 말풍선 안에서 링크로 표시한다. 같은 출처(S-ERP) 링크는 라우터 이동, 외부 링크는 새 탭(`noopener noreferrer`)으로 연다. 본문은 계속 평문으로 렌더링하며 HTML은 해석하지 않는다.
- 말풍선 아래에 기존 피드 공용 `FeedLinkPreviews`(`DocumentLinkPreviews` 재사용, testId `message-link-previews`)로 미리보기 카드를 표시한다.
  - 문서 공유 링크(`/groupware/doc/write?share=…` 또는 `documentId=`): 문서 카드, 클릭 시 문서 상세 패널.
  - 공지 공유 링크(`/groupware/community/notice?share=…`): 공지 카드, 클릭 시 공지 상세 패널.
  - 외부 링크: 기존 링크 미리보기 API의 OG 제목·설명·이미지 카드.
  - 권한이 없거나 삭제된 대상은 "접근할 수 없거나 삭제된 문서/공지입니다."로 표시한다(받는 사람 권한 기준).
- 카드가 늦게 로드되어 높이가 늘어나도 사용자가 하단을 보고 있었다면 하단을 유지한다.
- 공유 링크 생성은 기존 문서·공지의 링크 복사 기능을 사용하며, 첨부/공유 버튼은 미지원이다. API/스키마 변경은 없다.

### 시각 매핑

- 알림/쪽지 VO의 `LocalDateTime` 컬럼은 log4jdbc `ResultSetSpy`가 `getObject(LocalDateTime.class)`를 지원하지 않으므로 `mapper-config.xml`에 등록한 `LocalDateTimeTimestampTypeHandler`(getTimestamp 기반)로 매핑한다.
