# 20261015_016 목록 조회 배치 처리 상세사양서

공지사항 목록 및 전자결재 피드에서 목록 행 단위로 실행되는 추가 조회를 제거하고, 댓글 count 및 페이지 메타데이터를 단건 조회 의미와 동일하게 유지한다.

## 2. 공지 목록 데이터 계약

### 조회 흐름

공지 목록은 기존 목록/전체 건수 SQL을 유지한 다음, 결과 post IDs에 대해 아래 데이터 집합을 batch 조회한다.

- `tb_common_file`: `tenant_id`, `owner_type='NOTICE'`, `owner_id IN postIds`, `deleted_yn='N'`
- `tb_common_comment`: tenant와 owner type/IDs로 최대 최신 3개 최상위 대화와 그 답글 조회. `limit+1`번째 root group은 `hasPrevious` 산출용이며 응답에 포함하지 않는다.
- 최상위 댓글 수: `parent_comment_id IS NULL`, `deleted_yn='N'` 조건으로 기존 단건 count와 동일하게 계산한다.
- 댓글 파일: 화면에 전달할 댓글 IDs 전체를 `owner_type='NOTICE_COMMENT'`로 한 번 조회한다.

### 페이지 응답

- 표시 댓글 수는 답글 수가 아니라 최상위 root group 수를 기준으로 최대 3개다.
- 반환 순서는 단건 페이지 API와 같이 선택된 root group의 시간 순서를 보존하고, 각 group 안에는 답글을 둔다.
- `hasPreviousComments`는 네 번째 pageable root group이 있는 경우 true다.
- `nextBeforeCommentId`는 이전 페이지가 존재할 때 반환 목록의 가장 오래된 root comment ID이고, 그 외에는 null이다.
- `commentCount`는 기존 단건 `countCommonComments`와 동일하게 삭제되지 않은 최상위 댓글 수다.
- 첨부파일은 댓글 ID별로 매핑되며, soft-deleted 댓글에는 첨부파일을 노출하지 않는다.

## 3. 전자결재 피드 데이터 계약

### 조회 흐름

기존 `GET /api/v1/groupware/approvals/documents?includeDetails=true`를 유지한다. 목록에서 조회한 전자결재 IDs를 사용해 각각 다음 batch 조회를 수행한다.

1. 본문 상세: tenant, owner IDs, 기안자 또는 결재 참여자 권한 조건.
2. 결재선: tenant와 electronic approval IDs. 기존 프로필/도장 join 및 단계/참여자 정렬을 보존한다.
3. 문서 첨부: `owner_type='APPROVAL'`, soft-deleted 제외.
4. 시스템 이벤트: `comment_type='SYSTEM'`, soft-deleted 제외.
5. 사용자 댓글: `comment_type='USER'`이고 각 문서의 최신 3개 root group 및 답글.
6. 댓글 수: soft-deleted가 아닌 `comment_type='USER'`, `parent_comment_id IS NULL` row만 문서별 집계.
7. 댓글 첨부: 전체 댓글 IDs를 `owner_type='APPROVAL_COMMENT'`로 묶어 조회.

상세 batch SQL은 기존 단건 상세 SQL의 권한 predicate와 동등해야 한다. 파일/댓글/결재선 조회의 owner IDs는 권한 확인을 통과한 목록 쿼리 결과에서만 가져온다.

### 응답 보존

- `DocumentApprovalFeedItemVO` 필드, 목록 필드 값, 본문/결재선/첨부/시스템 이력/댓글 포함 여부를 유지한다.
- 댓글 카운트는 최상위 사용자 댓글 수이며 답글은 포함하지 않는다.
- 댓글 페이지는 최상위 사용자 댓글 3개 기준으로 `hasPreviousComments`, `nextBeforeCommentId`를 기존 단건 조회 의미와 일치시킨다.
- 삭제된 댓글은 기존 `[삭제된 댓글입니다.]`, `삭제된 댓글`, null writer ID, empty attachments로 표시한다.
- 빈 문서 목록은 빈 결과를 반환하고 owner ID IN query를 발생시키지 않는다.
- 사용자별 뷰 이력/조회수 갱신은 feed 목록 조회에서 실행하지 않는다.

## 4. 호출량 기준

- 공지 목록: 목록 조회 및 전체 건수 이후 관계별 batch SQL 횟수는 페이지 결과 수에 독립적이다. 댓글 파일 조회는 페이지 전체에서 최대 한 번이다.
- 전자결재 feed: 목록 조회 이후 상세/결재선/파일/이벤트/댓글/댓글 수/댓글 파일은 데이터 종류별 batch SQL로 구성한다. 두 번째 문서가 추가되어도 문서별 단건 상세/결재선/댓글 조회가 추가되지 않는다.
- 하나의 거대 join으로 댓글·결재선·파일의 곱집합을 만드는 접근은 사용하지 않는다.

## 5. 보안 및 DB 계약

- 각 배치 SQL은 tenant ID를 필수 조건으로 둔다.
- 상세 batch SQL은 기존 기안자/참여자 제한을 동등하게 적용한다.
- 파일 조회는 owner type과 soft delete 필터를 유지한다.
- DB MCP `list_tables`와 개별 `describe_table`에서 `tb_common_comment`, `tb_common_file`, `tb_board_post`, `tb_electronic_approval_main`, `tb_electronic_approval_line_info`의 관련 key/type/삭제 컬럼을 확인했다.
- 스키마/행 데이터 변경은 없다.

## 6. 검증

1. `CommonCommentServiceTest`: owner별 그룹화, 최신 루트+답글, extra root의 페이지 여부, cursor, root-only count와 empty ID를 검증한다.
2. `NoticeBoardServiceImplTest`: 다중 post 응답, attachments, root count, 댓글 페이지 metadata, comment attachment single batch call을 검증한다.
3. `DocumentApprovalServiceImplTest`: 다중 문서 응답 매핑, 권한 조건을 반영한 batch detail, 관계별 batch call 및 단건 조회 미호출을 검증한다.
4. `DocumentApprovalMapperTest`: mapper 등록, tenant/authorization predicate, USER-only/root-only 조건을 생성 SQL에서 검증한다.
5. 집중 테스트 명령:

   ```powershell
   cd backend
   mvn test -q "-Dtest=CommonCommentServiceTest,NoticeBoardServiceImplTest,DocumentApprovalServiceImplTest,DocumentApprovalMapperTest"
   ```

6. 전체 테스트 명령:

   ```powershell
   cd backend
   mvn test -q
   ```

6. UI가 변경되지 않으므로 브라우저 시각 확인 및 스크린샷은 비대상이다. 결과 문서에 사유를 기록한다.
