# 20261001_001 전자결재 기안양식관리 상세 사양서

## 1. 문서 상태와 기준

- 상태: 사용자 검토 및 구현 승인 완료 (2026-10-01)
- 상위 작업지시서: [20261001*001*전자결재*기안양식관리*작업지시서.md](../../directions/20261001/20261001_001_전자결재_기안양식관리_작업지시서.md)
- 계획서: [20261001*001*전자결재*기안양식관리*계획서.md](../../plan/20261001/20261001_001_전자결재_기안양식관리_계획서.md)
- 참고 화면: HACCP `HaccpBaseManagementPage`
- 구현 기준: S-ERP `CommonCodeManagementPage`, `WarehouseManagementPage`, 기존 F1-Grid 및 공통코드 API

이 사양은 HACCP의 원본 category group/work/authority 테이블을 그대로 이관한 기안양식 메타데이터 관리 화면을 대상으로 한다. 분류와 주기는 S-ERP 공통코드를 사용한다. 분류는 페이지 내부 상세코드 도움창에서 관리한다. 별도 템플릿 본문 편집기와 전자결재 상신/결재 흐름은 포함하지 않는다.

## 2. 메뉴와 화면 구성

- 메뉴명: 기준정보 > 전자결재관리 > 기안양식관리
- 메뉴 코드: `CO_WF_FORM`
- 메뉴 경로: `/co/workflow/form`
- 라우팅: 기존 `/co/*` 대시보드 셸을 유지하고 `selectedModule.id === 'co' && currentPageKey === 'form'` 분기에서 화면을 선택한다.
- 화면 조립: `PageHeader`, `PageSearchArea`, `PageMessageArea`, 기존 권한별 액션 그룹과 F1-Grid를 사용한다. 빈 분류 안내는 오류와 같은 `PageMessageArea` 레이아웃에서 info severity로 표시한다.
- breadcrumb는 Dashboard에서 전달된 메뉴 breadcrumb를 사용하며, 임의의 HACCP 헤더나 독립 레이아웃을 만들지 않는다.

- 통합 검색어는 양식코드와 양식명에 부분 일치한다. Enter 또는 조회 액션으로 적용한다.

| 등록주기 | `regTermId`      | 공통코드 선택  | 공통코드 선택 | 현재 테넌트 활성 `WF_FORM_CYCLE` 항목 ID              |
| 검토자   | `reviewerId`     | 사용자 선택    | 사용자 선택   | `tb_login_account.login_id`                           |

| 담당자   | `assigneeIds`    | 다중 선택      | 다중 선택     | 원본 `employee_no VARCHAR(10)` 값 목록                |

- 생성 시 `cataTypeCode`가 비어 있으면 `EgovConfigAppIdGen.codeIdGnrService`의 `tb_drafting_work_category` 설정으로 3자리 코드를 생성한다. 테넌트 내 삭제되지 않은 양식 코드 중복은 서버와 DB unique index에서 거부한다.
- 수정 시 기존 `cataTypeCode`는 변경할 수 없다.
- `categoryItemId`/`regTermId`는 숫자형 공통코드 항목 ID를 저장한다. `reg_term`만 대응 항목의 `item_nm`으로 동기화하고 `code_name`은 양식명으로 유지한다.

## 3. 공통코드 계약

기존 `tb_common_code_group`, `tb_common_code_item`과 다음 그룹/항목을 사용한다. 두 그룹은 활성 테넌트별로 멱등 seed한다. 분류 항목은 원본 HACCP 행에서 복사하거나 migration으로 seed하지 않고 기안양식 페이지의 상세 도움창에서 등록한다.

| 그룹 코드       | 그룹명            | 항목 코드 | 항목명 | 정렬 |
| --------------- | ----------------- | --------- | ------ | ---: |
| `WF_FORM_CYCLE` | 기안양식 등록주기 | `DAY`     | 일     |   10 |
| `WF_FORM_CYCLE` | 기안양식 등록주기 | `WEEK`    | 주     |   20 |
| `WF_FORM_CYCLE` | 기안양식 등록주기 | `MONTH`   | 월     |   30 |
| `WF_FORM_CYCLE` | 기안양식 등록주기 | `EVENT`   | 발생시 |   40 |

- 프론트엔드는 기존 `fetchCommonCodeGroups()`로 두 그룹을 찾고 `fetchCommonCodeItems(groupId)`로 활성 항목을 가져온다.
- 그룹 코드와 항목 코드를 정확히 비교하고 `useAt === 'Y'`인 데이터만 선택 옵션으로 노출한다.
- 백엔드는 저장 시 `LoginVO.tenantId` 범위에서 그룹 및 항목이 모두 활성 상태인지 검증한다. 다른 테넌트/그룹의 동일 코드, 미존재 코드, 비활성 코드는 거부한다.
- 분류 그룹 항목은 별도 공통코드 메뉴 이동 없이 `CommonCodeItemHelpDialog`에서 조회/추가/수정한다. 도움창 목록은 F1-Grid를 사용한다.
- 추가/수정은 기존 `POST /api/v1/co/master/common-code/groups/{groupId}/items`, `PUT /api/v1/co/master/common-code/groups/{groupId}/items/{itemId}`를 사용한다. 삭제 UI/API는 제공하지 않고 `useAt=N` 비활성화를 사용한다.
- 기존 API의 `EgovAccessControlHelper.isTenantAdmin(user)` 제한을 유지한다. 도움창 쓰기 동작은 tenant admin이며 현재 메뉴의 `CREATE` 또는 `UPDATE` 권한이 있을 때만 노출한다. 일반 사용자는 조회/선택만 한다.
- 공통코드 group/item CRUD API를 새로 만들지 않는다. 신규 UI 도움창만 재사용 컴포넌트로 만든다.

### 분류 상세 도움창

- 목록, 행추가, 행복사, 편집은 F1-Grid와 `rowFormPlugin`으로 제공한다. 분류 추가 버튼은 `F1GridRef.addRow()`와 동일하게 신규 form modal을 연다.
- 공통코드는 물리 삭제하지 않으므로 F1-Grid context menu에서 행삭제 항목은 숨긴다. 비활성은 row form의 `useAt=N`으로 저장한다.
- 저장/취소 버튼은 항상 모달 하단에 노출하고, 기존과 순서를 바꿔 저장을 왼쪽, 취소를 오른쪽에 둔다. 하단에 별도 상세코드 입력 폼을 렌더링하지 않는다.
- 모달 하단 action 위에 구분선을 두고, 제목 우측 상단에 닫기 X를 제공한다.
- 페이지의 Grid/API 상태는 `DraftFormGrid`, `useDraftFormManagement`, page types/services 경계로 분리한다.

## 4. 프론트엔드 API 계약

파일: `frontend/src/pages/co/workflow/form/services/draftFormManagement.service.ts`

### 목록 조회

`GET /api/v1/co/workflow/forms`

Query parameters:

| 이름             | 형식    | 필수   | 의미                                        |
| ---------------- | ------- | ------ | ------------------------------------------- |
| `keyword`        | string  | 아니오 | 양식코드 또는 양식명 부분 검색              |
| `keyword`        | string  | 아니오 | `cata_type_code` 또는 `code_name` 부분 검색 |
| `categoryItemId` | number  | 아니오 | 분류 공통코드 항목 ID                       |
| `regTermId`      | number  | 아니오 | 등록주기 공통코드 항목 ID                   |
| `useAt`          | `Y`/`N` | 아니오 | 사용여부 exact match                        |

성공 응답은 기존 `ResultVO`의 `result.resultList`를 사용한다. 결과가 없으면 빈 배열을 반환한다.

### 사용자 선택 목록 조회

`GET /api/v1/co/workflow/forms/users`

- reviewer, approver, assignee 선택용 API다. S-ERP에 전체 사용자 목록 서비스가 없어 이 endpoint를 추가한다.
- 인증 사용자의 `LoginVO.tenantId`만 사용하고 요청 파라미터로 tenant ID를 받지 않는다.
- `tb_user.use_at='Y'`와 연결된 `tb_login_account.use_at='Y'` 사용자만 반환한다. 부서명은 같은 tenant의 `tb_department`를 left join한다.
- 응답은 `result.resultList`이며 다음 필드를 포함한다.

| 필드           | 타입             | 의미                                                |
| -------------- | ---------------- | --------------------------------------------------- |
| `userId`       | number           | authority `employee_no`에 문자열로 저장할 사용자 ID |
| `loginId`      | number           | `reviewer_id`, `approver_id`에 저장할 로그인 ID     |
| `userNm`       | string           | 사용자 표시명                                       |
| `departmentNm` | string 또는 null | 소속 부서 표시명                                    |

- 응답에는 현재 tenant의 활성 사용자만 포함한다.

### 사용자 선택 목록 조회

`GET /api/v1/co/workflow/forms/users`

- 프론트의 reviewer/approver/assignee 선택 옵션용 tenant-scoped 조회 API다. 현재 S-ERP에는 전역 활성 사용자 조회 서비스가 없어 추가한다.
- 인증된 사용자의 `LoginVO.tenantId`를 사용하며 요청으로 tenant ID를 받지 않는다.
- `tb_user.use_at='Y'` 및 연결된 `tb_login_account.use_at='Y'`인 사용자만 반환한다. 부서명은 `tb_department`에서 tenant 조건을 포함해 left join한다.
- 성공 응답: `result.resultList` 배열. 항목 필드:

| 필드           | 타입             | 의미                                                |
| -------------- | ---------------- | --------------------------------------------------- |
| `userId`       | number           | 담당자 `employee_no`로 사용할 `tb_user.user_id`     |
| `loginId`      | number           | 검토/승인자 FK로 사용할 `tb_login_account.login_id` |
| `userNm`       | string           | 사용자 표시명                                       |
| `departmentNm` | string 또는 null | 소속 부서명                                         |

- tenant 밖 사용자와 비활성 사용자 정보는 반환하지 않는다.

### 등록

`POST /api/v1/co/workflow/forms`

요청:

```json
{
  "cataTypeCode": "",
  "codeName": "정기점검",
  "categoryItemId": 123,
  "regTermId": 456,
  "reviewerId": 102,
  "approverId": 103,
  "assigneeIds": ["110", "111"],
  "useAt": "Y"
}
```

- `reviewerId`, `approverId`는 선택된 `loginId`를 전송한다.
- `assigneeIds`는 선택된 `userId`를 10자리 이하 문자열로 전송한다. 저장 시 현재 tenant의 활성 `tb_user`인지 검증하고 원본 authority 테이블의 `employee_no`에 문자열로 저장한다. 10자 초과/미존재 userId는 거부한다.

- 성공: HTTP 201, `result.item`에 생성된 양식 반환
- `cataTypeCode`가 비어 있으면 `EgovConfigAppIdGen.codeIdGnrService`가 생성한 3자리 값을 사용한다. 이 빈은 `IDS` 테이블의 `tb_drafting_work_category` 키를 사용하고 3자리 zero-padding을 설정한다.
- `regTermId`는 활성 `WF_FORM_CYCLE` 항목 ID이며, API는 조회한 `itemNm`을 `regTerm`에도 저장한다. `codeName`은 양식명이고 분류명으로 사용하지 않는다.

### 수정

`PUT /api/v1/co/workflow/forms/{draftingWorkCategoryId}`

요청 필드: `cataTypeCode`, `codeName`, `categoryItemId`, `regTermId`, `reviewerId`, `approverId`, `assigneeIds`, `useAt`. 비어 있는 `cataTypeCode`는 현재 값을 유지하며, 생성 시에만 자동 생성한다.

- 성공: HTTP 200, `result.item`에 갱신된 양식 반환
- 삭제 대신 `useAt: "N"`으로 비활성화한다.

| 응답 키                     | 형식             | 의미                              |
| --------------------------- | ---------------- | --------------------------------- |
| `draftingWorkCategoryId`    | number           | `tb_drafting_work_category` PK    |

| `codeName`                  | string           | 원본 양식명                       |
| `categoryItemId`            | number           | 분류 공통코드 항목 ID             |

## 5. 백엔드 권한 및 예외 계약

- 인증 주체의 `LoginVO.tenantId`만 조회/수정 범위로 사용한다. 요청에서 tenant ID를 받지 않는다.
- 인증 주체의 `LoginVO.tenantId`만 조회/수정 범위로 사용한다. 요청에서 tenant ID를 받지 않는다.
- 사용자 옵션 조회도 인증 tenant의 활성 사용자만 반환한다. 조회는 인증된 사용자에게 허용한다.
- 목록 조회는 인증된 사용자에게 허용한다.
- 목록 및 사용자 선택 목록 조회는 인증된 사용자에게 허용한다.
- 등록/수정은 기존 시스템 관리 API와 동일하게 `EgovAccessControlHelper.isTenantAdmin(user)`를 요구한다. 프론트 액션도 전달된 메뉴 권한(`CREATE`, `UPDATE`)에 따라 표시한다.
- `CommonCodeItemHelpDialog`의 분류 항목 추가/수정은 재사용하는 기존 common-code API가 tenant admin을 요구한다. UI는 tenant admin이며 기안양식 메뉴의 `CREATE` 또는 `UPDATE` 권한이 있을 때만 편집 액션을 표시한다. 서버의 기존 admin 검사도 유지한다.
- 오류는 기존 `ResultVO` 및 `ResponseCode` 패턴을 따른다.

| 상황                                    | HTTP | 처리                                     |
| --------------------------------------- | ---: | ---------------------------------------- |
| 인증되지 않음                           |  401 | 기존 Spring Security 처리                |
| 목록/등록/수정 권한 없음                |  403 | 기존 권한 오류 응답                      |
| 공통코드 상세 도움창 쓰기 권한 없음     |  403 | 기존 common-code API의 tenant-admin 거부 |
| 필수값 누락, 길이 초과, 잘못된 사용여부 |  400 | 입력 검증 메시지                         |
| 비활성/미존재 분류 또는 주기 코드       |  400 | 활성 테넌트의 해당 코드 그룹 항목이 아님 |

- 비활성/미존재/다른 tenant의 `loginId`·`userId`는 400으로 거부한다. `userId`는 원본 `employee_no VARCHAR(10)` 범위로 제한한다.
  | 비활성/미존재/다른 tenant 사용자 ID | 400 | 현재 tenant의 활성 사용자/공통코드가 아님 |
  | 테넌트 내 양식코드 충돌 | 400 | 기존 입력 검증 오류 패턴으로 중복 코드 오류 반환 |
  | 수정 대상이 현재 테넌트에 없음 | 404 | 대상 미존재 |
  | 서버/DB 오류 | 500 | 공통 예외 처리 |

### 코드 관계와 동기화

- `WF_FORM_CATEGORY`/`WF_FORM_CYCLE` 그룹을 테넌트별 seed하며 cycle 항목 `DAY`, `WEEK`, `MONTH`, `EVENT`를 seed한다. Category item은 페이지 도움창으로 추가한다.
- `category_item_id`와 `reg_term_id`가 참조하는 item은 현재 tenant의 활성 올바른 code group 소속이어야 한다. FK는 item ID 존재만 보장하고 tenant/group/use validation은 서비스에서 한다.
- `category_item_id`의 항목명은 join으로 분류명에 표시한다. 원본 `code_name`은 양식명이다.
- `reg_term_id`의 `item_nm`을 같은 트랜잭션에서 원본 `reg_term`에 동기화한다.
- 새 양식코드는 기존 `codeIdGnrService` (`EgovConfigAppIdGen`, `tb_drafting_work_category`, 3 digits)를 재사용한다. 신규 `tb_electronic_approval_form` 또는 새 sequence는 만들지 않는다.
- 원본 인덱스에 더해 `category_item_id`, `reg_term_id` 조회 인덱스를 추가한다. 기존 단일 테이블 초안과 관련 rollback은 제거한다.
- 날짜별 SQL/change-schema/rollback은 `20261001_001` 번호로 양쪽 DB 폴더에 동일하게 두고 `docs/database/db-schema.md`에 반영한다.

## 7. 로딩·검색·저장 상태

- 최초 진입 시 공통코드 그룹/항목과 목록을 비동기로 조회한다.
- 목록 조회 중에는 F1-Grid 로딩 상태를 표시한다. 검색 실패 시 기존 조건/결과를 무심코 덮지 않고 `PageMessageArea`에 오류를 노출한다.
- 공통코드 그룹/항목 조회 실패 시 `PageMessageArea`에 오류를 표시한다. 분류 항목이 없으면 빈 상태와 관리자용 `분류 설정` 액션을 제공하고 양식 등록은 분류가 추가될 때까지 막는다.
- 분류 도움창 추가/수정 성공 시 코드 항목과 양식 목록/옵션을 다시 조회한다. 공통코드 수정/비활성화로 기존 양식과 참조가 달라지지 않도록 item ID는 바꾸지 않고 `useAt`만 갱신한다.
- 등록/수정 성공 시 목록을 다시 조회하고 S-ERP 공통 성공 피드백을 표시한다.
- 저장 중 중복 제출을 차단하며, 서버 검증 오류는 폼과 페이지 메시지에 표시한다.
- 반응형 기준 뷰포트는 375px, 768px, 1280px다. 좁은 화면의 상세검색은 한 열로 접고 Grid는 내부 가로 스크롤을 사용한다.

- `backend/DATABASE/20261001/20261001_001_haccp_drafting_work_schema.sql`
- `backend/DATABASE/20261001/20261001_001_haccp_drafting_work_change_schema.md`

실제 SQL 적용은 구현 승인과 검증 절차가 끝난 뒤에만 수행한다. 롤백은 work/authority 데이터가 있거나 사용자 생성 category code item이 FK로 참조되면 중단한다. 공통코드 그룹/seed 항목은 migration marker가 맞고 외부 참조가 없을 때만 제거한다.

## 9. 필수 검증 시나리오

1. `/co/workflow/form` 진입 시 공통 헤더와 전달된 breadcrumb, 기안양식 F1-Grid가 표시된다.
2. 기본 검색 필드는 하나뿐이며 양식코드/양식명 검색 결과만 Grid에 반영된다.
3. 상세검색의 분류/주기/사용여부가 현재 통합 검색어와 함께 API에 전달된다.
4. 분류/주기 옵션은 기존 공통코드 API에서 정확한 그룹 코드와 활성 항목만 표시한다.
5. 등록 시 빈 `cataTypeCode`에는 기존 3자리 ID generator가 적용되고, 코드 중복은 tenant/group 범위에서 거부된다.
6. 다른 테넌트/그룹/비활성 분류·주기 item ID는 저장되지 않으며 `reg_term_id`와 `reg_term`이 일치한다. 분류명은 `category_item_id` join으로 표시되고 `code_name`은 양식명으로 보존된다.
7. 분류 설정 도움창에서 항목 조회/추가/수정/비활성화가 가능하며, 비관리자 또는 메뉴 쓰기 권한이 없는 사용자는 편집할 수 없다.
8. reviewer/approver는 현재 tenant `tb_login_account.login_id`만 허용하고, assignee mapping은 기존 authority 계약(`employee_no`)에 저장한다.
9. 로딩, 빈 결과, API 오류, 검증 오류, 저장 성공 상태가 S-ERP 공통 피드백으로 표시된다.
10. 검색/다이얼로그/Grid가 375px, 768px, 1280px 화면에서 겹치거나 페이지 전체 가로 스크롤을 만들지 않는다.

## 10. 검토가 필요한 제안

- `WF_FORM_CATEGORY` 그룹에는 초기 분류 item을 넣지 않고, 테넌트 관리자가 기안양식 페이지의 도움창에서 필요 분류를 등록한다.
- `WF_FORM_CYCLE`에는 `DAY`, `WEEK`, `MONTH`, `EVENT` 코드를 seed하며 원본 `reg_term`은 항목명으로 유지한다.
- 양식코드는 원본 `cata_type_code`와 기존 `codeIdGnrService` 3자리 생성 규칙을 사용한다.
- 이번 페이지에는 별도 템플릿 본문 에디터를 포함하지 않는다.
