## 1. 역할 선택과 매핑 조회

- 역할 그리드 `onSelectionChange`의 첫 번째 ID를 `selectedRoleId`에 저장한다.
- `selectedRoleId`가 빈 값이거나 `new-role-` 접두사이면 사용자 매핑 목록을 비우고 조회하지 않는다.
- 조회 effect의 의존성은 역할 객체가 아닌 `selectedRoleId`로 제한한다.
- 각 요청에는 증가하는 요청 ID를 부여한다. 응답 ID가 최신 요청 ID와 다르면 state를 갱신하지 않는다.
- 조회 중에는 로딩 문구를, 실패 시에는 오류 문구를 우측 그리드 영역에 표시한다.

## 2. 역할 그리드 UI

- 카드 제목은 `권한 관리`를 유지한다.
- 우측 상단 `role="toolbar"`, `aria-label="권한 그리드 제어"`에 다음 아이콘 버튼을 둔다.
  - 선택 행 삭제: 선택 행이 없으면 비활성화하며 `roleGridRef.deleteSelectedRows()` 호출
  - 현재 행 내보내기: 활성 행을 CSV 파일로 내보냄
- 신규 역할은 F1-Grid 컨텍스트 메뉴 `행 추가`만으로 만든다.
- 컬럼 편집 규칙:
  - 역할 코드: 신규 행에서만 편집 가능
  - 역할명, 설명, 사용 여부: 신규·기존 행에서 편집 가능
  - 사용자 수: 읽기 전용

## 3. 역할 변경 저장

### 3.1 dirty 규칙

- `F1GridRef.getChanges()`의 삽입, 수정, 삭제 목록을 매 렌더링에서 dirty 판단 근거로 사용한다.
- 신규 행을 삭제하면 공통 F1-Grid는 해당 행을 rows/state에서 제거하고 변경 목록에 포함하지 않는다.
- 역할 또는 사용자 매핑 변경 목록이 하나라도 있으면 상단 저장 버튼을 활성화한다.

### 3.2 저장 규칙

- 역할 신규 행은 `POST /api/v1/system/roles`로 저장한다.
- 역할 수정 행은 `PUT /api/v1/system/roles/{roleId}`로 저장한다.
- 요청 본문:

```json
{
  "roleCode": "OPERATOR",
  "roleNm": "운영자",
  "roleDc": "운영 역할",
  "useAt": "Y"
}
```

- 역할 코드와 역할명은 필수이며, 미입력 시 저장 요청을 보내지 않고 페이지 오류 메시지를 표시한다.
- 기존 역할 삭제 행이 있으면 역할 삭제 API가 없으므로 역할 저장을 중단하고 오류를 표시한다.
- 모든 역할 저장 요청이 성공하면 `GET /api/v1/system/roles`로 목록을 재조회하고 역할 그리드 key를 갱신한다. 재마운트된 그리드는 변경 목록이 비어야 한다.

## 4. 사용자 매핑 추가와 저장

- 매핑 그리드의 우클릭 컨텍스트 메뉴는 `행 추가` 항목을 노출하지 않는다. 사용자 추가는 별도 확인 흐름에서 처리하며, 그리드의 우클릭 메뉴 자체는 공통 제어만 유지한다.
- 다이얼로그 후보는 현재 조회 결과의 미할당 사용자만 사용하며, 로그인 ID·사용자명·부서로 검색할 수 있다.
- 사용자를 선택하고 확인하면 매핑 그리드에서 해당 사용자의 `assigned` 값이 true로 변경되고 매핑 변경 목록에 추가된다.
- 저장 시 변경 전 assigned 값과 비교한다.
  - false → true: `POST /api/v1/system/roles/{roleId}/users`
  - true → false: `DELETE /api/v1/system/roles/{roleId}/users/{loginId}`
- 선택 역할이 신규 미저장 역할이면 사용자 매핑 추가 및 저장은 비활성화한다.
- 모든 저장이 성공하면 선택 역할의 `GET /api/v1/system/roles/{roleId}/users`를 재조회한다.

### 4.1 역할 전환 확인

- 사용자 매핑 그리드에 미저장 변경이 있을 때 다른 역할 행을 클릭하면 대상 역할을 즉시 선택하지 않고 확인 다이얼로그를 연다.
- 다이얼로그는 다음 액션을 제공한다.
  - `계속 편집`: 다이얼로그를 닫고 현재 역할 및 현재 변경을 유지한다.
  - `저장 후 이동`: 현재 역할의 변경을 저장한다. 역할/매핑 저장과 재조회가 모두 성공하면 대상 역할을 선택하고 대상 역할의 매핑을 조회한다. 실패하면 대상 역할을 선택하지 않고 현재 변경을 유지한다.
  - `변경 취소 후 이동`: 매핑 그리드를 마지막 서버 조회 기준으로 되돌리고 대상 역할을 선택·조회한다. 서버 저장 요청은 발생하지 않는다.
- 역할 전환 확인은 사용자 매핑 dirty에만 적용한다. 역할 그리드의 변경은 상단 저장 또는 기존 역할 삭제 오류 처리로 유지한다.

### 4.2 저장 신뢰성

- 역할 및 사용자 매핑 저장은 실행 중 재진입할 수 없다.
- 다건 저장에서는 성공한 역할 ID와 사용자 매핑 방향별 항목을 완료 체크포인트로 기록한다. 이후 항목 실패 시 재시도는 완료 체크포인트 항목을 다시 호출하지 않는다.
- 저장 완료 후 재조회는 저장 시작 시점의 역할 ID와 현재 선택 역할 ID가 동일할 때만 해당 그리드를 갱신한다.
- 역할이 바뀌면 진행 중이던 이전 역할의 조회·저장 후 재조회 응답은 현재 역할의 사용자 목록을 갱신할 수 없다.

## 5. 상단 액션과 메시지

- `PageHeader`의 조회와 저장 액션에 메뉴 관리와 같은 `SearchIcon`, `SaveIcon`을 적용한다.
- 저장 액션은 역할 또는 사용자 매핑 변경이 있을 때만 활성화한다.
- API 또는 유효성 실패는 `PageMessageArea`에 표시한다.
- 저장 성공 메시지는 기존 notification context를 사용한다.

## 6. 권한 및 DB 영향

- 기존 역할 API와 역할 사용자 매핑 API의 테넌트 관리자 권한 정책을 그대로 사용한다.
- DB 변경 없음: 기존 `tb_role`, `tb_login_account`, `tb_login_account_role` 관계만 조회·저장한다.
- 따라서 SQL 스크립트, rollback 스크립트, `db-schema.md` 수정은 발생하지 않는다. 결과 문서에 해당 없음 판단 근거를 기록한다.

## 7. 검증 기준

- 역할 A 선택 후 역할 B를 선택하면 최종적으로 B의 매핑만 표시된다.
- 기존 역할 행을 수정하고 저장하면 PUT 요청과 재조회가 발생한다.
- 행 추가 후 저장하면 재조회 직후 저장 버튼이 비활성화된다.
- 행 추가 후 삭제하면 변경 목록이 비어 저장 버튼이 비활성화된다.
- 미할당 사용자를 선택해 저장하면 역할 사용자 추가 API가 호출되고 재조회 결과에 반영된다.
- 사용자 매핑 변경 후 다른 역할을 클릭하면 선택 전환 확인 다이얼로그가 표시되고, 각 선택지의 저장·취소·유지 동작이 정확히 수행된다.
- 저장 중 역할을 전환해도 이전 역할의 저장 후 응답이 현재 역할의 매핑 목록을 덮어쓰지 않는다.
- 다건 저장 중 일부 요청이 실패한 뒤 재시도해도 이미 성공한 역할·매핑 API는 중복 호출되지 않는다.
- 모바일, 태블릿, 데스크톱에서 카드·툴바·그리드가 겹치지 않는다.
