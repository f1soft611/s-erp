# 20260921_001 공지사항 첨부파일 중복·삭제 오류 및 확장자 아이콘 수정 상세 사양서

## 1. 범위

대상 화면은 `/groupware/community/notice`이며, 공지사항 일반 첨부파일의 업로드 후 조회, 수정 삭제, 다운로드와 목록 표시를 다룬다. 본문 이미지와 댓글 첨부의 외부 계약은 변경하지 않는다.

## 2. 데이터 분류 규칙

| 구분        | owner_type | file_usage_type | 일반 첨부 목록 표시 | 일반 첨부 삭제          |
| ----------- | ---------- | --------------- | ------------------- | ----------------------- |
| 공지 파일   | `NOTICE`   | `ATTACHMENT`    | 표시                | 허용                    |
| 본문 이미지 | `NOTICE`   | `EMBEDDED`      | 표시하지 않음       | 일반 첨부 삭제에서 제외 |

- 공통 파일 조회의 기준은 `tenant_id`, `owner_type`, `owner_id`, `deleted_yn = 'N'`이다.
- 일반 첨부 응답의 `boardFileId`는 `tb_common_file.file_id`와 동일한 값이다.
- 화면에서 임시 파일은 `file`이 존재하며 `boardFileId`가 없고, 저장된 파일은 `boardFileId`가 존재한다.

## 3. 백엔드 동작 사양

### 3.1 목록·상세 조회

1. `CommonFileService.listFiles(tenantId, "NOTICE", postId)`로 공통 파일을 조회한다.
2. `fileUsageType = ATTACHMENT`인 파일만 `attachments`에 포함한다.
3. `fileUsageType = EMBEDDED`인 파일은 본문 이미지 URL 재작성에만 사용한다.
4. 일반 첨부를 DAO 조회 결과와 다시 합치지 않는다.
5. `attachmentCount`는 응답의 일반 첨부 수와 동일해야 한다.
6. 같은 `fileId`는 응답에 한 번만 나타나야 한다.

### 3.2 삭제·다운로드

- 삭제: `DELETE /api/v1/groupware/boards/notice/attachments/{boardFileId}?postId={postId}`
- 다운로드: `GET /api/v1/groupware/boards/notice/attachments/{boardFileId}/download?postId={postId}`
- 두 API 모두 인증된 사용자의 `tenantId`와 `postId`를 기준으로 파일 소유 여부를 확인한다.
- 파일이 없거나 다른 공지의 파일이면 `404 NOT_FOUND`와 `공지사항 첨부파일을 찾을 수 없습니다.`를 반환한다.
- `postId`가 없으면 `400 BAD_REQUEST`와 소유 정보 필요 메시지를 반환한다.
- 정상 삭제는 공통 파일 서비스의 owner-scoped soft delete를 사용한다.

### 3.3 게시글 수정

- 게시글 본문 수정과 일반 첨부 업로드·삭제는 각각 기존 API를 사용한다.
- 프론트가 유지하는 기존 첨부의 `boardFileId`만 삭제 API로 전송한다.
- 새 파일 업로드 실패 시 해당 저장 시도에서 성공한 새 파일을 정리하고 오류를 반환한다.
- 기존 파일 삭제 실패 시 성공 메시지를 표시하지 않고 오류 상태를 유지한다.

## 4. 프론트엔드 UI 사양

### 4.1 첨부 항목

- 파일 아이콘은 파일명 확장자에 따라 매핑한다.
- `pdf`, `xls/xlsx`, `doc/docx`, `ppt/pptx`, `hwp`, `zip`, `png/jpg/jpeg`는 확장자별 아이콘·색상을 사용한다.
- 미지원 확장자는 기본 파일 아이콘을 사용한다.
- 파일명은 기존처럼 ellipsis 처리하며, 다운로드·삭제 버튼과 겹치지 않는다.
- 최소 375px 화면에서 아이콘, 파일명, 액션 버튼이 잘리지 않아야 한다.

### 4.2 수정 삭제 상태

- 서버 첨부: `id`와 `boardFileId`를 보존한다.
- 새 첨부: `file`을 보존하고 `boardFileId`는 없다.
- 제출 시 `defaultAttachments` 중 현재 목록에 없는 서버 첨부의 `boardFileId`를 `removedAttachmentIds`로 만든다.
- 파일 ID가 없는 임시 첨부는 삭제 API 대상에서 제외한다.

## 5. API 응답 계약

일반 첨부 항목은 다음 필드를 유지한다.

```json
{
  "boardFileId": 123,
  "postId": 54,
  "fileName": "업무일정.xlsx",
  "fileSize": 1024,
  "objectKey": "tenant/1/notice/54/...",
  "bucketName": "document-attachments",
  "mimeType": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "contentType": "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
  "fileUsageType": "ATTACHMENT"
}
```

- 목록·상세 응답의 `attachments` 배열과 `attachmentCount`는 같은 일반 첨부 집합을 표현한다.
- 업로드 응답은 `item` 안에 동일한 첨부 필드를 반환한다.
- 삭제·다운로드 성공 응답은 기존 `ResultVO` 형식과 메시지를 유지한다.

## 6. 권한 및 예외 처리

- 인증되지 않았거나 `tenantId`가 없는 요청은 기존 인증 정책에 따라 `401 UNAUTHORIZED`를 반환한다.
- 다른 테넌트 또는 다른 게시글의 파일 ID를 사용한 삭제·다운로드는 `404 NOT_FOUND`로 처리한다.
- 업로드 파일이 없거나 비어 있으면 `400 BAD_REQUEST`를 반환한다.
- 저장 중 첨부 업로드가 실패하면 새로 업로드된 파일을 정리하고 게시글 저장 실패로 처리한다.
- 삭제 중 하나라도 실패하면 프론트는 성공 상태로 닫거나 성공 메시지를 표시하지 않고 오류를 표시한다.

## 7. 회귀 검증 케이스

1. 일반 첨부 1개 업로드 후 목록 재조회: `attachments.length = 1`, 동일 `boardFileId` 중복 없음
2. 일반 첨부와 본문 이미지가 함께 있는 공지: 일반 첨부에는 `ATTACHMENT`만 표시되고 본문 이미지는 렌더링됨
3. 수정 화면에서 기존 일반 첨부 제거 후 저장: 삭제 API가 실제 `boardFileId`와 `postId`를 전달하고 2xx 응답
4. 삭제 후 목록·상세 재조회: 삭제 파일 미표시, `attachmentCount` 감소
5. 다른 게시글의 파일 ID 삭제 시도: 404 반환
6. `xlsx`, 미지원 확장자 첨부 표시: 확장자별 아이콘과 기본 아이콘이 각각 표시됨
7. 375px 및 1280px 뷰포트: 파일명, 아이콘, 액션 버튼의 겹침·잘림 없음

## 8. 문서 및 DB 영향

- 신규 테이블·컬럼·인덱스·마이그레이션 없음
- `backend/DATABASE/20260921/` 및 `docs/database/20260921/` SQL/Rollback 파일: 해당 없음
- 구현 후 결과 문서에 원인, 변경 파일, 테스트 명령, 브라우저 캡처 경로를 기록한다.
