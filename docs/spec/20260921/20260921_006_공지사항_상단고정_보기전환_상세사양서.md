# 20260921_006 공지사항 상단 고정 및 공통 보기 전환 상세 사양서

## 1. 화면 구성

대상 화면은 `/groupware/community/notice`이다.

1. 기존 페이지 헤더와 필터 영역을 유지한다.
2. 필터 아래에 상단 고정 영역을 배치한다.
3. 상단 고정 영역의 우측 끝에 피드형·리스트형 보기 컨트롤을 배치한다.
4. 상단 고정 영역 아래 본문에는 선택된 모드의 목록과 기존 우측 요약 패널을 배치한다.
5. 기본 모드는 피드형이다.

## 2. 공통 표시 모델

공통 컴포넌트는 공지사항 API 타입을 참조하지 않고 아래 의미의 제네릭 표시 모델을 받는다.

```ts
type CommonViewMode = 'feed' | 'list';

type CommonViewItem = {
  id: string | number;
  title: string;
  authorLabel: string;
  dateLabel: string;
  isPinned?: boolean;
  metaLabel?: string;
  summary?: string;
};
```

실제 타입명과 필드명은 기존 프로젝트 규칙에 맞춰 구현 단계에서 확정한다. 도메인별 추가 정보는 제네릭 payload 또는 render prop으로 전달하며 공통 컴포넌트가 특정 도메인 필드를 해석하지 않는다.

## 3. 공통 컴포넌트 책임

### 3.1 보기 모드 컨트롤

- `feed`와 `list` 두 선택지를 제공한다.
- 현재 선택 상태와 접근 가능한 이름을 표시한다.
- 클릭 시 `onChange(mode)`를 호출한다.
- API 호출이나 상태 저장은 수행하지 않는다.

### 3.2 상단 고정 영역

- `items` 중 `isPinned === true`인 항목을 표시한다.
- 고정 항목이 없으면 빈 상태를 표시한다.
- 항목 내용은 도메인 중립적인 제목·작성자·일시 표시 모델을 사용한다.
- 고정 등록·해제 API나 권한 판단은 수행하지 않는다.

### 3.3 피드형 목록

- 카드 기반 세로 목록을 제공한다.
- 기존 공지사항의 댓글·첨부·상세 확장 등 복잡한 동작은 공지사항 조립 계층의 콜백으로 연결한다.
- 다른 도메인은 필요한 상호작용만 render prop/콜백으로 주입한다.

### 3.4 리스트형 목록

- 행 기반 목록으로 제목·작성자·작성일시를 표시한다.
- 피드형의 본문·댓글·첨부·좋아요·북마크 UI를 표시하지 않는다.
- 항목 클릭 콜백은 계약상 열어둘 수 있으나, 이번 공지사항 작업에서는 우측 상세 현황 패널을 연결하지 않는다.

### 3.5 스켈레톤

- 피드형 스켈레톤과 리스트형 스켈레톤을 별도 컴포넌트로 제공한다.
- 피드형 스켈레톤은 카드형 헤더·제목·본문·액션 형태를 따른다.
- 리스트형 스켈레톤은 행과 제목·작성자·일시 열 형태를 따른다.
- 선택 모드와 다른 스켈레톤을 표시하지 않는다.

## 4. 공지사항 어댑터

`CommunityNoticePage` 또는 공지사항 전용 adapter 모듈이 다음을 담당한다.

- `NoticeFeedItem`의 `id`, `title`, `meta`, `createdAt`, `highlight`를 공통 표시 모델로 변환한다.
- `highlight` 또는 API의 `isNotice === 'Y'`를 `isPinned`로 변환한다.
- 공지사항의 피드 전용 이벤트와 기존 `NoticeFeedList` 동작을 연결한다.
- 리스트형에서는 제목·작성자·작성일시만 전달한다.

## 5. 상태 및 재조회 계약

```ts
type ViewModeState = {
  mode: CommonViewMode;
  isLoading: boolean;
  errorMessage?: string;
};
```

- 초기 `mode`: `feed`.
- 보기 전환 클릭 시 페이지가 선택 모드를 갱신한 뒤 기존 `fetchNoticePosts` 조회 경로를 호출한다.
- 조회 중에는 기존 목록을 모드별 스켈레톤으로 대체한다.
- `feed` 선택 시 피드형 스켈레톤, `list` 선택 시 리스트형 스켈레톤을 사용한다.
- 조회 성공 시 새 응답을 공지사항 표시 모델로 변환한다.
- 조회 실패 시 선택 모드 영역에 오류와 재시도 진입점을 표시한다.
- 모드 선택값은 서버나 영구 사용자 설정에 저장하지 않는다.

## 6. API 계약

백엔드 API 계약은 변경하지 않는다.

- 목록 조회: 기존 공지사항 목록 조회 API와 `fetchNoticePosts`를 재사용한다.
- HTTP 메서드, 엔드포인트, 요청 필드, 응답 필드, 상태 코드는 기존 계약을 그대로 사용한다.
- 보기 모드는 API 요청 파라미터나 서버 저장 필드가 아니다.
- API 실패 시 기존 오류 처리와 재시도 흐름을 유지한다.

## 7. 권한 및 예외 처리

- 기존 공지사항 조회·작성·수정·삭제 권한 정책을 변경하지 않는다.
- 공통 컴포넌트는 권한을 판단하지 않고 호출부가 허용한 콜백만 실행한다.
- 고정 공지가 없으면 빈 상태를 표시한다.
- 목록이 비어 있으면 기존 빈 목록 상태를 표시한다.
- 재조회 중 연속 클릭이 발생해도 최신 요청 결과가 현재 선택 모드와 일치하도록 요청 상태를 관리한다.
- 리스트형 상세 패널은 이번 범위에서 렌더링하지 않는다.

## 8. 반응형 기준

- 375px: 보기 컨트롤이 상단 고정 영역 안에서 줄바꿈 또는 축소되어 가로 스크롤을 만들지 않는다.
- 768px: 상단 고정 영역과 목록 행의 제목·작성자·일시가 겹치지 않는다.
- 1280px: 기존 목록·요약 2열 구조와 보기 컨트롤이 안정적으로 유지된다.
- 텍스트가 길면 말줄임 또는 줄바꿈을 사용하되 행 높이가 비정상적으로 확장되지 않도록 한다.

## 9. 테스트 기준

- 공통 피드형 컴포넌트가 전달된 항목을 카드로 표시한다.
- 공통 리스트형 컴포넌트가 제목·작성자·작성일시만 표시한다.
- 상단 고정 영역이 고정 항목과 빈 상태를 각각 표시한다.
- 피드형·리스트형 컨트롤 클릭 시 모드별 목록 재조회가 호출된다.
- 재조회 중 모드별 스켈레톤이 표시된다.
- 조회 실패 시 선택 모드 오류 상태가 표시된다.
- 기존 피드형 공지의 첨부·댓글·상세 확장 회귀가 없다.
- 375px·768px·1280px 브라우저에서 겹침·잘림·가로 스크롤이 없다.

## 10. 제외 사항

- 리스트 항목 클릭 후 우측 상세 현황 패널
- 게시판·자료실·그룹웨어 업무 화면의 실제 적용
- 백엔드·DB·API 계약 변경
- 보기 모드 영구 저장
