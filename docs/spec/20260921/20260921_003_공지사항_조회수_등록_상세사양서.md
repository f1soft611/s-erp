# 20260921_003 공지사항 조회수 등록 상세 사양서

## 1. 대상

- 화면: `/groupware/community/notice`
- 상세 API: `GET /api/v1/groupware/boards/notice/posts/{postId}`
- 저장 테이블: `tb_board_post`, `tb_board_post_view_history`

## 2. 조회수 정책

| 조건                             | 조회수 처리           |
| -------------------------------- | --------------------- |
| 사용자가 공지글을 처음 상세 조회 | 1 증가                |
| 같은 사용자의 새로고침·반복 조회 | 증가하지 않음         |
| 같은 사용자의 동시 요청          | 1회만 증가            |
| 다른 사용자의 최초 상세 조회     | 사용자별 1회 증가     |
| 목록 조회                        | 증가하지 않음         |
| 존재하지 않거나 삭제된 글        | 이력·조회수 변경 없음 |

중복 기준은 `tenant_id + post_id + login_id`이다.

## 3. DB 계약

### 3.1 `tb_board_post_view_history`

| 컬럼            | 타입      | 제약                             | 설명               |
| --------------- | --------- | -------------------------------- | ------------------ |
| view_history_id | bigserial | PK                               | 조회 이력 식별자   |
| tenant_id       | bigint    | NOT NULL, FK                     | 테넌트 식별자      |
| post_id         | bigint    | NOT NULL, FK                     | 공지 게시글 식별자 |
| login_id        | bigint    | NOT NULL, FK                     | 로그인 계정 PK     |
| viewed_at       | timestamp | NOT NULL, 기본 CURRENT_TIMESTAMP | 최초 조회 시각     |

- 유니크 제약: `(tenant_id, post_id, login_id)`
- 물리 삭제보다 공지글 soft delete 정책을 우선한다.
- 조회 이력은 조회수 중복 방지 목적이며 사용자 화면에 직접 노출하지 않는다.

## 4. 인증 사용자 식별

- 컨트롤러의 `LoginVO.id`를 현재 테넌트의 `tb_login_account.login_code`와 매칭한다.
- 매칭된 `tb_login_account.login_id` bigint를 조회 이력의 `login_id`로 사용한다.
- tenant 조건을 함께 사용하여 동일 로그인 코드가 다른 테넌트에서 충돌하지 않게 한다.
- 인증 정보가 없으면 기존 인증 실패 처리(`401`)를 유지한다.
- 인증 정보는 있으나 계정 PK를 찾지 못하면 조회수 처리 없이 상세 조회를 성공시키지 않고 서버 오류/계약 오류로 처리한다.

## 5. API 계약

### 요청

```text
GET /api/v1/groupware/boards/notice/posts/{postId}
Authorization: Bearer <token>
```

### 성공 응답

- HTTP `200`
- 기존 `ResultVO` 구조 유지
- `item.viewCount`: 최초 조회 처리 후의 누적 조회수
- 그 외 제목, 본문, 첨부파일, 댓글 필드는 기존 계약 유지

### 예외 응답

- 인증 없음: 기존 `401` 처리
- 게시글 없음/삭제됨: 기존 `404` 처리
- 내부 DB 오류: 기존 전역 예외 처리 정책 적용

## 6. 백엔드 처리 순서

1. `postId`와 `tenantId`로 삭제되지 않은 공지를 확인한다.
2. 인증 사용자의 로그인 코드로 `login_id`를 해석한다.
3. 조회 이력 INSERT를 실행한다.
4. INSERT가 새 행을 생성한 경우에만 `tb_board_post.view_count = view_count + 1`을 실행한다.
5. 게시글을 재조회해 증가된 `viewCount`를 확보한다.
6. 기존 첨부파일·본문 이미지·댓글 보강을 수행한다.
7. `item`으로 반환한다.

조회 이력 INSERT는 PostgreSQL `ON CONFLICT DO NOTHING`과 영향 행 수를 이용해 최초 조회 여부를 판별한다. 조회수 UPDATE는 `is_deleted = 'N'` 조건과 원자 증가식을 사용한다.

## 7. 프론트엔드 동작

- 목록 API 호출은 조회수 증가를 유발하지 않는다.
- 상세 응답의 `viewCount`를 공지 피드의 조회수 표시 영역에 사용한다.
- 서버 응답을 기준으로 갱신하며, 클라이언트에서 임의로 +1하지 않는다.
- 조회수 등록 실패 시 기존 상세 조회 오류 처리 정책을 따른다.

## 8. 권한 및 보안

- 기존 공지사항 상세 조회 인증 정책을 유지한다.
- 테넌트 조건과 로그인 계정 조건을 모든 조회 이력 처리에 적용한다.
- 클라이언트가 전달하는 사용자 ID는 사용하지 않고 인증 컨텍스트만 신뢰한다.
- 조회 이력의 사용자 식별 정보는 API 응답이나 로그에 노출하지 않는다.

## 9. 회귀 검증

1. 사용자 A의 첫 상세 조회 후 `viewCount`가 1 증가한다.
2. 사용자 A의 반복 상세 조회 후 `viewCount`가 유지된다.
3. 사용자 B의 첫 상세 조회 후 사용자 A의 기존 증가분에 추가로 1 증가한다.
4. 동일 사용자 동시 상세 조회에서 이력은 1건이고 조회수도 1회만 증가한다.
5. 목록 조회 전후 조회수가 동일하다.
6. 삭제·미존재 공지는 조회 이력과 조회수가 변경되지 않는다.
7. 상세 응답의 `item.viewCount`가 DB 증가값과 일치한다.
8. 기존 첨부파일·댓글·본문 이미지 응답이 유지된다.
