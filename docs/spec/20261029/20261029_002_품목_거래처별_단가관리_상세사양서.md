## 1. DB 검증 및 적용 상태

- 대상은 central DB의 `public` schema다. 현재 MCP 테이블 목록에는
  `tb_item_partner_price`가 없다.
- `tb_material_info`는 PK `material_id`, unique
  `(material_id, tenant_id)`와 `(tenant_id, material_code)`를 가진다.
  품목 선택 가능 조건은 현재 활성 조건
  `delete_status = 'N' AND deleted_at IS NULL`이다.
- `tb_customer_info`는 PK `customer_id`, unique
  `(customer_id, tenant_id)`와 `(tenant_id, customer_code)`를 가진다.
  신규 단가에 선택 가능한 거래처는 `use_at = 'Y'`다.
- `tb_sales_order_dt.unit_price`는 `NUMERIC(15,2)`다.
- MCP에서 테이블 목록, 관련 테이블 컬럼, PK/unique 메타데이터를 조회했다.
  업무 행/tenant 데이터는 읽지 않았다. DDL은 작성 후에도 적용하지 않는다.

### Keys, constraints, and indexes

- PK: `(price_id)`.
- Unique: `(tenant_id, material_id, customer_id, trade_type, start_dt)`.
- FKs:
  - `tenant_id -> tb_tenant(tenant_id)`.
  - `(material_id, tenant_id) -> tb_material_info(material_id, tenant_id)`.
  - `(customer_id, tenant_id) -> tb_customer_info(customer_id, tenant_id)`.
- Checks: `trade_type IN ('매입', '매출')`, `use_at IN ('Y','N')`,
  `unit_price >= 0`, `moq IS NULL OR moq >= 0`,
  `end_dt IS NULL OR end_dt >= start_dt`.
- Indexes: `(tenant_id, material_id)`, `(tenant_id, customer_id)`,
  `(tenant_id, trade_type, start_dt, end_dt)`.
- Same tenant/item/customer/trade/start-date always conflicts, including a
  currently unused row. Different start dates with overlapping effective
  periods are allowed; no exclusion constraint is created.
- The screen has no physical-delete operation. Inactive prices remain unique
  and can be reactivated or edited through update.

### Migration lifecycle

- Forward SQL, rollback SQL, and change-history markdown live under the
  matching `docs/database/20261029` and `backend/DATABASE/20261029` paths.
- The mirrored SQL/history files must be identical.
- Rollback checks the table exists and is empty before dropping only the
  specifically named indexes/table. It never uses `CASCADE`; unexpected
  dependencies stop rollback.
- `db-schema.md` labels this table as a proposed, unapplied schema.
- No migration script is run through MCP or any other DB connection.

  Existing dashboard menu permissions gate visible read/create/update actions.

### Search and list

Base API: `/api/v1/co/master/item-partner-prices`.

Optional GET query parameters:

| Parameter | Meaning |
|---|---|
| `keyword` | Partial match on item/partner code and name |
| `tradeType` | Exact `매입` or `매출` |
| `effectiveOn` | Return rows with `start_dt <= date` and (`end_dt` is null or `end_dt >= date`) |
| `useAt` | Exact `Y` or `N` |

The list order is trade type, item code, partner code, start date descending,
then `price_id`. There is no pagination in this feature. User-visible columns:
No, trade type, item code/name, partner code/name, unit price, currency,
effective start/end, MOQ, use status. Search and default filters are applied
only when the user submits a search.

## 4. Frontend row model and form

### Price row

```ts
type ItemPartnerPriceRow = {
  priceId: number | string;
  materialId: number | null;
  materialCode: string;
  materialName: string;
  customerId: number | null;
  customerCode: string;
  customerName: string;
  tradeType: '매입' | '매출';
  unitPrice: number | null;
  currency: string;
  startDt: string;
  endDt: string | null;
  moq: number | null;
  useAt: 'Y' | 'N';
  tenantId?: number;
  createdBy?: string;
  createdAt?: string;
  updatedBy?: string;
  updatedAt?: string;
};
```

New grid IDs are local strings and are not server identifiers. Successful
batch response includes an explicit local-ID-to-server-ID mapping.

### Row form

- Groups: `거래조건` (거래구분, 품목, 거래처), `단가조건` (단가, 통화,
  적용시작일, 적용종료일, 최소주문수량, 사용여부).
- `tradeType`, `materialId`, `customerId`, `unitPrice`, `currency`, and
  `startDt` are required. `endDt` and `moq` may be empty.
- Item/partner selection uses `shared/components/master-picker` and existing
  item/customer search services. Selection stores the internal ID and
  displays code/name; users never type IDs.
- New row defaults: `tradeType` is unset and must be explicitly selected,
  `currency='KRW'`, `endDt=null`, `moq=null`, `useAt='Y'`.
- Unit price and MOQ must be finite, nonnegative, at most 13 integer digits
  and 2 fractional digits, compatible with `NUMERIC(15,2)`. Blank MOQ maps to
  SQL NULL; zero remains zero.
- End date must not precede start date. Date parsing and server persistence
  use date-only ISO `YYYY-MM-DD`; no timezone conversion is allowed.
- Currency is trimmed and at most 10 characters; an empty value defaults to
  `KRW`. No ISO-only restriction or exchange-rate conversion is added.
- Update may change the pair/trade/start date, but the resulting business key
  must not match another row in the tenant.
- Deleted rows are rejected by batch API. Use status `Y/N` to deactivate.

## 5. Excel template and import parser

- Template and upload support `.xlsx` only. `.xls`, CSV, macro-enabled, and
  other file types are rejected with an explicit message.
- Template first worksheet header row is exactly:
  `거래구분`, `품목코드`, `거래처코드`, `단가`, `통화`, `적용시작일`,
  `적용종료일`, `최소주문수량`, `사용여부`.
- Item/partner codes are Excel text cells to preserve leading zeroes. The
  template includes an instruction row/sheet stating trade values, allowed
  formats, date examples, and that blank currency/use status default to
  `KRW`/`Y`. The parser maps columns by header, not fixed
  order, and rejects duplicate/missing required headers.
- Maximum import data rows: 1,000. Files larger than 10 MiB are rejected
  before parsing.
- Parse only the first worksheet. Ignore fully blank rows; nonblank malformed
  rows remain visible as errors and are never silently dropped.
- Dates may be Excel date cells or strict ISO `YYYY-MM-DD` strings. Numeric
  amounts may be numeric cells or plain decimal strings; dates such as
  `2026-13-40`, NaN/infinity, exponent notation, more than two fraction
  digits, negative values, and values beyond `NUMERIC(15,2)` are invalid.
- The parser retains the source worksheet row number (including the header
  offset). ExcelJS is dynamically imported only when the user downloads a
  template or selects an upload. The frontend does not add SheetJS/xlsx.
- Parsed values show in a preview dialog before affecting the main grid.
  Users may correct editable business cells and request validation again.
  Invalid rows remain visible; row errors are accessible and identify the
  source spreadsheet row.

## 6. API contract

All responses use the existing `ResultVO` helper and `result.resultList` /
`result.item` conventions. `tenantId`, audit actor, and timestamps are
server-owned.

### GET `/api/v1/co/master/item-partner-prices`

Returns `result.resultList: ItemPartnerPriceVO[]` for the authenticated
tenant. Each record contains the row/form fields, display code/name for both
masters, and optional audit fields. A malformed response is a visible API
error, not an empty list.

### POST `/api/v1/co/master/item-partner-prices/validate-import`

Request:

```json
{
  "rows": [{
    "sourceRowNumber": 2,
    "tradeType": "매입",
    "materialCode": "000123",
    "customerCode": "000045",
    "unitPrice": "1250.50",
    "currency": "KRW",
    "startDt": "2026-10-01",
    "endDt": null,
    "moq": null,
    "useAt": "Y"
  }]
}
```

The request contains no tenant or master IDs. Backend resolves active item and
customer IDs within the principal tenant, validates every value, detects
same-file duplicate business keys and checks existing exact-key conflicts
across both active/inactive price rows. It is read-only and does not reserve
keys.

Success response includes one result for every input row:

```json
{
  "item": {
    "rows": [{
      "sourceRowNumber": 2,
      "materialId": 123,
      "materialCode": "000123",
      "materialName": "표시 품목명",
      "customerId": 45,
      "customerCode": "000045",
      "customerName": "표시 거래처명",
      "errors": []
    }]
  }
}
```

Errors are structured `{code, message}` items per row. Unknown/inactive item
or customer, invalid fields, duplicate input key, and existing exact-key
conflict are row errors. If any row has errors, frontend cannot stage any rows.
Malformed request, empty input, over 1,000 rows, or failed response validation
returns an explicit 400/error and is not treated as an empty validation result.

### POST `/api/v1/co/master/item-partner-prices/save-batch`

Request:

```json
{
  "prices": {
    "insertedRows": [{
      "priceId": "new-1",
      "materialId": 123,
      "customerId": 45,
      "tradeType": "매입",
      "unitPrice": 1250.5,
      "currency": "KRW",
      "startDt": "2026-10-01",
      "endDt": null,
      "moq": null,
      "useAt": "Y"
    }],
    "updatedRows": [],
    "deletedRows": []
  }
}
```

The server validates all rows, verifies active tenant-scoped masters for new
and changed associations, rejects repeated keys and collisions with other
records, and applies all inserts/updates in one transaction. Nonempty
`deletedRows` is HTTP 400. Unique constraint violations caused by a race
return an explicit conflict/input error; the transaction rolls back.

Success returns `result.item.prices: ItemPartnerPriceVO[]` and
`result.item.rowIdMappings` mapping each local row ID to its new positive
server `priceId`. An empty change set is rejected rather than reported as a
successful write. Existing grid changes are kept on any error.

### Errors

- Invalid request, missing/inactive master, invalid values, existing or
  request-internal duplicate, unique race: HTTP 400 with a user-displayable
  message.
- Missing authenticated tenant: HTTP 401.
- Non-admin create/update: HTTP 403.
- Tenant-scoped price ID absent or owned by another tenant: HTTP 404.
- Database and network failures remain visible; do not return success-shaped
  fallbacks.

## 7. Save and import user flow

### Manual registration/edit

1. User opens the row form from the page action or row detail action.
2. User selects item and customer through the shared pickers and enters price
   terms.
3. F1-Grid validation and service normalization reject invalid values before
   request.
4. Page Save submits all manual/import-staged changes in one batch request.
5. On success, server rows and ID mappings are reconciled with
   `acceptSavedRows`; on failure, typed values and dirty rows remain.

### Excel import

1. User downloads the template or selects an `.xlsx`.
2. Dynamic parser validates extension/size/workbook/headers and displays a
   preview with source row numbers.
3. Client detects invalid values and duplicates within the file.
4. User corrects values in preview and clicks `검증`.
5. Server import-preflight resolves active item/customer codes, checks
   exact-key duplicates and returns row errors; no database write occurs.
6. With zero errors, the dialog enables `그리드에 추가`. Confirming stages
   every preview row as a new F1-Grid row and closes the dialog.
7. Page Save sends manual and imported rows together. The final batch request
   repeats all validations and enforces the unique index.
8. Preflight or final save error preserves row values. If final save fails,
   the import dialog can be reopened only if that can preserve staged rows;
   otherwise errors are shown in the grid and the dirty rows remain editable.

No imported row updates an existing `price_id`.

## 8. Loading, unsaved edits, and responsive behavior

- Initial list loading, retryable list error, empty results, import parsing,
  preflight, saving, and successful save are distinct states.
- While preflight is pending, disable revalidation/staging and prevent closing
  from discarding edits without the established confirmation flow.
- Search during dirty changes uses the existing unsaved-change confirmation;
  canceled search restores applied criteria.
- Save action is disabled when no changes exist or while saving/loading.
  Save errors do not clear `hasChanges`.
- At 1280px, keep header/search/actions compact when space permits. At 768px
  and 375px, allow wrapping and vertically arrange dialog contents. Grid and
  preview table use internal horizontal scrolling; page itself must not
  overflow horizontally.
- Verify actual browser layout at 375px, 768px, and 1280px.
