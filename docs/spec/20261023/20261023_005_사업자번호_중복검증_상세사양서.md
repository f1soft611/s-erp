## 공통 프론트 계약

- `validation.unique`는 기존 boolean 외에 `'digits'`를 허용한다. true는 기존 trim 비교, false/미설정은 비활성이다.
- digits는 값에서 ASCII 숫자 0~9만 남겨 비교한다. 기존 inputFormat의 숫자 추출과 같고 앞자리 0을 유지한다. 입력값/표시값 자체는 unique 검증으로 변경하지 않는다.
- 숫자가 없는 빈 정규화 값은 고유성 인덱스에서 제외한다. 기존 필수/자리수 검증 순서는 유지한다.
- 사업자번호에 `{ unique: 'digits' }`를 선언한다. `123-45-67890`, `1234567890`, `123 45 67890`은 같다.
- 기존 활성 행 전체/자기 행 제외/삭제 제외/신규·수정 draft 비교를 재사용한다.
- 폼 적용·최종 저장에서 `사업자번호 값이 중복되었습니다.`를 기존 상단 오류·빨간 표시로 전달하고 진행을 차단한다.
- 서버 검색 결과 밖의 번호는 서버 검증이 최종 확인한다.

## 서버 및 DB 계약

- 등록/수정 시 `businessNo.replaceAll("[^0-9]", "")`로 비교키 생성. 빈 키는 고유성 사전 검사하지 않는다. 저장/응답 표기는 기존대로 유지한다.
- Mapper는 `regexp_replace(business_no, '[^0-9]', '', 'g')`와 비교하고 tenant 조건 및 수정 자기 ID 제외를 사용한다. 사용여부 조건 없음.
- 사전 또는 신규 인덱스 충돌 메시지는 `이미 사용 중인 사업자번호입니다.`이며 기존 400 입력 오류 처리 흐름을 따른다. 이름·코드 충돌 분류는 유지한다.
- `uq_tb_customer_info_tenant_business_no` unique index on `(tenant_id, regexp_replace(business_no, '[^0-9]', '', 'g'))`, 숫자 정규화 결과 비어 있지 않은 행만 포함한다.
- migration은 잠금 후 동일 표현식으로 사전 중복을 확인하고, 중복이 있으면 개인정보/번호를 출력하지 않는 오류로 전체 중단한다. rollback은 이 인덱스만 삭제한다.
- 기존 NULL/빈 번호를 허용하는 서버 저장 계약은 변경하지 않는다. 프론트의 기존 required/10자리 조건은 유지한다.
- DB 실제 적용·데이터 정리·실제 동시 세션 검증은 수행하지 않는다. 배포 전 인덱스 적용 없이는 동시성 보장이 불완전함을 명시한다.

## MCP 근거

2026-10-23 기본 DB MCP에서 list_tables → describe_table(tb_customer_info) → pg_indexes metadata 제한 조회. business_no는 nullable varchar이고 사업자번호/거래처명 unique index는 없으며 tenant/code unique는 있다. 실제 업무 행은 조회하지 않았으므로 기존 중복 유무는 미확인이다. 이전 tenant 전용 DB 문서와 기본 DB metadata는 구분한다.

## 검증

- 공통 digits 정규화, 앞자리 0, 자기 ID 제외, true/false 기존 동작 보존.
- 거래처 폼 신규 중복 차단, 유효한 다른 번호 적용, 인라인으로 동일 번호 변경 후 저장 차단·빨간 셀·API 미호출.
- 서버 등록/수정 사전 검사 조건, 빈 값 건너뜀, 정규화 값·원본 저장 표기 유지, insert/update index 충돌 메시지.
- Mapper tenant/자기 ID/useAt 조건 및 SQL/rollback 사본 일치.
- 3개 viewport 실제 브라우저 확인과 결과 문서.
