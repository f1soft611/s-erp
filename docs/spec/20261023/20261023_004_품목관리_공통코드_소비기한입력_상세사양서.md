## DB 확인 범위

지정 tenant MCP에서 `list_tables`로 테이블을 확인하고 `describe_table`로 `tb_common_code_group`, `tb_common_code_item`, `tb_material_info`의 필드를 확인했다. 제한 조회로 품목 화면에 연결된 공통코드와 그룹/상세 인덱스, 두 기존 소비기한 CHECK 및 기준/숫자 조합의 집계만 확인했다. 업무 행을 반환하지 않는 집계와 코드 행 외의 tenant·계정·인증 정보는 조회하지 않았다. 기본 S-ERP MCP에서 공통코드 테이블/인덱스 메타데이터와 관련 코드 부재를 확인했다.

공통코드 PK는 테이블 시퀀스를 기본값으로 사용한다. 그룹 자연 키는 `(tenant_id, group_code)`, 상세 항목 자연 키는 `(group_id, item_code)`다. 따라서 ID를 정적으로 복제하지 않고 코드 그룹으로 실제 target group ID를 조회한다.

## 공통코드 시드 계약

### 대상 및 실행

- 그룹은 `MATERIAL_TYPE`, `STORE_METHOD`, `EXPIRY_STATUS` 세 개로 제한한다.
- 상세 항목은 아래 12개로 제한한다.
- target tenant ID는 psql 변수 `target_tenant_id`로만 지정한다. SQL 파일에 tenant ID를 하드코딩하지 않는다.
- 실행은 다음 형식이며 `ON_ERROR_STOP=1`로 SQL 오류가 발생하면 트랜잭션을 중단한다.

```powershell
psql -v ON_ERROR_STOP=1 -v target_tenant_id=<tenant_id> -f docs/database/20261023/20261023_004_seed_material_common_codes.sql
```

- 스크립트는 단일 트랜잭션이다. 존재하지 않는 tenant 또는 FK 오류로 일부 그룹만 남기지 않고 전체 롤백한다.
- 그룹 삽입은 `(tenant_id, group_code)`, 상세 삽입은 `(group_id, item_code)` 충돌에 `ON CONFLICT DO NOTHING`을 사용한다. 기존 정의는 갱신하거나 삭제하지 않는다.
- 시드의 destructively deleting rollback은 제공하지 않는다. 실행 전에 없던 그룹만 안전하게 특정할 근거가 없으므로, 자동 삭제는 사용자 정의 데이터까지 지울 수 있다.
- 스크립트는 읽기 전용 MCP에 실행하지 않는다. 운영 대상 DB 적용은 별도 승인 및 환경 검증 이후 담당자가 수행한다.

## 품목 소비기한 입력 계약

### 저장값

기존 `tb_material_info.expiryed_status` (`varchar(10) NOT NULL DEFAULT 'NONE'`) 및 `expiryed_count` (`integer NULL`)과 API 필드 `expiryedStatus`, `expiryedCount`를 유지한다. 새 컬럼, API 경로 또는 별도 단위 코드는 추가하지 않는다.

| 기준 | 소비기한 숫자 | 폼 표시 |
| --- | --- | --- |
| `NONE` | 반드시 NULL | 기준 `없음`; 숫자 입력 비활성·비움 |
| `DAY` | 1~2147483647 양의 정수 | 숫자 옆 단위 `일` |
| `MONTH` | 1~2147483647 양의 정수 | 숫자 옆 단위 `개월` |
| `YEAR` | 1~2147483647 양의 정수 | 숫자 옆 단위 `년` |

### 행 폼

- 소비기한 기준과 숫자는 `기타·소비기한` 섹션에서 연속된 order로 배치한다. 넓은 폼에서는 나란히 배치되고 좁은 폼에서는 기존 그리드 열 규칙에 따라 위아래로 표시될 수 있다.
- 숫자 필드 label은 선택값에 맞춰 `소비기한 숫자 (일)`, `소비기한 숫자 (개월)`, `소비기한 숫자 (년)`으로 바뀐다. 기준이 `NONE`이면 숫자 입력을 비활성화하고 값은 비운다.
- `NONE`에서 다른 기준으로 바꾸면 count는 비어 있으므로 사용자가 입력해야 한다.
- 활성 기준끼리 전환할 때는 숫자를 보존한다. 단위가 달라졌다는 것을 새 label로 확인할 수 있다.
- 기준과 숫자의 조합이 유효하지 않으면 행 폼 `적용` 단계에서 숫자 필드 오류를 표시하고 적용을 막는다.
- 코드 그룹 로딩 또는 다른 편집으로 기존 소비기한 값을 자동 수정하지 않는다. 비정상 기존 데이터가 조회되는 경우 화면은 원본을 보존하고 저장 검증 또는 DB 제약 오류를 명시한다.

### 입력 검증과 API

- 프론트 payload 정규화와 행 폼 검증은 status/count 조합을 확인한다. 숫자 null/빈 값은 null로 처리한다. 소수, 0, 음수, `2147483647` 초과, 빈 active count, 값이 남은 `NONE`은 저장 API에 보내지 않는다.
- 백엔드 `MaterialInfoServiceImpl.saveParams`에서 저장 요청을 DAO에 전달하기 전에 동일 조합을 검증한다. 일반 입력 오류는 기존 `IllegalArgumentException` → HTTP 400 흐름으로 반환한다.
- JSON 정수 역직렬화기의 소수 차단 및 Java Integer 범위 제한을 보존한다.
- 배치 저장은 개별 행에 동일한 service validation을 적용하고 기존 단일 트랜잭션/전체 롤백을 유지한다.

## DB 제약 변경

새 제약명은 `ck_tb_material_info_expiryed_pair`다. 기존 `ck_tb_material_info_expiryed_status` 및 `ck_tb_material_info_expiryed_count`는 유지한다.

```sql
ALTER TABLE public.tb_material_info
    ADD CONSTRAINT ck_tb_material_info_expiryed_pair
    CHECK (
        (expiryed_status = 'NONE' AND expiryed_count IS NULL)
        OR
        (expiryed_status IN ('DAY', 'MONTH', 'YEAR') AND expiryed_count > 0)
    );
```

롤백은 위 제약만 제거한다.

```sql
ALTER TABLE public.tb_material_info
    DROP CONSTRAINT ck_tb_material_info_expiryed_pair;
```

forward/rollback과 변경 이력 파일은 `docs/database/20261023` 및 `backend/DATABASE/20261023`에 동일 보관한다. 이력에는 날짜, 테이블, 제약 내용, 저장 호환 영향, 롤백을 적는다. `docs/database/db-schema.md`의 품목 CHECK 설명도 업데이트한다. SQL은 생성/정적 검증까지만 진행하며 운영 DB에는 적용하지 않는다.

3. `frontend/tests/f1-grid-form-modal.test.tsx`에서 동적 label, disabled, 활성/비활성 폼 검증을 테스트한다.
4. `frontend/tests/material-management.test.tsx`에서 status 전환, unit label, 유효/무효 payload 쌍을 테스트한다.
5. `mvn -Dtest=MaterialInfoServiceImplTest test`로 네 가지 정상 조합 및 잘못된 조합을 검증한다.
6. `npm run build`와 두 프론트 집중 테스트를 수행한다.
7. 실제 S-ERP 브라우저에서 375/768/1280px 폼 배치 및 네 기준 동작을 확인하고 영문 소문자·숫자·하이픈 파일명으로 결과 스크린샷을 저장한다.
8. 최종 결과에 실제 MCP DB에 시드나 스키마를 적용하지 않았음을 구분해 기록한다.
