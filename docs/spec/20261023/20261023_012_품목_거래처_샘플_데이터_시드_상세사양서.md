## 확인한 DB 계약

기본 `s-erp-postgresql-readonly`에서 `list_tables` 후 다음 테이블의 컬럼 메타데이터를 직접 확인했다.

- `public.tb_customer_info`
- `public.tb_material_info`
- `public.ids`
- `public.tb_common_code_group`
- `public.tb_common_code_item`

업무 데이터 행, tenant 행, 사용자/계정 데이터, IDS 카운터 값을 조회하지 않았다. 실제 DB에 SQL을 실행하지 않는다.

## 생성 행 계약

### 거래처 100건

| DB 컬럼 | 생성 규칙 |
| --- | --- |
| `tenant_id` | 필수 psql 변수 `target_tenant_id` |
| `customer_id` | 테이블 기본값 시퀀스 |
| `customer_code` | `public.ids`의 `tb_customer_info` 예약 범위에서 6자리로 생성 |
| `customer_name` | `샘플 거래처 001`~`샘플 거래처 100` |
| `cust_name_abbr` | 샘플 번호를 포함한 가상 약칭 |
| `business_no` | 고유한 10자리 테스트 값. 첫 9자리를 순번으로 만들고 표준 가중치 검증 체크섬과 다른 마지막 숫자를 붙여 실재 사업자번호로 사용될 수 없게 함 |
| `business_status_1`, `business_item_1` | 일반적인 샘플 업태/종목 문자열 |
| `cust_memo` | 식별용 마커 `SAMPLE_SEED_20261023` |
| `use_at` | `'Y'` |
| `created_at`, `updated_at` | 실행 시각 |
| 전화/주소/계좌/대표자 관련 선택 컬럼 | NULL, 개인정보 형태의 임의값을 생성하지 않음 |

### 품목 100건

| DB 컬럼 | 생성 규칙 |
| --- | --- |
| `tenant_id` | 필수 psql 변수 `target_tenant_id` |
| `material_id` | 테이블 기본값 시퀀스 |
| `material_code` | `public.ids`의 `tb_material_info` 예약 범위에서 6자리로 생성 |
| `material_name` | `샘플 품목 001`~`샘플 품목 100` |
| `material_spec`, `material_weight`, `safe_invoice` | 각 행의 순번을 사용한 가상 규격/수치 |
| `material_type_code` | 14자 이하인 같은 tenant의 활성 `ITEM_TYPE` 항목 중 순번에 따라 선택 |
| `unit` | 6자 이하인 같은 tenant의 활성 `ITEM_UNIT` 항목 중 순번에 따라 선택 |
| `customer_code` | 같은 스크립트가 만든 거래처 100건 중 동일 순번의 6자리 코드 |
| `material_kind`, `store_method` | 활성 `MATERIAL_TYPE`, `STORE_METHOD` 항목이 있으면 순번에 따라 선택. 없으면 NULL |
| `expiryed_status`, `expiryed_count` | `'NONE'`, NULL |
| `delete_status`, `mat_cata_type` | `'N'`, 빈 문자열 |
| `etc` | 식별용 마커 `SAMPLE_SEED_20261023` |
| `created_at`, `updated_at` | 실행 시각 |

미기재 선택 컬럼은 DB 기본값을 사용하거나 NULL로 둔다. 추가 스키마/API 변경은 없다.

## 실행 절차와 순서

실행자는 데이터베이스 접근 권한을 가진 별도 승인 절차로 다음처럼 실행한다. tenant 값은 명령 실행 시 입력하고 SQL 파일에는 저장하지 않는다.

```text
psql -v ON_ERROR_STOP=1 -v target_tenant_id=<tenant_id> -f <script.sql>
```

1. psql이 `target_tenant_id` 변수를 확인한다. 변수 누락/잘못된 숫자는 오류로 처리한다.
2. 트랜잭션을 시작하고 temp 테이블에 tenant 값을 보관한다.
3. `public.ids`의 `tb_customer_info`, `tb_material_info` 행을 `table_name` 순서로 `FOR UPDATE` 잠근다. 둘 중 하나라도 없으면 오류로 중단하며 카운터 행을 만들지 않는다.
4. `public.tb_customer_info`와 `public.tb_material_info` 각각에 `SHARE ROW EXCLUSIVE` 잠금을 잡는다. 이는 두 테이블 전체에 적용된다. 기존 쓰기 트랜잭션이 끝날 때까지 대기하며, 시드가 끝날 때까지 모든 tenant의 해당 테이블 INSERT/UPDATE/DELETE를 대기시킨다. 일반 SELECT는 허용한다.
5. tenant 존재, `ITEM_TYPE`·`ITEM_UNIT` 활성 항목, 같은 tenant의 샘플 마커/이름/사업자번호 충돌을 확인한다. 조건 불충족 시 `RAISE EXCEPTION`으로 종료한다.
6. 전체 테이블의 1~6자리 숫자형 코드를 대상으로 최댓값을 계산한다. IDS `next_id`와 기존 코드 최댓값+1 중 큰 값을 예약 시작으로 한다. 각 카운터는 100 증가시키며, 반환된 이전 경계에서 정확히 100개 코드를 생성한다.
7. 범위가 1~999999인지, 필요한 코드/옵션이 정확히 준비됐는지 검증한다. 코드 소진/초과 또는 옵션 부재 시 전체 롤백한다.
8. 거래처 100건을 추가하고, 생성된 거래처 코드와 활성 공통코드를 참조해 품목 100건을 추가한다.
9. 마커 기준 실제 삽입 건수가 각각 100인지 트랜잭션 안에서 검증한 다음 커밋한다.

모든 코드 카운터 갱신은 행 생성과 동일 트랜잭션이다. 시드 실행 중 오류나 후행 행 수 검사 실패가 발생하면 데이터와 카운터 변경이 함께 롤백된다. 기존 행은 UPDATE/DELETE하지 않는다. 스크립트 재실행에서 같은 tenant의 이름, 번호, 마커가 발견되면 전부 중단한다.

## 입력 데이터 안전성

- 회사명, 품목명, 대표자명, 주소, 연락처, 계좌 등 실재하는 개인정보를 복사하거나 생성하지 않는다.
- 사업자번호 형태의 샘플 문자열은 중복 검사와 10자리 형식 테스트를 위한 가상 식별자다. 표준 사업자번호 체크섬을 일부러 틀리게 만들어 실재 사업자번호로 사용될 수 없게 한다.
- 공통코드는 tenant별 활성 항목만 사용하고, 필수 `ITEM_TYPE`/`ITEM_UNIT` 부재를 임의 코드로 대체하지 않는다.
- 샘플 marker는 재실행 충돌 검사와 결과 건수 검증에만 사용한다.

## 검증 기준

- Node 내장 테스트에서 양쪽 SQL 파일의 바이트가 동일하고 다음 항목이 있는지 확인한다.
  - 필수 tenant psql 변수 및 `ON_ERROR_STOP`
  - 단일 `BEGIN`/`COMMIT`
  - IDS 카운터 `FOR UPDATE` 후 두 관리 테이블의 `SHARE ROW EXCLUSIVE` 잠금
  - 100건 생성, 6자리 code range, 공통코드 및 중복 충돌 오류 처리
  - 거래처/품목 행의 UPDATE/DELETE 부재
- `node --test tools\tests\test_customer_material_sample_seed.cjs`
- `git diff --check` 및 PowerShell `Get-FileHash -Algorithm SHA256`으로 사본 일치를 점검한다.
- MCP는 읽기 전용 메타데이터 확인에만 사용하며, PostgreSQL 구문을 실제 DB에서 검증하거나 데이터 삽입하지 않는다. 실제 적용 검증은 실행자가 별도 승인 후 수행한다.

## 범위 제외

- 실DB/테넌트 업무 행 조회 및 데이터 쓰기
- DDL, 테이블·컬럼·제약 변경, 공통코드 생성/수정
- 기존 샘플 데이터 자동 갱신/건너뛰기/삭제
- 프론트엔드 및 백엔드 애플리케이션 코드 변경
- 화면 변경이 없으므로 브라우저 스크린샷
