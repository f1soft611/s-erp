# 거래처명 공통 중복 검증 상세 사양

## 기준

- [계획서](../../plan/20261023/20261023_003_거래처명_공통중복검증_계획서.md)
- 기존 필수 검사 중복 제거는 이름 고유성 검사 제거가 아니었다. 기존 구현은 거래처코드만 중복 방지했으며 이번에 이름 정책을 추가한다.

## 프론트 계약

- 컬럼 `validation?: { unique?: boolean }`; 거래처명에 `validation: { unique: true }`.
- 고유값은 문자열 앞뒤 공백 제거 후 비교하며 대소문자는 구분한다. null/undefined/빈 문자열/공백은 고유성 검사에서 제외하고 `required`에 맡긴다. 숫자 0과 boolean false는 유효한 비교값이다.
- 자기 행은 `rowKey` 값으로 제외한다. 신규 행은 다른 신규 행 및 기존 행과 비교하고 수정 draft는 자기 원본을 제외한 최신 활성 행과 비교한다.
- 그리드 필터/정렬/가상화와 무관하게 전체 활성 행을 비교 대상으로 한다. 삭제 표시 행은 제외한다.
- 중복 인덱스는 검증 실행마다 한 번 구성한다. 각 행마다 전체 행을 반복 순회하지 않는다.
- 필수/자리수/범위 검사 후 unique, 기존 사용자 정의 `validate` 순서로 처리한다.
- 오류는 `거래처명 값이 중복되었습니다.` 형식으로 기존 `onValidationErrors`에 전달한다. 폼 적용·저장 차단과 빨간 오류 표시·상단 메시지를 유지한다.
- 서버 검색 결과에 없는 행까지 프론트가 중복 없음으로 보증하지 않는다.

## 백엔드 및 DB 계약

- 등록/수정 모두 필수 이름을 trim 후 같은 tenant에서 `btrim(customer_name) = customerName`으로 검사한다. 사용여부 조건은 넣지 않는다. 수정은 현재 customer ID를 제외한다.
- 같은 이름 충돌은 `이미 사용 중인 거래처명입니다.`로 기존 400 오류 흐름을 사용한다.
- 최종 동시성 방어: `uq_tb_customer_info_tenant_name` unique index on `(tenant_id, btrim(customer_name))`. 이름 NULL은 기존 계약을 유지하고 저장 API는 기존처럼 필수로 검사한다.
- 기존 코드 unique 오류는 기존 메시지를 유지한다. PostgreSQL에서 위 name index가 충돌했다고 확인된 경우에만 이름 오류로 분류한다.
- 배치의 중복도 동일 트랜잭션 안에서 후속 서비스 사전 검사 또는 DB 인덱스로 차단되고 전체 rollback한다.
- 이름 맞교환/해제 후 재사용은 기존 순차 배치 저장의 중간 충돌 제한을 유지한다. 동시 다중행 rename 처리/지연 제약 기능은 범위 밖이다.
- 마이그레이션은 테이블을 잠근 뒤 기존 tenant/name 중복이 있으면 이름/tenant 값을 출력하지 않고 명시적 오류를 낸다. 자동 데이터 정리하지 않는다. 인덱스 생성과 점검은 단일 트랜잭션이다.
- `docs/database/20261023`와 `backend/DATABASE/20261023`에 동일 SQL/변경 이력/rollback을 보관한다. 실제 적용은 별도 운영 승인 대상이다.

## MCP 확인

2026-10-23 기본 `s-erp-postgresql-readonly`에서 `list_tables` → `describe_table(tb_customer_info)` → `pg_indexes` 제한 metadata 조회 완료. 이름 unique index는 없고 tenant/code unique index가 있다. 이 기본 DB의 customer_name은 nullable이며 기존 문서의 tenant 전용 DB 정보와 다르므로 혼동하지 않는다. tenant 업무 행·계정·인증 정보·연결 문자열은 조회하지 않았다.
