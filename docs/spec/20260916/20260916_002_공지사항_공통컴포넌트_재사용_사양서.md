# 20260916_002 공지사항 공통 컴포넌트 재사용 상세 사양서

## 1. 개요

이 작업은 공지사항 화면에 존재하는 피드/첨부/댓글 영역을 재사용 가능한 공통 컴포넌트로 분리한다. 구현 범위는 프론트엔드 화면 구성만 포함하며, 서버 API와 DB는 기존 계약을 유지한다.

구현 목표는 다음과 같다.

- 공지사항 전용 네이밍을 제거하고 기능 중심 이름으로 정리한다.
- 공지사항 페이지는 3개 공통 컴포넌트를 조립하는 구조로 만든다.
- 첨부, 댓글, 피드가 서로 독립적으로 재사용될 수 있게 한다.

## 2. 사용자 요구사항

1. 공지사항 읽기 화면에서 표시되는 피드, 첨부, 댓글을 각각 재사용 가능한 단위로 분리한다.
2. 이름이 `Notice*` 계열처럼 특정 화면에 묶이지 않도록 기능 중심으로 설계한다.
3. 기존 공지사항 화면 동작과 스타일은 유지한다.
4. 같은 패턴이 다른 게시판 또는 피드형 화면에도 바로 재사용 가능해야 한다.

## 3. 비기능 요구사항

- 기존 MUI 스타일 체계와 간격, 색상 톤 유지
- 다크모드 대응 유지
- 파일명 줄임, 확장자 아이콘, 버튼 액션 유지
- 댓글 작성/답글 버튼 구조 유지
- 접근성 속성(aria-label, button label) 유지

## 4. 컴포넌트 설계

### 4.1 FeedList

`FeedList`는 게시글 카드, 메타 정보, 본문, 액션 버튼 영역을 표현하는 공통 피드 컴포넌트이다.

#### 필수 props

- `items`: 피드 데이터 배열
- `isDark?: boolean`
- `expandedItemId?: string | number | null`
- `onToggleExpand?: (id: string | number) => void`
- `onToggleLike?: (id: string | number) => void`
- `onToggleBookmark?: (id: string | number) => void`
- `onEdit?: (item: FeedItem) => void`
- `onDelete?: (id: string | number) => void`

#### 책임

- 카드 레이아웃 렌더링
- 작성자, 날짜, 조회수 메타 표시
- 본문 요약/확장 처리
- 상태 뱃지, 수정/삭제 버튼 렌더링

### 4.2 AttachmentList

`AttachmentList`는 파일 목록을 공통으로 표시하는 컴포넌트이다.

#### 필수 props

- `files: Array<{ id: string; name: string; size?: number; extension?: string }>`
- `isDark?: boolean`
- `mode?: 'view' | 'edit'`
- `showActions?: boolean`
- `onDownload?: (id: string) => void`
- `onRemove?: (id: string) => void`

#### 책임

- 파일명, 확장자 아이콘, 파일 크기 표시
- 다운로드 또는 삭제 버튼 렌더링
- 빈 목록이면 `null` 또는 빈 상태 UI 반환

### 4.3 CommentThread

`CommentThread`는 본문 아래의 댓글/답글 트리를 표시하고, 입력/답글 액션을 처리하는 공통 컴포넌트이다.

#### 필수 props

- `comments: CommentNode[]`
- `draft?: string`
- `onDraftChange?: (value: string) => void`
- `onSubmitComment?: (content: string) => void`
- `onReply?: (commentId: string | number) => void`
- `isDark?: boolean`

#### 책임

- 작성자, 시각, 내용 표시
- 중첩 댓글 트리 렌더링
- 답글 버튼 및 입력 영역 제공
- 기존 공지사항 댓글 UX와 동일하게 동작

## 5. 데이터 계약

본 작업은 기존 `NoticeFeedItem`, `NoticeAttachmentListItem`, `NoticeCommentItem` 구조를 재사용한다.

- 새 컴포넌트는 기존 데이터를 변환해서 받아도 된다.
- 공통 컴포넌트는 상위 화면에서 데이터 변환이 이루어진 형태를 주입하는 것만으로 동작해야 한다.
- 외부 화면이 다른 구조를 넘길 수 있으나, 핵심 필드는 `id`, `name`, `content`, `author`, `time` 등으로 표준화한다.

## 6. 화면 동작 규칙

1. 공지사항 페이지에서 기존 목록/확장/댓글 기능이 동일하게 동작해야 한다.
2. 첨부 목록은 다운로드 또는 삭제 액션이 유지되어야 한다.
3. 댓글 트리는 답글 구조와 입력 UI를 유지해야 한다.
4. 피드 카드 본문은 기존 `summary`/`body` 확장 로직을 유지해야 한다.
5. 다크모드/기본 라이트모드 모두 동일한 구성으로 표시된다.

## 7. 구현 원칙

- 페이지 전용 로직을 공통 컴포넌트로 이동시키되, 페이지 이벤트 핸들러는 유지한다.
- 공통 컴포넌트는 사이드 이펙트 없이 렌더링 중심으로 구성한다.
- `groupware` 네이밍을 강제하지 않고, 기능 중심 네이밍을 우선한다.
- 공지사항 페이지는 단순 조립 화면이 되도록 구성한다.

## 8. 검증 기준

### UI 기준

- 공지사항 목록이 기존과 동일하게 보인다.
- 첨부 아이콘, 파일명, 액션 버튼이 동일하게 렌더링된다.
- 댓글/답글이 기존 구조대로 보인다.
- `NoticeFeedList`가 사용자의 행동을 그대로 유지한다.

### 코드 기준

- TypeScript 타입 검사 통과
- shared 컴포넌트 경로와 import 경로가 일관적이다.
- 불필요한 중복 코드가 제거된다.

### DB/백엔드 기준

- DB 스키마 변경 없음
- 기존 API 계약 유지
- DB 영향도 평가: 없음

## 9. 완료 조건

- 피드/첨부/댓글이 각각 독립적인 공통 컴포넌트로 분리됨
- 공지사항 페이지는 이 3개 컴포넌트를 조립하는 방식으로 동작함
- 기존 UX가 유지됨
- No DB/API 변경
- 빌드 및 관련 테스트가 통과함
