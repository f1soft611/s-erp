# 20260916_003 공지사항 첨부 API 공통화 상세 사양서

## 1. 목적

공지사항 첨부 파일 기능을 공지사항 전용 로직에서 분리하고, 다른 기능에서도 동일하게 재사용할 수 있도록 공통 첨부 API를 정립한다.

이 작업은 기존 공지사항 화면 동작과 API 응답을 유지하면서, 구현 구조만 공통 계층으로 재사용 가능한 형태로 정리하는 것을 목표로 한다.

## 2. 설계 원칙

1. 공통 첨부 기능은 그룹웨어/공지사항 전용 의존성을 가지지 않는다.
2. 공지사항 기존 동작은 그대로 유지하고, 내부적으로 공통 서비스에 위임한다.
3. API 경로와 응답 구조는 기존 공지사항 호출부에 영향이 없도록 보존한다.
4. 공통 첨부 모듈은 `tenantId`, `ownerType`, `ownerId`, `fileMeta`, `uploadedBy`를 중심으로 동작한다.

## 3. 공통 첨부 모듈 구조

### 3.1 패키지 구성

- `egovframework.com.attachment.controller.AttachmentApiController`
- `egovframework.com.attachment.service.AttachmentService`
- `egovframework.com.attachment.service.impl.AttachmentServiceImpl`
- `egovframework.com.attachment.domain.model.AttachmentFileVO`

### 3.2 책임 분리

- Controller: HTTP 엔드포인트 처리
- Service: 파일 유효성 검증, MinIO 저장, DB 메타 저장, 삭제/다운로드 처리
- VO: 첨부 메타 정보 표현
- NoticeBoardService: 공지사항 전용 데이터 연동만 담당하도록 축소

## 4. 공통 API 계약

### 4.1 첨부 파일 업로드

- Method: `POST`
- Path: `/api/v1/attachments/upload`
- Auth: `Authorization` required
- Content-Type: `multipart/form-data`
- Request params:
  - `file`: 첨부 파일 객체 (필수)
  - `ownerType`: 첨부 소유 타입, 예: `NOTICE`, `BOARD`, `FEED` (필수)
  - `ownerId`: 소유 객체 식별값, 예: 게시글 ID (필수)
  - `tenantId`: 인증 컨텍스트에서 추출 가능하므로 별도 전달이 없을 수도 있음
- Response:
  - `resultVO` 구조 유지
  - `item` 안에 첨부 메타 포함
  - 필드 예시:
    - `attachmentId`
    - `fileName`
    - `objectKey`
    - `bucketName`
    - `fileSize`
    - `mimeType`
    - `uploadedBy`
    - `ownerType`
    - `ownerId`
    - `storageProvider`

### 4.2 첨부 파일 목록 조회

- Method: `GET`
- Path: `/api/v1/attachments`
- Query params:
  - `ownerType`
  - `ownerId`
- Response:
  - `resultList` 배열
  - 각 요소는 첨부 메타 정보

### 4.3 첨부 파일 삭제

- Method: `DELETE`
- Path: `/api/v1/attachments/{attachmentId}`
- Auth: `Authorization` required
- Response:
  - 성공 메시지
  - 기존 공지사항 API와 동일한 ResultVO 스타일 유지

### 4.4 첨부 파일 다운로드

- Method: `GET`
- Path: `/api/v1/attachments/{attachmentId}/download`
- Auth: `Authorization` required
- Response:
  - 파일 스트림
  - `Content-Disposition: attachment` 처리

## 5. 기존 공지사항 API 호환성

### 5.1 유지 경로

공지사항 기존 경로는 그대로 유지한다.

- `POST /api/v1/groupware/boards/notice/posts/{postId}/attachments`
- `DELETE /api/v1/groupware/boards/notice/attachments/{boardFileId}`
- `GET /api/v1/groupware/boards/notice/attachments/{boardFileId}/download`

### 5.2 위임 방식

- 공지사항 컨트롤러는 기존 입력값을 공통 첨부 서비스 입력 형태로 변환하여 호출한다.
- 내부 공통 서비스가 실제 업로드/삭제/다운로드를 처리한다.
- 공지사항 전용 메서드 이름은 유지하되, 구현은 공통 로직 위임으로 변경한다.

## 6. 응답 및 에러 처리 규칙

### 6.1 성공 응답

- 공지사항 기존 응답 구조를 유지한다.
- `ResultVO` with `ResponseCode.SUCCESS` used by existing system.

### 6.2 공통 에러 규칙

- 400: 파일이 비어 있거나 필수 값 누락
- 401: 인증되지 않은 사용자
- 404: 첨부 파일 없음
- 500: MinIO 저장/삭제/조회 실패

## 7. 권한 및 인증 정책

- 첨부 파일 API는 인증된 사용자만 접근 가능하다.
- `tenantId`는 인증 principal 또는 요청 컨텍스트에서 검증한다.
- 공지사항 API와 공통 첨부 API 모두 동일한 인증 로직을 사용한다.

## 8. DB 및 스키마 영향

- 본 작업은 기존 첨부 메타 저장 방식을 재사용한다.
- 신규 테이블을 추가하거나 기존 테이블 구조를 변경하지 않는다.
- 따라서 DB 스키마 변경 스크립트는 작성하지 않는다.

## 9. 구현 제한 사항

- 서버 API 구조를 임의로 대폭 변경하지 않는다.
- 기존 공지사항 응답 포맷을 깨지 않도록 유지한다.
- 첨부 기능은 공통 DTO/Service 중심으로 분리하되, 공지사항 전용 활용 사례는 어댑터로 처리한다.

## 10. 검증 기준

- 기존 공지사항 첨부 업로드 기능이 정상 동작한다.
- 첨부 삭제가 정상적으로 Soft Delete 또는 삭제 처리된다.
- 다운로드 시 파일명과 MIME 타입이 유지된다.
- 공통 서비스가 다른 도메인에서도 동일한 방식으로 재사용 가능하다.
- Maven 테스트/빌드가 통과한다.
