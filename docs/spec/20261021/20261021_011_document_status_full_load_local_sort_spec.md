# 20261021_011 문서현황 전체 조회 및 로컬 정렬·필터 상세사양서

## 1. 요구사항 및 원인

문서현황 사용자는 화면에 표시되는 페이지 이동 UI가 아니라 검색조건과 날짜 범위에 맞는 전체 목록을 조회한다. 조회 후 정렬 및 헤더 필터를 조작해도 목록 API를 재호출하지 않아야 하며, 헤더 필터 메뉴가 표시되고 실제 적용되어야 한다.

현재 프런트엔드는 `F1GridDataSource`에 `pageSize: 200`을 지정한다. F1Grid는 첫 200행을 요청한 다음 스크롤이 끝에 가까워질 때 다음 `offset`을 추가해 요청한다. 페이지 버튼은 없지만 내부적으로 서버 페이징이 수행된다. F1Grid는 데이터소스에서 `sortState` 변경 시 첫 페이지를 다시 요청하고, 문서현황 서비스는 정렬 정보를 API에 전달한다. 문서현황 그리드의 `disableFiltering`은 헤더 필터 메뉴를 숨긴다.

백엔드 `searchDocuments`는 기본 `limit=200` 및 최대 `limit=200`을 강제하고 Mapper SQL은 항상 `LIMIT/OFFSET`을 적용한다. 프런트만 수정해서는 전체 기간 결과를 가져올 수 없다.

## 2. API 계약

### 2.1 전체조회 모드

- 검색 경로: 기존 `GET /api/v1/groupware/approvals/documents/search`
- 프런트 요청: `scope`와 검색조건을 전달하되 `offset`, `limit`, `sortField`, `sortDirection`은 보내지 않는다.
- 페이징 파라미터가 모두 없으면 검색조건에 맞는 모든 결과를 정렬 순서대로 반환한다.
- `totalRowCount`는 검색조건으로 일치한 전체 행 수를 계속 반환한다.
- 기본 정렬은 현재 정책인 `updatedAt DESC`, 동률 시 `electronicApprovalId DESC`를 유지한다.
- tenant/사용자 권한, 검색 파라미터 검증, 결과 필드 및 응답 모양을 유지한다.

### 2.2 기존 페이징 모드

- `offset` 또는 `limit`이 하나라도 제공되면 기존 페이징 모드로 처리한다.
- 누락된 offset은 0, 누락된 limit은 200으로 기본 설정한다.
- offset 음수, limit 1 미만 또는 200 초과는 기존대로 HTTP 400으로 거부한다.
- Mapper SQL에는 `LIMIT` 및 `OFFSET`이 포함되고 기존 정렬/필터 및 전체 건수 쿼리는 유지한다.
- API의 응답은 두 모드 모두 `resultList`, `totalRowCount`를 포함하는 기존 구조를 유지한다.

### 2.3 SQL/DB 범위

- 기존 `selectRelatedDocumentPage` SQL의 정렬과 검색조건 fragment를 재사용한다.
- 전체조회에서는 limit/offset 파라미터를 매퍼에 전달하지 않고 SQL의 `LIMIT/OFFSET` 절을 생략한다.
- 기존 페이징 요청에는 limit/offset 절을 유지한다.
- 신규 테이블, 컬럼, 인덱스 또는 데이터 변경은 없다.

## 3. 프런트엔드 계약

### 3.1 서비스

- `searchDocumentStatus(filters, signal)`은 기존 URL과 검색 필터 직렬화를 재사용한다.
- 이 메서드는 offset/limit/정렬 필드를 query에 넣지 않고 `resultList`와 `totalRowCount`를 기존 방식대로 검증한다.
- 요청의 AbortSignal을 API 클라이언트로 전달한다.
- 기존 `createDocumentStatusDataSource`의 페이지·정렬 변환 및 응답 검증은 보존한다.

### 3.2 페이지와 그리드

- 문서현황은 초기 기본 날짜, 세션에서 복원한 검색조건, 사용자가 실행한 검색조건에 맞춰 전체조회 API를 호출한다.
- 응답 완료까지 Grid 로딩 상태를 표시하고 모든 결과를 `rows`로 전달한다.
- F1Grid의 `dataSource` 및 문서현황의 데이터소스 오류 콜백은 사용하지 않는다. 요청 오류는 기존 `PageMessageArea` 및 재시도 경로로 전달한다.
- 필터 조건을 실행해 새 검색을 할 때만 목록 API를 다시 요청한다. 정렬 변경, 헤더 필터 적용/해제는 전부 로컬 데이터에서 처리한다.
- 문서현황의 `disableFiltering` 옵션을 제거한다.
- 검색조건 적용 시 선택 행을 해제한다. 현재 문서 수정·처리 완료 뒤에는 전체조회 목록을 다시 로드한다.
- 날짜 기본값, 검색 세션 저장/복원/초기화, 빈 결과 안내, 상세 오버레이, 엑셀 내보내기 및 기존 읽기 전용 컨텍스트 메뉴를 보존한다.

## 4. 오류 및 로딩

- API 응답 검증 오류와 네트워크 오류는 기존 `Error` 정책으로 처리하며 빈 결과처럼 성공 형태로 숨기지 않는다.
- 검색조건 또는 재시도 변경으로 이전 요청이 무효화되면 AbortController로 이전 요청을 취소한다.
- 오류는 기존 메시지 영역에 명시하고 `다시 조회` 버튼으로 동일한 검색조건을 다시 실행한다.
- 전체 행은 메모리에 보관하므로 응답 건수 증가에 따른 초기 응답 시간 및 메모리 증가를 허용한다. 검색조건과 기본 결재신청 기간은 기존과 동일하게 적용한다.

## 5. 검증 기준

### 백엔드

- offset/limit 없는 요청은 전달된 날짜 및 상세검색 조건과 tenant/사용자 제한을 적용해 전체 목록을 반환한다.
- offset/limit 없는 매퍼 SQL에는 `LIMIT`/`OFFSET`이 없고 정렬/검색조건은 유지된다.
- offset/limit이 있는 호출은 기존 서비스 파라미터와 SQL의 200행 최대 페이징 계약을 유지한다.
- 검색 결과 count 쿼리와 응답 shape에는 회귀가 없다.

### 프런트엔드

- 초기 및 상세검색 API 요청에 `offset`, `limit`, `sortField`, `sortDirection`이 없다.
- 200건보다 많은 응답도 전체 행 수로 그리드에 전달된다.
- 문서현황 헤더 필터 메뉴가 열리고 실제 전체 행에 필터를 적용한다.
- 정렬 및 필터 적용/해제 전후 문서검색 API 호출 수가 증가하지 않는다.
- 새 검색, 재시도, 세션 복원/초기화, 날짜 기본값, 선택/상세 패널, 오류/빈 결과에 대한 기존 테스트가 통과한다.

### 문서 및 브라우저

- 375px, 768px, 1280px에서 목록과 헤더 메뉴가 잘리거나 겹치지 않는지 브라우저로 확인한다.
