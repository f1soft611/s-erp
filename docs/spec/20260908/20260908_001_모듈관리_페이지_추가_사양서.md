# 모듈 관리 페이지 추가 상세 사양서

## 1. 문서 정보

- 작업지시서: `docs/directions/20260908/20260908_001_모듈관리_페이지_추가_작업지시서.md`
- 계획서: `docs/plan/20260908/20260908_001_모듈관리_페이지_추가_계획서.md`
- 작업 분류: `bounded`
- 대상 영역: 프론트엔드 중심, 백엔드 기존 API 보완 포함
- DB 스키마 변경: 없음

## 2. 목표

환경설정 > 시스템관리 하위에 모듈 관리 페이지를 추가한다. 화면은 권한 관리 페이지의 상단 경로, 조회/저장 액션, 검색 영역, 메시지 영역, F1-Grid 패턴을 따르고, 모듈 관리는 단일 F1-Grid로 구성한다.

## 3. 사용자 흐름

1. 사용자는 대시보드 좌측 메뉴에서 환경설정 > 시스템관리 > 모듈관리를 선택한다.
2. 화면 진입 시 `/api/v1/system/modules`로 모듈 목록을 조회한다.
3. 조회 결과는 모듈 관리 F1-Grid에 표시된다.
4. 사용자는 검색 입력으로 모듈 코드, 모듈명, 아이콘명, 루트 경로를 필터링한다.
5. 사용자는 F1-Grid 컨텍스트 메뉴의 행 추가로 신규 모듈 행을 만든다.
6. 사용자는 기존 행을 직접 편집하거나 선택 행을 삭제한다.
7. 변경사항이 생기면 상단 저장 버튼이 활성화된다.
8. 저장 성공 시 목록을 재조회하고 dirty 상태를 해제한다.
9. 저장 실패 시 페이지 메시지 영역에 오류를 표시하고 변경 상태를 유지한다.

## 4. 화면 구성

### 4.1 PageHeader

- breadcrumb: 전달받은 `breadcrumbItems`가 있으면 그대로 사용한다.
- fallback breadcrumb: `[selectedModule.name, currentMenuName]`
- description: `content.description`
- actionGroups:
  - 조회: read 권한이 true일 때 표시, 클릭 시 모듈 목록 재조회
  - 저장: create 또는 update 권한이 true일 때 표시, dirty 상태이고 저장 중이 아닐 때 활성화

### 4.2 PageSearchArea

- 검색 입력 1개를 제공한다.
- placeholder: `모듈 코드/명/경로/아이콘 검색`
- aria-label: `모듈 검색`
- `TextField`는 전역 MUI margin 영향을 피하기 위해 `margin="none"`을 명시한다.
- 검색어 변경은 클라이언트 필터로 처리한다.

### 4.3 PageMessageArea

- 조회, 저장, 삭제, 필수값 검증 실패 메시지를 표시한다.
- 닫기 버튼을 누르면 메시지를 빈 문자열로 초기화한다.

### 4.4 콘텐츠 영역

- `ModuleManagementPanel` 하나만 렌더링한다.
- 카드 또는 패널 스타일은 기존 권한 관리/메뉴 관리 페이지의 테두리, shadow 없음, 내부 padding 패턴과 맞춘다.
- 모바일에서는 검색 입력이 한 줄 전체 너비를 사용하고, 그리드는 내부 스크롤로 보존한다.

## 5. F1-Grid 사양

### 5.1 기본 설정

- rowKey: `id`
- ariaLabel: `F1-GRID 모듈 관리`
- rowHeight: `32`
- minRowHeight: `32`
- maxRowHeight: `320`
- showCheckbox: `false`
- createRow: 신규 모듈 기본값 반환
- editorPlugins: 모듈 코드, 모듈명, 아이콘명, 루트 경로, 정렬 순서, 사용 여부 편집 허용
- canExportExcel: 페이지 권한의 excel 값 사용
- excelFileName: `module-management-export`

### 5.2 컬럼

| field | headerName | type | editable | 설명 |
| --- | --- | --- | --- | --- |
| `moduleCode` | 모듈 코드 | text | true | 저장 필수값, 백엔드 `moduleCode` |
| `moduleName` | 모듈명 | text | true | 저장 필수값, 백엔드 `moduleNm` |
| `iconName` | 아이콘명 | text | true | 백엔드 `iconNm`, 빈 값 허용 |
| `moduleUrl` | 루트 경로 | text | true | 백엔드 `moduleUrl`, 빈 값 허용 |
| `sortOrder` | 정렬 순서 | number | true | 백엔드 `sortOrder`, 숫자 변환 실패 시 0 |
| `menuCount` | 메뉴 수 | number | false | 백엔드 `menuCount`, 삭제 가능 여부 판단 참고 |
| `use` | 사용 여부 | checkbox | true | 백엔드 `useAt`, true는 `Y`, false는 `N` |

### 5.3 신규 행 기본값

```ts
{
  id: `new-module-${Date.now()}`,
  moduleCode: '',
  moduleName: '',
  iconName: 'Folder',
  moduleUrl: '',
  sortOrder: 0,
  menuCount: 0,
  use: true,
}
```

### 5.4 dirty 상태

- `insertedRows`, `updatedRows`, `deletedRows` 중 하나라도 있으면 dirty true로 본다.
- 변경 집합이 모두 비면 dirty false로 본다.
- 저장 성공 후 재조회와 grid key 갱신으로 F1-Grid 기준 데이터를 교체한다.

## 6. API 계약

### 6.1 모듈 목록 조회

- Method: `GET`
- URL: `/api/v1/system/modules`
- 권한: 인증 사용자, 기존 서버 정책 적용
- Response body:

```json
{
  "resultList": [
    {
      "moduleId": 1,
      "tenantId": 1,
      "moduleCode": "GROUPWARE",
      "moduleNm": "그룹웨어",
      "iconNm": "FileText",
      "moduleUrl": "/groupware",
      "sortOrder": 1,
      "useAt": "Y",
      "menuCount": 2,
      "createdAt": "2026-08-31T00:00:00",
      "updatedAt": "2026-09-08T00:00:00"
    }
  ]
}
```

### 6.2 모듈 등록

- Method: `POST`
- URL: `/api/v1/system/modules`
- 권한: `PLATFORM_ADMIN` 또는 `TENANT_ADMIN`
- Request body:

```json
{
  "moduleCode": "QUALITY",
  "moduleNm": "품질관리",
  "iconNm": "ClipboardCheck",
  "moduleUrl": "/quality",
  "sortOrder": 3,
  "useAt": "Y"
}
```

- Success: HTTP 201, `item`에 등록된 모듈 반환
- Validation error: `INPUT_CHECK_ERROR`, 메시지 표시
- 필수값: `moduleCode`, `moduleNm`

### 6.3 모듈 수정

- Method: `PUT`
- URL: `/api/v1/system/modules/{id}`
- 권한: `PLATFORM_ADMIN` 또는 `TENANT_ADMIN`
- Request body: 등록 요청과 동일
- Success: HTTP 200, `item`에 수정된 모듈 반환
- 백엔드 보완 기준: `moduleCode`가 요청에 있으면 중복 검증 후 `tb_module.module_code`에 반영해야 한다.
- Validation error:
  - 모듈 코드 누락: `모듈 코드는 필수입니다.`
  - 모듈명 누락: `모듈명은 필수입니다.`
  - 중복 코드: `이미 사용 중인 모듈 코드입니다.`

### 6.4 모듈 삭제

- Method: `DELETE`
- URL: `/api/v1/system/modules/{id}`
- 권한: `PLATFORM_ADMIN` 또는 `TENANT_ADMIN`
- Success: HTTP 200
- 제한: 하위 메뉴가 존재하면 기존 서버 메시지 `하위 메뉴가 존재하는 모듈은 삭제할 수 없습니다.`를 표시한다.

## 7. 프론트엔드 데이터 정규화

### 7.1 API VO

```ts
interface SystemModuleVO {
  moduleId?: unknown;
  tenantId?: unknown;
  moduleCode?: unknown;
  moduleNm?: unknown;
  iconNm?: unknown;
  moduleUrl?: unknown;
  sortOrder?: unknown;
  useAt?: unknown;
  menuCount?: unknown;
}
```

### 7.2 화면 행 변환

- `moduleId`는 `String(value ?? '')`로 변환한다.
- `moduleCode`, `moduleNm`, `iconNm`, `moduleUrl`은 문자열로 변환한다.
- `sortOrder`, `menuCount`는 `Number(value)`가 유효하지 않으면 0으로 둔다.
- `useAt`이 `N`이면 `use: false`, 그 외는 `use: true`로 둔다.

### 7.3 저장 요청 변환

```ts
{
  moduleCode: row.moduleCode.trim(),
  moduleNm: row.moduleName.trim(),
  iconNm: row.iconName.trim() || null,
  moduleUrl: row.moduleUrl.trim() || null,
  sortOrder: Number.isFinite(Number(row.sortOrder)) ? Number(row.sortOrder) : 0,
  useAt: row.use ? 'Y' : 'N',
}
```

## 8. 권한 정책

- read: 조회 버튼 표시와 조회 동작 허용 여부에 사용한다.
- create/update: 저장 버튼 표시와 저장 동작 허용 여부에 사용한다.
- delete: 선택 행 삭제 동작 허용 여부에 사용한다.
- excel: F1-Grid 내보내기 허용 여부에 사용한다.
- `selectedMenuPermissions`가 없으면 기존 권한 관리 페이지와 같이 기본 read/write 허용 관례를 따르되, 삭제는 명시 권한이 있을 때만 허용한다.

## 9. 예외 처리

- 목록 조회 실패: `모듈 목록을 불러오지 못했습니다.` 또는 서버 오류 메시지 표시
- 저장 실패: 서버 오류 메시지 또는 `모듈 저장에 실패했습니다.` 표시
- 삭제 실패: 서버 오류 메시지 표시
- 필수값 실패: `모듈 코드와 모듈명은 필수입니다.` 표시
- 저장 중 중복 클릭: 저장 in-flight Promise를 재사용하거나 저장 버튼을 비활성화해 중복 요청을 막는다.
- 부분 저장 실패: 성공한 작업 체크포인트를 유지해 재시도 시 성공 작업을 중복 호출하지 않는다.

## 10. 라우팅 및 메뉴 노출

- `DashboardContent`는 다음 조건에서 `ModuleManagementPage`를 렌더링한다.

```ts
selectedModule.id === 'settings' && currentPageKey === 'modules'
```

- 메뉴 경로는 `/settings/system/modules`를 사용한다.
- 로컬 fallback 메뉴인 `adminUserMenus.json`에는 `모듈관리` 항목을 추가한다.
- 실제 백엔드 메뉴 데이터에는 같은 path가 존재해야 화면 선택이 가능하다. 기존 DB에 메뉴가 없는 것으로 확인되면 별도 DB 데이터 변경 작업으로 분리하거나, 사용자 승인 후 seed DML 문서를 추가한다.

## 11. 반응형 기준

- 375px: 검색 입력은 전체 너비로 줄바꿈되고, 그리드는 패널 내부에서 가로 스크롤을 허용한다.
- 768px: 검색 입력과 액션 영역이 겹치지 않아야 한다.
- 1280px: 권한 관리/메뉴 관리와 같은 밀도의 관리 화면으로 표시한다.
- 텍스트가 버튼, 헤더, 셀 영역과 겹치면 안 된다.

## 12. 테스트 기준

### 12.1 프론트엔드

- 페이지 진입 시 API 결과가 그리드에 표시된다.
- 검색어가 모듈 코드, 모듈명, 아이콘명, 루트 경로에 적용된다.
- 기존 행 수정 시 저장 버튼이 활성화된다.
- 저장 클릭 시 PUT 요청 payload가 API 계약과 일치한다.
- 신규 행 필수값 누락 시 API 호출 없이 오류 메시지가 표시된다.
- 삭제 권한이 있을 때 선택 행 삭제 후 저장 시 DELETE 요청이 발생한다.

### 12.2 백엔드

- `updateModule`은 `moduleCode`를 필수값으로 검증한다.
- `updateModule`은 중복이 아닌 `moduleCode`를 DAO update 파라미터로 전달한다.
- MyBatis `updateModule` SQL은 `module_code`를 함께 갱신한다.

### 12.3 브라우저 검증

- 환경설정 > 시스템관리 > 모듈관리 클릭으로 화면에 진입한다.
- 1280px 데스크톱 캡처에서 상단 경로, 조회/저장 버튼, 검색, 메시지 영역, 그리드가 보인다.
- 375px 모바일 캡처에서 검색 영역과 그리드가 겹치지 않는다.

## 13. DB 영향

- DB 스키마 변경은 없다.
- 기존 테이블 `tb_module`과 기존 컬럼을 사용한다.
- 스키마 SQL, 변경 이력 Markdown, 롤백 SQL은 작성하지 않는다.
- 결과 문서와 작업 원장에는 `DB 스크립트: 해당 없음, 기존 스키마 영향 검토 완료`를 기록한다.

## 14. 완료 기준

- 모듈 관리 메뉴 선택 시 모듈 관리 페이지가 렌더링된다.
- 권한 관리 페이지와 같은 상단 경로, 버튼, 검색, 메시지, F1-Grid 패턴을 따른다.
- 모듈 목록 조회, 신규 등록, 기존 수정, 삭제 저장 흐름이 API와 연동된다.
- 모듈 코드와 모듈명 필수값 오류가 사용자에게 표시된다.
- 저장 성공 후 재조회로 dirty 상태가 해제된다.
- 백엔드 수정 API는 `moduleCode` 변경을 실제 DB에 반영한다.
- 프론트/백엔드 테스트, 빌드, 브라우저 캡처 결과가 결과 문서에 기록된다.
