# 20261120_002 매출마감관리 조회 API 및 프론트엔드 상세사양서

기준: [작업지시서](../../directions/20261120/20261120_002_매출마감관리_프론트엔드_작업지시서.md), [계획서](../../plan/20261120/20261120_002_매출마감관리_프론트엔드_계획서.md), [설계](../../superpowers/specs/2026-11-20-sales-closing-front-end-design.md)

## 1. 범위와 데이터 경계

- 영업관리 > 매출관리 > 매출마감관리 프론트 화면과 읽기 API를 추가한다.
- 운영 화면은 API 결과만 표시하고 상세/요약 행을 임의 생성하지 않는다.
- 선택 동작과 거래처 필터는 타입이 정의된 순수 로직으로 구현하고, 테스트에서만 최소 fixture를 사용한다.
- API는 기존 출하·수주·거래처·품목·거래명세서 테이블을 사용한다. 신규 테이블/컬럼과 실제 DB 적용은 범위에 포함하지 않는다.
- 매출마감 메뉴 seed/롤백을 포함하며 실제 DB에는 적용하지 않는다.

## 2. 검색 영역

- `PageSearchArea`의 통합검색에는 출하번호, 수주번호, 거래처, 품목을 안내하는 placeholder를 사용한다.
- 검색 화살표를 눌러 기존 상세검색 패널을 연다.
- 상세검색에는 필수 출하일 기간 검색과 출하현황과 동일한 당월 기본값, 기존 오늘/이번주/이번달/전월/최근 30일 빠른 선택을 제공한다.
- 거래처는 단일 필드에서 여러 거래처를 선택한다. 매출처/수주처 역할별 필드는 만들지 않는다.
- 복수 선택 도움창은 기존 `MasterPickerDialog`와 `CommonDialog`, 기존 거래처 검색 콜백을 사용한다. 체크박스 선택은 임시 상태이고 적용 버튼을 눌러야 외부 필터 값에 반영된다. 취소/닫기는 임시 선택을 폐기한다.
- 기존 단건 거래처/품목/구매처 도움창 사용자의 props와 콜백은 그대로 유효해야 한다.
- 상세검색 고객 선택은 draft/applied 값을 분리한다. 상세검색 적용 시 draft를 applied로 반영하고, reset 시 선택 고객과 날짜 조건을 기본값으로 되돌린다. 적용하지 않고 상세검색 패널을 닫으면 고객 draft를 applied 값으로 복원한다.
- 거래처 필드는 출하일과 같은 상세검색 반응형 그리드의 바로 다음 필드로 배치하고 별도 상단 여백을 두지 않는다. 선택이 1건이면 기존 코드·거래처명을 표시하고, 여러 건이면 첫 거래처명과 `외 N건`으로 요약한다. 선택한 거래처는 필드 아래에 개별 칩으로 표시하며, 칩의 제거 버튼은 해당 draft 거래처만 즉시 제외하고 검색 적용은 상세검색의 조회 버튼에서 수행한다.
- `PageSearchArea`는 `detailExtraContent`를 상세검색 필드와 같은 반응형 그리드 안에 표시하고 `detailExtraActiveFilterCount`(적용한 거래처 수)를 적용 필터 배지/접근성 설명의 기존 상세조건 수에 더한다. 기존 사용처는 두 prop이 없어도 동작이 바뀌지 않는다.

## 3. 화면 레이아웃

- 페이지 제목은 `매출마감관리`, 모듈은 `sales`, 페이지 키는 `revenue-closing`이다.
- 검색 아래 메인 영역은 좌측 매출대상 상세와 우측 거래처별 요약으로 구성한다.
- 데스크톱(1280px)은 좌측 상세가 가용 폭 대부분을 차지하고 우측 요약은 고정 폭을 사용한다. 태블릿/모바일은 요약을 위, 상세를 아래로 쌓는다.
- 매출대상 상세 F1Grid는 `selectionMode="row"`로 클릭 행 전체를 선택하며 셀 범위 선택, 체크박스 및 다중 행 선택은 사용하지 않는다.
- 통합검색에서 적용된 검색어는 출하번호, 수주번호, 거래처 코드/명, 품목 코드/명에 공통 F1Grid 빨간색 강조를 적용한다. 조회 대기 중에는 상세 F1Grid의 공통 로딩 오버레이를 표시한다.
- 페이지 컨테이너는 flex/grid 자식의 `minWidth: 0`, `minHeight: 0`을 지정해 외부 overflow를 막는다.
- 세로 overflow는 좌측 상세 F1Grid에만 허용한다. 요약 영역에는 별도 세로 스크롤 컨테이너를 두지 않는다. 상세 F1Grid의 가로 overflow는 그리드 내부에 둔다.

## 4. 매출대상 상세 F1Grid

API 응답의 상세 행은 출하 상세 한 행 단위다. 컬럼은 다음 업무 정보를 표현한다.

| 필드 | 헤더 | 표시 |
| --- | --- | --- |
| `deliveryNo` | 출하번호 | 출하 문서 식별자 |
| `deliveryDt` | 출하일 | 기준일 |
| `orderNo` | 수주번호 | 연계 수주 식별자 |
| `customerName` | 거래처 | 통합 거래처 |
| `materialCode` | 품목코드 | 품목 식별자 |
| `materialName` | 품목명 | 품목 설명 |
| `closingStatus` | 마감상태 | 마감/미마감 |
| `quantity` | 수량 | 출하 기준 수량 |
| `salesAmount` | 매출금액 | 공급가 |
| `vatAmount` | 부가세 | 부가세 |
| `totalAmount` | 합계 | 매출금액과 부가세 합계 |

- 행 key와 `storageKey`는 매출마감 전용의 안정적인 이름을 사용한다.
- Excel 내보내기는 메뉴 권한의 `excel` 값이 true인 경우에만 활성화한다.
- 거래처 요약 필터가 선택되면 해당 `customerId` 행만 전달하고, 전체 선택이면 모든 행을 전달한다.
- 통합검색, 날짜, 선택 거래처는 적용 검색조건으로 API 요청에 전달한다.

## 5. 거래처별 요약

- 우측 고정 패널은 제목, 전체 매출대상 요약, 선택 가능한 compact 거래처 카드 목록으로 구성한다. 전체·마감·미마감 값을 명확한 라벨과 절제된 색상으로 빠르게 비교할 수 있게 하며, 고객명·코드·출하건수를 좁은 카드에 읽기 쉽게 배치한다. 거래처가 많아도 패널 높이를 과도하게 차지하지 않도록 카드 높이와 간격을 줄인다.
- 조회 중에는 요약 영역에 스켈레톤 카드를 표시하고 기존 요약 카드는 숨긴다.
- 각 거래처 카드를 누르면 좌측 상세를 해당 `customerId`로 필터링한다. 전체 카드는 상세 필터를 해제한다.
- 요약 집계 건수는 출하 상세 행 수가 아니라 고유 출하 헤더 수다. 활성 거래명세서가 연결된 출하는 마감, 그렇지 않은 출하는 미마감으로 집계한다.
- 별도의 세로 스크롤을 만들지 않는다. API 결과가 비어 있으면 기존 빈 상태 규칙을 사용하며 가짜 수치나 임의 row cap을 넣지 않는다.

## 6. 매출마감 조회 API

- 경로: `GET /api/v1/sales/revenue-closings/search`.
- 파라미터: 필수 `deliveryDtFrom`, `deliveryDtTo`(ISO 날짜); 선택 `keyword`; 반복 가능 `customerIds`(양의 정수, 미지정 시 전체 거래처).
- 응답: `details`(출하 상세별 매출대상 행 배열), `customerSummaries`(거래처별 `totalCount`, `closedCount`, `openCount` 배열).
- 상세는 `tb_sales_delivery_hd`와 `tb_sales_delivery_dt`를 기준으로 수주·거래처·품목을 tenant-qualified join하고 출하일 기간과 선택 조건을 적용한다. 통합검색은 출하번호, 수주번호, 거래처 코드/명, 품목 코드/명에 적용한다.
- `closingStatus`는 같은 tenant의 활성 `tb_sales_statement_hd` 존재 여부로 결정한다. 활성 거래명세서는 `(tenant_id, sales_delivery_id)`당 최대 하나라는 partial unique index 계약을 따른다.
- 거래처 요약은 동일 조회조건에 해당하는 출하 헤더를 거래처별로 그룹화하고, 출하 헤더를 한 번만 세어 중복 상세 행이 건수를 부풀리지 않게 한다.
- 조회 권한은 메뉴 `revenue-closing`의 `READ`를 확인하고 tenant ID는 인증 사용자에서만 취한다. 요청의 tenant ID는 받지 않는다.
- 스키마 변경 없이 기존 테이블만 조회하며 실제 DB에 데이터 변경을 하지 않는다.

## 7. 메뉴 seed 및 롤백

### DB MCP 확인 근거

- `s-erp-postgresql-readonly`에서 `list_tables`를 실행해 `tb_module`, `tb_menu`, `tb_menu_permission`, `tb_role_menu_permission`, `tb_permission`, `tb_role`, `tb_user_menu_favorite` 존재를 확인했다.
- `describe_table`에서 모듈/메뉴의 tenant/module/menu code, 이름, URL, parent, sort, use 컬럼과 메뉴-권한/역할-메뉴-권한/역할/즐겨찾기 연결 컬럼을 확인했다.
- 제한된 metadata 조회에서 `tb_menu`의 unique key `(tenant_id, menu_code)`, `tb_menu_permission`의 `(menu_id, permission_id)`, `tb_role_menu_permission`의 `(role_id, menu_id, permission_id)`를 확인했다.
- 제한 조회에서 현재 SALES 메뉴 구조에 활성 `매출관리` 부모가 없음을 확인했다. tenant ID 및 실제 메뉴 행 값은 이 문서에 기록하지 않는다.

### 삽입 계약

- 스크립트 경로: `docs/database/20261120/20261120_001_seed_sales_revenue_closing_menu.sql` 및 동일한 `backend/DATABASE` 복사본.
- 메뉴 부모: `SALES_REVENUE`, 이름 `매출관리`, URL `/sales/revenue`.
- 메뉴 자식: `SALES_REVENUE_CLOSING`, 이름 `매출마감관리`, URL `/sales/revenue/revenue-closing`; 프론트 page key는 `revenue-closing`.
- parent가 현재 없으므로 부모 그룹과 신규 화면을 함께 등록한다. 기존 영업 메뉴 그룹을 이동하거나 변경하지 않는다.
- 실행 전 명시적으로 승인된 target tenant ID를 `v_tenant_id`에 지정한다. 기본값은 `NULL`이며 지정하지 않으면 예외로 중단한다. tenant를 조회·추정하거나 SQL을 실제 DB에 적용하지 않는다.
- 자식 메뉴 권한은 화면이 조회 전용이므로 READ, EXCEL을 등록한다. 해당 tenant의 활성 `SALES_DELIVERY_STATUS` 역할 권한 중 READ/EXCEL을 복사한다. 다른 tenant 역할은 건드리지 않는다.
- 각 menu code가 다른 모듈/경로/부모/이름/use 상태로 이미 존재하면 예외 처리한다. 정상 동일 상태의 재실행은 중복 행을 만들지 않는다.
- 롤백은 이 기능의 역할 권한, 메뉴 권한, 즐겨찾기 및 예상 경로의 자식 메뉴만 삭제한다. 부모는 이 자식 삭제 뒤 다른 child가 없고 예상 code/path인 경우에만 삭제한다.
- 날짜별 seed/rollback/change record를 `docs/database/20261120`와 `backend/DATABASE/20261120`에 byte-identical하게 보관한다. DB 변경 이력에 날짜, 적용 대상, 영향 범위 및 롤백 방법을 기록한다.

## 6. 고객 복수 선택 계약

- `MasterPickerDialog`의 기존 단건 계약은 유지한다.
- 복수 모드는 입력된 `selectedValues`에서 임시 선택 상태를 시작하고, 결과 체크박스가 임시 선택을 토글한다.
- 적용은 현재 선택 목록을 한 번 호출하며 닫는다. 취소/닫기는 변경을 전달하지 않는다.
- 검색어 변경이나 새 결과 로딩이 기존 선택을 제거하지 않는다.
- 요청 세대 확인, 로딩/검색 오류/빈 결과 구분은 기존 단건 도움창 동작을 보존한다.
- `CustomerMultiPicker`는 고객 이름/코드를 접근 가능한 필드에 표시하고, 여러 이름이 넘칠 때 폭을 깨뜨리지 않는다. 도움창 제목/설명/크기 및 닫기 접근성은 기존 `CommonDialog` 패턴을 따른다.
