## 2. 백엔드 `egovframework.let.system.accounts` (A 계정 관리)
`controller` / `service` / `service/impl` / `domain/model` / `domain/repository`, Mapper는 `mapper/let/system/accounts`. 기존 `roles`·`policies`와 같은 구조와 응답 형식을 따른다. 모든 API는 현재 테넌트로 제한하고 권한은 `ST_ACCOUNTS` 메뉴 권한을 따른다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/v1/system/accounts` | 목록. 쿼리 `keyword`(이름·사번·로그인 ID·부서 통합), `status`(`ALL`/`ACTIVE`/`DISABLED`/`LOCKED`/`RETIRED`) |
| PUT | `/api/v1/system/accounts/{loginId}/status` | 본문 `{ "useAt": "Y"/"N" }` 허용/미허용 |
| POST | `/api/v1/system/accounts/{loginId}/password-reset` | 임시 비밀번호 생성·저장, 변경 강제 Y, 잠금 해제. 응답에 임시 비밀번호를 1회만 포함 |
| POST | `/api/v1/system/accounts/{loginId}/unlock` | `locked_at` 비우고 실패 횟수 0 |
| PUT | `/api/v1/system/accounts/{loginId}/roles` | 본문 `{ "roleIds": [..] }` 역할 전체 교체 |

- 목록 행: `loginId`, `loginCode`, `userNm`, `employeeNo`, `departmentNm`, `positionNm`, `roles[{roleId, roleNm}]`, `useAt`, `locked`, `retired`, `passwordChangeRequired`, `passwordChangedAt`, `hasPhoto`. 상태 표시는 우선순위 `퇴직 > 미허용 > 잠김 > 사용`이고 필터 `RETIRED`는 퇴직일이 오늘 이하인 사원이다.
- 검증(서버, 위반 시 400/409와 한국어 메시지):
  - 자기 자신 미허용 불가.
  - 역할은 1개 이상, 같은 테넌트의 사용 중인 역할만 허용.
  - 관리자 역할(`PLATFORM_ADMIN`·`TENANT_ADMIN`·`ADMIN`)을 가진 마지막 계정의 관리자 역할 제거·미허용 불가.
  - 다른 테넌트의 `loginId`는 404.
- 임시 비밀번호(사용자 확정: 서버 발급 + 로그인 시 변경 필수): `SecureRandom`으로 12자(대문자·소문자·숫자 각 1자 이상, 혼동 문자 제외). 저장은 기존 방식 `EgovFileScrty.encryptPassword(비밀번호, 로그인 ID)`. 서버 로그와 감사 정보에 평문을 남기지 않는다.
- 모든 쓰기는 `updated_at = now()`, `updated_by`를 기록한다.
- **퇴사자 로그인 차단(C)**: 일반 로그인 쿼리(`actionLogin`)와 토큰 갱신·현재 사용자 조회 쿼리에 `(u.retire_dt IS NULL OR u.retire_dt > CURRENT_DATE)`를 추가한다. 별도 상태를 저장하지 않으므로 퇴직일을 지우면 로그인이 다시 가능하다.

## 3. 로그인 보안 (잠금 정책)
> 구현 중 확인한 사실: **토큰 갱신(`/auth/refresh`)은 DB를 보지 않고 토큰 안의 정보만 믿었다**. 그래서 미허용·퇴직 처리해도 갱신 토큰(7일)이 살아 있으면 계속 쓸 수 있었다. 갱신 때 계정 상태(허용·사용 중 사원·미퇴직)를 확인하도록 고쳤다(§2). 액세스 토큰은 15분이라 미허용은 최대 15분 안에, 갱신 시점에 확정 반영된다.

`EgovLoginServiceImpl.actionLogin`과 `SystemPolicyService`를 확장한다. 정책 읽기는 `getStatementIssueMode`와 같은 방식으로 `getLoginLockPolicy(tenantId)`(사용 여부, 기준 횟수)를 추가한다. 값이 없거나 범위(3~10) 밖이면 미사용으로 본다.

1. 정책이 **미사용**이면 현재 로직과 완전히 같다(실패 누적·잠금 검사 없음).
2. 사용이면 로그인 시도 전에 입력 ID(로그인 ID 또는 이메일)로 계정을 찾는다. 이미 `locked_at`이 있으면 비밀번호가 맞아도 거부하고 실패 횟수는 올리지 않는다.
3. 로그인 실패이고 계정이 존재하면 `login_attempt_count`를 1 올리고, 기준 횟수에 도달하면 `locked_at = now()`.
4. 로그인 성공이면 `login_attempt_count`를 0으로 되돌린다.
5. 응답(`resultCode` 300) 메시지: 일반 실패는 기존 문구, 잠김은 "계정이 잠겼습니다. 관리자에게 문의해 주세요."로 구분한다. 존재하지 않는 계정은 누적하지 않고 기존 실패 문구를 쓴다.
6. 관리자 해제·비밀번호 초기화로 `locked_at`과 횟수를 비운다. 시간 경과 자동 해제는 없다.
7. 정책을 미사용으로 바꾸면 기존 `locked_at`이 남아 있어도 로그인을 막지 않는다(화면에는 "잠김(정책 미사용)"으로 표시).

## 4. 최초 로그인 비밀번호 변경 강제 (B)
- 표시 대상: `password_change_required = 'Y'`. 관리자 초기화와 사원등록 계정 발급(2-1)이 Y로 설정한다. 사원등록 발급은 이 컬럼을 쓰도록 수정하고 `password_changed_at`은 변경 시에만 채운다. 기존 계정은 기본 N이라 영향이 없다.
- 로그인 응답 `resultVO`에 `passwordChangeRequired`(boolean)를 추가하고 JWT에 같은 클레임을 담는다(`LoginVO` 필드 추가).
- `JwtAuthenticationFilter`: 클레임이 true이면 `PUT /api/v1/users/me/password`, 로그아웃, `/auth/refresh`, `/auth/login-jwt*` 외의 모든 `/api/**` 요청을 403 `{ "code": "PASSWORD_CHANGE_REQUIRED" }`로 거부한다.
- `PUT /api/v1/users/me/password` 성공 시 `password_change_required = 'N'`, `password_changed_at = now()`로 바꾸고 새 비밀번호는 현재 비밀번호와 달라야 한다(서버 검증 추가).
- `/auth/refresh`는 DB의 플래그를 읽어 새 토큰의 클레임을 정한다(관리자가 로그인 중인 계정을 초기화한 경우를 반영).
- 프론트: 로그인 응답(`resultVO.passwordChangeRequired`)이 true이거나 API가 `PASSWORD_CHANGE_REQUIRED`를 돌려주면 세션에 표시하고 메뉴 없이 비밀번호 변경 화면만 보여 준다(`ProtectedRoute`). **구현 중 확정**: 변경에 성공하면 새 토큰을 받지 않고 로그아웃한 뒤 "비밀번호를 변경했습니다. 새 비밀번호로 다시 로그인해 주세요." 안내(정보 색)를 로그인 화면에 보여 준다. 변경 화면에는 로그아웃 버튼을 둔다.

## 5. 사진 정책·내 정보 연동 (C)
- `ProfileSettingsServiceImpl.updateMyProfile`: 정책 `PROFILE_PHOTO_EDIT_MODE = ADMIN_ONLY`이면 요청의 `profileImage`가 현재 값과 다를 때 400 "사진은 관리자만 변경할 수 있습니다."로 거부한다(이메일·도장 이미지 변경은 영향 없음). 허용이면 `tb_login_account.profile_image`와 함께 **사원 마스터 `tb_user.photo_image`도 같이 기록**한다.
- `MyProfileVO`에 `photoEditable`(정책 결과), `employeeNo`, `positionNm`을 추가하고 내 정보 화면에서 사번·직위를 읽기 전용으로 보여 준다. 사진 변경 버튼은 `photoEditable`이 false이면 비활성과 안내 문구를 보여 준다.
- 사진이 바뀌었는지는 화면이 받은 값을 그대로 돌려보냈는지로 판단한다(저장된 값과 문자열이 같으면 변경 없음). 변경 없음이면 다시 해석·재압축하지 않고 사원 마스터도 덮어쓰지 않는다. 정책이 관리자 전용이면 사진 삭제도 변경으로 보고 거부한다.
- 관리자(사원등록)의 사진 저장은 2-1 동작 그대로 `tb_user`와 `tb_login_account`에 함께 기록한다.
