# 매출마감 선택 마감 및 화면 개선 상세사양서

기준: [작업지시서](../../directions/20261120/20261120_003_매출마감_선택마감_스크롤_및_요약개선_작업지시서.md), [계획서](../../plan/20261120/20261120_003_매출마감_선택마감_스크롤_및_요약개선_계획서.md)

## 1. 마감 선택 및 처리 계약

- 상세 그리드는 F1Grid 체크박스 선택 열과 row multi-select를 사용한다.
- 응답 상세 행의 `rowId`는 `sales_delivery_detail_id`다. 체크된 행 중 `closingStatus === 'OPEN'`인 행의 `rowId`를 중복 제거해 제출한다. `salesDeliveryId`는 표시/출하 문서 연결 용도이며 마감 집계 키가 아니다.
- 같은 출하의 여러 품목 행은 각각 독립 마감한다. 같은 출하에서 선택된 상세 행은 한 거래명세서의 상세로 저장한다. 이미 마감된 행의 체크박스는 비활성화하고 서버 검증도 유지한다.
- 선택 가능한 미마감 상세 행이 없으면 마감 버튼은 비활성화한다. 버튼은 CREATE 권한이 있을 때만 표시한다.
- 마감 여부는 `tb_sales_delivery_dt.revenue_closed_at` 유무로만 판정한다. 출하 등록 자동 발행이나 일반 거래명세서 발행만으로는 `OPEN` 상태를 바꾸지 않는다.
- 실행 전 CommonDialog에 실제 처리 대상인 미마감 상세 행 수를 표시한다. 취소 시 선택/데이터는 유지하고 API를 호출하지 않는다.
- 실행 시 `getSystemDate()`로 서버 기준일을 조회한 뒤 batch close API를 호출한다. 날짜 조회 실패 및 API 실패는 오류로 표시하고 성공으로 처리하지 않는다.
- 성공 시 선택을 비우고 현재 검색 조건으로 상세/요약을 재조회한다.
- API: `POST /api/v1/sales/revenue-closings/close`, body `{ salesDeliveryDetailIds: number[], statementDt: 'YYYY-MM-DD' }`.
- 성공 응답은 `{ closedCount, items }` 형태이며 `closedCount`는 마감 기록된 상세 수, `items`는 이번 처리에서 새로 발행한 거래명세서 목록이다. 이미 거래명세서가 있는 행만 선택했으면 `items`는 빈 배열이어도 정상 성공이다. 요청은 빈 목록을 금지하고 양의 정수 ID만 허용한다. 중복 ID는 서버에서 정규화한다.
- 거래명세서 일반 등록은 발행 가능한 출하를 복수 선택하고, 선택한 출하들의 상세를 F1Grid에서 선택한다. 여러 출하번호의 상세를 한 거래명세서로 묶되 모든 출하는 같은 거래처여야 한다. 신규 등록은 명세일·선택한 `salesDeliveryDetailIds`·비고를 전송하고, 기존 문서 보기/수정은 상세 목록을 읽기 전용으로 표시한다.
- `GET /api/v1/sales/statements/source-deliveries`는 거래처 ID와 미발행 상세 ID 목록을 출하별로 제공한다. 이미 발행된 상세는 조회 대상에 포함하지 않으며, 일부 상세만 미발행이면 출하 행은 남기고 미발행 상세만 선택할 수 있다. 출하등록 AUTO 자동 발행은 기존 동작대로 새 출하의 모든 상세를 한 문서로 발행한다.
- 기존 API 호출 호환을 위해 일반 등록 요청에서 상세 ID 목록이 생략된 경우 서버는 해당 출하의 모든 발행 가능 상세를 사용한다. 화면은 항상 명시적인 비어 있지 않은 선택 목록을 전송한다.
- API는 인증 tenant 범위에서 상세와 상위 출하를 잠근다. 비활성/미존재 상세 또는 이미 매출마감된 상세가 하나라도 있으면 전체 요청을 롤백하고 명시적 오류를 반환한다. 일반 발행 API는 선택 상세가 이미 발행됐거나 선택 출하의 거래처가 다르면 거부한다.
- 선택한 상세 ID는 여러 출하에 걸쳐도 허용하되 해당 출하들의 거래처 ID가 모두 같은지 서버에서 검증한다. 상세별 snapshot은 선택한 ID만 저장하고 거래명세서 상세의 nullable `sales_delivery_detail_id`가 각 원본 출하 상세를 식별한다.
- 마감 batch에서 선택 상세에 활성 거래명세서가 이미 있으면 중복 발행하지 않는다. 새로 발행이 필요한 상세만 거래처별 한 문서에 묶고, 선택한 모든 상세에는 `revenue_closed_at`과 `revenue_closed_by`를 기록한다.
- 기존 활성 거래명세서 상세는 `(tenant_id, sales_delivery_id, line_no)`로 원본 출하 상세와 연결해 backfill하지만, 마감 기록은 생성하지 않는다. 과거/자동 발행만 된 행은 명시적으로 마감 처리할 때까지 `OPEN`이다.
- 거래명세서 soft-delete 시 상세 원본 ID 링크를 해제하지만 매출마감 timestamp는 변경하지 않는다.
- 활성 거래명세서 헤더의 출하 단위 unique index를 제거하고 거래명세서 상세의 원본 출하 상세 ID에 유일 인덱스를 둔다. 한 출하의 서로 다른 라인 또는 같은 거래처의 서로 다른 출하 라인을 같은 문서로 발행할 수 있지만 동일 라인은 중복 발행할 수 없다.
- 거래명세서 상세 목록과 인쇄물은 각 행의 원본 출하번호/출하일을 표시한다. 헤더의 출하번호는 상세의 원본 출하번호 목록을 요약해 보여준다.
- API는 `revenue-closing` 메뉴 CREATE 권한을 요구한다. DB seed는 CREATE 메뉴 권한과 동일 tenant의 활성 `SALES_STATEMENT_CREATE` 역할 grant를 제공한다.

## 2. 반응형 레이아웃과 스크롤

- 1280px에서는 상세 그리드가 남은 폭을 차지하고 거래처 요약은 고정 폭 오른쪽 패널이다. 페이지 바깥 세로 overflow는 숨기고 상세 그리드와 요약 고객 목록이 각각 내부 스크롤을 갖는다.
- 768px 및 375px에서는 요약을 상세 위에 놓고 바깥 페이지를 세로 스크롤할 수 있게 한다. 상세 영역은 최소 표시 높이를 보장해 검색/요약이 길어져도 상세 그리드가 잘리지 않는다.
- 좁은 화면의 거래처 목록은 요약 패널 내부에서 스크롤되어 요약 전체가 상세를 밀어내지 않게 한다.
- grid/flex 자식은 `minHeight: 0`, `minWidth: 0`을 유지한다. 가로 overflow는 F1Grid 내부에 한정한다.

## 3. 거래처별 요약 디자인

- 큰 카드 반복 대신 한 줄 요약 KPI(전체/마감/미마감)와 compact 행 목록을 사용한다.
- 행은 거래처명/코드를 왼쪽에 두고 전체 건수, 마감 건수, 미마감 건수를 정렬된 열로 표시한다. 모바일에서는 명칭과 합계가 첫 줄, 마감/미마감 수가 둘째 줄인 밀도 높은 행으로 배치한다.
- 마감은 녹색 계열, 미마감은 주의 색상 계열을 사용하되 텍스트 라벨을 함께 표시한다.
- 선택 행은 테두리/배경/좌측 강조선으로 구분하고 `aria-pressed`를 유지한다. 전체 요약 선택 시 기존 상세 필터가 해제된다.
- 거래처 목록 컨테이너에 `minHeight: 0; overflow-y: auto`를 적용한다. 요약 영역의 제목과 전체 KPI는 스크롤해도 보이게 둔다.
- 조회 중 기존 스켈레톤을 유지하고 조회 실패/빈 데이터에는 가짜 건수를 표시하지 않는다.

## 4. 권한/데이터/오류 경계

- API tenant는 로그인 사용자에서만 가져오고 request tenant 필드는 받지 않는다.
- 그리드 상태 표시는 `Chip` 배지를 사용해 마감/미마감을 텍스트와 색상으로 구분한다.
- API는 `revenue-closing` CREATE를 검사한다. 프론트 버튼은 페이지 권한 `create`로 제어한다.
- 모든 출하 및 거래명세서 조회/기록은 tenant 키를 조건으로 한다. 조회 상태/요약은 출하 상세의 명시적 마감 필드 기준으로 상세 행 수를 집계한다.
- 동시 마감 충돌은 `409 CONFLICT` 등 기존 API 오류 규칙으로 사용자에게 명시한다. batch 중 하나의 오류도 전체 batch rollback이어야 한다.
- 기준일 조회 오류/권한 오류/검증 오류/충돌 오류에서 성공 메시지나 성공 상태를 표시하지 않는다.

## 5. 검증

- 프론트 테스트: 매출마감과 거래명세서 발행의 상세 multi-selection, 같은 출하번호의 상세별 집계, 마감 완료 행 체크박스 비활성화, 상태 배지, 확인 취소, 날짜/API 오류, 성공 후 재조회 및 선택 초기화, 권한 처리.
- 요약 테스트: 고객 선택 필터, 전체 선택 해제, 다수 행 목록 overflow 구조, loading/empty state.
- 백엔드 테스트: 양수 상세 ID/빈 입력/날짜 검증, tenant scope, 상세·출하 잠금, 상세별 활성 명세 충돌, 선택 상세 snapshot 저장, AUTO 전체 상세 발행, batch transaction rollback, CREATE permission.
- build/lint 및 관련 Maven 테스트를 수행한다.
- 375/768/1280px에서 작은 화면의 페이지 스크롤과 요약 내부 스크롤, 넓은 화면의 그리드/요약 독립 스크롤을 브라우저로 확인한다.
- 결과 스크린샷은 tenant 실제 데이터를 노출하지 않는 빈 상태 또는 mock fixture로 기록한다.
