|---|---|

CHECK: `order_source IN ('ORDER','DIRECT','JOIN')`. 인덱스: `(tenant_id, order_dt DESC)`, `(tenant_id, user_id)`. 행 삭제·수정 API는 없다(이력은 추가만).
메뉴: `HR_INFO_ORDER` "인사명령"(`/hr/info/order-manage`, 인사정보 아래, 순서 30). 권한 READ·CREATE는 사원관리(`HR_INFO_EMPLOYEE`) 역할 권한을 복사한다.

## 2. 명령 유형 (현재 구현된 사원 항목 기준)
| 코드 | 이름 | 변경항목 | 명령 후 값 입력 |
|---|---|---|---|
| TRANSFER | 부서이동 | DEPARTMENT(`department_id`) | 부서 선택(사용 중 부서) |
| PROMOTION | 승진(직위) | POSITION(`position_code`) | 직위 공통코드 |
| GRADE_UP | 승급(직급) | LEVEL(`level_id`) | 직급 공통코드 |
| EMPLOYMENT_TYPE_CHANGE | 근무형태변경 | EMPLOYMENT_TYPE | 근무형태 공통코드 |
| LEAVE | 휴직 | SUSPEND_DT(+ BACK_DT 비움) | 날짜(기본 명령일) |
| RETURN | 복직 | BACK_DT | 날짜(기본 명령일) |
| RETIRE | 퇴직 | RETIRE_DT | 날짜(기본 명령일) |
| (자동) JOIN | 입사 | JOIN_DT·DEPARTMENT·POSITION | 신규 등록 시 자동 |
| (자동) DIRECT_EDIT | 직접 수정 | 위 항목 중 변경분 | 사원관리 수정 시 자동 |

## 3. 처리 규칙
- 권한: 테넌트 관리자 + 메뉴 권한(CREATE=처리, READ=조회).
- 명령일: 필수, 오늘 이하. 미래 날짜는 400.
- 대상: 재직·휴직 사원(퇴직 제외), 1명 이상, 한 요청에 중복 사원 불가.
- 값 검증(유형별): 부서이동·승진·승급·근무형태변경은 **현재와 같은 값이면 거절**, 부서는 사용 중 부서, 코드는 공통코드에 있어야 함. 휴직은 이미 휴직 중이면 거절, 복직은 휴직 중이어야 하고 복직일 ≥ 휴직일, 퇴직은 퇴직일 ≥ 입사일.
- 휴직: 새 휴직일을 쓰고 기존 복직일을 비운다(상세 2행: `SUSPEND_DT`, 값이 있었으면 `BACK_DT`).
- 사원 정보 변경은 사원 서비스(`updateEmployee`)를 거친다: 현재 사원 값에 변경항목만 바꿔 저장하므로 필수값·날짜 검증, 부서 사용 여부 확인이 그대로 적용된다. 어느 한 사원이라도 실패하면 **전체 롤백**하고 `"<사원명>: <사유>"` 오류(HTTP 400/404/409 유지).
- 이력 기록: 처리 1회 = 헤더 1건(출처 `ORDER`) + 사원별 변경항목 상세. 직접 수정은 사원 저장 1회 = 헤더 1건(유형 `DIRECT_EDIT`, 출처 `DIRECT`, 명령일 오늘) + 추적 항목 중 **실제로 값이 바뀐 것만** 상세. 신규 등록은 헤더 1건(유형 `JOIN`, 출처 `JOIN`, 명령일 입사일) + 입사일·부서·직위 상세(명령 전 없음). 변경이 없으면 이력을 만들지 않는다.
- 인사명령으로 처리한 변경은 사원 서비스가 직접 수정 이력을 중복 기록하지 않도록 출처를 구분해서 넘긴다.
- 처리 완료 응답: `{ orderId, count, items:[{ userId, userNm, fieldCode, preName, postName }] }`.

## 4. API (`/api/v1/hr/orders`)
- `GET /types`: 명령 유형 목록 `{ code, name, fieldCode, inputKind('department'|'code'|'date'), codeGroup }`(READ).
- `POST /process`: 요청 `{ orderType, orderDt:'YYYY-MM-DD', remark, items:[{ userId, postValue }] }`. 부서·코드는 ID/코드, 날짜는 `YYYY-MM-DD`. 응답 3절.
- `GET /history?from=&to=&keyword=&orderType=&source=`: 상세 단위 목록(처리일시 내림차순, 최대 500건). 행: `orderId, createdAt, orderDt, orderType, orderTypeName, source, userId, userNm, employeeNo, fieldCode, fieldName, preName, postName, remark, createdByName`. `keyword`는 사원명·사번.
- 모두 관리자 전용(비관리자는 403).

## 5. 화면 (`pages/hr/order`, 라우트 `/hr/info/order-manage`)
- 구성: PageHeader(제목은 메뉴 이름) + **탭 2개: "인사명령 처리", "처리 내역"**. 사원관리와 같은 레이아웃·메시지 영역 규칙을 따른다.
- **처리 탭**: ① 명령 입력 줄(명령 유형 선택, 명령일[기본 오늘, 오늘 이하], 명령 후 값[유형별 컨트롤: 부서 선택 도움창 / 공통코드 선택 / 날짜(기본 명령일)], 비고). ② "사원 선택" 버튼(사원 선택 도움창 다중 선택)으로 대상 담기, 표(부서·직위·사번·이름·**현재값(명령 전)**·**명령 후 값**(상단 값이 기본, 행에서 수정 가능)·제외 버튼). ③ "발령 처리(N명)" 버튼 → 확인창(유형·명령일·인원) → 처리 후 성공 메시지, 표 초기화, 처리 내역 탭의 조회 갱신. 유형을 바꾸면 명령 후 값과 대상 표의 후 값을 초기화한다.
- **처리 내역 탭**: 조회조건(처리일 기간 기본 최근 1개월, 사원명·사번, 유형, 출처) + 읽기 전용 표(처리일시, 명령일, 사원, 유형, 변경항목, 명령 전, 명령 후, 출처, 처리자, 비고).
- 서버 오류·검증 오류는 상단 메시지 영역에 표시한다. 필수 입력(유형·명령일·대상·명령 후 값) 누락은 해당 칸 오류 표시 + 메시지.
