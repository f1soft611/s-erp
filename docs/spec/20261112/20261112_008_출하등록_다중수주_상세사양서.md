# 출하등록 다중 수주 선택 상세사양

## 1. 사용자 흐름

1. 출하구분을 `수주출하`로 설정하고 수주 도움창을 연다.
2. 검색 결과는 기존 미납 계획 상세 행 단위로 표시한다. 체크박스 선택 열 다음에 `수주번호`와 `계획번호`를 표시하고, 여러 계획 상세에 반복되는 같은 수주번호 셀은 병합한다. 계획번호는 표시 전용이며 클릭 선택은 하지 않는다.
3. 그리드 체크박스는 다중 선택을 지원한다. 행 하나를 체크하면 그 행이 속한 수주의 모든 조회 결과 상세행을 선택 대상으로 취급한다.
4. 하단 `선택`은 선택한 수주별 계획 상세행 전체를 출하 상세로 전달한다. 거래처가 다르면 오류를 표시하고 도움창을 유지한다.
5. 동일 거래처의 수주 여러 개를 선택하면 한 출하 문서의 상세행으로 합친다. 출하 기본정보의 연결 수주번호는 선택된 번호를 `, `로 연결해 표시하고 거래처/장소/배송방법은 첫 선택 수주 값으로 초기화한다.

## 2. UI 및 반응형

- 공통 `CommonDialog`를 유지하고 제목/검색 문구/그리드 접근성 이름은 수주 선택 의미로 변경한다.
- F1Grid의 행 체크박스를 선택 열로 둔다. `수주번호` 셀은 같은 수주 상세행 사이에서 `mergeRows`로 병합하고, 각 계획 상세행에는 표시 전용 `계획번호`와 기존 수주일자/계획일자/거래처/품목/수량 정보를 함께 보여준다.
- `F1Grid` 체크 선택을 켜고 다중 선택을 허용한다. 하단 액션 순서는 `선택`, `닫기`이며 선택 대상이 없으면 선택 버튼을 비활성화한다.
- 같은 거래처 여부가 맞지 않으면 사용자에게 설명 가능한 오류를 표시하고 창을 닫지 않는다.
- 검색/조회 오류는 기존 `PageMessageArea` 패턴을 사용한다.
- 검색 행의 넓은 표는 그리드 내부에서 가로 스크롤한다. 375px, 768px, 1280px에서 실제 브라우저 레이아웃을 확인한다.

## 3. 프론트엔드 데이터 계약

- `SourceOrderRow`는 기존 `salesOrderId`, `salesOrderDetailId`, `salesDeliveryPlanDetailId` 식별자를 유지한다.
- 선택 콜백은 수주별 전체 계획 상세 행 배열을 반환한다. 중복 수주 선택이나 상세 중복은 만들지 않는다.
- `DeliveryRow`에 `salesOrderId`를 보존하며 ORDER 상세 저장 payload의 각 행에 해당 ID를 전달한다.
- 헤더 `salesOrderId`는 첫 선택 수주의 대표 ID를 유지하여 기존 응답/참조를 호환한다. `orderNo`는 선택된 고유 수주번호를 `, `로 표시한다.
- DIRECT payload 및 기존 단일 ORDER payload는 기존 형식을 유지하되, ORDER 상세에 상세별 `salesOrderId`를 추가한다.

## 4. 백엔드 처리

- ORDER 요청의 모든 상세는 양수 `salesOrderId`, 수주 상세 ID 및 계획 상세 ID를 가져야 한다. 각 상세의 수주·품목·거래처·계획 연결을 확인한다.
- 대표 헤더 수주 ID는 요청 상세에서 사용되는 첫 수주 ID와 같아야 한다.
- 수주 헤더는 ID 오름차순으로 잠근다. 모든 수주가 활성·미완료이며 출하 거래처와 일치하는지 확인한다.
- 수주 출하 누계와 계획 delivered 누계를 상세별 원 수주를 기준으로 검증·증감한다. 수정·삭제는 기존 상세와 새 상세를 수주별로 집계해 증감한다.
- 헤더 `orderNo` 응답은 출하 상세에 연결된 고유 수주번호를 정렬된 `, ` 목록으로 반환한다. 현황 행의 `salesOrderId`와 `orderNo`는 해당 상세행의 원 수주를 표시한다.
- DIRECT는 헤더/상세 수주 참조가 모두 NULL이어야 한다. 기존 권한, 오류 상태, 초과출하 정책, 수량/금액 검증은 유지한다.

## 5. DB

- `tb_sales_delivery_dt.fk_sales_delivery_dt_hd_order`(상세 수주 ID가 헤더 대표 수주와 같아야 하는 복합 FK)를 제거한다.
- 상세행별 수주-수주상세 복합 FK, 계획 상세 복합 FK, 헤더/tenant/출하구분 FK는 유지한다.
- 신규 컬럼 또는 업무 데이터 마이그레이션은 없다. 기존 단일 주문 출하는 헤더/상세 참조가 동일하므로 그대로 유지된다.
- 롤백은 상세행 원 수주가 헤더 대표 수주와 다른 레코드가 없을 때만 FK를 복구한다. 다중 수주 문서가 존재하면 명시적으로 실패시켜 데이터 훼손을 방지한다.
## 6. 검증

- 프론트엔드: 여러 수주 선택, 같은 수주 전체행 선택, 다른 거래처 오류, 비활성 버튼, 합쳐진 출하 payload, 기존 단일 수주/직출하 회귀를 확인한다.
- 백엔드: 상세별 수주 저장, 다중 주문 잠금 순서, 거래처 일치, 주문별 수량 증가/감소, 취소/삭제 및 응답의 수주번호 집계를 확인한다.
- DB: 정방향 FK 제거, 롤백 보호 조건, 날짜별 파일 사본 동일성을 확인한다.
- `npm run build`, 관련 Vitest, `SalesDeliveryServiceImplTest`와 mapper/schema contract 테스트를 실행한다.
