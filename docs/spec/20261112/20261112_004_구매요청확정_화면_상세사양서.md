## 1. 상태 전환

```text
REQUESTED(요청) ──확정──▶ CONFIRMED(확정) ──확정 취소──▶ REQUESTED(요청)
                            │
                            └─ 행별 발주대기 마감 Y/N 저장 (상태 변화 없음)
```

| 동작 | 허용 상태 | 아니면 |
| --- | --- | --- |
| 확정 | `REQUESTED` | 409 "이미 확정된 구매요청입니다. 화면을 다시 조회해 주세요." |
| 발주대기 마감 저장 | `CONFIRMED` | 409 "확정된 구매요청만 발주대기 마감을 처리할 수 있습니다." |
| 확정 취소 | `CONFIRMED` | 409 "확정된 구매요청만 확정 취소할 수 있습니다." |

- 모든 상태 전환은 헤더를 `FOR UPDATE`로 잠근 뒤 상태를 확인한다.
- 삭제된 요청(`use_at = 'N'`)과 다른 테넌트 요청은 404.
- 구매요청등록의 수정·삭제는 기존대로 `REQUESTED`에서만 가능하다. 확정 취소 후에는 다시 수정할 수 있다.

## 3. API

기본 경로 `/api/v1/materials/purchase-request-confirms`. 응답은 기존 `ResultVO` 구조를 따른다.

### 3.1 확정 대상 목록 `GET /candidates`

| 파라미터 | 설명 |
| --- | --- |
| `keyword` | 구매요청번호·요청자명·요청 비고 부분일치 |
| `status` | `REQUESTED`(기본) / `CONFIRMED` / `ALL` |

- 정렬: 요청일 내림차순, 구매요청번호 내림차순. 최대 200건.
- 응답 `resultList[]`: `purchaseRequestId`, `requestNo`, `requestDt`, `requesterName`, `requestDeptName`,
  `status`, `detailCount`, `remark`, `confirmDt`.

### 3.2 단건 조회 `GET /{purchaseRequestId}`

`result.item`:

| 구분 | 필드 |
| --- | --- |
| 헤더 | `purchaseRequestId`, `requestNo`, `requestDt`, `requesterName`, `requestDeptName`, `status`, `remark`, `confirmDt`, `confirmerName`, `totalAmt`, `updatedByName`, `updatedAt` |
| 상세 `details[]` | `purchaseRequestDetailId`, `lineNo`, `materialId`, `materialCode`, `materialName`, `materialSpec`, `unit`, `requestQty`, `requestDeliveryDt`, `useType`, `useTypeName`, `requestRemark`, `confirmQty`, `confirmDeliveryDt`, `warehouseId`, `warehouseName`, `orderType`, `orderTypeName`, `supplierId`, `supplierCode`, `supplierName`, `unitPrice`, `currencyCode`, `amount`, `confirmRemark`, `orderCloseAt` |

### 3.3 확정 `POST /{purchaseRequestId}/confirm`

```json
{
  "confirmDt": "2026-11-12",
  "details": [
    {
      "purchaseRequestDetailId": 10,
      "confirmQty": 20,
      "confirmDeliveryDt": "2026-11-19",
      "warehouseId": 1,
      "orderType": "RAW_MATERIAL",
      "supplierId": 5,
      "unitPrice": 1200,
      "currencyCode": "KRW",
      "confirmRemark": null
    }
  ]
}
```

검증(위반 시 400, 행 목록 불일치는 409):

- `confirmDt` 필수.
- `details`의 상세 id 집합이 저장된 상세 행 집합과 정확히 같아야 한다(누락·중복·다른 요청 행 → 409
  "구매요청 상세가 변경되었습니다. 화면을 다시 조회해 주세요.").
- `confirmQty` 필수, 0보다 큰 수, 정수부 13자리·소수 2자리 이내. 0 확정은 없다.
- 모든 행에 `confirmDeliveryDt`, `warehouseId`, `orderType`, `supplierId` 필수.
- `currencyCode` 선택, 영문 대문자 3자리. 비어 있으면 `KRW`.
- `unitPrice` 선택, 0 이상, 소수 2자리 이내.
- `warehouseId`: 같은 테넌트, `disuse_at = 'N'`.
- `orderType`: 같은 테넌트 `PURCHASE_ORDER_TYPE` 사용 중 항목.
- `supplierId`: 같은 테넌트 `tb_customer_info`, `use_at = 'Y'`.
- `confirmRemark` 500자 이내.

저장:

- 상세: 입력값 저장, `amount = round(confirmQty × unitPrice, 2, HALF_UP)`(단가 없으면 0),
  `currency_code = currencyCode`(없으면 `KRW`), `order_close_at = 'N'`, `updated_by/at` 갱신.
- 헤더: `status = 'CONFIRMED'`, `confirm_dt`, `confirmer_id`(로그인 사용자의 `tb_user.user_id`),
  `total_amt = 상세 amount 합계`, `updated_by/at` 갱신.
- 응답: 3.2와 같은 `item`.

### 3.4 발주대기 마감 저장 `PUT /{purchaseRequestId}/order-close`

```json
{ "details": [ { "purchaseRequestDetailId": 10, "orderCloseAt": "Y" } ] }
```

- 일부 행만 보내도 된다. 상세 id는 이 요청의 행이어야 한다(아니면 400). `orderCloseAt`은 `Y`/`N`.
- 값이 바뀐 행만 `order_close_at`, `updated_by/at`을 갱신한다. 응답은 3.2의 `item`.

### 3.5 확정 취소 `POST /{purchaseRequestId}/cancel-confirm`

- 헤더: `status = 'REQUESTED'`, `confirm_dt`·`confirmer_id` NULL, `total_amt = 0`, `updated_by/at` 갱신.
- 상세: 확정 컬럼(`confirm_qty`, `confirm_delivery_dt`, `supplier_id`, `warehouse_id`, `order_type`,
  `unit_price`, `currency_code`, `confirm_remark`) NULL, `amount = 0`, `order_close_at = 'N'`, `updated_by/at` 갱신.
- 응답은 3.2의 `item`.

### 3.6 기본 단가 `GET /unit-price?materialId=&supplierId=&baseDt=`

- `tb_item_partner_price`에서 같은 테넌트, `material_id`, `customer_id = supplierId`,
  `trade_type = '매입'`, `use_at = 'Y'`, `start_dt <= baseDt`, (`end_dt IS NULL` 또는 `end_dt >= baseDt`)인
  행 중 `start_dt` 내림차순, `price_id` 내림차순 첫 행.
- 응답 `result.item`: `{ "unitPrice": 1200, "currency": "KRW" }`, 없으면 `item: null`.
- 거래구분이 매입인 단가만 가져온다. `trade_type`은 단가관리 화면이 저장하는 값(`'매입'`)을 그대로 쓴다
  (MCP 확인). 이후 코드값으로 바뀌면 별도 지시로 수정한다.
- 이후 "기본적용단가" 설정이 생기면 그 단가를 먼저 쓰고, 없을 때 위 규칙을 쓴다(이번 범위 밖).

## 4. 화면

### 4.1 구조 (출하등록과 같은 배치)

```text
┌ PageHeader: 구매자재 > 구매관리 > 구매요청확정   [요청 불러오기] [확정] / [저장] [확정 취소] ┐
├ 구매요청 기본정보                                                                          ┤
│ 구매요청번호 │ 요청일 │ 요청자 │ 요청부서 │ 상태 │ 확정일* │ 확정자 │ 합계금액 │ 요청 비고  │
├ 구매요청 상세 (F1-Grid)                                                                    ┤
│ 요청 정보(읽기 전용) │ 확정수량* │ 확정납기일* │ 입고창고* │ 발주구분* │ 구매처* │ 단가 │ … │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

- 처음에는 빈 화면과 "요청 불러오기로 확정할 구매요청을 선택하세요." 안내를 보여 준다.
- 버튼은 UPDATE 권한이 있을 때만 보인다.
  - `REQUESTED`: [확정]
  - `CONFIRMED`: [저장](발주대기 마감 변경이 있을 때 활성), [확정 취소](확인 대화상자 후 실행)
- 저장하지 않은 변경이 있는 상태에서 다른 요청을 불러오거나 화면을 떠나면 기존 미저장 확인 대화상자를 띄운다.

### 4.2 요청 선택 다이얼로그

- 제목 "구매요청 선택". 검색어 입력, 상태 select(요청·확정·전체, 기본 요청), [검색].
- F1-Grid 컬럼: 구매요청번호(버튼, 클릭 시 선택), 요청일, 요청자, 요청부서, 상태, 품목 수, 확정일, 비고.
- 열리면 기본 조건으로 바로 조회한다.

### 4.3 기본정보

- 구매요청번호·요청일·요청자·요청부서·상태·요청 비고: 읽기 전용.
- 확정일: `REQUESTED`일 때 입력(기본값 오늘), `CONFIRMED`이면 저장값 읽기 전용.
- 확정자: `CONFIRMED`이면 저장된 확정자, 아니면 빈칸.
- 합계금액: 상세 금액 합계(화면 계산, 확정 후에는 저장값).

### 4.4 상세 그리드

| 컬럼 | 편집 | 규칙 |
| --- | --- | --- |
| No, 품목코드, 품목명, 규격, 단위, 요청수량, 요청납기일, 사용용도 | 아니오 | 요청 정보 |
| 확정수량 | 요청일 때 | 필수, 0보다 큰 수, 소수 2자리. 불러올 때 기본값 = 요청수량 |
| 확정납기일 | 요청일 때 | 필수. 기본값 = 요청납기일 |
| 입고창고 | 요청일 때 | select(사용 중 창고), 필수. 기본값 없음 |
| 발주구분 | 요청일 때 | select(`PURCHASE_ORDER_TYPE`), 필수 |
| 구매처 | 요청일 때 | 거래처 선택 다이얼로그(코드 셀), 필수 |
| 구매처명 | 아니오 | 선택한 거래처 이름 |
| 단가 | 요청일 때 | 선택, 0 이상. 구매처 선택(변경) 시 3.6 기본 단가로 채움, 없으면 빈칸 |
| 통화 | 아니오 | 기본 단가의 통화, 없으면 KRW |
| 금액 | 아니오 | 확정수량 × 단가 (단가 없으면 0) |
| 확정비고 | 요청일 때 | 선택, 500자 이내 |
| 발주대기 마감 | 확정일 때 | 체크박스(Y/N) |

- 확정 상태에서는 확정 입력 컬럼이 읽기 전용이고 발주대기 마감만 편집할 수 있다.
- 행 추가·삭제는 없다(요청 행 그대로).
- 확정 전 화면 검증 메시지는 서버 메시지와 같은 문구를 쓴다.
