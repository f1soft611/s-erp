# 수주·출하 흐름 데이터 초기화 상세사양서

## 1. 근거 및 목적

- 작업지시서: [20261112_010 수주·출하 흐름 데이터 초기화 작업지시서](../../directions/20261112/20261112_010_수주_출하흐름_데이터_초기화_작업지시서.md)
- 계획서: [20261112_010 수주·출하 흐름 데이터 초기화 계획서](../../plan/20261112/20261112_010_수주_출하흐름_데이터_초기화_계획서.md)
- 승인 설계: [Sales Order and Delivery Data Reset Design](../../superpowers/specs/2026-11-12-sales-order-delivery-reset-design.md)

지정 테넌트의 기존 수주부터 출하등록까지 업무 기록을 삭제해 흐름을 처음부터 재등록할 수 있도록 하는 운영자 실행 SQL이다. 스키마나 애플리케이션은 변경하지 않으며, 이 작업에서는 대상 DB에 스크립트를 실행하지 않는다.

## 2. 대상과 제외

### 삭제 범위

- 선택된 테넌트의 모든 `tb_sales_order_hd` 헤더와 FK cascade에 따른 수주 상세.
- 선택된 테넌트의 모든 `tb_sales_delivery_plan_hd` 헤더 및 계획 상세.
- 선택된 테넌트의 모든 `tb_sales_delivery_hd` 헤더 및 출하 상세. 수주 출하와 `DIRECT` 직출하를 모두 포함한다.
- 대상 출하를 참조하는 거래명세서 헤더와 그 상세.
- 대상 수주 헤더 또는 상세를 참조하는 구매요청 상세가 하나라도 있으면 해당 테넌트 구매요청 헤더 전체와 모든 형제 상세.
- 삭제된 구매요청 상세가 참조하던 구매확정 헤더 중, 구매요청 상세가 더 이상 참조하지 않는 헤더.

대상 테넌트에 속한 비활성 데이터도 삭제한다. 업무 데이터의 `use_at`, 상태, 생성일 등으로 범위를 제한하지 않는다.

### 보존 범위

- 테넌트, 거래처, 품목, 창고, 사용자 및 기타 마스터 데이터.
- 다른 테넌트의 업무 데이터.
- 삭제 대상 구매요청과 무관한 구매요청 및 구매확정.
- PK 시퀀스와 `tb_id_sequence` 등 문서번호 발급 상태.

## 3. DB 계약 근거

`s-erp-postgresql-readonly` MCP의 `list_tables`, 관련 `describe_table`, 제한된 `information_schema` FK 메타데이터 조회만 사용했다. 업무 데이터 행이나 테넌트 식별정보는 조회하지 않았다.

- 출하 상세는 출하 헤더, 계획 상세, 수주 상세를 참조하며, 관련 FK 삭제 규칙은 `NO ACTION`이다.
- 계획 상세는 계획 헤더와 수주 상세를 참조한다. 계획 헤더에는 현재 수주 ID 컬럼이 없다.
- 수주 상세는 수주 헤더 삭제 시 cascade 된다.
- 구매요청 상세는 요청 헤더에 cascade로 연결되고 수주 헤더/상세를 참조한다. 따라서 수주를 지우기 전에 연결 구매요청 문서를 제거한다.
- 거래명세서 상세는 명세서 헤더를 참조하고, 명세서 헤더는 출하 헤더를 참조한다. 두 단계 모두 `NO ACTION`이므로 먼저 명세서 상세와 헤더를 삭제한다.
- 구매확정 헤더는 요청 상세에서 참조될 수 있다. 삭제 후보가 된 헤더라도 남은 요청 상세가 참조하면 보존한다.
- 테넌트 식별은 `tb_tenant.tenant_id`를 대상으로 검증한다.

## 4. 입력 및 실행 절차

1. 실행자는 스크립트 상단의 tenant 입력란에 양수 `tenant_id`를 지정한다. tenant ID를 다른 환경이나 MCP 조회에서 추론하지 않는다.
2. 스크립트는 명시적 트랜잭션을 열고 tenant 입력값의 숫자 변환·양수 여부와 `tb_tenant` 존재 여부를 확인한다. 조건을 충족하지 않으면 삭제 전에 실패한다.
3. 삭제 예정 헤더/상세/연결문서 ID를 테넌트 범위로 임시 목록에 보관해 예상 삭제 수를 출력한다.
4. 실행자는 출력된 범위를 확인한다. 스크립트 기본 마지막 명령은 `ROLLBACK`이므로 검토 실행은 데이터를 남기지 않는다.
5. 실제 초기화가 승인된 경우, 실행자는 별도 백업을 확인하고 마지막 `ROLLBACK`만 `COMMIT`으로 바꿔 실행한다. 모든 변경은 한 트랜잭션에서 커밋되며, 오류 발생 시 전체가 취소된다.
6. 업무 동시 등록이 없는 시간에 실행한다. 예상하지 못한 FK 참조·동시 변경·SQL 오류는 우회하지 않고 전체 롤백한다.

기본 스크립트 실행은 안전한 영향 확인을 위한 롤백 전용이다. 데이터 삭제를 확정하려면 운영자가 명시적으로 커밋 상태로 바꾸어야 한다. 커밋 후에는 SQL 롤백이 불가능하며 백업 복구가 필요하다.

## 5. 삭제 순서

다음 순서로 삭제해 확인된 `NO ACTION` 제약을 보존한다.

1. `tb_sales_statement_dt` → `tb_sales_statement_hd`: 대상 출하 ID의 명세서만 삭제.
2. `tb_sales_delivery_dt` → `tb_sales_delivery_hd`: 대상 테넌트의 모든 출하 삭제.
3. `tb_sales_delivery_plan_dt` → `tb_sales_delivery_plan_hd`: 대상 테넌트의 모든 계획 삭제.
4. `tb_purchase_request_hd`: 대상 수주 헤더 또는 상세 ID를 참조하는 요청이 포함된 문서 전체를 삭제한다. 상세는 헤더 FK cascade로 삭제된다.
5. `tb_purchase_confirm_hd`: 삭제된 요청의 상세가 참조했던 후보 중 동일 테넌트의 남은 요청 상세가 참조하지 않는 헤더만 삭제한다.
6. `tb_sales_order_hd`: 대상 테넌트의 수주를 삭제하고, 수주 상세는 기존 FK cascade에 맡긴다.

구매요청 문서 탐색은 상세의 `sales_order_id`가 대상 수주 헤더에 속하거나 `sales_order_detail_id`가 대상 수주 상세에 속하는 경우를 모두 포함한다. `purchase_request_dt.tenant_id`와 헤더의 `tenant_id`도 대상 테넌트와 일치시킨다.

## 6. 검증 기준

- 입력 ID가 없거나 숫자가 아니거나 0 이하이거나 존재하지 않는 테넌트이면 삭제 전에 오류가 난다.
- 각 삭제 ID 집합은 대상 테넌트 헤더에서 유도되고, tenant를 벗어난 데이터는 선택하지 않는다.
- 명세서 상세/헤더가 출하보다 먼저, 출하가 계획보다 먼저, 계획/출하/구매요청이 수주보다 먼저 삭제된다.
- 공유 구매확정은 남은 상세가 하나라도 참조하면 삭제되지 않는다.
- 기본 스크립트에는 활성 `COMMIT`이 없고 마지막 트랜잭션 명령은 `ROLLBACK`이다.
- `TRUNCATE`, `CASCADE` 삭제, `setval`, 시퀀스 초기화 및 마스터 데이터 삭제는 포함하지 않는다.
- `docs/database`와 `backend/DATABASE`에 보관한 SQL 및 변경기록 쌍이 서로 동일하다.
- SQL은 검증만 하며 이 작업에서 DB에 적용하지 않는다.

## 7. 운영 제한

- SQL로 커밋한 삭제를 복원하는 역방향 스크립트는 제공하지 않는다. 실행 전 백업이 필요하다.
- 스키마 변경이 없으므로 `db-schema.md` 및 스키마 롤백 파일은 수정하지 않는다.
- 사용자 화면, API, 백엔드 코드, 데이터 시드, 데이터베이스 자체는 이번 범위에 포함하지 않는다.
