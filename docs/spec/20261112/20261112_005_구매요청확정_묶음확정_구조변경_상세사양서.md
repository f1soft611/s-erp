## 1. 데이터베이스

### 1.1 신규 `public.tb_purchase_confirm_hd` 구매요청확정 메인

| 컬럼 | 타입 | NULL | 설명 | MES |

제약: `pk_purchase_confirm_hd`, `uk_purchase_confirm_hd_no (tenant_id, confirm_no)`,
`uk_purchase_confirm_hd_id_tenant (purchase_confirm_id, tenant_id)`, FK 테넌트·확정자,
`ck_purchase_confirm_hd_use_at`, `ck_purchase_confirm_hd_total_amt (>= 0)`,
`ck_purchase_confirm_hd_currency (^[A-Z]{3}$)`. 인덱스 `ix_purchase_confirm_hd_tenant_dt (tenant_id, confirm_dt DESC)`.

### 1.2 `public.tb_purchase_request_hd` 변경

- 추가: `purchase_confirm_id BIGINT NULL`, FK `fk_purchase_request_hd_confirm (purchase_confirm_id, tenant_id)` →
  `tb_purchase_confirm_hd (purchase_confirm_id, tenant_id)`, 인덱스 `ix_purchase_request_hd_confirm`.
- 삭제: `confirm_dt`, `confirmer_id`(FK `fk_purchase_request_hd_confirmer` 포함), 제약 `ck_purchase_request_hd_confirmed`.
- 추가 제약 `ck_purchase_request_hd_confirm_link`:
  `(status = 'REQUESTED' AND purchase_confirm_id IS NULL) OR (status = 'CONFIRMED' AND purchase_confirm_id IS NOT NULL)`.
- `total_amt`는 그 요청 행들의 금액 합계로 유지한다.

### 1.3 기존 데이터 이전 (create 스크립트 안)

1. 확정 상태 요청 중 상세 통화가 2개 이상인 건이 있으면 `RAISE EXCEPTION`으로 중단한다.
2. 확정 상태 요청마다 확정 메인 1건을 만든다. 확정번호는 확정일별로 `MC-yyyyMMdd-NNNN`을 1부터 매기고,
   `tb_id_sequence`의 `MATERIAL_CONFIRM_NO` 값을 발급한 최대값 이상으로 맞춘다.
   확정일·확정자·합계는 기존 요청 헤더 값, 통화는 상세 통화(없으면 `KRW`).
3. 요청 헤더에 `purchase_confirm_id`를 채운 뒤 컬럼을 삭제한다.

### 1.4 롤백

요청 헤더에 `confirm_dt`, `confirmer_id`를 다시 만들고 확정 메인 값으로 채운 뒤, 이전 제약을 복원하고
`purchase_confirm_id`와 `tb_purchase_confirm_hd`를 삭제한다. 취소된 확정(`use_at = 'N'`) 이력은 사라진다.

## 2. 상태 전환

| 동작 | 대상 | 조건 | 결과 |
| --- | --- | --- | --- |
| 묶음 확정 | 요청 여러 건 | 모두 `REQUESTED`, 사용 중 | 확정 메인 1건 생성, 요청 모두 `CONFIRMED` + 확정 ID |
| 발주대기 마감 | 확정 메인 | `use_at = 'Y'` | 행별 `order_close_at` |
| 확정 취소 | 확정 메인 | `use_at = 'Y'` | 확정 메인 `use_at = 'N'`, 묶인 요청 모두 `REQUESTED`, 확정 ID·확정값·마감·금액 초기화 |

- 확정할 요청은 ID 오름차순으로 헤더를 `FOR UPDATE` 잠그고 상태를 확인한다. 하나라도 요청 상태가 아니거나 없으면
  409 "이미 확정되었거나 삭제된 구매요청이 있습니다. 다시 불러와 주세요."
- 확정 메인은 `FOR UPDATE`로 잠근다. 취소된 확정에 마감·취소를 하면 409 "취소된 확정입니다."

## 3. API

기본 경로 `/api/v1/materials/purchase-request-confirms` (READ: 조회, UPDATE: 확정·마감·취소).

| 메서드·경로 | 설명 |
| --- | --- |
| `GET /candidates?keyword=` | 확정 대상(요청 상태) 구매요청 목록. 응답 필드는 004와 같음. 최대 200건 |
| `GET /request-details?purchaseRequestIds=5,6` | 고른 요청들의 상세 행(요청 정보 포함). 요청 상태가 아닌 건이 있으면 409. 한 번에 최대 50건 |
| `GET /?keyword=&status=` | 확정 목록. `status`: `ACTIVE`(기본) / `CANCELED` / `ALL`. 최대 200건 |
| `GET /{purchaseConfirmId}` | 확정 단건(헤더 + 상세 행) |
| `POST /` | 묶음 확정(201) |
| `PUT /{purchaseConfirmId}/order-close` | 발주대기 마감 저장 |
| `POST /{purchaseConfirmId}/cancel` | 확정 취소 |
| `GET /unit-price?materialId=&supplierId=&baseDt=` | 기본 매입 단가(004와 같음) |

### 3.1 상세 행 공통 필드

004의 상세 필드에 요청 정보 `purchaseRequestId`, `requestNo`, `requestDt`, `requesterName`, `requestDeptName`를 더한다.
정렬: 구매요청번호, 행 번호.

### 3.2 확정 목록 행

`purchaseConfirmId`, `confirmNo`, `confirmDt`, `confirmerName`, `currencyCode`, `totalAmt`, `requestCount`, `remark`, `useAt`.
정렬: 확정일 내림차순, 확정번호 내림차순.

### 3.3 확정 단건

`purchaseConfirmId`, `confirmNo`, `confirmDt`, `confirmerName`, `currencyCode`, `totalAmt`, `remark`, `useAt`,
`updatedByName`, `updatedAt`, `details[]`(3.1). 취소된 확정은 요청 연결이 해제되어 `details`가 비어 있다.

### 3.4 묶음 확정 `POST /`

```json
{
  "confirmDt": "2026-11-12",
  "remark": null,
  "purchaseRequestIds": [5, 6],
  "details": [ { "purchaseRequestDetailId": 11, "confirmQty": 20, "confirmDeliveryDt": "2026-11-19",
                 "warehouseId": 1, "orderType": "RAW_MATERIAL", "supplierId": 4, "unitPrice": 1200,
                 "currencyCode": "KRW", "confirmRemark": null } ]
}
```

- `confirmDt` 필수, `remark` 500자 이내, `purchaseRequestIds` 1~50건·중복 없음.
- `details` 상세 id 집합 = 고른 요청들의 전체 상세 행 집합(아니면 409 "구매요청 상세가 변경되었습니다…").
- 행별 검증은 004 3.3과 같다(확정수량 > 0, 필수값, 단가 0 이상, 참조 데이터 사용 중).
- **통화**: 모든 행의 `currencyCode`(비면 `KRW`)가 같아야 한다. 다르면 400
  "통화가 다른 품목은 함께 확정할 수 없습니다. 같은 통화 품목끼리 확정해 주세요."
- 저장: 확정번호 채번 → 확정 메인 INSERT(통화, 합계) → 상세 확정값 UPDATE → 요청 헤더마다 `status`,
  `purchase_confirm_id`, `total_amt`(그 요청 행 합계) UPDATE. 응답은 3.3.

### 3.5 발주대기 마감 / 확정 취소

- 마감: body `{ "details": [{ "purchaseRequestDetailId": 11, "orderCloseAt": "Y" }] }`. 상세 id는 이 확정에 묶인 행이어야
  한다(아니면 400). 바뀐 행만 갱신. 응답 3.3.
- 취소: 묶인 요청들의 상세 확정값 초기화(004 3.5와 같음) → 요청 헤더 `REQUESTED`, `purchase_confirm_id = NULL`,
  `total_amt = 0` → 확정 메인 `use_at = 'N'`. 응답 3.3.

## 4. 화면

### 4.1 버튼

| 버튼 | 표시 | 동작 |
| --- | --- | --- |
| 요청 불러오기 | UPDATE | 요청 다중 선택 다이얼로그. 그리드를 비우고 고른 요청만 표시한다(누적하지 않음). 작성 중 내용이나 열린 확정의 미저장 변경이 있으면 먼저 확인한다 |
| 확정 불러오기 | 항상 | 확정 선택 다이얼로그 |
| 신규 | 항상 | 화면 비움(미저장 확인) |
| 확정 | UPDATE, 신규 작성 중이고 행이 있을 때 | 검증 → 통화 확인 → 확정 |
| 선택 요청 빼기 | 신규 작성 중, 상세 툴바 | 체크한 행이 속한 요청의 모든 행을 뺀다 |
| 저장 | UPDATE, 사용 중 확정을 연 상태 | 발주대기 마감 저장(변경 있을 때 활성) |
| 확정 취소 | UPDATE, 사용 중 확정을 연 상태 | 확인 대화상자 후 취소 |

- 확정을 연 상태에서 [요청 불러오기]를 누르면 신규 작성으로 바꾸는지 확인한 뒤 진행한다.

### 4.2 기본정보

확정번호(신규면 "확정 시 자동 채번"), 확정일(신규면 입력·기본 오늘), 확정자, 상태(신규 작성 / 확정 / 확정 취소),
통화(행 통화, 섞이면 "혼합"), 합계금액, 요청 건수, 확정 비고(신규면 입력).

### 4.3 상세 그리드

- 앞쪽에 구매요청번호·요청일·요청자 컬럼을 두고 같은 요청끼리 셀을 병합한다(`mergeRows`).
- 나머지 컬럼과 편집 규칙은 004 4.4와 같다. 신규 작성 중에는 행 체크박스를 보여 준다.

### 4.4 통화 혼합 경고

[확정] 시 행 통화가 2종류 이상이면 경고 대화상자
"통화가 다른 품목이 섞여 있습니다(KRW, USD). 같은 통화 품목끼리 확정해 주세요."를 띄우고 저장하지 않는다.

### 4.5 다이얼로그

- 요청 선택: 검색어, F1-Grid 다중 체크, [선택 불러오기]. 요청 상태 건 전체를 보여 준다(불러오면 그리드를 교체하므로 제외 목록 없음). 컬럼은 004와 같다(상태 제외).
- 확정 선택: 상태 select(사용·취소·전체, 기본 사용), 검색어. 컬럼: 확정번호(버튼), 확정일, 확정자, 요청 건수, 통화,
  합계금액, 상태, 비고.
