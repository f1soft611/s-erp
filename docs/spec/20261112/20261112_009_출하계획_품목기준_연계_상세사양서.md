## 2. 목표와 범위

계획과 출하의 원본 선택 및 수량 검증 단위를 각각 수주상세와 출하계획상세로 통일한다. 한 계획에 서로 다른 수주의 선택 품목 행을 담을 수 있고, 한 출하에 서로 다른 계획의 선택 품목 행을 담을 수 있다. 출하계획현황은 계획상세 한 건당 한 행으로 표시한다.

포함:

- MANUAL 다중수주 출하계획과 AUTO 단일수주 계획 생성 규칙
- 수주상세별 계획 가능 잔량, 계획상세별 출하 가능 잔량
- 개별 행 선택, 한 출하의 단일 거래처 검증, 계획상세별 계획현황
- 기존 권한·테넌트 경계, 정책 검증, 카운터의 트랜잭션 갱신
- 계획 헤더의 단일 수주 참조 제거를 위한 스키마 변경 의도와 제한된 롤백

제외:

- 거래명세서 및 이에 속한 화면·테이블·데이터 변경
- 기존 `DIRECT` 직출하 흐름의 변경
- 이 문서 작성 단계에서의 DB 조회, DDL 작성·적용 또는 업무 데이터 조회

## 3. API 및 데이터 계약

### 3.1 확인된 현재 경로와 외부 응답 형태

경로는 현재 API 컨트롤러의 매핑을 기준으로 한다. 본 사양은 새 경로를 추가로 가정하지 않는다.

| 업무 | 현재 경로 | 확인된 동작 및 응답 형태 |
|---|---|---|
| 계획 등록·수정 | `/api/v1/sales/delivery-plans` (`POST`), `/api/v1/sales/delivery-plans/{salesDeliveryPlanId}` (`PUT`) | 요청은 `SalesDeliveryPlanRequestVO`이며 `details`를 포함한다. 성공 응답은 `item`을 사용한다. |
| 계획 단건·AUTO 수주별 조회 | `/api/v1/sales/delivery-plans/{salesDeliveryPlanId}`, `/api/v1/sales/delivery-plans/by-order/{salesOrderId}` (`GET`) | 성공 응답은 `item`을 사용한다. AUTO 조회 경로는 유지한다. `by-order`는 현재 AUTO 모드의 수주당 단일 계획 조회에만 사용한다. |
| 계획 원본 검색·현황 | `/api/v1/sales/delivery-plans/source-orders`, `/api/v1/sales/delivery-plans/status` (`GET`) | 응답은 각각 `items` 목록을 사용한다. 현황 검색은 기존 `SalesDeliveryPlanStatusSearchVO` 및 프론트엔드 `DeliveryPlanFilters` 계약을 따른다. |
| 출하 등록·수정 | `/api/v1/sales/deliveries` (`POST`), `/api/v1/sales/deliveries/{salesDeliveryId}` (`PUT`) | 요청 상세는 `SalesDeliveryDetailRequestVO`이며 성공 응답은 `item`을 사용한다. |
| 출하 원본 검색·현황 | `/api/v1/sales/deliveries/source-orders`, `/api/v1/sales/deliveries/status` (`GET`) | 응답은 `items` 목록을 사용한다. 원본 행의 현재 타입은 `SourceOrderRow`/`SalesDeliverySourceOrderVO`이다. |

인증 주체의 테넌트와 사용자 ID를 사용하고 기존 권한·테넌트 검사 경계를 유지한다. 구현은 위 경로와 응답 외피를 바꾸지 않는다. 응답 필드는 아래 승인된 행 식별자와 현재 요청/응답 모델에 이미 존재하는 필드를 우선 사용한다. 이 절에 열거되지 않은 신규 엔드포인트, 파라미터, 오류 코드 또는 필드는 이 사양으로 확정하지 않는다.

### 3.2 출하계획 요청 및 응답

- 계획 헤더는 계획 문서를 나타내며 단일 수주를 대표하는 저장 관계를 갖지 않는다.
- MANUAL 계획 요청의 각 `details` 행은 해당 행의 `salesOrderId`와 `salesOrderDetailId`를 함께 전달한다. 이 계약은 `SalesDeliveryPlanDetailRequestVO`에 행별 `salesOrderId`를 추가하고, 헤더의 단일 `salesOrderId`를 출처 판단에 사용하지 않는 변경이다.
- `salesDeliveryPlanDetailId`, `planDt`, `plannedQty`는 현재 상세 요청 모델의 이름과 의미를 유지한다. 계획 상세 응답은 각 행의 `salesDeliveryPlanId`, 수주·수주상세 식별자와 해당 품목/수량을 제공한다.
- AUTO는 기존 `/by-order/{salesOrderId}` 흐름을 유지하고, 자동 생성 계획 하나에는 해당 수주만 포함한다. 행별 수주 참조로 저장하더라도 AUTO가 여러 수주를 한 계획으로 합치지 않는다.
- MANUAL에서는 한 수주가 여러 계획 문서의 상세에 포함될 수 있으므로 `/by-order/{salesOrderId}`의 단일 결과가 보장되지 않는다. 이 경로는 MANUAL에서 거부하고, MANUAL 계획은 계획 ID로 조회한다. 임의로 첫 계획을 선택하지 않는다.
- 기존 단일 수주 계획을 포함한 계획 상세의 분할 행을 보존한다. 같은 수주상세에 대한 복수 계획 행은 별개 행으로 유지한다.

### 3.3 출하 요청 및 원본 행

- ORDER 출하 상세는 기존 `salesDeliveryPlanDetailId`를 계속 보유한다. 이 ID가 계획 상세 원본을 식별하며 수주상세 또는 계획 헤더 선택을 대신하지 않는다.
- 출하 원본 검색 결과는 계획상세 행 단위다. 현행 `SalesDeliverySourceOrderVO`/`SourceOrderRow` 식별 필드인 `salesDeliveryPlanDetailId`, `salesOrderId`, `salesOrderDetailId`와 고객·계획·품목·수량 정보는 각 원본 행에 대응한다.
- 선택된 복수 계획상세 행을 한 출하의 `details`로 전송한다. 선택한 계획상세 ID 이외의 형제 행을 서버나 클라이언트가 자동으로 추가하지 않는다.
- 기존 다중수주 출하 요청의 호환 계약을 유지한다. 헤더 `salesOrderId`는 첫 선택 상세의 대표 수주 ID이며, 서버는 첫 상세의 수주 ID와 일치하는지 검증한다. 응답 `orderNo`는 상세 행에 연결된 고유 수주번호를 정렬한 뒤 `, `로 연결한다. 각 상세의 실제 출처 관계는 상세의 계획상세·수주상세 식별자로 검증하며, 대표 헤더 ID를 사용해 행을 확장하지 않는다.
- 거래처는 출하 헤더에서 하나만 지정한다. 계획에 여러 거래처의 상세가 포함되어도 허용하되, 한 출하로 선택하는 모든 행의 거래처는 하나로 일치해야 한다.

## 4. 처리 및 화면 동작

### 4.1 계획 대상 선택 및 저장

1. 계획 원본 선택기는 수주 헤더가 아닌 수주상세 품목 행을 표시한다. 각 행의 수주·수주상세 식별자와 고객·품목·수량 정보로 원본을 구분한다.
2. 사용자는 체크한 행만 선택한다. 같은 수주의 행을 선택해도 미선택 형제 행을 자동으로 선택하거나 계획 상세에 추가하지 않는다.
3. MANUAL은 복수 수주의 선택 행을 하나의 계획 문서에 저장할 수 있다. 같은 원본 수주상세를 날짜/수량으로 나누는 기존 분할 동작을 유지한다.
4. 선택되지 않은 원본 행, 다른 테넌트의 행, 요청의 수주와 수주상세가 일치하지 않는 행은 저장할 수 없다. 수량·원본 관계는 서버가 최종 검증한다.
5. AUTO는 주문 저장과 연결된 기존 생성 흐름을 유지하며 수주 한 건당 계획 한 건이다. AUTO의 단일 수주 계획을 MANUAL 다중수주 동작으로 바꾸지 않는다.

### 4.2 계획 잔량과 수정

원본 수주상세 `d`의 계획 가능량은 다음과 같다.

`계획 가능량(d) = 수주상세 수량(d) - 해당 수주상세를 참조하는 활성 계획상세 plannedQty 합계`

합산은 `(salesOrderId, salesOrderDetailId)` 원본 조합별로 한다. 미계획 잔량이 양수인 수주상세만 신규 계획 원본 검색 대상이다. 분할 행은 같은 원본 조합의 합계로 검증한다.

계획 수정에서는 수정 대상 계획의 기존 수량을 다른 활성 계획의 합계에서 제외한 뒤, 요청한 수정 계획 행들의 합계가 원 수주상세 수량을 넘지 않는지 검사한다. 기존 납품 실적보다 계획 수량을 낮출 수 없다는 현재 보호 동작을 유지한다. 동시 수정 시 서버가 원본과 수량을 다시 검증하고, 승인된 트랜잭션/잠금 흐름 안에서 저장한다.

### 4.3 출하 대상 선택, 잔량 및 초과 정책

계획상세 `p`의 출하 가능량은 다음과 같다.

`출하 가능량(p) = 계획상세 plannedQty(p) - 해당 계획상세의 deliveredQty(p)`

- 출하 원본 검색은 `출하 가능량 > 0`인 계획상세만 반환한다. 이 조건은 `BLOCK`과 `WARN` 모두 동일하다. 이미 완전히 소진된 행을 WARN에서 검색·선택 가능하게 하지 않는다.
- 사용자는 검색 결과에서 계획상세 행을 개별 선택한다. 동일 계획에 속한 미선택 형제행은 출하 상세에 포함하지 않는다. 여러 계획의 행을 함께 선택할 수 있다.
- 부분 출하를 유지한다. 정상 범위에서는 각 행의 요청 출하량이 현재 출하 가능량을 넘지 않도록 검증한다.
- `WARN`은 초과를 무조건 허용하거나 검색 가능한 행을 늘리는 정책이 아니다. 원본 검색 당시 양수 잔량으로 선택 대상이 된 행에 대해, 확인 절차에서 사용자가 초과 수량을 명시적으로 확인하면 그 행의 초과 출하를 허용할 수 있다. 초과 확인은 기존 `overDeliveryConfirmed` 및 `[OVER_DELIVERY_CONFIRM_REQUIRED]` 재시도 계약을 유지한다. `BLOCK`은 확인 플래그가 있어도 초과를 거부한다.
- 서버는 저장 시 최신 잔량·정책·원본 관계를 재검증한다. 원본 변경이나 동시 저장에 따른 불일치는 서버가 거부하며, 초과 확인은 오래된 검증을 무효화하지 않는다.

### 4.4 단일 거래처 및 직출하

- 계획은 서로 다른 고객의 수주 상세를 포함할 수 있다.
- 출하 선택에서 서로 다른 고객의 행을 함께 확정하려 하면 거부하고 선택 창을 유지하여 사용자가 단일 고객 행만 다시 고르게 한다. 고객 정보는 선택 행별 원본에서 검증한다.
- 단일 고객 행 여러 개 및 서로 다른 계획의 행을 하나의 출하에 기록할 수 있다.
- 여러 수주 상세를 선택한 경우에도 출하 기본정보의 연결 수주 ID는 첫 선택 행을 대표값으로 유지하고, 거래처·장소·배송방법 초기값은 첫 선택 수주를 따른다. 출하 상세별 원본 ID와 응답의 수주번호 집계는 기존 다중수주 계약을 유지한다.
- `DIRECT`는 계획 없이 등록하는 기존 동작을 유지하며 계획상세 참조를 만들거나 필요로 하지 않는다. 본 품목 기준 변경이 직출하 요청·수량 처리에 영향을 주지 않는다.

### 4.5 출하계획현황

- 현황 목록은 계획 헤더가 아니라 계획상세 기준이며, 반환한 각 행은 서로 다른 `salesDeliveryPlanDetailId`에 대응한다. 같은 계획의 다른 품목/분할 행을 합쳐 한 행으로 만들지 않는다.
- 각 행에 해당 상세의 출처 수주번호·수주 ID, 고객 ID/코드/명, 품목 정보, 계획일, 수주수량, 계획수량, 출하수량 및 출하 잔량을 표시한다. 계획번호 등 반복되는 헤더 정보는 기존 그리드 병합 패턴으로 표현할 수 있지만 행 단위 데이터는 병합으로 소실시키지 않는다.
- 행 선택/상세 열기는 해당 행이 속한 계획을 대상으로 하며, 계획 수정 폼에서 기존 행의 원본 상세 정체성과 분할 관계를 유지한다.
- 화면 오류는 기존 페이지의 오류 표시 패턴을 사용한다. 구체적인 화면 문구·새 오류 코드는 현행 컴포넌트/백엔드 계약을 확인하지 않고 추가하지 않는다.

## 5. 검증 및 오류 처리

클라이언트 검증은 선택 누락·중복, 필수 입력, 수량 형식, 단일 고객 선택 등 즉시 안내 가능한 항목을 검사한다. 서버 검증이 최종 권한이며, 다음 항목을 기존 응답·상태 처리 방식으로 거부한다.

- 존재하지 않거나 비활성/타 테넌트인 수주, 수주상세, 계획 또는 계획상세
- 수주 ID와 수주상세 ID 또는 계획상세와 그 원본 수주의 불일치
- 미선택 형제행을 포함한 요청, 중복 출하계획상세 ID, 계획/출하 수량 잔량 초과
- 단일 출하의 거래처 혼합
- 기존 권한·계획 모드·테넌트 정책 위반 및 동시 변경으로 무효화된 수량

기존 서비스의 트랜잭션 원자성을 유지한다. ORDER 출하 생성·수정·삭제 때 계획상세 `deliveredQty`와 원 수주상세 `shippedQty` 증감을 같은 트랜잭션에서 처리하고, 계획 생성·수정의 원본 주문 잠금 및 순서는 관련 기존 계약을 따른다. 계획의 이전·제안 수량 비교와 저장도 동일한 원본별 수량 일관성을 지키며, 실패한 검증은 문서와 카운터 일부만 저장하는 결과를 만들지 않는다.

## 6. 스키마 변경 의도와 롤백 제약

구현 단계에서 metadata-only PostgreSQL MCP 확인 후 현재 제약과 이력을 기준으로 변경안을 확정한다. 본 사양 작성에서는 DB MCP를 호출하거나 실제 스키마 존재 여부를 단정하지 않는다.

- 계획 헤더의 단일 `sales_order_id` 관계와 수주당 계획 헤더 단일성을 강제하는 제약을 제거한다.
- 계획상세 헤더 관계는 계획 ID와 테넌트 범위를 보장하고, 각 계획상세의 수주 ID/수주상세 ID 관계는 상세 행에 유지한다.
- 기존 계획/출하상세 데이터와 각 상세의 원본 연결은 보존한다. 구체적인 제약명·컬럼·인덱스는 구현 전 MCP 메타데이터와 현재 DDL을 확인해 확정하며 여기서 추정하지 않는다.
- 변경 SQL, 변경 이력 및 롤백 SQL은 기존 프로젝트 규칙에 따라 날짜별로 `docs/database`와 `backend/DATABASE`에 쌍으로 관리하고, DB에 직접 적용하지 않는다.
- 롤백은 모든 계획 헤더에 적어도 한 상세가 있고, 각 계획의 모든 상세가 동일한 원 수주 하나만 참조하여 헤더 단일 수주 관계를 손실 없이 복구할 수 있을 때만 허용한다. 상세가 없거나 둘 이상의 원 수주를 가진 계획이 있으면 임의로 수주를 선택하지 않고 롤백을 중단한다. 롤백 가드와 데이터 복구 순서는 구현 단계에서 현재 스키마에 맞춰 검증한다.

## 7. 인수 테스트 기준

| 구분 | 승인 기준 |
|---|---|
| MANUAL 계획 선택 | 서로 다른 수주에서 선택한 수주상세 행만 하나의 계획에 저장되고 미선택 형제 행은 포함되지 않는다. |
| 계획 분할 및 합산 | 같은 수주상세의 여러 계획 행을 유지하고 그 합계가 해당 수주상세의 가용량을 넘으면 거부한다. |
| 계획 수정 잔량 | 수정 대상 계획의 기존 수량을 제외한 가용량으로 수정 요청을 검증하며, 다른 계획의 수량을 과소 계산하지 않는다. |
| AUTO | 자동 생성 계획 하나에 한 수주만 존재하고 기존 주문 생성/계획 동작이 유지된다. 수주별 단일 계획 조회는 AUTO에서만 허용되며 MANUAL에서는 모호한 결과를 임의 선택하지 않는다. |
| 계획 현황 | 계획상세마다 한 결과 행이 나오며 행의 수주·고객·품목 정보가 그 상세의 원본과 일치한다. |
| 출하 검색 | `BLOCK`과 `WARN` 모두 잔량이 양수인 계획상세만 검색되며 완전 소진 행은 나오지 않는다. |
| 정확 행 출하 | 여러 계획에서 선택한 행만 저장되고 동일 계획의 미선택 형제행은 자동 포함되지 않는다. |
| 부분 출하 및 WARN | 양수 잔량 행의 부분 출하가 가능하다. WARN은 선택 당시 유효한 양수 잔량 행에 대해 초과 확인을 허용할 수 있지만, BLOCK은 초과를 거부한다. |
| 고객 제한 | 계획 내 복수 고객은 허용되며, 한 출하의 선택 행은 단일 고객이어야 한다. 혼합 선택은 창을 닫지 않고 거부된다. |
| DIRECT 및 보안 경계 | 직출하는 기존과 동일하고, 테넌트/권한/정책 검증을 우회할 수 없다. |
| 트랜잭션/카운터 | 출하 생성·수정·삭제의 성공 시 두 출하 누계가 함께 조정되고, 실패 시 일부 카운터나 문서가 변경되지 않는다. |
| 롤백 | 다중수주 계획이 존재하면 헤더 단일 수주 제약 복구를 중단하고 데이터를 임의 변환하지 않는다. |
| 범위 | 거래명세서, 관련 테이블·화면·데이터 변경이 포함되지 않는다. |

## 8. 구현 전 확인 사항

- 계획 및 출하 API의 현행 요청/응답 타입과 경로는 3절에 적은 코드 기준으로 확인했다. 제안된 행별 관계 필드 이외의 API 이름이나 필드를 추정하지 않는다.
- 계획/출하 테이블의 현재 컬럼·제약 metadata 확인은 구현 전 별도 read-only MCP 단계에서 수행한다. 이 사양 작성에서는 업무 데이터와 DB를 조회하지 않았다.
- 화면 문구, 오류 상태 코드, 상세 조회에 필요한 추가 필드는 실제 구현 전 관련 타입·서비스·테스트와 대조해 확정하며, 승인 요구에 없는 계약은 추가하지 않는다.
