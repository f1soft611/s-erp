## 1. 업무 흐름

```text
구매요청등록(요청) ──▶ 구매요청확정(확정) ──▶ 발주등록 ──▶ …
      │                       │
      └ 요청 상태에서만         └ 확정 시 확정 컬럼 입력
        수정·삭제 가능            (다음 작업)
```

- 확정하지 않을 요청은 요청자가 삭제한다.
- 구매요청 1건은 한 번에 확정한다. 확정번호는 따로 없다.

### 3.3 롤백

- 두 테이블에 행이 있으면 `RAISE EXCEPTION`으로 중단한다.
- 행이 없으면 상세 → 헤더 순으로 DROP 한다.
- 메뉴 롤백은 추가한 역할 권한 → 메뉴 권한 → 메뉴 → 모듈 순으로 삭제하고,
  모듈에 다른 메뉴가 남아 있으면 모듈은 남긴다.

## 4. 백엔드 API

기본 경로 `/api/v1/materials/purchase-requests`. 응답은 기존 `ResultVO` 형식을
따른다. 메뉴 권한은 수주등록 API와 같은 방식으로 검사한다.

| 메서드 | 경로 | 권한 | 동작 |
| --- | --- | --- | --- |
| POST | `/` | CREATE | 신규 저장, 번호 채번 후 저장 결과 반환 |
| GET | `/{purchaseRequestId}` | READ | 헤더 + 상세 조회 (`use_at = 'Y'`, 같은 테넌트) |
| PUT | `/{purchaseRequestId}` | UPDATE | 헤더·상세 수정 |
| DELETE | `/{purchaseRequestId}` | DELETE | `use_at = 'N'` 소프트 삭제 |

### 4.1 저장 요청 본문

```json
{
  "requestDt": "2026-11-12",
  "remark": "",
  "details": [
    {
      "purchaseRequestDetailId": null,
      "materialId": 101,
      "requestQty": 10,
      "requestDeliveryDt": "2026-11-20",
      "useType": "PRODUCTION",
      "requestRemark": ""
    }
  ]
}
```

### 4.2 조회 응답 (주요 필드)

헤더: `purchaseRequestId`, `requestNo`, `requestDt`, `requesterId`,
`requesterName`, `requestDeptId`, `requestDeptName`, `status`, `totalAmt`,
`remark`, `createdBy`, `createdAt`, `updatedBy`, `updatedAt`, `details[]`.

상세: `purchaseRequestDetailId`, `lineNo`, `materialId`, `materialCode`,
`materialName`, `materialSpec`, `unit`, `requestQty`, `requestDeliveryDt`,
`useType`, `useTypeName`, `requestRemark`, `confirmQty`.

### 4.3 서비스 규칙

- 신규 저장 시 `MR-yyyyMMdd-NNNN` 채번: generator key `MATERIAL_REQUEST_NO`,
  scope1 = tenantId, scope2 = 요청일 `yyyyMMdd`.
- 신규 저장 시 `status = 'REQUESTED'`, `total_amt = 0`, 확정 컬럼은 NULL,
  `order_close_at = 'N'`.
- `created_by` / `updated_by`는 로그인 사용자 식별값으로 서버에서 설정한다.
  클라이언트 값은 받지 않는다.
- 수정·삭제는 `status = 'REQUESTED'`일 때만 허용한다. `CONFIRMED`이면 409 성격의 업무
  오류 메시지 "확정된 구매요청은 수정할 수 없습니다."를 반환한다.
- PUT의 상세 처리:
  - `purchaseRequestDetailId`가 있으면 해당 행을 수정하고 `updated_by/at`을 갱신한다.
  - 없으면 새 행을 추가한다.
  - 요청에 없는 기존 행은 삭제한다.
  - 저장 후 `line_no`를 1부터 다시 매긴다.
- 검증: 상세 1행 이상, 품목·요청수량(> 0)·요청납기일·사용용도 필수,
  품목과 사용용도는 같은 테넌트의 사용 중 데이터여야 한다.
- 구매 가능 품목계정(2026-11-12 추가): 품목의 `material_type_code`가 `RAW`(원재료),
  `SUB`(부재료), `SUPPLY`(소모품)이어야 한다. 품목이 없거나 삭제됐으면 404
  "품목을 찾을 수 없습니다.", 다른 계정이면 400 "구매요청할 수 없는 품목계정입니다.
  원재료, 부재료, 소모품만 선택할 수 있습니다."를 반환한다. 수정 저장 때도 모든 행에
  같은 검증을 적용한다.
- 요청자(`requester_id`)와 요청부서(`request_dept_id`)는 신규 저장 시 서버가
  로그인 사용자와 그 사용자의 `tb_user.department_id`로 설정한다. 클라이언트에서
  받지 않고, 수정 시에도 바꾸지 않는다. 부서가 없는 사용자는 `request_dept_id`를
  NULL로 저장한다.

## 5. 프론트엔드 화면

### 5.1 구조

수주등록([SalesOrderCreatePage.tsx](../../../frontend/src/pages/sales/order/create/SalesOrderCreatePage.tsx))과 같다.

```text
┌ PageHeader: 구매자재 > 구매관리 > 구매요청등록   [신규][저장][삭제] ┐
├ 구매요청 기본정보 ──────────────────────────────────────────────────┤
│ 구매요청번호(자동) │ 요청일* │ 요청자(읽기) │ 요청부서(읽기)           │
│ 상태(읽기)        │ 비고(전체 폭)                                     │
├ 구매요청 상세 ──────────────────────────── [상세 행 추가][품목 선택] ┤
│ No │ 품목코드* │ 품목명 │ 규격 │ 단위 │ 요청수량* │ 요청납기일* │ 사용용도* │ 비고 │
└────────────────────────────────────────────────────────────────────┘
```

### 5.2 기본정보

| 필드 | 동작 |
| --- | --- |
| 구매요청번호 | 읽기 전용. 저장 전에는 "저장 시 자동 채번" |
| 요청일 | 필수, 기본값 오늘 |
| 요청자 | 읽기 전용. 저장 전에는 로그인 사용자 이름, 저장 후에는 저장된 요청자 |
| 요청부서 | 읽기 전용. 저장 후 서버가 설정한 부서 이름 표시 |
| 상태 | 읽기 전용. 코드값을 한글 라벨(`REQUESTED`→요청, `CONFIRMED`→확정)로 표시 |
| 비고 | 선택, 최대 500자 |

### 5.3 상세 그리드 (F1-Grid)

| 컬럼 | 편집 | 규칙 |
| --- | --- | --- |
| No | 아니오 | 행 순번 |
| 품목코드 | 예 | 공통 품목 선택기, 필수. 원재료·부재료·소모품 계정 품목만 조회 |
| 품목명 / 규격 / 단위 | 아니오 | 품목 선택 시 `tb_material_info`에서 채움 |
| 요청수량 | 예 | 필수, 0보다 큰 수, 소수 둘째 자리 |
| 요청납기일 | 예 | 필수, 날짜 |
| 사용용도 | 예 | 필수, `PURCHASE_USE_TYPE` 공통코드 select |
| 비고 | 예 | 선택, 최대 500자 |

- 행 추가, 우클릭 행 복사·삭제는 수주등록과 같다.
- 하단 합계: 요청수량 합계.

### 5.4 embedded 모드

- 20261112_003 구매요청현황의 조회/수정 다이얼로그에서 쓰도록, 수주등록과 같은
  `embedded`, `mode`(`create`/`view`/`edit`), `purchaseRequestId`, `onSaved`,
  `onDeleted`, `onEmbeddedActionsChange` props를 지원한다.
- `view` 모드는 모든 입력을 읽기 전용으로 표시한다.

### 5.5 동작

- 저장 성공 시 번호·상태·작성/수정 정보를 다시 조회해 표시하고 성공 메시지를 보인다.
- 저장 후 같은 화면에서 수정·삭제할 수 있다. 삭제는 확인 대화상자 후 처리하고
  화면을 신규 상태로 초기화한다.
- `CONFIRMED` 상태를 불러오면 모든 입력과 저장·삭제 버튼을 비활성화한다.
- 필수값 누락 시 저장하지 않고 상단에 오류 목록을 표시한다.
- 저장하지 않은 변경이 있을 때 화면을 떠나면 기존 unsaved guard를 쓴다.
- 권한: CREATE 없으면 신규 저장 불가, UPDATE 없으면 수정 불가,
  DELETE 없으면 삭제 버튼 숨김.
