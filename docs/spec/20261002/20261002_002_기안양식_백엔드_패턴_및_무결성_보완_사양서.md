## 2. Controller 및 VO OpenAPI 문서화

- `DraftingWorkApiController` 클래스에 `@Tag`를 지정한다.
- 목록/사용자 옵션/등록/수정에 `@Operation`과 `@ApiResponses`를 붙여 기존 API 문서 패턴을 적용한다.
- 모든 `@AuthenticationPrincipal LoginVO user` 인자는 `@Parameter(hidden = true)`로 문서 파라미터에서 제외한다.
- `DraftingWorkVO`, `DraftingWorkSaveRequestVO`, `DraftingWorkUserOptionVO`, `DraftingWorkSearchConditionVO`에 클래스 `@Schema`와 필드별 설명을 추가한다.
- 검색 조건 VO는 외부 API 본문으로 직접 노출되지는 않지만, 기준정보의 검색 VO 문서화 패턴에 맞춰 필드 의미를 기록한다.
- `createdAt`은 기존 API 계약 및 Mapper의 `TO_CHAR` 반환과 일치하게 문자열로 유지한다.

## 3. 담당자 목록 null 처리

- `assigneeIds`가 생략되었거나 명시적으로 null이면 담당자 미지정인 빈 목록으로 처리한다.
- 생성/수정 서비스는 동일한 정규화된 목록으로 검증 및 authority 저장을 수행한다.
- 다른 유효성 검증 및 테넌트 사용자 검증 정책은 바꾸지 않는다.
- 테스트는 null 목록 생성이 예외 없이 진행되고 authority mapping INSERT가 호출되지 않음을 검증한다.

## 4. 양식 코드 중복 무결성

- 코드 유일성 범위는 `(tenant_id, cata_type_code)`이며 `delete_status`가 `'Y'`가 아닌 행에 적용한다. PostgreSQL predicate는 `delete_status IS DISTINCT FROM 'Y'`로 null도 미삭제 행에 포함한다.
- `use_at = 'N'`은 비활성일 뿐 삭제가 아니므로 해당 코드가 계속 유일성 범위에 포함된다.
- Service의 사전 중복 검사는 사용자에게 빠른 피드백을 제공하기 위해 유지한다.
- 실제 INSERT는 동일 predicate를 지정한 `ON CONFLICT ... DO NOTHING RETURNING drafting_work_category_id`를 사용한다.
- INSERT가 ID를 반환하지 않으면 Service가 기존 중복 코드 메시지의 `IllegalArgumentException`을 발생시키며 Controller는 `ResponseCode.INPUT_CHECK_ERROR`와 HTTP 400을 반환한다.
- DB 변경은 부분 unique index 생성이며 기존 데이터 정리나 SQL 자동 실행은 범위 밖이다. 사전 중복 확인 결과가 양수면 migration 적용을 중단한다.
- rollback은 새 unique index만 제거하며 테이블/데이터는 건드리지 않는다.

## 5. 회귀 검증

- Controller 테스트: 중복 코드 서비스 오류가 HTTP 400 및 기존 입력 오류 응답으로 변환됨을 확인한다.
- Service 테스트: `assigneeIds == null`을 빈 목록으로 처리하고 insert 충돌(null 반환)을 중복 코드 입력 오류로 바꾸는지 확인한다.
- Mapper 테스트: insert statement가 partial unique index와 일치하는 conflict target을 쓰고 INSERT key를 반환하는지 확인한다.
- DB migration SQL은 MCP 사전 계약 및 중복 집계와 대조하되 실행하지 않는다.
