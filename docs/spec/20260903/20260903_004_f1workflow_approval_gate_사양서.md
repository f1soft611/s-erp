# F1Workflow 사용자 승인 게이트 상세 사양서

## 승인 상태

F1Workflow는 다음 상태를 순서대로 관리한다.

1. `brainstorming`: 요구사항을 질문과 대안 비교로 정제한다.
2. `direction-review`: 작업지시서를 작성하고 사용자 검토 및 승인을 기다린다.
3. `design-review`: 계획서와 상세 사양서를 작성하고 사용자 검토 및 승인을 기다린다.
4. `implementation`: 계획서와 상세 사양서가 승인된 경우에만 구현 절차를 시작한다.

## 전역 하드 게이트

- 작업지시서가 작성되고 사용자에게 제시되기 전에는 계획서, 사양서, 워크트리, 실행 계획, 서브에이전트, 테스트, 코드 수정, 빌드, 배포를 진행하지 않는다.
- 계획서와 상세 사양서가 모두 작성되고 사용자에게 제시되기 전에는 구현 관련 단계를 진행하지 않는다.
- 계획서와 상세 사양서에 대해 사용자가 명시적으로 승인하기 전에는 워크트리 생성, 실행 계획 작성, 서브에이전트 실행, 테스트 작성 및 수정, 코드 및 설정 파일 수정, 빌드와 배포를 진행하지 않는다.
- 사용자가 변경을 요청하면 해당 문서를 수정하여 다시 제시하고, 새로운 명시 승인을 기다린다.

## 승인 요청 형식

### 작업지시서 승인

작업지시서 파일 경로와 목표, 범위, 제외 범위를 간단히 제시한 뒤 다음 의미의 승인을 요청한다.

`작업지시서의 목표와 범위가 맞으면 승인해 주세요. 승인 후 계획서와 상세 사양서를 작성합니다.`

### 계획서 및 사양서 승인

계획서와 상세 사양서 파일 경로, 변경 대상 파일, 검증 방법을 간단히 제시한 뒤 다음 의미의 승인을 요청한다.

`계획서와 상세 사양서가 맞으면 구현을 승인해 주세요. 명시 승인 전에는 구현을 시작하지 않습니다.`

## 승인 판정

- 작업지시서 승인 허용: `작업지시서 승인`, `승인`, `진행`, `yes`, 또는 문맥상 작업지시서 범위에 대한 명백한 동의.
- 구현 승인 허용: `구현 승인`, `구현 시작`, `승인`, `진행`, `yes`, 또는 문맥상 계획/사양에 대한 명백한 동의.
- 불허: 질문, 검토 의견, 추가 요구사항, 모호한 긍정 표현. 이 경우 구현을 시작하지 않고 필요한 문서를 갱신한 뒤 다시 승인을 요청한다.
- 작업지시서 승인은 설계 문서 작성만 허용한다. 구현은 계획서와 사양서의 별도 승인을 받아야 한다.

## 관련 스킬별 의무

- `02-brainstorm.md`: 작업지시서 승인 전 종료 상태를 정의한다.
- `03-design-validation.md`: 계획서와 사양서의 승인 전 종료 상태를 정의한다.
- `04-git-setup.md`부터 `10-code-review.md`까지: 계획서와 사양서의 사용자 승인 여부를 사전 조건으로 확인한다.

## 검증 기준

- 최상위 프롬프트와 관련 스킬이 승인 전 금지 동작을 모순 없이 표현한다.
- 수정 대상 Markdown 파일의 진단 오류가 없다.
