## 1. UI 구성

### 1.1 페이지 구조

권한 관리 페이지는 메뉴 관리 페이지와 동일한 사용자 흐름을 유지한다.

- 상단 경로 영역: 현재 선택된 설정 모듈 및 현재 메뉴명 표시
- 상단 버튼 영역: 조회, 저장, 삭제, 엑셀 또는 페이지별 권한에 맞는 액션 표시
- 검색 영역: 권한명/권한코드/사용자명 검색 필드와 모듈 또는 역할 필터
- 메시지 영역: 오류/성공 메시지를 표시하는 전역 메시지 영역
- 콘텐츠영역 1: 권한관리 F1-Grid
- 콘텐츠영역 2: 권한별 사용자 매핑 F1-Grid

### 1.2 권한관리 F1-Grid

권한관리 영역은 역할 목록을 표시하고, 선택된 역할 기준으로 메타 정보를 확인한다.

필수 컬럼 예시:

- `roleCode`: 역할 코드
- `roleNm`: 역할명
- `userCount`: 사용자 수
- `useAt`: 사용 여부
- `roleDc`: 설명

동작 규칙:

- 검색 시 역할 코드, 역할명, 설명을 기준으로 필터링한다.
- 행 선택 시 해당 역할을 활성 선택 상태로 유지한다.
- dirty 상태가 있으면 저장 버튼을 활성화하고, 저장 후 목록을 재조회한다.
- 이미 존재하는 역할 생성/수정 규칙은 `SystemRoleApiController`와 동일하게 유지한다.

### 1.3 권한별 사용자 매핑 F1-Grid

권한별 사용자 매핑 영역은 선택된 역할에 속한 사용자를 표시하고, 미할당 사용자 목록과 매핑 여부를 관리한다.

필수 컬럼 예시:

- `loginId`: 로그인 ID
- `userNm`: 사용자명
- `departmentNm`: 소속 부서
- `assigned`: 매핑 여부
- `lastLoginAt`: 최종 로그인 시각(선택)

동작 규칙:

- 선택된 역할이 없거나 로딩 중이면 빈 상태를 표시한다.
- 사용자 매핑 그리드는 선택 역할 기준으로 현재 할당된 사용자와 미할당 사용자 구분을 관리한다.
- 사용자 추가/제거는 행 상태 변경으로 갱신하고, 저장 시 서버에 반영한다.
- 사용자 매핑 변경은 별도 dirty 상태로 처리하되, 권한 목록과 충돌하지 않도록 우선순위를 둔다.

## 2. API 계약

### 2.1 기존 역할 API

#### GET /api/v1/system/roles

- 설명: 테넌트 기준 역할 목록 조회
- 응답:

```json
{
  "resultCode": "SUCCESS",
  "resultList": [
    {
      "roleId": 1,
      "tenantId": 1,
      "roleCode": "PLATFORM_ADMIN",
      "roleNm": "플랫폼 관리자",
      "roleDc": "시스템 전체 관리자",
      "useAt": "Y",
      "isSystemRole": "Y"
    }
  ]
}
```

#### POST /api/v1/system/roles

- 설명: 새 역할 생성
- 요청 필드: `roleCode`, `roleNm`, `roleDc`, `useAt`
- 응답: 생성된 역할 정보 포함
- 권한: 테넌트 관리자 이상

#### PUT /api/v1/system/roles/{id}

- 설명: 역할 수정
- 요청 필드: `roleNm`, `roleDc`, `useAt`
- 응답: 수정된 역할 정보 포함
- 권한: 테넌트 관리자 이상

### 2.2 권한 코드 API

#### GET /api/v1/system/permissions

- 설명: 활성 권한 코드 목록 조회
- 응답: `permissionId`, `permissionCode`, `permissionName`, `sortOrder`
- 권한: 테넌트 관리자 이상

### 2.3 권한별 사용자 매핑 API (신규 또는 확장)

#### GET /api/v1/system/roles/{roleId}/users

- 설명: 해당 역할에 매핑된 사용자 목록 및 미할당 사용자 목록 조회
- 응답 예시:

```json
{
  "resultCode": "SUCCESS",
  "assignedUsers": [
    {
      "loginId": "admin01",
      "userNm": "관리자",
      "departmentNm": "운영팀",
      "assigned": true
    }
  ],
  "unassignedUsers": [
    {
      "loginId": "user01",
      "userNm": "사용자1",
      "departmentNm": "영업팀",
      "assigned": false
    }
  ]
}
```

#### POST /api/v1/system/roles/{roleId}/users

- 설명: 역할에 사용자 매핑 추가
- 요청 필드: `loginId` 또는 `userId`
- 응답: 결과 메시지

#### DELETE /api/v1/system/roles/{roleId}/users/{loginId}

- 설명: 역할에서 사용자 연결 해제
- 응답: 결과 메시지

### 2.4 에러 규칙

- 접근 권한이 없으면 `403 Forbidden` 응답
- 필수 값 누락 시 `400/INPUT_CHECK_ERROR` 응답
- 해당 역할/사용자가 없으면 `404` 또는 도메인별 에러 메시지 반환
- 서버 에러는 `PageMessageArea`를 통해 사용자에게 표시한다.

## 3. 권한 정책

- 테넌트 관리자 이상만 권한 관리 화면에 접근할 수 있다.
- `PLATFORM_ADMIN` 역할은 비활성화가 불가하며, 기존 역할 서비스 규칙을 유지한다.
- 사용자 매핑 수정은 본인이 관리 가능한 테넌트의 사용자와 역할에만 적용된다.
- 동일한 사용자를 중복 매핑하지 않는다.

## 4. 상태/상호작용 규칙

### 4.1 검색

- 검색어는 권한명/권한코드/설명 기준으로 필터링한다.
- 사용자 매핑 그리드에서는 로그인 ID/사용자명/부서 정보로 검색 가능하게 한다.
- 검색 결과가 비어 있으면 빈 상태 메시지를 표시한다.

### 4.2 dirty 상태

- F1-Grid 내부 값 변경 시 dirty 상태를 계산한다.
- 변경 상태가 있을 때만 저장 버튼이 활성화된다.
- 값이 원래 값으로 복원되면 dirty 상태가 해제되어 저장 버튼이 비활성화된다.
- 저장 전 사용자 확인 다이얼로그가 필요한 경우 기존 메뉴 관리 페이지와 동일한 패턴을 적용한다.

### 4.3 메시지 영역

- 저장 성공 시 성공 메시지 표시
- API 오류 시 메시지 영역에 오류 메시지 표시
- 중복/필수 값 누락 등은 inline validation 또는 메시지 영역에 안내한다.

## 5. 예외/에지 케이스

- 선택된 역할이 없으면 사용자 매핑 영역은 빈 상태를 표시한다.
- 사용자가 저장 중인 상태에서는 추가/삭제 행 편집이 제한된다.
- 로딩 상태 동안 검색 및 저장 동작이 중복 실행되지 않도록 비활성화한다.
- API 응답이 비어 있거나 표준 포맷을 따르지 않는 경우에도 화면이 깨지지 않고 빈 목록/에러 메시지를 보여준다.

## 6. 검증 항목

- 상단 경로, 버튼, 검색, 메시지 영역이 메뉴 관리 페이지와 동일한 패턴으로 표시된다.
- 권한관리 F1-Grid와 사용자 매핑 F1-Grid가 2개의 독립 콘텐츠 영역으로 표시된다.
- 역할 선택 시 해당 역할의 사용자 매핑 목록이 올바르게 로드된다.
- 사용자 매핑 추가/삭제 저장이 서버와 정상적으로 동작한다.
- dirty 상태와 저장 버튼 활성화/비활성화가 일관되게 동작한다.
- 관리자 권한이 없는 사용자는 접근 시 403 처리된다.
- 프론트엔드 빌드와 백엔드 테스트가 통과한다.

## 7. 비기능 요구사항

- 반응형 레이아웃을 유지한다.
- 좁은 뷰포트에서도 검색 영역과 2개 그리드 영역이 자연스럽게 축소된다.
- 텍스트, 버튼, 입력 영역이 서로 겹치지 않는다.
- 페이지별 권한과 액션은 기존 `PermissionGroup` 및 `PageHeader` 구조를 준수한다.
