# 20261008_005 문서 임시저장 및 첨부 저장 상세 사양서

## 1. 목적과 범위

문서작성 화면의 명시적 임시저장을 실제 저장으로 연결한다. 본문, 결재선, `SYSTEM/DRAFT_SAVED` 타임라인 메시지는 PostgreSQL 단일 트랜잭션으로 처리한다. 첨부는 기존 MinIO 및 `tb_common_file`을 재사용하되, 결재 문서 전용 권한 검사를 거친다.

이번 범위에서 저장하는 이벤트는 `DRAFT_SAVED`뿐이다. 결재 신청/승인/합의/반려/반송/회수, 일반 사용자 댓글, 자동저장 및 기존 문서함에서 초안을 검색·재진입하는 기능은 포함하지 않는다.

구현 대상 파일과 단계는 [20261008_005 문서 임시저장 및 첨부 저장 계획서](../../plan/20261008/20261008_005_문서임시저장_첨부_계획서.md)를 따른다. `tb_common_comment.comment_type` 및 `event_type`은 중앙 DB에 이미 적용됐다는 사용자 확인이 있으므로, 실제 메타데이터 대조에서 다르게 확인되지 않는 한 컬럼을 추가하지 않는다.

## 2. DB 계약 확인 게이트

백엔드 계약을 확정하기 전에 `s-erp_central`의 읽기 전용 메타데이터로 아래 내용을 확인한다.

| 테이블 | 확인할 계약 |
|---|---|
| `tb_electronic_approval_main` | 실제 컬럼명/타입/null/default, tenant와 작성자 키, 본문 컬럼, 문서 상태 제한, 양식 FK |
| `tb_electronic_approval_line_info` | 단계/참여자 순서, 참여유형 및 action status 제약, tenant 복합 FK/unique |
| `tb_common_comment` | `comment_type`/`event_type`의 존재·타입·기본값, SYSTEM 이벤트 제약, owner 및 작성자 필드 |
| `tb_common_file` | owner/tenant/object key/bucket/file name/checksum 컬럼 및 조회·soft-delete 계약 |

메타데이터 도구가 현재 실행 환경에서 제공되지 않으면 DDL을 실행하지 않는다. 저장소의 날짜별 SQL, Mapper XML, VO 및 도메인 코드를 대체 근거로 삼고, 실제 중앙 DB에서 확인되지 않은 제약은 미확인으로 결과 문서에 남긴다. 저장 컬럼 계약이 확정되지 않은 경우 임의 컬럼을 가정해 API 구현을 진행하지 않는다.

저장소의 `20261008_003` DDL은 `tb_common_comment` event CHECK에서 `DRAFT_SAVED`를 허용하지 않는다. 기존 type/event 컬럼은 중복 생성하지 않고, 허용 코드만 추가하는 `20261008_004` migration 및 롤백을 `backend/DATABASE/20261008/`와 `docs/database/20261008/`에 기록한다. 현재 세션에서는 실제 중앙 DB 제약을 읽기 전용 MCP로 재확인할 수 없어 migration은 미적용 초안으로 남기며 `docs/database/db-schema.md`에 미확인 사실을 기록한다.

## 3. 식별자와 신뢰 경계

- 인증 사용자는 `@AuthenticationPrincipal LoginVO`에서 얻는다. `tenantId`, 감사 주체인 `id`, 표시명 `name`, 작성자 부서명은 서버가 설정한다. 기존 댓글/공지/파일 API와 같이 `LoginVO.id`(로그인 코드)는 `drafter_id`, SYSTEM `writer_id`, `updated_by`, `uploaded_by` 감사 값으로 사용한다.
- 요청 본문은 `tenantId`, `drafterId`, 작성자 이름, 업로더 ID, `comment_type`, `event_type`, 문서 상태를 입력받지 않는다.
- 화면의 결재 참여자 선택값은 `tb_user.user_id` 문자열이다. 기존 사용자 옵션 조회는 `u.user_id`를 반환하고 로그인 프로필의 `employeeId`도 `u.user_id`이며, `LoginVO.uniqId` 역시 `u.user_id::text`다. 따라서 `participant_user_id`에는 검증한 참여자의 `user_id`를 저장하고, 작성자가 첫 결재 단계에 포함됐는지는 `LoginVO.uniqId`와 비교한다. `LoginVO.id`(로그인 코드)와 사용자 선택값을 혼용하지 않는다.
- 참여자 키는 인증 tenant에 속하고 활성 상태인 사용자인지 서버에서 확인한다. 표시 이름/부서명은 요청의 값을 신뢰하지 않고 검증된 서버 사용자 정보에서 스냅샷한다.
- 모든 조회/변경은 tenant 범위로 한정한다. 작성 세션이 보유한 문서 ID나 파일 소유 값만으로 권한을 허용하지 않는다.

## 4. 임시저장 API

신규 Controller는 기존 `ResultVO`/`ResultVoHelper`, 인증 방식, `/api/v1/groupware/...` 경로 패턴을 따른다.

### 4.1 생성

`POST /api/v1/groupware/approvals/drafts`

요청 JSON:

```json
{
  "documentType": "DRAFTING",
  "draftingWorkCategoryId": 12,
  "title": "문서 제목",
  "contentsJson": {},
  "contentsHtml": "<p>본문</p>",
  "contentsText": "본문",
  "approvalLines": [
    {
      "stageOrder": 1,
      "participantOrder": 1,
      "participantType": "APPROVAL",
      "participantUserId": "user-key"
    },
    {
      "stageOrder": 2,
      "participantOrder": 1,
      "participantType": "AGREEMENT",
      "participantUserId": "reviewer-key"
    },
    {
      "stageOrder": 3,
      "participantOrder": 1,
      "participantType": "REFERENCE",
      "participantUserId": "reader-key"
    }
  ]
}
```

`draftingWorkCategoryId`는 양식 미선택 시 `null`이다. 화면 문서 표시명은 저장 코드로 변환한다: `기안서`→`DRAFTING`, `업무연락`→`BUSINESS_CONTACT`, `지출결의서`→`EXPENSE_RESOLUTION`, `근태신청`→`ATTENDANCE_APPLICATION`. 편집기 JSON은 JSONB 값으로, HTML/평문은 현재 편집기 상태에서 추출한 파생값으로 전송한다. 서버는 기존 `RichTextDocumentSanitizer`로 JSON/HTML을 정리하고, 평문은 안전한 HTML에서 생성하므로 클라이언트의 파생 평문을 신뢰하지 않는다.

성공 시 HTTP `201` 및 `ResultVO`의 `item`에 `electronicApprovalId`, `documentStatus: "DRAFT"`를 반환한다. 사용자 행위/문서 데이터가 저장되지 않으면 성공 응답을 반환하지 않는다.

### 4.2 같은 작성 세션의 재저장

`PUT /api/v1/groupware/approvals/drafts/{electronicApprovalId}`

요청 body는 생성과 같은 형식이다. 서버는 `tenant_id`, `drafter_id`, `document_status='DRAFT'` 조건을 모두 만족하는 문서만 갱신한다. 갱신 성공 시 문서 ID를 유지하고, 제출 상태의 문서나 다른 작성자의 문서는 변경하지 않는다. 문서함에서 임의 ID를 열어 수정하는 동작은 제공하지 않는다.

성공 응답은 생성과 동일하게 문서 ID 및 `DRAFT` 상태를 반환한다. 존재하지 않거나 권한 없는 ID는 저장 여부를 노출하지 않는 기존 API 오류 정책에 맞춰 거부한다.

### 4.3 요청 검증

- 문서 유형은 위 네 저장 코드 중 하나이며 제목은 공백이 아니고 DB 허용 길이를 넘지 않는다.
- 본문 JSON은 유효한 JSON 객체여야 한다. HTML은 기존 본문 sanitization/저장 규칙을 따른다.
- 양식 ID는 존재하고 tenant 범위/사용 가능 상태가 유효해야 한다. 미선택은 허용한다.
- 결재선의 `stageOrder`와 `participantOrder`는 양수여야 하며, 같은 문서 내 사용자 중복 및 같은 순서 위치 중복을 거부한다.
- 참여유형은 `APPROVAL`, `AGREEMENT`, `REFERENCE`만 허용한다. UI가 제공하는 참여자 유형 외 값은 저장하지 않는다.
- 첫 결재 단계에 principal의 `uniqId`에 해당하는 작성자 본인이 포함되는 기존 화면 동작을 보존한다. 참여자 집합은 적어도 하나의 결재/합의 참여자를 포함해야 한다.
- 인증 주체를 위조하려는 필드가 요청에 포함되어도 사용하지 않는다.

## 5. 원자적 저장 및 시스템 메시지

하나의 Spring `@Transactional` 서비스 호출에서 아래 순서를 수행한다.

1. 인증 tenant/작성자와 양식·참여자 유효성을 검증한다.
2. 문서 신규 생성 또는 작성자 소유 `DRAFT` 문서를 조건부 갱신한다.
3. 기존 결재선 행을 교체하고 검증된 참여자별 행을 단계/단계 내 순서에 맞춰 저장한다.
4. `tb_common_comment`에 문서 소유의 시스템 저장 이력을 한 건 추가한다.
5. 저장된 문서 ID 및 `DRAFT` 상태를 반환한다.

결재선은 다음 컬럼을 저장한다: `tenant_id`, `electronic_approval_id`, `stage_order`, `participant_order`, `participant_type`, 서버에서 검증한 `participant_user_id`, 검증한 사용자 이름/부서 스냅샷, 초기 처리 상태. `REFERENCE`의 처리 상태 및 처리 시각/의견은 null이고, 결재/합의 행은 실제 DB 계약에 맞는 미처리 상태로 생성한다.

SYSTEM 메시지는 `owner_type='APPROVAL'`, `owner_id=<문서 ID>`, `comment_type='SYSTEM'`, `event_type='DRAFT_SAVED'`, null parent로 저장한다. 행위자 ID와 이름은 principal에서 가져온다. 메시지 내용은 서버가 관리하는 고정 시스템 문구를 사용하며 클라이언트 문구를 신뢰하지 않는다. 명시적 저장 성공마다 한 건씩 추가한다.

문서/결재선/SYSTEM 메시지 중 어느 한 저장이 실패하면 전체 DB 변경을 rollback하고 원래 오류를 호출자에게 전달한다. 일반 댓글 CRUD 경로는 USER 댓글만 수정·삭제할 수 있고 SYSTEM 댓글은 수정·삭제·답글 부모로 사용할 수 없도록 한다. 기존 USER 댓글의 등록/수정/soft-delete 동작은 보존한다.

전자결재 사용자 댓글 UI는 이번 범위에서 제외한다. 따라서 일반 공통 댓글 API는 `ownerType=APPROVAL`에 대한 목록/등록을 거부한다. 향후 전자결재 댓글을 추가할 때는 문서 권한 검사를 포함한 전용 API를 별도 사양으로 구현한다.

## 6. 결재 첨부 API 및 파일 저장

### 6.1 전용 API 계약

- `GET /api/v1/groupware/approvals/{electronicApprovalId}/attachments`: 권한 확인 후 해당 문서의 soft-delete되지 않은 첨부 목록을 반환한다.
- `POST /api/v1/groupware/approvals/{electronicApprovalId}/attachments`: multipart `file` 한 건을 업로드하고 새 `fileId`/파일 메타데이터를 반환한다.
- `DELETE /api/v1/groupware/approvals/{electronicApprovalId}/attachments/{fileId}`: 문서/tenant 소유를 확인하고 공통 파일 서비스의 owner-aware soft-delete를 호출한다.
- `GET /api/v1/groupware/approvals/{electronicApprovalId}/attachments/{fileId}/download`: 문서/tenant 소유를 확인한 뒤 기존 다운로드 스트리밍을 수행한다.

임시저장 상태에서의 첨부 쓰기/삭제 권한은 문서 작성자에게만 허용한다. 각 경로는 문서 ID의 tenant 및 작성자/권한 정책을 먼저 검사한다. 범용 `/api/v1/common/files` API는 `ownerType=APPROVAL` 요청을 거부해 결재 전용 권한 검사를 우회하지 못하게 한다. 승인 전용 파일 등록의 `uploadedBy`는 principal의 `LoginVO.id`로 설정한다.

### 6.2 object key와 표시 이름

- `CommonFileVO.fileName`은 사용자가 올린 표시용 파일명으로 보존한다.
- MinIO object key에는 원본 파일명을 사용하지 않고, tenant/owner 경로 아래 새 파일마다 생성한 UUID를 사용한다. 같은 tenant/owner/파일명으로 여러 번 업로드해도 object key가 서로 달라야 한다.
- `filePath`, `objectKey`, `bucketName` 메타데이터는 실제 업로드 객체와 일치해야 한다. 기존 owner type의 다운로드는 저장된 메타데이터의 object key를 사용하므로 기존 파일 접근은 유지된다.
- 기존 공통 업로드의 확장자/크기/MIME 검사 정책을 먼저 확인해 동일한 서버 검증을 적용한다. 브라우저 `accept`만으로 파일을 검증하지 않는다.

### 6.3 MinIO/DB 실패 보상

MinIO 업로드가 성공한 뒤 DB metadata insert 또는 저장 결과 조회가 실패하면, 이번 요청에서 생성한 bucket/object key에 한해서 MinIO `delete(bucketName, objectKey)`를 시도한다. MinIO 업로드가 실패한 경우에는 삭제를 시도하지 않는다. metadata 기록이 성공한 객체나 다른 파일의 key는 삭제하지 않는다.

MinIO 및 DAO 의존성이 준비되지 않았으면 MinIO 업로드 전에 저장 실패를 발생시킨다. DB insert가 null ID를 반환하거나 persisted row 확인 결과가 없으면 성공형 대체 ID를 반환하지 않고 저장 실패로 처리한 뒤 새 object를 보상 삭제한다.

보상 삭제 실패 시 최초 DB 오류를 최종 업로드 오류의 원인으로 유지한다. cleanup 오류는 최초 오류의 suppressed exception으로 붙이고, structured error log에 bucket/object key 및 두 예외를 남긴다. cleanup 오류가 최초 오류를 덮어 성공/실패 원인을 바꾸면 안 된다.

테스트는 아래 세 경로를 각각 확인한다.

1. MinIO 업로드 성공 + DB insert 성공: metadata에 동일 object key와 표시 파일명이 저장된다.
2. MinIO 업로드 성공 + DB metadata 실패 또는 null insert ID: 새 object만 보상 삭제되고 원래 저장 오류가 전달된다.
3. DB 실패 + 보상 삭제 실패: 원래 DB 예외가 유지되고 cleanup 예외가 suppressed/logged 된다.

## 7. 프론트엔드 동작

- 저장 중에는 임시저장 버튼을 비활성화하고 진행 상태를 알린다. 저장 실패 시 제목/본문/결재선/선택 파일을 보존한다.
- 첫 문서 저장 성공 후 반환된 `electronicApprovalId`를 현재 작성 세션 상태에 보유한다. 재저장과 첨부 재시도에서 새 문서 생성 요청을 반복하지 않는다.
- 저장 전에는 문서 ID를 표시하지 않는다. 첫 저장 응답으로 ID를 받은 뒤에는 `CommonDialog`의 `description` 영역에 `임시저장 문서 ID: {id}` 형식으로 모달 제목 바로 아래 표시하고, 본문에는 별도로 중복 표시하지 않는다. 같은 작성 세션에서 재저장해도 표시 위치와 ID는 유지한다.
- 문서 저장이 성공한 뒤 신규 파일을 각각 전용 첨부 API로 업로드한다. 첨부마다 `pending`, `uploaded`, `failed`, `unknown` 상태를 보유하고 표시한다.
- `uploaded` 파일을 다시 업로드하지 않으며 `failed` 파일만 개별 재시도한다. 응답이 유실되거나 유효한 `fileId`가 없어 업로드 성공 여부를 판정할 수 없으면 `unknown`으로 표시하고 확인 없이 자동 재업로드하지 않는다. 첨부 목록 재조회 결과로 완료가 판명되면 업로드 완료로 반영하고, 판명되지 않으면 사용자에게 모호한 상태를 명시한다.
- 문서 저장 오류와 첨부 부분 실패는 메시지를 구분한다. 첨부 전체 상태가 성공으로 확정되기 전에는 전체 저장 완료로 표시하거나 대화상자를 자동으로 닫지 않는다.
- 기존 `AttachmentList`의 아이콘/파일명/삭제 UX를 재사용한다. 기존 공지사항 테스트 ID와 동작을 바꾸지 않는다.

## 8. 보안/오류 동작

- 미인증/tenant 미확인은 401, 유효하지 않은 입력은 400, 존재하지 않거나 접근할 수 없는 문서/파일은 기존 API의 정보 노출 방지 정책에 맞춘 오류를 반환한다.
- 클라이언트가 지정한 tenant, 작성자, 업로더, owner type, owner ID만으로 접근을 허용하지 않는다.
- `APPROVAL` 파일의 목록/업로드/삭제/다운로드는 모두 문서 권한 검사 후 수행한다.
- USER 댓글 API는 `comment_type='SYSTEM'` 레코드를 변경하거나 답글 대상으로 취급하지 않는다.
- 일반 댓글 API는 `ownerType=APPROVAL`의 목록/등록을 거부해 tenant 인증만으로 문서 타임라인에 접근하지 못하게 한다.
- 부분 성공을 전체 성공 응답으로 숨기지 않는다. DB 문서 저장 성공 후 첨부 실패는 저장된 문서 ID를 유지하고 첨부별 실패만 반환/표시한다.

## 9. 검증 시나리오

### 백엔드

- 새 초안 저장에서 문서, 참여자 순서, SYSTEM 이벤트가 정확히 한 트랜잭션으로 생성된다.
- 재저장에서 같은 문서 ID가 유지되고 결재선이 새 요청으로 교체되며 SYSTEM 이벤트가 저장 시점마다 추가된다.
- 결재선 저장 실패 또는 SYSTEM 메시지 저장 실패 시 문서/결재선/메시지 변경이 rollback된다.
- 위조 actor, tenant 밖/비활성 참여자, 중복 참여자, 잘못된 상태/문서 유형 및 타 작성자 초안 갱신을 거부한다.
- 일반 USER 댓글의 기존 동작은 통과하고 SYSTEM 수정/삭제/답글은 거부된다.
- `APPROVAL` 권한이 없는 사용자의 file list/upload/delete/download 및 범용 API 우회가 거부된다.
- 같은 owner/같은 표시 파일명 업로드에서 key가 다르고 binary가 서로 보존된다.
- DB metadata 실패와 보상 삭제 성공/실패의 원인 보존을 확인한다.

### 프론트엔드/브라우저

- 요청 DTO에서 인증 주체 필드가 빠지고 문서 유형/본문/결재선/참조 순서가 계약대로 변환된다.
- 성공한 문서 ID를 재사용하고 저장 중 중복 요청을 막는다.
- 저장 전에는 문서 ID가 숨겨지고, 저장 성공 후에는 공통 다이얼로그 제목 아래 description에 한 번만 표시된다.
- DB 저장 오류 때 입력 상태가 보존된다.
- 첨부 부분 실패 때 성공 파일을 재업로드하지 않고 실패 파일만 다시 시도한다.
- 응답 누락/모호한 업로드 결과는 `unknown`으로 안내하고 맹목적으로 중복 업로드하지 않는다.
- 화면에서 저장/첨부 추가·삭제/실패·재시도를 확인하고 375px, 768px, 1280px에서 overflow 및 컨트롤 겹침이 없다.

## 11. 저장 피드백 및 차단 로딩 표시 (2026-10-12 후속 승인)

### 11.1 저장 결과 피드백

- 문서 저장과 선택된 첨부 업로드가 모두 성공으로 확인되면 `useNotification().showSuccess('문서가 임시저장되었습니다.')`로 공통 성공 토스트를 표시한다. 모달 내부에는 성공 Alert를 표시하지 않는다.
- 문서 저장 API가 실패하면 기존 오류 문구를 모달 콘텐츠 상단 오류 영역에 표시하고 입력값/첨부/이미 작성된 문서 ID를 유지한다. 공통 성공 토스트는 호출하지 않는다.
- 첨부 업로드 중 하나라도 실패하거나 결과가 미확정이면 저장된 문서 ID와 파일별 상태를 보존하고, `문서는 저장되었지만 첨부파일 N건의 상태 확인이 필요합니다.`를 모달 상단 오류 영역에 표시한다. 해당 파일의 오류 및 기존 재시도/상태 확인 제어는 파일 행에도 유지한다. 이 경우 성공 토스트는 표시하지 않는다.
- 미확정 업로드의 서버 목록 대조에서 해당 파일 한 건의 업로드가 확인되면 파일 상태를 `uploaded`로 바꾸고 `첨부파일 업로드가 확인되었습니다.` 성공 토스트를 표시한다. 목록 대조 실패, 삭제 실패, 재시도 실패는 상단 오류 영역 및 가능한 경우 파일별 오류 상태에 표시한다.
- 첨부 재시도 및 상태 조회가 진행되는 동안 중복 작업을 막는다. 기존 저장 API 호출/문서 ID 유지/모달 자동 닫기 동작은 그대로 둔다.

### 11.2 최초 조회/기안양식 조회 표시

- 초기 작성 정보 조회(`isLoading`) 또는 선택 양식 본문 조회(`templateLoading`) 중에는 문서 구분 탭 바로 아래의 전체 본문 영역을 중앙 `CircularProgress`로 대체한다. `aria-label`은 `문서 정보 불러오는 중`으로 제공한다.
- 공통 모달 제목/description, 닫기 컨트롤, 문서 구분 탭 및 footer는 유지한다. 로딩 중 저장, 탭 전환, 서식 도구, 첨부 선택을 비활성화한다.
- 로딩 중에는 양식 메타데이터, 결재선, 제목, 본문 편집기, 첨부 목록을 화면/접근성 트리에서 숨긴다. 기존 폼 subtree는 마운트 상태를 유지해 편집기와 작성 상태를 초기화하지 않는다.
- 초기 조회 또는 양식 조회 실패 시 해당 로딩 스피너를 제거하고 기존 작성 본문을 복원하며, 실패 메시지를 모달 콘텐츠 최상단 오류 영역에 표시한다. 탭 아래에 별도의 로딩 안내 Alert는 표시하지 않는다.

### 11.3 회귀 확인

- 두 번의 정상 저장 각각 공통 성공 알림을 발생시키고 모달 내부 성공 Alert가 없음을 검증한다.
- 문서 저장 실패와 첨부 부분 실패는 상단 오류 Alert를 유지하고 첨부 부분 실패 시 파일별 오류/재시도 상태도 유지한다.
- 최초 조회와 기안양식 조회의 pending 상태에서 접근 가능한 progressbar 및 공통 모달 구조를 확인하고, resolve 뒤 본문 복구와 reject 뒤 상단 오류 표시를 검증한다.
- 375px, 768px, 1280px에서 초기/양식 로딩 및 로딩 해제 후 페이지 가로 overflow가 없음을 브라우저로 확인한다.
