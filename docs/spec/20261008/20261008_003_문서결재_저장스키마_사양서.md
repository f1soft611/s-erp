# 20261008_003 문서 결재 저장 스키마 상세 사양서

## 1. 대상 및 근거

- 대상 DB 계약: S-ERP 중앙 PostgreSQL 스키마.
- 사용자가 승인한 저장 구조: 본문/결재선은 전용 테이블, 사용자 댓글과 결재 시스템 메시지는 공통 댓글 타임라인, 좋아요는 별도 관계 테이블, 첨부는 공통 파일 재사용.
- 화면 근거: `DocumentKind`는 기안서/업무연락/지출결의서/근태신청이고, 작성 상태는 임시저장/결재대기/결재중/보완요청/완료이다. Tiptap 본문은 JSON으로 읽고 양식 HTML에서 초기화할 수 있다. `DocumentApprovalStage`는 `approval` 또는 `agreement` 단계와 사용자 목록을 가지며 별도 참조 사용자 목록도 존재한다.
- 식별자 근거: `LoginVO.id`는 문자열, `LoginVO.tenantId`는 `Long`이다. 현재 공통 댓글의 `writer_id`와 파일의 `uploaded_by`는 문자열이다. 결재 참여자 선택기 값도 문자열 사용자 키이며, 폼 사용자 옵션에는 별도의 숫자 `loginId`도 있으므로 본 스키마는 화면이 실제로 보존하는 문자열 키를 사용하고 계정 FK는 추정하지 않는다.
- 공통 댓글 근거: `comment_id`는 `BIGSERIAL`, `tenant_id`는 `BIGINT`, `owner_type/owner_id` 기반 소유권, 대댓글, `deleted_yn`, `last_modified_by` 감사 필드를 사용한다.
- 분류 근거: `tb_drafting_work_category.drafting_work_category_id`는 전역 PK이며 `tenant_id`도 있다. 저장 행은 해당 양식 ID를 참조하고, 양식 tenant 일치는 서비스에서 검증한다.
- DB MCP: 앞선 설계 확인 과정에서 중앙/tenant 테이블 목록과 공통 테이블 존재 여부를 조회했다. 현재 계획 실행 도구에는 `s-erp-postgresql-readonly` 호출 도구가 노출되지 않아 메타데이터를 재호출하지 못했다. 아래 계약은 저장소 스키마 문서, 기존 SQL 이력, 도메인 코드 및 앞선 MCP 목록 확인을 함께 근거로 한다. 데이터 행 조회는 하지 않았다.

## 2. 테이블 정의

### 2.1 `tb_electronic_approval_main`

문서의 제목/본문/상태/작성자 스냅샷을 저장하는 문서 단위 원본이다.

| 컬럼 | 타입 | null/default | 설명 |
|---|---|---|---|
| `electronic_approval_id` | `BIGSERIAL` | PK | 문서 ID이며 공통 파일/댓글의 `owner_id` |
| `tenant_id` | `BIGINT` | NOT NULL, tenant FK | 테넌트 범위 |
| `drafting_work_category_id` | `BIGINT` | NULL, 양식 FK | 선택한 기존 작성 양식. 미선택 가능 |
| `document_type` | `VARCHAR(40)` | NOT NULL | 아래 문서 유형 코드 |
| `document_status` | `VARCHAR(30)` | NOT NULL, `DRAFT` | 문서 상태 코드 |
| `title` | `VARCHAR(300)` | NOT NULL | 문서 제목 |
| `contents_json` | `JSONB` | NOT NULL, `{}` | 편집기 Tiptap JSON 본문 |
| `contents_html` | `TEXT` | NULL | 화면 렌더링/양식 호환 HTML |
| `contents_text` | `TEXT` | NULL | 검색/요약용 평문 파생값 |
| `drafter_id` | `VARCHAR(100)` | NOT NULL | 인증/화면 사용자 키 |
| `drafter_name` | `VARCHAR(150)` | NOT NULL | 작성자 이름 스냅샷 |
| `drafter_department_name` | `VARCHAR(150)` | NULL | 작성 시 부서명 스냅샷 |
| `created_at` | `TIMESTAMP` | NOT NULL, current timestamp | 생성 시각 |
| `updated_at` | `TIMESTAMP` | NOT NULL, current timestamp | 갱신 시각 |
| `updated_by` | `VARCHAR(100)` | NULL | 마지막 갱신 사용자 키 |
| `submitted_at` | `TIMESTAMP` | NULL | 최초 상신 시각 |

문서 유형 값은 화면 표시값과 분리한 코드로 저장한다.

| 저장 코드 | 현재 화면 표시값 |
|---|---|
| `DRAFTING` | 기안서 |
| `BUSINESS_CONTACT` | 업무연락 |
| `EXPENSE_RESOLUTION` | 지출결의서 |
| `ATTENDANCE_APPLICATION` | 근태신청 |

문서 상태는 현재 화면에서 제공하는 상태만 코드화한다: `DRAFT`(임시저장), `PENDING`(결재대기), `IN_PROGRESS`(결재중), `REVISION_REQUESTED`(보완요청), `COMPLETED`(완료). 신규 상태나 전이 규칙은 이번 DDL에 추가하지 않는다.

### 2.2 `tb_electronic_approval_line_info`

결재 단계별 참여자 한 명을 한 행으로 저장한다. 구조화된 처리 상태의 원본이며, 댓글은 표시용 타임라인 표현이다.

| 컬럼 | 타입 | null/default | 설명 |
|---|---|---|---|
| `electronic_approval_line_id` | `BIGSERIAL` | PK | 결재선 행 ID |
| `tenant_id` | `BIGINT` | NOT NULL | 테넌트 범위 |
| `electronic_approval_id` | `BIGINT` | NOT NULL | 본문 FK |
| `stage_order` | `INTEGER` | NOT NULL | 1부터 시작하는 단계 순서 |
| `participant_order` | `INTEGER` | NOT NULL | 단계 내 참여자 순서 |
| `participant_type` | `VARCHAR(20)` | NOT NULL | `APPROVAL`, `AGREEMENT`, `REFERENCE` |
| `participant_user_id` | `VARCHAR(100)` | NOT NULL | 작성 화면 사용자 선택 키 |
| `participant_name` | `VARCHAR(150)` | NOT NULL | 참여자 이름 스냅샷 |
| `participant_department_name` | `VARCHAR(150)` | NULL | 참여자 부서명 스냅샷 |
| `action_status` | `VARCHAR(20)` | 조건부 NULL | 결재 처리 상태 |
| `action_at` | `TIMESTAMP` | NULL | 처리 시각 |
| `action_comment` | `TEXT` | NULL | 처리 의견 |
| `created_at` | `TIMESTAMP` | NOT NULL, current timestamp | 생성 시각 |

처리 상태는 `WAITING`, `PENDING`, `APPROVED`, `REJECTED`, `RETURNED`로 제한한다. `REFERENCE` 행은 `action_status`, `action_at`, `action_comment`가 모두 NULL이어야 한다. 결재/합의 행은 `action_status`가 필수이며, 미처리 `WAITING`/`PENDING`은 처리 시각/의견이 NULL이고, 처리 완료 `APPROVED`/`REJECTED`/`RETURNED`는 처리 시각을 갖는다. 단계 진행 시점과 합의의 세부 승인 전이 로직은 후속 API 사양 범위다.

제약/인덱스:

- 본문은 `(tenant_id, electronic_approval_id)` 복합 unique 키를 제공하고 line의 동일 복합 컬럼 FK가 tenant 일치를 강제한다.
- `(tenant_id, electronic_approval_id, stage_order, participant_order)` unique로 단계 내 정렬 위치를 보장한다.
- `(tenant_id, electronic_approval_id, participant_user_id)` unique로 문서 내 참여자 중복을 방지한다.
- `stage_order > 0`, `participant_order > 0` 및 참여유형/처리상태 조합을 CHECK로 제한한다.
- 문서별 결재선 조회 인덱스와 `(tenant_id, participant_user_id, action_status)` 처리 대기 조회 인덱스를 둔다.

### 2.3 공통 댓글 확장

| 컬럼 | 타입 | null/default | 설명 |
|---|---|---|---|
| `comment_type` | `VARCHAR(20)` | NOT NULL, `USER` | 기존 댓글은 USER, 처리 메시지는 SYSTEM |
| `event_type` | `VARCHAR(50)` | NULL | SYSTEM 메시지의 안정된 이벤트 코드 |

허용 `comment_type`은 `USER`, `SYSTEM`이다. `USER`의 `event_type`은 NULL이고, `SYSTEM`은 공백이 아닌 `event_type`을 필수로 하며 CHECK로 `APPROVED`, `REJECTED`, `RETURNED`만 허용한다. SYSTEM 댓글은 `owner_type='APPROVAL'`, `owner_id=electronic_approval_id`로 연결한다.

기존 `content`, 작성자, 대댓글, soft delete, 수정 행위자 필드는 변경하지 않는다. SYSTEM 행의 append-only 성격은 서비스/API에서 강제한다. 본 마이그레이션은 공통 댓글 API를 구현/수정하지 않으므로 전자결재 연결 전 일반 수정·삭제·답글·좋아요 요청을 차단하는 후속 작업이 필요하다.

### 2.4 `tb_common_comment_like`

| 컬럼 | 타입 | null/default | 설명 |
|---|---|---|---|
| `comment_like_id` | `BIGSERIAL` | PK | 좋아요 관계 ID |
| `tenant_id` | `BIGINT` | NOT NULL, tenant FK | 인증된 tenant |
| `comment_id` | `BIGINT` | NOT NULL, 복합 댓글 FK | 좋아요 대상 |
| `user_id` | `VARCHAR(100)` | NOT NULL | 인증된 `LoginVO.id` |
| `created_at` | `TIMESTAMP` | NOT NULL, current timestamp | 좋아요 생성 시각 |

`(tenant_id, comment_id, user_id)` unique로 중복 좋아요를 방지한다. `tb_common_comment(tenant_id, comment_id)`에 복합 unique를 추가해 tenant가 다른 댓글을 참조할 수 없도록 한다. unlike는 인증된 사용자가 소유한 해당 관계 행을 삭제한다. SYSTEM 댓글 좋아요는 서비스/API에서 거부하고 좋아요 수는 관계 행 집계로 계산한다.

## 3. 관계, 트랜잭션 및 권한

- 문서 본문과 결재 참여자 저장은 동일 트랜잭션으로 수행한다.
- 처리 시 결재선 상태 변경과 SYSTEM 댓글 추가는 동일 트랜잭션으로 수행하며, 하나가 실패하면 함께 rollback한다.
- `tb_common_file`은 기존 소유 유형으로 문서 ID를 연결한다. 임시 파일 승격 계약은 별도 작업이다.
- 기존 공통 댓글/파일 API의 인증·tenant 확인만으로 문서 접근 권한이 보장된다고 간주하지 않는다. 문서별 열람/참여 권한 검증을 추가하기 전에는 전자결재 화면과 연결하지 않는다.
- 작성자/행위자 ID와 이름은 인증 principal에서 얻고 클라이언트가 제출한 ID/시스템 메시지를 신뢰하지 않는다.
- 결재 참여자 키가 해당 인증 tenant의 활성 사용자에 속하는지 서비스에서 검증한다. 이 DDL은 화면의 문자열 선택 키와 사용자 계정 FK 타입 간 계약을 추정하지 않으므로 참여자/작성자 문자열에 계정 FK를 추가하지 않는다.

## 4. 삭제 정책 및 롤백

- 결재 본문 삭제 시 결재선은 FK `ON DELETE CASCADE`로 함께 제거한다. 실제 문서 삭제 정책/API는 이번 범위에서 구현하지 않는다.
- 양식 삭제 시 문서는 보존되도록 양식 FK는 `ON DELETE SET NULL`을 사용한다.
- 댓글은 기존 soft-delete 정책을 유지한다. 물리 삭제 시 좋아요 관계는 FK cascade로 제거한다.
- rollback 순서는 좋아요 테이블, 댓글 복합 unique, 댓글 event/type 제약과 컬럼, 결재선 테이블, 결재 본문 테이블 순이다.
- 기존 공통 파일/댓글/분류 테이블은 삭제하지 않는다.

## 5. 산출물 및 비목표

- backend 및 docs 스키마 이력 경로에 동일한 forward/change/rollback 파일 3종을 보관한다.
- `docs/database/db-schema.md`와 작업 결과 문서를 갱신한다.
- 이 문서는 DDL 초안과 저장 계약만 정의한다. API/화면 구현 및 실제 DB 적용은 금지한다.
