## 대상 파일

- `frontend/src/pages/dashboard/components/dashboardPages.ts` (신규): 업무 화면 지연 로딩 등록부

- 대시보드를 렌더링하는 테스트 16개 파일(문서작성 6개 파일은 공용 harness 1곳): 화면 모듈 preload 추가

## 상세 사양

### 1. 지연 로딩 등록부 (`dashboardPages.ts`)

`DashboardContent.tsx`가 정적 import하던 업무 화면 컴포넌트 48개 전부를 같은 이름으로 export한다. 경로와 export 이름은 바꾸지 않는다.

```ts
export const SalesOrderCreatePage = lazyPage(
  () => import('../../sales/order/create/SalesOrderCreatePage'),
  'SalesOrderCreatePage',
);
```

- `lazyPage(load, exportName)`은 원래 컴포넌트와 같은 props 타입의 컴포넌트를 반환한다(타입 검사로 확인).
- 모듈 로드 promise는 화면별로 한 번만 만들고 재사용한다.
- 화면 모듈이 이미 로드된 상태에서 마운트되면 원래 컴포넌트를 바로 렌더링한다. 아직이면 `React.lazy` 컴포넌트로 렌더링해 상위 `Suspense`가 기다린다.
- 한 번 마운트된 인스턴스는 언마운트될 때까지 같은 컴포넌트 타입을 유지한다(로드 완료 후 재렌더링 때 화면 상태가 다시 마운트되지 않도록).
- `preloadDashboardPages(): Promise<void>`: 등록된 모든 화면 모듈을 불러온다. 이후 렌더링은 동기로 표시된다. 운영 코드에서는 호출하지 않고, 테스트에서 변경 전의 동기 렌더링 조건을 재현하는 데 사용한다.
- 로드 실패 처리는 `React.lazy`와 같다(오류는 상위 오류 경계로 전달).

### 2. Suspense 경계 (`DashboardContent.tsx`)

```tsx
export function DashboardContent(props: DashboardContentProps) {
  return (
    <Suspense fallback={null}>
      <DashboardContentView {...props} />
    </Suspense>
  );
}
```

- fallback은 `null`이다. `AppRouter`의 라우트 fallback과 같다(앱 진입 스피너 제거 정책).
- 화면 선택 조건, 전달 props, 알 수 없는 page key 처리, 기본 현황 화면은 변경하지 않는다.
- 정적 import 유지: MUI, `PageHeader`, `pageContentMap`, 타입 import. `ComingSoonPage` export는 유지한다.

### 3. 테스트

- 변경 전 기준선: `DashboardContent` 또는 `pages/dashboard/DashboardPage`를 import하는 테스트 21개 파일.
- 해당 파일은 렌더링 직후 화면을 동기로 조회한다(약 130곳). 각 파일 최상위에 다음을 추가해 변경 전과 같은 조건(모든 화면 모듈 로드 완료)에서 실행한다. 테스트 본문과 단언은 바꾸지 않는다.

  ```ts
  beforeAll(() => preloadDashboardPages(), 60_000);
  ```

  - 제한 시간 60초: 변경 전에는 이 로드가 시간 제한 없는 import 단계에서 일어났다. 기본 hook 제한(10초)은 병렬 실행 부하에서 넘을 수 있다.
  - `beforeAll`은 파일의 `vi.mock` 등록 이후 실행되므로 화면 모듈도 mock된 서비스를 사용한다.
- 변경 후 같은 21개 파일을 실행해 기준선 대비 새 실패가 없어야 한다.
