# 20261123_002 단가등록 개편 상세사양서

근거: [작업지시서](../../directions/20261123/20261123_002_item-price-redesign_작업지시서.md), [계획서](../../plan/20261123/20261123_002_item-price-redesign_계획서.md)

## 1. 단가 선택 규칙 (백엔드 공통 서비스 `ItemPriceLookupService`)

공통 전제: 단가 행은 `tb_item_partner_price`(테넌트, 품목, 거래처, 거래구분)에서 `use_at = 'Y'`이고 기준일이 `start_dt` 이상 `end_dt` 이하(종료일 없으면 무기한)인 행이다. 같은 품목·거래처에 유효 행이 여럿이면 시작일이 가장 늦은 행, 같으면 `price_id`가 큰 행(현재 서비스 규칙 유지). 통화·단가는 원화 단가가 있으면 KRW와 `unit_price`, 외화 단가만 있으면 `currency`와 `foreign_unit_price`(현재 규칙 유지). 공통단가(거래처 없음) 대체 조회는 제거한다.

선택된 단가 행의 **부가세구분(`tax_type`)과 부가세포함(`vat_included_at`)도 단가·통화와 함께 결과에 담아 돌려준다**(`ItemPriceLookupVO`에 이미 있는 필드, 구매요청확정·수주 모두 같은 결과를 쓴다). 구매요청확정 그리드는 이 값을 채우고, 일치하는 단가가 없으면 현재 기본값(과세·부가세 미포함)을 쓴다.

### 1.1 구매요청확정 (매입, 품목 일괄 조회)
입력: 테넌트, 품목 ID 목록, 기준일. 품목별로:

| 조건 | 거래처 | 단가·통화·발주구분 |
| --- | --- | --- |
| 단가 거래처가 1곳(사용 중 단가 행이 있는 거래처 수) | 그 거래처 | 그 거래처의 기준일 유효 행. 없으면 비움 |
| 단가 거래처가 2곳 이상 | 기본 거래처(`tb_item_default_supplier`) | 기본 거래처의 기준일 유효 행. 없으면 비움 |
| 2곳 이상인데 기본 거래처가 없음(기존 데이터) | 비움 | 비움 |
| 단가 거래처 없음 | 비움 | 비움 |

- "거래처 수"는 기준일과 상관없이 사용 중 단가 행이 있는 서로 다른 거래처 수다(기본 거래처 필수 규칙과 같은 기준).
- 1곳이어도 기본 거래처가 지정돼 있으면 같은 거래처이므로 결과는 같다.
- 기존 `findDefaultSupplierPrices`는 이 규칙으로 대체하고 구매요청확정(`loadRequestDetails`)이 호출한다. 요청 기본값(요청 단가)이 있으면 이 값으로 덮어쓰는 현재 동작은 유지한다.

### 1.2 수주 (매출, 거래처 지정 조회)
- `findPrice(tenantId, "매출", materialId, customerId, baseDt)`: 수주처(거래처)+품목의 유효 행을 §1 규칙으로 고른다. 없으면 null. 통화는 단가 행의 통화를 결과에 담아 돌려주고, 호출 쪽 화면 통화로 거르지 않는다.
- 이 서비스는 영업 소스에서 아직 호출하지 않는다. 연동은 영업 담당자가 하며 안내문을 결과 문서에 적는다.

## 2. 저장·검증

- 거래처 없는 단가 저장 금지: 신규·수정·엑셀 모두 `customerId` 필수(메시지: 거래처를 선택하세요). 기존 저장 경로의 공통단가 분기를 제거한다.
- 매입 기본 거래처 규칙(저장 요청에 포함된 품목에만 적용): 저장 후 상태에서 그 품목의 사용 중 단가 거래처가 2곳 이상이면 기본 거래처가 정확히 1개여야 한다. 위반 시 400과 품목·사유 메시지. 거래처가 1곳이면 기본 지정은 선택이다.
- 기본 거래처로 지정한 거래처의 단가 행이 모두 없어지는 삭제는 기본 지정 해제와 함께 처리한다(남은 거래처가 2곳 이상이면 새 기본 지정이 필요하므로 위 규칙에 걸린다).
- 매출은 기본 거래처 필드·검증이 없다(`tradeType = 매출`에서 기본 거래처 값이 오면 무시하지 않고 400).
- 엑셀: 거래처 열 필수, "공통단가" 안내 문구 제거. 매입 양식의 기본거래처 열은 유지한다.

## 3. 조회 API

| 엔드포인트 | 변경 |
| --- | --- |
| `GET /overview` | `tradeType` 필수(현재 유지), `itemTypes`(쉼표 구분 계정분류 코드, 비우면 전체) 추가. 한 행이 한 품목: 품목코드·품목·규격·단위·계정분류, 단가 거래처 수, (매입) 기본 거래처명. 공통단가·특별단가 개념의 열·집계 제거 |
| `GET /customer-overview` | `itemTypes` 추가(거래처 기준은 거래처 목록이므로 오른쪽 품목 단가 목록에 적용) |
| `GET /`(목록·이력) | `itemTypes` 추가. 단가 행에 품목 계정분류 필터 적용 |
| 필터 `priceFilter` | `ALL`, `NO_PRICE`(단가 행이 없는 품목), 매입 전용 `NO_DEFAULT_SUPPLIER`(거래처 2곳 이상인데 기본 거래처 없음). `NO_COMMON_PRICE`·`HAS_SPECIAL`은 제거 |
| 품목별 단가 행 | 좌우 그리드 오른쪽용: 목록 API에 품목 ID 조건(`materialId`)이 있는지 구현 시 확인하고 없으면 추가 |

- 계정분류 필터 컬럼은 `tb_material_info.material_type_code`(품목 계정 코드)다. `item_type` 컬럼은 비어 있어 쓰지 않는다. 읽기 전용 DB 확인(2026-11-23): 품목 103건 모두 값이 있고 PRODUCT 20, SEMI 17, GOODS 18, RAW 16, SUB 16, SUPPLY 16건이다. 기본 조건 매입(RAW,SUB,SUPPLY)은 48건, 매출(PRODUCT,SEMI,GOODS)은 55건을 조회한다.
- `itemTypes`의 각 값은 위 6개 코드여야 한다(그 밖의 값은 무시하지 않고 400).
- 권한 검사(`ItemPriceAccessService`)는 변경 없음.

## 4. 프론트엔드

### 4.1 `PageSearchArea` 멀티선택
- `PageSearchField`에 `multiple?: boolean`(select 전용) 추가. 값은 선택 코드를 쉼표로 이은 문자열(`RAW,SUB,SUPPLY`), 비어 있으면 전체. 세션 저장(`isPageSearchValues`)과 값 타입은 변경하지 않는다.
- 단일 select의 "전체" 항목은 멀티에서는 쓰지 않는다(아무것도 고르지 않으면 전체). 선택 칩 또는 쉼표 요약으로 표시한다.
- 기존 select 사용처(`multiple` 없음)의 동작은 바뀌지 않는다.

### 4.2 계정분류 조회조건
- 필드 `itemTypes`, 라벨 "품목 계정분류", 옵션은 코드가 고정된 정적 목록(사용자 제공 코드 기준 확정, 공통코드 조회 없음): `PRODUCT` 제품, `SEMI` 반제품, `GOODS` 상품, `RAW` 원재료, `SUB` 부재료, `SUPPLY` 소모품.
- 기본값: 매입 `RAW,SUB,SUPPLY`, 매출 `PRODUCT,SEMI,GOODS`. 세 탭 모두에 둔다(이력 탭 포함).

### 4.3 컬럼 순서
- 품목 기준·거래처 기준·이력: 품목코드, 품목, 규격, 단위를 나란히 둔다. 거래처 정보 열은 그 다음에 둔다.
- 거래처 기준 탭 오른쪽 그리드 등 현재 합쳐진 열(품목코드/품목)을 분리한다.

### 4.4 품목 기준 좌우 그리드
- 왼쪽: 품목 목록(F1Grid, 520px). 열: No·품목코드·품목·규격·단위·계정분류·거래처 수. 기본 거래처는 오른쪽 단가 목록의 "기본 거래처" 체크 열에서 보고 지정한다(왼쪽 폭을 줄이려고 왼쪽 목록에는 넣지 않았다. API는 기본 거래처명을 계속 내려준다). 행 선택 시 오른쪽을 갱신한다.
- 오른쪽: 선택 품목의 거래처별 단가(F1Grid, 현재 적용 중·예정만). 열: 거래처 선택(코드·이름 합침), 단가·통화·적용기간·사용여부 등 현재 단가 그리드 열. 새 행 폼 상단에는 선택한 품목이 비활성으로 보이고, 매입은 "기본 거래처" 체크가 거래처 오른쪽에 있다(거래처를 고르고 단가를 입력해야 체크할 수 있다). 매입에는 발주구분과 "기본" 체크(품목당 1개)가 있다. 신규 행·수정·삭제·저장은 거래처 기준 탭의 단가 그리드와 같은 변경 집합·일괄 저장 API를 쓴다.
- 기본 체크: 같은 품목의 다른 행 기본이 해제되는 규칙은 변경이 반영된 뒤(onChangesChange)에 처리한다(기존 구현 방식 유지). 저장 시 §2 검증 오류는 화면 메시지로 보여 준다.
- 엑셀: 품목 기준 탭 전용 양식(`itemPriceOverviewExcel.service.ts`, 품목 한 줄에 단가 열을 둔 양식)은 공통단가 전제 구조라 폐지하고, 거래처별 단가 양식 하나(거래처·품목·단가 행)로 통합한다(사용자 확인 필요).
- 트리(`ItemPriceOverviewTree`)와 공통단가·특별단가 관련 코드·문구·필터는 제거한다. 대시보드 설명 문구에서도 "공통단가" 설명을 뺀다.
- 그리드 `storageKey`는 새 사용처마다 고유하게 둔다.

## 5. 데이터베이스 스크립트 (`20261123_002_*`)

- 백업: `tb_item_partner_price_common_backup_20261123`(원본 열 복사) 생성 후 `customer_id IS NULL` 행 복사.
- 삭제: `DELETE FROM tb_item_partner_price WHERE customer_id IS NULL`, 이어서 `customer_id` NOT NULL 설정(사용자 확정).
- 기본 거래처 보정(기존 테스트 데이터): 매입에서 사용 중 단가 거래처가 2곳 이상인데 `tb_item_default_supplier` 행이 없는 품목에 기본 거래처를 지정한다. 거래처는 **실행일 기준 유효 단가가 있는 거래처를 우선**하고, 여러 곳이면 그중 시작일이 가장 늦은 행의 거래처, 유효 단가가 아무 곳에도 없으면 시작일이 가장 늦은 행의 거래처로 정한다(미래 시작 단가의 거래처가 기본이 되는 것을 피함). 현재 대상은 품목 ID 8 하나이며(거래처 4는 유효, 거래처 8은 2026-11-26 시작 예정) 이 규칙이면 거래처 4가 된다. 롤백 시에는 이 스크립트가 추가한 행만 지우도록 대상 품목 ID를 변경 이력에 기록한다.
- 롤백: 기본 거래처 보정 행 삭제 → 제약 해제 → 백업에서 복원 → 백업 테이블 삭제.
- 변경 이력 문서에 변경 전후 건수(삭제 대상 건수, 백업 건수)를 기록한다. `docs/database`와 `backend/DATABASE`에 동일 복사하고 `db-schema.md`를 갱신한다.

## 6. 테스트 기준

- 조회 서비스: 거래처 1곳(유효/무효), 2곳 이상+기본(유효/무효), 2곳 이상+기본 없음, 거래처 없음, 수주처+품목 일치/불일치.
- 저장 검증: 공통단가 저장 거부, 2곳 이상 기본 필수, 기본 변경 후 삭제, 매출 기본 값 400.
- 매퍼·컨트롤러: `itemTypes` 필터, 잘못된 코드 400.
- 프론트: `multiple` select 값 직렬화·기본값·기존 select 불변, 컬럼 순서, 좌우 그리드 선택·저장·기본 거래처 규칙, 엑셀 양식.
