## 납품처 관리

- 화면의 좌우 그리드와 제목·선택 표시 기준은 공통코드 관리
  (`CommonCodeManagementPanel`)다. 현재 외부 여백은 유지하고, 좌측은
  거래처 관리, 우측은 납품처 관리와 선택 거래처를 표시한다.
  우측 상단에는 권한별 추가·삭제·저장 버튼을 두고 별도 수정 버튼 없이
  그리드를 편집한 뒤 저장한다. 공통 헤더·검색·메시지와 반응형 분할,
  미저장 변경 보호를 적용한다.
- 백엔드는 기존 기준정보의 Controller / Service / DAO / Mapper 계층,
  테넌트 범위와 트랜잭션·권한 검증을 따른다.
- 영업관리 > 기준정보에 납품처 관리 메뉴와 seed를 추가한다.
- 거래처별 납품처 등록 여부를 표시하고 선택한 거래처에 속하는 납품처를
  등록·수정·삭제한다. 하나의 거래처는 여러 납품처를 가질 수 있다.
- 거래처 목록의 납품처 등록·미등록 상태는 배지로 가운데 정렬한다.
- 표시·관리 항목은 납품처코드, 납품처명, 사업자번호, 납품처주소, 담당자,
  이동전화번호, 전화번호, 팩스번호, 비고다. 납품처코드는 자동 발급한다.
- 납품처는 별도 마스터로 관리하고 수주가 참조하는 납품처는 삭제를 막는다.
- API 및 데이터 참조는 인증된 테넌트와 거래처 범위를 검증한다.
- 납품처 API는 `/api/v1/sales/destinations`를 사용한다. `GET`은
  `customerId`로 목록을 조회하고, `POST`, `PUT /{id}`, `DELETE /{id}`는
  관리 메뉴의 해당 권한을 검사한다. `GET /customers`는 거래처 코드·명과
  테넌트별 납품처 등록 여부를 반환하며 선택적 `keyword`를 지원한다.
  그리드의 신규·수정 행은 `POST /save-batch`에서 해당 권한을 검사하고
  하나의 트랜잭션으로 저장한다.
- 납품처 마스터 `tb_sales_destination`은 테넌트·거래처에 속하고
  테넌트별 유일한 코드를 갖는다. 수주에는 `sales_destination_id`와
  `billing_customer_id`를 저장한다. 수주 거래처와 납품처의 소속 일치는
  테넌트 포함 복합 외래 키로 보장한다.
- 다른 테넌트의 기존 수주를 건드리지 않도록 두 신규 열은 DB에서 nullable로
  추가하고 신규·수정 요청의 필수 여부는 서버에서 검증한다. 기존
  `delivery_place` 열은 하위 호환을 위해 보존하되 화면 입력은 대체한다.

## 수주등록

- 기존 납품장소 입력을 납품처 필수 선택으로 대체한다.
- 거래처 선택 이후 그 거래처에 속한 납품처만 선택할 수 있다. 거래처를
  변경하면 이전 납품처 선택을 초기화한다.
- 매출처는 기존 거래처 선택 도움창으로 선택하며 필수다.
- 거래처·납품처·매출처를 같은 행에 배치한다. 좁은 화면에서는 기존
  반응형 규칙에 따라 줄바꿈한다.
- 저장과 재조회·수정에서 선택을 유지하며 서버에서도 필수값과 참조 관계를
  검증한다.

## 초기화 및 DB 변경

- 기존 수주를 신규 필드로 변환하지 않는다. 명시된 단일 테넌트의 수주,
  출하계획, 출하, 거래명세서, 매출마감 및 관련 종속 데이터를 참조 관계에
  맞는 순서로 삭제하는 초기화 스크립트를 작성한다. 다른 테넌트와
  기준정보는 보존한다.
- 초기화 및 스키마·메뉴 SQL은 저장소에 제공하고 실제 DB에 실행하지
  않는다. 스키마 변경과 seed는 날짜별 이력과 롤백을 관리한다.

## 검증

- 등록 여부, CRUD, 자동 코드, 수주 참조 중 삭제 제한, 테넌트 및 거래처
  범위 검증을 확인한다.
- 거래처 변경 시 납품처 초기화, 필수값, 저장·재조회·수정, 매출처
  도움창 선택을 확인한다.
- 초기화 SQL의 단일 테넌트 범위와 종속 관계, 다른 테넌트 및 기준정보
  보존을 검증한다.
- 기존 화면 패턴에 맞추고 375·768·1280px 실제 브라우저 확인과
  스크린샷을 결과 문서에 남긴다.
