# 전자결재 공통 알림 연동 상세 사양서

## 1. 기능 범위

기존 공통 알림함에 전자결재 상태 이벤트를 추가한다. 신규 알림은 사용자별이며 기존 `NotificationService`, header popover, inbox, realtime refresh, Web Push outbox를 재사용한다. 이메일 발송은 범위 밖이다.

### 알림 계약

| 항목 | 값 |
|---|---|
| event type | `APPROVAL_WORKFLOW` |
| source type | `APPROVAL_STATUS_EVENT` |
| source ID | `tb_common_comment.comment_id`인 결재 시스템 이력 ID |
| target ID | 해당 이력의 `owner_id`인 전자결재 문서 ID |
| 이동 경로 | `/groupware/doc/write?approvalId=<targetId>` |
| 읽음/숨김 | 기존 사용자별 공통 알림 동작 |
| Web Push | 기존 알림 저장 후 공통 enqueue 흐름 재사용 |

이력 ID는 이벤트마다 새로 생성되므로 같은 문서가 보완요청 후 재상신되어도 알림 고유키가 달라진다. 제목은 이벤트의 목적을 짧게 표시하고 요약은 문서 제목 등 필요한 최소 표시값으로 제한한다. 알림 요약에 결재 의견/반려 사유 전문을 복제하지 않는다.

## 2. 이벤트별 생성 기준

| 업무 전이 | 알림 제목 예시 | 수신자 |
|---|---|---|
| 최초 상신 | 결재 요청 | 상신 후 현재 `PENDING`인 `APPROVAL`/`AGREEMENT` 사용자 |
| 재상신 | 재상신 결재 요청 | 재상신 후 현재 `PENDING`인 `APPROVAL`/`AGREEMENT` 사용자 |
| 승인 후 다음 단계 활성화 | 결재 요청 | 새로 `PENDING`이 된 다음 단계의 승인/합의 사용자 |
| 일반 결재 최종 완료 | 최종 승인 | 기안자 |
| 문서가 기안자 최종확인 대기 상태가 됨 | 최종 확인 요청 | 기안자 |
| 반려 | 문서 반려 | 기안자 |
| 보완요청 | 문서 보완 요청 | 기안자 |
| 업무연락 전송 | 업무연락 도착 | 해당 문서의 `REFERENCE` 사용자 |

- 해당 단계에 `PENDING` 사용자가 남아 있는 승인 동작은 알림을 추가 발행하지 않는다.
- 다음 단계 알림은 다음 단계 활성화에 성공한 뒤 해당 단계의 현재 대기자만 대상으로 한다.
- 상신/재상신 수신자는 기존 저장 결재선에서 조회한다. 업무연락 수신자는 검증된 저장 또는 요청 결재선의 참조 참여자에서 조회한다.
- 승인 결과 수신자는 문서 기안자로 결정한다. 행위자가 대상에 포함되면 제외한다.
- 수신자 ID는 클라이언트가 임의로 지정하지 못한다. tenant와 활성 사용자 상태를 기존 결재 사용자 검증 패턴으로 확인한다.
- `BUSINESS_CONTACT` 문서는 상신 시 `COMPLETED` 상태가 되며, 알림은 지정 참조자에게 발행한다. 일반 승인 대기자 알림으로 취급하지 않는다.
- 알림 생성과 시스템 이력 생성은 현재 `submit`/`processAction` 트랜잭션 안에 둔다. 실패하면 해당 트랜잭션을 rollback한다.

## 3. 서버 변경 계약

### 결재 시스템 이력

`DocumentApprovalDraftSupportService.insertSystemEvent`의 반환 타입을 `Long`으로 바꾸어 `CommonCommentDAO.insertSystemComment`가 반환한 이력 ID를 반환한다. 기존 이력 호출자는 반환값을 사용하지 않아도 된다.

### 수신자 조회

결재 DAO에 다음 조회 책임을 추가한다.

- 문서/tenant 기준 현재 `PENDING`인 `APPROVAL`, `AGREEMENT` 참여자의 distinct user ID
- 업무연락의 활성 tenant `REFERENCE` 참여자 ID

수신자 조회는 existing account/user 활성 조건을 재사용한다. 결재 상태 업데이트 이후 대상 목록을 조회하여 현재 상태와 일치시킨다.

### 공통 알림

- `NotificationServiceImpl.createEvent`는 기존 두 조합 외에 `APPROVAL_WORKFLOW` + `APPROVAL_STATUS_EVENT`만 허용한다.
- 목록 eventType 필터도 `APPROVAL_WORKFLOW`를 허용한다.
- `Notification_SQL_postgresql.xml`은 `APPROVAL_STATUS_EVENT`도 `tb_common_comment.owner_type='APPROVAL'`로 join해 `targetId`를 가져온다.
- 원본 이력이 없어 targetId가 없으면 프런트엔드는 안전하게 이동하지 않는다.

## 4. DB 변경

`tb_notification`은 기존 테이블이며 새 컬럼이나 테이블을 추가하지 않는다. 현재 DDL의 `chk_notification_event_source`가 허용하는 쌍에 아래 조합을 추가한다.

```text
APPROVAL_WORKFLOW / APPROVAL_STATUS_EVENT
```

작성할 파일:

- `docs/database/20261116/20261116_001_extend_notification_approval_events.sql`
- `docs/database/20261116/20261116_001_extend_notification_approval_events_change.md`
- `docs/database/20261116/20261116_001_rollback.sql`
- backend/DATABASE의 동일 파일
- `docs/database/db-schema.md`의 허용 이벤트 조합 및 변경 이력

Rollback은 신규 이벤트 행을 먼저 제거한 뒤 기존 CHECK 정의를 복원한다. migration/rollback은 저장소 초안일 뿐이며 실제 DB에는 적용하지 않는다.

MCP 확인은 `list_tables`와 세 테이블의 `describe_table`까지 성공했다. `tb_notification` CHECK 정의의 읽기 전용 조회는 실패했으므로 라이브 제약은 미확인이다. 변경 이력과 결과 문서에 이 사실 및 DDL 대체 근거를 기록한다.

## 5. 프런트엔드 변경

- `NotificationEventType`에 `APPROVAL_WORKFLOW`, `NotificationSourceType`에 `APPROVAL_STATUS_EVENT`를 추가한다.
- notification 응답 validator에서 새 조합은 `sourceId > 0`, `targetId > 0`이어야 유효하다.
- path resolver는 새 조합을 전자결재 문서 상세로 이동시킨다.
- 공통 알림함에 `전자결재` 표시와 유형 필터 선택지를 추가한다.
- header popover는 기존처럼 알림 제목/요약을 표시하며 별도 UI는 추가하지 않는다.
- 알림 읽음 실패가 원본 이동을 막지 않는 기존 동작을 유지한다.
- 공지, 수주, 출하, 재고의 알림 유형은 이번 범위에 추가하지 않는다.

## 6. 이메일 후속 처리 검토

이번 변경은 메일 발송 기능을 추가하지 않는다. 저장소에는 `spring-boot-starter-mail`과 SMTP 프로파일 설정이 있으나 코드상 실제 sender service는 확인되지 않았다. 사용자 프로필에는 이메일 주소 편집이 있으나 별도의 이메일 수신 동의/검증 설정은 확인되지 않았다.

향후 추가를 권장하는 발송 조건:

1. 중요 결재 이벤트에 한정한다.
2. 푸시 전송이 전체 활성 기기에서 재시도 후 최종 실패했거나 활성 구독 기기가 없는 경우를 대체 발송 후보로 삼는다.
3. 메일은 해당 이벤트의 알림 수신자 본인에게 발송하며 발신자는 시스템 주소다.
4. 알림이 미읽음이라는 이유만으로는 발송하지 않는다. 미읽음은 전달 실패의 증거가 아니다.
5. 인앱 알림 저장 실패 시에는 메일로 대체하지 않는다. 결재와 알림의 원자성은 기존 트랜잭션에서 보장한다.
6. 메일 자체 실패는 독립 outbox에서 제한 재시도/운영 알림으로 처리하며 결재를 rollback하지 않는다.
7. 메일 구현 전에 명시적 수신 동의, 이메일 주소 검증, secret 관리, 개인정보 최소화, idempotency, 재시도 및 푸시/메일 중복 정책을 별도 승인한다.

## 7. 검증 기준

- 최초 상신, 재상신 및 업무연락은 올바른 수신자에게 이벤트 이력 ID 단위로 생성된다.
- 부분 승인으로 같은 단계에 `PENDING`이 남으면 다음 단계/기안자 알림이 생기지 않는다.
- 다음 단계가 실제 활성화된 경우에만 새 결재자가 알림을 받고, 최종/반려/보완 시 기안자가 알림을 받는다.
- 현재 행위자가 수신 대상이면 자기 알림이 없다.
- tenant, 활성 사용자, 알림 소유자 및 문서 접근 권한 경계가 유지된다.
- 알림 조회 응답에 eventType/sourceType/targetId가 정확하고 프런트에서 문서 상세로 이동한다.
- 공통 알림 필터, 읽음/숨김, realtime 갱신, Web Push, 기존 멘션/쪽지 이벤트가 회귀하지 않는다.
- backend focused tests 및 frontend notification tests/build가 통과한다.
- 날짜별 migration 두 사본, rollback, `db-schema.md`, 결과 문서 및 브라우저 스크린샷이 포함된다.
- 메일 발송은 구현되지 않았음을 명시하고 가능성/후속 조건을 결과에 기록한다.
