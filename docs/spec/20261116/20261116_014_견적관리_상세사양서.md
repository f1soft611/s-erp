# 견적관리 화면 추가 상세사양서

## 1. 목적과 범위

영업관리 > 견적관리에 견적서작성과 견적현황을 추가한다. 등록·현황 화면은 기존 수주등록·수주현황의 화면 구조, 권한 처리, F1-Grid 사용 방식을 따른다. WSA305/WSA306은 업무 흐름과 견적 품목 필드 참고 자료로만 사용하며, 현재 API·DB 계약의 근거로 간주하지 않는다.

견적 품목은 품목 마스터에서 선택하거나 직접 입력할 수 있다. 직접 입력 품목은 견적 상세의 스냅샷 값으로만 저장하며 품목 마스터를 생성하거나 변경하지 않는다. 수주등록에서는 견적번호를 선택할 수 있지만 선택은 필수가 아니며 기존 `quotNo` 문자열 계약을 유지한다.

작업장, 소수점 정책, 수주현황 표시 변경, 거래명세서 정책, 공통코드 분류 및 테넌트별 품목 분류는 별도 작업이다.

## 2. 화면 및 사용자 흐름

### 2.1 견적서작성

- 경로: 영업관리 > 견적관리 > 견적서작성 (`quotation-create`)
- 신규 저장 시 견적번호를 서버에서 자동 채번한다. 번호 형식은 `QT-YYYYMMDD-####`이며 테넌트 및 견적일자별 순번을 사용한다.
- 수주등록 화면과 동일하게 헤더와 상세 그리드를 분리하고, 페이지 헤더 액션 권한은 메뉴 권한을 따른다.
- 헤더 항목:

| 항목 | 필수 | 동작 |
|---|---:|---|
| 견적번호 | 자동 | 저장 전에는 자동 채번 안내, 저장 후에는 생성 번호 표시 |
| 견적작성일 | 예 | 기본값은 시스템 업무일 |
| 거래처 | 예 | 기존 거래처 마스터 선택기 사용 |
| 견적제출일 | 아니오 | 날짜 입력 |
| 참조 | 아니오 | 거래처 참조 정보 텍스트 |
| Incoterms | 아니오 | 자유 입력 텍스트 |
| 결제조건 | 아니오 | 자유 입력 텍스트 |
| 견적유효기간 | 아니오 | 자유 입력 텍스트 |
| 화폐단위 | 아니오 | 자유 입력 텍스트 |
| 비고 | 아니오 | 여러 줄 텍스트 |

- WSA305의 사업장, 결재란, 영문 출력 여부, 직원 연락처, VAT 포함·외화 출력 플래그는 현재 작업의 데이터 계약 및 요청 범위 밖이므로 추가하지 않는다.
- 상세 그리드 항목:

| 항목 | 필수 | 동작 |
|---|---:|---|
| 품목코드 | 아니오 | 직접 입력 가능, 마스터 품목 선택 시 코드 스냅샷 입력 |
| 품목명 | 예 | 직접 입력 또는 마스터 품목 선택 |
| 규격 | 아니오 | 직접 입력 또는 마스터 품목 선택 시 값 복사 |
| 단위 | 아니오 | 직접 입력 또는 마스터 품목 선택 시 값 복사 |
| 견적수량 | 예 | 0보다 큰 숫자 |
| 견적단가 | 예 | 0 이상의 숫자 |
| 견적금액 | 계산 | 수량 × 단가, 직접 수정 불가 |
| 비고 | 아니오 | 행별 텍스트 |

- 마스터 품목 선택 시 `materialId`와 코드·명·규격·단위 스냅샷을 저장한다. 직접 입력 시 `materialId`는 null이며 입력한 코드·명·규격·단위를 스냅샷으로 저장한다.
- 상세 행은 1건 이상이어야 하며 모든 행에 품목명, 유효한 수량, 유효한 단가가 있어야 저장할 수 있다.
- 상세 금액 계산은 현재 수주등록의 금액 계산과 동일하게 소수 둘째 자리 반올림을 적용한다. 공급가액은 상세 금액 합계, 부가세는 공급가액의 10%, 총액은 공급가액과 부가세의 합계이다. 소수점 정책의 모듈별 설정은 이 작업에서 구현하지 않는다.
- 저장·수정·삭제 후 성공/오류 메시지는 기존 화면 알림 패턴을 사용한다. 저장 전 신규 초기화나 상세 이탈 확인은 기존 공통 확인 다이얼로그를 따른다.

### 2.2 견적현황

- 경로: 영업관리 > 견적관리 > 견적현황 (`quotation-status`)
- F1-Grid 행은 견적 상세 기준으로 표시하고 견적번호·거래처 등 헤더 값은 같은 견적의 행에서 병합한다.
- 기본 필수 검색조건은 견적작성일 시작일·종료일이며 기본 기간은 최근 1개월부터 시스템 업무일까지이다. 선택 검색은 견적번호, 거래처, 품목명, 제출일 범위로 구성한다.
- 목록의 견적번호를 선택하면 상세 패널을 연다. 상세에서는 헤더와 품목 행을 확인하고 기존 수주현황의 상세/편집 패턴에 따라 조회·수정·삭제를 제공한다.
- 편집은 작성자이며 수정 권한이 있고 견적이 사용 중인 경우에만 허용한다. 삭제는 물리 삭제 대신 `use_at = 'N'`으로 처리한다.

### 2.3 수주등록의 견적 연결

- 현재 `quotNo`는 선택 입력 텍스트이므로 API와 `tb_sales_order_hd.quot_no` 계약을 유지한다.
- 새 견적 선택기는 견적 번호를 검색하고 선택된 견적의 번호를 기존 `quotNo` 값으로 반영한다. 거래처가 이미 선택된 경우 동일 거래처의 사용 중인 견적만 조회한다.
- 견적 선택은 계속 선택 사항이며, 견적 선택 없이 기존 수주 저장이 가능하다. 기존 텍스트 입력 동작을 유지해 과거 수주번호나 외부 견적번호도 기존처럼 입력할 수 있다.
- 선택한 견적과 수주의 거래처가 다르면 선택기에서 결과를 제한하고, 견적 선택 후 거래처가 바뀌면 견적번호를 비운다.

## 3. 데이터 및 API 계약

현재 DB에는 견적 테이블이 없고 `tb_sales_order_hd.quot_no`는 견적 테이블 FK가 없는 선택 문자열이다. 새 견적 데이터는 별도 헤더·상세 테이블로 관리하고 수주 테이블에는 컬럼을 추가하지 않는다.

### 3.1 테이블

`tb_sales_quotation_hd`:

- 기본 키: `quotation_id`
- 테넌트 및 번호: `tenant_id`, `quotation_no`; `(tenant_id, quotation_no)` 유일
- 업무 헤더: `quotation_dt`, nullable `submit_dt`, `customer_id`, nullable `customer_reference`, `incoterms`, `payment_term`, `valid_term`, `currency_code`, `remark`
- 합계: `supply_amt`, `vat_amt`, `total_amt` (`NUMERIC(15,2)`)
- 공통 관리: `use_at`, `created_by`, `created_at`, `updated_by`, `updated_at`
- 거래처 FK와 사용자 범위 조회는 `tenant_id`를 포함한다.

`tb_sales_quotation_dt`:

- 기본 키: `quotation_detail_id`
- 부모·테넌트·순번: `quotation_id`, `tenant_id`, `line_no`; `(quotation_id, line_no)` 유일
- 품목 참조: nullable `material_id`; 설정된 경우에만 테넌트가 일치하는 품목 마스터 FK 적용
- 품목 스냅샷: nullable `material_code`, 필수 `material_name`, nullable `material_spec`, `unit`
- 견적 값: `quotation_qty`, `unit_price`, `line_amt` (`NUMERIC(15,2)`), nullable `remark`
- 헤더 FK는 `(quotation_id, tenant_id)` 복합 키를 참조하고 헤더 삭제 시 상세를 cascade 처리한다.

### 3.2 API

모든 견적 API는 인증 사용자의 테넌트와 사용자 ID를 사용하고 요청 본문의 테넌트 값은 신뢰하지 않는다.

| 메서드 | 경로 | 목적 |
|---|---|---|
| POST | `/api/v1/sales/quotations` | 견적 생성 |
| GET | `/api/v1/sales/quotations/{quotationId}` | 테넌트 범위 상세 조회 |
| PUT | `/api/v1/sales/quotations/{quotationId}` | 작성자 및 사용 중 견적 수정 |
| DELETE | `/api/v1/sales/quotations/{quotationId}` | 작성자 및 사용 중 견적 미사용 처리 |
| GET | `/api/v1/sales/quotation-status` | 기간·견적·거래처·품목 조건으로 상세 목록 조회 |
| GET | `/api/v1/sales/quotations/options` | 수주 화면의 견적 선택 결과 조회; `customerId`와 `keyword` 선택 조건 |

- 번호는 `IdSequenceService`의 `SALES_QUOTATION_NO`, 테넌트 ID, `yyyyMMdd` 범위로 생성하며 순번은 4자리로 표시한다.
- 저장 서비스는 거래처 소유권을 확인한다. `materialId`가 있으면 해당 테넌트의 품목인지 검증하고, 없으면 `materialName`을 포함한 입력 스냅샷을 저장한다.
- 금액은 서버에서 다시 계산하며 클라이언트가 보낸 `lineAmt`, `supplyAmt`, `vatAmt`, `totalAmt`는 신뢰하지 않는다.
- 조회·수정·삭제는 `tenant_id` 및 `use_at = 'Y'` 조건을 사용한다. 수정·삭제는 작성자만 가능하고, 삭제는 미사용 처리한다.
- 목록 및 선택기 API는 테넌트 범위에서만 조회한다. 선택기 검색은 견적 번호와 거래처 이름을 대상으로 하고, `customerId`가 전달되면 해당 거래처로 제한한다.

## 4. 프론트엔드 구성

- `DashboardContent`에 `quotation-create`, `quotation-status` 페이지 키 분기를 추가하고 `pageContentMap`에 메뉴 콘텐츠를 등록한다. `menuService`는 메뉴 경로 마지막 세그먼트를 페이지 키로 사용한다.
- 견적 등록 페이지는 업무 전용 `create/` 폴더에 화면, 상세 그리드, 계산/행 변환 함수, 서비스, 타입을 둔다.
- 견적 현황 페이지는 `status/` 폴더에서 검색 상태, 목록·상세 조회, 그리드, 상세 패널, 편집 다이얼로그를 역할별로 관리한다. 상세/수정 폼은 견적 등록 컴포넌트를 실제로 재사용한다.
- 수주등록은 공통 `MasterPicker` 패턴을 사용해 선택된 번호를 기존 `quotNo` 문자열에 세팅한다.
- MUI 다이얼로그는 `CommonDialog`를 사용하고, 현재 화면의 접근성, 권한, 오류, 로딩, 미저장 변경 처리 방식을 유지한다.
- 견적 메뉴 데이터는 `tb_module`의 활성 `SALES` 모듈 아래 `SALES_QUOTATION`(`견적관리`) 부모와 `SALES_QUOTATION_CREATE`·`SALES_QUOTATION_STATUS` leaf로 seed한다. 경로 마지막 세그먼트가 각각 `quotation-create`·`quotation-status`가 되도록 `menu_url`을 설정한다.
- 메뉴 seed는 `docs/database/20261116/`과 `backend/DATABASE/20261116/`에 동일하게 두고, 실행 전 승인된 `tenant_id`를 명시하도록 NULL 가드를 둔다. 애플리케이션 코드에 테넌트별 메뉴 행을 하드코딩하지 않는다.
- 작성 leaf는 `READ`/`CREATE`/`UPDATE`/`DELETE`, 현황 leaf는 `READ`/`EXCEL` 메뉴 권한을 지원한다. 해당 테넌트의 기존 수주 등록·현황 메뉴에 역할별 권한이 있으면 견적 leaf에 대응 권한을 복사하며, 기존 역할 부여가 없는 역할은 권한관리에서 별도로 부여한다.
- 메뉴 seed는 읽기 전용 DB MCP로 실제 적용하지 않는다. 롤백은 메뉴 및 권한 행을 삭제하지 않고 세 메뉴를 비활성화해 즐겨찾기·권한 참조를 보존한다.

## 5. 보안·오류·호환성

- 테넌트, 거래처, 품목 소유권 검증은 인증 사용자 기준으로 수행한다. 다른 테넌트의 ID를 요청에 넣어도 접근할 수 없어야 한다.
- 조회 대상 없음은 404, 요청값 오류는 400, 작성자/수정 권한 또는 상태 충돌은 403/409 등 기존 API 오류 규칙을 따른다.
- Java 운영 코드는 Java 8 문법·API만 사용한다.
- 견적 상세의 직접 입력 경로에서 품목 마스터 insert/update 호출이 발생하지 않아야 한다.

## 6. 검증 기준

- 백엔드 단위/API/매퍼 테스트: 번호 생성, 금액 서버 재계산, 상세 입력 검증, nullable master ID, 테넌트 격리, 작성자 수정/삭제 권한, 사용 중 필터.
- 프론트엔드 서비스/컴포넌트 테스트: 필수값, direct-input 및 master-selection 행, 금액 재계산, CRUD 응답 오류, 검색 기간 검증, page-key 등록, 수주 화면 견적 선택 및 초기화.
- 회귀: 기존 수주등록에서 견적을 선택하지 않은 저장, 기존 텍스트 견적번호 입력, 수주현황 표시를 검증한다.
- 빌드·브라우저: 프론트엔드 빌드와 테스트, 백엔드 테스트를 실행한다. 실제 브라우저에서 견적작성·현황·수주 선택 흐름을 375px, 768px, 1280px로 확인하고 스크린샷을 결과 문서에 저장한다.
- DB 확인 근거: `s-erp-postgresql-readonly`의 `list_tables`, `describe_table` 결과와 새 스키마·메뉴 seed 파일을 결과 문서에 기록한다. 조회한 테넌트 업무 데이터 행은 기록하지 않는다.
