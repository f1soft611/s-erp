## 검증

1. 이동된 페이지의 테스트와 API 서비스 테스트를 실행한다.
2. `sales-delivery-item-flow.browser.mjs`로 계획 등록/현황과 출하 흐름의 동적 import가 동작하는지 확인한다.
3. 프런트엔드 빌드와 변경한 TS/TSX 파일의 lint를 실행한다.
4. `rg`로 `frontend/src` 및 `frontend/tests`에 이전 `sales/statement`/`sales/delivery-plan` import가 남지 않았음을 확인한다. API URL 문자열은 검색 결과에서 구분한다.

## 추가 사양: 거래명세서 내부 구조

기준은 `sales/order/create` 및 `sales/order/status`의 역할별 폴더 구조다.

```text
sales/delivery/statement/
  create/
    SalesStatementCreatePage.tsx
    components/StatementSourcePicker.tsx
    components/StatementDetailGrid.tsx
    hooks/useSalesStatementCreate.ts
    data/statementDetailColumns.ts
    data/statementSourceColumns.tsx
    types/salesStatementCreate.types.ts
  status/
    SalesStatementStatusPage.tsx
    components/StatementDetailPanel.tsx
    components/StatementEditorDialog.tsx
    hooks/useSalesStatementStatus.ts
    data/statementStatusColumns.tsx
    data/statementStatusSearch.ts
  components/StatementPrint.tsx
  components/statement-print.css
  data/statementPrint.ts
  services/salesStatement.service.ts
  types/salesStatement.types.ts
```

- 등록·현황 페이지는 화면 조립을 담당하고 각 hook이 기존 상태와 이벤트 처리를 그대로 제공한다.
- 공유 API와 타입은 등록 화면에 종속시키지 않는다. 기존 응답·요청 필드와 endpoint는 그대로 유지한다.
- 등록 상세, 출하 선택, 현황의 컬럼 순서·값·링크 이벤트는 기존과 동일하게 유지한다.
- 출력의 한글 금액 변환, 줄 수 계산, 페이지 분할 및 빈 행 계산은 순수 함수로 옮긴다.
- 빈 폴더나 형식만 맞추기 위한 파일은 만들지 않는다.
- 검증은 기존 거래명세서 페이지·라우팅·출력 테스트와 프런트 빌드/lint를 사용한다.
  실제 브라우저 검증은 합성 응답만 사용하며 기존 서버를 종료하거나 실제 데이터를 변경하지 않는다.
