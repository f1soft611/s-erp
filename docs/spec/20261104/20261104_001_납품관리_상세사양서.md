# 납품관리 상세사양서

## 기준 및 설계 결정

- [작업지시서](../../directions/20261104/20261104_001_납품관리_작업지시서.md), [계획서](../../plan/20261104/20261104_001_납품관리_계획서.md).
- 기존 수주 UI, 서비스 응답 `ResultVO.result.item/items`, 인증 principal 및 테넌트 복합 FK 패턴 유지.
- 권장안: 전용 납품 헤더/상세 + 선택적 수주 참조. 수주 테이블 재사용은 직납품에 가짜 수주를 강제하고, 두 개의 등록 화면은 검증/사용성을 중복시키므로 채택하지 않는다.
- 자동 진행 기준: 단일 수주별 부분납품 허용, 수주 없는 직납품 허용, 저장된 납품은 실제 납품수량으로 반영. 재고·회계 자동 연동은 하지 않는다.

## 화면 및 메뉴

- 영업관리(`/sales`) > 납품관리(`/sales/delivery`).
- 납품등록 `/sales/delivery/delivery-create`, menu code `SALES_DELIVERY_CREATE`, pageKey `delivery-create`.
- 납품현황 `/sales/delivery/delivery-status`, menu code `SALES_DELIVERY_STATUS`, pageKey `delivery-status`.
- 부모 menu code `SALES_DELIVERY`; 현재 경로 마지막 조각을 pageKey로 사용하는 메뉴 시스템에서 수주의 `create`/`status`와 충돌하지 않는다.
- 메뉴 SQL은 명시적 대상 tenant ID를 실행자가 지정하는 방식으로 작성한다. 모듈은 기존 `/sales` 또는 `SALES`를 확인하며 ID와 tenant 행을 하드코딩하지 않는다.
- 지원 권한: 등록 READ/CREATE/UPDATE/DELETE, 현황 READ/EXCEL. 역할 부여는 기존 수주 경로의 대응 권한을 가진 역할에 한해 복제하고 일반 역할 전체에 확대하지 않는다.

## 입력 및 동작

- 헤더: 납품일자(필수), 납품구분(`DIRECT` 직납품 / `ORDER` 수주납품), 거래처(필수), 수주번호(수주납품 필수), 납품장소(200), 배송방법(50), 비고(500).
- 상세: 품목(필수), 납품수량(양수), 단가(0 이상), VAT(0 이상, 생략 시 10%), 공급가/합계(서버 계산), 연결 수주상세 ID(수주납품만).
- 신규는 직납품 기본값. 수주납품 선택 시 수주 도움창에서 잔량 있는 수주를 선택한다. 선택한 수주의 거래처·납품장소·배송방법과 미납 상세를 불러온다.
- 수주 상세의 기본 납품수량은 잔량. 행 제거 및 수량·단가·VAT 변경 가능하나 품목/거래처/수주상세 ID는 임의 변경 불가.
- 저장된 문서의 구분·거래처·연결 수주는 변경 불가. 수정 시 날짜·납품장소·배송방법·비고·상세 수량/단가/VAT 및 동일 수주 내 상세 선택만 허용한다. 직납품 품목은 변경 가능하다.
- 저장 후 재조회하여 서버 번호/금액 표시, 수정/삭제/신규 제공. 오류 시 입력 보존, pending 중 중복 요청 차단, dirty 이탈 확인.
- 삭제는 확인 후 `use_at='N'`. 삭제 전 상세는 이력으로 보존한다.
- 현황: 납품일 시작/종료 필수, 기본 당월; 통합검색, 납품구분·거래처·품목·납품번호 조건. 필수 기간 칩 해제 불가. 저장된 검색값 복원 시에도 기간 검증.
- 현황은 헤더+상세 1행씩 표시; 납품번호, 일자, 구분, 거래처, 연결 수주번호, 품목, 수량, 단가, 공급가, VAT, 합계, 장소/방법/비고. 번호 클릭 시 상세 조회 후 권한에 따른 수정/삭제 제공.
- 모든 화면은 375/768/1280px에서 페이지 전체 가로 overflow 없이 그리드 내부 스크롤.

## API 계약

기본 `/api/v1/sales/deliveries`, 기존 공통 API client 사용.

| Method | 상대경로 | 결과 |
|---|---|---|
| POST | 빈 경로 | 201, `result.item` 납품 헤더+상세 |
| GET | `/{salesDeliveryId}` | `result.item`, 테넌트·사용 중 문서 |
| PUT | `/{salesDeliveryId}` | `result.item`, 수정 후 조회 |
| DELETE | `/{salesDeliveryId}` | 공통 성공 메시지 |
| GET | `/source-orders?keyword=...` | `result.items`, 미납 수주 상세 목록 |
| GET | `/status?deliveryDtFrom=YYYY-MM-DD&deliveryDtTo=YYYY-MM-DD` | `result.items`, 헤더+상세 현황 |

### 요청

```json
{
  "deliveryDt": "2026-11-04",
  "deliveryType": "DIRECT",
  "customerId": 10,
  "salesOrderId": null,
  "deliveryPlace": "",
  "deliveryMethod": "",
  "remark": "",
  "details": [
    { "materialId": 20, "salesOrderDetailId": null, "deliveryQty": 2, "unitPrice": 100, "vatAmt": 20 }
  ]
}
```

수주납품은 `deliveryType=ORDER`, `salesOrderId` 양수, 각 상세 `salesOrderDetailId` 양수. 직납품에서는 두 참조 모두 null.

### 응답

- 납품 item: `salesDeliveryId`, `deliveryNo`, `deliveryDt`, `deliveryType`, `customerId`, `customerCode`, `customerName`, `salesOrderId`, `orderNo`, `deliveryPlace`, `deliveryMethod`, `remark`, `totalAmt`, `createdBy`, `writer`, `details`.
- 상세: `salesDeliveryDetailId`, `lineNo`, `materialId`, `materialCode`, `materialName`, `unit`, `salesOrderDetailId`, `deliveryQty`, `unitPrice`, `supplyAmt`, `vatAmt`, `totalAmt`.
- source-orders 각 행: `salesOrderId`, `salesOrderDetailId`, `orderNo`, `orderDt`, `customerId`, `customerCode`, `customerName`, `deliveryPlace`, `deliveryMethod`, `lineNo`, `materialId`, `materialCode`, `materialName`, `unit`, `orderQty`, `shippedQty`, `remainingQty`, `unitPrice`.
- status 각 행: 헤더 item 필드 중 `details` 제외 + 상세 필드, 그리드 row key는 `salesDeliveryDetailId`.
- status 선택 검색: `keyword`, `deliveryType`, `customerKeyword`, `materialKeyword`, `deliveryNo`.
- source-orders는 취소/출하완료/미사용 수주 제외, 잔량>0, tenant 범위, 최대 200행. keyword는 수주번호·거래처를 검색.

## 서버 검증 및 원자성

- principal의 tenant/user만 사용; 없으면 401. 양수 ID·일자·1개 이상 상세·텍스트 길이·NUMERIC(15,2) 정밀도/범위 검증은 400.
- 거래처/품목은 해당 tenant 소유 및 사용 가능 여부 확인. 없는 참조는 404.
- 중복 수주상세 거부; 연결 수주의 거래처·품목·상세 소속을 확인. 잔량 초과/취소·완료 수주/편집 불가 충돌은 409.
- 금액: 공급가=수량×단가 HALF_UP scale2; VAT 생략 시 공급가×0.10; 상세 합계=공급가+VAT; 헤더 합계=상세 합.
- 채번: `IdSequenceService`, `SALES_DELIVERY_NO`, tenant/date scope, `SD-yyyyMMdd-0001`, 길이 최대 30.
- 한 트랜잭션에서 헤더→수주 헤더 잠금→잔량검증→상세 저장/수주 shipped_qty 증감. 신규 수주납품은 수주 헤더를 먼저 잠그고 상세를 조회한다. 수정/삭제는 납품 헤더 잠금 후 기존 연결 수주 잠금. 수주 ID는 수정 불가이므로 다중 수주 잠금 경합을 만들지 않는다.
- 수정: 기존 납품수량을 먼저 출하수량에서 제외한 유효 잔량을 기준으로 새 요청 검증, 실제 증감은 동일 트랜잭션에서 적용. 실패 시 모두 롤백.
- 삭제: 기존 연결 상세의 수량만 정확히 차감, 논리삭제 후 재삭제는 404로 이중 차감 방지.
- 수주 수정/삭제도 동일 수주 헤더 FOR UPDATE 잠금을 획득하고 납품 참조 이력 존재 시 409. 삭제된 납품도 상세 참조 이력을 보존하므로 연결 수주 상세의 재생성/삭제는 차단한다. 수주 상태·line_status 자동 변경은 하지 않는다.
- MyBatis nullable bigint는 `jdbcType=BIGINT`, numeric는 `jdbcType=NUMERIC`, 날짜는 기존 LocalDate TypeHandler/명시적 date cast 사용.

## DB

- `tb_sales_delivery_hd`: BIGSERIAL PK `sales_delivery_id`, tenant_id, delivery_no varchar30, delivery_dt date, delivery_type varchar10, customer_id, nullable sales_order_id, delivery_place varchar200, delivery_method varchar50, total_amt numeric15,2, remark varchar500, use_at char1, created_by/updated_by varchar100, timestamps.
- `tb_sales_delivery_dt`: BIGSERIAL PK `sales_delivery_detail_id`, sales_delivery_id, tenant_id, delivery_type varchar10(헤더와 동일), line_no, material_id, nullable sales_order_id/sales_order_detail_id, delivery_qty/unit_price/supply_amt/vat_amt/total_amt numeric15,2.
- tenant별 번호 유일, 헤더+tenant 유일, 헤더+line 유일, 수량 양수/금액 비음수 CHECK, DIRECT/ORDER 참조 형태 CHECK.
- 헤더의 거래처·수주와 상세의 품목·부모 헤더·수주상세는 tenant 복합 FK. 상세 source order는 헤더와도 일치해야 한다.
- 기존 수주상세에 `(sales_order_detail_id,sales_order_id,tenant_id,material_id)` 복합 UNIQUE를 추가하여 수주/품목/tenant 참조 일치를 DB에서도 보장한다.
- 상세에서 헤더 `(sales_delivery_id,tenant_id,sales_order_id)` 및 `(sales_delivery_id,tenant_id,delivery_type)` 복합 FK. ORDER 행은 부모 source와 일치, DIRECT는 두 order 컬럼 모두 null. delivery_type까지 부모 FK에 포함하여 nullable source FK의 NULL 검사 우회로 서로 다른 구분의 상세가 저장되지 않게 한다.
- 날짜/거래처/수주참조/품목 인덱스 및 컬럼 주석. 적용/메뉴/rollback/이력은 양쪽 날짜 폴더에 동일 보관.
