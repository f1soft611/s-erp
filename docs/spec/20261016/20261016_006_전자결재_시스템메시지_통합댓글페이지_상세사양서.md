# 20261016_006 전자결재 시스템 메시지 통합 댓글 페이지 상세 사양서

## 1. 개요

문서작성 피드와 상세 패널에서 시스템 메시지를 사용자 댓글과 별도로 전부 표시하는 대신, 둘을 하나의 최신순 페이지 항목 집합으로 조회한다. 사용자가 처음 보는 항목 수와 이전 페이지 단위가 일정하고, 전체 건수·남은 건수·cursor가 같은 항목 정의를 사용하도록 한다.

## 2. 기준 문서 및 DB 계약 확인

- 작업지시서: [20261016_006 전자결재 시스템 메시지 통합 댓글 페이지 작업지시서](../../directions/20261016/20261016_006_전자결재_시스템메시지_통합댓글페이지_작업지시서.md)
- 계획서: [20261016_006 전자결재 시스템 메시지 통합 댓글 페이지 계획서](../../plan/20261016/20261016_006_전자결재_시스템메시지_통합댓글페이지_계획서.md)
- 승인 설계: [시스템 메시지 통합 댓글 페이지 설계](../../superpowers/specs/2026-10-16-document-approval-system-messages-pagination-design.md)
- 구현 계획: [시스템 메시지 통합 댓글 페이지 구현 계획](../../superpowers/plans/2026-10-16-document-approval-system-messages-pagination.md)

백엔드/API 계약 변경 전 `s-erp-postgresql-readonly` MCP를 직접 호출했다.

- `list_tables`에서 `public.tb_common_comment`을 확인했다.
- `describe_table("tb_common_comment")`에서 `comment_id`(BIGINT, sequence 기본값), `tenant_id`, `owner_type`, `owner_id`, nullable `parent_comment_id`, `deleted_yn`, `created_at`, `comment_type`, `event_type`를 확인했다.
- 시스템 메시지와 사용자 댓글이 공통 댓글 레코드로 구분되어 저장되는 기존 계약과 Mapper 사용을 확인했다.
- 행 데이터는 조회하지 않았다. 이번 작업은 신규 컬럼/테이블을 요구하지 않으며 DB 스키마 변경을 하지 않는다.

## 3. 용어 및 페이지 항목

- **사용자 댓글 루트**: `comment_type='USER'`, `parent_comment_id IS NULL`인 스레드의 최상위 행.
- **댓글 스레드**: 사용자 댓글 루트와 그 답글들. 루트 하나가 페이지 항목 하나다.
- **시스템 메시지**: `comment_type='SYSTEM'`인 시스템 이력. 각 메시지가 페이지 항목 하나이며 사용자 댓글 조작 대상이 아니다.
- **통합 항목**: 사용자 댓글 스레드 또는 시스템 메시지 중 하나.
- **이전 페이지 cursor**: 이전에 반환한 페이지에서 가장 오래된 통합 항목의 `comment_id`. USER/SYSTEM 모두 같은 cursor 필드에 사용한다.

답글은 부모 사용자 댓글과 같은 페이지에 포함하고 독립 페이지 항목 또는 추가 건수로 세지 않는다. 기존 페이지 조회는 스레드 안에 삭제되지 않은 행이 하나라도 있으면 루트를 표시하며, 루트 자체가 삭제된 경우에도 삭제 표시 placeholder를 보인다. 이처럼 답글이 남아 화면에 표시되는 삭제 루트 스레드는 통합 페이지 항목 및 건수에 한 번 포함한다. 루트와 모든 답글이 삭제된 스레드는 제외한다. 시스템 메시지는 삭제되지 않은 루트만 페이지 항목으로 조회한다.

## 4. 조회 및 정렬 동작

| 구분 | 통합 페이지 항목 제한 | 설명 |
|---|---:|---|
| 최초 조회 | 3 | 문서별 최신 USER 루트와 SYSTEM 메시지를 합쳐 최신순으로 선택 |
| 이전 조회 | 최대 20 | 동일한 혼합 집합에서 cursor보다 오래된 항목 선택 |

정렬 키는 `created_at DESC, comment_id DESC`로 페이지를 선택하고, 사용자에게는 페이지 안에서 오래된 항목부터 시간순으로 렌더링한다. 같은 시간에는 `comment_id`가 안정적인 보조 정렬 키다.

이전 조회는 cursor ID를 현재 사용자 tenant와 전자결재 문서(owner) 범위에서 확인하고 해당 행의 `(created_at, comment_id)`보다 엄격히 오래된 행을 선택한다. 따라서 cursor가 SYSTEM 메시지 ID여도 동작하고, 같은 시간의 더 큰 ID가 이전 페이지에 중복 포함되지 않는다. cursor가 유효한 전자결재 댓글/시스템 루트가 아니거나 다른 owner/tenant에 속하면 기존 API의 유효성/접근 정책에 따라 오류를 반환하며, 새 페이지로 성공 처리하지 않는다.

피드 일괄 조회에서는 문서별로 독립해 3개씩 선택한다. 한 문서의 댓글/시스템 메시지가 다른 문서의 페이지 한도를 차지해서는 안 된다.

## 5. API 응답 계약

기존 `GET /{electronicApprovalId}/comments?limit={n}&beforeCommentId={id}` 경로를 유지한다. `limit` 기본값은 3이며 기존 허용 범위를 유지한다. 프런트엔드는 최초에 3, 이전 조회에 20을 요청한다.

응답은 기존 필드에 페이지 범위 SYSTEM 항목을 추가한다.

```json
{
  "comments": [
    {
      "commentId": 104,
      "commentType": "USER",
      "parentCommentId": null,
      "content": "<p>검토 의견</p>",
      "attachments": []
    }
  ],
  "systemEvents": [
    {
      "commentId": 103,
      "commentType": "SYSTEM",
      "eventType": "SUBMITTED",
      "content": "문서가 결재신청되었습니다.",
      "writerName": "시스템",
      "createdAt": "2026-10-16T01:00:00.000+00:00"
    }
  ],
  "resultCnt": 4,
  "hasPrevious": true,
  "nextBeforeCommentId": 103
}
```

- `comments`: 선택된 USER 루트와 답글들, 기존 권한/삭제 마스킹/첨부 데이터 유지.
- `systemEvents`: 현재 페이지에 속한 SYSTEM 루트만 포함. 각 항목은 cursor 정렬에 필요한 양의 정수 `commentId`와 메시지 식별/내용/작성 시각을 포함한다.
- `resultCnt`: 문서에서 표시 가능한 사용자 댓글 스레드 수와 시스템 메시지 수 합계. 삭제된 루트에 활성 답글이 남아 있으면 그 스레드를 한 번 세며, 모든 행이 삭제된 스레드와 답글은 세지 않는다.
- `hasPrevious`: 선택한 통합 항목보다 오래된 통합 항목이 존재하는지 나타낸다.
- `nextBeforeCommentId`: `hasPrevious=true`일 때 현재 페이지에서 가장 오래된 통합 루트 ID, 아니면 `null`.

피드 선조회 payload의 `comments`, `systemEvents`, `commentCount`, `hasPreviousComments`, `nextBeforeCommentId`도 동일 정의를 사용한다. 피드의 `systemEvents`에는 전체 이력이 아니라 최초 3개 혼합 페이지에 포함된 시스템 메시지만 넣는다. 상세 패널에서 기존 detail 응답으로 전체 이력이 먼저 도착하더라도 댓글 페이지 로딩 완료 후 표시 상태는 그 페이지의 시스템 메시지로 교체하고, 이전 페이지를 불러오면 더 오래된 페이지 메시지를 앞에 추가한다.

## 6. 프런트엔드 표시 및 상태

1. USER 댓글 트리와 SYSTEM 페이지 항목은 별도 타입/컬렉션으로 유지한다.
2. `commentId`로 각 SYSTEM 항목을 식별하고 `createdAt`, `commentId` 기준으로 사용자 댓글 루트와 합쳐 렌더링한다. 시스템 메시지는 기존 읽기 전용 스타일을 유지한다.
3. SYSTEM 메시지는 댓글 입력, 답글, 편집, 삭제, 첨부 조작 handler에 전달하지 않는다.
4. 반응 바의 댓글 건수는 통합 `commentCount`를 한 번만 표시한다. `systemEvents.length`를 더해 중복 계산하지 않는다.
5. 남은 건수는 `commentCount - (현재 로드된 표시 가능 USER 루트 스레드 수 + 현재 로드된 SYSTEM 수)`로 계산한다. 삭제 표시 루트에 활성 답글이 남아 있는 경우도 한 스레드로 세며, 사용자 댓글 답글은 로드 항목 수에 추가하지 않는다.
6. 기존 최초 3개 및 이전 20개 요청 방식을 유지하되 페이지 API가 USER와 SYSTEM의 혼합 항목 수를 기준으로 처리한다.
7. 이전 페이지 요청이 실패하면 기존 항목, cursor, 남은 건수를 유지하고 명시적 댓글 오류/재시도 UI를 보인다. 재시도는 실패한 동일 cursor로 수행한다.
8. 피드 선조회와 리스트 상세 패널의 댓글 조회에서 같은 합산 규칙을 사용한다.
9. USER 댓글과 SYSTEM 메시지가 모두 없을 때 `등록된 댓글이 없습니다.` 빈 상태 문구는 표시하지 않으며, 댓글 입력창은 계속 사용할 수 있다. 기존 로딩 표시와 오류/재시도 동작은 유지한다. 회귀 검증은 [빈 댓글 안내문구 제거 결과](../../result/20261016/approval-empty-comment-state/20261016_012_전자결재_빈댓글_안내문구_제거_결과보고서.md)를 참고한다.

## 7. 오류 및 호환성

- 문서 권한, tenant 범위, USER 댓글 mutation, 첨부 권한은 기존 정책을 유지한다.
- malformed SYSTEM 메시지, 빠진 cursor/count 필드 등 페이지 응답 계약 위반은 성공 형태의 빈 페이지로 대체하지 않고 기존 서비스 검증 오류로 처리한다.
- 공통 `CommonCommentPageVO`를 확장하지 않고 전자결재 전용 페이지 응답 DTO를 사용해 다른 댓글 API 응답에 필드를 추가하지 않는다.
- DB 스키마, 공지사항 댓글 피드, 시스템 이력 생성 시점/내용은 변경하지 않는다.

## 8. 검증 기준

- USER/SYSTEM 루트가 섞인 최초 응답에서 문서별 통합 항목 최대 3개를 선택하고 답글은 부모 스레드 아래 보존한다.
- `resultCnt`, `hasPrevious`, cursor가 표시 가능한 USER 스레드와 SYSTEM 전체 집합을 기준으로 일치한다. 삭제된 루트에 활성 답글이 남은 스레드는 페이지/건수에 한 번 포함되고, 완전히 삭제된 스레드는 제외된다.
- SYSTEM cursor와 USER cursor 각각으로 이전 페이지를 조회할 수 있고, 동시간 ID 경계에서 중복이나 누락이 없다.
- 이전 페이지에서 최대 20개 통합 루트를 반환하고 전체 소진 시 버튼을 숨긴다.
- 댓글 수/남은 수가 시스템 메시지를 정확히 한 번 포함하고 답글을 중복 산정하지 않는다.
- USER 첨부, 삭제 마스킹, 쓰기/답글/수정/삭제, 오류 및 재시도 회귀 테스트가 통과한다.
- 집중 백엔드 테스트, 서비스/API 프런트엔드 테스트, 프런트엔드 production build를 검증한다.
- `/groupware/doc/write`의 375px, 768px, 1280px 실제 브라우저 확인과 결과 스크린샷을 기록한다.
