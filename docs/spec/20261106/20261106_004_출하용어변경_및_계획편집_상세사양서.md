# 출하 용어 변경 및 출하계획 편집 상세사양서

## 승인 설계와 범위

- [설계 문서](../../superpowers/specs/2026-11-06-sales-shipment-terminology-design.md)의 승인된 내용을 구현 기준으로 삼는다.
- 화면과 메뉴에서 영업 납품 업무의 용어를 출하로 변경한다. `납품관리`는 `출하관리`, `납품등록/납품현황`은 `출하등록/출하현황`, `납품계획`은 `출하계획`, 계획 메뉴는 `출하계획등록/출하계획현황`으로 표시한다.
- 기존 페이지 키, URL, 메뉴 코드, API 경로/JSON 필드, DB 식별자와 정책 코드는 변경하지 않는다.
- 주문/수주 자체의 명칭 및 직납품/수주 연계 흐름은 유지한다.

## 메뉴·정책 명칭

| 기존 식별자 | 변경 표시명 |
|---|---|
| `SALES_DELIVERY` | 출하관리 |
| `SALES_DELIVERY_CREATE` | 출하등록 |
| `SALES_DELIVERY_STATUS` | 출하현황 |
| `SALES_DELIVERY_PLAN` | 출하계획 |
| `SALES_DELIVERY_PLAN_CREATE` | 출하계획등록 |
| `SALES_DELIVERY_PLAN_STATUS` | 출하계획현황 |
| `DELIVERY_PLAN_MODE` policy name | 출하계획 운영모드 |
| `OVER_DELIVERY_POLICY` policy name | 초과출하 정책 |

각 메뉴 설명과 정책 설명도 업무 사용자에게 보이는 문구에서 납품 용어를 출하로 정리한다. 기존 메뉴 URL, 계층, 권한 매핑 및 정책 타입/값/선택지/버전은 변경하지 않는다. 기존 테넌트의 메뉴·정책 레코드는 날짜별 데이터 업데이트 SQL로 변경하고, `docs/database`와 `backend/DATABASE` 사본은 동일하게 유지한다. SQL은 문서로만 제공하며 실행하지 않는다.

## 운영 모드별 계획 흐름

| 모드 | 출하계획등록 | 출하계획현황 | 계획 생성 |
|---|---|---|---|
| `MANUAL` | 계획이 없는 수주를 선택해 등록하거나 기존 계획을 수정 | 전체 계획 조회 및 권한에 따른 수정 | 사용자가 신규 계획 생성 가능 |
| `AUTO` | 자동 생성된 기존 계획을 불러와 수정 | 전체 계획 조회 및 권한에 따른 수정 | 수주 저장 시에만 자동 생성; 수동 신규 생성 불가 |

- 계획 조회, 상태 조회, 기존 계획 수정은 두 모드 모두 허용한다. 수동 신규 생성 API는 MANUAL 전용으로 유지한다.
- 출하계획등록의 수주 선택 API는 MANUAL에서 미계획 수주를, AUTO에서 기존 자동계획이 있는 수주를 반환한다.
- AUTO에서 계획을 선택하면 계획 ID/번호와 저장된 계획 상세 행을 로드하고, 동일 상세를 새 계획으로 중복 생성하지 않고 기존 계획을 수정한다.
- MANUAL에서는 기존 계획 상세를 불러와 수정하는 동작을 유지한다.
- 상세 계획일·계획수량은 사용자 권한에 따라 저장한다. 이미 납품 참조가 있는 계획행의 기존 편집·삭제 제한, delivered quantity 정합성, 원 수주 및 테넌트 귀속 검증을 유지한다.
- 출하계획현황은 계획 기간 검색, 상세 조회, 조회/수정 권한을 유지한다. 상태 값은 기존에 정의가 없으므로 새로 만들지 않는다.

## AUTO 수주 수정과 계획 보존

- 수주 생성 시 기존과 같이 주문과 자동 계획을 한 트랜잭션에서 만든다.
- AUTO 수주 수정에서 기존 자동계획 상세의 계획일과 계획수량을 주문 수량으로 다시 덮어쓰지 않는다.
- 기존 수주 상세 ID와 해당 계획 상세 ID를 유지한다. 신규 수주 상세에는 기존 납기일 fallback과 수주수량을 사용해 자동 계획 상세를 추가한다.
- 주문 수량을 늘려도 편집된 계획수량은 자동으로 증가시키지 않는다. 남은 미계획 수량은 사용자가 계획 화면에서 편집한다.
- 주문 수량을 기존 계획합계보다 낮추는 요청은 HTTP 409로 거부한다. 수주 상세 삭제는 해당 계획/출하 참조 여부와 기존 무결성 규칙에 따른다.
- 계획 저장과 수주 저장은 수주 헤더 잠금 순서 및 동일한 트랜잭션 경계로 경쟁 상태를 방지한다. 실제 납품·직납품 처리 규칙은 변경하지 않는다.

## API 및 저장 계약

- API 경로와 기존 DTO/응답 필드명은 유지한다.
- 계획 조회/현황 및 기존 계획의 GET/PUT는 AUTO와 MANUAL에서 허용한다.
- 계획 등록 POST는 MANUAL에서만 허용한다. AUTO에서는 신규 계획 생성 시도를 거부하고 기존 계획 편집은 허용한다.
- 출하계획 수주선택 조회는 인증 테넌트와 현재 모드에 맞는 주문만 반환한다. 요청의 tenant ID를 신뢰하지 않는다.
- 출하계획 번호, 수주 ID, 수주 상세 ID, 계획 상세 ID, 출하 참조와 delivered quantity의 계약을 그대로 유지한다.
- 기존 `tb_system_policy`의 `DELIVERY_PLAN_MODE`와 `OVER_DELIVERY_POLICY` 코드는 유지하며 화면 표시명/설명만 변경한다. 실제 적용값은 계속 기존 tenant 컬럼에서 읽고 쓴다.
- 새 데이터 구조나 컬럼은 추가하지 않는다. 마이그레이션은 기존 메뉴/정책의 표시명 및 설명 데이터만 변경한다.

## 테스트 및 완료 기준

- AUTO/MANUAL의 메뉴 표시 및 출하 용어를 확인한다.
- AUTO 등록 화면이 기존 계획을 로드·수정하며 신규 계획을 생성하지 않는지 확인한다.
- MANUAL 계획 신규 등록과 기존 수정, 양 모드의 계획현황 조회/수정을 확인한다.
- AUTO 수주 수정은 사용자 편집 계획일/수량을 보존하고, 신규 상세 계획을 추가하며, 계획합보다 낮은 수주수량을 거부한다.
- 계획/출하 참조와 tenant 범위, 권한 제한 및 기존 delivered quantity 검증을 회귀 확인한다.
- SQL/rollback의 변경 대상·조건을 정적으로 검토하고 두 복사본의 동일성을 검사한다. 실제 DB에는 적용하지 않는다.
- 관련 backend 테스트, 변경 범위 frontend 테스트, frontend build/lint, 375/768/1280px 브라우저 확인과 스크린샷을 결과 문서에 남긴다.
