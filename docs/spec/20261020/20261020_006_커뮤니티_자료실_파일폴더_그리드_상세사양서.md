## 2. 데이터 모델

### 폴더

- 폴더 데이터는 인증 tenant의 활성 `WF_ARCHIVE_CATEGORY` 공통코드 그룹 항목이다.
- 공통코드 `itemCode`는 `tb_board_post.category_code`에 저장한다. 새 테이블/컬럼이나 공통코드 그룹을 추가하지 않는다.
- 분류 도움창은 기존 `CommonCodeItemHelpDialog`를 재사용한다. `title` 및 그리드 접근성 레이블은 선택적 props로 추가하고, 기존 기안양식 호출 기본값을 바꾸지 않는다.
- 사용중지 폴더는 루트에서 계속 표시하고 열람/다운로드를 허용한다. 비활성 폴더 안에서는 새 업로드, 이름 변경, 이동, 삭제를 허용하지 않는다. 재활성화되면 파일 작업을 다시 허용한다.

### 파일과 게시글

- `tb_common_file` 한 건이 파일 한 건이며 `owner_type='ARCHIVE'`, `owner_id=tb_board_post.post_id`로 게시글에 연결된다.
- 파일 목록 응답은 활성 archive 첨부를 기준으로 하여 `tb_common_file` 한 건당 한 행을 만든다. 필드: `boardFileId`, `postId`, `fileName`, `fileSize`, `mimeType`, `uploadedAt`, `writerName`, `categoryCode`.
- 파일명은 `tb_common_file.file_name`, 소유자는 연결 게시글의 `writer_name`, 올린 날짜/크기는 첨부의 `created_at`/`file_size`를 사용한다.
- 신규 업로드 파일마다 게시글을 1건 생성한다. `title`은 안전하게 정규화한 원본 파일명, `contents`는 null, 작성자/tenant는 인증 사용자, 게시판 코드는 `ARCHIVE`다. 파일명은 현재 서버 제목 검증 한도인 200자를 넘지 않아야 하며 넘으면 업로드를 거부하고 이유를 표시한다.
- 기존 다중 첨부 게시글은 변환/복제하지 않고 첨부별 목록 행으로 펼친다. 기존 첨부 없는 자료 게시글만 soft delete한다.
- 첨부 삭제 후 게시글에 활성 첨부가 없으면 게시글도 soft delete한다.

## 3. 화면 및 동작

### 탐색 그리드

- 자료실 루트에는 `폴더` 섹션 행, 폴더 행, `파일` 섹션 행, 루트 파일 행 순서로 표시한다. 폴더를 열면 해당 폴더의 파일 행만 표시하고 `자료실 > 폴더명` 경로와 루트 이동 동작을 제공한다.
- 폴더는 한 단계만 제공하며 하위 폴더는 없다.
- 단일 F1-Grid에서 `section`, `folder`, `file` 행 유형을 구분한다. row key는 유형과 공통코드/파일 ID로 안정적으로 구성한다.
- 컬럼은 `이름`, `소유자`, `올린 날짜`, `크기`, `작업` 순서다. 파일명/폴더명은 긴 문자열도 줄바꿈/말줄임으로 그리드 밖으로 넘치지 않는다.
- 파일 행 소유자는 게시글 작성자, 날짜는 파일 생성 시각, 크기는 바이트를 사용자 친화적 단위로 표시한다. 폴더 행은 공통코드 생성 시각을 사용할 수 있으면 표시하고 소유자/크기는 `—`로 표시한다.
- 기본 정렬은 최근 파일 우선이며 그리드 정렬/편집/Excel 내보내기는 비활성화한다.
- 검색은 현재 위치의 파일명과 소유자에 적용한다. 루트에서는 폴더명도 클라이언트에서 필터링한다. 검색 결과에도 현재 위치 조건을 유지한다.

### 신규 파일 등록

- 권한이 있는 사용자가 `새 자료 등록`을 누르면 hidden multiple file input의 운영체제 파일 선택창을 즉시 연다.
- 선택이 취소되면 요청을 보내지 않는다. 하나 이상 선택되면 선택된 각 파일을 순서대로 개별 업로드 요청한다. 별도 폼, 제목/설명 입력 또는 확인 다이얼로그를 표시하지 않는다.
- 업로드 중 진행상태와 파일별 성공/실패를 표시한다. 실패한 파일은 재시도 가능하며, 실패를 성공 또는 빈 목록으로 표시하지 않는다.
- 루트에서 선택한 파일은 분류 없이 업로드하고, 폴더 안에서는 현재 폴더 코드를 자동 지정한다.
- 업로드 후 `tb_board_post.title`은 파일명으로 자동 저장된다.

### 파일 작업

- 파일명 선택 또는 다운로드 작업은 기존 인증 다운로드 API로 연결한다.
- 활성 폴더의 파일 행 더보기는 `이름/폴더 변경`, `삭제`, `다운로드`를 제공한다. 이름/폴더 변경은 별도 다이얼로그이며 입력값은 파일명과 목적지(루트 또는 활성 폴더)다.
- 파일명은 공백만 입력할 수 없고 200자를 넘을 수 없다. 경로 구분자/경로 탐색 문자열은 파일명으로 허용하지 않는다.
- 단일 첨부 게시글의 파일명 변경은 `tb_common_file.file_name`과 `tb_board_post.title`을 함께 갱신한다. 다중 첨부 legacy 게시글의 파일명 변경은 해당 첨부 파일명만 갱신한다.
- 단일 첨부 게시글의 폴더 이동은 해당 게시글 `category_code`만 갱신한다. 다중 첨부 legacy 게시글에서 하나의 첨부만 이동하면 해당 첨부 이름/분류로 새 게시글을 만들고 `tb_common_file.owner_id`를 변경한다. 다른 첨부는 원 게시글에 남는다. MinIO 객체는 복사하지 않고 `object_key`를 유지한다.
- 삭제는 확인 대화상자를 거친다. 이동/삭제 작업 중 해당 행 버튼은 중복 요청을 막도록 비활성화한다.
- 비활성 폴더 안의 파일 행은 다운로드만 허용한다.

## 4. HTTP API 계약

모든 응답은 기존 `ResultVO` envelope를 사용한다. 인증 tenant는 서버 principal에서 가져오며 요청 tenant 값은 사용하지 않는다.

| Method/Path | 입력 | 결과/규칙 |
|---|---|---|
| `GET /api/v1/groupware/boards/archive/files` | `offset`, `limit`, optional `keyword`, optional `folderCode` | `folderCode` 누락은 루트(`category_code IS NULL`), 지정 값은 해당 폴더. `resultList`는 파일별 행, `resultCnt`는 파일 개수. |
| `POST /api/v1/groupware/boards/archive/files` | multipart 필수 `file`, optional `folderCode` | 단일 파일을 게시글/첨부로 생성하고 새 파일 행 반환. 빈 파일/잘못된 이름/비활성·미등록 폴더는 오류. |
| `PUT /api/v1/groupware/boards/archive/files/{boardFileId}` | JSON `postId`, `fileName`, nullable `folderCode` | 파일명 변경 및/또는 루트/활성 폴더 이동. tenant/게시판/소유권/현재 폴더/목적지 폴더 검증 후 행 반환. |
| `DELETE /api/v1/groupware/boards/archive/attachments/{boardFileId}?postId=...` | 소유 게시글 ID | 기존 소유권 검증을 유지. 마지막 활성 첨부이면 게시글 soft delete. |
| `GET /api/v1/groupware/boards/archive/attachments/{boardFileId}/download?postId=...` | 소유 게시글 ID | 기존 인증 다운로드 및 tenant/소유권 검증을 유지. |

- 자료실 신규 작성은 위 파일 업로드 API만 사용한다. 기존 게시글 단독 생성/전체 수정/전체 삭제 mutation은 더 이상 제공하지 않아 빈 게시글 생성이나 폴더 단위 외 파일 조작 우회를 허용하지 않는다.
- 기존 코드 검색 결과 자료실 post CRUD 호출자는 자료실 페이지뿐이다. API 제거 전 구현 시점에 다시 검색하고 다른 in-repository 소비자가 발견되면 계약 중단점에서 사용자 확인을 받는다.
- 업로드는 게시글 생성, 파일 업로드, 결과 조립의 단일 서비스 흐름으로 수행한다. 저장 실패 시 게시글/파일 메타데이터를 정리하여 화면에 빈 자료를 남기지 않고 오류를 반환한다.
- 모든 쓰기/업로드/이름 변경/이동/삭제는 기존 자료실 관리자 및 게시판 정책에 의해 서버에서 권한 검사한다.
- 비활성 폴더의 파일 mutation은 서버에서도 거부한다. 다운로드는 허용한다.

## 5. 백엔드 검증 규칙

- `offset >= 0`, `limit > 0` 및 허용된 최대 page 크기를 검증한다.
- 검색은 `file_name` 또는 소유 게시글 `writer_name`에 적용한다. 파일 목록/총건수 모두 tenant, `board_type_code='ARCHIVE'`, `owner_type='ARCHIVE'`, `file_usage_type='ATTACHMENT'`, `deleted_yn='N'`를 동일하게 적용한다.
- 폴더 코드는 인증 tenant의 `WF_ARCHIVE_CATEGORY` 그룹에서 확인한다. 새 업로드/목적지 이동은 활성 항목만 허용하고, 목록/기존 파일 열람은 비활성 항목도 허용한다.
- 새 업로드용 `tb_board_post.title`은 정규화된 원본 파일명과 같아야 한다. 200자를 넘거나 비어 있으면 `400`으로 거부한다.
- 이름 변경/이동은 해당 tenant의 `ARCHIVE` post와 활성 attachment를 모두 검증한다. 파일 ID만 다른 post에 적용할 수 없으며, 동일 tenant 밖의 파일/post/folder ID를 거부한다.
- 파일명 변경/owner 재연결/post metadata 갱신은 DB 트랜잭션 범위에서 일관성 있게 수행한다. 파일 저장소 객체는 이름 변경/이동 시 그대로 유지한다.
- 파일 삭제 성공 여부를 명시하고, 마지막 첨부 확인과 post soft delete는 경쟁 조건을 막기 위해 적절한 post lock/transaction으로 처리한다.

## 6. 기존 데이터 정리 및 DB 관리

- 일회성 정리 SQL은 tenant별 `ARCHIVE` 게시글 가운데 활성 `ARCHIVE` 첨부가 없는 행만 `is_deleted='Y'`로 변경한다. 파일 행은 변경하지 않는다.
- 정리 대상 추적 및 안전한 rollback을 위해 스크립트는 고유한 cleanup actor 값을 `last_modified_by`/`last_modified_by_name`에 기록한다. rollback은 그 actor marker가 남아 있고 활성 첨부가 여전히 없는 archive 게시글만 복구한다. 다른 actor로 갱신된 행은 변경하지 않는다.
- `backend/DATABASE/20261020`와 `docs/database/20261020`에 동일한 SQL, 변경 이력, rollback 파일을 둔다. 변경 이력에는 날짜, 적용 대상, 범위, tenant 경계, soft-delete 방식, rollback 조건을 적는다.
- 스키마 DDL은 없으므로 `docs/database/db-schema.md`를 변경하지 않는다.
- 실제 실행 전 기본 workspace MCP에서 PII가 없는 aggregate count와 대상 범위를 확인한다. 기본 MCP 조회가 불가능하면 tenant별 DB를 추정하거나 우회하지 않고, 연결/조회 미확인 사실을 결과에 기록하며 DML 적용을 중단한다. read-only MCP로 DML을 수행하지 않는다.

## 7. 권한 및 오류 처리

- `새 자료 등록`: tenant admin + 현재 메뉴 `create` 권한 + `ARCHIVE` file upload 정책.
- 이름/폴더 변경: tenant admin + 현재 메뉴 `update` 권한.
- 파일 삭제: tenant admin + 현재 메뉴 `delete` 권한.
- 폴더 코드 추가/수정: 기존 공통코드 item endpoint 서버 권한을 유지하고 화면에서는 tenant admin 및 자료실 `create` 또는 `update` 권한으로 편집을 허용한다.
- 읽기 및 다운로드는 현재 메뉴/게시판 read 정책을 따른다.
- 업로드 일부 실패, 목록 조회 실패, 이름/폴더 변경 실패, 삭제 실패, 다운로드 실패를 오류 상태/알림으로 노출한다. 실패한 항목은 화면에서 성공으로 표시하지 않고 재시도/복구 경로를 제공한다.
