## 근거와 승인

- [작업지시서](../../directions/20261020/20261020_005_document-file-view_작업지시서.md)
- [계획서](../../plan/20261020/20261020_005_document-file-view_계획서.md)
- 사용자는 문서 직접 첨부와 댓글 첨부 모두 포함 및 서버 파일 전용 페이지/공통 UI 설계를 승인했다.
- 사용자는 이 상세 사양서를 검토·승인하고 현재 작업 폴더에서 직접 구현·검증을 진행하도록 확인했다.

## 1. 조회 대상

- 로그인 tenant의 미삭제 문서 중 본인이 작성한 문서 또는 결재·합의·참조 참여 문서.
- 기존 `documentReadAccess`를 재사용한다. 본인 DRAFT는 포함하고 타인의 DRAFT는 제외한다.
- 직접 첨부: 파일 `owner_type = APPROVAL`, `owner_id = electronic_approval_id`.
- 댓글 첨부: 파일 `owner_type = APPROVAL_COMMENT`, `owner_id = comment_id`; 댓글은 같은 tenant의 `owner_type = APPROVAL`, `comment_type = USER`, 미삭제 댓글이어야 한다.
- 모든 파일은 `deleted_yn = N`, `file_usage_type = ATTACHMENT`여야 한다.
- 본문 삽입 이미지는 제외한다. 댓글 본문 이미지와 일반 첨부의 구분도 같은 파일 용도 조건을 따른다.
- 문서 유형·scope·선택 문서 조건은 기존 문서작성 필터와 같은 의미로 적용한다.
- 로그인 tenant·작성자·참여자 식별값은 인증 사용자에서만 가져온다.
- `actorParams`의 쓰기 경로 기본값인 `documentStatus=DRAFT`는 파일 조회 파라미터에서 제거한다. ALL에서 암묵적인 문서 상태 필터를 적용하지 않으며, DRAFT/COMPLETED 등 명시적인 scope만 기존 의미로 적용한다. 다음 페이지 커서 권한 확인에도 같은 조건을 사용한다.

## 2. 정렬과 페이지

- 정렬 키는 `file.created_at DESC, file.file_id DESC`이다. 문서 수정일이나 댓글 수정일로 대신하지 않는다.
- 화면에 전달하는 페이지 크기는 고정 20개다. 서버는 최대 21개를 읽어 다음 페이지 여부를 판단한다.
- 커서는 마지막으로 전달한 파일의 ID다. 서버는 해당 파일을 현재 tenant·권한·필터 안에서 찾아 원본 시각과 ID를 비교한다.
- 다음 페이지는 `(created_at, file_id)`가 커서 파일보다 작은 파일만 반환한다.
- 이 방식으로 시각이 같은 파일과 timestamp의 밀리초 미만 정밀도에도 누락·중복을 방지한다.
- 커서 파일이 삭제되거나 권한/필터가 바뀌어 찾을 수 없으면 400으로 알리고, 화면은 목록 새로고침을 통해 첫 페이지로 재시작할 수 있게 한다. 권한이 없는 파일의 존재 여부를 구분해 노출하지 않는다.
- 목록 조회 도중 추가된 최신 파일은 목록 새로고침 시 표시한다.

## 3. 신규 API 계약

`GET /api/v1/groupware/approvals/files`

쿼리:

| 이름 | 의미 |
| --- | --- |
| scope | 기존 문서 scope, 기본 ALL |
| documentType | 기존 문서 유형 필터, 선택 |
| electronicApprovalId | 기존 선택 문서 필터, 선택 |
| beforeFileId | 다음 페이지 커서, 양의 안전한 정수, 선택 |

기존 ResultVO 응답 envelope의 `resultList`, `hasNext`, `nextBeforeFileId`를 사용한다.

```json
{
  "resultList": [
    {
      "fileId": 101,
      "fileName": "sample.pdf",
      "fileSize": 1200,
      "mimeType": "application/pdf",
      "uploadedByName": "Sample User",
      "createdAt": "2026-10-20T00:00:00.000+00:00",
      "electronicApprovalId": 10,
      "documentTitle": "Sample Document",
      "commentId": null
    }
  ],
  "hasNext": false,
  "nextBeforeFileId": null
}
```

- `commentId`는 직접 첨부에서 null, 댓글 첨부에서 댓글 ID다.
- `createdAt`은 기존 서버의 날짜 직렬화 형식을 유지하고 클라이언트의 기존 날짜 유틸로 표시한다. 예시의 타임존을 새 전역 설정으로 강제하지 않는다.
- 업로더 이름은 파일 uploaded_by와 기존 사용자 이름 조회 관계를 이용한다. 업로더 정보가 없거나 삭제된 경우 `알 수 없음`으로 표시하며 문서 기안자를 업로더로 오인 표시하지 않는다.
- hasNext가 true면 nextBeforeFileId는 반드시 마지막 노출 파일 ID이고 목록은 20개다. false면 커서는 null이다.
- 저장 경로·object key·bucket·tenant·인증/계정 정보를 응답에 추가하지 않는다.
- 입력 오류·인증 오류는 기존 예외 처리 규칙을 유지한다. 유효하지 않은 응답을 빈 목록으로 바꾸지 않는다.
- 기존 목록/피드/상세 API 응답 형태는 변경하지 않는다.

## 4. 공통 UI

- 파일형은 공통 보기 토글의 선택적 기능이다. 기본은 기존 feed/list 두 모드다.
- 공통 FileView는 파일 항목, 초기/추가 로딩, 오류 문구, 재시도, hasNext, 추가 조회 콜백, 다운로드 및 원문 보기 콜백을 받는다.
- 파일 아이콘은 확장자/MIME에 따라 표시하고 파일명·소유자·올린 날짜·크기를 표 형태로 배치한다.
- 파일명 클릭은 다운로드한다. 행의 별도 `원문 보기` 버튼은 문서 상세를 연다.
- 소유자는 파일 업로더다. 파일이 포함된 원문 제목과 댓글 첨부 여부를 부가 설명으로 표시한다.
- 표 머리글은 소유자, 올린 날짜, 크기를 사용한다. 크기는 기존 형식 유틸을 우선 재사용한다.
- 폴더 구분, 즐겨찾기, 파일 삭제, 일괄 다운로드, 업로드 기능은 추가하지 않는다.
- 모바일은 이름과 메타정보를 줄바꿈하여 페이지 전체의 가로 스크롤을 방지한다.
- 사용자 승인 표시 보완: 파일 목록 루트 배경은 `common.white`로 지정하여 머리글과 행 기본 배경을 흰색으로 표시한다. 페이지 배경과 행 hover는 변경하지 않는다.
- 마지막 페이지에 `모든 파일을 불러왔습니다.` 문구나 이를 위한 하단 여백을 표시하지 않는다. hasNext=false에 따른 추가 요청 종료는 유지한다.
- 로딩은 status, 오류는 alert, 동작은 키보드 접근 가능한 버튼/링크로 제공한다.

## 5. 문서작성 연결과 상태

- 피드형·리스트형 옆에 파일형을 추가한다. 우측 요약 패널과 기존 문서 상세/작성 모달을 유지한다.
- 파일형에서는 문서 상단고정 목록/카운트로 파일을 분리하지 않는다.
- 파일형 진입 시 파일 페이지와 필요한 요약만 조회한다. 파일 수집을 위해 전체 문서/댓글/피드 상세를 조회하지 않는다.
- 실제 스크롤 컨테이너를 기준으로 하단 sentinel의 교차를 감지한다.
- hasNext가 true이고 로딩/오류 상태가 아닐 때만 다음 페이지를 조회한다.
- 요청이 끝나기 전 반복 감지는 같은 페이지를 중복 요청하지 않는다.
- 필터 변경, 전체 조회, 문서 선택 변경, 명시적 새로고침은 이전 요청을 무효화하고 첫 페이지로 초기화한다.
- 페이지 전환/언마운트 후 응답은 무시한다. 다음 페이지 실패 시 기존 파일 행은 유지하며 자동 재시도 루프를 만들지 않는다.
- 첫 페이지 오류와 추가 페이지 오류에 재시도를 제공한다. 커서 무효 오류는 `목록 새로고침`으로 재시작한다.
- 더 이상 파일이 없으면 추가 요청을 종료한다. 처음부터 없으면 `첨부파일이 없습니다.`를 표시한다.
- 파일 다운로드에는 문서/댓글별 기존 함수를 사용하며 다운로드 시점의 권한을 다시 검증한다.
- 작성/상세 액션 후 기존 목록 갱신 경로에 파일 페이지 초기화도 연결한다.

## 6. DB MCP 확인

2026-10-20 기본 `s-erp-postgresql-readonly`의 `list_tables`와 아래 테이블의 `describe_table`을 직접 호출했다. 데이터 행 조회는 하지 않았다.

- `tb_common_file`: owner_type, owner_id, uploaded_by, deleted_yn, created_at, file_usage_type; 시각과 파일 ID는 NOT NULL.
- `tb_common_comment`: tenant/owner 관계, writer, deleted_yn, comment_type.
- `tb_electronic_approval_main`: tenant, drafter_id, document_status, deleted_yn, document_type.
- `tb_electronic_approval_line_info`: tenant, electronic_approval_id, participant_user_id, participant_type.
- 업로더 이름 관계 추가 확인: `tb_user`의 tenant_id, login_id, user_nm과 `tb_login_account`의 tenant_id, login_id, login_code.

기존 코드는 직접 첨부에 APPROVAL, 댓글 첨부에 APPROVAL_COMMENT를 사용하며 업로드 시 사용자 로그인 코드를 저장한다. 기존 계정·사용자 조인 패턴과 위 메타데이터를 확인하여 같은 tenant에서 업로더 표시 이름만 조회한다.

현재 설계에는 DDL·마이그레이션이 필요하지 않다. 성능상 인덱스 변경이 필요한 것으로 확인되면 별도 SQL·변경 이력·롤백과 누적 스키마 문서를 함께 갱신한다.

## 7. 완료 검증

1. 직접 첨부·댓글 첨부 혼합 45개에서 최초 20개, 다음 20개, 마지막 5개가 시간/ID 내림차순으로 누락·중복 없이 표시된다.
2. 같은 시각의 여러 파일도 안정적으로 페이징된다.
3. 타 tenant, 타인 DRAFT, 비참여 문서, 삭제 문서·댓글·파일, 본문 이미지는 제외된다.
4. 본인 DRAFT와 결재·합의·참조 참여 문서는 기존 권한 범위로 조회된다.
5. 업무구분/scope/선택 문서 변경과 새로고침에서 이전 응답이 섞이지 않는다.
6. 다음 페이지 로딩 중 반복 스크롤은 한 번만 요청한다. 마지막 페이지 뒤 요청이 없다.
7. 조회 실패·다운로드 실패가 명시적으로 표시되고 재시도 가능하다.
8. 다른 페이지 토글에는 파일형이 나타나지 않고 기존 피드·리스트 테스트가 유지된다.
9. 프론트엔드 대상 테스트/빌드와 백엔드 관련 테스트가 통과한다.
10. 375px, 768px, 1280px 브라우저에서 표·버튼·긴 파일명·자동 로딩을 확인하고 합성 데이터 스크린샷을 결과 문서에 저장한다.

## 8. 파일형 로딩 스켈레톤 보완

- `isLoading`이 true이고 아직 표시된 파일이 없을 때에는 초기 진행 표시 대신 파일 행 형태의 스켈레톤 8개를 표시한다.
- 목록의 기존 머리글은 유지하며 데스크톱에서는 이름·소유자·올린 날짜·크기 열과 정렬을 맞춘다.
- 모바일에서는 기존 파일 행과 같이 이름을 중심으로 배치하고 페이지 전체 가로 넘침을 만들지 않는다.
- 다음 페이지 로딩 중에는 기존 파일 행을 유지하고 목록 아래에 기존 진행 표시를 보여준다. 별도 스켈레톤 행은 추가하지 않는다.
- 오류, 빈 결과, 종료 상태, 재시도, 새로고침, 자동 페이지 로딩 및 흰색 배경은 변경하지 않는다.
- 백엔드 API, 파일 조회 계약, 페이지 크기 및 파일 데이터 구조는 변경하지 않는다.

## 9. 페이징 스피너 및 다크테마 가독성 보완

- 다음 파일 페이지 조회 중 기존 파일 행을 유지하고, 시각적으로는 안내 문구 없이 가운데 정렬된 MUI 로딩 스피너만 표시한다.
- 로딩 컨테이너는 `role="status"`와 한국어 접근성 이름을 제공하고 스피너는 progressbar로 노출한다.
- 라이트 테마에서 목록 표면은 승인된 흰색(`common.white`)으로 유지한다.
- 다크 테마에서는 고정 흰색 대신 앱 테마의 `background.paper`를 사용해 파일명, 메타데이터, 테두리, hover와 로딩 표시의 대비를 유지한다.
- 첫 페이지 스켈레톤의 조건/배치, 오류·빈 목록·재시도·새로고침 및 자동 페이지 처리 동작은 변경하지 않는다.
- 서버, API, 파일 페이지 규격 및 응답 데이터는 변경하지 않는다.
