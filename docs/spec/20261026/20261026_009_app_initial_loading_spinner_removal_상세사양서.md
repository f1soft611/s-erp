## 적용 위치

- 앱 라우트 모듈 lazy-load 중 `AppRouter`가 표시하는 `Suspense` fallback을 변경한다. lazy loading은 유지하되 loading spinner는 표시하지 않는다.
- 대시보드 첫 진입에서 메뉴 정보를 요청하는 `DashboardPage`의 `menusLoading` 대기 분기도 변경한다.
- 공통 로딩 스피너 컴포넌트와 나머지 사용처는 변경하지 않는다.

## 사용자 흐름 및 기대 동작

1. 인증된 사용자가 `/`, `/dashboard` 또는 대시보드 하위 경로에 진입한다.
2. 라우트 모듈을 lazy-load하는 동안 앱 진입 스피너를 표시하지 않는다.
3. 메뉴 정보 및 모듈 정보를 가져오는 동안 대시보드의 기존 배경 셸을 표시하되, 중앙 스피너와 사이드바/본문은 표시하지 않는다.
4. 메뉴 데이터가 준비되면 기존 사이드바와 현재 라우트의 본문을 표시한다.
5. 메뉴 조회 재시도까지 실패하면 기존 실패 안내와 다시 불러오기 버튼을 표시한다.
6. 대시보드 초기 진입 외의 조회·저장 로딩 표시와 기존 공통 스피너 사용처는 그대로 유지한다.

## 상태 및 데이터 계약

- `menusLoading` 상태, 조회 API, 1회 재시도, 취소 처리, 라우트 검증 및 에러 상태는 변경하지 않는다.
- 로딩 중에 빈 메뉴나 임시 본문을 대신 표시하지 않는다.
- UI에서 로딩 indicator를 제거해도 데이터 요청이나 사용자 권한 판정이 조기에 완료된 것으로 취급하지 않는다.

## 검증 기준

1. 기존 지연 메뉴 응답 테스트에서 route module 및 메뉴 응답 대기 중 `progressbar`가 없어야 한다.
2. 메뉴 응답 전 `종합현황` 제목이 없어야 한다.
3. 지연 응답을 resolve한 후 기존 `종합현황` 대시보드 제목이 표시되어야 한다.
4. `npm run test -- tests/app-router-not-found.test.tsx`와 `npm run build`가 통과해야 한다.
5. 375px, 768px, 1280px에서 초기 메뉴 응답 대기 화면에 스피너 및 대시보드 콘텐츠가 없고, 가로 넘침이 없어야 한다.
6. 각 뷰포트 확인 스크린샷 및 실행 결과를 날짜별 결과 문서에 기록한다.
