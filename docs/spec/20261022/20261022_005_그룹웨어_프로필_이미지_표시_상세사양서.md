# 그룹웨어 프로필 이미지 표시 상세사양서

## 1. 목표

문서·공지 흐름에서 이미 사용자 프로필/아바타를 보여주는 위치는 저장된 프로필 이미지가 있을 때 사진을 표시한다. 이미지가 없거나 로드되지 않으면 해당 위치의 현재 이름/이니셜 fallback을 그대로 표시한다.

## 2. 범위 및 제외

### 포함

- 문서 상세 기안자, 결재/합의/참조 참여자 및 댓글 작성자
- 공지 피드 작성자와 댓글 작성자
- 문서·공지의 기존 프로필/사용자 선택 표시 중 이미지 URL을 받는 위치
- 공통 프로필 아바타 컴포넌트, 타입/응답 어댑터, 기존 읽기 응답의 nullable 이미지 데이터

### 제외

- 현재 프로필 아바타가 없는 일반 텍스트에 새 아바타를 추가
- 전자결재 상태 도장 및 시스템 이벤트 표현 변경
- 프로필 수정/업로드, 신규 이미지 저장 API, 새 DB 테이블/컬럼 또는 migration
- 문서/공지 이외 도메인의 표시 변경
- 댓글, 문서, 공지의 기존 권한·정렬·조회수·저장 동작 변경

## 3. 사용자 표시 규칙

| 위치 | 이미지 값 | 이미지 누락/로드 실패 fallback |
|---|---|---|
| 공지 작성자 피드 카드 | 공지 작성자의 프로필 이미지 | 현재 `FeedCard`에 전달되는 작성자 이니셜 텍스트 |
| 공지 댓글 | 댓글 작성자의 프로필 이미지 | 현재 댓글 아바타의 작성자 이름 앞 2자 |
| 문서 기안자 | 기안자 프로필 이미지 | 현재 아바타의 기안자 이름 첫 글자 |
| 문서 결재·합의·참조 참여자 | 기존 `participantProfileImage` | 현재 참여자 이름 첫 글자 |
| 문서 댓글 | 댓글 작성자의 프로필 이미지 | 기존 댓글 아바타 fallback |
| 기존 문서 사용자 선택 | 기존 사용자 옵션 `avatarUrl` | 현재 선택기 fallback |

공통 `ProfileAvatar`는 이름과 nullable 이미지 URL을 받고 MUI `Avatar`의 `src` 및 `alt`에 연결한다. 호출자는 기존 fallback 텍스트와 크기/스타일을 넘긴다. 빈 이미지 URL은 `undefined`로 처리하며, 이미지 로드 실패 시 같은 fallback이 나타나야 한다. 사용자명이 그대로 표시되는 텍스트, 메뉴/댓글 동작과 접근성 이름은 바꾸지 않는다.

## 4. API 및 모델 계약

기존 응답 envelope와 조회 권한을 유지하면서 아래 optional/nullable 읽기 필드를 제공한다.

- 공지 모델: `writerProfileImage`를 목록 및 상세 응답에 추가한다.
- 공통 댓글 모델: `writerProfileImage`를 사용자 댓글 목록/페이지 응답에 추가한다. 시스템 이벤트의 작성자 표현은 기존대로 유지한다.
- 전자결재 상세 모델 및 조립 피드 항목: `drafterProfileImage`를 상세 응답에 추가하고, `DocumentApprovalWriteServiceImpl`이 상세에서 피드 항목으로 복사한다.
- 공통 댓글 모델: `writerProfileImage`를 사용자 댓글의 목록/페이지/댓글 ID 단건 재조회 응답에 추가한다. 생성·수정 직후 응답도 목록과 동일한 이미지를 제공한다.
- 결재선: 기존 `participantProfileImage` 필드를 재사용한다.

필드가 없거나 null이어도 기존 클라이언트와의 호환성을 유지한다. 신규 이미지 저장/조회 API를 만들지 않는다. 결과 조회는 해당 요청의 tenant 범위로 제한하며 관련 기존 글/댓글/결재선 행을 제거하지 않도록 LEFT JOIN한다.

### 확인된 데이터 계약

- 읽기 전용 DB MCP의 `list_tables`에서 `tb_user`, `tb_login_account`, `tb_board_post`, `tb_common_comment`, `tb_electronic_approval_main`, `tb_electronic_approval_line_info`를 확인했다.
- `describe_table`에서 `tb_login_account`에 nullable `profile_image text`, `login_code`, `login_id`, `tenant_id`가 있고 `tb_user`에 `user_id`, `login_id`, `tenant_id`가 있음을 확인했다. 글/댓글/기안자 ID 컬럼은 문자열이며 각 테이블에 `tenant_id`가 있다.
- [NoticeBoardApiController.java](../../../backend/src/main/java/egovframework/let/groupware/community/notice/controller/NoticeBoardApiController.java)는 로그인 사용자의 `getId()`를 글 생성 actor ID 및 상세 조회 login code로 전달한다. [CommonCommentApiController.java](../../../backend/src/main/java/egovframework/com/common/controller/CommonCommentApiController.java)는 댓글 `writerId`로 동일 값을 전달한다. [DocumentApprovalAccessServiceImpl.java](../../../backend/src/main/java/egovframework/let/groupware/approval/common/service/impl/DocumentApprovalAccessServiceImpl.java)는 기안자 ID로 `getId()`를 전달하며 로그인 ID lookup은 `tb_login_account.login_code`를 사용한다.
- 따라서 공지 `writer_id`, 공통 댓글 `writer_id`, 전자결재 `drafter_id` 이미지는 실제 `tenant_id`와 `login_code`가 일치하는 `tb_login_account`에서 LEFT JOIN으로 읽는다. 결재선 참여자 이미지의 기존 `tb_user` → `tb_login_account` tenant 범위 LEFT JOIN은 유지한다.
- 기존 Mapper SQL에서 DB 행이나 개인정보를 조회하지 않았으며 스키마 컬럼 메타데이터만 확인했다. DB 변경은 필요하지 않다.

## 5. 화면 데이터 흐름

1. 기존 읽기 API에서 작성자/댓글 작성자/기안자와 선택적 이미지 필드를 반환한다. 공지 작성 결과는 기존 상세 재조회에서, 댓글 생성/수정 결과는 기존 ID 재조회에서 이 필드를 반환한다.
2. 프론트 API 타입과 기존 notice/document adapter가 이미지를 해당 view model로 전달한다.
3. 작성자/댓글 카드와 상세 화면의 사람 아바타가 `ProfileAvatar`를 사용한다.
4. 결재/합의/참조 참여자의 기존 이미지 필드도 같은 컴포넌트에 연결한다.
5. 기존 fallback child를 그대로 사용하므로 데이터가 비어 있거나 이미지가 실패해도 사용자 이름 표시가 보존된다.

## 6. 테스트 사양

### 공통 컴포넌트

- 이미지 URL이 있으면 Avatar 이미지 `src`에 해당 값이 전달된다.
- null/빈 이미지 URL이면 caller fallback 텍스트가 보인다.
- 이미지 `error` 이후 이미지는 표시되지 않고 같은 caller fallback이 보인다.
- `alt`, 지정 크기, 스타일 props가 지정대로 전달된다.

### 공지/댓글

- 공지 목록/상세 응답의 `writerProfileImage`가 피드 작성자 아바타에 연결된다.
- 댓글 응답의 `writerProfileImage`가 댓글 모델과 avatar renderer에 전달된다.
- 작성자/댓글 이미지가 없을 때 기존 이니셜 fallback이 유지된다.
- 시스템 이벤트 및 삭제 댓글에 사용자 프로필 이미지가 부적절하게 적용되지 않는다.

### 문서

- 상세 기안자의 nullable 프로필 이미지가 작성자 avatar에 전달된다.
- 조립된 전자결재 피드 항목도 상세 응답의 `drafterProfileImage`를 받는다.
- 기존 결재선 이미지와 새 기안자·댓글 이미지 모두 적용된다.
- 이미지가 없으면 기안자 및 참여자별 현재 이름 fallback이 유지된다.
- 승인 상태 도장, 승인 상태 텍스트, 문서 작성/결재/댓글 상호작용은 변경되지 않는다.

### 백엔드

- 공지 목록/상세, 사용자 댓글 목록/페이지, 전자결재 상세/피드 결과에서 nullable 이미지 필드가 매핑된다.
- 관련 사용자 및 계정의 join 조건은 MCP에서 확인한 실제 키와 tenant 조건을 사용한다.
- LEFT JOIN으로 사용자/계정/이미지가 없을 때 기존 글·댓글·결재선 행이 유지된다.
- 시스템 이벤트의 현재 반환 필드 및 상세 API 권한/응답 구조가 유지된다.
