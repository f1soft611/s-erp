# 그룹웨어 스키마 및 공통코드 스크립트 상세사양서

## 1. 기준 및 실행 범위

- 작업지시서: [20261022_009_그룹웨어_스키마_스크립트_작업지시서.md](../../directions/20261022/20261022_009_그룹웨어_스키마_스크립트_작업지시서.md)
- 계획서: [20261022_009_그룹웨어_스키마_스크립트_계획서.md](../../plan/20261022/20261022_009_그룹웨어_스키마_스크립트_계획서.md)
- 승인 설계: [2026-10-22-groupware-schema-and-codes-design.md](../../superpowers/specs/2026-10-22-groupware-schema-and-codes-design.md)
- DB 근거: `s-erp-postgresql-readonly`의 `public` 테이블 목록, 대상 테이블 컬럼, 제약/인덱스 메타데이터 및 공통코드 카탈로그 조회

목적은 공유 기반 스키마 이후에 실행하는 신규 그룹웨어 기준 DDL 및 초기 공통코드 시드 제공이다. 연결된 DB에서 쓰기 작업을 수행하거나 테이블을 직접 생성하지 않는다. 기존 운영 DB의 현재 테이블과 이력 변경을 합친 기준 스키마이므로, 이미 그룹웨어 테이블이 존재하는 환경에서는 실행하지 않는다.

## 2. 공유 기반 선행 테이블

다음 테이블은 본 DDL에서 만들거나 수정하지 않으며, 새 환경에 이미 생성되어 있어야 한다.

- `tb_tenant`, `tb_module`, `tb_menu`
- `tb_login_account`, `tb_user`
- `tb_common_code_group`, `tb_common_code_item`
- `tb_common_file`, `tb_common_comment`, `tb_common_comment_like`

전자결재 타임라인 연동을 위해 `tb_common_comment`에는 현재 스키마의 `comment_type`, `event_type`, 테넌트/댓글 복합키와 이벤트 검사 제약이 필요하다. 이 공통 테이블의 생성 또는 변경은 별도 스키마 작업 범위다.

## 3. 그룹웨어 테이블 기준

모든 PK/FK/UNIQUE/CHECK 및 인덱스 정의는 읽기 전용 DB MCP의 현재 `public` 메타데이터와 날짜별 이력의 최종 변경을 반영한다. 시간 컬럼은 `timestamp without time zone`이며 기본값이 확인된 경우 `CURRENT_TIMESTAMP`를 사용한다.

| 테이블 | 컬럼 및 데이터 책임 | 키/제약 및 주요 인덱스 |
| --- | --- | --- |
| `tb_board_type` | `board_type_code`, `board_name`, `menu_id`, `board_kind`, 읽기/쓰기 권한 레벨, 첨부/사용 여부, 정렬, 생성/수정 시각 | PK `board_type_code`; `menu_id` → `tb_menu`; `board_kind`는 `notice`, `board`, `archive`; 활성/권한 필드 NOT NULL |
| `tb_board_post` | `post_id`, 게시판 유형, 제목/본문, 작성자, 조회/댓글 수, 고정/삭제, tenant, category, 본문 JSON/HTML/text, 수정자, 로그인 팝업 여부/종료일, 생성/수정 시각 | PK `post_id`; `board_type_code` → `tb_board_type`; `tenant_id` → `tb_tenant`; 팝업 CHECK; tenant/type 최신순 인덱스와 활성 공지 팝업 부분 인덱스 |
| `tb_board_post_view_history` | `view_history_id`, `tenant_id`, `post_id`, `login_id`, `viewed_at` | PK `view_history_id`; tenant/post/login FK; UNIQUE `(tenant_id, post_id, login_id)`; 게시글 조회 인덱스 |
| `tb_notice_popup_dismissal` | `tenant_id`, `post_id`, `login_id`, `dismissed_on DATE NOT NULL` | 복합 PK `(tenant_id, post_id, login_id)`; tenant FK; 게시글 및 로그인 계정 FK, 각 삭제 시 기존 동작대로 cascade |
| `tb_drafting_work_category_group` | 그룹 ID, tenant, 분류 코드/명, 표시 순서, 사용/삭제 상태, 생성/수정자 및 시각 | PK 그룹 ID; tenant 및 작성/수정 로그인 계정 FK; UNIQUE `(tenant_id, cata_code)` |
| `tb_drafting_work_category` | 분류 ID, tenant/그룹/공통코드 참조, 분류 타입/명/순서, 템플릿 JSON/HTML, 검토자/결재자, HACCP/기간/담당 코드, 사용/삭제 상태, 감사 컬럼 | PK 분류 ID; tenant, 분류 그룹, 공통코드 항목, 기간 공통코드 항목, 검토/결재/감사 로그인 계정 FK; 현행 조회용 인덱스 |
| `tb_drafting_work_category_authority` | 권한 ID, tenant, 분류 ID, 분류 타입, 사번, 사용/삭제 상태, 감사 컬럼 | PK 권한 ID; tenant 및 분류/감사 계정 FK; UNIQUE `(tenant_id, drafting_work_category_id, employee_no)` |
| `tb_electronic_approval_main` | 결재 ID, tenant, 기안 업무분류 ID, 문서 유형/상태, 제목, 본문 JSONB/HTML/text, 기안자/부서, 문서번호 코드, 삭제/조회 수, 제출/생성/수정 정보 | PK 결재 ID; UNIQUE `(tenant_id, electronic_approval_id)`; tenant 및 기안분류 FK; 문서유형/상태/문서번호 일치, 삭제 여부, 조회 수 CHECK; tenant/status 및 tenant/drafter 인덱스 |
| `tb_electronic_approval_line_info` | 결재선 ID, tenant/결재 ID, 단계/참여자 순서, 참여 유형/사용자, 처리 상태/시각/설명, 대기 시각 | PK 결재선 ID; tenant-결재 복합 FK; 유일 participant 및 위치; 단계/순서 양수; 참여 유형 및 상태/시각 조합 CHECK; 결재선 순서 및 pending 사용자 인덱스 |

| `tb_electronic_approval_line_template_info` | 템플릿 상세 ID, tenant/템플릿 ID, 단계/참여자 순서, 유형, 참여자 사용자 ID | PK 상세 ID; tenant-템플릿 복합 FK; 참여자 및 순서 UNIQUE; 양수 순서와 승인/합의/참조 CHECK; 템플릿 단계 순서 인덱스 |

| `tb_electronic_approval_view_history` | 조회 이력 ID, tenant/결재 ID, login ID, 조회 시각 | PK 조회 이력 ID; tenant/문서 복합 FK와 tenant/login FK; UNIQUE `(tenant_id, electronic_approval_id, login_id)`; 문서 인덱스 |

### 현행 전자결재 값 제약

- 문서 유형: `DRAFTING`, `BUSINESS_CONTACT`, `EXPENSE_RESOLUTION`, `ATTENDANCE_APPLICATION`
- 문서번호 코드 매핑: 각각 `001`, `008`, `004`, `031`
- 문서 상태: `DRAFT`, `PENDING`, `IN_PROGRESS`, `REVISION_REQUESTED`, `COMPLETED`, `REJECTED`
- 결재선 참여 유형: `APPROVAL`, `AGREEMENT`, `REFERENCE`
- 결재 처리 상태 및 timestamp 조합은 MCP에서 확인한 `chk_electronic_approval_line_action`을 유지한다.
- 댓글 시스템 이벤트는 선행 공통 댓글 스키마의 CHECK로 관리하고 공통코드 그룹으로 중복 정의하지 않는다.

## 4. 공통코드 시드

`tb_tenant.use_at = 'Y'`인 각 테넌트를 대상으로 한다. 그룹은 `(tenant_id, group_code)`, 상세 항목은 `(group_id, item_code)` 충돌 시 `DO NOTHING`으로 처리한다. 그룹 코드 설명 및 상세 자유서술 설명은 tenant 데이터를 복사하지 않고 빈 문자열로 저장한다.

| 그룹 코드 | 그룹명 | 항목 코드와 이름 (정렬 순서) |
| --- | --- | --- |
| `NOTICE_GUBUN` | 공지사항 구분 | `ALL` 전체(1), `IMPORTANT` 중요 공지(2), `OPERATION` 운영(3), `SECURITY` 보안(4), `MUST_READ` 필독(5) |
| `WF_ARCHIVE_CATEGORY` | 자료실 분류 | `001` 업무양식(0), `002` 메뉴얼(0), `003` 교육자료(0), `004` 테스트자료(0) |
| `WF_DOC_CATEGORY` | 문서구분(그룹웨어) | `001` 기안(0), `004` 지출(0), `008` 업무(0), `031` 근태(0) |
| `WF_FORM_CATEGORY` | 기안양식 분류 | `001` 기안서(1), `008` 업무연락(2), `004` 지출결의(3), `031` 근태신청(4), `201` HACCP(선행)(5), `202` HACCP(HA)(6) |
| `WF_FORM_CYCLE` | 기안양식 등록주기 | `DAY` 일(10), `WEEK` 주(20), `MONTH` 월(30), `EVENT` 발생시(40) |

총 5개 그룹과 23개 상세 항목을 시드한다. 기존 동일 코드의 명칭/설명을 덮어쓰지 않는다.

## 5. 파일 및 롤백 사양

- 생성 DDL: `20261022_009_create_groupware_schema.sql`
- 공통코드 시드: `20261022_009_seed_groupware_common_codes.sql`
- 테이블 롤백: `20261022_009_rollback_groupware_schema.sql`
- 변경 이력: `20261022_009_change_groupware_schema.md`
- 위 4개 파일은 `backend/DATABASE/20261022/`와 `docs/database/20261022/`에 바이트 단위로 동일하게 둔다.
- DDL은 명시적 `public.`을 사용하고 트랜잭션으로 묶는다. 대상 테이블은 `IF NOT EXISTS` 없이 생성하여 부정합 상태를 숨기지 않는다.
- 테이블 롤백은 FK 의존성 역순으로 13개 그룹웨어 테이블만 제거한다. 공유 기반 테이블/데이터는 삭제하지 않는다.
- 시드 데이터는 기존 그룹/상세코드를 제거하는 자동 rollback을 제공하지 않는다. 충돌 시 기존 코드를 유지하며 데이터 삭제는 수동 검증 없이 수행하지 않는다.

## 6. 검증 및 완료 기준

- 13개 테이블과 외부 FK 선행조건이 명확하며, 대상 테이블의 최신 컬럼/제약/인덱스가 MCP 및 날짜별 DDL과 일치한다.
- 시드에 5개 그룹 및 23개 항목, 활성 tenant 조건, 두 유니크 키의 conflict 처리가 있다.
- rollback은 그룹웨어 전용 테이블 13개만 정확히 역순 제거한다.
- backend/docs SQL 및 변경 이력 사본 SHA-256이 동일하다.
- `git diff --check`가 통과한다.
- DB는 읽기 전용 MCP로만 확인하고 어떠한 DDL/DML도 적용하지 않는다.
