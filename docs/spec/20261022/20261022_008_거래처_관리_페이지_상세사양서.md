## 4. 검색 조건

### 기본 검색

- 기본 입력은 한 개만 제공한다.
- `keyword`: trim한 부분 검색 값으로 다음 필드를 OR 조건 검색한다.
  - `customer_code`
  - `customer_name`
  - `cust_name_abbr`
- Enter 키 및 조회 액션으로 조건을 적용한다.

### 상세 검색

`PageSearchArea`의 상세 패널을 사용하며 F1-Grid 컬럼 `search` 메타데이터에서 생성한다. 상세 검색 적용 시 기본 검색과 함께 같은 API 요청으로 전송한다.

| Query parameter | 대상 컬럼 | 일치 기준 |
| --- | --- | --- |
| `presidentName` | `president_name` | 부분 일치 |
| `businessNo` | `business_no` | 부분 일치 |
| `juridNo` | `jurid_no` | 부분 일치 |
| `businessStatus1` | `business_status_1` | 부분 일치 |
| `businessItem1` | `business_item_1` | 부분 일치 |
| `useAt` | `use_at` | `Y`/`N` 정확 일치 |

초기 조회는 사용/미사용을 모두 포함한다. 상세 검색 입력 변경만으로 API를 호출하지 않고 검색 적용 액션에서 확정한다. 검색 결과는 코드 오름차순, 동률이면 `customer_id` 오름차순이다. 검색 API는 현재 필터에 해당하는 전체 목록을 반환하며 별도 페이지네이션은 추가하지 않는다.

사업자번호(`businessNo`)와 법인등록번호(`juridNo`)의 상세검색 입력은 ASCII 숫자와 `-`만 허용한다. 입력 또는 붙여넣기에서 다른 문자는 즉시 제거한다. 상세검색에서는 입력 최대 자리수(사업자 10, 법인 13)를 적용하지만, 부분 검색을 위해 자리수 미완성 값은 그대로 허용한다.

## 5. F1-Grid 목록과 폼

### 목록 컬럼

1. `customerId` — No (`rownumber`, 검색 제외)
2. `customerCode` — 거래처코드
3. `customerName` — 거래처명
4. `custNameAbbr` — 약칭
5. `presidentName` — 대표자
6. `businessNo` — 사업자번호
7. `businessStatus1` — 업태
8. `businessItem1` — 종목
9. `telephoneNo` — 전화번호
10. `address` — 주소
11. `useAt` — 사용여부

`customerCode`, `customerName`, `custNameAbbr`는 기본 검색 필드로 연결하고, 상세검색 가능한 컬럼에는 위 표의 검색 메타데이터를 지정한다. 헤더 정렬/필터, 행 선택, 설정 저장, 허용된 경우 Excel 내보내기는 기존 F1-Grid 동작을 유지한다.

### 행 폼

폼의 업무 필드는 거래처코드, 거래처명, 약칭, 대표자, 사업자번호, 법인등록번호, 업태, 종목, 우편번호, 주소, 전화번호, 팩스번호, 메모, 사용여부다.

- 신규의 거래처코드는 비워둘 수 있다. 비어 있으면 서버가 코드를 생성한다.
- 사용자가 거래처코드를 입력하면 그대로 사용하고 테넌트 내 중복은 거부한다.
- 수정 시 거래처코드는 필수이며 비우면 저장을 거부한다.
- 거래처명은 공백 제거 후 필수다.
- `useAt`은 `Y`/`N`만 허용하고 신규 기본값은 `Y`다.
- `customerId`, `tenantId`, `createdBy`, `createdAt`, `updatedBy`, `updatedAt`은 편집하지 않는다.
- `businessNo`, `juridNo`, `postCode`, `telephoneNo`, `facsimileNo`는 공통 F1-Grid `inputFormat` 옵션을 사용한다.
  - `businessNo`: `000-00-00000`, 입력 최대 10자리, 저장 허용 10자리
  - `juridNo`: `000000-0000000`, 입력 최대 13자리, 저장 허용 13자리
  - `postCode`: 숫자만, 입력 최대 5자리, 저장 허용 5자리
  - `telephoneNo`/`facsimileNo`: 서울 02 번호 9자리 `02-xxx-xxxx`/10자리 `02-xxxx-xxxx`, 그 외 10자리 `0xx-xxx-xxxx`/11자리 `0xx-xxxx-xxxx`, 입력 최대 11자리(`02`는 10자리 상한)
- 다섯 필드의 자동 포맷과 최대 자리수 제한은 행 폼, 인라인 편집, F1-Grid TSV 붙여넣기에 동일 적용한다. 사업자번호·법인등록번호 상세검색에도 같은 설정을 전달하며 부분 검색 값은 허용한다. 입력된 앞자리 0과 숫자는 문자열로 보존한다.
- 저장 검증은 `grid.validate()` 경로에서 수행하며, 비어 있지 않은 값만 자리수 검증한다. 이때 사용자가 수정하지 않은 기존 번호/연락처 값도 저장 대상 행이면 동일하게 검증하며, 규칙을 벗어나면 저장을 차단한다. API와 DB 형식은 변경하지 않는다.
- 등록/수정 저장 완료 후 현재 검색 조건으로 목록을 다시 조회한다.
- 저장 중 중복 요청을 방지하고, 검증/API 오류는 메시지 영역에 표시한다.

## 6. API 계약

공통 응답은 기존 `ResultVoHelper`의 결과 구조를 따른다.

### OpenAPI 도메인 모델

- `CustomerInfoVO`, `CustomerInfoSaveRequestVO`, `CustomerInfoSearchCondition`, `CustomerInfoChangeVO`, `CustomerInfoBatchChangeSetVO`, `CustomerInfoBatchSaveRequestVO`, `CustomerInfoBatchSaveResultVO`의 클래스와 모든 업무 필드에 `@Schema(description = ...)`를 제공한다.
- `CustomerInfoChangeVO`는 저장 요청 모델의 필드 설명을 상속한다. 신규 로컬 ID와 수정 서버 ID의 차이를 설명한다.
- 거래처명 필수, 신규 거래처코드 자동채번/수정 코드 필수, `useAt` 허용값 `Y`/`N`, 삭제 행 거부를 실제 서비스 계약과 동일하게 기술한다. 예시에는 실제 업무·개인 데이터를 사용하지 않는다.
- DB 스키마나 JSON 필드 이름/타입은 바꾸지 않는다.

### 공통코드 백엔드 패턴 적용

- 검색 조건은 tenant가 없는 `CustomerInfoSearchCondition`으로 받고, 서비스가 인증 tenant와 정규화한 검색값을 Map으로 만들어 DAO에 전달한다.
- 목록은 무조건/조건 조회 overload를 제공한다. 조회 Controller의 성공 반환형은 `ResultVO`다.
- `findByIdOrThrow`는 tenant-scoped 조회 실패 시 `ResponseStatusException(HttpStatus.NOT_FOUND)`를 발생시킨다. Controller는 공통코드처럼 입력 검증 오류를 HTTP 400으로 변환한다.
- 공통코드와 달리 채번은 기존 승인된 eGov IDS를 유지하고, 거래처의 감사 사용자 ID도 유지한다. 배치와 개별 API는 같은 등록/수정 서비스를 재사용한다.

### POST `/api/v1/co/master/customers/save-batch`

- 요청: `{ "customers": { "insertedRows": [], "updatedRows": [], "deletedRows": [] } }`.
- 변경 행에는 기존 저장 업무 필드와 `customerId`가 있다. 신규의 로컬 ID는 서버 identity로 사용하지 않으며, 수정 ID는 양의 정수 문자열로 검증한다.
- 신규/수정은 한 트랜잭션으로 처리한다. 검증·DB 오류 등 어느 행이든 실패하면 전체 변경을 롤백한다. eGov IDS에서 이미 소비한 번호는 재사용하지 않아 번호 공백은 허용한다.
- `deletedRows`가 비어 있지 않으면 HTTP 400으로 거부한다. 삭제 대신 `useAt` 수정으로 상태를 바꾼다.
- 성공: HTTP 200, `result.item.customers`에 저장된 거래처 목록.
- 프론트 저장 버튼은 단일 배치 요청만 사용한다. 저장 실패 시 기존 변경 상태를 유지하고 성공 후 현재 조건으로 재조회한다. 저장이 완료된 뒤 재조회만 실패한 경우 변경 상태를 해제해 중복 등록을 막고 조회 재시도 안내를 표시한다.

### GET `/api/v1/co/master/customers`

선택 Query: `keyword`, `presidentName`, `businessNo`, `juridNo`, `businessStatus1`, `businessItem1`, `useAt`.

성공 응답: `result.resultList`에 현재 tenant의 `CustomerInfoVO` 목록을 반환한다. Tenant ID는 `LoginVO`에서 가져온다.

### POST `/api/v1/co/master/customers`

요청 body의 business 필드: `customerCode`, `customerName`, `custNameAbbr`, `presidentName`, `businessNo`, `juridNo`, `businessStatus1`, `businessItem1`, `postCode`, `address`, `telephoneNo`, `facsimileNo`, `custMemo`, `useAt`.

서버는 tenant와 audit 사용자를 principal에서 설정하고, `customer_id`는 기존 DB default를 사용한다. 빈 `customerCode`에만 `customerCodeIdGnrService`를 적용한다. 성공 상태는 201이며 `result.item`에 생성 행을 반환한다.

### PUT `/api/v1/co/master/customers/{customerId}`

POST와 같은 업무 body를 받는다. tenant-scoped 행만 수정하고 identity/tenant/created 감사 필드는 보존한다. 성공 상태는 200이며 `result.item`에 수정 행을 반환한다.

### 오류 계약

- 입력 검증, 같은 tenant의 코드 중복, 채번 실패/소진: HTTP 400 및 사용자에게 노출 가능한 메시지
- 비관리자의 생성/수정: HTTP 403
- 현재 tenant에 속하지 않거나 존재하지 않는 `customerId`: HTTP 404
- 읽기/저장 네트워크 오류: 공통 API 오류를 보존하고 페이지 오류 영역에 표시

## 7. 거래처 코드 채번과 마이그레이션

- 코드 생성 서비스 bean: `customerCodeIdGnrService`; implementation `EgovTableIdGnrServiceImpl`; `table = "IDS"`, `tableName = "tb_customer_info"`, prefix `""`, `cipers = 6`, fill char `'0'`, block size `1`.
- `customer_id`는 현재 `tb_customer_info_customer_id_seq`가 계속 생성한다. 거래처 코드에는 별도 PostgreSQL sequence 또는 테이블을 만들지 않는다.
- eGov generator의 기본 무기록 초기 요청은 `0`을 반환하므로 `20261022_005` migration에서 `ids`의 `tb_customer_info` 행을 미리 초기화한다.
- 초기 `next_id`는 전체 테이블의 1~6자리 숫자 `customer_code` 중 최댓값 + 1이며 숫자 코드가 없으면 `1`이다. 기존 generator row가 있으면 현재 `next_id`와 비교해 더 큰 값만 보존한다.
- eGov generator의 결과는 6자리 zero-padding 문자열이다. 서비스는 1~999999 범위 밖의 결과를 명시적 채번 소진 오류로 거부한다. 이미 해당 tenant의 코드로 사용 중이면 다음 값을 최대 10회 확인한다.
- 동일 tenant의 수동 코드/수정 코드 중복은 서비스에서 사전 확인하고 `(tenant_id, customer_code)` DB unique constraint로 최종 방어한다.
- 변경 번호 `20261022_005`로 counter initialization SQL, 변경 이력 Markdown, rollback SQL을 `backend/DATABASE/20261022`와 `docs/database/20261022`에 동일하게 둔다.
- rollback은 앱 버전만 되돌리고 `ids` 카운터를 낮추거나 삭제하지 않는다. 발급된 거래처 코드 재사용을 막기 위해 DB rollback SQL은 의도적으로 counter를 보존한다. 적용 여부를 MCP로 확인하거나 MCP에 스크립트를 실행하지 않는다.
- `docs/database/db-schema.md`에 `tb_customer_info` 및 기존 `ids` 테이블 메타데이터를 반영한다.

## 8. 오류/로딩/반응형 및 검증

- 최초 목록 로딩, 재조회, 저장 중 상태를 구분해 표시한다.
