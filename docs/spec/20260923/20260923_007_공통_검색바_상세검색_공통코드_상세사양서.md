# 20260923_007 공통 검색바 상세 검색 및 공통코드 적용 상세사양서

## 1. 화면 UI 사양

### 1.1 기본 상태

- `PageSearchArea`는 기존 페이지 콘텐츠 흐름 안에서 한 줄 높이로 렌더링한다.
- 기본 검색 필드는 페이지가 지정한 기본 필드 하나를 표시한다.
- 공통코드 관리에서는 `keyword` 입력을 기본 필드로 사용하며 그룹 코드·그룹명·그룹 설명을 통합 검색한다.
- 우측 끝 토글 버튼은 `aria-expanded`로 상세 오버레이 상태를 노출한다.
- 기존 검색 영역의 배경, 테두리, 검색 아이콘 스타일은 유지하되 상세 오버레이와 시각적으로 구분한다.

### 1.2 상세 검색 오버레이

- 검색 영역을 확장하지 않고 검색바를 기준으로 콘텐츠 위에 absolute 또는 동등한 레이어로 표시한다.
- 오버레이는 검색바 아래 또는 페이지 콘텐츠 상단을 덮으며, 페이지 전체 가로 스크롤을 만들지 않는다.
- 필드는 반응형 grid/flex로 배치한다.
- 우측 하단 action 영역에 `검색 닫기`와 `검색` 버튼을 배치한다.
- 검색 닫기: 현재 입력값을 유지한 채 오버레이만 닫는다.
- 검색: 입력값을 정규화하고 페이지의 조회 콜백을 호출한 뒤 오버레이를 닫는다.
- Escape 및 외부 클릭 동작은 기존 공통 UI 규칙과 충돌하지 않는 범위에서 제공한다.
- 로딩 중에는 중복 검색 실행을 막고, 오류는 기존 `PageMessageArea` 등 페이지 오류 표시 흐름으로 전달한다.

### 1.3 반응형 기준

- 375px: 필드는 한 열, action 버튼은 겹치지 않는 세로 또는 동일 폭 배치
- 768px: 필드는 2열을 기본으로 하되 긴 입력은 전체 폭 사용 가능
- 1280px: 필드는 필요한 만큼 여러 열로 배치하며 오버레이가 페이지 밖으로 넘치지 않음
- 모든 크기에서 텍스트, 입력, 토글, 검색 닫기 버튼이 잘리지 않음

## 2. 검색 필드 모델

```ts
type PageSearchFilterValue = string | number | boolean | null;

type PageSearchFilter = {
  field: string;
  type:
    | 'text'
    | 'number'
    | 'decimal'
    | 'currency'
    | 'date'
    | 'select'
    | 'checkbox';
  label: string;
  searchSpan?: 1 | 2 | 3 | 4 | 5;
  group?: string;
  value?: PageSearchFilterValue;
  from?: string;
  to?: string;
  options?: Array<{ value: string | number | boolean; label: string }>;
};
```

- F1 컬럼의 `field`, `headerName`, `type`, `options`, `min`, `max`를 검색 필드에 반영한다.
- F1 컬럼의 `search?.hidden`, `search?.label`, `search?.group`, `search?.order`, `search?.span`을 검색 필드에 반영한다.
- `search.hidden=true`는 검색 필드를 제외하고, `search.order`는 오름차순 표시 순서로 사용한다.
- `search.span`은 폼모달 전용 `form.span`과 독립적인 검색 전용 옵션이다.
- `search.span`은 `1 | 2 | 3 | 4 | 5`를 사용하며, 데스크톱 기준 1열, 2열, 3열, 4열, 5열 너비를 의미한다.
- 상세 검색 그리드는 데스크톱 최대 5열, 태블릿 2열, 모바일 1열로 배치한다.
- 화면 폭이 좁아지면 `search.span`은 반응형 규칙에 따라 줄어들 수 있지만 필드 내용이 잘리거나 겹치지 않아야 한다.
- 타입 미지정은 `text`로 간주한다.
- `number`, `decimal`, `currency`는 숫자 입력으로 생성한다.
- `date`는 하나의 필드가 아니라 `{ field, from, to }` 상태를 사용한다.
- 날짜 범위 검증:
  - from/to 모두 없으면 조건 미전송
  - from만 있으면 `field >= from`
  - to만 있으면 `field <= to`
  - 둘 다 있으면 `field BETWEEN from AND to`
  - from이 to보다 크면 검색 실행을 막고 필드 오류를 표시한다.
- `select`는 F1 컬럼의 `options`로 선택지를 구성한다.
- `checkbox`는 명시된 값 매핑을 사용하며 대표 화면의 `useAt` 같은 상태 필드에 적용한다.
- `rownumber`, `code`, 렌더 전용 컬럼은 페이지 어댑터가 검색 대상에서 제외한다.

## 3. 대표 화면 사양

### 3.1 공통코드 그룹 목록

검색 기준 컬럼:

| 필드        | 표시명    | 검색 타입 | 비고      |
| ----------- | --------- | --------- | --------- |
| `groupCode` | 그룹코드  | text      | 부분 일치 |
| `groupNm`   | 그룹명    | text      | 부분 일치 |
| `groupDc`   | 그룹 설명 | text      | 부분 일치 |

- 현재 그룹 컬럼에서 타입이 생략된 필드는 text로 자동 변환한다.
- `id`, `parentGroupId`, `sortOrder`, `useAt`는 이번 대표 상세 검색에서는 제외한다.
- 기본 검색은 `keyword` 하나로 세 필드 중 하나라도 부분 일치하는 그룹을 조회한다.
- 상세 검색은 입력된 필드만 AND로 적용한다.
- 상세 코드 목록 검색은 이번 작업에서 제공하지 않는다.

### 3.2 상태 흐름

1. 페이지 진입 시 검색 상태는 빈 기본 keyword와 빈 상세 조건으로 초기화한다.
2. 기본 입력 변경은 조회를 즉시 실행하지 않고 로컬 상태에 반영한다.
3. 상세 검색 토글은 오버레이 표시 상태만 변경한다.
4. 검색 버튼 또는 기존 페이지 조회 동작이 실행되면 미저장 변경사항을 확인한다.
5. 확인이 필요 없으면 검색 조건으로 그룹 API를 호출한다.
6. 성공 시 그룹 목록을 교체하고 기존 선택/상세 목록 흐름을 유지한다.
7. 실패 시 기존 그룹 목록을 임의로 비우지 않고 오류 메시지를 표시한다.

## 4. API 계약

### Endpoint

`GET /api/v1/co/master/common-code/groups`

### Query parameter

| 이름        | 타입   | 필수   | 설명                                                |
| ----------- | ------ | ------ | --------------------------------------------------- |
| `keyword`   | string | 아니오 | `group_code`, `group_nm`, `group_dc` 통합 부분 검색 |
| `groupCode` | string | 아니오 | 그룹 코드 부분 검색                                 |
| `groupNm`   | string | 아니오 | 그룹명 부분 검색                                    |
| `groupDc`   | string | 아니오 | 그룹 설명 부분 검색                                 |

- 공백 문자열은 미입력으로 정규화한다.
- `keyword` 조건은 세 컬럼에 OR로 적용한다.
- 상세 조건 여러 개는 AND로 적용한다.
- 기본 검색과 상세 검색 값을 동시에 보내는 경우에도 서버는 명시된 조건을 모두 적용한다. 프론트는 일반적으로 한 모드의 조건만 전송한다.

### 성공 응답

- HTTP 200
- 기존 `ResultVO` envelope 및 `result.resultList` 구조 유지
- 결과 행 필드는 기존 `CommonCodeGroupVO` 계약을 유지한다.

### 오류 응답

- 인증 실패/권한 실패: 기존 보안 정책 및 상태 코드 유지
- 잘못된 날짜 범위 등 프론트 검증 대상은 요청 전에 차단한다.
- 서버 예외: 기존 공통 오류 응답 형식 유지

## 5. 백엔드 처리 사양

- Controller는 `@RequestParam(required = false)`로 네 개의 query parameter를 받는다.
- Service는 tenant ID와 검색 조건을 DAO에 전달한다.
- DAO는 기존 Long tenantId 전용 호출을 검색 조건 Map 호출로 확장하되, 기존 호출 의미를 보존한다.
- Mapper WHERE 절은 항상 `g.tenant_id = #{tenantId}`를 포함한다.
- `keyword`는 `LOWER(COALESCE(g.group_code, '')) LIKE LOWER(CONCAT('%', #{keyword}, '%'))` 형태의 OR 조건으로 처리한다.
- 각 상세 값은 값이 있을 때만 조건을 추가한다.
- 기존 정렬 `parent_group_id NULLS FIRST`, `sort_order`, `common_code_group_id`를 유지한다.
- SQL 문자열 비교는 MyBatis OGNL 조건에서 이중따옴표 규칙을 따른다.

## 6. 권한 및 데이터 보호

- 기존 인증된 사용자의 tenant ID만 조건에 사용한다.
- 클라이언트가 tenant ID를 query parameter로 전달하지 않는다.
- 검색 결과에 다른 tenant 그룹이 섞이지 않아야 한다.
- 검색은 조회 권한 정책을 우회하지 않는다.

## 7. 테스트 사양

### Frontend

- PageSearchArea 기본 한 줄 및 기본 필드 렌더링
- 토글로 상세 오버레이 열기/닫기
- text/number/select/checkbox/date 필드 생성
- date from/to 상태와 역전 범위 검증
- 검색 닫기 시 API 미호출
- 검색 실행 시 query parameter 변환
- 공통코드 검색 성공/실패 및 미저장 변경 경고

### Backend

- query parameter 없는 전체 조회
- `keyword`의 세 컬럼 OR 검색 파라미터 전달
- groupCode/groupNm/groupDc 단일 조건
- 복수 상세 조건 AND 처리
- 공백 조건 미적용
- tenant 조건 및 기존 정렬 유지
- 기존 응답 구조 회귀 방지

### Browser

- 375px, 768px, 1280px 상세 오버레이 캡처
- 실제 API 요청 query string 확인
- 검색 결과 갱신, 닫기, Escape/외부 클릭 확인

## 8. 제외 사항

- 다른 관리 페이지의 상세 검색 자동 적용
- 공통코드 상세 항목 검색
- DB schema migration
- 페이지네이션/정렬 계약 변경
- 사용자가 입력 중인 draft 검색값은 즉시 저장하지 않는다.
- 조회 버튼으로 조회가 성공한 경우에만 기본 검색어, 상세 검색값, 적용 필터를 `sessionStorage`에 저장한다.
- 페이지 재진입 시 마지막으로 성공한 적용 필터를 최초 조회 조건으로 사용한다.
- 상세 검색의 초기화는 현재 입력값만 비우며, 기존에 성공 저장된 조회 상태는 유지한다.
