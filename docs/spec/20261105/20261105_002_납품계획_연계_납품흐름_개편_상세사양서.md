# 납품계획 연계 납품흐름 개편 상세사양서

> 수량 상한 및 초과납품 동작은 [20261105_003 초과납품 정책](20261105_003_초과납품_정책_상세사양서.md)이 우선한다. BLOCK은 기존 차단을 유지하며 WARN은 명시적 확인 후 실제 납품량의 기준 초과를 허용한다.

## 기준 및 DB 근거

- [작업지시서](../../directions/20261105/20261105_002_납품계획_연계_납품흐름_개편_작업지시서.md), [계획서](../../plan/20261105/20261105_002_납품계획_연계_납품흐름_개편_계획서.md), [승인 설계](../../superpowers/specs/2026-11-05-sales-delivery-planning-design.md).
- 기본 읽기 전용 DB MCP의 `list_tables` 및 `describe_table` 결과: `tb_tenant`에는 현재 모드 설정 없음, 수주 헤더/상세는 `tb_sales_order_hd/dt`, 현재 납품계획 테이블 없음, 납품 테이블은 작업 20261104 DDL 기준 추가 예정이며 기본 DB 목록에서 확인되지 않음. 업무 행은 조회하지 않았다.

## 운영 흐름

| 테넌트 모드 | 수주 저장 | 계획 화면 | 수주납품 등록 |
|---|---|---|---|
| `MANUAL` | 수주만 저장 | 사용자가 납품계획 등록/수정/조회 | 계획 상세 잔량 기준 |
| `AUTO` | 수주+계획을 같은 트랜잭션에 생성 | 메뉴 숨김, API 직접 호출도 거부 | 자동 생성된 계획 상세 잔량 기준 |

- 직납품(`DIRECT`)은 두 모드에서 모두 계획 없이 가능하다.
- 신규 및 기존 테넌트 기본 모드는 `AUTO`로 하여 기존 수주→납품 UX를 보존한다.
- 자동 계획 일자는 상세 납기일, 헤더 납기일 순으로 상속한다. 둘 다 없으면 `plan_dt=NULL`로 미정 처리하며 임의 날짜를 만들지 않는다.
- MANUAL 신규 수주는 계획이 생성되기 전까지 수주납품이 불가하다.
- 수주별 계획 헤더는 하나이며 상세에서 같은 수주상세를 여러 예정일/수량 행으로 분할할 수 있다. 계획 헤더는 수주당 하나, 계획 상세는 복수행이다.

## DB 계약

### 테넌트 설정

- `tb_tenant.delivery_plan_mode VARCHAR(10) NOT NULL DEFAULT 'AUTO' CHECK IN ('AUTO','MANUAL')`.
- SQL은 기존 tenant 전체 행에 `AUTO`를 채운다.

### `tb_sales_delivery_plan_hd`

- `sales_delivery_plan_id BIGSERIAL PK`
- `tenant_id BIGINT NOT NULL`, `sales_order_id BIGINT NOT NULL`, `plan_no VARCHAR(30) NOT NULL`, use/audit 컬럼.
- UNIQUE `(tenant_id, plan_no)`, `(sales_order_id, tenant_id)`, `(sales_delivery_plan_id, tenant_id, sales_order_id)`.
- tenant FK 및 `(sales_order_id, tenant_id)` 복합 FK.

### `tb_sales_delivery_plan_dt`

- `sales_delivery_plan_detail_id BIGSERIAL PK`, `sales_delivery_plan_id`, `tenant_id`, `sales_order_id`, `sales_order_detail_id`, `material_id`, `line_no`, nullable `plan_dt`, `planned_qty NUMERIC(15,2)`, `delivered_qty NUMERIC(15,2) DEFAULT 0`.
- 상세도 생성/수정자 및 시각 감사 컬럼을 가진다.
- 같은 원 수주상세의 분할행을 허용한다. `(sales_delivery_plan_id, line_no)`만 유일하다.
- 수주상세·계획헤더·품목 테넌트/수주 참조 복합 FK, 계획수량 양수 및 `0 <= delivered_qty <= planned_qty` CHECK.
- 납품상세가 복합키 `(plan_detail_id, tenant_id, sales_order_id, sales_order_detail_id)`로 참조한다.

### 기존 납품 스키마

- `tb_sales_delivery_dt.sales_delivery_plan_detail_id` nullable 컬럼을 추가한다.
- `ORDER` 납품 상세는 수주/수주상세/계획상세 참조가 모두 필수이며 plan detail과 order/order detail 일치 복합 FK를 가진다.
- `DIRECT` 상세는 세 참조를 모두 NULL로 유지한다.
- 기존 `(sales_delivery_id, sales_order_detail_id)` unique는 제거하고 `(sales_delivery_id, sales_delivery_plan_detail_id)` unique로 변경한다. 한 수주상세에 계획 분할행이 둘 이상 있을 경우 같은 납품서에 둘을 각각 기록할 수 있다.
- 기존 수주 전체에 주문당 하나의 계획 헤더와 수주 상세당 계획 상세를 backfill한다. 기존 납품 상세도 매칭 상세에 연결하며 계획의 `delivered_qty`는 수주상세의 현행 `shipped_qty`로 초기화한다. 기존 레코드에서 주문/수주상세/수량 정합성이 보장되지 않으면 migration은 적용 전에 중단해야 한다.
- 새 테이블, 변경, rollback SQL과 이력 문서는 `docs/database/20261105`와 `backend/DATABASE/20261105`에 동일하게 둔다. `docs/database/db-schema.md`를 갱신한다. DB에는 적용하지 않는다.

## API 및 동시성

- tenant 모드는 기존 납품 API 응답의 `deliveryPlanMode` 필드로 노출하여 화면 및 메뉴 노출에 쓴다.
- `/api/v1/sales/delivery-plans`: POST/GET, `/{id}` GET/PUT, `/status`, `/source-orders`; 테넌트 및 메뉴 권한은 기존 authenticated tenant와 leaf menu permission 체계를 사용한다.
- 계획 등록 요청은 order ID, 여러 상세의 `salesOrderDetailId`, nullable `planDt`, `plannedQty`를 받는다. 서버가 거래처/품목/수량을 수주에서 조회하고 ID를 검증한다.
- AUTO 수주 생성은 헤더·상세·계획 헤더·상세를 단일 트랜잭션으로 저장한다. MANUAL 수주 생성은 계획을 만들지 않는다.
- 수주 수정은 헤더 잠금 후 기존 상세를 line number 기준 UPDATE/INSERT/DELETE 동기화한다. 계획/출하된 양보다 적은 주문수량, plan/delivery 참조 상세의 삭제 또는 품목 변경은 409. AUTO면 각 상세의 단일 자동 계획 잔량을 신규 주문수량에 맞춰 조정한다. MANUAL의 기존 계획수량은 유지한다.
- 수주 헤더 `FOR UPDATE`를 모든 수주·계획·납품 변경에서 가장 먼저 취득한다. 이후 plan header/detail을 잠근다. 계획 저장은 원 수주상세 전체 계획 합이 order qty 이하인지, delivered qty 이하로 계획을 줄이지 않는지 검증한다.
- ORDER 납품의 각 행은 plan detail ID를 사용한다. 계획 detail delivered qty + 요청 수량은 planned qty를 초과하지 않고, 수주 shipped qty도 order qty를 초과하지 않아야 한다. create/update/delete에서 계획 delivered qty와 수주 shipped qty를 같은 트랜잭션으로 조정한다.
- 수주 수정 시 ID 보존은 기존 line number 정체성에 따른다. 행 재정렬은 해당 line number identity를 바꾸므로 계획이 있는 수주에서는 불가하며 UI에서 순번을 안정적으로 유지한다.

## 화면 및 메뉴

- Sales 메뉴를 `수주관리(수주등록/수주현황)`, `납품계획(등록/현황)`, `납품관리(등록/현황)`로 구분한다.
- Plan menu leaf page keys: `delivery-plan-create`, `delivery-plan-status`. MANUAL에서만 보이고 AUTO에서는 메뉴트리/API 모드로 숨긴다. 서버에서 MANUAL 전용 CRUD를 시행한다.
- 계획등록은 수주 선택, 수주 헤더 읽기 전용, 상세별 계획일/계획수량 편집, 행 추가·삭제(분할), 저장 전 계획합·잔량 표시, 저장/조회/수정 동작을 제공한다. order item/customer는 수주에서만 온다.
- 계획현황은 계획번호/수주번호/거래처/계획상태, 예정일별 품목·계획·납품·잔량을 조회하고 상세 패널에서 등록 화면으로 연다.
- 납품등록의 `수주납품` 선택기를 `계획 선택`으로 변경한다. 선택한 계획행을 납품 상세에 로드하고 plan detail identity를 불변으로 보낸다. 동일 order detail의 계획 분할행은 서로 다른 상세로 표시한다. 잔량 초과 저장을 서버가 거부한다.
- AUTO에서 페이지를 직접 열거나 MANUAL 전용 API를 호출해도 backend는 권한/모드 검사를 수행한다. 메뉴 숨김은 UI 편의일 뿐 보안 경계가 아니다.
