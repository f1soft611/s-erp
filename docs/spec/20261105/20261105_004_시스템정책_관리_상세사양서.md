# 시스템 정책 관리 상세사양서

## 범위와 화면

- 환경설정 > 시스템관리 > 시스템 정책. 현재 테넌트에만 적용하고 테넌트 선택기는 없다. 기존 중앙→테넌트 DB 복제 운영을 변경하지 않는다.
- 정책 검색(이름/코드/설명), 업무 분류, 타입·설명·현재값 목록을 제공한다. 상단 PageHeader 조회/정책 추가 버튼, 항목별 수정·삭제와 변경이력을 제공한다.
- 정책 추가/수정 대화상자는 이름, 코드, 분류, 설명, 타입, 타입별 값과 제약을 입력한다. 생성 후 코드·타입은 고정한다.
- BOOLEAN 스위치, NUMBER 숫자(min/max/단위), SELECT 선택지(값/표시명 행 추가·삭제), TEXT 문자열, DATE 날짜, USER_LIST 테넌트 사용자 검색/다중선택.
- 정책 제공 상태와 BOOLEAN 실제값을 혼동하지 않도록 별도의 포괄 사용여부 스위치를 두지 않는다. false·0·빈 배열은 유효한 명시값이다.
- 저장·삭제 중 중복 요청/입력 변경 방지. 닫기·목록 재조회 시 미저장 변경 확인. 저장 실패 시 입력 보존. 삭제는 확인 후 수행하며 시스템 정책은 삭제 금지.
- 임의 신규 정책은 설정값 저장까지만 지원한다. 업무 로직 자동 생성·임의 SQL 실행은 제공하지 않으며 화면에 안내한다.
- 375/768/1280px 반응형. 분류와 검색은 좁은 화면에서 줄바꿈하고 편집기는 전체 폭 안에서 표시한다.

## API 및 타입

기존 ResultVO envelope를 사용한다. 모든 API는 `LoginVO.roleCode == PLATFORM_ADMIN`만 허용하며 tenantId/사용자 식별은 인증정보에서 받는다. 요청의 tenantId는 사용하지 않는다.

- GET `/api/v1/system/policies`: `result.resultList: Policy[]`.
- POST 동일 경로: 생성, `result.item: Policy`.
- PUT `/{id}`: 수정, `result.item: Policy`. 버전 불일치 HTTP 409.
- DELETE `/{id}?version=N`: 버전 일치 확인, 삭제 및 이력.
- GET `/{id}/history`: `result.resultList: {action, changedBy, changedAt, beforeValue, afterValue}[]` (최대 50건, 값은 JSON).
- GET `/users?keyword=...`: 동일 테넌트 활성 사용자 최대 50명, `result.resultList: {userId:number,userName:string}[]`. 개인정보 추가 필드 반환 금지.

Policy: `policyId:number, policyCode:string, policyName:string, category:string, description:string, valueType:BOOLEAN|NUMBER|SELECT|TEXT|DATE|USER_LIST, value:JSON, options:{value:string,label:string}[], minValue:number|null, maxValue:number|null, unit:string, version:number, systemPolicy:boolean, updatedAt:string`.

생성 payload는 Policy에서 id/version/systemPolicy/updatedAt를 제외한다. 수정은 같은 payload에 version을 추가한다. 코드 대문자 영문·숫자·언더스코어 2~80자, 이름 100자, 분류 80자, 설명 1000자. 선택지는 1~50개·중복 값 금지, value/label 각각 100자. TEXT 최대 2000자. NUMBER 유한수·범위 검증. DATE 실제 ISO 날짜 검증. USER_LIST 양의 사용자 ID 중복 금지·최대 100명, 모든 ID의 현재 테넌트 소속/활성 검증.

단위는 30자, 사용자 검색어는 100자 이내로 제한한다. 타입에 해당하지 않는 선택지·숫자 제약·단위는 빈 값으로 정규화한다. 생성 응답은 기존 ResultVO 성공 계약의 HTTP 200이며, 검증 오류는 HTTP 400, 중복·버전 충돌은 HTTP 409로 반환한다. 이력 changedBy는 사용자명이며 없으면 사용자 ID로 표시한다.

수정은 코드/타입 불변. 시스템 정책은 선택지·제약을 임의 변경하지 못하며 값만 허용된 enum으로 변경한다. 납품계획 모드 변경은 기존 계획이 있는 경우 거부하여 자동 변환을 하지 않는다. 초과정책은 기존 BLOCK/WARN 저장 계약을 유지하며 전환 시 기존 실적을 삭제·증액하지 않는다.

## 저장 및 기존 정책 연결

`tb_system_policy`는 tenant_id + policy_code 유일, 값/선택지 JSONB, version, system_policy, 생성/수정자·시각을 가진다. `tb_system_policy_history`는 생성·수정·삭제 전후 스냅샷을 보관한다. 삭제 이력 보존을 위해 정책 FK cascade를 사용하지 않는다.

기존 `DELIVERY_PLAN_MODE`, `OVER_DELIVERY_POLICY`는 기존 tb_tenant 적용값을 읽어 표시하고 저장 시 같은 트랜잭션에 기존 컬럼을 갱신한다. 정책 테이블 내 복제된 value가 기존 컬럼과 다르더라도 실제 적용값은 기존 컬럼이 우선한다. 기존 업무 Mapper/서비스는 변경하지 않는다. 사용자 생성 정책은 새로운 값 저장소를 사용한다.

중앙 기본값은 테넌트 생성 시 복제될 초기값이며 런타임 상속·기존 테넌트 일괄 덮어쓰기는 없다. 신규 정책 배포는 별도 운영 절차이다.

## DB 근거와 검증

이번 세션 기본 MCP `list_tables`, `describe_table(tb_tenant/tb_user/tb_role_menu_permission)` 호출로 정책 테이블 없음, 납품 관련 테이블 및 tb_tenant의 기존 두 정책 컬럼 존재를 확인했다. 업무 데이터 행은 조회하지 않았다. 메뉴·역할·권한 세부 계약은 추가 describe 및 기존 날짜별 SQL로 확인한다. 실제 DB에는 DDL을 적용하지 않는다.

TDD로 권한·타입별 검증·중복코드·낙관적 잠금·시스템 정책 삭제 보호·이력·기존값 보존을 확인한다. 결과 문서에는 API 합성 브라우저와 실제 연동 범위를 구분한다.
