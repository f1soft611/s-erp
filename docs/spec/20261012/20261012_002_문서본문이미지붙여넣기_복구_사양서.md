# 20261012_002 문서 본문 이미지 붙여넣기 복구 상세 사양서

## 1. 목적 및 범위

문서작성 본문에서 clipboard image paste를 공통 이미지 upload/save lifecycle에 연결한다. 임시 이미지 업로드, 문서 초안 저장 시 이미지 promote 및 본문 URL rewrite, 본문 이미지 조회, 폐기/교체 이미지 cleanup을 지원한다.

- 프런트엔드: 공통 `RichTextEditor` 및 `useRichTextEditorSaveLifecycle`를 사용한다.
- 백엔드: `EmbeddedImageStorageService` 및 `EmbeddedImageDocumentProcessor`를 사용한다.
- 이미지 owner type은 `APPROVAL`, owner ID는 전자결재 문서 ID로 고정한다.
- 일반 첨부 API, 결재선, SYSTEM 이력 정책은 변경하지 않는다.
- 새 테이블/컬럼은 추가하지 않는다.

작업 설계와 실행 순서는 [승인 설계](../../superpowers/specs/2026-10-12-document-approval-inline-image-paste-design.md), [작업지시서](../../directions/20261012/20261012_002_문서본문이미지붙여넣기_복구_작업지시서.md), [구현 계획](../../plan/20261012/20261012_002_문서본문이미지붙여넣기_복구_계획서.md)을 따른다.

## 2. 확인된 현재 계약

- `RichTextEditor`는 이미지 clipboard paste에서 기본 브라우저 동작을 막고 `uploadImage`가 없으면 image node를 삽입하지 않는다.
- 문서 composer는 `uploadImage` 및 common save lifecycle을 연결하지 않는다.
- 공통 temp storage는 tenant, supported MIME, 실제 이미지 signature, 공통 크기 제한을 검증하고 token/preview URL을 제공한다.
- `EmbeddedImageDocumentProcessor`는 owner type/id별 이미지 조회, temp token validation, promotion, HTML/JSON stable URL rewrite, retained file ID 산출을 담당한다.
- `EmbeddedImageStorageService.completeOwnerSave`는 현재 owner 이미지 중 retained되지 않은 metadata를 soft-delete하고 transaction commit 후 object/temp cleanup을 수행한다.
- `tb_common_file` owner type은 기존 문서 첨부에서도 `APPROVAL`로 쓰이며 embedded image metadata는 같은 공통 파일 저장소를 사용한다.

## 3. 프런트엔드 동작

### 3.1 Clipboard paste와 임시 업로드

1. 이미지 clipboard paste는 기존 `RichTextEditor`가 처리한다.
2. composer adapter는 approval temp upload API를 호출하고 결과를 editor image attributes로 매핑한다.
   - `src` ← `previewUrl`
   - `alt` ← `fileName`
   - `uploadToken`, `fileSize`, `mimeType`, `objectKey`를 기존 editor lifecycle 속성으로 전달한다.
3. 공통 lifecycle은 해당 업로드 session을 관리한다. paste를 취소하거나 node가 제거되면 해당 temporary token/file name을 DELETE API로 정리한다.
4. 이미지 upload 중에는 저장 버튼과 save callback을 비활성/차단한다.
5. 업로드 실패는 composer 상단 오류 영역에 표시한다. shared editor의 실패 처리에 따라 실패 image node는 제거하고 성공한 본문 텍스트는 보존한다.
6. 일반 첨부 선택 및 upload retry는 기존 기능을 유지하고 inline image로 섞지 않는다.

### 3.2 Draft save request

기존 draft payload에 아래 두 배열을 추가한다. 각 배열은 이미지가 없으면 빈 배열이며, 기존 client가 배열을 보내지 않는 경우 백엔드에서 빈 배열로 취급한다.

```json
{
  "embeddedImages": [
    {
      "uploadToken": "canonical upload token",
      "fileName": "image.png",
      "imageUrl": "current editor image URL",
      "fileId": null,
      "objectKey": "temporary object key",
      "fileSize": 12345,
      "mimeType": "image/png",
      "width": null
    }
  ],
  "temporaryImages": [
    {
      "uploadToken": "canonical upload token",
      "fileName": "image.png"
    }
  ]
}
```

- `embeddedImages`: 현재 editor snapshot에서 upload token이 있는 임시 이미지의 metadata. 새 이미지의 token/name 및 editor image attributes를 담는다. 이미 저장된 이미지는 token이 없으므로 본문 HTML/JSON의 stable URL과 file metadata로 processor가 확인한다.
- `temporaryImages`: 이번 작성 세션에서 업로드된 모든 임시 이미지. 저장 본문에서 제외된 이미지를 cleanup하기 위해 보낸다.
- HTML과 JSON의 image node attributes가 최종 참조 기준이며, request의 metadata만으로 이미지 소유권을 만들지 않는다.

작성 취소 또는 닫기 시 `cleanupTemporaryImages()`를 실행한다. 저장 API 실패 때는 temporary uploads를 삭제하지 않아 사용자가 재시도할 수 있게 둔다.

## 4. 백엔드 API

모든 경로는 stateless authentication의 기존 `/api/v1/**` 인증 정책을 따른다.

### 4.1 임시 이미지 업로드

- `POST /api/v1/groupware/approvals/embedded-images/temp`
- `multipart/form-data`: `file`
- controller가 authenticated `LoginVO`를 확인하고 `EmbeddedImageStorageService.uploadTemporaryImage(tenantId, file)`을 호출한다.
- 성공: HTTP `201`, 기존 ResultVO envelope의 `item`에 `EmbeddedImageUploadVO`를 반환한다.
- MIME/content signature/지원 확장자/기존 공통 이미지 최대 크기는 공통 storage 서비스 정책을 따른다. 별도 정책을 추가하지 않는다.

### 4.2 임시 이미지 삭제

- `DELETE /api/v1/groupware/approvals/embedded-images/temp/{uploadToken}?fileName={fileName}`
- 인증 tenant로 `deleteTemporaryImage`를 호출한다.
- 누락/잘못된 token 또는 filename은 기존 공통 storage validation status/message를 따른다.

### 4.3 저장된 draft 이미지 조회

- `GET /api/v1/groupware/approvals/{electronicApprovalId}/embedded-images/{fileId}`
- 호출 전에 `requireDraftOwner(user, electronicApprovalId)`를 적용한다.
- 이후 `streamOwnedImage(tenantId, "APPROVAL", electronicApprovalId, fileId, response)`를 호출한다.
- 응답은 공통 이미지 storage의 binary stream이며 content type, `Content-Disposition:inline`, `X-Content-Type-Options:nosniff`, private cache 설정을 따른다.
- 존재하지 않거나 다른 owner/file usage인 경우 공통 storage의 404 정책을 따른다.
- 제출/승인 후 approver access는 이 작업 범위가 아니다.

## 5. Draft 저장 및 이미지 처리

### 5.1 Domain DTO

`DocumentApprovalEmbeddedImageVO`는 JSON fields `uploadToken`, `fileName`, `imageUrl`, `fileId`, `objectKey`, `fileSize`, `mimeType`, `width`를 갖는다. `embeddedImages`와 `temporaryImages`는 같은 DTO를 공유하고 `temporaryImages`에서는 `uploadToken`, `fileName`만 필요하다. Editor snapshot의 `src`를 `imageUrl`로 매핑하고, editor attribute가 없는 optional metadata는 null로 전송한다.

### 5.2 공통 processor 입력

승인 서비스는 두 DTO list에서 공통 processor가 검증에 사용하는 `uploadToken`, `fileName`을 `EmbeddedImageUploadVO`로 변환하고 아래 값으로 processor를 호출한다.

- `tenantId`: authenticated principal
- `ownerType`: `APPROVAL`
- `ownerId`: 새로 발급됐거나 갱신 중인 approval ID
- `html`/`json`: request의 body
- `referencedImageMetadata`: `embeddedImages`를 token/name으로 변환한 목록
- `temporaryUploads`: `temporaryImages`
- `uploadedBy`: authenticated user login ID
- URL resolver: `/api/v1/groupware/approvals/{approvalId}/embedded-images/{fileId}`만 생성/해석

processor는 HTML/JSON sanitized body를 각각 검사한다. 같은 owner에 이미 저장된 이미지의 fileId/objectKey/stable URL은 유지할 수 있다. 다른 tenant/owner image, 현재 temp session이 아닌 token, token/name 중복, metadata 모순은 거부한다. 임시 URL 또는 허용되지 않은 내부 API image URL을 stable URL로 저장하지 않는다.

### 5.3 Create draft

1. 인증, 요청, category 및 결재선 검증을 기존과 동일하게 수행한다.
2. 같은 transaction에서 main row를 insert해 approval ID를 얻는다.
3. 발급 ID와 함께 common processor를 실행해 temp images를 `APPROVAL` owner로 promote하고 HTML/JSON을 stable URL/metadata로 rewrite한다.
4. rewritten HTML/JSON 및 HTML에서 재산출한 text를 main row에 반영한다. 업데이트가 정확히 한 행이 아니면 저장을 실패시킨다.
5. 결재선 저장과 `DRAFT_SAVED` 시스템 메시지를 기존 transaction에서 처리한다.
6. `completeOwnerSave(tenantId, "APPROVAL", approvalId, temporaryImages, retainedFileIds)`를 호출한다.
7. 성공 후 기존 draft response를 반환한다.

### 5.4 Update draft

1. 기존 draft owner 검증을 수행한다.
2. 기존 approval ID로 processor를 실행한다.
3. rewritten HTML/JSON/text를 기존 조건부 main update에 반영한다.
4. 결재선과 `DRAFT_SAVED` 메시지 저장을 유지하고 `completeOwnerSave`를 호출한다.

Create/update 모두 기존 `@Transactional(rollbackFor = Exception.class)` 범위를 유지한다. Processor, document update, approval line, system event 중 실패하면 DB rollback과 공통 image storage의 rollback object cleanup이 동작한다. Commit 뒤 `completeOwnerSave`가 제거 대상의 MinIO object와 남은 temp session objects를 정리한다.

## 6. 오류 및 보안

- 인증 정보가 없으면 401; image upload가 비었거나 image signature/metadata가 잘못되면 기존 공통 storage의 400/413 정책을 따른다.
- 다른 사용자의 draft나 존재하지 않는 draft image는 승인 문서 존재를 노출하지 않는 기존 404 정책을 따른다.
- `ownerType`, tenant, owner ID, file usage `EMBEDDED`와 fileId를 함께 검증한다.
- 클라이언트의 `objectKey`, URL, owner ID를 권한 증거로 신뢰하지 않는다. 소유 판정은 공통 file metadata와 resolver allowlist를 사용한다.
- 이미지 업로드 중 저장을 막는다. image upload error는 composer의 상단 오류 UI에 보이고 실패 placeholder는 body에 남지 않는다.
- Draft 저장 실패 시 본문, 결재선, document ID, 일반 첨부 및 재시도 가능한 temp image session을 보존한다.
- 일반 첨부 API와 attachment retry flow는 변경하지 않는다.

## 7. DB/스키마 계약

- 추가 테이블/컬럼이 없다. 기존 common file metadata row에 owner `APPROVAL`, `file_usage_type='EMBEDDED'`를 사용한다.
- `EmbeddedImageStorageServiceImpl`, `CommonFile_SQL_postgresql.xml`, `docs/database`의 common-file schema history가 현재 저장/목록/soft-delete 계약의 근거다.
- 현재 세션의 도구 목록에서는 `s-erp-postgresql-readonly`가 제공되지 않아 live DB MCP 확인을 수행할 수 없다. 작업 결과에는 이 사유와 Mapper/domain/test 기반 대체 근거를 남긴다. 기존 DB 계약과 달라 schema change가 필요해지면 구현을 중지하고 별도 SQL/rollback/문서 승인 작업으로 분리한다.

## 8. 검증 기준

### 프런트엔드

- Clipboard image paste가 approval temp endpoint를 호출하고 preview image node를 추가한다.
- 업로드 완료 전에는 save callback이 실행되지 않는다.
- 업로드 실패 시 상단 오류가 표시되고 실패 node는 제거된다.
- Save request의 HTML/JSON image attributes, `embeddedImages`, `temporaryImages`가 맞게 연결된다.
- Composer close는 temp cleanup을 실행하고 저장 API 오류는 temp uploads를 유지한다.
- 기존 일반 첨부 및 draft save service 테스트는 모두 유지된다.

### 백엔드

- Temp upload/delete는 인증 principal의 tenant만 사용한다.
- Image stream은 authenticated draft owner만 허용한다.
- Create/update 각각에서 referenced temp image가 `APPROVAL` owner로 promote되고 HTML/JSON stable URL과 file metadata가 일치한다.
- 기존 owner의 retained image는 보존되고 본문에서 제거된 image는 save commit 뒤 cleanup된다.
- 잘못된 token/filename/metadata/owner URL은 거부되고 다른 owner의 image를 참조할 수 없다.
- Processor/main/line/system event 중 실패 시 DB changes가 rollback되고 promoted object cleanup이 실행된다.
