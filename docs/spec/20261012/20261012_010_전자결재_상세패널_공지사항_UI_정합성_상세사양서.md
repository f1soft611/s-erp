# 20261012_010 전자결재 상세 패널 공지사항 UI 정합성 상세사양서

## 목적과 기준

전자결재 문서 상세 패널의 정보 배치와 상호작용을 공지사항 피드에 맞춘다. 기존 순차 결재와 참여자 권한은 보존한다. 별도 문서 이력 섹션은 없애고 SYSTEM 이벤트를 USER 댓글 루트와 함께 시간순으로 표시한다. 기안자에게 상태가 허용하는 수정/삭제 메뉴를 제공하고 삭제는 감사 이력을 보존하는 논리 삭제로 처리한다.

## 확인된 PostgreSQL 계약

`s-erp-postgresql-readonly`의 `list_tables`, `describe_table`, `pg_constraint` catalog 조회를 사용했다. 실제 테이블 행은 조회하지 않았다.

- `tb_electronic_approval_main`은 `electronic_approval_id BIGINT`, `tenant_id BIGINT`, `drafter_id VARCHAR`, `document_status VARCHAR`를 가진다. 현재 `deleted_yn` 컬럼은 없다.
- 문서 상태 CHECK는 `DRAFT`, `PENDING`, `IN_PROGRESS`, `REVISION_REQUESTED`, `COMPLETED`, `REJECTED`만 허용한다. 삭제를 `document_status`에 추가하지 않는다.
- `tb_electronic_approval_line_info`에는 `stage_order`, `participant_order`, `participant_type`, `participant_user_id`, `action_status`, `pending_at`, `action_at`, `action_comment`가 있다. 현재 CHECK는 `REFERENCE`의 action 값이 전부 NULL이거나, `APPROVAL`/`AGREEMENT`가 유효한 WAITING/PENDING/완료 action 상태를 갖도록 제한한다.
- `tb_common_comment`에는 이미 자체 댓글 논리 삭제용 `deleted_yn CHAR NOT NULL DEFAULT 'N'`이 있다. 본 사양의 새 논리 삭제 필드는 `tb_electronic_approval_main.deleted_yn VARCHAR(1) NOT NULL DEFAULT 'N'`으로 추가하며 댓글 필드를 재사용하거나 변경하지 않는다.
- `chk_tb_common_comment_event_type`은 USER의 NULL event 또는 SYSTEM의 비어 있지 않은 `APPROVED`, `REJECTED`, `RETURNED`, `DRAFT_SAVED`, `SUBMITTED`, `RESUBMITTED`, `COMPLETED` event를 허용한다. 여기에 `DELETED`만 추가한다.
- 문서 상태·결재선 action 제약, 컬럼 타입이나 FK는 변경하지 않는다. `docs/database/20261012/20261012_002`에 forward/change/rollback 파일을 만들고 `docs/database/db-schema.md`를 갱신한다. 운영 DB에는 적용하지 않는다.

## 상세 화면 계약

### 패널과 카드 순서

- `PostDetailPanel`의 title은 고정 `문서 상세`, subtitle은 `문서 ID: {electronicApprovalId}`다. 닫기/overlay 기존 동작은 유지한다. subtitle이 없는 공지사항 상세의 기존 표현은 바뀌지 않는다.
- 카드 첫 행에는 기안자 표시명/아바타, 기안일, 기능 없는 핀 아이콘, 기안자 더보기, 문서 상태 배지를 배치한다.
- 본문은 다음 순서로 표시한다.
  1. 읽기 전용 기안자와 기안일 메타정보
  2. 작성 화면과 동일한 순서의 읽기 전용 결재선: 단계/유형, 이름, 부서, 처리상태, 처리 의견
  3. 문서 제목
  4. 본문 내용
  5. 인증된 본문 이미지 미리보기 목록
  6. `AttachmentList` 기반 문서 첨부 목록
  7. 공지사항형 좋아요/북마크 UI
  8. 댓글 타임라인과 기존 USER 댓글 작성기
- 본문 embedded image는 본문 내 원래 위치에 번호/대체 텍스트 참조를 남기고, 실제 이미지는 별도 미리보기 목록에서 한 번만 표시한다. 이를 통해 본문 흐름과 이미지의 문맥 연결을 유지하면서 중복 렌더링을 막는다. 기존 approval 인증 embedded-image blob 경로와 object URL 정리를 재사용한다. 이미지 로딩 실패를 빈 목록/성공 상태로 숨기지 않는다.
- 좋아요/북마크는 프런트엔드 컴포넌트 수명 동안만 상태를 바꾸고 새로고침/상세 재열기 후에는 초기화한다. API 요청과 DB 저장은 하지 않는다. 핀은 아이콘만 표시하며 클릭 동작을 제공하지 않는다.

### 수정/삭제 메뉴

- 상세 서버 응답에 `isDrafter: boolean`을 추가한다. Mapper는 `(m.drafter_id = #{drafterId}) AS is_drafter`를 계산하고 원본 drafter ID는 응답하지 않는다. `actorParams(user)`의 인증된 `drafterId`를 사용한다.
- 프런트엔드는 `isDrafter`가 boolean인지 응답 검증한다. 누락/잘못된 형식이면 명시적으로 오류 처리하며 `false` 같은 성공형 기본값을 만들지 않는다.
- 비기안자에게 기안자 메뉴를 노출하지 않는다. 수정은 `DRAFT`와 `REVISION_REQUESTED`에만 제공하고 기존 수정 화면/재상신 흐름을 유지한다.
- 삭제는 본인 `DRAFT` 또는 삭제 조건을 만족하는 본인 `PENDING`에만 메뉴를 제공한다. UI 조건은 표시용이다. 서버 검증 결과가 언제나 최종 권한이다.
- 삭제 메뉴를 누르면 확인 UI를 연다. 취소는 요청하지 않는다. 성공한 경우만 패널을 닫고 현재 문서 목록/요약 갱신 callback을 실행한다. API 오류면 패널을 유지하고 명시적 오류를 표시한다.

## 댓글 및 SYSTEM 이력 계약

- 별도 `문서 이력` 섹션은 렌더링하지 않는다.
- 상세 응답 `systemEvents`와 기존 USER 댓글 조회 결과를 결합하되 SYSTEM 이벤트와 USER root 댓글만 `createdAt` 오름차순으로 정렬한다. USER 대댓글은 해당 USER root의 하위에 남긴다.
- SYSTEM 행은 `isSystemEvent: true`로 표시하고 작성/답글/수정/삭제/첨부 조작 affordance와 callback을 제공하지 않는다. USER 댓글의 권한·첨부·기존 서비스 callback은 그대로 유지한다.
- 사용자 댓글 페이지네이션은 기존 USER 전용 API 결과에만 적용한다. SYSTEM 행을 댓글 개수에 포함하거나 USER 댓글을 중복 표시하지 않는다.
- 공지사항은 `isSystemEvent` 없이 기존 USER 댓글만 전달하므로 변경 전과 동일하게 렌더링되어야 한다.

## 삭제 API 및 서버 권한 계약

### Endpoint

| Method / path | 인증·입력 | 성공 응답 |
|---|---|---|
| `DELETE /api/v1/groupware/approvals/{electronicApprovalId}` | 인증 `LoginVO`, 양의 문서 ID. 요청 본문 없음. tenant/기안자 ID를 요청에서 받지 않음 | 기존 `ResultVO` 성공 wrapper와 삭제 완료 메시지 |

문서 소유자는 `LoginVO.id`와 `tb_electronic_approval_main.drafter_id`로 비교한다. 결재선 사용자 비교는 기존 `LoginVO.uniqId`와 `participant_user_id` 계약을 따른다. tenant는 인증 `LoginVO.tenantId`에서만 가져온다.

### 허용 상태와 동시성

- 기안자 소유의 `DRAFT`는 삭제 가능하다.
- 기안자 소유의 `PENDING`은 다음 조건을 모두 만족할 때만 삭제 가능하다.
  - stage 1의 기안자 `APPROVAL` 행이 자동 승인되어 `action_status='APPROVED'`이고 `action_at IS NOT NULL`이다.
  - 다른 모든 `APPROVAL`/`AGREEMENT` 행은 `WAITING` 또는 `PENDING`이고 `action_at IS NULL`, `action_comment IS NULL`이다.
  - `REFERENCE`는 결재 action 이력이 없는 유형이므로 삭제 판단에서 제외한다.
- 다른 결재 참여자가 `APPROVED`, `REJECTED`, `RETURNED`를 처리했거나 상태가 `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `REVISION_REQUESTED`이면 삭제를 거부한다.
- service는 기존 `selectDocumentApprovalForUpdate` 행 잠금으로 상태를 재확인한다. 해당 잠금 조회는 삭제 문서에서 행을 반환하지 않는다. 결재 action도 같은 문서 행을 잠그므로 삭제와 action은 직렬화된다.
- `PENDING`의 결재선 검증은 잠금된 문서에 연결된 `APPROVAL`/`AGREEMENT` 라인만 검사한다. 검증이 끝난 후 SYSTEM 이벤트와 soft-delete 갱신을 같은 `@Transactional(rollbackFor = Exception.class)` transaction에서 수행한다.

### 원자적 삭제

- event 필드는 `owner_type='APPROVAL'`, `owner_id=electronicApprovalId`, `comment_type='SYSTEM'`, `event_type='DELETED'`, `content='문서가 삭제되었습니다.'`이며 작성자 ID/이름과 tenant는 인증 객체에서 가져온다.
- `tb_electronic_approval_main.deleted_yn`만 `N`에서 `Y`로 갱신한다. `document_status`를 `DELETED`로 바꾸지 않는다.
- 갱신 조건은 `tenant_id`, 문서 ID, 기안자 ID, `document_status IN ('DRAFT','PENDING')`, `deleted_yn='N'`을 모두 포함하고, 영향 행 수가 정확히 1이 아니면 성공 처리하지 않는다.
- SYSTEM insert 또는 문서 갱신이 실패하면 예외를 전파해 두 변경 모두 rollback한다. 문서, 결재선, 댓글 이력, 첨부 메타데이터 및 이미지 파일을 물리 삭제하지 않는다.

### 오류 응답

- ID가 null/0/음수이면 `400 BAD_REQUEST`.
- 인증 누락/불완전은 기존 인증 helper의 status를 유지한다.
- 다른 tenant, 비기안자, 삭제 문서/존재하지 않는 문서는 기존 존재 은닉 규칙에 맞춰 `404 NOT_FOUND`.
- 허용되지 않는 상태/결재선 이력 및 동시 상태 충돌은 `409 CONFLICT`.
- DB 오류는 성공 응답이나 fallback으로 숨기지 않는다. 삭제 화면은 API 실패를 명시하고 열린 상세를 유지한다.

## 삭제 문서의 일반 접근 차단

`deleted_yn='Y'` 문서는 일반 사용자 조회 및 참여자 접근 검증에서 숨긴다. 문서 상태/결재선 데이터와 하위자료는 보존한다.

- 문서 목록, 요약 집계/알림, 상세 조회
- 참여자 여부, 삭제/결재 처리용 문서 잠금, 임시저장 소유자/상태 확인
- 기존 참여자 검증을 거치는 USER 댓글 조회/작성/수정/삭제와 댓글 첨부 조회/다운로드/삭제
- 문서 첨부 및 인증 본문 이미지 조회/다운로드

기존 approval 권한 검증 helper와 전용 API를 유지하고, 삭제 문서에 대한 비참여 접근은 존재 여부를 노출하지 않는 `404`를 반환한다. 공통 댓글/파일 API 권한 범위는 넓히지 않는다.

## migration/배포 규칙

- `tb_electronic_approval_main.deleted_yn VARCHAR(1) NOT NULL DEFAULT 'N'`와 `Y/N` CHECK를 추가한다.
- `chk_tb_common_comment_event_type`은 기존 USER/SYSTEM 형태와 이벤트 허용 목록을 유지하면서 SYSTEM `DELETED`를 추가한다.
- forward migration, 변경 이력, rollback SQL은 `docs/database/20261012`와 `backend/DATABASE/20261012`에 동일하게 둔다. 변경 이력에는 변경일, 대상 테이블, API/조회 영향, 적용 전제, 롤백 제한을 기록한다.
- rollback은 삭제 표시가 `Y`인 문서 또는 `DELETED` 이벤트가 있으면 데이터 손실을 막기 위해 중단한다. 그렇지 않은 경우에만 이벤트 CHECK를 이전 목록으로 복구하고 컬럼을 제거한다.
- `docs/database/db-schema.md`에 새 문서 논리 삭제 컬럼과 event 계약을 반영한다.
- migration이 대상 DB에 선행 반영되기 전에는 `deleted_yn`을 참조하는 신규 코드를 배포하지 않는다. 본 구현 작업에서는 DB MCP를 통한 변경/DDL 실행을 금한다.

## 검증 기준

### 백엔드

- service 테스트: 400/404/409 실패 상황, 소유자 비교, DRAFT 성공, 제한된 PENDING 성공 및 외부 action 이력 차단
- 원자성: `DELETED` SYSTEM 이벤트와 `deleted_yn='Y'` 갱신 성공 및 각각의 실패 시 rollback
- 동시성: 삭제와 결재 action 양쪽이 동일 문서 행 잠금을 사용함을 확인
- Mapper: 일반 조회/참여자/잠금 경로의 bound SQL이 삭제 문서를 제외하는지 확인
- Controller: DELETE method/path, 인증 `LoginVO` 위임, 성공 `ResultVO` 확인

### 프런트엔드

- service: DELETE URL, positive safe integer 검증, 실패 전파, `isDrafter` boolean 런타임 검증
- 상세 UI: panel title/subtitle, 문서 카드 콘텐츠 순서, 별도 이력 섹션 제거, 읽기 전용 결재선과 SYSTEM 행
- 권한/삭제 UX: 기안자/상태별 메뉴, 확인 취소, 성공 시 닫기와 목록/요약 갱신, 실패 시 열린 상세와 오류
- 댓글: SYSTEM 조작 불가, USER 작성/답글/수정/삭제/첨부와 Notice 기존 동작 회귀
- 좋아요/북마크: 임시 상태만 변경하며 approval 요청 없음. 핀은 동작 없음.
- `npm run build` 및 `frontend/tests/document-write-page.test.tsx`, `document-approval-service.test.ts`, `feed-components.test.tsx` 대상 Vitest

### 브라우저와 결과

- `frontend/AGENTS.md` 기준 375px, 768px, 1280px에서 panel title/ID, 읽기 전용 결재선, 좁은 헤더, 본문/이미지/첨부/댓글의 가로 overflow를 확인한다.
- 더보기/삭제 확인창은 열기·취소 흐름만 실제 브라우저에서 확인하며 삭제/결재를 확정하지 않는다. API 성공/실패는 mock 기반 Vitest에서 검증한다.
