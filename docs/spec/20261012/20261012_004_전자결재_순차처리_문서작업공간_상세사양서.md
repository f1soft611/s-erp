# 20261012_004 전자결재 순차처리 및 문서작업공간 상세 사양서

## 목적

문서 임시저장 이후 결재신청, 순차 승인, 동시 합의, 반려, 보완요청, 재상신을 서버가 안전하게 처리하고 관련 시스템 이력을 `tb_common_comment`에 append-only로 기록한다. 문서작성 화면은 기안자·결재자·합의자·참조자가 관련된 문서와 결재 건수를 제공한다.

## 확정 범위

### 포함

- 작성 최신 본문·결재선의 서버 검증 및 원자적 결재신청/재상신.
- 순서 기반 승인, 단계 내 합의 동시 처리, 활성 처리자 검증, 반려/보완 상태 전이.
- 문서·결재선·시스템 이력 목록·요약·상세 조회와 관련 참여자 권한 검증.
- 참여자에 대한 문서 첨부 및 본문 이미지 읽기 권한.
- 문서작성 화면의 우측 독립 결재 요약·문서 상태·알림 카드, 상세 모달 및 결재 액션.
- `pending_at`, `eabus_no`, 문서/이벤트 CHECK 변경에 대한 양쪽 날짜별 SQL·변경이력·롤백 및 누적 스키마 갱신.

### 제외

- 사용자 댓글·대댓글, 좋아요, 문서 고정/해제 또는 고정 상태 저장.
- 별도 결재 단계/회차 이력 테이블, 위임·대결·회수, 결재선 변경, 새 병렬 승인 유형.
- 별도 전자결재 포털, 저장된 검색/조회 및 목록 페이지네이션 UX.
- 결재선과 무관한 사용자의 본문·첨부·이력 접근.

## 기존 계약 및 확인 근거

- 현행 문서 API prefix는 `/api/v1/groupware/approvals`이며 공통 응답은 `ResultVO`의 `resultCode`, `resultMessage`, `result` 맵을 사용한다. 현재 draft 생성은 HTTP 201, draft 갱신 및 조회는 성공 `ResultVO`를 사용한다.
- 기존 draft 요청 `DocumentApprovalDraftSaveRequestVO`는 `documentType`, `draftingWorkCategoryId`, `title`, `contentsJson`, `contentsHtml`, `contentsText`, `approvalLines`, `embeddedImages`, `temporaryImages`를 포함한다. 결재신청 요청은 이 계약을 재사용해 화면의 최신 본문과 결재선을 제출한다.
- `LoginVO.tenantId`는 tenant 경계, `LoginVO.id`는 로그인/기안자 식별, `LoginVO.uniqId`는 결재선 참여자 식별에 사용한다. 사용자 식별자를 요청 본문에서 신뢰하지 않고 로그인 객체에서 가져온다.
- 기존 `CommonCommentDAO.insertSystemComment`를 사용하며 시스템 행의 `owner_type=APPROVAL`, `comment_type=SYSTEM`, `event_type`, 행위자 및 시각을 보존한다.
- 기존 `selectCommonCommentList`는 USER/SYSTEM을 모두 반환하므로 승인 상세 타임라인은 tenant·owner 조건과 `comment_type=SYSTEM`을 강제하는 전용 조회를 추가한다.
- PostgreSQL 메타데이터 확인에서는 `tb_electronic_approval_main`의 `eabus_no` 및 `REJECTED`, `tb_electronic_approval_line_info`의 `pending_at`, `tb_common_comment`의 `SUBMITTED`/`RESUBMITTED`/`COMPLETED` 허용 여부가 추가되어야 하는 것으로 확인되었다. 확인 당시 `DRAFT_SAVED`는 허용되어 있었으나 과거 제약 오류와의 환경/시점 차이는 확정하지 못했다.
- 구현 직전 `s-erp-postgresql-readonly`의 `list_tables`와 필요한 `describe_table`로 컬럼·CHECK·FK를 재확인한다. 이력이 현재와 다르면 기존 적용 migration 및 Mapper를 대조하고 결과 문서에 근거를 남긴다. 개인정보가 포함된 데이터 행은 조회하지 않는다.

## 사용자·문서 권한

1. 모든 approval 데이터 쿼리는 인증 객체의 `tenantId`를 조건으로 사용한다. 문서 작성자 비교는 `LoginVO.id`, 결재선 참여자 비교는 `LoginVO.uniqId`를 사용한다.
2. 문서 관련 사용자는 해당 tenant에서 `drafter_id`가 현재 로그인 사용자이거나 결재선의 `participant_user_id`가 현재 `uniqId`와 일치하는 사용자다. `APPROVAL`, `AGREEMENT`, `REFERENCE`를 모두 읽기 참여로 인정한다.
3. 목록·요약·상세·SYSTEM 타임라인·기존 첨부 목록/다운로드·본문 이미지 조회는 관련 사용자에게만 허용한다. 연결되지 않은 사용자와 tenant가 다른 사용자는 문서 존재 여부를 노출하지 않도록 404 처리한다.
4. 임시저장 문서 수정 및 첨부 추가/삭제는 기안자만 허용한다. 수정/첨부 업로드를 허용하는 문서 상태는 `DRAFT`와 `REVISION_REQUESTED`뿐이다. 결재신청 뒤에는 기안자라도 첨부 변경을 할 수 없다.
5. 결재 액션은 현재 상태가 `PENDING`인 결재선 중 요청 사용자가 담당하는 `APPROVAL` 또는 `AGREEMENT` 행에만 허용한다. `REFERENCE`는 승인 액션, `action_at`, `action_comment`를 갖지 않는다.
6. 누락/불완전 인증은 401, 필드·결재선 검증 오류는 400, 접근 불가/없는 문서는 404, 이미 처리되었거나 상태가 맞지 않는 동시 요청은 409로 응답한다. 예외를 성공 모양으로 변환하지 않는다.

## HTTP API 계약

기존 prefix `/api/v1/groupware/approvals`를 사용하며 성공 응답은 `ResultVO` 관례를 따른다. 경로의 `electronicApprovalId`는 양의 정수다.

| 메서드 및 경로 | 권한 | 요청 | 성공 결과 |
|---|---|---|---|
| `POST /drafts` (기존) | 로그인 사용자 | 기존 draft 요청 | 201, `result.item.electronicApprovalId`, `documentStatus=DRAFT` |
| `PUT /drafts/{electronicApprovalId}` (기존) | 해당 문서 기안자, 상태 `DRAFT` 또는 `REVISION_REQUESTED` | 기존 draft 요청 | `result.item` |
| `POST /{electronicApprovalId}/submit` (신규) | 해당 문서 기안자, 상태 `DRAFT` 또는 `REVISION_REQUESTED` | 기존 draft 요청 전체. 문서 유형, 최신 본문, 결재선 및 이미지 메타데이터 포함 | `result.item`에 ID, `eabusNo`, `documentStatus=PENDING`, `submittedAt` |
| `POST /{electronicApprovalId}/actions` (신규) | 해당 문서의 현재 활성 결재자/합의자 | 아래 action 요청 | `result.item`에 문서 상태와 최신 결재선 처리 상태 |
| `GET /documents` (신규) | 해당 tenant의 로그인 사용자 | 선택 query `scope`, `documentType`, `electronicApprovalId` | `result.resultList` |
| `GET /summary` (신규) | 해당 tenant의 로그인 사용자 | 없음 | `result.item`에 기본 건수, 상태별 건수, notice 항목 |
| `GET /documents/{electronicApprovalId}` (신규) | 해당 문서 관련 사용자 | 없음 | `result.item`에 문서·첨부·결재선·SYSTEM 이력 |
| `GET /{electronicApprovalId}/attachments` (기존 권한 확장) | 관련 사용자 | 없음 | `result.resultList` |
| `GET /{electronicApprovalId}/attachments/{fileId}/download` (기존 권한 확장) | 관련 사용자 | 없음 | 파일 스트림 |
| `GET /{electronicApprovalId}/embedded-images/{fileId}` (기존 권한 확장) | 관련 사용자 | 없음 | 보호된 이미지 스트림 |

### 결재 액션 요청

```json
{
  "action": "APPROVED",
  "actionComment": "검토 의견"
}
```

- `action`은 `APPROVED`, `REJECTED`, `RETURNED` 중 하나다.
- `actionComment`는 문자열 또는 생략/null이다. `REJECTED`와 `RETURNED`에는 trim 후 빈 값이 아닌 사유가 필수이고, `APPROVED`에서는 선택이다.
- 최대 길이는 DB에서 확인한 `action_comment` 및 `tb_common_comment.content` 실제 타입/길이를 넘지 않아야 한다.
- 최종 승인 응답에는 문서 상태 `COMPLETED`를 포함한다. 사용자 행위의 `APPROVED`와 최종 `COMPLETED` 이벤트는 모두 타임라인에 기록한다.

### 목록 query 및 항목

- `scope`: `ALL`(기본), `MY_PENDING`, `IN_PROGRESS`, `DRAFT`, `COMPLETED`, `REVISION_REQUESTED`, `REJECTED`.
- `documentType`: `DRAFTING`, `BUSINESS_CONTACT`, `EXPENSE_RESOLUTION`, `ATTENDANCE_APPLICATION` 중 선택. 좌측 업무구분을 전체로 초기화하면 생략한다.
- `electronicApprovalId`: 있으면 단일 문서를 반환하며 notice 항목에서 좌측에 해당 문서만 표시할 때 사용한다. 이 경우에도 참여자/tenant 검증은 동일하다.
- `MY_PENDING`은 현재 사용자의 `PENDING` 결재선이 존재하는 문서만 반환한다. `IN_PROGRESS`는 문서 상태 `PENDING` 또는 `IN_PROGRESS`다. `DRAFT`는 현재 사용자가 기안한 `DRAFT`다. 나머지 scope는 관련 문서 중 지정 상태를 조회한다.
- `ALL`은 현재 사용자가 기안자·결재자·합의자·참조자로 연결된 모든 상태의 문서를 반환한다. 문서 ID 기준으로 중복 제거하고 `updated_at` 최신순, ID 내림차순으로 안정 정렬한다.
- 항목은 기존 좌측 화면이 사용하는 `electronicApprovalId`, `eabusNo`, `documentType`, `documentStatus`, `title`, `drafterName`, `createdAt`, `updatedAt`, `submittedAt`, 본문 텍스트에서 만든 표시용 `summary`를 제공한다. `isPinned` 상태나 DB 컬럼을 새로 만들지 않는다.
- 문서 유형은 화면 업무구분으로 매핑한다. 상태 표시는 `DRAFT=임시저장`, `PENDING=결재대기`, `IN_PROGRESS=결재중`, `REVISION_REQUESTED=보완요청`, `COMPLETED=완료`, `REJECTED=반려`다.

### 결재 요약 및 notice 응답

`GET /summary` 응답의 `result.item`은 아래 정보를 제공한다.

```json
{
  "actionRequiredCount": 0,
  "inProgressCount": 0,
  "draftCount": 0,
  "completedCount": 0,
  "revisionRequestedCount": 0,
  "rejectedCount": 0,
  "notices": []
}
```

- 모든 건수는 현재 tenant/관련 사용자 범위 안에서 문서 ID 중복 없이 계산한다.
- `actionRequiredCount`: 현재 사용자에게 활성 `PENDING` 결재선이 있는 문서 수.
- `inProgressCount`: 관련 문서 중 `PENDING` 또는 `IN_PROGRESS` 문서 수.
- `draftCount`: 현재 사용자가 기안한 `DRAFT` 문서 수.
- 상태별 3건수는 관련 문서 중 `COMPLETED`, `REVISION_REQUESTED`, `REJECTED` 문서 수다.
- `notices`는 현재 사용자 처리 대상 문서의 `결재 요청 도착`과 기안자가 수정할 `보완 요청 문서`를 포함한다. 기존 UI의 최대 3건 제한과 최신 변경 순서를 유지한다. 항목은 `electronicApprovalId`, `title`, `documentStatus`, `noticeType`, `updatedAt`을 제공한다.
- `noticeType`은 `ACTION_REQUIRED` 또는 `REVISION_REQUESTED`다.

### 상세 응답

`result.item`은 다음을 포함한다.

- 문서 ID/번호/유형/상태, 기안자명, 작성/상신 시각, 제목, sanitized 본문 JSON/HTML/text.
- 문서의 일반 첨부 정보. 파일 내용은 기존 보호된 다운로드 경로로 조회한다.
- 순서대로 정렬된 결재선: `stageOrder`, `participantOrder`, 참여 유형/사용자 표시 정보, `actionStatus`, `pendingAt`, `actionAt`, `actionComment`.
- `ownerType=APPROVAL`, 현재 문서 ID, 현재 tenant와 `commentType=SYSTEM`으로 제한한 `tb_common_comment` 타임라인. `createdAt` 오름차순으로 표시한다. 사용자 댓글 API나 임의 USER 댓글 노출은 추가하지 않는다.
- 참조자의 조회 권한은 유지하지만 참조자에게 처리 버튼을 제공하지 않는다.

## 저장·첨부·결재신청 흐름

1. 임시저장은 기존 `POST /drafts` 및 `PUT /drafts/{id}`를 사용한다. 저장 성공 toast와 기존 오류 표시, 이미지 업로드 lifecycle을 보존한다.
2. 결재신청은 저장과 별도의 버튼이다. 프런트엔드는 최신 editor snapshot, 현재 결재선과 embedded image metadata를 포함한 `DocumentApprovalDraftSaveRequestVO` 계약을 최종 submit API에 전달한다.
3. 처음 제출하는 문서는 첨부 API가 문서 ID를 요구하므로 기존 임시저장 생성 과정을 먼저 실행해 ID를 확보한다. 이어 대기 중인 일반 첨부를 기존 첨부 API로 업로드한다. 이미 저장된 문서는 새/대기 첨부 업로드를 끝낸 뒤 제출한다. 파일 업로드가 실패하거나 결과가 불명확하면 최종 제출을 중단하고 draft/보완요청 문서를 보존하며 오류를 보여준다.
4. 첨부 준비 후 `POST /{id}/submit` 한 번이 최신 본문·결재선·문서 상태 전이·상신 이벤트를 함께 저장한다. 이 API 내 오류는 모두 rollback한다. 첨부 업로드는 앞선 독립 API라 submit rollback이 이미 업로드된 파일을 삭제하지 않는다.
5. 신규 문서에서 자동 임시저장 생성이 일어나면 기존 `DRAFT_SAVED` 이벤트를 남긴 뒤 `SUBMITTED` 이벤트를 남긴다. 기존 사용자가 명시적으로 저장한 draft도 동일하게 `DRAFT_SAVED` 이벤트가 유지된다.
6. 상신 버튼은 중복 요청을 막는다. 상신 성공 시 toast를 표시하고 작성 모달을 닫은 뒤 목록·요약을 갱신한다. 상신 실패 시 모달 상단 오류 영역에 원인을 표시하고 입력을 보존한다.

## 결재선 검증 및 상태 전이

### 상신 전 검증

- 요청 문서는 기존 허용 document type 중 하나이며 제목/본문 JSON은 기존 draft 검증 계약을 통과한다.
- `approvalLines`는 비어 있지 않고, 참여자는 현재 tenant의 활성 사용자이며 각 사용자는 문서 안에서 중복되지 않는다.
- 기안자는 `APPROVAL` 1단계 첫 참여자이자 유일한 기안자 행이다.
- 일반 `APPROVAL` 참여자는 개별 단계로 배치하고 같은 `AGREEMENT` 단계의 참여자는 같은 stage order에 둔다. 한 stage 안의 참여 유형은 일관된다. stage 순서는 연속적이고 participant order는 1부터 연속적이다.
- `REFERENCE` 참여자는 모든 처리 단계 뒤의 마지막 순서에 배치하며 action 대상이 아니다.
- 기안자 외 승인/합의 참여자가 최소 한 명 있어야 한다. 기안자만 있는 결재선은 draft 저장은 가능하나 submit은 400으로 거절한다.
- `eabusNo`는 요청에서 받지 않는다. 서버가 document type별로 결정한다.

### 상태 전이 규칙

| 명령/상태 | 문서 상태 | 결재선 상태 | SYSTEM 이벤트 |
|---|---|---|---|
| 임시저장 생성/수정 | `DRAFT` | 참여 처리행 `WAITING`, 참조행 처리시각 없음 | `DRAFT_SAVED` |
| 최초 상신 | `PENDING` | 기안자 1단계 `APPROVED`/`actionAt` 기록/`pendingAt=NULL`; 첫 비기안자 단계 `PENDING`; 이후 처리 단계 `WAITING`; 참조행은 미처리 | `SUBMITTED` |
| 일반 승인, 같은 합의 단계 참여자 미완료 | `IN_PROGRESS`(최초 처리자가 승인한 시점부터) | 활성 행 `APPROVED`; 같은 단계의 나머지 활성 행은 `PENDING` | `APPROVED` |
| 단계 전체 승인, 다음 단계 있음 | `IN_PROGRESS` | 다음 stage 전체를 활성화: 일반 승인자 한 명 또는 같은 합의 stage 전원 `PENDING`; 후속은 `WAITING` | 행위별 `APPROVED` |
| 최종 단계 전원 승인 | `COMPLETED` | 마지막 활성 행 `APPROVED` | 행위별 `APPROVED`, 최종 `COMPLETED` |
| 반려 | `REJECTED` | 반려 처리행 `REJECTED`, `actionAt`/필수 사유 저장; 이후 단계 활성화 안 함 | `REJECTED` |
| 보완요청 | `REVISION_REQUESTED` | 요청 처리행 `RETURNED`, `actionAt`/필수 사유 저장; 이후 단계 활성화 안 함 | `RETURNED` |
| 보완 후 재상신 | `PENDING` | 기안자 단계 자동 완료, 첫 비기안자 단계만 새 회차 `PENDING`, 후속 단계 `WAITING`; 새 활성행 `pendingAt` 갱신 | `RESUBMITTED` |

- 일반 결재자는 한 명씩 stage 순서로 처리한다. 합의 stage는 모든 참여자를 동시에 `PENDING`으로 활성화하고 전원 `APPROVED` 이후 다음 stage로 진행한다.
- 활성화할 때 `pending_at`을 기록한다. 실제 활성화된 참여자의 최종 처리 후에도 그 회차의 `pending_at`을 보존한다. 기안자 자동 완료는 대기 단계가 아니므로 `pending_at=NULL`이다.
- `WAITING` 행은 `pending_at`, `action_at`, `action_comment`가 NULL이어야 한다. `PENDING` 행은 `pending_at`이 있고 `action_at`, `action_comment`가 NULL이어야 한다. 완료/반려/보완 행은 `action_at`이 필수다. `REFERENCE`는 처리 상태/시각/사유를 갖지 않는다.
- 재상신은 현재 결재선을 새 회차로 초기화하지만 `tb_common_comment`의 이전 이벤트는 변경/삭제하지 않는다. 별도 회차별 결재선 처리이력 테이블은 추가하지 않는다.
- 상태 변경은 main row 잠금 또는 현재 상태를 조건으로 한 원자적 update와 update count 확인으로 경합을 차단한다. 최종 상태 변경, 결재선 변경 및 SYSTEM 이벤트 삽입은 `@Transactional(rollbackFor=Exception.class)` 경계에 포함한다. 하나라도 실패하면 전체 상태 변경을 rollback하고 409 또는 서버 오류를 명시한다.
- 완료·반려 상태에서 추가 action이나 재상신은 허용하지 않는다. `REVISION_REQUESTED`는 기안자의 재상신만 허용한다.

## 시스템 이력 이벤트

| `event_type` | 발생 시점 | 내용/작성자 |
|---|---|---|
| `DRAFT_SAVED` | 임시저장 create/update | 기존 동작을 유지하고 인증 기안자 기록 |
| `SUBMITTED` | 최초 상신 성공 | 인증 기안자 및 제출 시각 |
| `RESUBMITTED` | 보완요청 후 재상신 성공 | 인증 기안자 및 재상신 시각 |
| `APPROVED` | 결재자/합의자의 승인 액션 성공 | 실제 처리자 및 선택 사유 |
| `REJECTED` | 반려 액션 성공 | 실제 처리자 및 필수 사유 |
| `RETURNED` | 보완요청 액션 성공 | 실제 처리자 및 필수 사유 |
| `COMPLETED` | 마지막 승인으로 완료될 때 | 마지막 승인 actor, 완료 시각 |

모든 행은 `owner_type=APPROVAL`, 해당 문서 ID, `comment_type=SYSTEM`, `parent_comment_id=NULL`, `deleted_yn=N`을 사용한다. 행위자 이름/ID는 요청에서 받지 않고 인증 정보 및 검증된 참여자 정보에서 생성한다. 반려/보완/승인 사유는 현재 결재선의 `action_comment`와 이벤트 `content` 양쪽에 저장한다. 이벤트 목록은 현재 연결된 사용자만 조회하며 이벤트에 저장된 사유는 재상신 뒤에도 보존된다.

## DB 변경 사양

### `tb_electronic_approval_main`

- `eabus_no VARCHAR(3)` 추가. 선행 0을 보존한다.
- 서버 매핑: `DRAFTING=001`, `BUSINESS_CONTACT=008`, `EXPENSE_RESOLUTION=004`, `ATTENDANCE_APPLICATION=031`.
- draft 생성/수정과 결재신청/재상신 모두 서버가 document type으로 값을 정해 저장한다. nullable/요청값으로 두지 않는다.
- 기존 행은 `document_type`으로 backfill하고 허용 조합 CHECK와 NOT NULL을 적용한다. 매핑되지 않는 document type은 임의 값 처리 없이 migration 오류로 드러내고 확인한다.
- `document_status` CHECK에 `REJECTED`를 추가한다.

### `tb_electronic_approval_line_info`

- nullable `pending_at TIMESTAMP` 추가하고 상태별 무결성 CHECK를 실제 제약 이름에 맞춰 보완한다.
- 활성 대기 중인 `PENDING`은 pending_at 필수, `WAITING`은 action 필드 및 pending_at NULL, 처리된 결재행은 action_at 필수다. 자동 완료 기안자 및 참조 행에 대한 예외는 상태 전이 규칙과 일치시킨다.

### `tb_common_comment`

- 기존 이벤트를 유지하면서 `SUBMITTED`, `RESUBMITTED`, `COMPLETED`를 허용한다. 기존 `APPROVED`, `REJECTED`, `RETURNED`, `DRAFT_SAVED`가 적용된 환경도 보존한다.
- `comment_type=SYSTEM` 행은 위 이벤트 코드 중 하나를 갖고, 사용자 댓글은 기존 `event_type IS NULL` 계약을 유지한다.
- `CommonCommentDAO.selectApprovalSystemEvents`와 대응 Mapper는 `tenant_id`, `owner_type=APPROVAL`, `owner_id`, `comment_type=SYSTEM`, `deleted_yn=N`으로 제한하고 `created_at ASC`로 반환한다. 공통 댓글 조회 범위나 USER 댓글 기능은 변경하지 않는다.

### 마이그레이션 산출물/rollback

- SQL, 변경이력 문서, rollback SQL을 `backend/DATABASE/20261012/`와 `docs/database/20261012/`에 같은 번호·내용으로 보관한다. `NNN`은 실제 적용된 날짜 폴더를 확인한 뒤 다음 번호를 선택한다.
- 변경이력은 날짜, 대상 테이블, 적용 내용/순서, 데이터 영향, rollback 여부를 기록한다. `docs/database/db-schema.md`를 동일 작업에서 최신화한다.
- rollback은 새 상태/event 행을 삭제하지 않는다. 기존 CHECK로 돌아갈 수 없는 `REJECTED`, 신규 event 사용 데이터 또는 역변환 불가 데이터가 있으면 실행을 중단하도록 guard한다. 조건이 충족될 때만 새 CHECK와 컬럼을 되돌리며 데이터 삭제로 rollback을 가장하지 않는다.
- 두 날짜별 저장소의 SQL·rollback은 내용이 동일해야 하며 순서·constraint 이름·재실행 전제는 실제 DB MCP 메타데이터와 일치해야 한다.

## 프런트엔드 화면 및 동작

### 좌측 문서 영역

- 현재 `DocumentWritePage`의 `PinnedViewToolbar` → 고정 문서가 있을 때만 `PinnedItemsPanel` → 선택 보기의 `FeedView`/`ListView` → 기존 `EmptyDocumentList` 순서 및 조건부 표시를 변경하지 않는다.
- 좌측 샘플 데이터는 목록 API로 대체하되 표시/필터 컴포넌트 트리는 유지한다. DB에 고정 상태 계약이 없으므로 API 응답에 임의 `isPinned`를 생성하거나 새 고정 기능/빈 고정 영역을 추가하지 않는다.
- 문서 상태/요약 선택은 업무구분을 전체로 초기화하고 선택한 필터를 서버 조회에 적용한다. 피드/리스트 보기 모드는 유지한다.
- notice 항목 선택은 업무구분을 전체로 초기화하고 ID가 지정된 문서만 기존 좌측 영역에서 보여준다. 별도 상세 경로로 이동하지 않는다.
- 좌측 Feed/List 항목 선택은 현재 화면의 상세 모달을 연다. 클릭 handler 추가는 가능하지만 표시 구조/순서는 변경하지 않는다.

### 우측 패널 소스 분리

- `ApprovalSummaryPanel`: 독립 카드에 `내가 처리할 결재`, `결재 진행 중`, `작성 중 문서`만 표시한다.
- `DocumentStatusPanel`: 별도의 독립 카드에 `완료`, `보완요청`, `반려`와 각 건수를 표시한다.
- `ApprovalNoticePanel`: 별도의 독립 카드에 최대 3건의 결재 요청/보완 요청을 표시한다.
- `DocumentWritePage`의 우측 slot에서 위 컴포넌트를 해당 순서대로 세로 배치한다. 세 컴포넌트는 별도 파일로 분리하고 데이터 계산/서버 요청은 서비스 및 페이지 hook 책임으로 둔다.
- 기존 `ContentSplitLayout`의 breakpoint/sticky 동작을 유지한다. 좁은 화면에서는 좌측 아래로 세 카드를 표시하고 1280px급 넓은 화면에서는 우측 열에서 순서대로 쌓는다.

### 상세/액션 모달

- 문서 상세는 현재 작성 작업공간 안의 `DocumentApprovalDetailDialog`에서 표시한다. 상세 로딩·빈 필드·API 실패를 각각 기존 공통 로딩/빈 상태/오류 패턴으로 처리한다.
- 모든 관련자는 본문·첨부·결재선·SYSTEM 이력을 조회한다. 승인/반려/보완 버튼은 해당 현재 로그인 사용자의 활성 `PENDING` 결재/합의행이 있는 경우에만 표시한다.
- 승인 사유는 선택, 반려와 보완요청 사유는 trim 후 필수다. 실패 시 모달 상단 오류 영역에 원인을 남기고 작성 중 사유를 보존한다. 성공 시 toast를 표시하고 모달을 닫은 뒤 목록·요약을 다시 조회한다.
- 기안자는 본인이 작성한 `REVISION_REQUESTED` 문서만 재상신할 수 있다. 참조자는 조회만 가능하다.
- 본문 HTML은 저장된 sanitization 결과를 사용하고 embedded image source는 인증된 approval 이미지 조회 경로를 쓴다. 본문·첨부를 tenant/참여자 권한 검사 없이 노출하지 않는다.

## 오류·동시성·빈 상태 처리

- 잘못된 body/결재선/지원하지 않는 action/필수 사유 누락은 400, 미인증은 401, 타 tenant 또는 비참여 문서는 404, stale 상태 및 이미 완료된 action은 409로 응답한다.
- DB/스토리지 오류를 성공 응답·빈 결과로 바꾸지 않는다. 서비스에서 기존 예외 처리 경로를 따르고, 요청자가 확인할 수 있는 에러 메시지를 제공한다.
- 목록/요약/상세 API 실패는 오류 상태로 나타내며 실제 0건과 구별한다.
- 첨부 업로드 결과가 ambiguous인 경우 기존 `unknown` 처리와 retry/reconcile 동작을 보존하고 최종 제출을 막는다.
- 로딩 중 결재신청/action 중복을 막고, 이전 요청이 끝나기 전에 동일 문서의 재요청을 허용하지 않는다. 서버 검증은 UI disable 상태에 의존하지 않는다.

## 검증 기준

### 백엔드 테스트

- 순차 승인, 합의자 동시 `PENDING` 및 전원 승인 후 다음 단계 활성화.
- 기안자 단계 자동 승인, 기안자 외 처리자 필수, 참조자 action 불가.
- 반려 종료, 보완요청, 재상신 상태 초기화와 append-only 이력 보존.
- 타 tenant/비참여자/비활성 사용자의 상세·이력·첨부·본문 이미지 접근 거부.
- 문서/결재선 갱신이나 시스템 메시지 삽입 실패 시 transaction rollback.
- 경쟁 action, 중복 action, 완료/반려 문서 재요청의 409/정확한 무변경.
- migration 코드와 Mapper의 모든 새 컬럼, CHECK 및 문서 유형 코드 조합.

- 활성 처리자 액션 표시, 승인 사유 선택, 반려/보완 사유 필수, 처리 성공 후 갱신과 실패 표시.
