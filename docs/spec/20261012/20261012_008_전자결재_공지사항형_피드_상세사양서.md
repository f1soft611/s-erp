# 20261012_008 전자결재 공지사항형 피드 상세 사양서

## 목적

전자결재 작업공간에서 목록/피드 항목을 선택하면 공지사항과 같은 우측 상세 패널을 표시한다. 문서 본문·이미지·첨부·결재 진행·시스템 이력·참여자 USER 댓글을 함께 제공하되 기존 순차결재 및 권한을 유지한다.

## 사용자 흐름 및 화면

### 좌측 문서 영역

- 피드/리스트 전환, 문서 업무구분 필터, 기존 상단 고정 문서 표시는 유지한다. 고정 문서가 없으면 빈 고정 영역을 만들지 않는다.
- 피드 보기에는 공지사항 카드형 문서 카드, 리스트 보기에는 기존 문서 리스트를 표시한다.
- 좁은 모바일 화면에서는 카드 작성자/일시와 문서 유형·상태 배지를 줄바꿈해 배치하고, 작성자명이 세로로 쪼개지거나 페이지 가로 넘침이 생기지 않도록 한다.
- 카드와 행 선택은 같은 문서 상세 패널을 연다. 상세를 닫으면 목록, 필터, 보기 모드를 유지한다.
- 카드에 필요한 작성자, 시각, 유형, 상태, 제목과 요약은 목록 응답을 사용한다. 카드별 상세 API 요청을 새로 보내 N+1 호출을 만들지 않는다.

### 우측 상세 패널

- `PageAreaOverlay`와 `PostDetailPanel`의 닫기, backdrop, Escape, 반응형 동작을 따른다. 모바일 상세 패널은 사용 가능한 화면 폭 전체를 사용한다.
- 상세 패널이 열려 있는 동안 문서 목록의 기본 우측 요약 영역은 숨긴다. 닫으면 요약을 복원한다.
- 상세 콘텐츠는 문서 제목·번호·기안자·시각·상태, 안전하게 처리한 본문 HTML과 승인된 본문 이미지, 문서 첨부, 결재선 진행 및 사용자 행위 사유, SYSTEM 이벤트, USER 댓글/대댓글 순서로 표시한다.
- 기존 활성 처리자만 결재 처리할 수 있고, 반려·보완요청 필수 사유, 승인 선택 사유, 보완요청 기안자 수정/재상신을 그대로 유지한다. 참조자는 결재 액션을 할 수 없다.
- 문서 로딩 중에는 패널 콘텐츠 영역에 로딩 상태를 표시한다. 상세 API 오류를 빈 결과나 성공으로 바꾸지 말고 사용자에게 오류 상태를 노출한다.

## 권한 모델

모든 요청은 `LoginVO`의 `tenantId`를 사용한다. 문서 기안자는 `LoginVO.id`, 결재선 참여자는 `LoginVO.uniqId`와 `participant_user_id`로 비교한다.

| 사용자 관계 | 상세/본문 이미지/문서 첨부/SYSTEM 조회 | USER 댓글 조회/작성 | 결재 액션 |
|---|---:|---:|---:|
| 문서 기안자 | 허용 | 허용 | 기존 상태/역할 규칙만 허용 |
| APPROVAL 결재 참여자 | 허용 | 허용 | 현재 활성 처리자만 허용 |
| AGREEMENT 합의 참여자 | 허용 | 허용 | 기존 합의 활성 단계만 허용 |
| REFERENCE 참조 참여자 | 허용 | 허용 | 금지 |
| 비참여자 또는 tenant 불일치 | 404로 존재 은닉 | 404로 존재 은닉 | 금지 |

- 새 댓글의 writer ID/name과 tenant는 인증 객체에서만 결정한다. 요청 본문의 owner, tenant, writer, comment type은 권한/소유 근거로 받지 않는다.
- 댓글 수정/삭제와 해당 댓글 파일 추가/삭제는 댓글 작성자만 가능하다. USER 댓글과 부모 댓글은 같은 tenant·approval 문서에 연결되어야 한다. SYSTEM 행은 읽기 전용이며 답글 부모로 사용할 수 없다.
- `commentId`와 `fileId`의 존재만 확인해서는 안 된다. 문서 ID, 댓글 owner, comment type, tenant 및 file owner의 연관을 매 요청 검증한다.
- 범용 API에 owner 식별자를 넣어 전용 권한 검증을 우회하지 못하게 한다. 공통 댓글 API는 `APPROVAL`을 거부하고, comment ID만 받는 범용 수정/삭제도 `owner_type='APPROVAL'`을 거부한다. 공통 파일 API는 owner 지정 경로에서 `APPROVAL`과 `APPROVAL_COMMENT`를 거부하고, file ID만 받는 다운로드/삭제 Mapper도 두 owner type을 제외한다.

## 확인된 PostgreSQL 계약

확인 시점에 `s-erp-postgresql-readonly`의 `list_tables`, `describe_table` 및 제한된 PostgreSQL catalog SELECT를 사용했다. 행 데이터는 조회하지 않았다.

- `tb_common_comment`: `comment_id`/`owner_id`는 bigint, `tenant_id`는 bigint, `owner_type`/`comment_type`은 varchar, `event_type`은 nullable varchar, `content`는 text다.
- `chk_tb_common_comment_event_type`은 USER의 `event_type IS NULL` 또는 허용 목록에 있는 비어 있지 않은 SYSTEM event를 허용한다. SYSTEM 목록은 `APPROVED`, `REJECTED`, `RETURNED`, `DRAFT_SAVED`, `SUBMITTED`, `RESUBMITTED`, `COMPLETED`다.
- comment parent FK는 `parent_comment_id -> tb_common_comment.comment_id`만 보장한다. 같은 tenant·owner·USER인지 여부는 DB가 보장하지 않으므로 서비스 검증이 필수다.
- `tb_common_file`: owner type/id는 polymorphic 문자열/bigint이며 approval 또는 comment association FK는 없다. `file_usage_type` CHECK 허용값은 `ATTACHMENT`, `EMBEDDED`뿐이다.
- `tb_electronic_approval_main` 및 `tb_electronic_approval_line_info`의 tenant와 문서 ID, participant 필드를 기존 approval DAO 접근 검증에 사용한다.
- 신규 테이블/컬럼/제약은 추가하지 않는다. 댓글 첨부는 기존 허용값 `ATTACHMENT`를 사용한다.

## API 계약

기준 prefix: `/api/v1/groupware/approvals`. 성공 응답은 기존 `ResultVO` wrapper를 따른다. ID는 양의 정수다. 인증 누락은 401, 잘못된 입력은 400, 문서/댓글/파일에 대한 비참여 접근 또는 owner 불일치는 404로 처리한다. 저장소의 기존 예외 매핑이 다르면 해당 패턴을 확인해 테스트와 이 절을 함께 조정한다.

### 사용자 댓글

| Method / path | 요청 | 성공 |
|---|---|---|
| `GET /{electronicApprovalId}/comments?limit=3&beforeCommentId={id}` | `limit` 선택(1–100), `beforeCommentId` 선택 | `result.resultList`와 `result.comments`에 USER 댓글 페이지, `hasPrevious`, `nextBeforeCommentId` |
| `POST /{electronicApprovalId}/comments` | `{ "content": "...", "parentCommentId": 123 }` (`parentCommentId` 선택) | HTTP 201, `result.item`에 저장된 USER 댓글 |
| `PUT /{electronicApprovalId}/comments/{commentId}` | `{ "content": "..." }` | HTTP 200, `result.item`에 갱신된 USER 댓글 |
| `DELETE /{electronicApprovalId}/comments/{commentId}` | 없음 | HTTP 200, 성공 메시지; 공통 service의 soft delete 동작 유지 |

- 저장은 `owner_type='APPROVAL'`, `owner_id=electronicApprovalId`, `comment_type='USER'`, `event_type=NULL`이다.
- 목록 쿼리, 페이지 계산 및 root count는 USER만 대상으로 한다. 기존 공통 댓글 페이지 Mapper는 같은 owner의 USER/SYSTEM을 모두 반환하므로 approval USER 전용 DAO 조회 또는 동등하게 분리된 조건을 둔다. 기존 공통 댓글 목록 동작은 바꾸지 않는다.
- `POST`는 기존 `CommonCommentService.createComment`의 trimming 및 USER 부모 검증을 재사용하고, 문서 접근을 먼저 검증한다.
- `PUT/DELETE` 전에는 해당 comment ID가 요청 문서에 속한 USER 행인지 확인한다. 공통 댓글 service의 작성자 기반 update/soft-delete 조건을 재사용한다. 갱신 행이 0개이면 성공 응답을 만들지 않는다.

### 댓글 첨부파일

| Method / path | 요청 | 성공 |
|---|---|---|
| `GET /{electronicApprovalId}/comments/{commentId}/attachments` | 없음 | `result.resultList`에 해당 USER 댓글의 파일 목록 |
| `POST /{electronicApprovalId}/comments/{commentId}/attachments` | multipart `file` | HTTP 201, `result.item`에 업로드 메타데이터 |
| `GET /{electronicApprovalId}/comments/{commentId}/attachments/{fileId}/download` | 없음 | 인증된 파일 스트림 |
| `DELETE /{electronicApprovalId}/comments/{commentId}/attachments/{fileId}` | 없음 | HTTP 200, 성공 메시지 |

- 파일 owner는 서버에서 `owner_type='APPROVAL_COMMENT'`, `owner_id=commentId`, `file_usage_type='ATTACHMENT'`, `tenant_id=LoginVO.tenantId`로 설정한다. 업로더는 `LoginVO.id`다.
- 업로드와 삭제는 댓글 작성자, 목록과 다운로드는 문서 참여자에게 허용한다.
- 모든 경로에서 문서 참여 및 `commentId -> (tenant, APPROVAL, electronicApprovalId, USER)` 관계를 검증한다. 파일 읽기/삭제 전 file ID가 `(tenant, APPROVAL_COMMENT, commentId, ATTACHMENT)`에 속하는지 검증한다.
- 댓글 이미지 첨부는 일반 첨부 메타데이터로 표시하고 기존 `CommentThread` 첨부 렌더링 및 인증된 download 경로를 사용한다. 본문 embedded image는 기존 approval embedded-image API를 사용하며 임시 upload token이나 저장소 URL을 문서 HTML에 노출하지 않는다.
- 댓글 생성과 파일 업로드는 별도 요청이다. 업로드 일부가 실패하면 이번 동작에서 이미 업로드한 파일을 전용 삭제 API로 정리하고 원 오류를 사용자에게 표시한다.

## UI 상태 및 오류 처리

- feed/list/detail/comments 각각 loading, empty, error를 구분한다. 기존 상세 패널 로딩 패턴을 재사용한다.
- 댓글 저장/수정/삭제/첨부 업로드·삭제 성공은 기존 toast 패턴, 실패는 오류 메시지와 재시도 가능한 상태를 보인다. 실패를 빈 댓글 목록 또는 성공 응답으로 변환하지 않는다.
- USER 댓글만 `CommentThread`에 전달한다. `isEditable`은 로그인 작성자 비교 결과, 삭제 상태는 soft-delete 표식으로 만든다. SYSTEM 이벤트는 별도 읽기 전용 타임라인에서 렌더한다.
- `CommentThread`에 댓글/대댓글 작성, 댓글 수정/삭제, 이전 페이지 로딩, 첨부 업로드·다운로드·작성자 삭제를 연결한다. 댓글 이미지 첨부는 MIME 기반으로 안전하게 표현하고 다른 origin이나 upload-token URL을 신뢰하지 않는다.
- 기존 결재 action button visibility와 서버 검증은 변경하지 않는다.

## 테스트 및 검증

### 백엔드

- 인증 누락 401, 비참여자/다른 tenant 404, 참가자 조회 허용, 참조자 댓글 허용·결재 액션 거부.
- 생성 주체는 principal이며 owner type/id/comment type/event type은 서버가 고정한다.
- 페이지와 root count에서 SYSTEM이 빠지고 USER만 반환된다. SYSTEM 댓글 수정/삭제/답글 대상으로 사용 거부.
- 교차 문서/tenant parent, comment ID, file ID를 거부한다. 댓글 작성자만 댓글 수정/삭제 및 자기 댓글 첨부 추가/삭제가 가능하다.
- 공통 Comment API의 approval 댓글 수정/삭제가 comment ID 직접 호출로도 거부된다. 공통 File API의 `APPROVAL_COMMENT` owner 목록/업로드 및 file ID 직접 다운로드/삭제가 거부되며 정상 공지 및 비approval 동작은 유지한다.
- 기존 embedded-image authorization, 결재 액션 및 순차 결재 관련 회귀 테스트를 실행한다.

### 프런트엔드

- 목록 행/피드 카드 선택, 우측 panel close/backdrop/Escape, 필터·보기 모드 유지, 상세 loading/error를 검증한다.
- SYSTEM 이벤트와 USER 댓글 분리, 댓글 CRUD/대댓글/이전 페이지, 파일 업로드·다운로드·삭제·이미지 표시 및 오류 상태를 검증한다.
- 기존 승인·반려·보완요청·재상신 액션과 권한 표현을 회귀 검증한다.
- 관련 Vitest와 frontend production build를 실행한다.

### 브라우저

- `frontend/AGENTS.md` 규칙에 따라 기존 S-ERP dev server를 확인/재사용하고 `375px`, `768px`, `1280px`에서 피드/리스트, 상세 overlay, 긴 본문/첨부/댓글, 페이지 가로 overflow를 검사한다.
- 캡처는 `docs/result/20261012/document-approval-workspace/screenshots/`에 저장한다.

## 변경 이력

- 초기 작성일: 2026-10-12
