# 20260917_001 공지사항 오류 수정 상세 사양서

## 1. 개요

본 사양서는 공지사항 페이지의 네 가지 오류 수정과 실제 브라우저 검증 기준을 정의한다.

- 실제 브라우저에서 공지사항 저장, 수정, 삭제가 정상 동작하는지 확인한다.
- 첨부파일 포함 저장, 수정, 삭제를 실제 UI로 검증한다.
- 댓글과 답글의 저장, 수정, 삭제를 실제 UI로 검증한다.
- 댓글 작성 실패 시 로컬 목록이 오염되지 않아야 한다.
- 첨부 포함 저장 후 게시글이 서버 정렬 위치에 표시되고 작성 입력값이 초기화되어야 한다.
- 문제 발생 시 즉시 원인 분석 후 코드 수정과 재검증을 수행한다.

## 2. 요구사항 정의

### 2.1 저장

- 사용자가 공지사항을 작성하면 페이지 목록에 정상 반영되어야 한다.
- 첨부 파일이 포함된 공지사항 역시 정상 저장되어야 한다.
- 댓글과 답글도 정상적으로 저장되어야 한다.
- 게시글 생성 성공 응답에서 `postId`를 확보한 뒤 첨부 업로드를 수행한다.
- 첨부 업로드 중 하나라도 실패하면 성공 상태를 확정하지 않고 업로드된 파일을 정리한 뒤 오류를 표시한다.
- 저장 성공 후 목록은 서버 정렬 기준을 따르며 단순 append로 위치를 결정하지 않는다.
- 저장 성공 후 작성 모달의 제목, 본문, 첨부파일 draft를 빈 값으로 초기화한다.

### 2.2 수정

- 공지사항 수정 시 기존 내용이 로드되고 변경 사항이 저장되어야 한다.
- 첨부 파일 추가/삭제 수정 역시 정상 반영되어야 한다.
- 댓글과 답글 수정 시 해당 내용이 즉시 갱신되어야 한다.

### 2.3 삭제

- 사용자가 삭제 액션을 수행하면 실제 데이터가 사라지거나 목록에서 제거되어야 한다.
- 첨부 파일이 포함된 공지 삭제 시 연관 첨부도 정합성 있게 처리되어야 한다.
- 댓글과 답글 삭제 시 계층 구조가 유지되어야 한다.

### 2.4 예외 처리

- 저장/수정/삭제 실패 시 사용자에게 오류 메시지가 표시되어야 한다.
- 네트워크 또는 API 실패가 발생하더라도 UI가 정지하지 않아야 한다.
- 재조회가 필요한 경우 목록이 새로고침되어 최근 상태를 반영해야 한다.
- 댓글/답글 생성 API 실패 시 로컬 댓글 트리에 항목을 추가하지 않고 입력을 재시도할 수 있어야 한다.

## 3. 화면/UI 요소 요구사항

### 3.1 공지사항 작성/수정 모달

- 제목 입력 영역이 정상 동작해야 한다.
- 본문 에디터 값이 실제 저장될 수 있어야 한다.
- 첨부 파일 선택이 정상 동작해야 한다.
- 저장 시 모달이 닫히고 목록이 갱신되어야 한다.
- 저장 완료 후 새 작성 모달은 빈 제목과 본문으로 시작해야 한다.

### 3.2 공지사항 목록 및 상세

- 목록이 로드되고 새 공지가 즉시 표시되어야 한다.
- 수정된 공지가 다시 목록에서 보이거나 갱신되어야 한다.
- 삭제된 공지가 목록에서 제거되어야 한다.

### 3.3 댓글/답글 UI

- 댓글 작성 폼이 정상 활성화되어야 한다.
- 답글 작성 폼이 정상 활성화되어야 한다.
- 댓글/답글 목록이 계층 구조로 보이며 수정/삭제 액션이 동작해야 한다.

## 4. API/데이터 계약

본 작업은 기존 프론트엔드 서비스 계약을 기준으로 검증한다.

### 4.1 공지사항 API

- `fetchNoticePosts(page, size, keyword)`
- `fetchNoticePostDetail(postId)`
- `createNoticePost(payload)`
- `updateNoticePost(postId, payload)`
- `deleteNoticePost(postId)`
- `uploadNoticeAttachment(postId, file)`
- `deleteNoticeAttachment(boardFileId)`
- `downloadNoticeAttachment(attachment)`

게시글 생성/수정 payload의 주요 필드는 `title`, `contents`, `contentsHtml`, `contentsJson`, `contentsText`, `writerId`, `writerName`, `isNotice`이며, 생성 응답은 `item.postId`를 반환해야 한다.

첨부 업로드는 `POST /api/v1/groupware/boards/notice/posts/{postId}/attachments`의 multipart `file` 필드를 사용한다. 기존 첨부 삭제는 `DELETE /api/v1/groupware/boards/notice/attachments/{boardFileId}?postId={postId}`를 사용한다.

### 4.2 공통 댓글 API

- `GET /api/v1/common/comments?ownerType=NOTICE&ownerId={postId}&limit=3&beforeCommentId={cursor}`
- 초기 조회는 `limit=3`을 사용하고, 추가 조회는 `beforeCommentId` 커서로 이전 루트 댓글을 요청한다.
- 응답은 하위 호환을 위해 `resultList`를 유지하며, 새 계약은 다음 필드를 사용한다.
  - `comments`: 댓글/답글 평면 레코드 배열. 각 레코드의 `parentCommentId`를 기준으로 프론트가 트리를 구성한다.
  - `hasPrevious`: 더 이전 댓글 존재 여부
  - `nextBeforeCommentId`: 다음 이전 조회에 사용할 커서
- `commentCount`는 삭제되지 않은 댓글/답글만 센다.
- 삭제된 부모는 `deletedYn=Y`, `content=[삭제된 댓글입니다.]`인 tombstone 레코드로 반환될 수 있으며, 활성 답글은 해당 부모 아래에 유지된다.
- `createCommonComment(ownerType, ownerId, content, parentCommentId?)`
- 댓글 생성은 `POST /api/v1/common/comments`에 `ownerType=NOTICE`, `ownerId={postId}`, `content`, 선택적 `parentCommentId`를 전달한다.
- 댓글 첨부파일은 `ownerType=NOTICE_COMMENT`, `ownerId={commentId}`를 사용한다. 업로드/조회/다운로드/삭제 모두 동일한 소유 계약을 적용한다.

공지 상세 초기 로드는 게시글, 첨부파일, 댓글 페이지를 조합한 외부 목록 API 한 번으로 제공한다. 저장 후 목록 갱신은 서버 목록 재조회 또는 저장 응답을 서버 정렬 규칙에 맞게 반영하는 방식 중 하나를 사용하되, 임의 append를 완료 기준으로 삼지 않는다.

### 4.3 예상 동작

- 작성 API 성공 시 서버가 결과 item 또는 result 반환한다.
- 수정 API 성공 시 반영된 값이 다시 조회된다.
- 삭제 API 성공 시 목록/상세에서 제거되어야 한다.
- 댓글/답글은 ownerType/ownerId와 parentCommentId가 일관되게 전달된다.
- 댓글 생성 실패 응답은 `showError`로 사용자에게 전달되고 성공 토스트나 로컬 댓글 추가가 발생하지 않는다.

## 5. 예외/에러 기준

### 5.1 필수 에러 대응

- 저장 실패 시 사용자에게 `showError` 메시지가 표시되어야 한다.
- 댓글/답글 저장 실패 시 별도 메시지가 표시되어야 한다.
- 파일 업로드 실패 시 공지 저장 전체가 중단되기 전에 사용자 피드백이 제공되어야 한다.
- 첨부 업로드 실패 시 재시도 가능한 작성 상태를 유지하고, 부분 성공 파일은 정리한다.

### 5.2 재검증 기준

- 동일 시나리오를 다시 수행해 에러가 재발하지 않는지 확인한다.
- 수정 코드는 기능 단위에서 안정적으로 동작해야 한다.

## 6. 구현 원칙

- 기능을 임의로 추가하지 않는다.
- 기존 구조와 API 인터페이스를 우선 유지한다.
- 문제는 실제 브라우저 재현을 통해 확인하고 최소 수정 범위로 해결한다.
- 백엔드 DB/스키마 변경은 필요하지 않다.

## 7. 검증 기준

### 7.1 브라우저 검증

- 저장/수정/삭제 작업을 실제 브라우저에서 수행한다.
- 첨부파일과 댓글/답글을 실제 사용자 흐름으로 확인한다.
- 오류 발생 시 즉시 수정하고 재검증한다.
- 최소 뷰포트는 375px, 768px, 1280px로 한다.
- 저장 성공 후 목록 위치, 모달 제목 초기화, 첨부 표시, 댓글 실패 상태를 브라우저에서 확인한다.

### 7.2 코드 검증

- `cd frontend && npm run build`
- 필요한 관련 테스트 또는 smoke 검증 수행

## 8. 완료 조건

- 공지사항 CRUD 동작이 브라우저에서 정상 동작한다.
- 첨부파일 포함 CRUD 동작이 정상 동작한다.
- 댓글/답글 CRUD 동작이 정상 동작한다.
- 수정 내역과 검증 결과가 결과 문서에 기록된다.
- DB 변경이 없음을 기록한다.
