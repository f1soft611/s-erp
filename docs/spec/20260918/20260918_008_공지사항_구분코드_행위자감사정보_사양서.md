# 20260918_008 공지사항 구분코드 및 행위자 감사정보 상세 사양서

## 1. 데이터 계약

### 공통코드

- 그룹 코드: `NOTICE_GUBUN`
- 그룹 조회: 기존 `/api/v1/co/master/common-code/groups`
- 상세 조회: 기존 `/api/v1/co/master/common-code/groups/{groupId}/items`
- 사용 조건: `useAt = 'Y'`
- 정렬: 기존 공통코드 API의 `sortOrder`
- 저장값: `itemCode`
- 화면 표시값: `itemNm`

프론트 서비스는 그룹 목록에서 `groupCode === 'NOTICE_GUBUN'`을 찾은 뒤 해당 그룹 ID로 상세 항목을 조회한다. 그룹 또는 항목이 없으면 필터에는 전체 항목만 표시하고 작성/수정 저장은 서버 검증 오류로 처리한다.

### 게시글 필드

- Request: `noticeGubunCode`, `title`, 본문 필드, 첨부파일 ID 목록
- Response: `noticeGubunCode`, `noticeGubunName`(조회 시 공통코드 조합 가능), `writerId`, `writerName`, `lastModifiedBy`, `lastModifiedByName`
- 서버는 Request의 `writerId`, `writerName`을 저장하지 않는다.

### 댓글 필드

- Response에 `lastModifiedBy`, `lastModifiedByName`을 추가한다.
- 등록 Request에는 작성자 ID/이름을 두지 않는다.
- 수정·삭제 행위자는 인증 사용자 정보로만 결정한다.

## 2. 화면 사양

### 목록

- 기존 검색 영역에 구분 필터를 추가한다.
- 기본값은 전체이며, 이후 `NOTICE_GUBUN` 상세코드의 `itemNm`을 표시한다.
- 게시글 카드/행에는 구분명과 기존 중요공지 상태를 함께 표시한다.
- 좁은 화면에서는 필터가 다음 줄로 배치되며 가로 스크롤을 만들지 않는다.

### 작성/수정

- 제목 입력 위에 구분 선택 필드를 배치한다.
- 선택지는 전체가 아니라 사용 중인 `NOTICE_GUBUN` 상세코드다.
- 신규 작성 시 선택값을 필수로 검증한다.
- 수정 시 기존 `noticeGubunCode`를 초기 선택값으로 사용한다.
- 작성자 입력 UI가 있더라도 저장 요청에 포함하지 않거나 서버에서 무시한다.

## 3. API 계약

### 공지 목록

- `GET /api/v1/groupware/boards/notice/posts`
- Query: `keyword`, `page`, `size`, `noticeGubunCode`(선택)
- 성공: `200`, `resultList`에 구분 코드와 작성자/최신 행위자 정보 포함

### 공지 등록

- `POST /api/v1/groupware/boards/notice/posts`
- 성공: `201`
- 작성자: `LoginVO.id`, `LoginVO.name`
- 인증 실패: `401`
- 구분 코드 누락/미사용 코드: `400`

### 공지 수정

- `PUT /api/v1/groupware/boards/notice/posts/{postId}`
- 성공: `200`
- 최신 행위자: `LoginVO.id`, `LoginVO.name`
- 인증 실패: `401`, 게시글 없음: `404`

### 공지 삭제

- `DELETE /api/v1/groupware/boards/notice/posts/{postId}`
- 성공: `200`
- 삭제 행위자를 최신 행위자 컬럼에 기록
- 인증 실패: `401`, 게시글 없음: `404`

### 댓글/답글

- `POST /api/v1/common/comments`: 생성 작성자는 `LoginVO.id/name`
- `PUT /api/v1/common/comments/{commentId}`: 수정자 ID 권한을 검사하고 ID/name 기록
- `DELETE /api/v1/common/comments/{commentId}`: 작성자 ID 권한을 검사하고 ID/name 기록
- 인증 실패: `401`, 권한 대상 불일치 또는 없음: `404`, 잘못된 입력: `400`

## 4. DB 사양

### `tb_board_post`

- `notice_gubun_code VARCHAR(50) NULL`
- 기존 `last_modified_by VARCHAR`는 최신 행위자 ID로 사용
- `last_modified_by_name VARCHAR(150) NULL` 추가
- 등록 시 `last_modified_by`와 `last_modified_by_name`은 등록 사용자로 초기화한다.
- 수정/삭제 시 두 컬럼을 현재 로그인 사용자로 갱신한다.

### `tb_common_comment`

- `last_modified_by VARCHAR(100) NULL`
- `last_modified_by_name VARCHAR(150) NULL`
- 등록 시 두 컬럼을 작성자 정보로 초기화한다.
- 수정/삭제 시 두 컬럼을 현재 로그인 사용자로 갱신한다.

## 5. 보안 및 예외

- 테넌트 ID는 기존처럼 `LoginVO.tenantId`를 사용한다.
- 클라이언트가 보낸 작성자/수정자 ID·이름은 신뢰하지 않는다.
- 댓글 수정·삭제의 기존 `writer_id = actorId` 조건을 유지한다.
- 공통코드의 테넌트 범위와 사용 여부를 기존 조회 서비스 기준으로 검증한다.
- 구분 코드가 삭제되거나 사용 중지된 기존 게시글은 코드값을 그대로 보존하고 표시명은 코드값 대체 표시를 사용한다.

## 6. 테스트 기준

- 구분코드 조회·필터링·작성/수정 초기값
- payload 작성자 변조 무시
- 공지 등록/수정/삭제 행위자 저장
- 댓글/답글 등록/수정/삭제 행위자 저장 및 권한 제한
- 375px, 768px, 1280px 화면에서 입력/필터 겹침 없음
