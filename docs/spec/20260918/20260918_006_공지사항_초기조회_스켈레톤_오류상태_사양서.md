## 상태 전이 사양

### 초기 조회

1. 컴포넌트 마운트 시 `isInitialLoading`은 `true`다.
2. `fetchNoticePosts(1, 20, '')`가 완료되기 전까지 `notice-feed-skeleton`을 표시한다.
3. 고정 시간 기반 상태 변경은 사용하지 않는다.
4. API 성공 시 응답을 `toNoticeFeedItem`으로 변환하고 `isInitialLoading`을 `false`로 변경한다.
5. API 실패 시 `errorMessage`를 설정하고 `isInitialLoading`을 `false`로 변경한다.

### 오류 상태

- `errorMessage`가 있고 초기 로딩이 끝난 경우 오류 상태를 표시한다.
- 오류 상태는 전체 화면 높이를 사용하며 `alignItems: center`, `justifyContent: center`로 콘텐츠를 중앙 배치한다.
- 오류 문구는 렌더링하지 않는다.
- `IconButton`의 접근성 이름은 `공지사항 다시 불러오기`로 한다.
- 버튼 클릭 시 `loadNoticePosts()`를 호출한다.

### 재조회

- 재조회 시작 시 `isInitialLoading`을 `true`로 설정하고 오류 상태를 숨긴다.
- 재조회가 끝날 때 성공이면 목록/빈 상태를 표시하고, 실패이면 중앙 재조회 버튼을 다시 표시한다.
- 생성/수정 후 `loadNoticePosts({ silent: true })`는 기존처럼 전체 초기 스켈레톤을 표시하지 않고 새로고침 상태만 사용한다.

## 렌더링 우선순위

1. `isInitialLoading === true`: 기존 스켈레톤
2. 초기 로딩 종료 후 `errorMessage` 존재 및 공지 목록 없음: 중앙 재조회 버튼
3. `noticeItems.length === 0`: 기존 빈 상태
4. 그 외: 기존 공지 목록 및 요약 패널

## API 계약

- 메서드: `GET`
- 엔드포인트: `/api/v1/groupware/boards/notice/posts`
- 요청 쿼리: `page=1`, `size=20`, `keyword=`
- 성공 응답 사용 필드: `resultList: NoticeBoardPostApi[]`
- 실패 처리: API 예외를 화면 오류 상태로 변환하며 백엔드 계약은 변경하지 않는다.

## 권한 및 예외 처리

- 기존 공지사항 접근 권한 및 대시보드 메뉴 권한 처리는 변경하지 않는다.
- API 실패 원문은 사용자 화면에 노출하지 않는다.
- 재조회 버튼은 동일한 목록 API 호출 경로를 사용한다.
- 컴포넌트가 언마운트된 뒤 상태를 변경하지 않도록 기존 effect cleanup 구조를 유지한다.

## 테스트 사양

### 케이스 1: 지연 API 동안 스켈레톤 유지

- `fetchNoticePosts`를 pending 상태로 둔다.
- `notice-feed-skeleton`이 표시되는지 확인한다.
- 타이머 경과만으로 스켈레톤이 제거되지 않는지 확인한다.

### 케이스 2: API 실패 시 중앙 재조회 상태

- `fetchNoticePosts`가 reject 되도록 설정한다.
- 스켈레톤이 제거되는지 확인한다.
- `공지사항 다시 불러오기` 버튼이 표시되는지 확인한다.
- 오류 문구는 표시되지 않는지 확인한다.

### 케이스 3: 재조회 성공

- 첫 조회는 실패시키고 두 번째 조회는 공지 목록을 반환한다.
- 재조회 버튼 클릭 후 API 호출 횟수가 2회가 되는지 확인한다.
- 성공한 공지 제목이 표시되는지 확인한다.
