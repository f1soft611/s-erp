# 공통 Web Push 서비스 상세 사양서

근거: [승인 설계](../../superpowers/specs/2026-11-03-web-push-design.md), [구현 계획](../../plan/20261103/20261103_005_웹푸시_공통서비스_계획서.md), [작업지시서](../../directions/20261103/20261103_005_웹푸시_공통서비스_작업지시서.md).

## 1. 목표와 범위

기존 공통 알림 유형인 `APPROVAL_COMMENT_MENTION`과 `DIRECT_MESSAGE_RECEIVED`를 공통 백엔드 Web Push 서비스가 처리한다. 사용자가 켜기를 직접 선택하고 브라우저 권한을 허용한 기기에만 표준 Web Push를 발송한다. 인앱 알림과 쪽지 저장, 읽음, 보관 동작은 변경하지 않는다.

새 결재 요청·승인·반려 이벤트, 알림 유형별 푸시 설정, 이메일/SMS/모바일 앱 푸시 및 외부 관리형 푸시 사업자는 포함하지 않는다. 후속 업무 알림 확장에서 새 이벤트가 합의되어 공통 알림으로 발행될 때 이 전달 계약을 재사용할 수 있다.

## 2. 현재 구조와 확인된 데이터 근거

- `NotificationServiceImpl.createEvent`는 두 event/source 조합만 허용하며 tenant/recipient 단위 `tb_notification` 행을 삽입한다. PostgreSQL mapper는 `(tenant_id, recipient_user_id, event_type, source_type, source_id)` 충돌을 무시한다.
- `DirectMessageServiceImpl.saveMessage`는 쪽지 저장 transaction에서 `DIRECT_MESSAGE_RECEIVED` 공통 알림을 생성한다.
- `NotificationApiController`의 `ResultVO` 응답 envelope와 `LoginVO` 인증 principal 범위를 따른다.
- 읽기 전용 `s-erp-postgresql-readonly` MCP의 `list_tables`와 `describe_table`로 `tb_notification`, `tb_direct_message`, `tb_direct_message_thread`가 이미 존재하며 notification에 수신 tenant/user, event/source, read/archive/create 시각이 있고 쪽지에 tenant/thread/sender/recipient/content/read 정보를 둔 것을 확인했다. 푸시 관련 테이블은 없었다. 업무 행 데이터는 조회하지 않았다.

## 3. 구성 요소와 전달 흐름

### 3.1 서비스 경계

1. 결재 멘션 및 쪽지는 기존 `NotificationService.createEvent`만 호출한다.
2. 공통 알림 서비스는 notification을 insert한다. INSERT row count가 `1`인 경우에만 생성된 notification ID를 unique tuple `(tenantId, recipientUserId, eventType, sourceType, sourceId)`로 조회하고, 같은 transaction에서 단일 outbox를 enqueue한다. row count가 `0`인 duplicate는 ID 조회와 enqueue를 하지 않는다.
3. Outbox expansion worker가 due 작업을 DB lease로 claim하고 recipient의 현재 활성 구독을 조회해 알림별 기기 delivery를 만든다. 구독이 없으면 outbox를 `NO_RECIPIENT` terminal state로 완료하고 과거 알림을 소급하지 않는다.
4. Delivery worker는 기기별 작업을 별도 lease로 claim하고 DB transaction 밖에서 transport를 호출한다. 성공/실패는 해당 기기 delivery에만 반영한다.
5. 처리 결과가 모든 기기에서 terminal이면 outbox를 `COMPLETED`로 갱신한다. 한 기기 오류는 다른 기기 작업을 차단하지 않는다.

`tb_notification`이 인앱 원본이고, `tb_push_outbox`와 `tb_push_delivery`는 별도 전달 상태다. 푸시 실패는 이미 commit된 알림/쪽지 저장을 rollback하지 않는다. 알림 행과 outbox insert가 같은 transaction에서 원자적으로 성공하지 못하면 전체 notification transaction을 rollback한다.

### 3.2 Exactly-once 한계와 중복 억제

브라우저 Push Service로 보낸 요청은 DB transaction과 원자적으로 commit할 수 없다. 전송이 수락된 직후 응답이 유실되거나 worker가 종료되면 외부 전달 여부를 확정할 수 없어 exactly-once 전달은 보장하지 않는다. DB의 고유 키와 delivery 상태로 명시적인 이중 작업/이중 발송을 억제하고, 전송 결과가 불확실할 때 제한 재시도를 사용한다. Service Worker는 `tag = "s-erp-notification-" + notificationId` 및 `renotify: false`를 지정해 같은 기기의 중복 표시를 교체한다.

### 3.3 Worker 정책

- Outbox 및 delivery poll 주기: 5초, claim 배치 상한: 50건.
- Lease 유효기간: 최소 30초. 만료 lease는 다른 worker가 다시 claim할 수 있다. delivery는 한 건씩 claim하며, transport 준비 후 전송 직전에 lease를 갱신한다. 상태 갱신은 claim token/lease owner가 현재 작업 소유자일 때만 성공한다.
- 최초 전송을 포함해 delivery당 최대 5회 시도한다. 일시적 오류의 재시도 delay는 30초, 2분, 10분, 30분이며 전체 작업은 최초 생성 후 1시간을 지나면 `EXHAUSTED`로 terminal 처리한다.
- HTTP transport timeout은 연결 3초/read 5초와 별도로 전체 요청 deadline 기본 10초(최대 20초)를 적용하며, deadline 만료 시 connection을 disconnect한다. 전체 요청 제한은 최소 delivery lease(30초)보다 짧아야 하며, Web Push TTL은 3600초 이하로 제한한다.
- 일시 오류는 connection timeout/reset, HTTP 408, 429, 5xx만 재시도한다. 기타 4xx는 `PERMANENT_FAILURE`로 처리한다. Retry-After가 존재하면 지정된 간격과 backoff 중 긴 값을 사용하되 1시간 이후 재시도하지 않는다.
- HTTP 404/410은 해당 endpoint 구독을 `INACTIVE`로 전환한다. 401/403은 영구 전송 실패로 기록하고 subscription을 일괄 비활성화하지 않는다.
- 전송 직전 notification이 없거나 보관된 경우 해당 delivery를 `SUPPRESSED` 처리한다. 읽음된 알림도 OS 표시를 생략해 stale push를 줄인다.
- Scheduler는 기존 Spring scheduling 설정을 사용한다. database lease가 중복 실행과 다중 application 인스턴스를 조정한다. 실제 외부 Push Service로부터 받은 응답 외에 OS 표시 성공을 보장하지 않는다.

## 4. 데이터 계약과 migration 초안

실제 DB에 DDL을 실행하지 않는다. migration/change record/rollback은 `backend/DATABASE/20261103` 및 `docs/database/20261103`에 동일하게 작성하고 `docs/database/db-schema.md`를 갱신한다. 구현 전에 MCP로 현재 테이블 목록 및 충돌/제약 계약을 재확인한다.

### 4.1 `tb_push_subscription`

| 컬럼 | 타입/제약 | 의미 |
|---|---|---|
| `subscription_id` | `BIGSERIAL` PK | S-ERP 내부 구독 식별자 |
| `tenant_id` | `BIGINT` NOT NULL, tenant FK | 현재 소유 tenant |
| `user_id` | `BIGINT` NOT NULL, user FK | 인증된 현재 구독 소유자 |
| `endpoint_hash` | `BYTEA` NOT NULL UNIQUE | SHA-256(endpoint); 소유권 조회/중복 방지. 원 endpoint를 대체하지 않음 |
| `endpoint_ciphertext` | `BYTEA` NOT NULL | AES-GCM으로 암호화한 Push endpoint envelope |
| `keys_ciphertext` | `BYTEA` NOT NULL | AES-GCM으로 암호화한 직렬화된 `p256dh`/`auth` 키 |
| `encryption_key_version` | `VARCHAR(40)` NOT NULL | 복호화 key version |
| `status` | `VARCHAR(10)` NOT NULL, `ACTIVE`/`INACTIVE` CHECK | 구독 활성 상태 |
| `created_at`, `updated_at`, `inactive_at` | timestamp | 감사 및 정리 기준 시각 |

동일 endpoint는 tenant/user 전체에서 단 하나만 존재한다. 로그인 사용자가 브라우저의 endpoint/keys를 정상 등록하면 동일 endpoint 행의 owner/암호문을 한 transaction에서 현재 tenant/user로 갱신해 계정 전환 후 이전 사용자가 계속 수신하지 않도록 한다. 다른 `endpoint_hash`를 요청 payload로 제출해 기존 구독을 삭제할 수 없다. 활성 구독은 사용자당 최대 10개다.

### 4.2 `tb_push_outbox`

| 컬럼 | 타입/제약 | 의미 |
|---|---|---|
| `outbox_id` | `BIGSERIAL` PK | expansion 작업 ID |
| `notification_id` | `BIGINT` NOT NULL FK `tb_notification`, UNIQUE | 공통 알림별 최대 하나의 outbox |
| `status` | `VARCHAR(20)` NOT NULL, CHECK | `PENDING`, `PROCESSING`, `EXPANDED`, `NO_RECIPIENT`, `COMPLETED`, `FAILED` |
| `attempt_count` | integer NOT NULL default 0 | expansion claim 오류 횟수 |
| `lease_token` | UUID nullable | 현재 worker 소유 토큰 |
| `lease_until` | timestamp nullable | claim 만료 시각 |
| `created_at`, `updated_at`, `completed_at` | timestamp | 작업 추적 시각 |

### 4.3 `tb_push_delivery`

| 컬럼 | 타입/제약 | 의미 |
|---|---|---|
| `delivery_id` | `BIGSERIAL` PK | 구독 단위 전달 결과 |
| `outbox_id` | `BIGINT` NOT NULL FK `tb_push_outbox` | 대상 공통 알림의 작업 |
| `subscription_id` | `BIGINT` NOT NULL FK `tb_push_subscription` | 대상 브라우저 기기 |
| `(outbox_id, subscription_id)` | UNIQUE | 같은 알림·기기 중복 row 금지 |
| `status` | `VARCHAR(24)` NOT NULL, CHECK | `PENDING`, `PROCESSING`, `RETRY_WAIT`, `SENT`, `PERMANENT_FAILURE`, `EXHAUSTED`, `SUPPRESSED` |
| `attempt_count` | integer NOT NULL default 0 | 실제 전송 시도 횟수 |
| `next_attempt_at` | timestamp nullable | 재시도 시각 |
| `lease_token`, `lease_until` | UUID/timestamp nullable | 동시 worker claim |
| `last_error_code` | `VARCHAR(40)` nullable | endpoint/본문이 없는 고정 오류 분류 |
| `created_at`, `updated_at`, `completed_at` | timestamp | 상태/정리 추적 시각 |

Due claim에는 status와 next-attempt/lease를 지원하는 partial index를 둔다. 알림 외래키/제약은 확인한 현재 PK/삭제 정책과 일치해야 한다. 보존 기간은 terminal delivery/outbox 결과 90일, inactive subscription 90일이다. 활성 구독은 단순히 마지막 사용 시각이 오래되었다는 이유로 삭제하지 않는다. 404/410 또는 명시적 해제만 비활성화 사유로 삼는다. 활성 subscription이 알림 대상에 추가된 뒤 비활성화되면 해당 미전송 delivery는 `SUPPRESSED`로 끝낸다.

## 5. 웹 푸시 라이브러리와 비밀 설정

- 후보 라이브러리: `nl.martijndwars:web-push:5.1.2` (MIT, Java 8 지원, payload 암호화와 VAPID 지원; 공식 저장소 README 및 Maven Central POM 확인: [webpush-java](https://github.com/web-push-libs/webpush-java), [Maven Central](https://central.sonatype.com/artifact/nl.martijndwars/web-push/5.1.2)).
- 검증 결과, `web-push:5.1.2` 공개 POM은 취약 버전인 `jose4j:0.7.9`, `async-http-client:2.12.4`, `httpasyncclient:4.1.5`, Bouncy Castle `bcprov-jdk15on:1.70`과 CLI 전용 `jcommander:1.81`을 선언한다. 런타임에서 이들을 제외하고, Java 8 source/target을 선언한 `jose4j:0.9.7` 및 Java 8 지원 설명을 갖는 `bcprov-jdk18on:1.86`을 직접 고정한다. `jose4j`의 `slf4j-api:2.0.17`도 제외해 애플리케이션의 `slf4j-api:1.7.36`을 유지한다.
- 라이브러리 5.1.2 소스의 `PushService.preparePost(Notification, Encoding)`가 암호화 및 VAPID 요청을 `HttpPost`로 준비함을 확인했다. 이 메서드만 사용하고, 준비된 헤더/암호화 본문을 Java 8 `HttpURLConnection`으로 전달한다. 라이브러리의 `send/sendAsync`를 호출하지 않아 `async-http-client`와 `httpasyncclient`를 실행 트리에 둘 필요가 없으며, 연결/응답 timeout과 redirect 비활성화를 직접 적용한다.
- Maven runtime resolution에서 확인된 관련 버전은 `web-push:5.1.2`, `jose4j:0.9.7`, `bcprov-jdk18on:1.86`, 기존 `httpclient:4.5.14`/`httpcore:4.4.16`, `slf4j-api:1.7.36`이다. `async-http-client`, `httpasyncclient`, `jcommander`, `bcprov-jdk15on`은 resolved runtime에 없다. 이 버전 집합에 대해 OSV Maven query를 확인했으며 알려진 advisory 결과가 없었다. 재현 확인은 변경 시점의 Maven dependency resolution과 OSV querybatch 결과를 기준으로 한다.
- 서버 설정은 `WEB_PUSH_ENABLED`(기본 false), `WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY`, `WEB_PUSH_VAPID_SUBJECT`, `WEB_PUSH_SUBSCRIPTION_ENCRYPTION_KEY`, `WEB_PUSH_SUBSCRIPTION_ENCRYPTION_KEY_VERSION`을 사용한다. 운영 secret 값은 application properties, repository 또는 테스트 로그에 기록하지 않는다. 활성 상태인데 필수 private/encryption key 또는 올바른 subject가 없으면 앱 시작을 실패시킨다.
- VAPID private key는 deploy secret에서만 주입한다. 공개키는 로그인된 클라이언트가 구독할 때 반환할 수 있다. 키 회전 시 이전 encryption key version으로 저장한 구독을 새 key로 재암호화해 완료하기 전 기존 key를 제거하지 않는다. VAPID public/private pair 회전은 클라이언트 신규 구독과 기존 subscription 전송 호환성 확인 절차를 운영 문서에 기록한다.
- 구독 endpoint와 keys는 AES-256-GCM, 96-bit random nonce 및 128-bit authentication tag를 사용하는 versioned envelope로 저장한다. key는 base64url 32-byte로 secret 주입한다. Java 8 런타임에서 알고리즘/키 길이 지원을 시작 시 확인하고, 암호문·nonce·tag를 로그에 쓰지 않는다.

## 6. 인증된 구독 API

Base path: `/api/v1/groupware/push-subscriptions`. 모두 기존 `ResultVO` response envelope를 사용하며 인증 principal로 owner를 결정한다.

### 6.1 상태와 공개키

`GET /status?endpointHash=<64 lowercase hex, optional>`

인증된 사용자의 현재 활성 구독 개수와 기능 상태를 반환한다. `endpointHash`가 있으면 현재 사용자/tenant 소유의 해당 기기 등록 여부와 `subscriptionId`만 응답한다. endpoint hash는 브라우저에서 SHA-256으로 계산하며 원 endpoint를 query/log에 넣지 않는다.

```json
{
  "enabled": true,
  "activeDeviceCount": 2,
  "currentDevice": {
    "subscribed": true,
    "subscriptionId": 18
  },
  "vapidPublicKey": "<base64url-public-key>"
}
```

미등록 hash 또는 query 생략 시 `currentDevice.subscribed=false`, `subscriptionId=null`이다. feature disabled면 `enabled=false`, `vapidPublicKey=null`이며 서버는 outbox에서 `NO_RECIPIENT` 처리한다. endpoint/key 암호문은 반환하지 않는다.

### 6.2 현재 브라우저 구독 등록/갱신

`POST /` body:

```json
{
  "endpoint": "https://<allowed-push-service>/<opaque-token>",
  "keys": {
    "p256dh": "<base64url-public-key>",
    "auth": "<base64url-auth-secret>"
  }
}
```

- server는 `userId`/`tenantId` 필드를 받지 않는다.
- HTTPS endpoint 최대 길이 2048; `p256dh` decoded length 65 bytes; `auth` decoded length 16 bytes; JSON body 최대 8 KiB. 공백/잘못된 base64url/잘못된 P-256 point는 거부한다.
- endpoint host는 아래 정확한 HTTPS provider host 또는 하위 도메인만 허용한다: `fcm.googleapis.com`, `*.push.services.mozilla.com`, `web.push.apple.com`, `*.notify.windows.com`. Userinfo, non-default port, 일반 query/fragment 및 redirect는 거부한다. 단, WNS(`*.notify.windows.com`) endpoint는 provider 발송에 필요한 단일 비어 있지 않은 `token` query parameter만 허용하며 추가·중복 parameter는 거부한다. query token도 endpoint 자격자료로 취급해 로그/응답에 노출하지 않는다. 실제 지원 브라우저 endpoint sample은 비밀을 포함하지 않는 테스트 fixture로 검증하고 운영 중 endpoint provider 변경은 allowlist 업데이트가 필요하다.
- endpoint hash를 unique key로 upsert하고 암호화 자료 및 authenticated principal의 tenant/user를 원자 갱신한다. 각 사용자 최대 10개 활성 endpoint를 transaction 내에서 검증하며 등록은 멱등하다.
- 등록 후 hash 조회 DAO는 `endpointHash`를 명명된 map 값으로 전달하고 MyBatis는 이를 `BINARY`로 바인딩한다. `byte[]`를 직접 전달해 MyBatis의 `array` wrapper와 이름이 충돌하지 않도록 실제 바인딩 회귀 테스트를 적용한다.
- WNS query 허용 판단은 구독 정책과 실제 transport가 공유한다. transport는 허용된 query를 변경·삭제하지 않고 암호화된 POST 목적지에 유지한다. 합성 endpoint로 실제 라이브러리 요청 준비와 연결 경로를 회귀 검증한다.
- 등록 성공 응답은 `{ "registered": true, "subscriptionId": 18 }`. endpoint, keys, 사용자 식별자는 응답에 포함하지 않는다.

### 6.3 현재 사용자 소유 기기 구독 해제

`DELETE /{subscriptionId}`

- subscription id, tenant, principal user 일치 및 `ACTIVE` 상태에서만 비활성화한다. 다른 사용자/tenant id는 정보 누출 방지를 위해 404를 반환한다.
- 성공 시 `{ "unsubscribed": true }`; 반복 해제는 같은 사용자가 소유한 inactive row에 대해 `{ "unsubscribed": true }`로 멱등 응답한다.
- frontend는 브라우저 PushSubscription에서 endpoint를 읽어 SHA-256 hash를 계산하고 `/status`에서 현재 계정 소유 `subscriptionId`를 얻은 뒤 이 API를 호출한다. API 호출이 실패하면 로컬 `unsubscribe()`를 진행하지 않아 사용자에게 등록 해제 실패를 명확히 알린다.

### 6.4 인증, 빈도 및 오류

- 잘못된/없는 로그인은 기존 인증 오류, 잘못된 JSON/길이/endpoint/key는 400, 사용자당 활성 구독 상한 초과는 409/429, 미소유 ID는 404다.
- 상태/등록/해제는 1 사용자당 10회/분으로 제한한다. 재시도 UI는 backend 응답을 성공으로 대체하지 않는다.
- 인증된 `LoginVO`의 positive tenant id와 user id만 사용한다. endpoint host DNS를 resolve할 때 사설, loopback, link-local, multicast, unspecified IP를 차단하고 production egress도 동일 범위의 outbound를 막는다. HTTP redirect는 전송 adapter에서 따르지 않는다.

## 7. 브라우저 동의, 표시와 이동

### 7.1 지원 조건 및 등록

- HTTPS 또는 localhost secure context, `navigator.serviceWorker`, `PushManager`, `Notification`, Web Crypto SHA-256을 확인한다. 빠진 capability가 있으면 미지원 상태와 이유를 안내한다.
- 진입/로그인/알림 도착 시 권한 prompt를 표시하지 않는다. 설정 UI의 명시적 “이 기기에서 웹 푸시 켜기” 클릭에서만 `Notification.requestPermission()`을 호출한다.
- 권한이 `granted`일 때 `/sw.js`를 root scope로 등록하고, `pushManager.getSubscription()` 결과가 없을 때만 server public VAPID key로 `subscribe({ userVisibleOnly: true })`한다.
- API 등록이 실패해 새 browser subscription을 만들었던 경우 `unsubscribe()`를 best-effort 호출한다. 이미 존재하던 local subscription은 유지하고 오류를 표시해 재시도할 수 있게 한다.
- 이미 존재하는 endpoint를 다른 계정이 명시적으로 활성화하면 backend upsert가 owner를 현재 사용자로 이전한다. 자동 로그인/계정 복원만으로는 POST 등록을 호출하지 않는다.
- 앱의 끄기 동작은 현재 로그인 사용자가 소유하는 endpoint만 backend에서 먼저 deactivate하고 성공 후 browser unsubscribe를 한다. 브라우저 설정에서 permission이 외부 취소되어 서버가 구독을 직접 찾을 수 없는 경우 실제 push 404/410 응답으로 비활성화한다.

### 7.2 반응형 설정 UI

`ProfileSettingsPage.tsx`에 웹 푸시 섹션을 추가한다. 사용자 이름/부서/이미지 정보와 분리하고 유형별 알림 선택은 제공하지 않는다.

- 상태: loading, 이 브라우저에서 켜짐, 꺼짐, 브라우저 권한 차단, 미지원, API/등록 실패.
- 사용자가 켜기/끄기를 누르면 즉시 busy state, 실패는 오류 Alert, 성공은 현재 기기 상태와 active device count 갱신.
- 권한이 denied면 자동으로 prompt를 재호출하지 않고 브라우저 설정에서 허용해야 한다고 안내한다.
- 375px, 768px, 1280px에서 버튼/설명이 줄 바꿈되고 페이지 가로 overflow가 없다. profile 저장/취소와 무관하게 푸시 설정 저장이 독립한다.

### 7.3 Service Worker payload 및 click contract

Server push payload JSON은 정확히 다음 값만 가진다.

```json
{
  "notificationId": 12345,
  "kind": "notification"
}
```

title/body/icon은 SW 내부 상수이며 “새 업무 알림이 도착했습니다”처럼 고정된 일반 문구를 사용한다. `title`, `summary`, `content`, `sourceId`, user/tenant, endpoint, key 또는 caller URL은 payload에서 허용하지 않는다.

SW는 positive safe integer `notificationId` 외 값을 거부한다. 알림 클릭은 arbitrary URL을 읽지 않고 동일 origin의 `/groupware/notifications?pushNotificationId=<id>` 고정 경로만 열거나 기존 앱 창을 이 주소로 focus/navigate한다.

`NotificationInboxPage`는 이 query parameter를 읽어 기존 `markNotificationRead(id)` API를 호출한다. API가 owner-scoped notification을 반환하면 기존 `resolveNotificationPath(item)`로 문서 멘션/쪽지 대화 이동을 결정한다. 반환된 source/target을 클라이언트에서 다시 인증된 상세 API로 조회하고, 상세 화면은 현재 권한을 확인한다. 읽음 API가 401/404이거나 item이 invalid면 notification inbox 기본 화면을 유지한다. 외부 URL을 실행하지 않는다.

알림 클릭으로 공통 notification을 읽음 처리할 수 있지만 쪽지 메시지 read state를 변경하지 않는다. 쪽지 읽음 처리는 기존 대화 API 흐름만 수행한다.

## 8. 오류 및 개인정보 처리

- 사용자 거부, 미지원 capability, 만료 구독은 인앱 알림을 영향하지 않는다.
- Web Push 404/410은 단일 subscription 비활성화; 408/429/5xx/network timeout은 제한 재시도; 영구 4xx는 terminal 실패.
- HTTP error body, URI, VAPID credentials, subscription endpoint/keys, 알림 title/summary 및 쪽지 본문을 log/metric/trace에 남기지 않는다. 마지막 오류는 고정된 category code만 기록한다.
- Push endpoint 원문과 key는 저장된 AES-GCM envelope로만 유지한다. endpoint hash는 lowercase hex API query에서만 허용하고 URI query/log에 실제 endpoint를 허용하지 않는다.
- terminal status retention 90일 뒤 outbox/delivery 이력을 삭제할 수 있다. 구독 해제/404/410 뒤 90일이 지난 inactive subscription만 purge한다. 활성 endpoint는 dormant 기간으로 purge하지 않는다.

## 9. 테스트와 완료 기준

### Backend

- tenant/user principal 격리, endpoint allowlist/invalid address/redirect 제한, P-256/auth 크기 검증, limit, upsert idempotency, 소유권 transfer 및 다른 사용자의 해제 404를 검증한다.
- notification 신규 INSERT→같은 transaction outbox, rollback 원자성, unique duplicate→enqueue 없음, realtime 기존 동작 유지, 기존 두 event type만 허용을 검증한다.
- 2개 worker claim race, lease 만료 reclaim, outbox expansion, 구독 없는 상태, 다중 endpoint 독립 delivery, attempt/backoff 한도, 404/410, 영구 4xx, timeout/429/5xx, archived/read suppression, terminal cleanup을 검증한다.
- library transport은 mock server/adapter test에서 VAPID/payload, HTTPS allowlist, redirect 차단, timeout, response classification, 개인정보 미로그를 검증한다. 테스트에서 real Push Service로 보내지 않는다.
- 신규 운영 Java는 Java 8 문법/API로 유지하고 `javac --release 8` 또는 JDK 8 compile을 실행한다.

### Frontend

- 설정 진입 시 permission prompt가 발생하지 않고 사용자 클릭에서만 prompt/구독이 생성되는지 확인한다.
- denied/unsupported/error, 중복 enable, 기기별 status/hash, API 등록 실패 cleanup, 현재 기기 해제와 계정 전환 시 owner isolation을 테스트한다.
- SW payload schema, fixed generic copy, notification tag/renotify, invalid ID 거부, fixed same-origin click, unknown URL 거부를 단위 테스트한다.
- 클릭 query 처리에서 owner read API failure는 inbox fallback, 유효한 문서/쪽지 알림은 기존 resolver 경로, 쪽지 read API는 호출되지 않음을 확인한다.
- frontend build, 관련 Vitest, changed-file oxlint 및 실제 Chromium 브라우저를 375px/768px/1280px에서 실행한다. 실 browser smoke는 test synthetic API/PushManager만 이용하며 실제 credentials/DB/Push Service를 사용하지 않는다.
