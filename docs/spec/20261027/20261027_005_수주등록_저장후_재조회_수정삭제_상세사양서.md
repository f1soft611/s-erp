## 1. API

공통: `@AuthenticationPrincipal LoginVO` 의 테넌트/사용자만 사용한다. 인증 문맥이 없으면 401. 모든 SQL 은 `tenant_id` 조건을 포함하고, 헤더는 `use_at = 'Y'` 인 건만 대상으로 한다. 응답은 `ResultVoHelper.buildFromMap` 공통 봉투(`result.item`, `result.message`)를 사용한다.

### 1.1 `GET /api/v1/sales/orders/{salesOrderId}` — 수주 단건 조회

- 200: `item` = `SalesOrderVO`
  - 헤더 필드 + `customerCode`, `customerName`
  - `details[]` = `SalesOrderDetailVO` + `materialCode`, `materialName`, `line_no` 오름차순
- 404: 없거나 다른 테넌트이거나 삭제(`use_at='N'`)된 수주. 메시지 `수주를 찾을 수 없습니다.`

### 1.2 `PUT /api/v1/sales/orders/{salesOrderId}` — 수주 수정

- 요청: 등록과 동일한 `SalesOrderCreateRequestVO`. 검증 규칙(필수값, 길이, 금액 정밀도, 테넌트 거래처/품목 존재)도 등록과 같다.
- 수정 가능 조건: `status = '수주등록'` 이고 상세 `shipped_qty > 0` 인 행이 없다. 조건 위반 시 409 `출하가 진행되었거나 수주등록 상태가 아닌 수주는 수정/삭제할 수 없습니다.`
- 처리 (단일 트랜잭션):
  1. 헤더 `order_dt, customer_id, quot_no, delivery_dt, delivery_place, delivery_method, total_amt, remark, updated_by, updated_at=now()` 갱신. 수주번호(`order_no`)는 변경하지 않는다.
  2. 상세는 기존 행 전체 삭제 후 요청 순서대로 `line_no` 1부터 재등록한다 (출하 전 상태만 허용하므로 출하 이력 손실 없음, `UNIQUE(sales_order_id, line_no)` 충돌 없음).
- 200: `item` = 재조회한 `SalesOrderVO`, `message` = `수주가 성공적으로 수정되었습니다.`
- 400/404/409 는 위 규칙을 따른다.

### 1.3 `DELETE /api/v1/sales/orders/{salesOrderId}` — 수주 삭제

- 수정과 같은 가능 조건(409)과 존재 조건(404)을 적용한다.
- 헤더 `use_at = 'N'`, `updated_by`, `updated_at = now()` 소프트 삭제. 상세 테이블에는 `use_at` 이 없으므로 상세 행은 유지되며 헤더 기준으로 조회에서 제외된다.
- 200: `message` = `수주가 성공적으로 삭제되었습니다.`

## 2. 화면 동작

### 2.1 모드

| 모드 | 조건 | 수주번호 필드 | 수주상태 필드 |
| --- | --- | --- | --- |
| 신규 | 불러온 수주 없음 | `저장 시 자동 채번` | `수주등록` |
| 수정 | 저장 후 재조회된 수주 있음 | 조회된 `orderNo` | 조회된 `status` |

### 2.2 저장

- 신규 모드: `POST` 성공 → `GET /{salesOrderId}` 로 재조회 → 헤더/상세 그리드를 조회 결과로 재세팅 → 수정 모드 전환. 안내: `수주가 저장되었습니다. 수주번호: {orderNo}`
- 수정 모드: `PUT` 성공 → 응답 수주로 재세팅. 안내: `수주가 수정되었습니다. 수주번호: {orderNo}`
- 재세팅 후 미저장 변경 기준(baseline)은 조회된 값이다. 변경이 없으면 `저장` 버튼은 비활성, 이탈 확인창도 뜨지 않는다.
- 저장 후 재조회가 실패하면 오류 `수주는 저장되었지만 다시 불러오지 못했습니다. 수주번호: {orderNo}` 를 표시하고 입력을 잠근다. 사용자는 `신규` 로 새 입력을 시작한다.

### 2.3 삭제

- `삭제` 버튼: 삭제 권한(`delete`)이 있을 때 표시, 수정 모드이며 수정 가능 상태일 때만 활성.
- 클릭 시 `수주번호 {orderNo} 을(를) 삭제하시겠습니까?` 확인. 취소하면 아무 것도 하지 않는다.
- 성공 시 상단/하단을 신규 상태로 초기화하고 안내 `수주가 삭제되었습니다. 수주번호: {orderNo}` 를 표시한다.

### 2.4 신규

- `신규` 버튼: 쓰기 권한(`create || update`)이 있을 때만 표시, 저장/삭제 진행 중에는 비활성. 액션 영역 맨 앞에 둔다.
- 미저장 변경이 있으면 `저장되지 않은 수주 내용이 있습니다. 신규로 초기화하면 입력 내용이 사라집니다. 계속하시겠습니까?` 확인. 취소 시 유지.
- 초기화 대상: 수주일자(오늘), 거래처, 견적번호, 납기일자, 납품장소, 배송방법, 비고, 상세 그리드 행/선택/검증 표시, 금액 합계, 검증 오류, 오류/안내 메시지, 수주번호/상태 표시.

### 2.5 권한

| 버튼 | 표시 조건 | 활성 조건 |
| --- | --- | --- |
| 신규 | `create \|\| update` | 저장/삭제 중이 아님 |
| 상세 행 추가 / 선택 행 삭제 / 저장 | `create \|\| update` | 입력 가능 상태 (신규 모드는 `create`, 수정 모드는 `update` + 수정 가능 상태) |
| 삭제 | `delete` | 수정 모드 + 수정 가능 상태 |

`DashboardContent` 는 메뉴 권한(`selectedMenuPermissions`)을 수주등록 화면에 전달한다.

## 3. 검증 기준

1. 저장 후 GET 재조회 결과(거래처 코드/명, 품목 코드/명, 수량/단가/금액)가 화면에 재세팅된다.
2. 수정 모드에서 값을 바꾸고 저장하면 PUT 이 호출되고 POST 는 다시 호출되지 않는다.
3. 삭제 확인 후 DELETE 가 호출되고 화면이 신규 상태가 된다.
4. `신규` 클릭 시 상단/하단이 초기화되고, 미저장 변경이 있을 때만 확인창이 뜬다.
5. 쓰기 권한이 없으면 `신규`/`저장` 이 보이지 않고, 삭제 권한이 없으면 `삭제` 가 보이지 않는다.
6. 백엔드: 다른 테넌트/삭제된 수주 404, 출하 진행/상태 변경 수주 409, 수정 시 상세 재등록과 헤더 갱신, 삭제 시 소프트 삭제.
