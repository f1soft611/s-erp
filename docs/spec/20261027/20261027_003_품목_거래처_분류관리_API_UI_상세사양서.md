## API 계약

분류 컨트롤러의 메뉴 경로 분리 및 분류 테스트 코드는 `backend/pom.xml`의 source/target 1.8 API와 호환되게 구현한다. 이 호환 보완은 API·권한·DB 계약이나 프로젝트 JDK 설정을 변경하지 않는다.

Base path: `/api/v1/co/master/classifications`

| Method | Path | 요청 | 응답 |
|---|---|---|---|
| GET | `/items` | 없음 | `result.resultList: ClassificationVO[]` |
| POST | `/items` | `{name, parentId?, sortSeq?, useAt?}` | 201, `result.item` |
| PUT | `/items/{id}` | `{name, sortSeq?, useAt}` | `result.item` |
| GET | `/partners` | 없음 | `result.resultList: ClassificationVO[]` |
| POST | `/partners` | `{name, parentId?, sortSeq?, useAt?}` | 201, `result.item` |
| PUT | `/partners/{id}` | `{name, sortSeq?, useAt}` | `result.item` |

`ClassificationVO`: `id: Long`, `name: String`, `level: Integer`, `parentId: Long?`, `sortSeq: Integer`, `useAt: String`. API는 tenant ID나 감사 필드를 응답하지 않는다. 모든 쓰기 요청에서 `created_by`/`updated_by`는 인증 사용자 ID, 생성/수정 시간은 DB timestamp를 사용한다.

GET은 해당 업무 메뉴에서 READ/CREATE/UPDATE 중 하나 이상 권한이 있는 사용자만 호출할 수 있다. POST는 품목관리 또는 거래처관리 메뉴의 CREATE 권한, PUT은 해당 메뉴의 UPDATE 권한을 서버에서 확인한다. 검증은 `SystemMenuService.getMyMenuTree`가 계산한 사용자 메뉴 권한을 이용하며, 분류 종류별 메뉴 키는 프론트엔드와 같은 `/co/materials` 및 `/co/customers` 경로의 마지막 세그먼트로 매칭한다. tenant-admin 역할을 별도로 요구하지 않는다. 모든 DAO method에 인증 tenant ID를 전달한다. tenant ID를 클라이언트가 지정할 수 있는 필드는 두지 않는다.

POST는 부모가 없으면 level 1, 부모가 있으면 부모 level + 1을 저장한다. 품목 최대 level은 3, 거래처는 2다. 부모는 현재 tenant의 활성 row여야 한다. 자식 생성은 최대 레벨 아래에서 거부한다. 부모 검증 시 해당 부모 row를 transaction 안에서 잠가 부모 비활성화와 자식 등록 경합을 막는다. PUT은 부모/레벨을 받지 않아 계층 이동이 불가능하다. 활성 자식이 있는 노드는 `useAt=N`으로 바꿀 수 없다. 비활성 row의 재활성화는 활성 부모가 있는지 확인한다. 비활성화 시 대상 row를 transaction 안에서 잠가 활성 자식 검사와 자식 등록이 동시에 성공하지 않도록 한다.

검증: name trim 후 1~50자, `sortSeq`는 0 이상 정수, `useAt`은 정확히 `Y` 또는 `N`. 생략된 `sortSeq`는 0, `useAt`은 `Y`로 기본 설정한다. 중복 이름은 DB 초안상 unique 제약이 없으므로 별도 제한하지 않는다.

잘못된 payload/계층 규칙은 기존 `ResultVO` INPUT_CHECK_ERROR의 HTTP 400, 해당 메뉴 권한 없는 요청은 HTTP 403, 다른 tenant 또는 존재하지 않는 ID는 HTTP 404. DB 오류는 정상 성공으로 변환하지 않는다.

## Mapper/데이터 규칙

- type 경로는 서버 enum으로 `ITEM` 또는 `PARTNER`로 고정하고 외부 문자열을 SQL table/column identifier로 바인딩하지 않는다.
- `ITEM`은 `tb_cls_item(item_cls_id, tenant_id, item_cls_nm, item_cls_lvl, upper_item_cls_id, sort_seq, use_at, created_by, created_at, updated_by, updated_at)`.
- `PARTNER`는 `tb_cls_partner(partner_cls_id, tenant_id, partner_cls_nm, partner_cls_lvl, upper_partner_cls_id, sort_seq, use_at, created_by, created_at, updated_by, updated_at)`.
- 생성 ID는 PostgreSQL `RETURNING` 또는 MyBatis generated key 기존 프로젝트 패턴으로 회수한다.
- update와 parent lookup은 항상 `tenant_id` 조건을 사용한다. update 0 rows는 404로 응답한다.
- 목록은 `tenant_id`, `parent ID NULLS FIRST`, `sort_seq`, ID 순으로 반환한다.
- 물리 DELETE SQL/endpoint는 작성하지 않는다.

## UI 계약

- 17:46 후속 요청: 저장 버튼은 기존 권한/로딩/오류 조건 외에 `dirty || editorDirty`일 때만 활성화한다. 초기 조회/원복/저장 완료 시 비활성화하고 신규 행 또는 셀 변경 시 활성화한다. 편집 중 변경값도 저장 가능하며 부분 실패 시 남은 변경행은 재시도한다.
- 편집 중 저장을 누르면 pointerdown에서 셀 편집을 확정하고 변경 상태를 동기 반영한다. 편집 종료의 일시 비활성화로 첫 클릭이 유실되지 않으며 실제 API 저장은 기존 click 경로로만 수행한다.

- 17:30 후속 요청: 저장부터 저장 후 목록 재조회 완료까지 트리 전체 로딩은 표시하지 않는다. 기존 행을 표시하고 `저장` 버튼의 startIcon에 `AppLoadingSpinner size={16} color="inherit"`만 표시한다. 접근 가능한 로딩 이름은 `분류 저장 중`이다. 최초 조회/저장 외 수동 재조회는 기존 트리 로딩을 유지하며 편집·추가·중복 저장·닫기 차단은 저장 완료까지 유지한다.

- 분류 설정 버튼은 기존 헤더 actions에 넣고 `create || update` 메뉴 권한 조건에서 노출한다. 별도 `isTenantAdmin` 조건은 추가하지 않는다.
- 공통 Dialog props: `open`, `kind ('item'|'partner')`, `canCreate`, `canUpdate`, `onClose`.
- 내부 팝업은 `CommonDialog`를 재사용한다. title 아래 description은 `최대 {maxLevel}단계 · 셀을 더블클릭하여 편집한 뒤 저장하세요. 삭제 대신 사용여부를 해제하세요.`로 표시한다. 품목은 3단계, 거래처는 2단계다.
- 헤더 우측 상단 공통 X와 하단 닫기는 동일한 미저장 확인 경로를 호출하며 저장 중 닫기는 차단한다. 최상위 추가/하위 추가는 본문 그리드 위 우측 정렬하고 좁은 화면은 줄바꿈을 허용한다.
- Dialog 열 때 목록 fetch, loading skeleton/progress, 실패 메시지, 재조회 버튼을 제공한다.
- 사용자 변경 요청에 따라 목록/상세 입력 폼은 제거한다. 공통 `F1Tree`에서 `id`/`parentId` 계층을 표시하고 분류명·정렬순서·사용여부를 셀에서 직접 편집한다. 이 UI 계약이 최초 승인 설계의 목록/상세 폼 설명보다 우선한다.
- 새 root 추가 및 선택한 노드의 하위 추가를 제공한다. 최대 레벨은 하위 추가가 없고 화면에 표시된 최대 깊이를 명시한다.
- 여러 행의 편집 내용을 유지하면서 선택과 추가를 계속할 수 있다. 저장은 변경된 모든 행에 적용한다. 새 행은 음수 임시 ID를 가지며 저장되지 않은 부모 아래에도 하위 행을 추가할 수 있다.
- 저장 전 전체 변경 행의 분류명/정렬순서를 검증하고 사용 중인 자식의 상위 분류 및 신규 행의 부모가 사용 상태인지 확인한다. 기존 활성화/수정은 상위부터, 신규 생성은 부모부터, 기존 비활성화는 하위부터 단건 API로 순차 저장한다.
- 단건 API이므로 전체 원자적 저장은 보장하지 않는다. 중간 실패 시 성공 응답을 로컬 기준값에 반영하고 임시 부모 ID를 실제 ID로 교체한 뒤 나머지 변경값을 유지한다. 재저장 시 성공한 행은 제외한다.
- 전체 저장 성공 후 API 목록을 다시 가져와 선택/편집 내용을 갱신한다. 저장 성공 후 재조회만 실패한 경우 편집/저장을 차단하고 재조회로 복구해 중복 등록을 방지한다.
- 편집 중 닫기는 기존 공통 확인창으로 변경사항 폐기 여부를 확인한다. 창 닫기/새로고침의 미저장 보호도 유지한다. 행 선택과 추가에서는 편집값을 버리지 않으므로 확인창을 열지 않는다.
- CREATE 권한은 root/하위 추가를, UPDATE 권한은 기존 분류 편집/저장을 허용한다. 두 권한이 모두 없으면 설정 action을 노출하지 않는다.
- Dialog는 공통 `CommonDialog`의 기본 md 크기(820px 기준, 테두리 별도), 600px 미만에서는 full-screen 및 세로 배치를 사용한다. 내용 영역에만 overflow를 주고 viewport 폭을 넘기지 않는다.
- 그리드는 팝업 너비를 초과하지 않고 좁은 화면에서는 그리드 내부 가로 스크롤을 사용한다. 우클릭 추가/복제/삭제는 사용하지 않아 깊이·활성 상태·권한 검증을 우회하지 못하게 한다. 물리 삭제는 제공하지 않는다.
- master row 저장 데이터와 화면은 변경하지 않는다.

## 테스트 기준

- backend controller: 2 도메인의 GET 경로, tenant 전달, 메뉴 READ/CREATE/UPDATE 권한 검증, 비관리자여도 유효 권한이면 허용, 권한 없는 사용자는 403, 유효성 오류 400, 타 tenant ID 404.
- backend service: 레벨 생성, 최대 깊이/비활성 부모 거부, 다른 tenant 부모 거부, 잘못된 이름/정렬/useAt, active child 비활성화 거부, parent immutable update.
- frontend service: endpoints and DTO encode/decode.
- frontend dialog: loading/error/retry, root/child 생성, 선택 edit, save/reload, canEdit false, 품목/거래처 최대 레벨.
- frontend page: 각 페이지에 올바른 이름의 action이 있고 CREATE/UPDATE 메뉴 권한이 없으면 숨김. dialog의 추가/수정 control도 권한별로 제한.
- browser checks at 375, 768, and 1280 widths; no viewport horizontal overflow.

## 배포 및 검증 제한

- `20261027_002` migration은 미적용 상태이며 이 구현에서는 실행하지 않는다.
