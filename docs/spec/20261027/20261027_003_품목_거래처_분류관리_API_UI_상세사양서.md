## API 계약

Base path: `/api/v1/co/master/classifications`

| Method | Path | 요청 | 응답 |
|---|---|---|---|
| GET | `/items` | 없음 | `result.resultList: ClassificationVO[]` |
| POST | `/items` | `{name, parentId?, sortSeq?, useAt?}` | 201, `result.item` |
| PUT | `/items/{id}` | `{name, sortSeq?, useAt}` | `result.item` |
| GET | `/partners` | 없음 | `result.resultList: ClassificationVO[]` |
| POST | `/partners` | `{name, parentId?, sortSeq?, useAt?}` | 201, `result.item` |
| PUT | `/partners/{id}` | `{name, sortSeq?, useAt}` | `result.item` |

`ClassificationVO`: `id: Long`, `name: String`, `level: Integer`, `parentId: Long?`, `sortSeq: Integer`, `useAt: String`. API는 tenant ID나 감사 필드를 응답하지 않는다. 모든 쓰기 요청에서 `created_by`/`updated_by`는 인증 사용자 ID, 생성/수정 시간은 DB timestamp를 사용한다.

GET은 인증 사용자가 호출할 수 있다. POST/PUT은 `EgovAccessControlHelper.isTenantAdmin(user)`가 true여야 한다. 모든 DAO method에 인증 tenant ID를 전달한다. tenant ID를 클라이언트가 지정할 수 있는 필드는 두지 않는다.

POST는 부모가 없으면 level 1, 부모가 있으면 부모 level + 1을 저장한다. 품목 최대 level은 3, 거래처는 2다. 부모는 현재 tenant의 활성 row여야 한다. 자식 생성은 최대 레벨 아래에서 거부한다. PUT은 부모/레벨을 받지 않아 계층 이동이 불가능하다. 활성 자식이 있는 노드는 `useAt=N`으로 바꿀 수 없다. 비활성 row의 재활성화는 활성 부모가 있는지 확인한다.

검증: name trim 후 1~50자, `sortSeq`는 0 이상 정수, `useAt`은 정확히 `Y` 또는 `N`. 생략된 `sortSeq`는 0, `useAt`은 `Y`로 기본 설정한다. 중복 이름은 DB 초안상 unique 제약이 없으므로 별도 제한하지 않는다.

잘못된 payload/계층 규칙은 기존 `ResultVO` INPUT_CHECK_ERROR의 HTTP 400, tenant 관리자 아닌 쓰기는 HTTP 403, 다른 tenant 또는 존재하지 않는 ID는 HTTP 404. DB 오류는 정상 성공으로 변환하지 않는다.

## Mapper/데이터 규칙

- type 경로는 서버 enum으로 `ITEM` 또는 `PARTNER`로 고정하고 외부 문자열을 SQL table/column identifier로 바인딩하지 않는다.
- `ITEM`은 `tb_cls_item(item_cls_id, tenant_id, item_cls_nm, item_cls_lvl, upper_item_cls_id, sort_seq, use_at, created_by, created_at, updated_by, updated_at)`.
- `PARTNER`는 `tb_cls_partner(partner_cls_id, tenant_id, partner_cls_nm, partner_cls_lvl, upper_partner_cls_id, sort_seq, use_at, created_by, created_at, updated_by, updated_at)`.
- 생성 ID는 PostgreSQL `RETURNING` 또는 MyBatis generated key 기존 프로젝트 패턴으로 회수한다.
- update와 parent lookup은 항상 `tenant_id` 조건을 사용한다. update 0 rows는 404로 응답한다.
- 목록은 `tenant_id`, `parent ID NULLS FIRST`, `sort_seq`, ID 순으로 반환한다.
- 물리 DELETE SQL/endpoint는 작성하지 않는다.

## UI 계약

- 분류 설정 버튼은 기존 헤더 actions에 넣고 `isTenantAdmin && (create || update)` 조건에서 노출한다.
- 공통 Dialog props: `open`, `kind ('item'|'partner')`, `canEdit`, `onClose`.
- Dialog 열 때 목록 fetch, loading skeleton/progress, 실패 메시지, 재조회 버튼을 제공한다.
- hierarchy는 부모 우선으로 렌더링하고 하위 row에 레벨 들여쓰기를 적용한다. 선택한 분류 편집 영역에서 이름/정렬순서/사용여부를 수정한다.
- 새 root 추가 및 선택한 노드의 하위 추가를 제공한다. 최대 레벨은 하위 추가가 없고 화면에 표시된 최대 깊이를 명시한다.
- 저장 성공 후 API 목록을 다시 가져와 선택/편집 내용을 갱신한다. 오류 시 편집값을 유지하며 오류 메시지를 표시한다.
- 쓰기 권한이 없으면 보기만 가능하고 저장/추가 control은 표시하지 않는다.
- Dialog는 `fullWidth`, desktop max width `md`, 600px 미만에서는 full-screen 및 세로 배치를 사용한다. 내용 영역에만 overflow를 주고 viewport 폭을 넘기지 않는다.
- master row 저장 데이터와 화면은 변경하지 않는다.

## 테스트 기준

- backend controller: 2 도메인의 GET 경로, tenant 전달, admin 쓰기 접근, non-admin 403, 유효성 오류 400, 타 tenant ID 404.
- backend service: 레벨 생성, 최대 깊이/비활성 부모 거부, 다른 tenant 부모 거부, 잘못된 이름/정렬/useAt, active child 비활성화 거부, parent immutable update.
- frontend service: endpoints and DTO encode/decode.
- frontend dialog: loading/error/retry, root/child 생성, 선택 edit, save/reload, canEdit false, 품목/거래처 최대 레벨.
- frontend page: 각 페이지에 올바른 이름의 action이 있고 권한이 없으면 숨김.
- browser checks at 375, 768, and 1280 widths; no viewport horizontal overflow.

## 배포 및 검증 제한

- `20261027_002` migration은 미적용 상태이며 이 구현에서는 실행하지 않는다.

- DB 통합 테스트는 미수행이며 결과 문서에서 backend mock/unit 검증과 구분한다.
