## 1. API 계약

### 1.1 Route 및 응답

- Method/path: `POST /api/v1/sales/orders`
- 인증 principal: `@AuthenticationPrincipal LoginVO`
- 성공 HTTP status: `201 Created`
- 성공 body: 기존 `ResultVO` envelope의 `result.item` 안에 생성된 주문 반환
- 인증 principal, 입력, 참조 검증, 번호 생성 또는 DB 쓰기가 실패하면
  non-2xx 오류를 반환한다. 성공 형태의 fallback은 허용하지 않는다.

### 1.2 요청 DTO

```json
{
  "orderDt": "2026-10-27",
  "customerId": 1,
  "quotNo": null,
  "deliveryDt": null,
  "deliveryPlace": null,
  "deliveryMethod": null,
  "remark": null,
  "details": [
    {
      "materialId": 1,
      "orderQty": 2.00,
      "unitPrice": 100.00,
      "vatAmt": 20.00,
      "deliveryDt": null
    }
  ]
}
```

요청 허용 항목:

- Header: `orderDt`, `customerId`, `quotNo`, `deliveryDt`,
  `deliveryPlace`, `deliveryMethod`, `remark`
- Detail: `materialId`, `orderQty`, `unitPrice`, 선택 값 `vatAmt`,
  선택 값 `deliveryDt`

다음 항목은 요청에서 받지 않으며 보내더라도 저장 기준으로 신뢰하지 않는다:
`tenantId`, `createdBy`, `orderNo`, header/detail ID, `status`, `useAt`,
`lineNo`, `shippedQty`, `lineStatus`, `supplyAmt`, `totalAmt`.

### 1.3 응답

생성 응답의 `item`에는 최소 다음 저장값이 포함된다:

- `salesOrderId`, `tenantId`, `orderNo`, `orderDt`, `customerId`
- 저장된 헤더 `totalAmt`
- 상세별 `salesOrderDetailId`, `lineNo`, `materialId`, `orderQty`,
  `unitPrice`, `supplyAmt`, `vatAmt`, `totalAmt`, `deliveryDt`

응답은 저장된 서버 계산 결과와 DB 발급 ID를 나타낸다.

## 2. 인증 및 테넌트 경계

- `LoginVO` 자체, `tenantId`, `id` 중 하나라도 없으면 401.
- tenant/user는 body가 아닌 principal에서만 가져온다.
- 거래처 조회/검증은 `(customer_id, tenant_id)` 복합 범위로 제한한다.
- 품목 조회/검증은 `(material_id, tenant_id)` 복합 범위로 제한한다.
- 데이터베이스의 승인된 복합 FK는 최종 교차 테넌트 무결성 guard다.
- 사용자/tenant 데이터를 반환하거나 테스트에 복사하지 않는다.

## 3. 검증 및 계산

- `orderDt`, `customerId`, `details` 필수; `details`는 1개 이상.
- 모든 detail에 유효한 양수 `materialId` 및 tenant-owned 품목이 있어야 한다.
- `orderQty > 0`, `unitPrice >= 0`, `vatAmt >= 0`.
- numeric 입력은 `NUMERIC(15,2)`의 비음수 최대값/소수점 정밀도로 표현
  가능해야 한다. 숫자가 아니거나 무한/NaN에 해당하는 값은 거부한다.
- `supplyAmt = orderQty × unitPrice`, scale 2, `HALF_UP`.
- `vatAmt` 입력이 있으면 그 값의 scale 2 `HALF_UP`를 사용한다. 생략이면
  `supplyAmt × 0.10`, scale 2 `HALF_UP`.
- line total은 supply + VAT, scale 2 `HALF_UP`; header total은 저장할 각
  line total 합계다.
- 제출 순서대로 `lineNo`는 1부터 연속 할당한다.
- 서버 초기값: header status `수주등록`, detail `lineStatus` `대기`,
  `shippedQty` 0, `useAt` 스키마 기본값 Y.

## 4. 번호 생성

- 기존 `IdSequenceService`를 사용한다. 별도 sequence table을 추가하지 않는다.
- generator key: `SALES_ORDER_NO`
- scope key 1: principal의 tenant ID 문자열
- scope key 2: 주문일 `yyyyMMdd`
- 포맷: `SO-yyyyMMdd-` + 시퀀스 값(최소 4자리 zero padding)
- 시퀀스를 자르거나 재사용하지 않으며 결과가 `VARCHAR(30)`에 들어가지
  않으면 저장을 실패시킨다.
- 번호 생성/헤더/상세 삽입은 동일 트랜잭션에 속한다.

## 5. eGovFrame 구현 레이어

- `SalesOrderApiController`: `egovframework.let.sales.order.create.controller`
  패키지에서 인증/요청 binding, service 호출, 기존 `ResultVoHelper`/`ResultVO`
  item 응답을 처리한다. API 경로는 다른 `co` 업무 API와 같은
  `/api/v1/sales/orders`이며 `@Operation`, `@ApiResponses`,
  `@SecurityRequirement`로 문서화하고 `@ResponseStatus(CREATED)`를 사용한다.
- `SalesOrderService`: create 메서드 인터페이스.
- `SalesOrderServiceImpl`: 검증, 번호 생성, amount calculation,
  트랜잭션, 헤더/상세 순차 생성.
- `SalesOrderDAO`: `EgovAbstractMapper` 기반 헤더/상세 insert 및 tenant
  범위 마스터 검증.
- 요청/응답 VO는 `domain.model`에 두고, 시스템 업무 모델 패턴처럼
  `Serializable`, Lombok getter/setter, 클래스/필드 `@Schema`와 JavaDoc을
  제공한다.
- `EgovSalesOrderCreate_SQL_postgresql.xml`:
  `egovframework/mapper/let/sales/order/create`에 위치하는 PostgreSQL/MyBatis
  result/insert mapper.
  statement; 모든 바인딩은 `#{...}` 사용.
- 요청이 잘못됐으면 400, tenant에서 참조할 수 없는 거래처/품목이면 404,
  인증 문맥 오류면 401. SQL/예기치 않은 실패는 정상 오류 경로로 전파한다.
- 헤더나 상세 insert 하나라도 실패하면 전체 트랜잭션 rollback.

## 6. Frontend 저장 UX

- 공통 `apiClient`와 `apiPost`를 사용한다.
- 저장 payload에는 명세된 입력 필드만 넣는다. 계산된 공급가/합계/tenant/
  audit/sequence는 보내지 않는다.
- 고객, 수주일, 1개 이상의 품목 행, 품목 선택, 주문수량, 단가, VAT를
  submit 전 검증한다.
- invalid field와 form 오류를 명확히 표시한다.
- pending 중 버튼 비활성화, 중복 POST 금지.
- HTTP 성공 및 생성 response item 확인 후에만 수주번호 포함 성공 표시.
- 오류/누락 response/네트워크 오류에서는 입력과 상세 상태를 지우지 않는다.
- 저장 완료 후 수주 입력값은 그대로 보여주되 해당 주문은 saved 상태로
  처리하고 이탈 경고를 해제한다.

## 7. 순차 UX 개선

1. dirty form에 한해 Router 7 in-app navigation blocker와 browser
   `beforeunload` 경고를 제공한다. `useBlocker`를 사용하기 위해 앱 루트는
   Data Router를 사용하고, 취소는 작성화면 유지, 확인은 이동을 진행한다.
2. 상세 그리드 제목 옆에 선택 행용 `품목 선택` 버튼을 제공한다. 버튼과
   공통 도움창은 키보드로 사용할 수 있고, 선택한 품목 ID/코드/이름을
   대상 행에 함께 반영한다. 기존 코드 셀의 도움 버튼도 유지한다.
3. 375px/768px/1280px에서 페이지 전체 수평 overflow를 막고 필요한 상세
   컬럼은 grid 내부에서 스크롤한다. 필수 정보를 감추지 않는다.

## 8. DB 및 테스트 제약

- 초기 설계 시점에는 MCP `list_tables`에서 기본 DB에
  `tb_sales_order_hd`와 `tb_sales_order_dt`가 없었다. 이후 최신 MCP 목록에서
  두 테이블을 확인했고 `describe_table`로 Mapper가 쓰는 주요 컬럼 계약을
  확인했다. 행 데이터는 조회하지 않았다.
- 사용자가 테이블을 생성했으며 이 작업에서는 SQL/DDL/롤백/데이터 삽입을
  작성하거나 실행하지 않는다.
- 백엔드 테스트는 DAO mock을 사용하고 번호, 검증, tenant scope, 계산,
  저장 parameter, 컨트롤러 응답을 검증한다. transaction annotation과
  예외 전파를 검증하되 DB rollback 자체를 통합 검증했다고 주장하지 않는다.
- 프론트 테스트는 validation, request mapping, pending/success/error,
  input preservation, duplicate submit, dirty navigation을 검증한다.
- 실제 DB 통합 검증은 수행하지 않았다. 테이블 생성 여부와 별도로 승인된
  테스트 환경과 테스트 데이터 준비 후 진행한다.

## 9. 완료 기준

- API가 eGovFrame layer와 tenant-safe contract를 지킨다.
- frontend 수주 저장 UX와 후속 사용성 개선이 API 계약과 일치한다.
- 관련 backend/frontend 집중 검증, frontend build, 3개 viewport 브라우저
  확인 및 결과 보고서가 완료된다.
- 전체 frontend baseline failures는 수주 기능 검증과 분리해 결과에
  기록하며 무관한 코드 수정을 하지 않는다.
