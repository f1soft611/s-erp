## 대상 데이터베이스 및 현재 계약

- 대상: `.mcp.json`의 기본 `s-erp-postgresql-readonly`가 가리키는 central DB, schema `public`.
- 현재 master: `tb_material_info`, `tb_customer_info`; tenant 부모: `tb_tenant`.
- central `tb_customer_info.business_kind1/2/3`: nullable `character varying`, default 없음.
- `tb_material_info`는 `(material_id, tenant_id)` 복합 unique를 보유한다.
- `tb_customer_info`는 `(customer_id, tenant_id)` 복합 unique를 보유한다.
- `tb_tenant.tenant_id`는 PK다.
- 읽기 전용 MCP에서 업무행은 노출하지 않았다. conversion 선행 집계에서 business_kind1/2 비공백은 0건이었다.
- tenant 전용 DB는 적용 대상이 아니며 그 metadata를 central contract로 간주하지 않는다.

## 명명과 타입

S-ERP 기존 master/업무 테이블과 맞춰 내부 식별자는 `BIGSERIAL/BIGINT`, tenant는 `BIGINT`, 활성 상태는 `use_at CHAR(1)`, 감사시간은 `TIMESTAMP WITHOUT TIME ZONE`으로 둔다. 분류명은 SQL 초안의 도메인 명칭을 유지해 `item_cls_nm`, `partner_cls_nm`으로 한다. 사용자 입력용 별도 분류 코드는 만들지 않는다.

### `public.tb_cls_item`

| 컬럼 | 타입 | NULL/기본값 | 의미 |
| --- | --- | --- | --- |
| `item_cls_id` | `BIGSERIAL` | NOT NULL | 분류 내부 PK |
| `tenant_id` | `BIGINT` | NOT NULL | 소유 tenant |
| `item_cls_nm` | `VARCHAR(50)` | NOT NULL | 분류명 |
| `item_cls_lvl` | `SMALLINT` | NOT NULL | 1 대, 2 중, 3 소 |
| `upper_item_cls_id` | `BIGINT` | NULL | 같은 tenant 상위 분류 |
| `sort_seq` | `INT` | NOT NULL, 0 | 형제 분류 순서 |
| `use_at` | `CHAR(1)` | NOT NULL, `Y` | 사용여부 |
| `created_by` | `VARCHAR(10)` | NULL | 등록자 |
| `created_at` | `TIMESTAMP` | NOT NULL, `CURRENT_TIMESTAMP` | 등록일시 |
| `updated_by` | `VARCHAR(10)` | NULL | 수정자 |
| `updated_at` | `TIMESTAMP` | NULL | 수정일시 |

### `public.tb_cls_partner`

`partner_cls_id BIGSERIAL`, `tenant_id BIGINT`, `partner_cls_nm VARCHAR(50)`, `partner_cls_lvl SMALLINT`(1 대, 2 소), `upper_partner_cls_id BIGINT`, `sort_seq INT`, `use_at CHAR(1)`, `created_by VARCHAR(10)`, `created_at TIMESTAMP`, `updated_by VARCHAR(10)`, `updated_at TIMESTAMP`를 사용한다. NULL/기본값 및 의미는 품목분류와 같고, 거래처는 두 레벨만 허용한다.

## 키와 제약

### 분류 테이블 공통

- `PRIMARY KEY (<domain>_cls_id)`.
- `UNIQUE (<domain>_cls_id, tenant_id)`를 둔다. master/parent가 tenant 복합 FK를 참조할 수 있게 한다.
- `FOREIGN KEY (tenant_id) REFERENCES public.tb_tenant(tenant_id)`.
- `CHECK (use_at IN ('Y','N'))`.
- 대분류는 부모 ID가 NULL이고 하위 레벨은 부모 ID가 NOT NULL이 되도록 root/parent shape CHECK를 둔다.
- 부모 FK는 `(upper_<domain>_cls_id, tenant_id) REFERENCES (<domain>_cls_id, tenant_id)`로 tenant 경계를 제한한다.
- partner에 `UNIQUE (partner_cls_id, upper_partner_cls_id, tenant_id)`를 둬 고객의 child/parent composite FK target으로 사용한다.
- tenant/parent/sort 조회용 B-tree 인덱스를 둔다.
- FK는 cascade 삭제하지 않는다.
- 레벨 간 연속성, 품목 선택이 소분류인지, 활성 분류만 신규 선택 가능한지는 API에서 검증한다.

### master 연결

- `tb_material_info.item_cls_id BIGINT NULL` 추가.
- `FOREIGN KEY (item_cls_id, tenant_id) REFERENCES tb_cls_item(item_cls_id, tenant_id)`.
- `tb_material_info(tenant_id, item_cls_id)` index.
- `tb_customer_info.business_kind1/2`를 BIGINT NULL로 변경.
- 대분류 FK: `(business_kind1, tenant_id) REFERENCES tb_cls_partner(partner_cls_id, tenant_id)`.
- 소분류/상위분류 관계 FK: `(business_kind2, business_kind1, tenant_id) REFERENCES tb_cls_partner(partner_cls_id, upper_partner_cls_id, tenant_id)`.
- `tb_customer_info(tenant_id, business_kind1)` 및 `(tenant_id, business_kind2)` index.
- `business_kind2 IS NOT NULL`이면 `business_kind1 IS NOT NULL`인 CHECK를 둔다.
- 계층 FK는 소분류와 선택 대분류의 직접 부모 관계를 강제하지만, `business_kind1`이 레벨 1인지 및 각 분류가 활성 상태인지 API가 검증한다.

## Migration 순서와 중단 조건

1. transaction 시작 후 `tb_tenant`, `tb_material_info`, `tb_customer_info`를 필요한 강도로 잠근다.
2. 사전조건 DO block에서 분류 테이블이 아직 없고, target columns/type/nullability/default, tenant FK 대상, master composite unique target이 예상 계약과 일치하는지 검사한다. 잘못된 상태면 예외로 중단한다.
3. `business_kind1/2`에 NULL/공백이 아닌 값이 있는지 검사한다. 하나라도 있으면 예외로 중단한다. 확인 시점의 0건은 실제 실행 때 재검증을 대체하지 않는다.
4. 분류 테이블 및 제약/index/comment를 만든다.
5. `tb_material_info.item_cls_id`를 추가하고 tenant 복합 FK/index를 만든다. `mat_cata_type`은 건드리지 않는다.
6. 거래처 두 컬럼을 `NULLIF(btrim(column), '')::BIGINT`로 변환하고 CHECK/FK/index를 추가한다. `business_kind3`는 건드리지 않는다.
7. transaction commit.

`CREATE TABLE IF NOT EXISTS`나 `DROP ... CASCADE`를 사용하지 않는다. 예상 전제에 어긋나면 기존 객체를 덮어쓰지 않고 전체 transaction이 실패해야 한다.

## Rollback 계약

- transaction을 시작하고 양쪽 master 및 분류 테이블을 잠근다.
- 분류 테이블 중 하나라도 행이 있거나 `tb_material_info.item_cls_id`, `tb_customer_info.business_kind1/2`가 하나라도 non-NULL이면 예외를 발생시킨다.
- 안전 조건을 통과한 경우 명명된 마스터 FK/CHECK를 제거하고, `business_kind1/2`를 VARCHAR로 되돌리고, 품목 분류 컬럼을 제거한다.
- 생성된 인덱스와 `tb_cls_partner`, `tb_cls_item`을 자식 우선 순서로 삭제한다.
- `CASCADE`를 사용하지 않는다. 객체 이름/의존성이 예상과 다르면 자동 삭제하지 말고 수동 검토 대상으로 중단한다.
- 기존 business_kind가 migration 이후 분류 ID를 저장했거나 외부 객체가 의존하면 rollback은 금지한다. 먼저 별도 복구 설계와 데이터 백업이 필요하다.

## 컬럼 설명

- `tb_cls_item`: 품목분류마스터(대/중/소 테넌트 계층)
- `tb_cls_partner`: 거래처분류마스터(대/소 테넌트 계층)
- master `item_cls_id`: 품목 소분류 내부 ID(FK)
- `business_kind1`: 거래처 대분류 내부 ID(FK; central DB 기존 문자열 컬럼을 BIGINT로 전환)
- `business_kind2`: 거래처 소분류 내부 ID(FK; 지정된 대분류의 직접 하위)

## 미적용 상태와 검증

- DDL 및 rollback은 검토용 초안이며 central DB에 실행하지 않는다.
- `docs/database`와 `backend/DATABASE` 날짜 폴더의 동명 파일은 같은 내용이어야 한다.
- `db-schema.md`는 현재 적용 구조와 섞지 말고 `미적용 설계안`으로 분리해 기록한다.
- SQL은 트랜잭션, 중단 guard, FK 참조 키 순서, NULL/공백 변환, rollback 전제와 삭제 순서를 정적으로 확인한다.
- PostgreSQL 실행 검증을 하지 않았으면 실행 검증 완료로 표기하지 않는다.
