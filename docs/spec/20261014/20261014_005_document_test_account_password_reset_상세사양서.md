# 20261014_005 문서작성 테스트 계정 비밀번호 초기화 상세사양서

> 후속 변경: 직접 psql 실행 및 입력/로그 노출 위험은 [20261014_007 상세사양서](./20261014_007_document_test_account_password_reset_psql_상세사양서.md)를 따른다. 아래 외부 세션 해시 설정 절차는 superseded 되었다.

## 1. 근거 및 범위

- 작업지시서: [20261014_005 문서작성 테스트 계정 비밀번호 초기화](../../directions/20261014/20261014_005_document_test_account_password_reset_작업지시서.md)
- 계획서: [20261014_005 문서작성 테스트 계정 비밀번호 초기화](../../plan/20261014/20261014_005_document_test_account_password_reset_계획서.md)
- 승인 설계: [문서작성 테스트 계정 비밀번호 초기화 설계](../../superpowers/specs/2026-10-14-document-test-account-password-reset-design.md)
- 로그인 계정 계약: [20261007_005 문서작성 테스트 사용자 로그인 계정 보정](../20261007/20261007_005_document_user_picker_login_accounts_사양서.md)

작업 대상은 테넌트 코드 `T1358606250`의 문서작성 사용자 선택기 테스트 계정 10개다. 애플리케이션 로그인 구현, DB 스키마, 프로필/역할/권한은 변경하지 않는다.

## 2. 대상 계정

각 `NN`은 `01`부터 `10`까지다.

| 항목 | 계약 |
|---|---|
| 테넌트 | `tb_tenant.tenant_code = 'T1358606250'`, 활성 상태 |
| 로그인 코드 | `doc-write-test-user-NN` |
| 계정 활성 상태 | 기존 활성(`tb_login_account.use_at = 'Y'`)만 대상으로 하며 상태 자체는 변경하지 않음 |
| 해시 입력 설정 | `app.document_test_user_hash_NN` |
| 조직/사용자/역할 | 변경하지 않음 |

## 3. 인증정보 입력

- 운영자는 각 로그인 코드와 새 비밀번호에 맞는 10개의 해시를 SQL 실행 전 안전한 방법으로 준비한다.
- 각 해시는 현재 백엔드의 `EgovFileScrty.encryptPassword(password, login_code)` 계약과 일치해야 한다. 구현은 SHA-256 입력에 로그인 코드의 기본 문자 인코딩 바이트를 먼저 공급하고 비밀번호 바이트를 해시한 뒤 Base64로 인코딩한다.
- 설정 이름은 `app.document_test_user_hash_01`부터 `app.document_test_user_hash_10`까지다. 각 설정은 SQL을 실행하는 동일 PostgreSQL 세션에 존재해야 한다.
- SQL은 해시 값을 세션 설정에서 읽으며 평문 비밀번호를 읽거나 계산하지 않는다.
- 각 해시는 값이 존재하고 정확히 44자 Base64 SHA-256 표현인지 영속 데이터 변경 전에 검증한다. 누락 또는 형식 오류는 명시적 예외로 중단한다.
- 실제 비밀번호 및 해시값은 파일, 문서, 소스 코드, 테스트 출력, 세션 로그/명령 기록에 저장하지 않는다.

## 4. 사전 조건 및 트랜잭션

1. psql의 `ON_ERROR_STOP`을 활성화한다.
2. 트랜잭션을 시작하고 임시 매핑 테이블에 로그인 코드별 해시 설정 10개를 적재한다. 임시 테이블은 입력 누락을 명시적으로 감지할 수 있도록 해시 컬럼을 nullable로 둔다.
3. 해시 매핑이 정확히 10개인지, 모든 해시 형식이 올바른지 확인한다.
4. 활성 테넌트 코드가 정확히 하나인지 확인한다.
5. 지정 로그인 코드 10개에 해당하는 활성 계정이 동일 테넌트에 정확히 10개인지 확인한다.
6. 갱신 전 대상 로그인 계정 행에 `FOR UPDATE` 잠금을 건다.
7. 사전 조건 중 하나라도 실패하면 예외를 발생시켜 갱신하지 않는다. 업데이트 중 행 수가 10개가 아니어도 예외를 발생시키고 트랜잭션을 커밋하지 않는다.

## 5. 갱신 내용

한 번의 트랜잭션에서 지정된 10개 계정만 다음 컬럼을 갱신한다.

| 컬럼 | 값 |
|---|---|
| `password_hash` | 대응 로그인 코드의 해시 설정값 |
| `password_changed_at` | `CURRENT_TIMESTAMP` |
| `login_attempt_count` | `0` |
| `locked_at` | `NULL` |
| `updated_at` | `CURRENT_TIMESTAMP` |

`use_at`, `tb_user`, `tb_login_account_role`, 역할 정의, 메뉴 권한은 수정하지 않는다. SQL은 성공한 갱신 행 수가 10인지 확인한 다음 커밋한다.

## 6. 실행/복구 정책

- 데이터베이스 계약 근거: 읽기 전용 `s-erp-postgresql-readonly` MCP의 테이블/컬럼 메타데이터. MCP로 데이터 변경은 금지한다.
- 파일 위치: `docs/database/20261014` 및 동일 내용의 `backend/DATABASE/20261014`.
- 성공한 초기화에 대한 롤백 SQL은 제공하지 않는다. 이전 해시를 저장하지 않으며, 이를 복원하려면 이후 승인된 새 해시로 다시 초기화해야 한다.
- 이 저장소 작업에서 에이전트는 실행 SQL을 DB에 적용하지 않는다.

## 7. 검증 기준

- `node --test tools/tests/test_document_test_account_password_reset.cjs`가 정적 계약 검사를 모두 통과한다.
- SQL이 정확히 열 개의 `login_code`/GUC 쌍, 선행 해시·테넌트·계정 검증, 행 잠금, 지정 테넌트/활성 계정 조건, 허용된 다섯 개의 수정 컬럼 및 사후 갱신 행 수 검증을 포함한다.
- docs/backend의 SQL 및 변경 이력 각 쌍은 바이트 단위로 동일하다.
- 실제 DB 데이터 변경과 로그인 성공은 이 문서의 정적 검증 범위가 아니며, 수행한 것으로 보고하지 않는다.
