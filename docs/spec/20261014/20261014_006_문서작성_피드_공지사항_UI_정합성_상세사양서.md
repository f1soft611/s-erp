# 20261014_006 문서작성 상세 피드 및 수정 모달 정합성 상세 사양서

## 목적 및 기준

문서작성 `/groupware/doc/write`의 피드형을 현재 문서 상세 표현을 기반으로 한 공지사항 스타일의 상세 피드로 제공한다. 현재 범위/업무구분 조건을 만족하는 문서가 모두 피드에 나타나야 하며, 기존 우측 상세 패널의 결재 처리 및 편집 흐름은 유지한다.

## 화면 계약

### 필터 결과와 피드 카드

- 최초 선택 보기 방식은 `list`를 유지한다.
- `listDocumentApprovals(scope, documentType, electronicApprovalId)`의 현재 조건에 맞는 모든 응답 문서는 피드에 표시한다. 특정 ID 알림으로 좁혀진 경우에도 그 응답 문서가 누락되지 않는다.
- 고정 문서가 응답에 포함되면 피드에서 숨기지 않고 같은 상세 카드 형태로 표시한다. 기존 정렬 및 고정 표시 상태가 있으면 이를 보존한다.
- 각 상세 카드는 기존 `FeedCard` 공통 외형을 사용한다.
- 헤더는 기안자, 작성일/조회 메타, 문서 종류와 상태를 표시한다. 공지사항 피드와 같이 작성자 권한이 있을 때 기존 문서 수정/삭제 메뉴를 제공하되, 피드에 결재 처리 버튼은 노출하지 않는다. 문서에 없는 고정 토글 등 notice-only 작업은 추가하지 않는다.
- 카드 상세 내용은 결재선(읽기 전용), 문서 제목, 전체 rich-text 본문, 인증 embedded image, 첨부, 좋아요/북마크 바, 댓글 수 및 댓글 스레드를 포함한다.
- 좋아요/북마크는 현 문서 상세와 동일한 로컬 UI 토글이다. 좋아요 수는 항상 0이며 새 API/DB 저장 동작을 만들지 않는다.
- 댓글 생성/답글/수정/삭제, 이전 댓글 페이징, 댓글 첨부 다운로드/삭제 및 이미지 미리보기는 기존 `DocumentApprovalDetailFeed`의 API/권한/오류 동작을 재사용한다.
- 피드형/리스트형으로 전환할 때마다 현재 scope/documentType/electronicApprovalId 필터로 목록을 다시 조회한다. 데이터 요청 중 현재 모드에 대응하는 `FeedViewSkeleton` 또는 `ListViewSkeleton`을 표시한다.
- 리스트형은 기존 `GET /api/v1/groupware/approvals/documents` lightweight 응답을 사용한다. 피드형은 같은 endpoint에 `includeDetails=true`를 전달하고, 전체 상세 포함 응답 완료 뒤 모든 카드를 한 번에 렌더링한다.
- 피드 카드에서는 목록 응답에 포함된 상세/초기 댓글 데이터를 사용한다. 카드별 초기 `getDocumentApprovalDetail` 및 `listApprovalComments` 요청이나 viewport lazy loading은 하지 않는다. 이전 댓글 조회 및 댓글/첨부 변경은 기존 API를 계속 사용한다.
- 피드 목록 요청이 실패하거나 필수 상세/댓글 데이터가 누락된 경우 부분 피드를 표시하지 않고 페이지 오류 및 재시도를 제공한다. mode/filter 변경 전 요청의 늦은 응답은 최신 화면 상태를 덮어쓰지 않는다.
- 카드 클릭 및 댓글/첨부/반응 인터랙션으로 우측 상세 패널을 열지 않는다.
- 피드 메뉴에서 수정하면 Composer를 표시하고 닫을 때 목록과 마운트된 상세 카드를 quiet refresh한다. 리스트 상세 패널에서 수정하는 경우에는 패널을 계속 표시하고 선택 상세도 quiet refresh한다.

### 리스트형 상세 및 수정 모달

- 리스트 행 선택은 기존처럼 `PageAreaOverlay`와 `DocumentApprovalDetailFeed` 상세 패널을 연다.
- 상세 패널 안의 결재 처리 입력과 승인·반려·보완요청 버튼은 기존 권한 조건과 동작으로 유지한다.
- 상세 메뉴의 편집 액션은 `detailDocumentId`를 지우지 않고 Composer를 표시한다.
- Composer는 열린 상세 패널 위에 표시된다. 취소/닫기/저장 이후에도 같은 상세 패널을 유지한다.
- Composer 종료 후 문서 목록/요약을 quiet refresh하고, 이미 마운트된 feed 상세 카드와 선택된 상세의 refresh token을 변경한다.
- quiet refresh는 요청 중 기존 목록과 패널 내용을 유지하고 skeleton을 표시하지 않는다. 성공 응답에 따라 데이터를 교체한다.
- 목록/상세 요청이 실패하면 기존 화면의 오류 영역에 표시하고 실패를 성공처럼 처리하지 않는다.

## 데이터와 오류 처리

- 목록 API에 선택적 `includeDetails` 쿼리 파라미터를 추가한다. 누락 또는 false면 기존 `resultList` 응답 필드/의미를 변경하지 않는다. true면 기존 목록 row 필드에 상세 피드 필드를 추가한다.
- feed row가 추가하는 필드: `draftingWorkCategoryId`, `contentsJson`, `contentsHtml`, `contentsText`, `viewCount`, `isDrafter`, `approvalLines`, `attachments`, `systemEvents`, `comments`, `commentCount`, `hasPreviousComments`, `nextBeforeCommentId`.
- `comments`는 기존 댓글 서비스의 최초 3개 root 댓글 페이지이며 댓글별 첨부를 포함한다. `commentCount`, `hasPreviousComments`, `nextBeforeCommentId` 의미는 기존 `DocumentApprovalCommentPage` 계약과 같다. 오래된 댓글은 기존 페이지 API에서 가져온다.
- 피드 상세 hydration은 현행 범위/문서종류/ID 필터로 권한 확인된 목록 항목만 대상으로 한다. 이 선조회는 view history를 insert하거나 `viewCount`를 증가시키지 않는다. 우측 상세 패널의 `getDocumentApprovalDetail`은 현재 조회수 동작을 보존한다.
- 응답 내 어느 한 문서의 필수 상세, 첨부, 결재선 또는 초기 댓글 데이터 생성에 실패하면 전체 detailed-list API를 실패 처리한다. 피드에 부분 성공 형태의 문서를 섞지 않는다.
- Frontend summary 조회는 기존처럼 독립 요청으로 유지한다. “한 번 조회”는 모든 feed document data를 하나의 detailed document-list HTTP 응답으로 가져온다는 의미이며 summary API까지 합치는 것은 아니다.
- 인증 본문/댓글 이미지의 Blob URL은 컴포넌트가 unmount될 때 폐기한다.
- 사용자 표시 메시지는 기존 서비스 오류를 우선 사용하고 예외 메시지가 없는 경우에만 명시된 문서 상세/댓글 기본 오류 메시지를 사용한다.
- 문서 좋아요 서비스/저장 계약은 없으므로 기존 상세의 로컬 `isLiked` 동작만 재사용한다.
- 기존 결재 권한, 편집 권한, 댓글 권한은 변경하지 않는다.
- DB 스키마 변경은 없다. 구현 전 PostgreSQL MCP `list_tables` 및 관련 테이블 `describe_table`로 현재 계약을 확인하고 결과 문서에 근거를 기록한다.

## 접근성·반응형

- feed card는 문서 콘텐츠를 담는 article이며 모든 조작은 개별 버튼/입력 컨트롤로 제공한다.
- 모드 전환 로딩은 목록 콘텐츠 영역의 `role="status"`와 모드별 명확한 접근성 레이블로 표시한다. 에러/retry, 댓글 입력, 반응 버튼은 키보드 조작 가능해야 한다.
- 375px/768px/1280px에서 헤더, 상태 badge, 결재선, 본문, 첨부, 댓글, 편집 모달의 겹침/잘림 및 가로 overflow를 확인한다.
