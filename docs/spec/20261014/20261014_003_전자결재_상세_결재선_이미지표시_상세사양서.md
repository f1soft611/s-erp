# 20261014_003 전자결재 상세 결재선 프로필·도장 이미지 상세사양서

## 1. 목적 및 기준

기존 전자결재 상세 응답의 결재선 참여자에 프로필/도장 이미지 데이터를 추가하고, 상세 결재선에서 승인 상태, 합의 단계 및 참조자를 읽기 쉽게 표시한다. 이번 작업은 조회 전용 UI/API 응답 확장이며 결재 데이터 저장이나 DB 구조는 변경하지 않는다.

- 작업지시서: [20261014_003 작업지시서](../../directions/20261014/20261014_003_전자결재_상세_결재선_이미지표시_작업지시서.md)
- 계획서: [20261014_003 계획서](../../plan/20261014/20261014_003_전자결재_상세_결재선_이미지표시_계획서.md)
- 승인된 설계: [결재선 상세 표시 보완 설계](../../superpowers/specs/2026-10-14-document-approval-line-refinement-design.md)
- 워크플로우 근거: [전자결재 순차 상신 및 시스템 이력 설계](../../superpowers/specs/2026-10-12-document-approval-workflow-design.md)

## 2. 상세 API 및 데이터 계약

### 요청

```text
GET /api/v1/groupware/approvals/documents/{electronicApprovalId}
```

- 기존 인증 및 상세 접근권한 확인, HTTP 동작, `ResultVO` 응답 envelope를 유지한다.
- 새 endpoint를 추가하지 않는다.
- 현재 `approvalLines` 배열 경로와 기존 참여자 필드를 유지한다.

### 결재선 항목 추가 필드

| JSON 필드 | 타입 | nullable | 반환 규칙 |
|---|---|---|---|
| `participantProfileImage` | string | 예 | 결재·합의·참조 참여자 계정에 저장된 프로필 이미지. 이미지 또는 계정이 없으면 `null` |
| `participantStampImage` | string | 예 | 처리 완료된 승인 참여자의 도장 이미지. 대상이 아니거나 이미지가 없으면 `null` |

예시:

```json
{
  "item": {
    "approvalLines": [
      {
        "electronicApprovalLineId": 801,
        "stageOrder": 2,
        "participantOrder": 1,
        "participantType": "APPROVAL",
        "participantUserId": "42",
        "participantName": "결재자",
        "participantDepartmentName": "기획팀",
        "actionStatus": "APPROVED",
        "participantProfileImage": "data:image/png;base64,...",
        "participantStampImage": "data:image/png;base64,..."
      }
    ]
  }
}
```

이미지 응답 값은 기존 계정의 PNG/JPEG 데이터 URL을 그대로 사용한다. 상세 envelope 외부 구조 및 `approvalLines` 내 기존 정보의 의미는 바꾸지 않는다.

### 도장 반환 정책

| 참여자 종류 | `actionStatus` | 개인 도장 필드 | 상세 UI |
|---|---|---|---|
| `APPROVAL` | `APPROVED`, `REJECTED`, `RETURNED` | 저장 이미지 또는 `null` | 이미지가 있으면 개인 도장, 없거나 실패하면 현재 상태 도장 |
| `APPROVAL` | `WAITING`, `PENDING` | `null` | 항상 시스템 `대기`/`진행` 표시 |
| `AGREEMENT` | 모든 상태 | `null` | 합의 참여자 프로필·이름·부서·상태 표시 |
| `REFERENCE` | 처리 상태 없음 | `null` | 참조 참여자 프로필·이름·부서 표시 |

프로필 필드는 세 참여자 종류 모두에 대해 조회한다. 필드가 없거나 이미지 로드가 실패한 경우 화면에서 프로필은 이름 첫 글자로 대체한다.

## 3. 백엔드 조회 사양

### 조회 대상과 관계

- 현재 `selectApprovalLines` 조회와 상세 권한검증을 재사용한다.
- 전자결재 행의 `tenant_id`와 `electronic_approval_id` 필터 및 `stage_order`, `participant_order` 정렬은 그대로 유지한다.
- `tb_electronic_approval_line_info`에 `line` alias를 부여하고, 조회·필터·정렬 컬럼을 `line.`으로 한정해 JOIN 컬럼명 모호성을 방지한다.
- `tb_electronic_approval_line_info.participant_user_id`는 `tb_user.user_id`와 일치시킨다. 두 ID를 tenant 조건과 함께 조인한다.
- `tb_user.login_id`를 같은 tenant의 `tb_login_account.login_id`와 조인해 `profile_image`, `stamp_image`를 얻는다.
- 두 사용자/계정 관계는 LEFT JOIN한다. 사용자가 없거나 계정 연결이 없더라도 결재선 행과 저장된 `participant_name`, `participant_department_name`, `action_status`는 보존한다.
- 참여자 이름과 부서명은 기존 결재선 행의 저장값을 우선하며 사용자 조회로 덮어쓰지 않는다.

관계 개요:

```sql
LEFT JOIN public.tb_user u
  ON u.tenant_id = line.tenant_id
 AND CAST(u.user_id AS varchar) = line.participant_user_id
LEFT JOIN public.tb_login_account la
  ON la.tenant_id = u.tenant_id
 AND la.login_id = u.login_id
```

프로필은 `la.profile_image`에서 매핑한다. 도장은 아래 논리식이 참인 승인 행에서만 제공하고 그 외에는 `NULL`로 매핑한다.

```sql
line.participant_type = 'APPROVAL'
AND line.action_status IN ('APPROVED', 'REJECTED', 'RETURNED')
```

### 응답 모델

- Java `DocumentApprovalLineVO`에 `String participantProfileImage`, `String participantStampImage`와 표준 getter/setter를 추가한다.
- MyBatis `approvalLine` resultMap에 새 두 컬럼을 각각 대응하는 Java property에 매핑한다.
- TypeScript `DocumentApprovalLine`에는 `participantProfileImage?: string | null`, `participantStampImage?: string | null`을 추가한다.
- 개인정보 접근통제는 기존 상세 API의 권한 범위를 유지한다. 새로 조회할 수 있는 사용자는 만들지 않는다.

### DB 범위

- `tb_login_account.profile_image`, `stamp_image` 기존 nullable text 컬럼만 읽는다.
- 신규 테이블/컬럼/제약/인덱스, 데이터 migration, `db-schema.md` 변경은 없다.
- 사용자 이미지 등록/수정·파일 저장 API는 변경하지 않는다.

## 4. 화면 표시 사양

### 4.1 결재선 헤더

- 패널 제목은 `결재선`으로 유지한다.
- 제목 옆에는 `기안자 {drafterName} · {createdAt의 YYYY.MM.DD}`를 표시한다.
- 승인 카드 그룹 위에 있는 독립 `결재` 소제목은 제거한다.
- 제목 및 메타 정보, 승인 도장 텍스트, 참여자 이름·부서·상태는 MUI `body1` 기본 본문 크기를 기준으로 한다. 굵기·색상·말줄임은 레이아웃과 상태 구분에 필요한 범위에서 적용한다.

### 4.2 승인 카드

- 현재 `stageOrder`, `participantOrder` 표시 순서, 승인 카드 흐름과 기존 connector를 유지한다.
- 각 상태 도장을 기존보다 크게 표시한다.
- `APPROVED`, `REJECTED`, `RETURNED` 상태이며 `participantStampImage`가 유효한 경우에만 이미지를 도장 영역 안에 표시한다.
- 도장 데이터가 없거나 로드되지 않을 때 시스템 상태 텍스트와 색상을 복구한다.
- `WAITING` 및 `PENDING`은 상태에 맞는 시스템 텍스트 도장을 사용하고 개인 도장 이미지는 표시하지 않는다.
- 시스템 도장과 개인 도장 모두 기존 상태 접근성 이름을 보존한다. 장식 이미지에는 상태를 대체하지 않는 대체 텍스트를 부여한다.

### 4.3 합의

- `AGREEMENT` 참여자를 `stageOrder`별 단계로 그룹화한다.
- 단계 순번은 각 그룹에 한 번 표시하고 개인별 순번은 중복 표시하지 않는다.
- 그룹 내 순서는 `participantOrder` 오름차순이다.
- 단계는 테두리가 있는 그룹 카드로 표시하고 순번 원형 배지와 참여자 영역을 한 행에 배치한다.
- 참여자별 테두리 카드는 프로필·이름 1행, 기존 부서명·상태 배지 2행이다. 카드들은 가용 폭에 맞춰 가로 배치 후 자동 줄바꿈한다.
- 이름·부서·상태에는 MUI `body1` 기본 본문 크기를 사용한다.
- 프로필 이미지가 없는 경우 및 이미지 로드 오류 시 Avatar에 이름 첫 글자를 표시한다.
- 합의 영역 내부 가로 스크롤은 사용하지 않는다.
- 한 합의 단계의 동시 처리와 전원 승인 후 다음 단계 이동이라는 서버 규칙을 바꾸지 않는다.

### 4.4 참조

- `REFERENCE` 참여자에게 순번을 표시하지 않는다.
- 참조 참여자는 가로로 불필요하게 늘어나지 않는 테두리 카드로 프로필·이름 1행, 부서 2행으로 표시하고 가용 폭에 따라 자동 줄바꿈한다.
- 참조 이름과 부서에는 MUI `body1` 기본 본문 크기를 사용한다.
- 프로필, 이름, 기존 결재선에 저장된 부서명을 표시한다.
- 프로필 이미지가 없는 경우 및 로드 오류 시 Avatar에 이름 첫 글자를 표시한다.
- 참조 목록은 가용 폭에서 자동 줄바꿈하며 내부 가로 스크롤은 사용하지 않는다.

### 4.5 반응형 및 오류

- 합의·참조에서 이름이 길면 기존 카드 너비 기준으로 말줄임하되 전체 페이지 가로 overflow는 만들지 않는다.
- 375px, 768px, 1280px에서 참여자들이 자동 줄바꿈하며 레이아웃이 겹치지 않는다.
- 이미지 로드 오류는 상태 도장/이니셜 프로필 대체 표시로 처리한다.
- 상세 API, 권한, 문서 조회 실패는 기존 오류 표시를 유지하고 이미지 fallback으로 숨기지 않는다.

## 6. 테스트 및 검증 사양

### 백엔드 Mapper

- MyBatis mapper XML을 기존 `DocumentApprovalMapperTest` 방식으로 파싱한다.
- `approvalLine` resultMap에 `participantProfileImage`, `participantStampImage`가 연결됐음을 확인한다.
- 생성된 `selectApprovalLines` SQL에서 기존 tenant/document 필터와 순서가 보존되고, 사용자 ID/tenant 및 계정 ID/tenant LEFT JOIN이 생성되는지 확인한다.
- 프로필 이미지 컬럼이 매핑되고, 도장 CASE projection이 `APPROVAL` 및 처리완료 상태에 한정되는지 확인한다.
- `DocumentApprovalLineVO` 직렬화에서 JSON 키가 두 camelCase 필드명으로 나오는지 확인한다.
- 대체 계정이 없는 데이터의 결재선 유지 여부는 LEFT JOIN SQL 조건을 확인한다. 별도 사용자/계정 데이터 fixture를 만들거나 행 결과를 가정하는 DB 통합 테스트를 추가하지 않는다.

### 프론트엔드

- 상세 fixture에서 완료 승인자 이미지와 이미지 없는 승인자를 구분한다. `WAITING`·`PENDING` 개인 도장 값은 서버 계약상 `null`임을 확인한다.
- 도장 이미지가 있는 완료 상태와 로드 실패 fallback을 검증한다.
- 합의 참여자 두 명이 동일한 `stageOrder` 아래 한 번만 순번을 표시하고, `participantOrder`에 맞게 렌더링되는지 검증한다.
- 합의 참여자 각 항목에서 프로필/이니셜, 이름, 부서, 상태를 검증한다.
- 참조 참여자에 순번이 없고 프로필/이니셜, 이름, 부서가 있는지 검증한다.
- `결재선` 헤더/기안자/기안일 표시, `결재` 별도 소제목 제거, 기본 본문 크기, 읽기 전용 동작 및 기존 상태 표시를 검증한다.
- 로컬 DOM 테스트는 가로줄바꿈 CSS를 확인하고, 실제 크기와 overflow는 브라우저에서 별도 검증한다.
