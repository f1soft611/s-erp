# 20261014_001 전자결재 상세 작성자 헤더·결재선·조회수 상세사양서

## 1. 목적과 기준

전자결재 상세 화면의 작성자 메타 행과 읽기 전용 결재선을 제공된 참조 이미지에 맞춘다. 조회수는 실제 백엔드 누적값이며 인증 사용자별 문서당 최초 상세 조회 한 번만 증가한다.

- 작업지시서: [20261014_001 작업지시서](../../directions/20261014/20261014_001_전자결재_상세_결재선_조회수_작업지시서.md)
- 계획서: [20261014_001 계획서](../../plan/20261014/20261014_001_전자결재_상세_결재선_조회수_계획서.md)
- 승인된 설계: [전자결재 상세 헤더·결재선 설계](../../superpowers/specs/2026-10-14-document-approval-line-view-count-design.md)

## 2. 화면 사양

### 2.1 작성자 행

- 결재선 패널 위에 기존 문서 상세 작성자 행을 표시한다.
- 왼쪽에는 이름 첫 글자를 표시하는 원형 Avatar, 오른쪽에는 작성자 이름을 첫 줄에 표시한다.
- 이름 아래에는 `기안자 · YYYY.MM.DD · 조회 N`을 한 줄로 표시한다.
- 날짜는 `createdAt`을 `YYYY.MM.DD` 형태로 표시한다.
- N은 상세 응답의 `viewCount` 값 그대로이며 화면에서 `+1`, `0` 대체값 또는 고정 숫자를 만들지 않는다.
- 기존 고정 아이콘, 더보기 메뉴, 문서 상태 badge 및 작성자 수정/삭제 액션을 유지한다.

### 2.2 결재선 패널

- 작성자 행 다음에 별도의 둥근 모서리·옅은 배경 패널을 둔다.
- 패널 상단 왼쪽은 `결재선`, 이어서 `기안자 {drafterName} · {createdAt}`을 표시한다.
- 패널은 승인 카드 및 합의/참조 행을 포함하며 읽기 전용이다.
- 실제 결재 참여자를 `stageOrder`, `participantOrder` 오름차순으로 표시한다.
- 카드 슬롯은 기존 3행 높이 `32px / 64px / 32px`를 유지한다.
- 카드 1행은 부서명, 2행은 상태 도장과 선택적 처리 의견, 3행은 순번+이름이다.
- 순번과 이름은 함께 하나의 수평 그룹으로 카드 정중앙에 배치한다. 순번 폭은 고정하고 이름은 `min-width: 0`, `noWrap`, `text-overflow: ellipsis`를 적용한다.
- `PENDING` 상태 도장의 짧은 표시 텍스트는 `진행`, 접근성 라벨은 `결재 상태 처리 중`으로 제공한다. 나머지 상태는 기존 상태 의미를 보존한다.
- 카드 사이 connector는 짧은 선이 아닌 오른쪽 꺾쇠 아이콘만 사용한다. 마지막 참여자 뒤에는 connector를 숨긴다.
- 승인 카드 흐름의 폭이 화면보다 넓으면 해당 흐름 내부에서만 가로 스크롤한다.
- 승인 카드 아래 내부 구분선을 두고 합의와 참조를 각각 구분된 행으로 표시한다.
- 합의/참조의 각 참여자는 저장된 `stageOrder`와 이름을 함께 표시하고 긴 이름은 말줄임 처리한다. 참여자가 없으면 해당 행을 만들지 않는다.
- 합의/참조가 모두 없으면 하단 행과 해당 내부 구분선을 숨긴다.
- 패널 아래 기존 결재선 외부 구분선을 보존한다.
- 좁은 뷰포트에서 문서 페이지 자체에 수평 overflow를 만들지 않는다.

## 3. 조회수 정책

| 상황 | 동작 |
|---|---|
| 인증 사용자의 권한 있는 문서 첫 상세 조회 | 이력 1건 등록, 조회수 1 증가 |
| 같은 사용자의 재조회·새로고침·재시도 | 조회수 유지 |
| 같은 사용자의 동시 요청 | 이력 및 조회수 1회만 반영 |
| 같은 테넌트의 다른 사용자 첫 상세 조회 | 사용자별 1 증가 |
| 목록 조회 | 증가하지 않음 |
| 문서 없음·삭제·권한 없음 | 이력·조회수 변경 없음 |
| 인증 사용자를 로그인 계정으로 해석할 수 없음 | 저장 없이 명시적 계약 오류 |

중복 키는 `(tenant_id, electronic_approval_id, login_id)`이다. 조회수는 서버가 관리하며 클라이언트는 상세 응답을 그대로 표시한다.

## 4. DB 사양

### 4.1 `tb_electronic_approval_main`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `view_count` | integer | NOT NULL, DEFAULT 0, CHECK `view_count >= 0` | 인증 사용자별 최초 상세 조회 누적 수 |

### 4.2 `tb_electronic_approval_view_history`

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `view_history_id` | bigserial | PK | 조회 이력 PK |
| `tenant_id` | bigint | NOT NULL, FK | 테넌트 |
| `electronic_approval_id` | bigint | NOT NULL | 결재 문서 |
| `login_id` | bigint | NOT NULL, FK | 인증 로그인 계정 |
| `viewed_at` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 최초 조회 시각 |

- UNIQUE `(tenant_id, electronic_approval_id, login_id)`
- 복합 FK `(tenant_id, electronic_approval_id)` → `tb_electronic_approval_main(tenant_id, electronic_approval_id)`, 문서 삭제 시 cascade.
- FK `login_id` → `tb_login_account(login_id)`.
- 조회 최적화를 위해 `(tenant_id, electronic_approval_id)` 인덱스를 추가한다.

## 5. API 사양

### 요청

```text
GET /api/v1/groupware/approvals/documents/{electronicApprovalId}
```

### 응답 필드 추가

기존 `ResultVO` envelope와 기존 detail 필드는 유지한다.

```json
{
  "item": {
    "electronicApprovalId": 115,
    "viewCount": 2
  }
}
```

- `viewCount`는 0 이상의 정수이며 상세 권한 확인 및 해당 요청의 조회 기록 처리 후 값을 담는다.
- 첫 등록 여부와 무관하게 insert 시도 후 문서 행을 재조회해 현재 값을 반환한다. 이로써 동시에 들어온 중복 요청도 오래된 초기값을 응답하지 않는다.
- 문서 목록 API와 요약 API 계약은 변경하지 않는다.

## 6. 서버 처리 순서

1. `LoginVO` 인증 및 요청 문서 ID를 기존 방식으로 검증한다.
2. tenant와 기안자/결재 참여자 기준의 기존 상세 조회로 접근 권한과 문서 생존 여부를 확인한다. 결과가 없으면 기존 404 동작을 유지한다.
3. 인증 컨텍스트의 `LoginVO.id`를 같은 tenant의 활성 `tb_login_account.login_id`로 해석한다. 사용자 ID를 요청 파라미터로 받지 않는다.
4. 조회 이력을 `ON CONFLICT (tenant_id, electronic_approval_id, login_id) DO NOTHING RETURNING view_history_id`로 등록한다.
5. 새 이력이 반환된 경우에만 `view_count = view_count + 1`을 tenant·문서·미삭제 조건으로 원자 증가한다. 기대 행 수 1이 아니면 오류를 발생시켜 트랜잭션을 rollback한다.
6. insert 성공/충돌과 관계없이 상세 행을 다시 조회해 최신 `viewCount`를 확보한다.
7. 첨부, 결재선, 시스템 이벤트 hydration은 기존 흐름대로 수행하고 기존 response envelope로 반환한다.

조회 등록과 counter 갱신은 같은 트랜잭션에서 처리한다. 접근이 거부되었거나 인증 계정을 확인할 수 없는 경우 이력을 남기지 않는다.

## 7. 테스트 사양

### 백엔드 서비스

- 첫 상세 조회: 권한 있는 detail 조회, tenant-scoped login lookup, 새 history ID, counter 증가 1회, 최종 `viewCount` 재조회.
- 같은 사용자 반복 조회: history insert 결과 null, counter update 미호출, 현재 count 응답.
- 다른 로그인 계정: 해당 `login_id`로 history insert가 별도 시도됨.
- detail 조회 결과 없음: 404이며 login lookup/history insert/counter update 미호출.
- 계정 매핑 결과 없음: 오류이며 history insert/counter update 미호출.

### 백엔드 Mapper

- detail resultMap과 SELECT가 `view_count` → `viewCount`로 매핑됨.
- login lookup은 tenant, login code, `use_at='Y'`를 함께 사용함.
- history insert는 지정 복합 키에서 `ON CONFLICT DO NOTHING`을 사용하고 등록된 ID를 반환함.
- counter update는 tenant·document ID·`deleted_yn = 'N'`으로 제한되며 원자 `view_count + 1`식을 사용함.
- 기존 detail 권한 조건, status/approval lines, common events mapping이 유지됨.

### 프론트엔드

- 서버 `viewCount`와 detail의 drafter/date가 작성자 metadata 행에 표시됨.
- API 서비스는 `viewCount`가 0 이상의 정수인지 검증하며, 누락·음수·분수이면 기존 상세 응답 계약 오류(`전자결재 상세 응답을 확인할 수 없습니다.`)를 반환한다.
- 서비스 테스트에서 `viewCount`가 누락, 음수, 정수가 아닌 경우 상세 응답 계약 오류를 검증한다.
- 화살표는 참여자 수 - 1개, 참여자 순서는 stage/participant order와 일치한다.
- 합의·참조 각 행에 원래 순번이 있고 chip은 렌더링되지 않는다.
- 중앙 순번+이름, 긴 이름 말줄임, `PENDING`의 `진행` seal, 읽기 전용 유지.

### 반응형 및 문서

- 375px, 768px, 1280px에서 approval flow 외부의 수평 overflow가 없다.
- 브라우저 캡처는 공유 개인정보를 가리고 지정 결과 폴더에 저장한다.
- 실행한 테스트/빌드, MCP 확인 근거, DB migration/rollback 파일 및 미적용 여부를 결과 문서에 기록한다.
