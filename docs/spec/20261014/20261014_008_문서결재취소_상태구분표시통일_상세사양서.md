# 20261014_008 문서 결재 취소 및 상태·구분 표시 통일 상세 사양서

## 문서 목적

[승인 설계](../../superpowers/specs/2026-10-14-document-approval-cancel-status-consistency-design.md) 및 [작업지시서](../../directions/20261014/20261014_008_문서결재취소_상태구분표시통일_작업지시서.md)를 구현 가능한 API, 상태 전이, 표시 규칙 및 검증 조건으로 구체화한다.

## 결재 취소 API

기존 `/api/v1/groupware/approvals` 리소스와 인증 방식을 사용한다. 요청 본문은 없으며 인증 사용자와 경로 문서 ID를 전달한다.

| Method | 경로 | 허용 행위 | 정상 응답 |
|---|---|---|---|
| `POST` | `/{electronicApprovalId}/submission-cancellation` | 기안자의 상신 취소 | 기존 `ResultVO`의 `item`에 `DocumentApprovalDraftVO`, 상태 `DRAFT` |
| `POST` | `/{electronicApprovalId}/approval-cancellation` | 본인 `APPROVED` 결재선 취소 | 기존 `ResultVO`의 `item`에 `DocumentApprovalDraftVO`, 복귀 상태 `PENDING` 또는 `IN_PROGRESS` |

두 요청 모두 문서 행을 잠근 뒤 한 트랜잭션에서 권한/상태를 검증하고 변경 및 시스템 이력을 기록한다. 잘못된 ID, 문서 미존재, 권한 부족, 허용되지 않는 상태, 후속 결재 처리 또는 갱신 충돌은 기존 백엔드 오류 응답 규칙으로 실패시킨다. 프론트엔드는 실패를 성공으로 간주하지 않고 오류를 사용자에게 표시한다.

## 기안자 상신 취소

### 허용 조건

- 인증 사용자와 문서의 기안자가 일치한다.
- 문서가 삭제되지 않았고 현재 상태가 `PENDING`이다.
- `PENDING`은 첫 결재/합의 참여자가 처리하기 전의 상신 상태다.
- 인증 사용자 검증뿐 아니라 테넌트 조건도 모든 문서/결재선 갱신에 적용한다.

### 상태 전이

| 대상 | 취소 전 | 취소 후 |
|---|---|---|
| 문서 | `PENDING` | `DRAFT`, `submitted_at = NULL` |
| 승인/합의 결재선 | 처리되지 않은 `PENDING`/`WAITING` | `WAITING`, `pending_at`, `action_at`, `action_comment` 비움 |
| 참조 결재선 | 처리 상태 `NULL` | 처리 상태 `NULL` 유지 |
| 시스템 이력 | 기존 `SUBMITTED` 보존 | `SUBMISSION_CANCELED` 이벤트 추가 |

문서 ID, 본문, 첨부 및 기안선 구성은 보존하며 물리/논리 삭제하지 않는다. 취소된 임시저장 문서는 기존 편집 흐름을 통해 다시 상신할 수 있다.

### 거부 조건

`IN_PROGRESS`, `COMPLETED`, `REJECTED`, `REVISION_REQUESTED`, 다른 사용자의 문서, 존재하지 않는 문서는 취소할 수 없다. 상태 확인과 갱신 사이 경쟁으로 조건부 갱신이 한 행을 변경하지 못하면 전체 작업 및 이력 추가를 롤백한다.

## 결재자 승인 취소

### 허용 조건

- 문서 상태가 `PENDING` 또는 `IN_PROGRESS`이다.
- 인증 사용자가 해당 문서에서 `APPROVAL` 또는 `AGREEMENT` 역할의 `APPROVED` 결재선 당사자다.
- 1단계 자동 승인 기안선은 상신 완료 표시이며 승인 취소 대상으로 보지 않는다. 기안자의 취소는 상신 취소 기능으로만 수행한다.
- 현재 사용자 단계보다 높은 `stage_order`에서 `APPROVAL`/`AGREEMENT` 참여자의 처리 상태가 `APPROVED`, `REJECTED` 또는 `RETURNED`인 항목이 없다.
- 같은 단계의 병렬 합의/결재 동료 처리는 취소 제한에 포함하지 않는다.
- 결재 행위 및 문서 상태 검증은 잠금이 유지되는 동일 트랜잭션에서 수행한다.

### 상태 전이

| 대상 | 취소 전 | 취소 후 |
|---|---|---|
| 본인 결재선 | `APPROVED` | `PENDING`, `action_at` 및 `action_comment` 비움 |
| 뒤 단계의 미처리 활성선 | `PENDING` | `WAITING`, `pending_at` 비움 |
| 같은 단계 동료 | 기존 처리 상태 | 변경 없음 |
| 문서 | `PENDING` 또는 `IN_PROGRESS` | 1단계 자동 승인 기안선을 제외한 처리된 승인/합의선이 남으면 `IN_PROGRESS`, 없으면 `PENDING` |
| 시스템 이력 | 기존 승인 이벤트 보존 | `APPROVAL_CANCELED` 이벤트 추가 |

뒤 단계에 처리 기록이 없으면 해당 단계가 이미 활성화되어 있어도 취소를 허용하고 `WAITING`으로 되돌린다. 뒤 단계가 처리된 경우, 최종 완료(`COMPLETED`), 반려(`REJECTED`) 또는 보완요청 처리(`REVISION_REQUESTED`/`RETURNED`)는 이 기능으로 취소하지 않는다.

## 공통 표시 메타데이터

내부 상태 코드를 변경하지 않고 화면 라벨/색상을 공통 프론트 메타데이터로 변환한다. 색상은 텍스트와 함께 사용한다.

| 문서 상태 코드 | 표시 라벨 | 배지 색상 의미 |
|---|---|---|
| `DRAFT` | 임시저장 | 중립 |
| `PENDING` | 결재진행중 | 파랑 |
| `IN_PROGRESS` | 결재진행중 | 파랑 |
| `COMPLETED` | 승인 | 초록 |
| `REJECTED` | 반려 | 빨강 |
| `REVISION_REQUESTED` | 보완요청 | 주황 |

| 문서 유형 코드 | 작성/필터 정식명 | 배지 라벨 | 배지 색상 |
|---|---|---|---|
| `DRAFTING` | 기안서 | 기안 | 파랑 |
| `BUSINESS_CONTACT` | 업무연락 | 업무 | 청록 |
| `EXPENSE_RESOLUTION` | 지출결의서 | 지출 | 주황 |
| `ATTENDANCE_APPLICATION` | 근태신청 | 근태 | 보라 |

- 리스트, 피드, 상세는 같은 표시 조회 함수를 사용한다.
- 상세에는 상태 배지와 문서 구분 배지를 모두 표시한다.
- 공통 리스트의 구분 색상은 선택적 타입으로 전달하며, 지정하지 않은 기존 리스트 항목은 기존 기본 색상을 유지한다.
- 작성 폼과 필터의 정식 유형명은 변경하지 않는다.

## 본문 접기 및 결재선

- 긴 본문처럼 접기/확장이 활성화된 경우 접힌 상태에서는 결재선 영역 및 구분선을 숨긴다.
- `더보기` 후 본문과 결재선을 함께 표시하고 `접기` 후 함께 숨긴다.
- 짧은 본문 또는 접기 기능이 없는 본문은 현재처럼 결재선을 항상 표시한다.
- 이 조건은 문서 상세/피드 구성요소의 기존 본문 확장 상태를 사용한다. 공통 `FeedBodyContent`와 공지사항의 확장 동작은 변경하지 않는다.

## DB 변경 사양

신규 테이블/컬럼은 없다. `tb_common_comment`의 `chk_tb_common_comment_event_type` 제약에 다음 두 SYSTEM 이벤트를 추가한다.

- `SUBMISSION_CANCELED`
- `APPROVAL_CANCELED`

PostgreSQL MCP에서 확인한 기존 허용 이벤트는 `APPROVED`, `REJECTED`, `RETURNED`, `DRAFT_SAVED`, `SUBMITTED`, `RESUBMITTED`, `COMPLETED`, `DELETED`다. 기존 `USER` 이벤트의 `event_type IS NULL`, `SYSTEM` 이벤트의 비어 있지 않은 허용 이벤트 조건을 유지한다. 변경 이력 및 롤백 파일은 `20261014_003` 번호로 `docs/database/20261014/`와 `backend/DATABASE/20261014/`에 동일하게 생성한다. 롤백은 두 신규 이벤트를 참조하는 행이 존재하면 적용할 수 없음을 기록한다. MCP는 읽기 전용이며 DDL 적용 여부를 주장하지 않는다.

## 검증 기준

- 백엔드 서비스: 기안자 본인/PENDING만 취소 성공; 타인, 처리 후 상태, 없는 문서는 실패; 본문/첨부 식별은 보존; 결재선 초기화 및 취소 이력 기록을 확인한다.
- 백엔드 승인 취소: 본인 APPROVED 성공; 타인/미승인/후속 처리/최종 완료는 실패; 같은 단계 동료는 유지; 다음 단계 미처리선만 되돌림; 남은 처리선에 맞는 문서 상태를 확인한다.
- API: 두 POST 경로가 올바른 service method를 호출하고 `ResultVO.item` 상태를 반환한다.
- 매퍼: 테넌트/문서/액터 조건, 처리 상태, 단계 순서, 이벤트 초기화 필드, 제출 시각 초기화를 확인한다.
- 프론트엔드: 다섯 상태 라벨/색상, 네 문서 구분 라벨/색상, 상세 문서 구분 표시, 상세 전용 취소 가시성, 확인 취소 시 요청 없음, 성공 시 상세/목록/요약 갱신, 충돌 표시, 긴/짧은 본문 결재선 표시를 테스트한다.
- 통합 검증: 집중 백엔드/프론트엔드 테스트와 프론트엔드 build를 수행하고, 375px/768px/1280px에서 overflow 및 동작을 확인한다. 결과 보고서와 비민감정보 스크린샷을 저장한다.

## 승인된 UI 보완 상세 사양

### 배지 및 결재선 진행 표시

- 상태 및 문서구분 Chip은 화면별 기본값과 무관하게 `border-radius: 8px`을 사용한다.
- `DRAFT` 상태만 outlined로 표시하며, `PENDING`, `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `REVISION_REQUESTED`는 filled로 표시한다. 리스트도 피드·상세와 같은 상태 variant를 사용한다.
- 구분 Chip은 공통 구분 라벨 및 색상을 유지하면서 동일한 8px 반경을 적용한다.
- 결재선의 `PENDING` 테두리는 상태 배지의 `info` 색상과 일치시킨다. 같은 결재선의 상태 도장 테두리와 대체 텍스트도 해당 결재선 테두리 색을 사용한다. 중립 상태의 점선/그 외 상태의 실선 및 실제 도장 이미지 표시는 보존한다. 다른 결재선 상태 색상은 변경하지 않는다.

### 피드 및 상세 결재 툴바

- 피드 카드와 상세 상단 오른쪽 요소의 DOM/시각 순서는 다음과 같다.

  `현재 사용자에게 가능한 결재 동작 → 상태 배지 → 문서구분 배지 → 세로 구분선 → 상단고정 아이콘 → 더보기 아이콘`

- 승인 동작은 primary contained, 반려 및 상세 전용 상신/승인 취소는 error contained, 보완요청은 기존 warning 계열 outlined 버튼을 사용한다.
- 현재 사용자에게 결재 권한이 있으면 피드와 상세 양쪽에서 승인, 반려, 보완요청을 제공한다. 권한이 없으면 세 액션 버튼을 표시하지 않는다.
- 피드 결재 권한 판정에 필요한 현재 사원 ID는 피드 진입 시 한 번 조회해 모든 피드 카드에 공유한다. ID 조회에 실패하면 문서작성 화면에서 오류와 재시도를 제공하며, 카드별 중복 조회를 하지 않는다.
- 상세의 기존 처리 의견 입력 및 필수 사유 검증을 유지한다. 피드의 반려와 보완요청은 사유 대화상자를 열고, 사유가 비어 있으면 요청하지 않는다. 피드의 승인은 확인/사유 대화상자 없이 즉시 기존 승인 요청을 사용한다.
- 상신 취소와 승인 취소는 상세 전용으로 유지하며, 확인 대화상자와 기존 서버 오류 처리/완료 갱신을 사용한다.
- 세로 구분선과 상단고정 아이콘은 툴바 순서에 포함한다. 기존 상단고정 기능의 의미나 상태 변경은 추가하지 않는다.
- 승인, 반려, 보완요청, 상신 취소, 승인 취소 버튼은 문서 상세 댓글 `등록` 버튼과 같은 `size="small"` 크기 규칙을 사용한다(테마의 최소 높이 28px, 상하 padding 4px, 좌우 padding 10px). 버튼 너비는 라벨과 콘텐츠에 맞춘다.
- 결재 상태와 문서구분 Chip은 동일한 8px border-radius 값으로 표시한다.
- 결재 상태 및 문서구분 Chip 높이는 28px로 맞춘다. 액션 버튼은 상세 댓글 `등록` 버튼과 동일한 작은 버튼 크기 및 geometry를 유지한다.
- 툴바의 기존 Stack 간격 4px를 유지한다. 문서구분 Chip 오른쪽에 4px를 추가하여 Chip과 세로 구분선 사이는 총 8px로 표시하고, 세로 구분선과 상단고정 아이콘 사이는 4px로 유지한다. Divider에 별도 좌우 여백을 추가하지 않는다.
- 좁은 화면에서 버튼과 Chip은 줄바꿈할 수 있어야 하며 요소 간 겹침이나 페이지 가로 overflow가 없어야 한다.

### 삭제 메뉴

- 문서 삭제는 `DRAFT`에서만 허용한다. `PENDING`/`IN_PROGRESS` 결재 문서의 더보기 메뉴에서 삭제를 노출하지 않는다.
- 기안자에게 허용된 수정 또는 삭제 항목이 하나도 없으면 더보기 아이콘과 빈 메뉴를 모두 숨긴다.
- `DRAFT` 삭제 및 `REVISION_REQUESTED` 수정 메뉴는 기존 확인/처리 흐름을 보존한다.

### 검증 추가 기준

- 리스트/피드/상세에서 8px 반경과 상태 variant 규칙을 테스트한다.
- 진행 중 도장 테두리/대체 텍스트 색상이 결재선 참가자 테두리 색상과 같고, 상태·문서구분 Chip 높이가 28px인지 테스트한다.
- 툴바 요소의 순서 및 결재 가능한 사용자별 버튼 노출을 테스트한다.
- 툴바 액션 버튼의 댓글 `등록` 버튼 geometry 유지 및 문서구분 Chip 뒤 4px 추가 여백을 테스트한다.
- 피드 반려/보완요청에서 사유가 없을 때 API 호출이 없고, 사유가 있을 때 기존 `processDocumentApprovalAction` 계약으로 처리되는지 검증한다.
- `DRAFT`에서 삭제를 유지하고 상신된 문서에서는 더보기/삭제가 숨는지 검증한다.
- 375px/768px/1280px 실제 브라우저에서 툴바 wrapping, 겹침, overflow 및 각 동작을 확인한다.

자세한 TDD 단계와 파일 단위 작업은 [UI 보완 구현 계획](../../superpowers/plans/2026-10-14-document-approval-ui-refinement.md)을 따른다.
