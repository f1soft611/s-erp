# 회사정보와 거래명세서 상세사양서

## 회사정보

- 기준정보 관리 > 회사정보 관리에서 로그인 테넌트의 회사정보 한 건을 조회·수정한다.
- 기존 `tb_tenant`의 회사명(`tenant_nm`), 사업자번호(`business_registration_number`), 업종(`business_type`), 업태(`business_category`)을 재사용한다. 대표자명, 우편번호, 주소, 전화번호, 팩스번호는 별도 컬럼으로 보강한다.
- 관리자명과 대표자명은 다르므로 관리자명을 대표자로 사용하지 않는다. 다른 테넌트 ID를 요청으로 받지 않는다.
- 조회·수정 API는 `/api/v1/co/master/company`의 GET·PUT, 표준 `ResultVO`의 `item`을 사용한다. JSON 필드는 `companyName`, `businessNo`, `businessType`, `businessCategory`, `presidentName`, `postCode`, `address`, `telephoneNo`, `facsimileNo`이다.
- 회사명은 필수이며 나머지는 빈 값이 허용된다. 저장 시 공백을 정리하고 컬럼 길이를 검증한다. 기존 권한 체계를 적용한다.

## 거래명세서 저장과 연계

- 출하등록에서 생성된 수주출하 또는 직출하 한 건을 선택한다. 출하 1건당 활성 명세서 한 건만 허용하며 다른 테넌트의 출하를 선택할 수 없다.
- 저장 시 출하 헤더와 상세, 회사정보와 거래처정보를 서버에서 읽어 명세서 헤더·상세에 복사한다. 출하의 수량·단가·공급가·VAT·합계를 다시 추정하거나 재계산하지 않는다. 품목코드·품목명·규격·단위도 보존한다.
- 명세서 번호는 테넌트별 유일하게 서버에서 생성한다. 명세일, 비고와 모든 출력값은 명세서에 저장한다.
- 발행 이후 회사, 거래처, 품목, 출하를 변경해도 명세서에 보관된 출력값은 바뀌지 않는다. 명세서 수정 시 명세일과 비고만 변경하며 출하에서 가져온 상세와 공급자·거래처 스냅샷은 변경하지 않는다.
- 명세서 삭제는 사용 여부를 비활성화한다. 삭제 후 동일 출하로 재등록할 수 있다. 저장과 중복 검사는 하나의 트랜잭션과 DB 제약으로 보장한다.
- API는 인증 테넌트 기준으로 처리하며 다른 테넌트의 출하·명세서에는 접근할 수 없다. 기존 메뉴별 조회·등록·수정·삭제 권한을 서버와 화면에 적용한다.

## 화면과 출력

- 출하관리 아래 `거래명세서등록`, `거래명세서현황` 메뉴를 둔다. 메뉴와 권한 등록 SQL 및 롤백을 제공하되 실제 DB에는 적용하지 않는다.
- 등록 화면은 출하등록과 제목·버튼·기본정보·F1Grid 배치와 여백을 동일하게 사용한다. 출하번호 필드의 돋보기로 출하를 선택하고 상세를 표시한다.
- 현황 화면은 필수 명세일 기간으로 검색하며 기존 출하현황의 번호 클릭 상세를 따른다. 상세 보기와 수정은 등록 화면의 폼과 F1Grid를 공유하고 작성자 프로필과 등록일 표시도 기존 패턴에 맞춘다.
- 상세 출력은 저장된 스냅샷으로 공급자·공급받는자 정보(우편번호·팩스 포함), 명세일, 품목코드·품목명·규격·단위·수량·단가·공급가·VAT·합계·비고를 표시한다. A4 미리보기와 브라우저 인쇄를 제공하고 여러 페이지에서 상세가 잘리지 않게 한다.
- 모바일 375px, 태블릿 768px, 데스크톱 1280px에서 실제 렌더링을 확인한다.

## SQL과 검증

- 신규 컬럼과 명세서 테이블은 날짜별 SQL, 변경 이력, 롤백 및 `docs/database/db-schema.md`를 함께 관리한다. SQL은 두 스키마 폴더에 동일하게 둔다.
- 테넌트 격리, 미존재 출하, 중복 및 경쟁 저장, 과거 스냅샷 보존, 명세서 수정·삭제·재등록과 권한을 검증한다.
- 등록과 현황 상세가 같은 폼·그리드를 사용하는지, 품목 다수 인쇄·페이지 나눔 및 인쇄값 보존을 검증한다.
