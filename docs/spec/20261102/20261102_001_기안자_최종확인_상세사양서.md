## 범위와 용어

- 기안서(`DRAFTING`)의 최초 상신 및 보완요청 후 재상신에 적용한다. 승인 액션이 없는 업무연락(`BUSINESS_CONTACT`)의 발송 완료 흐름은 대상이 아니다.
- `FINAL_CONFIRMATION`은 사용자가 작성하는 결재/합의/참조선과 다른 서버 전용 참여 유형이다. 문서의 기안자를 유일한 참여자로 자동 등록한다.
- 최종확인은 최종 문서 상태와 구별되는 확인 여부 기록이다. 확인 전에도 승인 문서는 `COMPLETED`, 반려 문서는 `REJECTED` 상태다.
- `COMPLETED` SYSTEM event는 기존 문서의 이력과 업무연락 발송 이력에서 허용/보존한다. 이 변경은 기안서 최종 승인 때 추가 생성하던 이벤트만 신규 처리부터 중단한다.
- “최종 결재자에게 보낸다”는 앱 내 `내가 최종 확인할 문서` 대기 목록으로 제공한다. 이메일/푸시 발송은 포함하지 않는다.

## 상태 전이

| 이벤트 | 문서 상태 | 결재/확인 행 |
|---|---|---|
| 기안서 상신 | `PENDING` | 기안자 첫 승인 행 `APPROVED`; 첫 실제 결재/합의 단계 `PENDING`; 후속 단계 및 `FINAL_CONFIRMATION` `WAITING` |
| 일반 결재 또는 합의 진행 | `IN_PROGRESS` | 기존 순차/합의 처리 유지; `FINAL_CONFIRMATION` `WAITING` |
| 최종 승인 | `COMPLETED` | 마지막 승인 행 `APPROVED`; `FINAL_CONFIRMATION` `PENDING`, `pending_at=CURRENT_TIMESTAMP` |
| 반려 | `REJECTED` | 반려 행 `REJECTED`; `FINAL_CONFIRMATION` `PENDING`, `pending_at=CURRENT_TIMESTAMP` |
| 보완요청 | `REVISION_REQUESTED` | 보완요청 행 `RETURNED`; `FINAL_CONFIRMATION` `WAITING` |
| 보완 후 재상신 | `PENDING` | 사용자 결재선의 새 회차 초기화; `FINAL_CONFIRMATION` 한 행을 `WAITING`으로 생성 |
| 기안자 최종확인 | 기존 상태 유지 | `FINAL_CONFIRMATION` `PENDING` → `CONFIRMED`, `action_at` 기록 |

- 최종 승인/반려 문서 상태 전환, 현재 결재 처리 이벤트 및 최종확인 행 활성화는 같은 결재 처리 트랜잭션에서 수행한다.
- 기존 `FINAL_CONFIRMATION/WAITING` 행이 있으면 이를 `PENDING`으로 활성화한다. 배포 전 상신되어 행이 없는 진행 중 기안서는 기안자 계정과 문서 스냅샷을 사용해 같은 트랜잭션에서 최종확인 `PENDING` 행을 생성한다.
- 문서/결재 처리 이벤트 저장 또는 최종확인 행의 활성화/생성이 실패하면 전체 전이를 rollback한다.
- 최종확인 액션은 문서의 `document_status`, 결재/반려 행 및 첨부에 변경을 만들지 않는다.
- 반려와 보완요청 구분은 기존 action에 따른다. `REJECTED`만 최종확인 대기 대상이며 `RETURNED`는 대상이 아니다.

## 내부 최종확인 행

- 저장 위치: `tb_electronic_approval_line_info`.
- 생성 시점: `DRAFTING` 최초 상신 또는 `REVISION_REQUESTED` 재상신 트랜잭션에서 서버가 기존 사용자 라인 저장 후 생성한다.
- 생성 값:
  - `participant_type = 'FINAL_CONFIRMATION'`
  - `participant_user_id`는 인증 기안자의 `LoginVO.uniqId`
  - `participant_name`/부서 정보는 상신 시점의 검증된 기안자 정보 사용
  - `stage_order`는 사용자 결재선 및 참조 행의 최대 순번보다 1 큰 값; 예: 사용자 결재 5단계, 참조 없음이면 6
  - `participant_order = 1`, `action_status = 'WAITING'`, `pending_at/action_at/action_comment = NULL`
- 사용자 결재선의 기안자와 최종확인 행은 같은 `participant_user_id`를 사용한다. DB 유일성은 일반 참여자 간 문서별 중복을 계속 막고, 최종확인 유형은 문서당 한 행만 허용하도록 분리한다.
- 배포 전 제출된 진행 중 기안서는 최종 승인/반려 처리 시 최종확인 행이 없으면 그때 `PENDING` 행을 생성해 대기 목록으로 보낸다. 기안자 계정을 tenant 안에서 확인할 수 없거나 행 생성에 실패하면 최종 결재 전이를 rollback한다. 업무연락/기안서가 아닌 문서 및 배포 전 이미 종료된 문서는 backfill하지 않는다.
- 요청 payload의 허용 `participantType`은 기존 사용자 유형(`APPROVAL`, `AGREEMENT`, `REFERENCE`)에 한정한다. 클라이언트가 `FINAL_CONFIRMATION`을 제출하면 400으로 거부한다.
- 업무연락은 기존 참조자 전달 및 `COMPLETED` 전이를 그대로 사용하며 내부 최종확인 행을 만들지 않는다.
- 일반 승인 단계 탐색, 활성화, 일반 결재 권한, 참조확인 대상/목록은 `FINAL_CONFIRMATION`을 반드시 제외한다.
- 확인 상태는 다음만 허용한다.

| 유형 | 상태 | `pending_at` | `action_at` | `action_comment` |
|---|---|---|---|---|
| `FINAL_CONFIRMATION` | `WAITING` | NULL | NULL | NULL |
| `FINAL_CONFIRMATION` | `PENDING` | NOT NULL | NULL | NULL |
| `FINAL_CONFIRMATION` | `CONFIRMED` | NOT NULL | NOT NULL | NULL |

- 활성/확인 쿼리는 tenant, 문서 ID, 내부 행 ID, `FINAL_CONFIRMATION`, 기안자 participant ID를 제한 조건으로 사용한다.

## API

기존 API prefix `/api/v1/groupware/approvals`와 `ResultVO` 응답 관례를 사용한다.

| Method | Path | 인증/권한 | 성공 응답 |
|---|---|---|---|
| `POST` | `/{electronicApprovalId}/final-confirmation` | 기안자, 문서 상태 `COMPLETED`/`REJECTED`, 해당 `FINAL_CONFIRMATION` 행 `PENDING` | `result.item`에 `electronicApprovalId`, `actionStatus=CONFIRMED`, `actionAt` |

- Request body는 없다. 사용자/tenant/행위 시각은 인증 객체와 서버 DB에서 결정한다.
- 확인은 `selectDocumentApprovalForUpdate`로 문서를 잠근 뒤 수행한다. 확인 권한/종료 상태/활성 행을 한 트랜잭션 안에서 검증한다.
- 이미 `CONFIRMED`인 해당 기안자의 행은 새 이벤트를 추가하지 않고 현재 확인 결과를 반환한다.
- 타 사용자/비기안자/타 tenant/문서 미존재는 문서 존재를 노출하지 않는 기존 404 규칙을 따른다. 문서가 최종 상태가 아니거나 확인 행이 활성 상태가 아니면 409다. 잘못된 ID는 400, 미인증은 401이다.
- 참조확인 `POST /{id}/reference-confirmation`의 경로와 권한 판단을 바꾸지 않는다.

## SYSTEM 이벤트

| `event_type` | 발생 조건 | 내용 |
|---|---|---|
| `APPROVED` | 승인자의 결재 성공 | 기존 행위별 승인 이력 유지 |
| `REJECTED` | 결재자의 반려 | 기존 반려 이력 유지 |
| `RETURNED` | 보완요청 | 기존 보완 이력 유지 |
| `FINAL_CONFIRMATION_CONFIRMED` | 기안자의 최종확인 성공 | `기안자가 최종 확인을 완료했습니다.` |

- 새로운 최종확인 SYSTEM event는 확인 상태 갱신과 동일 트랜잭션에서 append-only로 추가한다. `writer_id/name`은 인증 기안자에서, `created_at`은 서버 시각에서 정한다.
- 승인 완료 때 기존에 추가하던 `COMPLETED` event 삽입은 기안서 승인 처리에서 중단한다. `document_status=COMPLETED` 갱신과 최종 승인자 `APPROVED` 이벤트는 계속 저장한다.
- 과거 `COMPLETED` 행은 삭제/변환하지 않는다. 업무연락 발송이 기록하는 기존 `COMPLETED` 이벤트도 유지한다. DB CHECK allowlist에서 `COMPLETED`를 제거하지 않는다.
- 일반 최종 상태 문서의 기존 상세 타임라인 조회가 `FINAL_CONFIRMATION_CONFIRMED`를 SYSTEM 이벤트로 반환한다.

## 목록 및 summary 응답

### 문서작성 API

- scope: `MY_FINAL_CONFIRMATION_PENDING`
- 조건: 현재 인증 사용자의 tenant와 `uniqId`에 연결된 `FINAL_CONFIRMATION/PENDING` 행, 문서 상태 `COMPLETED` 또는 `REJECTED`, 삭제되지 않은 문서.
- 결과는 문서 ID 중복 없이 최신 순서로 기존 `DocumentApprovalListItemVO`/문서 목록 계약을 사용한다.
- `MY_REFERENCE_PENDING`은 `REFERENCE`만 반환한다. `MY_PENDING`은 활성 `APPROVAL`/`AGREEMENT`만 반환한다.
- 기존 summary 응답에 다음 필드를 별도로 추가한다.
  - `finalConfirmationRequiredCount: number`
  - `finalConfirmationItems: DocumentApprovalRecord[]`
- 목록/집계 API 오류는 0건 성공으로 변환하지 않는다.

### 종합현황

- `approval` 객체에도 `finalConfirmationRequiredCount` 및 `finalConfirmationItems`를 독립 필드로 제공한다.
- 참조확인 카드와 별도로 `내가 최종 확인할 문서` 카드를 표시한다. 설명은 `최종 승인 또는 반려된 문서 중 아직 확인하지 않은 문서`로 한다.
- 항목을 선택하면 기존 전자결재 상세를 열며 확인 성공 후 종합현황의 summary를 다시 조회한다.

## 상세 UI

- `FINAL_CONFIRMATION` 참여 행은 일반 결재선 시각화에서 제외한다. 사용자 작성 결재선 및 참조선 표시는 기존 순서/모양을 유지한다.
- 최종확인 목록으로 상세를 연 기안자에게만 `최종확인` 버튼을 제공한다. 문서가 `COMPLETED` 또는 `REJECTED`이고 기안자의 행이 `PENDING`일 때만 노출한다. 서버 권한 검증은 UI 조건과 별도로 항상 수행한다.
- 확인 처리 중 버튼을 비활성화한다. 성공하면 문서 상세/시스템 이력, 문서작성 summary/목록 및 종합현황 summary를 갱신한다. 실패 시 기존 상세 오류 영역에 표시하고 확인 완료처럼 처리하지 않는다.
- SYSTEM event 표시 문구는 이벤트 코드와 무관하게 응답의 `content`를 그대로 사용한다.
- 문서작성 및 종합현황에서 참조확인 카운트/라벨은 그대로 `내가 확인할 문서`로 두고, 최종확인은 `내가 최종 확인할 문서`라고 명확히 분리한다.

## DB migration 및 근거

- 대상 테이블은 `tb_electronic_approval_line_info`, `tb_common_comment`다. 새 테이블/컬럼은 없다.
- 구현 전 `s-erp-postgresql-readonly`의 `list_tables` 후 각 대상 테이블 `describe_table`을 호출해 실제 participant/action/event CHECK, FK 및 적용 상태를 확인한다. 필요한 경우에만 비민감 제약 메타데이터를 제한 조회한다.
- 실제 제약의 이름과 허용 목록을 확인한 뒤 `20261102_003` SQL을 `backend/DATABASE/20261102` 및 `docs/database/20261102`에 동일 생성한다. 기존 메뉴 즐겨찾기 `001` 및 표시명 변경 `002` migration은 보존한다.
- 결재선 CHECK는 기존 `REFERENCE`의 미확인/CONFIRMED 상태와 결재·합의 상태를 보존하면서 위 `FINAL_CONFIRMATION` 세 상태만 추가한다. 기존 참여자 유일 제약은 일반 참여자 중복 및 문서당 최종확인 한 행을 각각 보장하는 partial unique index로 전환한다.
- SYSTEM event CHECK는 기존 허용 코드를 보존하면서 `FINAL_CONFIRMATION_CONFIRMED`를 추가한다. USER event의 `event_type IS NULL` 조건도 유지한다.
- 변경이력 파일에 날짜, 대상 테이블, 변경 내용, 영향 및 rollback 여부를 기재한다. rollback은 새 유형 행/신규 이벤트 사용 행이 있으면 삭제 없이 중단한다.
- `docs/database/db-schema.md`를 함께 갱신한다. DB MCP는 read-only이며 migration을 실제 적용하지 않는다.
- MCP를 사용할 수 없으면 이를 명시하고 날짜별 SQL 이력, 현재 Mapper, domain 코드만 대체 근거로 기록한다. 현재 DB 제약을 확인한 것처럼 기술하지 않는다.

## 검증

### 백엔드

- 상신 요청의 내부 유형 주입 거부, 승인 문서 자동 행 생성, 참조 라인과 stage 충돌 방지, 재상신 새 행 초기화.
- 업무연락 발송은 최종확인 행 없이 기존 완료 동작을 유지.
- 최종 승인: `COMPLETED`, 확인 행 `PENDING`, 신규 `COMPLETED` event 없음, 행위별 `APPROVED` event 존재.
- 동일 기안자의 일반 결재 행과 내부 최종확인 행이 공존하며, 최종확인 행이 없는 배포 전 진행 중 기안서는 최종 승인/반려 시 행을 생성한다.
- 반려: `REJECTED`, 확인 행 `PENDING`, `REJECTED` event 존재.
- 보완요청: `REVISION_REQUESTED`, 최종확인 행 비활성.
- 기안자 확인은 상태 불변, `CONFIRMED`/시각/한 SYSTEM event. 멱등 재요청에서 event 중복 없음.
- 비기안자/다른 tenant/진행 상태/미대기/다른 참여유형 거부 및 이벤트 삽입 실패 rollback.
- 새 목록 및 summary가 사용자/tenant 단위로 정확히 분리되고 참조확인 및 일반 결재 대기 수를 오염시키지 않는다.

### 프런트엔드

- scope parsing, summary 응답 validation, endpoint 요청/오류 전달.
- 최종확인 별도 summary/list, 상세 기안자 전용 액션, 일반 결재선 숨김, 성공 후 전체 summary/detail refresh.
- 종합현황 카드의 참조확인과 최종확인 분리 및 상세 이동.
- 기존 참조확인/결재 처리 테스트 회귀.
- `npm run test`, `npm run build`.
- 실제 브라우저 375px/768px/1280px에서 목록·상세 액션 wrapping, 잘림, 페이지 가로 overflow 확인 및 결과 스크린샷 저장.

## 제외

- 업무연락의 완료/참조확인 변경
- 이메일/푸시 알림, 기안자 확인 취소 또는 대리 확인
