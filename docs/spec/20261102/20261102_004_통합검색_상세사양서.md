## 결정과 범위

화면의 다중 API 합산은 권한/페이징이 흩어지고, 별도 검색엔진은 색인·운영 부담이 크다. **서버 통합 API + 기존 도메인 조회 재사용**을 채택한다. 1차 대상은 메뉴, 본인 관련 전자결재 문서, 공지다. 다른 업무/첨부/댓글/쪽지/이력 저장은 제외한다.

## API

`GET /api/v1/search?keyword=...&type=ALL&offset=0&limit=5`

- 인증 principal에서 tenant/user/역할을 가져온다. 클라이언트 소유자/tenant는 받지 않는다.
- keyword: trim 후 2~100자. type: ALL/MENU/DOCUMENT/NOTICE. offset: 0~10000. limit: 1~20. ALL의 offset은 0만 허용한다. 잘못된 값은 400, 인증 누락은 401이다.
- 기존 ResultVO의 `result.item` 안에 `{groups: SearchGroup[]}`를 반환한다.
- SearchGroup: `{type, items, totalCount, offset, limit}`. ALL은 MENU/DOCUMENT/NOTICE 순서, 개별 요청은 해당 유형만 반환한다. 권한이 없으면 해당 그룹 items=[]/totalCount=0이며 도메인 조회를 하지 않는다.
- SearchItem: `{id:number, type, title, description, path}`. HTML/파일/댓글/본문 원문은 반환하지 않는다.
- 메뉴는 이름·path 대소문자 무시 부분검색, 권한 트리 순서. description은 모듈/상위 메뉴 breadcrumb.
- 문서는 기존 문서현황 keyword(제목·문서번호·기안자), updatedAt DESC 기존 정렬/동률 ID 순서, 총건수/offset/limit을 재사용한다. description은 문서번호·기안자다.
- 공지는 기존 DAO keyword(제목·본문 텍스트·작성자), createdAt DESC/postId DESC 및 총건수/페이지를 재사용한다. 목록의 첨부/댓글 hydration은 호출하지 않는다. description은 작성자다.
- 문서/공지의 `%`, `_` 검색어 의미는 기존 도메인 SQL의 ILIKE 규칙을 유지한다.
- 조회 장애는 실패로 반환하고 빈 성공으로 위장하지 않는다. 모달에서 재시도한다.

## 권한과 이동

- 메뉴는 `SystemMenuService`가 반환한 활성 READ leaf만 반환하고 그룹/URL 없는 노드는 제외한다. 내부 단일 `/`로 시작하는 path만 허용한다.
- 문서는 상세를 표시하는 `/groupware/doc/write` READ가 있어야 검색한다. 기존 `DocumentApprovalStatusService.searchDocuments`의 tenant/deleted/본인 기안 또는 비초안 결재선 관련자 규칙을 그대로 사용한다. 상태 화면만 읽을 수 있고 문서작성 상세 메뉴에 접근할 수 없으면 보수적으로 문서 검색을 제공하지 않는다.
- 공지는 `/groupware/community/notice` READ가 있을 때 같은 tenant의 NOTICE/is_deleted=N만 검색한다.
- 문서 선택: `/groupware/doc/write?approvalId={id}`. 공지 선택: `/groupware/community/notice?dashboardPostId={id}`. 같은 공지 화면의 query 변경도 처리한다. 상세 API의 기존 권한/삭제 검증은 유지한다.
- 메뉴 선택은 원래 허용된 path로 이동한다. 검색 중에는 현재 콘텐츠/메뉴를 바꾸지 않는다.

## 화면과 상태

- 우측 상단 알림 앞 검색 아이콘. Tooltip/aria-label은 `통합검색`.
- 공통 CommonDialog size=md, 모바일 fullScreenOnMobile. 검색 필드, 조회 버튼, 전체/메뉴/문서/공지 유형 선택.
- Enter/조회 버튼으로 2자 이상 검색하며 100자 제한. 입력 중 자동 전체 조회나 검색 이력 저장은 없다.
- 전체는 각 유형 5개와 해당 유형 총건수. 더보기는 선택 유형 첫 페이지(10개)로 전환한다. 개별 유형은 이전/다음 페이지를 제공한다. limit를 넘는 대량 결과를 로딩하지 않는다.
- 조회 중 이전 결과는 감추고 상태를 표시한다. 빈 결과, 오류/재시도, 검색 전 안내를 구분한다.
- 새로운 검색/유형/페이지 요청 및 닫기 시 요청 세대를 바꿔 이전 응답의 상태 갱신을 막는다.
- 닫기 후 재진입은 빈 검색 상태. 결과는 React 평문이며 제목은 줄바꿈하고 path/설명은 overflow-wrap한다.
- 조회는 키보드 Enter, 결과는 Tab/Enter, 모달은 Escape/닫기 버튼으로 조작한다.

## DB 확인

읽기 전용 기본 PostgreSQL MCP의 list_tables 후 describe_table로 `tb_menu`, `tb_electronic_approval_main`, `tb_board_post`를 확인했다. menu_url/use_at, document_no/title/drafter_id/deleted_yn/tenant_id 및 공지 contents_text/board_type_code/is_deleted/tenant_id가 존재한다. 행 데이터/자격 증명은 조회하지 않았다. 기존 DAO/서비스를 재사용하므로 신규 테이블/컬럼/SQL migration은 없으며 DB에 DDL을 적용하지 않는다.

## 검증

서버: 인증, 잘못된 검색조건, READ leaf만 반환, 조회권한 없는 도메인 비호출, tenant/principal 전달, 기존 관련자 검색 서비스 재사용, 정상 응답/페이지/조회 실패.
프런트: API 파라미터, 검색 조건, 유형/페이지, 오류 재시도, 응답 역전/닫기 무효화, 결과 URL 이동, 같은 화면 공지 링크 변경.
실브라우저: 375/768/1280px, 공통 모달과 결과 목록/유형 버튼/페이지 controls에 의도하지 않은 가로 overflow가 없는지 확인하고 스크린샷을 저장한다.
