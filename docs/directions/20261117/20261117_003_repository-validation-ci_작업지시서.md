# 저장소 검증 환경 정합성 및 CI 작업지시서

## 요청과 순서

1. 공유 서버 사용 종료 후 잠금 파일 기준으로 프론트엔드 설치를 맞춘다.
2. 리뷰에서 재현된 저장키·테마 테스트 실패와 미완료 문서작성 테스트를 조사한다.
3. CI에 설치·lint·타입/빌드·전체 테스트 검사를 추가한다.

## 안전한 실행 범위

- 현재 4173 공유 서버와 동시 진행 중인 견적·출하 API 작업은 임의 종료·수정하지 않는다.
- 사용 종료를 확인할 수 없는 동안 `.worktrees/validation-ci`에 격리 설치하여 먼저 검증한다. 공유 작업 공간의 설치 완료로 표현하지 않는다.
- 의존성 버전 갱신 없이 기존 `package-lock.json`을 사용한다.
- 확정된 원인의 최소 수정만 적용하며 전체 기존 실패를 무관한 제품 변경으로 해결하지 않는다.
- 실제 DB, 백엔드 전체 테스트, 인증된 사용자 세션은 사용하지 않는다.
- 초기 검증 단계에서는 커밋·푸시·원격 브랜치 보호 정책을 변경하지 않는다. 아래 후속 지시로 이번 작업의 비구매 변경에 한해 커밋·푸시를 허용하며 원격 보호 정책은 계속 제외한다.

## 후속 지시: 구매 제외 및 발행

- 사용자 요청에 따라 구매 소스 세 파일의 임시 저장키 변경과 공통 문서의 해당 적용 안내를 철회한다. 다른 담당자의 변경은 보존한다.
- 구매 담당자 전달용 문서에 재현 조건, 대상 파일, 제안 키, 남은 실패, 완료 기준을 정리한다. 구매 코드와 테스트는 이번 커밋에서 변경하지 않는다.
- 테마 테스트, npm 검증 명령, CI, 이번 작업 문서·검증 자료만 명시적으로 선택하여 커밋·푸시한다. 다른 담당자의 미커밋 변경은 포함하지 않는다.
- 원격을 fetch한 뒤 현재 브랜치와 upstream의 커밋 일치를 확인한다. 강제 푸시·임의 merge·공유 서버 종료는 하지 않는다.
- 구매 변경 철회 후 저장키 검사가 다시 실패하는 것은 미반영 요구사항으로 공개하며 검사 제외로 숨기지 않는다.

## 완료 기준

- 잠금 파일 설치와 실행 버전, 공유 설치의 변경 여부를 구분해 기록한다.
- 재현된 실패의 원인과 수정 또는 미해결 근거, 문서작성 테스트의 종료 여부를 남긴다.
- CI는 실패를 숨기거나 테스트를 제외하지 않고 최소 권한으로 실행한다.
- 코드·문서 정합성과 관련 검증 결과를 `docs/result/20261117/repository-validation-ci`에 기록한다.
