# 20261117_006 기존 현황 화면 상태 조회 3종 정비 작업지시서

## 작업 목적

취소(`use_at='N'`)로 이력을 남기는 업무의 현황 화면은 상태 조회를 **정상(기본) / 취소 / 전체(취소 포함)** 세 가지로 제공한다(2026-11-17 사용자 확정). 입고현황·자재수입검사현황은 이 규칙으로 만들었고, **기존 발주현황·가입고현황**을 같은 규칙으로 정비한다.
지금은 두 화면 모두 상태 조건의 기본값이 없고 선택지도 정상/취소 2개뿐이라, 기본 조회에 취소건이 섞여 나오고 전체 조회를 만들 수 없다.

## 조사 결과 (2026-11-17)

| 화면 | 현재 | 판단 |
| --- | --- | --- |
| 발주현황 | 서버: 상태 없으면 필터 없음(취소건 포함), `ACTIVE`/`CANCELED`만 허용. 화면: 선택지 정상/취소, 기본값 없음 | **정비 대상** |
| 가입고현황 | 발주현황과 동일 | **정비 대상** |
| 구매요청현황 | 서버가 `use_at='Y'`로 고정(삭제한 요청은 영구히 안 보임). 화면의 상태 검색은 업무 상태(요청/부분확정/확정) | **변경 없음**(사용자 확정). 구매요청은 취소가 아니라 삭제(되돌릴 수 없음)이며 이력을 보여 주는 업무가 아니다 |
| 구매요청확정 목록(불러오기 창) | 상태(사용/취소) 선택을 이미 제공 | 불러오기 창이며 현황 화면이 아니므로 범위 밖 |
| 입고현황, 자재수입검사현황 | 이미 3종, 기본 정상 | 정비 불필요 |

## 업무 규칙

- 상태 조회 값: `ACTIVE`(정상, **기본**), `CANCELED`(취소), `ALL`(전체, 취소 포함). 기본 조회는 취소건을 제외한다.
- 서버: 상태 값이 없으면 `ACTIVE`로 본다. 허용 값은 `ACTIVE`/`CANCELED`/`ALL`, 그 외는 400.
- 화면: 상태 검색의 선택지는 정상·취소·전체, 기본값은 정상이다. 처음 진입에서 상태가 정상으로 선택되고 적용 조건 칩 "상태: 정상"이 보여야 한다. 상태는 필수 조건이라 칩에서 제거할 수 없고, 빈 값 "전체" 선택지는 만들지 않는다(옵션의 "전체"와 겹침). 예전에 저장된 검색 세션(상태 없음)이 남아 있어도 정상으로 시작한다. 입고현황·자재수입검사현황에도 같은 규칙을 적용한다(실서버 확인 중 사용자가 발견).
- 취소건 행은 목록에서 상태 열로 구분되고, 취소된 발주·가입고는 기존대로 조회·상세만 가능하다(기존 동작 유지).

## 범위

### 포함
- 백엔드: 발주현황·가입고현황 서비스의 상태 기본값(`ACTIVE`)과 `ALL` 허용, 테스트.
- 프론트: 두 현황 화면의 상태 선택지(전체 추가)·기본값·세션 복원 처리, 테스트.
- 결과 문서(스크린샷 포함), 메모리 규칙 갱신.

### 제외
- 구매요청현황(변경 없음), DB 변경 없음(스크립트·`db-schema.md` 변경 없음), 메뉴·권한 변경 없음.
- 전체 프론트 테스트 실행(별도 작업).

## 구현 절차
1. 계획서, 상세사양서(번호 `20261117_006`)
2. 백엔드 실패 테스트 → 구현
3. 프론트 실패 테스트 → 구현
4. 검증: 집중 테스트, 빌드, JDK 8 호환 컴파일, 실서버 API·브라우저 확인(데이터를 여러 건 만들어 정상·취소·전체를 모두 확인)
5. 결과 문서 `docs/result/20261117/status-filter-three-way`

## 완료 조건
- 발주현황·가입고현황을 처음 열면 정상건만 조회되고, 상태에서 취소·전체를 선택하면 해당 건이 조회된다.
- 취소한 발주·가입고가 기본 조회에서 사라지고 취소 조회와 전체 조회에서 보인다.
- 서버에 상태 없이 요청해도 정상건만 반환하고 `ALL`은 취소건을 포함한다.
- 기존 현황 화면의 다른 동작(상세·수정·취소·링크)은 바뀌지 않는다.
