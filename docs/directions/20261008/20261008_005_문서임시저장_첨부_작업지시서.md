# 20261008_005 문서 임시저장 및 첨부 저장 작업지시서

## 작업 목적

문서작성 화면의 임시저장을 실제 S-ERP 중앙 PostgreSQL 저장으로 연결한다. 문서 본문, 결재·합의·참조 결재선, 시스템 저장 메시지를 함께 저장하고, 공지사항 작성과 같은 첨부 UI/목록 동작을 결재 문서 권한 검증과 함께 제공한다.

## 확인된 전제

- 대상은 `s-erp_central`이며 tenant는 `tenant_id`로 분리한다.
- 사용자는 `tb_common_comment.comment_type`, `tb_common_comment.event_type` 컬럼이 중앙 DB에 이미 적용됐다고 확인했다. 구현 전 읽기 전용 DB 메타데이터를 조회해 실제 타입·기본값·제약을 확인한다.
- `tb_electronic_approval_main`, `tb_electronic_approval_line_info`는 20261008 저장 스키마 초안을 기준으로 하되, 실제 DB 계약과 다른 점이 있으면 구현 전에 기록하고 상세 사양을 조정한다.
- 현재 문서작성 화면에는 저장 API가 연결되어 있지 않다. 결재선 설정, 참조자, 본문, 제목, 첨부 선택은 작성 화면 상태에 보유된다.
- 공지사항의 첨부 UX를 참조하되, 공통 파일 서비스 사용 시 결재 문서별 권한 검사가 누락되지 않도록 별도 경계를 둔다.
- 공통 파일 서비스는 tenant/owner/파일명 조합으로 MinIO object key를 구성하므로, 동일 owner 내 같은 이름 파일 업로드가 객체를 덮어쓸 위험이 있다. 이번 작업에서 공통 경로의 고유 object key 생성으로 보완한다.
- 현재 MinIO 업로드 후 DB 메타데이터 저장에 실패하면 객체가 남을 수 있다. 고유 key 생성과 함께 해당 객체만 보상 삭제하고, 보상 삭제 실패도 원래 저장 오류와 함께 관찰 가능하도록 처리한다.

## 승인된 작업 범위

1. 문서작성 화면의 명시적 `임시저장` 동작을 구현하고 저장 중/성공/실패 상태를 표시한다.
2. `tb_electronic_approval_main`에 문서 유형, 제목, 본문 JSON/HTML/평문, 작성자 스냅샷 및 `DRAFT` 상태를 저장한다.
3. `tb_electronic_approval_line_info`에 결재·합의·참조 참여자를 사람별 행으로 저장하고 단계 및 단계 내 순서를 보존한다.
4. 본문/결재선 저장과 `tb_common_comment`의 `SYSTEM`/`DRAFT_SAVED` 메시지 등록을 하나의 DB 트랜잭션으로 수행한다.
5. 같은 작성 세션의 재저장은 새 문서 생성 대신 기존 초안을 갱신한다. 시스템 저장 메시지는 명시적 저장 시점마다 추가한다.
6. 공지사항 작성 첨부 UI와 같은 파일 선택, 확장자별 아이콘, 파일 목록 및 개별 제거 UX를 제공한다.
7. 첨부 바이너리와 메타데이터는 MinIO 및 `tb_common_file`을 재사용해 `owner_type='APPROVAL'`, `owner_id=<electronic_approval_id>`로 저장한다.
8. 결재 전용 첨부 API에서 인증 tenant 및 문서 권한을 확인한 뒤 공통 파일 서비스를 호출한다. 파일 행위자 ID는 인증 principal에서 설정한다.
9. 공통 댓글 API의 목록/등록 경로에서 `owner_type='APPROVAL'`을 차단하고, 일반 수정/삭제/답글 경로에서 SYSTEM 행을 변경하지 못하게 한다.
10. 공통 파일 서비스의 object key를 파일별 고유 값으로 생성해 같은 owner에 같은 파일명을 업로드해도 기존 MinIO 객체를 덮어쓰지 않게 한다. 표시 파일명과 기존 파일 접근은 보존한다.
11. 파일 메타데이터 저장/확인에 실패하면 이번 업로드의 고유 MinIO 객체만 보상 삭제한다. 보상 삭제가 실패해도 원래 저장 오류를 유지하고 정리 오류를 기록한다.
12. 파일 업로드의 부분 실패와 재시도를 정확히 표시하고, 문서 중복 생성과 확인된 성공 파일의 중복 업로드를 방지한다.
13. 실제 DB 제약 변경이 필요한 경우에만 날짜별 forward/change-record/rollback SQL 및 `db-schema.md` 갱신을 작성한다. 실제 DB에는 DDL을 실행하지 않는다.

## 이벤트 계약

- 이번 작업에서 기록하는 시스템 이벤트는 `DRAFT_SAVED`만이다.
- `SUBMITTED`, `APPROVED`, `REJECTED`, `RETURNED` 및 기타 상태 전이 이벤트는 후속 작업지시서에서 구현한다.
- `event_type` 허용 코드와 시스템 이벤트 생성 경로는 백엔드에서 검증한다. 저장소의 `20261008_003` DDL은 `DRAFT_SAVED`를 허용하지 않으므로 `20261008_004` 제약 확장 migration 초안을 작성하되, 중앙 DB 메타데이터를 재확인할 수 없으면 미적용 상태와 대체 근거를 결과 문서에 명시한다. 컬럼을 다시 추가하지 않는다.
- SYSTEM 행은 일반 사용자 수정·삭제·답글·좋아요 대상으로 허용하지 않는다.

## 작업 절차

1. 승인 설계 문서와 이 작업지시서를 대조하고, backend/frontend 영역 지침을 확인한다.
2. DB MCP 읽기 전용 도구로 중앙 `tb_common_comment`, `tb_electronic_approval_main`, `tb_electronic_approval_line_info`, `tb_common_file`의 존재 여부, 관련 컬럼 및 제약을 확인한다. 사용할 수 없으면 버전관리 SQL·매퍼·도메인 코드의 대체 근거와 미확인 사항을 기록한다.
3. 실제 문서작성 저장 버튼/데이터 구조, 인증 사용자 키, 공지 첨부 업로드 정책 및 공통 파일 API 권한 경계를 점검한다.
4. 계획서에서 백엔드 문서 저장·이벤트 트랜잭션, 결재 전용 첨부 권한 검사, 프론트 저장·재시도 UX, 회귀 검증을 구현 가능한 작업으로 나눈다.
5. 상세 사양서에서 API 계약, 저장 필드 변환, 결재선 재저장 규칙, 파일 업로드 실패 동작, 이벤트/권한/검증을 확정한다.
6. 실패 테스트를 먼저 작성하고 백엔드 저장/권한 경로를 구현한다.
7. 공지 첨부 패턴을 재사용해 프론트 문서 임시저장 및 파일 목록/제거/재시도를 구현한다. 불명확한 업로드 결과는 목록을 대조하기 전 자동 재전송하지 않는다.
8. 데이터베이스 변경이 필요한 경우에만 동일한 migration을 `backend/DATABASE/20261008/` 및 `docs/database/20261008/`에 작성하고 `docs/database/db-schema.md`를 동기화한다.
9. 관련 테스트, 백엔드 테스트/빌드, 프론트 테스트/빌드 및 375px/768px/1280px 브라우저 검증을 수행한다.
10. 결과 보고서와 화면 스크린샷을 `docs/result/20261008/document-draft-persistence/`에 기록한다.

## 범위 제외

- 결재 신청, 승인, 합의 처리, 반려/반송, 회수 및 상태 전이
- 일반 사용자 댓글, 답글, 댓글 수정/삭제 및 좋아요
- 자동저장과 기존 문서함에서 저장된 문서 검색/재진입
- 결재선 즐겨찾기와 양식 관리 변경
- 무관한 공지사항/공통 파일 리팩터링
- 개발/공유/운영 데이터베이스에 DDL 또는 업무 데이터 변경

## 완료 기준

- 명시적 임시저장 후 문서 본문과 결재·합의·참조 행이 저장되고 동일 작성 세션 재저장 시 문서 ID가 유지된다.
- 발급된 임시저장 문서 ID는 모달 제목 바로 아래 공통 description 영역에 표시하고, 본문에는 중복 표시하지 않는다.
- 문서/결재선 중 하나 또는 SYSTEM 메시지 저장이 실패하면 관련 DB 변경이 모두 rollback된다.
- 성공한 명시적 저장마다 `SYSTEM`/`DRAFT_SAVED` 이벤트가 한 건 기록되고 인증 행위자 정보가 사용된다.
- 첨부 UI/목록은 공지사항 작성 UX와 일관되고 `APPROVAL` 첨부 API에서 문서 권한이 검증된다.
- 범용 댓글 API가 전자결재 댓글 목록/등록을 노출하지 않고 SYSTEM 댓글 수정/삭제/답글을 거부한다.
- 같은 owner에 같은 파일명을 반복 업로드해도 각 파일의 MinIO object key가 고유하고 다른 파일 내용이 유지된다.
- DB 메타데이터 저장 실패 시 방금 올린 객체만 정리하며, 정리 실패가 원래 저장 실패를 덮어쓰지 않고 로그와 테스트에 드러난다.
- 부분 업로드 실패가 문서 저장 성공과 구분되어 안내되고, 성공 파일을 중복 등록하지 않고 실패 파일을 재시도할 수 있다.
- 업로드 결과가 불명확한 파일은 `unknown`으로 표시되고, 서버 첨부 목록 대조 전에는 자동 재업로드되지 않는다.
- 관련 백엔드/프론트 검증 및 반응형 브라우저 검증이 완료되며 결과 문서와 스크린샷이 포함된다.
- DB MCP 확인 근거 또는 실패 사유와 대체 근거가 결과 문서에 남는다.
