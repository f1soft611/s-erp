# 작업지시서

## 제목

권한 관리 페이지 패턴 기반 모듈 관리 페이지 추가

## 작업 분류

- 경로: `bounded`
- 사유: 기존 환경설정 > 시스템관리 화면 구조, 권한 관리 페이지의 PageHeader/PageSearchArea/PageMessageArea/F1-Grid 패턴, 기존 모듈 CRUD API를 재사용해 모듈 마스터 관리 화면을 추가한다. 새로운 권한 정책이나 대규모 백엔드 구조 변경은 포함하지 않는다.

## 배경

환경설정 > 시스템관리에는 메뉴 관리와 권한 관리 화면이 F1-Grid 기반으로 구성되어 있다. 백엔드에는 이미 `/api/v1/system/modules` 모듈 목록/등록/수정/삭제 API가 존재하고, 메뉴 관리 서비스에서도 모듈 목록을 조회해 사용하고 있다.

현재 모듈 마스터를 직접 관리하는 전용 프론트엔드 페이지가 없어 모듈 코드, 모듈명, 아이콘, 루트 경로, 정렬 순서, 사용 여부를 화면에서 관리하기 어렵다. 권한 관리 페이지와 같은 페이지 패턴을 적용하되, 모듈 관리는 관계 매핑 영역 없이 F1-Grid 1개로 충분한 구조로 구현한다.

## 목표

1. 환경설정 > 시스템관리 하위에 모듈 관리 페이지를 추가한다.
2. 권한 관리 페이지와 동일한 화면 패턴을 사용한다.
   - 상단 경로 영역
   - 상단 조회/저장 버튼 영역
   - 검색 영역
   - 메시지 영역
   - 콘텐츠 영역: 모듈 관리 F1-Grid 1개
3. 기존 모듈 CRUD API와 연동해 모듈 목록 조회, 신규 등록, 기존 수정, 삭제를 처리한다.
4. F1-Grid의 dirty 상태를 기준으로 저장 버튼 활성화와 저장 후 기준 데이터 갱신 흐름을 제공한다.
5. 기존 메뉴 관리/권한 관리 화면의 스타일, 권한 처리, 오류 메시지 패턴과 일관성을 유지한다.

## 요구사항

### 1. 화면 구성

- 신규 모듈 관리 페이지는 `frontend/src/pages/settings/system/modules/` 하위에 기존 페이지 구조와 유사하게 구성한다.
- 페이지 컴포넌트는 화면 조립과 조회/저장 흐름을 담당하고, F1-Grid 세부 동작은 패널 컴포넌트로 분리한다.
- 검색 영역에는 모듈 코드, 모듈명, 루트 경로, 아이콘명 기준 통합 검색 입력을 제공한다.
- 메시지 영역은 조회/저장/삭제 실패 메시지를 표시하고 닫을 수 있어야 한다.
- 콘텐츠 영역은 모듈 관리 F1-Grid 1개만 표시한다.

### 2. F1-Grid 컬럼 및 편집

- 모듈 관리 그리드는 최소 다음 컬럼을 제공한다.
  - 모듈 코드
  - 모듈명
  - 아이콘명
  - 루트 경로
  - 정렬 순서
  - 메뉴 수
  - 사용 여부
- 신규 행은 F1-Grid 컨텍스트 메뉴의 행 추가 흐름을 사용한다.
- 모듈 코드, 모듈명, 아이콘명, 루트 경로, 정렬 순서, 사용 여부는 편집 가능해야 한다.
- 메뉴 수는 서버 조회값을 표시하며 편집하지 않는다.
- 신규/수정 저장 시 모듈 코드와 모듈명은 필수값으로 검증한다.

### 3. API 연동

- 목록 조회는 기존 `/api/v1/system/modules` 응답을 사용한다.
- 신규 등록은 `POST /api/v1/system/modules`를 사용한다.
- 기존 수정은 `PUT /api/v1/system/modules/{id}`를 사용한다.
- 삭제는 `DELETE /api/v1/system/modules/{id}`를 사용한다.
- 요청 값은 기존 백엔드 `SystemModuleSaveRequestVO` 필드에 맞춘다.
  - `moduleCode`
  - `moduleNm`
  - `iconNm`
  - `moduleUrl`
  - `sortOrder`
  - `useAt`
- 저장 성공 후에는 모듈 목록을 다시 조회하고 F1-Grid 기준 데이터를 갱신해 dirty 상태를 해제한다.
- 저장 중 일부 요청이 실패하면 실패 메시지를 표시하고 아직 반영되지 않은 변경 상태를 유지한다.

### 4. 메뉴/라우팅 노출

- 대시보드 콘텐츠 라우팅에서 `settings` 모듈의 모듈 관리 메뉴 키를 인식해 모듈 관리 페이지를 렌더링한다.
- 실제 좌측 메뉴 노출은 기존 DB 기반 메뉴 데이터에 `모듈관리` 메뉴가 존재하는 경우를 우선 사용한다.
- 메뉴 seed 또는 DB 데이터 추가가 필요한 것으로 확인되면 계획서·사양서 단계에서 DB 영향으로 별도 기록한다.

### 5. 권한 및 사용성

- 페이지 상단 조회 버튼은 읽기 권한을 따른다.
- 저장 버튼은 생성 또는 수정 권한이 있고 F1-Grid 변경 사항이 있을 때 활성화한다.
- 엑셀 내보내기 권한이 있으면 F1-Grid의 기존 내보내기 흐름을 사용한다.
- 삭제 권한이 없으면 삭제 동작은 노출하거나 실행하지 않는다.
- 권한 값이 없을 때의 기본 동작은 기존 권한 관리 페이지의 관례를 우선 따른다.

## 접근 방식 비교

### 권장안: 권한 관리 페이지 패턴을 단일 모듈 그리드로 축소 적용

- 장점: 기존 사용자 경험과 코드 구조를 가장 잘 따른다. 페이지, 패널, 서비스, 타입 경계를 유지하면서 변경 범위가 작다.
- 단점: 모듈별 메뉴 미리보기나 상세 관계 편집은 제공하지 않는다.
- 판단: 사용자가 요청한 “F1-Grid 1개” 범위와 가장 잘 맞으므로 이번 작업의 기준으로 삼는다.

### 대안 1: 메뉴 관리 페이지 안에 모듈 관리 기능을 포함

- 장점: 메뉴와 모듈 관계를 한 화면에서 볼 수 있다.
- 단점: 메뉴 관리 화면의 책임이 커지고 기존 메뉴 CRUD 흐름과 섞여 회귀 위험이 커진다.
- 판단: 이번 요청의 “모듈 관리 페이지 추가” 취지와 맞지 않아 제외한다.

### 대안 2: 모듈 관리 전용 상세 다이얼로그 중심 구현

- 장점: 필드 검증과 설명을 단계적으로 보여주기 쉽다.
- 단점: 권한 관리 페이지/F1-Grid 패턴과 다르고, 단순 마스터 관리에는 UI가 과하다.
- 판단: 기존 F1-Grid 기반 관리 화면 일관성을 위해 제외한다.

## 변경 범위

### 프론트엔드

- `frontend/src/pages/settings/system/modules/` 신규 페이지/패널/서비스/타입 추가
- `frontend/src/pages/dashboard/components/DashboardContent.tsx`에 모듈 관리 페이지 렌더링 분기 추가
- 필요한 경우 기존 대시보드 메뉴 데이터 또는 타입 매핑에서 모듈 관리 메뉴 키 확인 및 최소 보정
- F1-Grid 기반 CRUD, dirty 상태, 저장 후 재조회, 오류 메시지 처리

### 백엔드

- 기본 범위는 기존 `egovframework.let.system.modules` API 재사용이다.
- 구현 중 API 계약 부족이 확인될 경우에만 최소 수정한다.
- 신규 테이블, 컬럼, 제약조건 변경은 기본 범위에 포함하지 않는다.

### 문서

- 승인 후 계획서와 상세 사양서를 `docs/plan/20260908`, `docs/spec/20260908`에 작성한다.
- 구현 후 결과 문서와 검증 증거를 `docs/result/20260908/module-management-page`에 작성한다.
- F1-Grid 관련 동작 변경이 발생하면 관련 F1-Grid 문서 갱신 여부를 함께 검토한다.

## 제외 범위

- 모듈별 메뉴 관계 편집 화면 추가
- 권한별 모듈 접근 정책 개편
- 모듈-메뉴 DB 스키마 재설계
- 대시보드 좌측 메뉴 전체 구조 개편
- 권한 관리 또는 메뉴 관리 화면의 무관한 리팩터링

## 완료 기준

- 환경설정 > 시스템관리에서 모듈 관리 메뉴 선택 시 모듈 관리 페이지가 렌더링된다.
- 페이지는 권한 관리 페이지와 같은 상단 경로, 버튼, 검색, 메시지, F1-Grid 구성 패턴을 따른다.
- 모듈 목록이 기존 모듈 API에서 조회되어 F1-Grid에 표시된다.
- 컨텍스트 메뉴로 신규 행을 추가하고 저장하면 등록 API가 호출되며 재조회 후 dirty 상태가 해제된다.
- 기존 행을 수정하고 저장하면 수정 API가 호출되며 재조회 결과가 표시된다.
- 선택 행 삭제가 허용되는 경우 삭제 API가 호출되고 재조회 결과가 표시된다.
- 모듈 코드와 모듈명 필수값 오류가 페이지 메시지로 표시된다.
- 저장 실패 시 변경 상태를 유지하고 오류 메시지를 표시한다.
- 프론트엔드 빌드/테스트 및 필요한 브라우저 캡처 검증 결과가 결과 문서에 기록된다.
- DB 변경이 없으면 결과 문서와 작업 원장에 `DB 스크립트: 해당 없음, 기존 스키마 영향 검토 완료`를 기록한다.

## 승인 필요 사항

이 작업지시서의 목표와 범위가 승인되면 다음 단계에서 계획서와 상세 사양서를 작성한다. 명시 승인 전에는 계획서, 사양서, 코드 수정, 테스트 실행, 빌드, 배포를 진행하지 않는다.
