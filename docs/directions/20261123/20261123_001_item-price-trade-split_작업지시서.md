# 20261123_001 단가등록 매입/매출 화면 분리 작업지시서

## 작업 목적

한 화면에서 매입·매출 단가를 한 줄로 관리하면서 열·폼·필터가 두 배로 늘고 매입 전용 항목(발주구분, 기본 거래처)이 섞여 복잡해졌다. **매입단가등록**과 **매출단가등록**을 별도 메뉴·화면으로 나누고, 각 화면은 자기 거래구분에 필요한 항목만 보여 준다. API도 거래구분별 메뉴 권한을 검사한다.

## 사용자 결정 (2026-11-23)

- 메뉴를 나눈다: 기존 "품목/거래처별 단가"를 **매입단가등록**으로 바꾸고, 같은 화면 구성을 쓰는 **매출단가등록**을 새로 만든다. 코드는 복사하지 않고 같은 컴포넌트에 거래구분 값만 다르게 연결한다.
- 개발 단계이므로 기존 주소(`/co/master/item-partner-prices`)의 북마크·리다이렉트는 고려하지 않는다.
- API도 분리한다: 거래구분별 메뉴 권한(매입단가등록/매출단가등록)을 서버가 검사한다.
- 매입 기준에 필요 없는 항목은 화면에서 뺀다(매출 화면에는 발주구분·기본 거래처가 없다).

## 현황 확인 (읽기 전용 DB MCP, 2026-11-23)

- `tb_menu` 단가 메뉴는 1건(ID 29, 코드 `CO_UPRICE`, 주소 `/co/master/item-partner-prices`, 부모 13, 정렬 50, 테넌트 1). 최대 menu_id는 72.
- 즐겨찾기 0건, 메뉴 권한(`tb_role_menu_permission`)은 역할 1에 READ·CREATE·UPDATE·DELETE·EXCEL 5건.
- 백엔드에는 컨트롤러에서 `SystemMenuService.getMyMenuTree`로 내 메뉴 권한을 읽어 화면 키(주소 마지막 마디)로 검사하는 기존 패턴이 있다(분류관리, 매출 견적 등). 단가 컨트롤러는 인증만 확인하고 메뉴 권한은 검사하지 않는다.

## 확정 범위

### 데이터베이스(메뉴 데이터만, 테이블 구조 변경 없음)
- 기존 메뉴 ID 29를 "매입단가등록"(주소 `/co/master/item-purchase-prices`)으로 바꾼다.
- "매출단가등록"(`/co/master/item-sales-prices`)을 테넌트별로 추가하고 기존 메뉴의 역할 권한을 복제한다.
- 날짜별 SQL·변경 이력·롤백 스크립트. SQL은 사용자가 직접 실행한다.

### 백엔드
- 품목 기준 조회, 거래처 기준 조회, 목록에 `tradeType` 필수 파라미터를 추가하고 한쪽 거래구분만 내려준다.
- 거래구분별 메뉴 권한 검사를 모든 단가 API에 적용한다(조회=READ, 신규=CREATE, 수정=UPDATE, 삭제=DELETE, 엑셀 검증=CREATE). 일괄 저장은 행의 거래구분(삭제·수정은 기존 행의 거래구분도)을 서버가 확인한다.
- 단가 상태 필터는 거래구분별 의미로 정리한다(공통단가 미등록 / 특별단가 있는 품목 / 매입 전용 기본 거래처 미지정).

### 프론트엔드
- 화면 컴포넌트가 `tradeType`을 받아 한쪽 열·폼·필터·엑셀만 보인다. 매입은 발주구분·기본 거래처·"매입 기본 거래처"가 추가된다.
- 대시보드에 화면 키 2개를 연결하고 기존 키를 제거한다.

## 범위 밖
- 영업 모듈 파일 수정(영업 담당자 개발 중). 단가 저장 구조·단가 조회 서비스·구매요청확정 변경.
- 구분별 데이터 분리·이관(테이블은 이미 거래구분별 행이다).

## 완료 조건
- 매입/매출 메뉴가 각각 열리고 해당 구분의 단가만 보이고 저장된다.
- 매출 메뉴 권한만 있는 계정이 매입 단가 API를 호출하면 403.
- 관련 백엔드·프론트 테스트, JDK 8 컴파일, 빌드, 375/768/1280px 브라우저 확인, 결과 문서.
