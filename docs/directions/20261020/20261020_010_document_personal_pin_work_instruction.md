# 문서작성 개인별 고정 문서 작업지시서

## 사용자 요구 및 승인

- 전자결재 문서의 상단 고정을 사용자별로 저장·조회한다.
- 개인별 고정 문서 전체를 일반 문서 페이지와 별도로 가져와 별도 상태/영역에 보관한다.
- 리스트형에서는 고정 문서를 상단 고정 패널에 표시한다. 피드형에서는 고정 문서를 일반 문서보다 먼저 표시한다.
- 고정/해제 아이콘은 공지사항 피드의 PushPin 액션과 같은 위치에 둔다.
- 사용자는 1차 하위 작업으로 개인별 고정 기능을 먼저 구현하고, 이후 일반 문서 목록의 서버 페이징을 진행하는 순서를 승인했다.
- 통합 설계는 [Personal Document Pins and Feed/List Pagination Design](../../superpowers/specs/2026-10-20-document-pin-and-feed-list-pagination-design.md)을 따른다.

## 승인 범위

- 별도 tenant/document/user 키의 고정 테이블, pin/unpin API, 고정 문서 목록 API를 추가한다.
- 고정/해제 대상은 요청 사용자가 현재 읽을 권한이 있는 문서로 제한한다.
- 고정 목록에는 요청자의 인증된 사용자 ID를 사용하며, 타 사용자나 클라이언트 입력 사용자 ID를 신뢰하지 않는다.
- 목록 조회는 tenant·문서 읽기권한·현재 scope·문서 유형·선택 문서 필터를 유지한다.
- 고정 목록은 최신 수정 문서 순으로 반환하고 별도의 임의 개수 제한을 두지 않는다.
- 피드/리스트 화면에서 고정 아이콘 액션과 고정 목록/상태를 연결한다.
- 사용자는 이 기능의 개인별 저장소를 별도 테이블로 구성하는 방안을 승인했다.

## 작업 절차

1. 이 작업지시서에 따라 계획서를 작성한다.
2. 계획서에 따라 상세 사양서를 작성하고 사용자 검토를 받는다.
3. 구현 전 기본 읽기 전용 DB MCP에서 `list_tables`와 관련 문서·사용자 테이블의 `describe_table`을 직접 확인한다. 이미 확인한 현재 메타데이터와 구현 직전 메타데이터를 비교한다.
4. 인증 사용자 접근검사, tenant 경계, 중복 pin 방지, 조회 필터, UI 액션을 검증하는 실패 테스트를 먼저 추가한다.
5. 날짜별 DB 변경 파일을 `docs/database/20261020`과 `backend/DATABASE/20261020`에 동일하게 생성한다. 변경 SQL, 변경 이력, 롤백 SQL 및 `docs/database/db-schema.md`를 함께 작성한다.
6. 백엔드와 프론트엔드 구현 및 대상 테스트를 수행한다.
7. 기존 4173 S-ERP 개발 서버를 확인 후 재사용해 화면을 확인하고, 직접 실행한 서버만 종료한다.
8. `docs/result/20261020/document-personal-pins`에 결과와 영문 소문자/숫자/하이픈 이름의 스크린샷을 기록한다.
9. 개인별 고정 기능을 완료한 뒤 [후속 페이징 작업지시서](./20261020_012_document_feed_list_pagination_work_instruction.md)의 일반 목록 페이징을 진행한다.

## 영향 범위

- 프론트엔드: 문서작성 feed/list 카드·행 액션, pin 상태·고정 목록 상태, API 서비스와 타입.
- 백엔드: 전자결재 고정 API·서비스·DAO·MyBatis와 권한 검증.
- DB: 사용자별 고정 관계 테이블 1개 및 인덱스/제약. SQL, 변경 설명, 롤백, 누적 스키마 모두 작성한다.
- 결과물: 개인별 고정 기능 결과서와 화면 검증 자료.
- 핀 상태는 공용 문서 레코드에 저장하지 않는다. 공지 게시글의 전역 `is_pinned`는 전자결재 개인 고정 상태로 재사용하지 않는다.
