# 작업지시서

## 제목

권한 관리 F1-Grid 선택·저장·사용자 매핑 흐름 개선

## 작업 분류

- 경로: `bounded`
- 사유: 기존 권한 관리 화면, F1-Grid 공통 기능, 기존 역할-사용자 매핑 API를 활용해 네 가지 동작을 보완한다. 새로운 권한 모델이나 독립 모듈을 도입하지 않는다.

## 배경

권한 관리 화면은 역할 목록과 권한별 사용자 매핑을 두 개의 F1-Grid로 제공한다. 현재 역할 행을 선택할 때 사용자 매핑 조회가 안정적으로 전환되지 않고, 역할 그리드의 상단 제어 영역이 메뉴 관리 페이지의 제어 패턴과 일치하지 않는다. 또한 기존 역할을 수정해도 업데이트 API가 호출되지 않으며, 신규 행을 저장한 뒤에도 그리드의 변경 기준 데이터가 갱신되지 않아 dirty 상태가 남을 수 있다. 사용자 매핑 영역에는 사용자를 명시적으로 추가하는 진입점도 부족하고, 매핑을 수정한 상태에서 다른 역할을 선택하면 변경을 잃을 위험이 있다.

## 목표

1. 역할 목록에서 행을 선택하면 선택한 역할 ID 기준으로 사용자 매핑 목록을 한 번만 조회하고 표시한다.
2. 메뉴 관리 페이지와 같은 우측 상단 그리드 제어 영역을 역할 관리 그리드에 적용한다.
3. 역할 그리드의 신규 행 생성과 기존 행 수정이 각각 생성·수정 API에 저장되도록 하고, 저장 직후 그리드 기준 데이터를 갱신해 dirty 상태를 해제한다.
4. 권한별 사용자 매핑 그리드에서 미할당 사용자를 추가하고 저장할 수 있는 흐름을 제공한다.
5. 스키마 변경이 필요한 경우에만 날짜별 SQL·변경 이력·롤백 파일을 `docs/database`와 `backend/DATABASE`에 동시 기록하고, `docs/database/db-schema.md`를 최신화한다.
6. 사용자 매핑의 미저장 변경이 있을 때 역할 전환 여부를 사용자에게 확인하고, 저장 중 선택 전환 및 부분 저장 실패로 인한 데이터 불일치를 방지한다.

## 요구사항

### 1. 역할 선택과 사용자 매핑 조회

- 역할 그리드의 선택 변경 이벤트에서 선택된 역할 ID를 기준으로 사용자 매핑 조회를 수행한다.
- 같은 역할 ID가 재렌더링되어도 중복 요청하지 않는다.
- 새로 추가되어 아직 저장되지 않은 역할을 선택한 경우에는 사용자 매핑 조회를 하지 않고 빈 상태를 표시한다.
- 요청 중 역할이 바뀌면 이전 요청 결과가 현재 선택 역할의 목록을 덮어쓰지 않아야 한다.

### 2. 역할 그리드 제어 영역

- 역할 관리 카드의 우측 상단에 메뉴 관리 페이지와 동일한 F1-Grid 제어 패턴을 적용한다.
- 최소 제공 기능은 선택 행 삭제와 현재 행 내보내기이며, 동작은 F1-Grid ref API를 사용한다.
- 신규 역할은 역할 그리드 컨텍스트 메뉴의 `행 추가`로 생성한다. 별도 `권한 등록` 버튼과 다이얼로그는 제공하지 않는다.

### 3. 역할 저장 및 dirty 상태

- 역할 그리드의 삽입·수정·삭제 변경 집합을 저장 버튼 활성화 근거로 사용한다.
- 새 행을 삭제해 F1-Grid 변경 집합이 비면 저장 버튼은 비활성화된다.
- 저장 시 신규 행은 생성 API, 기존 변경 행은 역할 ID별 수정 API로 저장한다. 역할 코드, 역할명, 설명, 사용 여부를 API 요청 값으로 정규화한다.
- 저장 성공 후 서버에서 역할 목록을 다시 조회하고, 새 rows prop으로 F1-Grid의 기준 데이터를 교체한다. 이때 inserted/updated/deleted 변경 집합은 비어 있어야 하며 저장 버튼은 비활성화된다.
- 여러 신규·수정 행이 있을 때는 모든 요청이 성공한 경우에만 목록을 재조회한다. 중간 실패 시 저장되지 않은 변경 상태를 유지하고 오류를 표시한다.
- 역할 삭제 API가 현재 제공되지 않으면 삭제된 기존 행은 서버에 반영하지 않으며, 저장 시 오류로 명확히 안내한다. 삭제 API 추가는 별도 범위로 둔다.

### 4. 사용자 매핑 추가와 저장

- 사용자 매핑 그리드는 선택 역할의 할당/미할당 사용자를 표시한다.
- 컨텍스트 메뉴의 `행 추가`는 매핑 대상 사용자 선택 UI를 열어야 하며, 미할당 사용자만 선택 후보로 표시한다.
- 선택한 사용자는 그리드에서 `매핑 여부`가 true인 신규 변경으로 표시한다.
- 사용자 매핑 변경은 저장 버튼을 활성화하고, 저장 시 역할 사용자 추가/해제 API를 호출한다.
- 저장 성공 후 선택 역할의 사용자 매핑 목록을 재조회한다.
- 사용자 매핑에 미저장 변경이 있는 상태에서 다른 역할 행을 클릭하면 확인 다이얼로그를 표시한다. 사용자는 현재 역할 유지, 저장 후 전환, 변경 취소 후 전환 중 하나를 선택한다.
- 저장 후 전환을 선택하면 현재 역할의 변경 저장이 성공한 뒤에만 대상 역할을 선택하고 조회한다. 저장 실패 시 대상 역할로 전환하지 않는다.
- 변경 취소 후 전환을 선택하면 현재 역할의 매핑 그리드를 마지막 서버 조회 기준으로 되돌린 뒤 대상 역할을 조회한다.
- 저장 중 또는 저장 후 재조회 중 역할이 전환되면 이전 역할의 응답이 현재 선택 역할의 목록을 덮어쓰지 않아야 한다.
- 여러 역할·사용자 매핑 저장 요청 중 일부가 성공한 뒤 실패하면, 성공 항목을 추적해 재시도 시 성공한 API 요청을 중복 호출하지 않는다.

### 5. 데이터베이스 영향

- 기본 구현은 기존 `tb_role`, `tb_login_account`, `tb_login_account_role` 관계와 기존 역할-사용자 매핑 API를 사용한다.
- 이 작업에서 테이블·컬럼·제약조건 변경이 없다면 DB 스크립트는 작성하지 않고, 결과 문서와 작업 원장에 `DB 스크립트: 해당 없음, 기존 스키마 영향 검토 완료`를 기록한다.
- 구현 중 스키마 변경이 확정되면 관련 SQL, 변경 이력 Markdown, 롤백 SQL을 양쪽 날짜 폴더에 작성하고 누적 스키마 문서를 갱신한다.

## 제외 범위

- 역할 삭제 API 및 데이터베이스 삭제 정책 신설
- 사용자/부서 마스터 구조 변경
- 권한 정책, 테넌트 관리자 판정 방식 변경
- 메뉴 관리 또는 다른 설정 화면의 구조 변경

## 완료 기준

- 역할 행 클릭마다 선택한 역할의 매핑 목록만 표시되고 stale 응답이 남지 않는다.
- 역할 그리드의 우측 상단 제어 영역에서 행 삭제와 내보내기를 사용할 수 있다.
- 행 추가 후 삭제하여 변경이 사라지면 저장 버튼도 비활성화된다.
- 기존 역할의 역할명·설명·사용 여부를 수정한 뒤 저장하면 수정 API 요청이 발생하고 재조회 결과가 그리드에 표시된다.
- 신규 역할 저장 후 역할 목록 재조회가 수행되며, 저장 버튼은 다시 비활성화된다.
- 미할당 사용자를 선택해 역할에 추가하고, 저장 후 서버 조회 결과에 반영된다.
- 역할 및 사용자 매핑 저장 실패는 페이지 메시지로 표시된다.
- F1-Grid 동작 문서, 결과 문서, 테스트·빌드·브라우저 캡처 증거를 작업 단위로 남긴다.
