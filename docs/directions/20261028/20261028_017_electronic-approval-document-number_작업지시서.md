# 전자결재 문서번호 발급 및 표시 작업지시서

## 요구사항

- 문서를 최초 임시저장할 때 서버가 `EA-YYYYMMDD-0001` 형식의 문서번호를 발급한다. 번호는 날짜와 tenant 범위로 연속 발급하며 네 자리보다 커지면 자르지 않는다.
- 임시저장 이후 수정, 결재신청, 재상신, 발송에서도 같은 문서번호를 유지한다.
- 문서 상세 제목 아래에는 내부 문서 ID 대신 `문서번호: EA-...`를 표시한다.
- 문서현황의 문서번호 열과 해당 상세검색은 내부 PK가 아닌 발급된 문서번호를 사용한다. 내부 PK는 API 경로와 상세 조회 식별자로 유지한다.
- 수주현황 상세 제목 아래에는 `수주번호: SO-...`를 표시한다.

## 설계 전제

- 저장된 초안도 문서현황에서 식별할 수 있도록 최초 임시저장 시 발급한다. 제출 시점 발급은 초안 목록에 번호가 없고, 클라이언트 발급은 중복 방지와 신뢰 가능한 저장 계약을 보장하지 못한다.
- 기존 `eabusNo`는 문서유형 구분 코드이므로 의미를 바꾸지 않는다. 문서번호는 별도 `documentNo` / `document_no` 필드로 관리한다.
- 번호 생성은 기존 `IdSequenceService`를 사용해 tenant와 날짜별로 수행한다. 클라이언트 요청값은 신뢰하지 않는다.
- 기존 문서의 번호는 `created_at` 날짜와 tenant별 생성 순서(생성 시각, 내부 ID)로 backfill하고 해당 날짜 sequence를 보정한다.

## 범위와 완료 기준

- 작업 순서: 작업지시서 → 계획서 → 상세 사양서 → 회귀 테스트 → 구현 → 브라우저 검증 → 결과 문서 및 스크린샷.
- DB/API 계약 변경을 포함한다. 날짜별 SQL, 변경 이력, 롤백 스크립트를 `docs/database`와 `backend/DATABASE`에 같은 내용으로 추가하고 `docs/database/db-schema.md`를 갱신한다.
- 목록/상세/임시저장 응답에 문서번호를 반환하고, 문서현황 정렬·검색과 상세 헤더가 새 필드를 사용해야 한다.
- 기존 문서 ID 기반 링크, 편집, 상신, 권한 범위, 문서유형 코드, 번호 없는 수주 API 동작을 유지한다.
- 해당 프론트엔드/백엔드 집중 테스트와 빌드를 수행하고, 실제 브라우저에서 375/768/1280px을 확인해 영문 경로의 결과 폴더에 기록한다.
