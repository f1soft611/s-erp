# 20261023_001 품목관리 공통코드·소비기한 입력 작업지시서

## 사용자 요청

- 지정 tenant MCP의 공통코드 그룹 및 상세코드를 조사해 S-ERP에 적용할 INSERT 스크립트를 만든다.
- 품목관리에서 소비기한 기준 옆에 기준 단위에 맞는 숫자를 입력할 수 있도록 한다.

## 확인 근거

- 기준 설계: [품목 공통코드 시드 및 소비기한 입력 설계](../../superpowers/specs/2026-10-23-material-common-codes-expiry-design.md)
- 지정 tenant MCP에서 `tb_common_code_group`, `tb_common_code_item`, `tb_material_info` 메타데이터와 세 공통코드 그룹 및 상세 항목을 확인했다.
- 품목관리에서 사용하는 그룹은 `MATERIAL_TYPE`, `STORE_METHOD`, `EXPIRY_STATUS`다. 확인한 상세코드는 총 12개다.
- 기본 S-ERP DB에서는 세 그룹이 조회되지 않았다. 적용 tenant ID는 SQL 실행 시 지정한다.
- `expiryed_status`와 `expiryed_count` 컬럼/API 필드는 이미 존재하므로 신규 컬럼은 만들지 않는다. 두 DB의 제한 집계에서는 기준-숫자 조합이 맞지 않는 기존 품목이 없었다.

## 작업 범위

### 공통코드 시드

- 그룹 3개와 상세코드 12개를 원본의 코드, 이름, 설명, 정렬순서, 활성상태 그대로 시드한다.
- 그룹/상세코드 PK는 시퀀스로 생성하고 그룹 코드 및 상세코드의 자연 키로 상세 항목을 연결한다.
- psql 변수 `target_tenant_id`로 대상 tenant를 지정한다. 스크립트는 트랜잭션으로 실행하고 `(tenant_id, group_code)` 및 `(group_id, item_code)` 충돌 시 기존 레코드를 수정하지 않는다.
- 시드 SQL은 `docs/database/20261023`와 `backend/DATABASE/20261023`에 동일하게 둔다. 읽기 전용 MCP를 통한 실행은 금지한다.

### 소비기한 입력 및 정합성

- 품목 행 폼에서 기존 소비기한 기준과 숫자 필드를 인접 배치하고 선택값의 단위를 표시한다.
- `NONE`이면 숫자를 NULL로 비우고 입력을 비활성화한다. `DAY`, `MONTH`, `YEAR`이면 1~2147483647의 정수를 필수로 한다.
- 프론트엔드 저장 검증, 백엔드 서비스 검증, PostgreSQL CHECK 제약을 같은 규칙으로 맞춘다.
- DB 변경 SQL, 변경 이력, 롤백을 두 스키마 이력 경로에 동일하게 추가하고 `docs/database/db-schema.md`를 갱신한다.

### 문서 및 검증

- 이 작업지시서를 기반으로 [계획서](../../plan/20261023/20261023_001_품목관리_공통코드_소비기한입력_계획서.md)를 작성한다.
- 계획서를 기반으로 [상세사양서](../../spec/20261023/20261023_001_품목관리_공통코드_소비기한입력_상세사양서.md)를 작성한 후 구현한다.
- 품목관리 문서 및 [F1-Grid 안내](../../../frontend/src/pages/f1-grid-docs/F1-GRID.md)를 변경사항에 맞게 갱신한다.
- 프론트엔드 집중 테스트·빌드, 백엔드 집중 테스트, SQL 정적 검증 및 375/768/1280px 브라우저 확인을 수행한다.
- 결과 문서와 스크린샷은 `docs/result/20261023/material-common-codes-expiry/`에 저장한다.

## 제외 사항

- 지정 MCP 또는 기본 S-ERP MCP를 통한 데이터 변경 및 스키마 적용
- 소비기한 새 컬럼/API 생성, 지정된 세 그룹 외 공통코드 추가
- 기존 tenant 코드 정의의 자동 덮어쓰기 및 임의 코드 정리

## 완료 조건

- psql 대상 tenant 변수를 입력하지 않으면 시드가 실행되지 않으며, 코드 충돌 시 기존 정의를 보존한다.
- 원본의 그룹 3개와 상세코드 12개를 모두 스크립트에 반영하고, 양쪽 DB 이력 경로의 시드/스키마 변경 파일이 동일하다.
- 소비기한 기준별 단위, 입력 활성상태, 프론트엔드·백엔드 검증, DB CHECK가 승인된 규칙을 따른다.
- 기존 품목 필드명·API 계약을 유지하고 기존 목록/저장 동작의 회귀가 없다.
- 계획·상세사양·결과 문서가 최신 구현과 일치하며 결과에 브라우저 스크린샷과 실제 DB 미적용 사실을 기록한다.
