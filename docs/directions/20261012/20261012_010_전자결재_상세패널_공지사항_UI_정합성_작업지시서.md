# 20261012_010 전자결재 상세 패널 공지사항 UI 정합성 작업지시서

## 작업 목적

전자결재 문서 상세 패널을 공지사항 피드와 일관된 구조로 정리한다. 문서 이력은 USER 댓글과 같은 시간순 타임라인에 읽기 전용 SYSTEM 행으로 통합하고, 기안자에게만 기존 규칙에 따른 수정 및 제한된 논리 삭제를 제공한다.

## 승인된 동작

### 상세 패널

- 패널 제목은 `문서 상세`, 보조 표시는 `문서 ID: {electronicApprovalId}`로 고정한다. 문서 제목은 카드 본문에 표시한다.
- 카드 본문 순서는 기안자/기안일 메타정보 → 읽기 전용 결재선 → 문서 제목 → 본문 → 본문 이미지 목록 → 첨부 목록 → 좋아요/북마크 → 댓글 타임라인이다.
- 카드 우측 상단에는 핀 표시, 기안자 메뉴, 결재 상태 배지를 둔다. 핀은 표시만 하고 동작을 추가하지 않는다.
- 좋아요/북마크는 공지사항과 같은 UI와 현재 화면 한정 임시 상호작용만 제공한다. approval API나 DB에 저장하지 않는다.
- 공지사항이 이미 사용하는 공통 패널, 첨부 목록, 댓글 컴포넌트를 재사용하고 기존 공지사항의 동작을 보존한다.

### 댓글과 시스템 이력

- 별도 `문서 이력` 섹션을 제거한다.
- 기존 approval USER 댓글/대댓글과 SYSTEM 이벤트를 하나의 시각순 댓글 타임라인으로 합친다.
- SYSTEM 이벤트는 읽기 전용이며 답글·수정·삭제·첨부 조작을 제공하지 않는다. USER 댓글의 기존 작성·답글·수정·삭제·첨부 흐름과 페이지네이션은 유지한다.

### 수정과 삭제 권한

- 수정은 본인 문서의 `DRAFT` 또는 `REVISION_REQUESTED`에서만 기존 흐름으로 제공한다.
- 삭제는 본인 `DRAFT`, 또는 문서가 `PENDING`이고 기안자 자동 승인 외 다른 `APPROVAL`/`AGREEMENT` 참여자가 처리한 이력이 전혀 없는 경우만 허용한다.
- `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `REVISION_REQUESTED`, 이미 다른 결재자가 처리한 `PENDING` 문서는 삭제할 수 없다.
- 화면 메뉴 노출은 서버 응답을 참고하되, 인증 사용자·tenant·소유자·현재 문서 상태·결재선 상태의 최종 검증은 서버에서 수행한다.
- 삭제 확인 후 서버는 문서 행을 잠그고, `deleted_yn='Y'` 논리 삭제와 `DELETED` SYSTEM 이벤트 기록을 같은 트랜잭션으로 처리한다. 기존 문서, 결재선, 댓글, 첨부 메타데이터와 본문 이미지를 물리 삭제하지 않는다.
- 삭제 성공 시 상세를 닫고 목록/요약을 갱신한다. 실패 시 상세를 유지하고 오류를 명시한다.

## 변경 범위

- 프런트엔드 전자결재 상세 피드, 공통 상세 패널의 선택적 문서 ID 보조 표시, 댓글의 읽기 전용 SYSTEM 표시, 삭제 서비스/메뉴/성공 후 갱신 및 관련 테스트를 변경한다.
- 백엔드 approval 전용 DELETE API, 상세 응답의 `isDrafter` 표시, transaction 삭제/권한 검증, SYSTEM 이벤트 append, 논리 삭제 컬럼에 따른 일반 조회/참여자 접근 차단 및 관련 테스트를 변경한다.
- DB migration, 변경 이력, 롤백 파일을 `docs/database/20261012`와 `backend/DATABASE/20261012`에 동일하게 작성하고 `docs/database/db-schema.md`를 갱신한다.
- 코드 배포는 `deleted_yn` 및 `DELETED` 제약 migration이 대상 DB에 반영된 후에만 가능하다. 이 작업에서는 문서화된 SQL 파일만 작성하며 운영 DB에 적용하지 않는다.

## 범위 제외

- 좋아요·북마크·핀의 서버/API/DB 영속화
- 삭제 문서 복원, 완전 삭제, 보존 기간 또는 파일 객체 정리
- 기존 결재 순서와 결재/합의 상태 전이 변경
- 공지사항 전체 상세의 재설계 또는 관련 없는 공통 컴포넌트 리팩터링

## 작업 절차

1. 본 작업지시서를 기준으로 구현 계획을 갱신하고 파일·테스트·순서를 확정한다.
2. 계획서를 기준으로 화면·API·DB·권한·오류·검증 계약을 상세사양서에 고정한다.
3. DB migration 파일, 변경 이력, 롤백 및 누적 스키마 문서를 작성한다. DB에는 적용하지 않는다.
4. 백엔드 실패 테스트를 먼저 추가하고 transaction 삭제 API 및 미삭제 조회 조건을 구현한다.
5. 프런트엔드 실패 테스트를 먼저 추가하고 문서 상세 UI, SYSTEM 행, 권한 메뉴와 삭제 후 갱신을 구현한다.
6. 관련 Maven/Vitest 타깃 테스트, 프런트엔드 production build 및 브라우저 반응형 검증을 수행한다.
7. 실제 검증 결과와 375px/768px/1280px 스크린샷을 결과 문서에 기록한다.

## 완료 조건

- 패널 제목/문서 ID, 본문 순서, 읽기 전용 결재선, 첨부/반응/댓글 UI가 승인된 설계와 일치한다.
- 별도 문서 이력 섹션이 없고 SYSTEM/USER 항목이 시간순으로 표시되며 SYSTEM 항목에는 mutation affordance가 없다.
- 본인에게만 허용 상태별 메뉴를 제공하며 서버가 삭제 규칙을 재검증한다.
- 문서 삭제 표시와 `DELETED` SYSTEM 이벤트는 원자적이고, 삭제 문서는 모든 일반 조회 및 참여자 기반 접근에서 숨겨진다.
- 원본/결재선/댓글/첨부는 보존되고 migration/rollback SQL은 실제 운영 DB에 적용되지 않는다.
- 작업지시서·계획서·상세사양서·결과보고서와 스크린샷이 날짜별 경로에 존재하며, 양쪽 schema migration 사본이 일치한다.
- 관련 backend/frontend 테스트, build, 375px/768px/1280px 브라우저 확인 결과가 결과보고서에 기록된다.
