# 공통 알림·쪽지함 통합 작업지시서

## 목적

문서 댓글 멘션과 사용자 쪽지 도착을 공통 알림함에 연결하고, 알림과 분리된 1:1 쪽지함을 제공한다. 알림 읽음 상태와 쪽지 읽음 상태는 각각 보유하되, 쪽지 대화를 열어 읽으면 해당 새 쪽지 알림도 읽음 처리한다.

## 범위

### 포함

- 인증 사용자별 공통 알림 목록, 미읽음 개수 및 읽음 처리 API/저장소
- 전자결재 문서 댓글의 `@사용자`, `@ALL` 선택과 서버 수신자 검증
- 1:1 쪽지 작성, 받은함/보낸함, 대화 조회, 읽음 처리, 답장
- 메시지 수신자에게 공통 알림 생성 및 쪽지와 알림 간 이동/읽음 연결
- 공통 업무 헤더의 알림 아이콘/미읽음 뱃지/최근 알림 팝오버와 쪽지 아이콘/미읽음 뱃지
- 반응형 화면, 집중 테스트, 결과 문서 및 브라우저 스크린샷
- 날짜별 DB migration, 변경 이력, 롤백 스크립트 및 누적 스키마 갱신

### 제외

- 메뉴 즐겨찾기 및 전역 통합검색
- 웹 푸시, 이메일/SMS 전달, WebSocket/SSE 실시간 갱신
- 그룹 쪽지, 첨부파일, 전달, 삭제/보관, 임시저장 및 외부 이메일 발송
- 댓글 편집으로 멘션 대상 변경 시 알림 재발행 또는 과거 알림 소급 수정
- 알림 일괄 읽음/삭제 및 알림 설정 화면

## 사용자 흐름

1. 사용자는 우측 상단 알림 아이콘에서 최근 알림과 미읽음 뱃지를 확인하고 전체 알림함으로 이동한다.
2. 댓글 작성자는 `@`로 같은 테넌트의 사용자를 선택하거나 `@ALL`을 선택한다. `@ALL`은 해당 문서를 볼 권한이 있는 사용자로 확장한다.
3. 쪽지 작성자는 같은 테넌트의 활성 사용자를 한 명 선택해 쪽지를 보낸다. 수신자는 공통 알림과 쪽지함 미읽음 표시를 각각 받는다.
4. 알림을 여는 것만으로 쪽지는 읽음 처리하지 않는다. 쪽지 대화에 진입하면 받은 미읽음 메시지와 그 메시지에 연결된 알림을 함께 읽음 처리한다.
5. 대화 참여자는 받은함/보낸함에서 대화를 열고 상대에게 답장한다. 보낸 쪽지에는 수신자의 읽음 상태를 표시한다.

## 설계 및 데이터 계약

- 알림은 사용자 수신자 단위로 저장하고 업무 발생원 타입/ID, 이벤트 타입, 표시용 제목/요약, 생성시각 및 읽음시각을 가진다. 발신자, tenant, 업무 수신자와 현재 인증 principal은 서버에서 검증한다.
- 쪽지는 대화와 메시지를 분리한다. 대화는 동일 tenant의 서로 다른 두 사용자만 참여자로 보유하고, 메시지는 발신자·수신자·본문·생성시각·수신자 읽음시각을 갖는다.
- 공통 알림은 쪽지 본문을 복제하지 않는다. 쪽지 도착 알림은 `DIRECT_MESSAGE_RECEIVED` 및 메시지 ID로 대화를 찾는다. 댓글 멘션 알림은 문서 ID와 댓글 ID를 참조한다.
- 신규 메시지 저장과 수신자 알림 생성은 한 트랜잭션으로 처리하며, 중복 요청이 같은 메시지 알림을 중복 생성하지 않게 한다.
- 쪽지 제목은 선택 사항이며 최대 120자, 본문은 일반 텍스트 최대 5,000자다. 댓글 content는 기존 HTML 저장 계약을 유지하며 멘션 사용자 ID 및 `mentionAll`을 별도 전달한다.
- `@ALL` 대상은 문서 접근 권한을 가진 현재 tenant의 활성 사용자이며 작성자 자신은 제외한다. 개별 멘션 ID는 서버에서 같은 범위의 활성 사용자인지 확인하고 중복 수신자를 제거한다.
- 읽음 API는 요청 사용자를 받지 않고 인증 사용자 및 tenant 기준으로 제한한다. 쪽지 대화도 현재 사용자가 참여자인 경우에만 조회/작성할 수 있다.

## DB MCP 확인 근거

기본 `s-erp-postgresql-readonly` MCP의 `list_tables`와 `describe_table`로 현재 계약을 확인했다.

- `tb_user`: `user_id`, `tenant_id`, `login_id`, `user_nm`, `use_at` 확인
- `tb_login_account`: `login_id`, `tenant_id`, `use_at` 확인
- `tb_common_comment`: 댓글 ID, tenant/owner, parent, content, writer, comment/event type 확인
- `tb_electronic_approval_main`: 문서 ID, tenant, 제목, 상태, 기안자 정보 확인
- `tb_electronic_approval_line_info`: 참여자 타입 및 사용자 ID 계약 확인
- 제약 메타데이터에서 `tb_user.user_id` 기본 키, 로그인/tenant 연결과 댓글 tenant-comment 유니크 키를 확인했다.
- 행 데이터는 조회하지 않았다. 현재 테이블 목록에 공통 알림 또는 쪽지 테이블은 없다.

구현 migration은 이 메타데이터와 코드상 인증/사용자 ID 변환을 대조해 작성하며, 실제 DB에 적용하지 않는다.

## 절차 및 완료 기준

1. 이 작업지시서와 승인 설계를 바탕으로 날짜별 계획·상세사양을 작성한다.
2. 알림/쪽지 서버 서비스, tenant 격리, 읽음 상태 및 댓글 멘션 계약의 실패 테스트를 먼저 작성한다.
3. 날짜별 신규 테이블과 인덱스 migration, 변경 이력, 롤백 파일을 `backend/DATABASE/20261030` 및 `docs/database/20261030`에 동일하게 작성하고 `docs/database/db-schema.md`를 갱신한다.
4. 인증 사용자 기준 알림/쪽지 API와 트랜잭션을 구현한다. 실제 DB에는 migration을 실행하지 않는다.
5. 댓글 `@사용자`/`@ALL`, 공통 알림함 팝오버/페이지, 쪽지 받은함/보낸함/대화 작성 UI를 구현한다.
6. API 권한, 중복 발행, 대화 참여자, 메시지 읽음과 연결 알림 읽음의 단위/통합 테스트 및 프런트엔드 테스트를 실행한다.
7. 백엔드 Maven 테스트와 프런트엔드 build/test를 실행한다.
8. 실제 브라우저에서 375px, 768px, 1280px 반응형 UI를 확인한다.
9. `docs/result/20261030/unified-notifications-messages/`에 변경 및 MCP 근거/검증 결과를 기록하고 화면 스크린샷을 보관한다.

## 완료 기준

- 새 쪽지 수신 시 수신자의 쪽지 미읽음 개수와 공통 알림 미읽음 개수가 각각 증가한다.
- 공통 알림을 읽어도 쪽지 자체는 미읽음으로 유지된다. 대화에서 쪽지를 읽으면 수신 메시지와 해당 새 쪽지 알림이 모두 읽음으로 바뀐다.
- 받은함/보낸함, 대화 및 읽음 상태는 tenant와 참여자를 기준으로 제한되고, 미참여 사용자의 조회/발송은 거부된다.
- 답장은 기존 두 참여자 사이에만 추가되고 같은 대화로 알림이 도착한다.
- 문서 멘션은 활성 tenant 사용자와 문서 접근 권한을 기준으로 검증되고 중복/자기 알림이 없다.
- 로딩, 빈 목록, API 오류, 발송 실패 및 재시도 동작이 명시적으로 표시된다.
- 기존 공통 토스트, 문서 시스템 이력/댓글 권한, 최근 메뉴 및 일반 댓글 동작은 회귀 없이 유지된다.
- 관련 검증, 실제 브라우저 스크린샷, migration/롤백/스키마 문서, 결과 문서가 모두 존재한다.
