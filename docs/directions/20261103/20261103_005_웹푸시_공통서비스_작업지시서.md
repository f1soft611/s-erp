# 공통 Web Push 서비스 작업지시서

## 근거와 승인

- 2026-11-03 승인된 [공통 웹 푸시 서비스 설계](../../superpowers/specs/2026-11-03-web-push-design.md)
- 실행 계획: [공통 Web Push 서비스 계획서](../../plan/20261103/20261103_005_웹푸시_공통서비스_계획서.md)
- 선행 공통기능 순서: [후속 확장 로드맵](../20261102/20261102_007_공통기능_후속확장_작업지시서.md)

## 목적

사용자가 명시적으로 동의한 브라우저 기기에 현재 공통 알림을 전달한다. 업무 멘션과 쪽지 도착은 업무별 구현을 두지 않고, 공통 백엔드 Web Push 서비스를 통해 같은 구독·전달·재시도·정리 흐름을 사용한다.

## 이번 단계의 범위

- 기존 공통 알림 유형 `APPROVAL_COMMENT_MENTION`과 `DIRECT_MESSAGE_RECEIVED`를 공통 Web Push outbox로 전달한다.
- 웹 알림 권한은 사용자가 프로필 설정에서 직접 켜기를 선택한 경우에만 요청한다.
- 사용자/테넌트별 브라우저 기기 구독을 등록, 갱신, 해제하고 중복 등록을 멱등하게 처리한다.
- 알림 행과 전달 대기 작업을 하나의 DB transaction에서 저장하고, 공통 worker가 비동기 전송한다.
- delivery를 알림·기기별로 기록해 일시 오류 재시도, 최종 실패, HTTP 404/410 구독 정리 및 중복 억제를 적용한다.
- payload와 OS 표시에는 일반 문구와 알림 ID만 포함한다. 푸시 선택 시 앱 내에서 로그인, tenant, 알림 소유자, 원본 접근 권한을 다시 검증한다.
- 미지원/권한 거부/오프라인/전송 실패에서도 기존 인앱 알림과 쪽지 흐름을 유지한다.
- 날짜별 DB migration/change record/rollback, 누적 schema 문서, 테스트, 반응형 브라우저 확인과 작업 결과를 포함한다.

## 제외

- 새로운 결재 요청·승인·반려 이벤트의 발행과 수신자 결정. 이는 로드맵 3단계에서 별도 합의한다.
- 이메일, SMS, 모바일 앱 push, 외부 관리형 푸시 중계사업자.
- 유형별 푸시 설정, 임의 사용자별 설정, 알림·쪽지 읽음/보관 동작 변경.
- 푸시 메시지 또는 OS 알림에 문서/쪽지 본문, 제목, 사용자 이름을 표시하는 기능.
- 브라우저 벤더 Push Service를 대체하는 자체 푸시 네트워크나 암호화 프로토콜 직접 구현.

## 필수 순서

1. 이 작업지시와 설계 근거를 바탕으로 API·DTO·DB·상태 전이·운영/보안 조건을 [상세 사양서](../../spec/20261103/20261103_005_웹푸시_공통서비스_상세사양서.md)에 확정하고 승인받는다.
2. 승인된 사양에 따라 MyBatis 계약 테스트를 먼저 작성한다. DB 변경 필요 시 기본 `s-erp-postgresql-readonly` MCP로 목록과 필요한 테이블 metadata를 직접 확인한다. tenant 서버/행 데이터는 불필요하게 조회하지 않는다.
3. `docs/database/20261103` 및 `backend/DATABASE/20261103`에 동기화된 날짜별 SQL, 변경 이력, rollback을 작성하고 `docs/database/db-schema.md`를 반영한다. DDL은 실제 DB에 자동 적용하지 않는다.
4. 인증된 기기별 구독 API와 endpoint 발신 제한을 구현·검증한다.
5. 공통 알림 저장과 outbox를 원자적으로 연동하고, lease 기반 공통 worker와 Java 8 호환 표준 Web Push transport를 구현한다.
6. 프런트엔드에서 사용자 동의, 현재 브라우저 구독/해제, Service Worker 일반 알림 표시와 안전한 클릭 이동을 구현한다.
7. 업무 멘션/쪽지가 같은 공통 흐름을 사용함, 재시도/만료/테넌트 경계 및 실패 격리를 테스트하고 결과를 기록한다.
8. 브라우저 375px/768px/1280px 화면을 확인하고 영문 파일명 스크린샷과 운영상 제한을 결과 문서에 남긴다.

## 수신자와 전달 정책

- push 수신자는 공통 알림 행의 `tenant_id`와 `recipient_user_id`에서만 결정한다. 쪽지 발신자나 브라우저 요청 payload의 사용자 ID를 이용해 임의 수신자를 만들지 않는다.
- push는 기존 공통 알림의 추가 채널이다. 푸시 저장/발송 실패가 알림 또는 쪽지 저장 transaction을 실패시키면 안 된다. 단, 알림과 outbox의 원자 기록 실패는 transaction을 rollback한다.
- 공통 알림의 unique 충돌로 새 알림 행이 생성되지 않으면 새 outbox를 만들지 않는다.
- 수신 시 활성 기기가 없으면 해당 notification outbox를 수신기기 없음 terminal 상태로 마감한다. 이후 등록된 기기에 과거 알림을 소급 발송하지 않는다.
- 한 알림의 각 활성 구독에 독립 delivery를 생성한다. 한 기기 전송 오류는 다른 기기 delivery를 중단하지 않는다.
- 전달은 외부 Push Service와 네트워크 실패 때문에 exactly-once를 보장할 수 없다. outbox/delivery unique key와 상태 추적으로 의도적인 중복 발송을 억제하고, 전송 결과가 불확실한 재시도는 best-effort로 처리한다. 브라우저 notification `tag`로 동일 알림 표시를 대체한다.

## 보안 및 운영

- VAPID 개인키는 repository, DB, frontend bundle에 넣지 않는다. 서버 secret 설정으로 주입하고 활성화되었는데 키가 없거나 잘못되면 시작 시 실패시킨다. 공개키만 인증 API로 전달한다.
- endpoint, `p256dh`, `auth`는 구독 자격자료로 취급한다. 요청/응답/로그에서 노출하지 않고 사양에서 정한 envelope encryption과 key version으로 저장한다.
- endpoint scheme/host를 표준 Push Service allowlist로 제한하고 HTTPS만 허용한다. HTTP redirects를 비활성화하고 production 네트워크 outbound policy에서도 private/loopback/link-local 목적지를 차단한다.
- 전송에는 Java 8 호환이며 유지 관리되는 라이브러리를 사용하고, crypto/VAPID 직접 구현은 금지한다.
- 백엔드는 알림 tenant/owner 권한과 현재 원본 접근권한을 재검증한다. 클라이언트가 보낸 navigation URL을 실행하지 않는다.
- 구독/API에는 payload 크기, 요청 빈도, 사용자별 활성 구독 상한을 둔다. endpoint·키·알림 내용은 로그/metric에 넣지 않는다.
- 제한된 재시도 횟수/최대 보류 기간을 적용하고, 404/410은 해당 endpoint 구독만 즉시 비활성화한다. 무한 재시도를 허용하지 않는다.

## 완료 조건

- 구독 등록 후 endpoint hash 조회는 실제 DAO/MyBatis 배열 처리와 JDBC 바인딩 경로를 검증한다. `byte[]` 직접 전달로 인한 파라미터 이름 불일치는 기존 저장·소유권 계약을 유지해 수정한다.
- WNS의 단일 `token` query 허용 규칙은 등록과 실제 발송에 동일하게 적용하며, 암호화된 POST의 목적지 query가 유지되는지 회귀 검증한다.
- 사용자 요청에 따라 쪽지/업무 표시 문구를 분리하고 기존 S-ERP 로고를 사용한다. 클릭은 알림 ID로 권한을 재검증한 뒤 상세로 이동하며 로그인 후에도 이 경로를 유지한다.

- `APPROVAL_COMMENT_MENTION`, `DIRECT_MESSAGE_RECEIVED` 모두 동일한 공통 outbox/worker/transport 경로를 사용하고 새 업무 이벤트를 발행하지 않는다.
- 인증 사용자·tenant 격리, endpoint 중복 등록/소유권 이전, 다른 사용자의 해제 차단, 명시적 동의가 테스트된다.
- 알림/outbox 원자성, idempotent enqueue, lease 동시성, 다중 기기별 결과, 404/410 정리, 재시도/terminal 상태와 worker 재시작이 테스트된다.
- payload/OS 표시/log에 업무 제목·요약·쪽지 본문·구독 자격자료가 노출되지 않고, 클릭 후 기존 권한 경계가 적용된다.
- Java 8 API 호환성을 확인하고 Maven focused tests, 프런트엔드 tests/build/lint, 375/768/1280 브라우저 확인을 결과에 기록한다.
- 날짜별 DB 이력과 backend 사본이 동일하고 실제 운영 DB에는 DDL을 적용하지 않는다.
- 결과 문서와 영문 파일명 스크린샷을 `docs/result/20261103/web-push/`에 보관한다.
