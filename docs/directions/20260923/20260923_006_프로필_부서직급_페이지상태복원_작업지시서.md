# 20260923_006 프로필 부서·직급 및 페이지 상태 복원 작업지시서

## 작업 분류

- 대상: 프론트엔드 + 백엔드 + 데이터베이스 스키마
- 경로 분류: architectural
- 관련 화면: 대시보드 프로필 팝오버, 공통코드 관리, 페이지 상태 복원 공통 훅
- 목적: 로그인 사용자의 부서명·직급명을 동적으로 표시하고, 관리 화면의 조회 조건·선택 상태·상세 조회 상태를 로그인 세션 동안 복원한다.

## 작업 배경

현재 로그인 사용자 정보에는 사용자 ID와 일부 역할 정보가 표시되지만 부서명과 직급명이 프로필 팝오버에 제공되지 않는다. DB 확인 결과 `tb_user`에는 `department_id`가 있으나 직급 식별자가 없고, `LEVEL` 공통코드 그룹에는 직급 항목이 관리되고 있다.

또한 `usePageSessionState`는 페이지 단위 상태를 저장할 수 있는 공통 기반을 갖추고 있으나, 공통코드 관리 화면에서 검색어·선택 그룹·상세 목록 조회 상태를 공통 정책으로 저장·복원하는 적용이 완료되지 않았다.

## DB 확인 근거

읽기 전용 PostgreSQL 확인 결과:

- `tb_user.department_id`: 부서 FK 후보
- `tb_department.department_id`, `department_nm`: 부서명 조회 기준
- `tb_common_code_group.group_code = 'LEVEL'`: 직급 공통코드 그룹
- `tb_common_code_item.common_code_item_id`: 직급 저장에 사용할 내부 ID
- 확인된 LEVEL 항목: `001 사원`, `002 대리`, `999 관리자`

## 목표

1. 사용자 프로필 팝오버에 사용자명, 부서명, 직급명을 동적으로 표시한다.
2. 직급은 `tb_user.level_id`로 저장하고 `tb_common_code_item.common_code_item_id`를 참조한다.
3. API에서는 프로필 표시를 위해 `departmentName`, `levelId`, `levelCode`, `levelName`을 제공한다.
4. 기존 역할명 표시가 필요하면 역할은 보조 정보로 유지하되 부서·직급을 우선 표시한다.
5. 페이지별 상태 저장·복원을 위한 공통 훅 사용 규칙을 정립한다.
6. 공통코드 관리 화면에서 검색어, 선택 그룹, 상세 조회 결과 및 그리드 선택 상태를 세션 동안 복원한다.
7. 다른 관리 화면에 확장 가능한 페이지 key 기반 구조를 유지한다.

## 기능 요구사항

### 1. 프로필 부서·직급 표시

- AppBar 프로필 팝오버에서 다음 정보를 동적으로 표시한다.
  - 사용자명
  - 부서명
  - 직급명
  - 이메일
- 프로필 API 응답에 부서·직급 정보가 없거나 조회에 실패하면 기존 사용자 ID·역할 정보로 fallback한다.
- 기존 프로필 이미지 및 로그아웃 동작은 유지한다.
- 직급명은 `LEVEL` 공통코드의 `item_nm`을 사용한다.
- DB에는 직급명이나 직급 코드를 직접 저장하지 않고 `level_id`만 저장한다.

### 2. 페이지 상태 복원 공통 훅

- 공통 훅은 페이지 key를 받아 `sessionStorage`에 JSON 상태를 저장·복원한다.
- 저장 범위는 로그인 세션으로 제한한다.
- 로그아웃 시 해당 세션 상태를 삭제한다.
- 페이지마다 독립된 key를 사용해 화면 간 상태 충돌을 방지한다.
- 상태 저장 대상은 화면 컴포넌트가 명시적으로 제공한 값만 포함한다.
- F1-Grid의 기존 렌더링·편집 동작은 유지하고, 선택 행 복원을 위한 최소 ref API만 확장한다.

### 3. 공통코드 관리 적용

다음 상태를 페이지 key `common-code-management`로 저장·복원한다.

- 그룹 검색어
- 선택된 공통코드 그룹 ID
- 선택 그룹의 상세 항목 조회 상태
- 그룹 그리드 선택 상태
- 상세 그리드 선택 상태가 화면에서 안정적으로 재조회 가능한 경우 해당 선택 키
- 그룹/상세 영역 스플리터의 분할 크기

복원 순서는 다음과 같다.

1. 그룹 목록 조회
2. 저장된 검색어 적용
3. 필터 결과 안에서 저장된 그룹 ID가 유효한지 확인
4. 유효하면 해당 그룹을 선택하고 상세 항목 조회
5. 유효하지 않으면 첫 번째 접근 가능 그룹을 선택
6. 상세 그리드 데이터 조회 후 저장된 선택 상태를 안전하게 적용

저장된 ID가 삭제되었거나 권한상 접근할 수 없으면 오류를 발생시키지 않고 현재 유효한 첫 항목으로 대체한다.

## API 및 데이터 계약

### 프로필 사용자 요약

기존 `GET /api/v1/menus/my` 응답의 `result.user`를 확장한다.

```json
{
  "userId": "admin",
  "name": "사용자명",
  "email": "user@example.com",
  "departmentName": "개발팀",
  "levelId": 123,
  "levelCode": "001",
  "levelName": "사원",
  "groupName": "플랫폼관리자",
  "roleName": "PLATFORM_ADMIN",
  "roles": ["PLATFORM_ADMIN"]
}
```

- `departmentName`, `levelId`, `levelCode`, `levelName`은 nullable 허용
- 기존 클라이언트와의 호환을 위해 기존 `userId`, `roles` 필드는 유지
- 인증되지 않은 사용자는 응답 대상이 아님

## DB 변경 범위

### 신규 컬럼

- 테이블: `tb_user`
- 컬럼: `level_id BIGINT NULL`
- 참조: `tb_common_code_item(common_code_item_id)`
- 삭제 정책: 직급 공통코드 삭제 시 사용자 데이터를 연쇄 삭제하지 않도록 `RESTRICT` 또는 기본 FK 정책 사용
- 기존 사용자 데이터: 초기값은 `NULL`로 유지하며 별도 일괄 매핑하지 않는다.

- `usePageSessionState` 또는 확장 공통 훅의 저장·복원 계약 정리

## 완료 기준

- 프로필 팝오버에서 사용자명·부서명·직급명·이메일이 API 기반으로 표시된다.
- 직급은 ID FK로 저장되고 LEVEL 공통코드명으로 표시된다.
- 기존 데이터와 신규 필드가 없는 토큰에 대해 fallback이 동작한다.
- 공통코드 관리에서 검색어와 선택 그룹, 상세 조회 상태가 페이지 이동 후 복원된다.
- 저장된 그룹이 더 이상 유효하지 않으면 유효한 그룹으로 안전하게 대체된다.
- 공통코드 관리 스플리터 분할 크기가 로그인 세션 동안 유지된다.
- 로그아웃 시 페이지 상태와 최근 메뉴 상태가 삭제된다.
- 프론트 빌드, 관련 Vitest, 백엔드 Maven 테스트가 통과한다.
- DB 변경 이력·롤백 문서와 결과 문서가 작성된다.
