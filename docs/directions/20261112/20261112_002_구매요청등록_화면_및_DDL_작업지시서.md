# 20261112_002 구매요청등록 화면 및 DDL 작업지시서

## 작업 목적

기존 MES의 구매요청등록(TMA103/TMA104)과 구매요청확정(TMA103A) 구조를
S-ERP 기준으로 다시 설계한다. 이번 작업은 구매자재 모듈의 첫 화면인
**구매요청등록**을 수주등록 화면과 같은 구조로 구현하고, 이후 확정·발주 단계가
그대로 이어서 쓸 수 있는 구매요청 헤더/상세 테이블을 만든다.

개발 기준은 "업무 흐름대로 명확하고 간소한 기본 버전"이다. MES의 업체별
누적 컬럼과 부가 기능은 가져오지 않고, 확장 여지만 남긴다.

## 확정 범위

### 데이터베이스

- 신규 테이블 `tb_purchase_request_hd`(구매요청 메인),
  `tb_purchase_request_dt`(구매요청 상세) 두 개를 만든다.
  MES 확정 메인(TMA103A)은 별도 테이블로 만들지 않고 헤더에 합친다.
- 확정번호는 따로 발급하지 않는다. 구매요청번호를 그대로 쓴다.
  구매요청 1건은 한 번에 확정한다(분할 확정 없음).
- 확정 관련 컬럼(확정일, 확정자, 확정수량, 확정납기일, 구매처, 입고창고,
  발주구분, 단가, 통화, 금액, 확정비고, 발주대기 마감)은 이번에 테이블에만
  만들고, 입력·처리는 구매요청확정 작업에서 구현한다.
- 수주 연계는 기능 없이 컬럼만 둔다. 상세의 `sales_order_id`,
  `sales_order_detail_id`가 비어 있으면 직접 요청, 값이 있으면 수주에서 넘어온
  요청이다. MES의 INPUT_GBN/OUT_GBN/T_ORDER_GBN 같은 출처 구분 고정값은
  만들지 않는다.
- 헤더와 상세 모두 `created_by`, `created_at`, `updated_by`, `updated_at`
  감사 컬럼을 둔다. 등록 후 품목별 수량·일자를 수정할 수 있으므로 상세에도
  필요하다. 타입은 수주·출하와 같게 `VARCHAR(100)` / `TIMESTAMP`로 한다.
- 금액은 상세에 확정수량×단가 하나만 저장하고, 헤더에는 상세 합계를 저장한다.
  부가세는 발주 단계에서 다룬다.
- 사용용도(`PURCHASE_USE_TYPE`)와 발주구분(`PURCHASE_ORDER_TYPE`)은
  [20261112_001 공통코드](../../database/20261112/20261112_001_change_purchase_common_codes.md)의
  코드값을 저장한다.
- 제거 컬럼: PLANT_CODE, CF_FLAG/CF_DEPT/CF_CHARGE/CF_DATE, DELETE_FLAG,
  CLOSING_FLAG(확정대기 마감), EMERGENCY_FLAG, DRAWING_NO,
  ESTIMATE_COMPANY, ESTIMATE_UPRICE, 외화 단가/금액, 재고 스냅샷 수량,
  BOMAUTO_GBN, FIRST_ARTICLE, FLOWINOUT, 수주 텍스트 복사 컬럼(T_ITEM_* 등),
  OPMAN_CODE3/4·OPTIME3/4.
- 확정하지 않을 요청은 요청자가 삭제한다. 확정대기 마감 기능은 두지 않는다.

### 모듈·메뉴

- 신규 모듈 `MATERIALS`(구매자재, `/materials`, 아이콘 `ShoppingCart`)와
  메뉴 `구매관리 > 구매요청등록`(`/materials/request/request-create`)을
  추가하는 seed 스크립트를 작성한다.
- 권한은 수주등록과 같게 READ/CREATE/UPDATE/DELETE를 부여하고,
  역할 권한은 수주등록 역할 권한을 복사한다.
- 대상 테넌트는 1이다.

### 백엔드

- 패키지 `egovframework.let.materials.request.create`에 Controller /
  Service / DAO / Mapper XML을 수주등록 패턴과 같게 만든다.
- 기능: 신규 저장, 단건 조회, 수정, 삭제.
- 구매요청번호는 `IdSequenceService`로 `MR-yyyyMMdd-NNNN` 형식으로
  채번한다(generator key `MATERIAL_REQUEST_NO`, tenant+요청일 scope).
- 상태는 DB에 영문 코드 `REQUESTED`(요청), `CONFIRMED`(확정)로 저장하고 화면에는 한글 라벨로 표시한다. `REQUESTED` 상태에서만 수정·삭제할 수 있다.
- Java 8 호환 문법만 사용한다.

### 프론트엔드

- 위치 `frontend/src/pages/materials/request/create/`.
- 화면 구조는 수주등록과 같다: 위에 기본정보 폼, 아래에 상세 F1-Grid.
  MES의 좌측 목록/우측 상세 분할 구조는 쓰지 않는다.
- 기본정보: 구매요청번호(자동), 요청일, 요청자·요청부서(로그인 사용자 기준, 읽기 전용), 상태, 비고.
- 상세: 품목(품목 선택기), 품목명, 규격, 단위, 요청수량, 요청납기일,
  사용용도, 비고.
- (2026-11-12 추가) 구매요청 품목은 품목계정(`ITEM_TYPE`)이 원재료(`RAW`)·부재료(`SUB`)·
  소모품(`SUPPLY`)인 품목만 조회·선택할 수 있다. 상품 등 다른 계정의 예외 구매는
  이번 범위에서 다루지 않는다.
- 저장 후 같은 화면에서 재조회·수정·삭제할 수 있다.
- MES의 글자색 상태 표시, "선택품목 다른이름으로 저장", 상단 일괄적용 영역은
  만들지 않는다. 여러 행에 같은 값을 넣는 일괄적용은 F1-Grid 우클릭 메뉴
  방식으로 하기로 했으나, F1-Grid 공통 기능 변경이라 팀 결정 후 별도 작업으로
  추가한다(보류).

## 제외 범위

- 구매요청현황 화면과 목록 조회 API (20261112_003에서 진행)
- 상세 그리드 일괄적용 (F1-Grid 공통 기능, 보류)
- 구매요청확정 화면과 확정·발주대기 마감 처리 (다음 작업)
- 수주 연계 생성 기능
- SQL 실제 DB 적용

## DB 확인 근거

`s-erp-postgresql-readonly` MCP로 다음을 읽기 전용으로 확인했다.

- `tb_sales_order_hd/dt`, `tb_sales_delivery_hd/dt` 컬럼 타입: 감사 컬럼
  `VARCHAR(100)`, 금액·수량 `NUMERIC(15,2)`, 번호 `VARCHAR(30)`,
  비고 `VARCHAR(500)`
- 참조 키: `tb_material_info (material_id, tenant_id)`,
  `tb_customer_info (customer_id, tenant_id)` 복합 유니크 존재.
  `tb_warehouse`는 `warehouse_id` PK와 `(tenant_id, warehouse_code)`만 있다.
  `tb_user.user_id`, `tb_department.department_id` PK, `tb_user.department_id` 존재.
- `tb_module`에 구매자재 모듈이 없고, 영업관리 메뉴 코드 체계
  (`ORDER_CREATE` 등)를 확인했다.
- 테넌트 업무 데이터 행은 조회하지 않았다.

## 구현 절차

1. 본 작업지시서로 계획서와 상세사양서를 작성한다.
2. SQL 정적 테스트와 프론트/백엔드 실패 테스트를 먼저 작성한다.
3. DDL·메뉴 seed·롤백·변경 이력을 `docs/database/20261112`와
   `backend/DATABASE/20261112`에 동일하게 작성하고 `db-schema.md`를 갱신한다.
4. 백엔드 저장·조회·수정·삭제 API를 구현한다.
5. 프론트엔드 화면과 서비스, 대시보드 라우트를 연결한다.
6. 테스트, 빌드, 브라우저 확인 후 결과 문서와 스크린샷을 남긴다.

## 완료 조건

- 상세사양의 컬럼·키·제약이 생성 SQL과 일치하고 두 경로 사본이 동일하다.
- 구매요청등록 메뉴에서 화면이 열리고, 품목을 선택해 저장하면
  `MR-yyyyMMdd-NNNN` 번호가 발급된다.
- 저장 후 상세 수량·납기일 수정, 행 추가·삭제, 문서 삭제가 동작하고
  감사 컬럼이 갱신된다.
- `CONFIRMED` 상태 요청은 수정·삭제가 거부된다.
- 프론트 테스트·빌드, 백엔드 테스트가 통과하고 결과 문서가 남는다.
