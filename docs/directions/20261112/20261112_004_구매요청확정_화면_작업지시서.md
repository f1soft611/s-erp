# 20261112_004 구매요청확정 화면 작업지시서

> **변경 안내 (2026-11-12)**: 단건 확정 구조는 [20261112_005 묶음 확정 구조 변경](20261112_005_구매요청확정_묶음확정_구조변경_작업지시서.md)으로 바뀌었다. 여러 요청을 묶어 확정번호(MC)를 발급하며, 행별 입력 규칙·기본 매입 단가·메뉴 권한은 이 문서를 그대로 따른다.

## 작업 목적

구매요청등록(20261112_002)으로 등록한 구매요청을 불러와 구매 담당자가
확정 정보를 입력하고 **확정**하는 화면을 만든다. 같은 화면에서 확정된 요청의
**발주대기 마감**과 **확정 취소**도 관리한다.

개발 기준은 "업무 흐름대로 명확하고 간소한 기본 버전"이다. 테이블은
20261112_002에서 확정 컬럼까지 미리 만들어 두었으므로 이번 작업에는 DDL 변경이
없고 메뉴 seed만 추가한다.

## 확정 범위

### 업무 규칙 (2026-11-12 사용자 확정)

| 상태 | 확정 화면에서 할 수 있는 일 |
| --- | --- |
| 요청 (`REQUESTED`) | 확정 정보 입력 후 **확정** |
| 확정 (`CONFIRMED`) | 행별 **발주대기 마감 / 마감 취소** 저장, **확정 취소** |

- 구매요청 1건은 한 번에 확정한다(분할 확정 없음). 모든 상세 행에 확정수량을 입력한다.
- 확정수량은 0보다 커야 하며 요청수량보다 많아도 된다(MOQ 등). 0 확정(구매 안 함)은 두지 않는다.
  구매하지 않을 품목은 확정 전에 요청에서 빼거나, 확정 후 발주대기 마감으로 처리한다.
- 확정 입력 항목: 확정일, 확정수량, 확정납기일, 입고창고, 발주구분, 구매처, 단가, 확정비고.
  - 확정자는 로그인 사용자로 서버가 설정한다.
  - 구매처는 행마다 선택한다. 구매처를 고르면 단가관리(`tb_item_partner_price`)의
    거래구분이 매입인 유효 단가를 기본값으로 채우고, 사용자가 고칠 수 있다. 단가가 없으면 빈값이다.
  - 통화는 가져온 단가의 통화를 쓰고, 단가 정보가 없으면 KRW로 한다.
  - 유효 단가가 여러 건이면 적용 시작일이 가장 늦은 단가를 쓴다. 이후 "기본적용단가" 설정이
    생기면 그 값을 먼저 쓰도록 바꾼다(이번 범위 밖).
  - 금액 = 확정수량 × 단가(부가세 제외). 헤더 합계금액은 상세 금액 합계다.
  - 입고창고는 사용자가 직접 선택한다. 기본 창고 자동 설정은 하지 않는다.
- 발주대기 마감: 확정된 품목 중 이번에는 발주하지 않을 품목을 표시한다. 마감한 행은
  이후 발주 화면의 발주 대기 목록에서 빠진다. 마감 취소로 되돌릴 수 있다.
  확정된 요청에만 할 수 있다.
- 확정 취소: 요청 상태로 되돌리고 확정 입력값과 마감 표시를 지운다. 발주 화면이
  생기면 발주된 건은 취소할 수 없도록 조건을 추가한다(이번 범위 밖).

### 데이터베이스

- 테이블 변경 없음. `tb_purchase_request_hd`의 `status`, `confirm_dt`, `confirmer_id`,
  `total_amt`와 `tb_purchase_request_dt`의 확정 컬럼, `order_close_at`을 사용한다.
- 메뉴 seed `구매관리 > 구매요청확정`(`/materials/request/request-confirm`)을 작성한다.
  권한은 READ/UPDATE, 역할 권한은 수주등록(`ORDER_CREATE`)의 READ/UPDATE를 복사한다.
  대상 테넌트는 1이다. SQL은 사용자가 직접 실행한다.

### 백엔드

- 패키지 `egovframework.let.materials.request.confirm`에 Controller / Service / DAO /
  Mapper XML을 기존 패턴대로 만든다.
- 기능: 확정 대상 요청 목록, 단건 조회, 확정, 발주대기 마감 저장, 확정 취소,
  기본 단가 조회.
- 상태 전환은 행 잠금(`FOR UPDATE`)으로 동시 처리를 막는다.
- Java 8 호환 문법만 사용한다.

### 프론트엔드

- 위치 `frontend/src/pages/materials/request/confirm/`.
- 화면 구조는 출하등록과 같다: 위에 기본정보, 아래에 상세 F1-Grid.
  요청 불러오기는 출하등록의 "계획 선택"(`SourceOrderPicker`) 방식을 따른다.
- 그리드는 요청 정보(읽기 전용)와 확정 입력 컬럼을 함께 보여 준다.
- 입고창고는 창고 목록(사용 중), 발주구분은 공통코드 `PURCHASE_ORDER_TYPE`,
  구매처는 공통 거래처 선택기를 쓴다.

## 제외 범위

- 여러 행에 같은 값을 넣는 일괄적용: F1-Grid 공통 기능 변경이라 보류 중이다
  (팀 결정 후 별도 작업). 이번에는 행마다 입력한다.
- 기본 입고창고 자동 설정, 창고 등록의 기본창고 옵션.
- 품목 선택 창 확장(계정 필터·표 형태): 별도 공통 작업으로 보류.
- 분할 확정, 확정 이력 보관, 발주 생성, 부가세·외화 처리.
- 확정 시 단가관리 자동 등록.

## DB 확인 근거 (MCP, 2026-11-12)

- `tb_warehouse`: 테넌트 1에 4건(자재창고, 생산현장창고, 제품창고, 외주창고-A),
  `disuse_at`으로 사용 여부를 구분한다.
- `tb_item_partner_price`: `material_id`, `customer_id`, `trade_type`, `unit_price`,
  `currency`, `start_dt`, `end_dt`, `use_at`. 매입 단가는 `trade_type = '매입'`으로
  저장되어 있다(현재 1건, KRW).
- 확정 컬럼과 CHECK 제약(확정 상태면 확정일·확정자 필수, 확정수량·단가 0 이상,
  `order_close_at` Y/N)은 20261112_002 DDL에서 적용·확인했다.

## 구현 절차

1. 계획서 작성 (`docs/plan/20261112`)
2. 상세 사양서 작성 (`docs/spec/20261112`)
3. 메뉴 seed·롤백·변경 이력 작성 (docs/database, backend/DATABASE 동일 사본)
4. 백엔드 실패 테스트 → 구현
5. 프론트 실패 테스트 → 구현, 라우트 연결
6. 검증: 집중 테스트, 빌드, Java 8 컴파일, 브라우저 375/768/1280px
7. 사용자 seed 실행 후 MCP 확인, 테스트용 자재 품목 매입 단가를 단가관리 API로 등록해 기본 단가
   불러오기 확인, 실제 서버에서 확정·마감·확정 취소 확인
8. 결과 문서와 스크린샷 작성 (`docs/result/20261112/purchase-request-confirm`)

## 완료 조건

- 요청 상태 건을 불러와 확정하면 상태·확정일·확정자·상세 확정값·금액·합계금액이 저장된다.
- 확정 건의 발주대기 마감/마감 취소가 저장된다.
- 확정 취소 시 요청 상태로 돌아가고 확정값·마감이 지워지며, 구매요청등록·현황에서 다시 수정할 수 있다.
- 잘못된 상태 전환(요청 건 마감, 확정 건 재확정 등)은 서버에서 거부된다.
- 결과 문서에 검증 결과, MCP 확인 근거, 커밋 제목·내용이 기록된다.
