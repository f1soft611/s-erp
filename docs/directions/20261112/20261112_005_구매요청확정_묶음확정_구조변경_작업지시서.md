# 20261112_005 구매요청확정 묶음 확정 구조 변경 작업지시서

## 작업 목적

20261112_004 구매요청확정은 구매요청 1건씩 불러와 확정했다. 실제 업무는 **여러 구매요청을 골라
한 번에 확정**하고, 그 묶음 단위로 **구매요청확정번호**를 받는다. MES가 확정 메인(TMA103A)을
별도 테이블로 둔 이유도 이 묶음 확정 때문이다.

20261112_002에서 확정 메인을 요청 헤더에 합쳤던 결정을 바꿔, 확정 메인 테이블을 새로 만들고
구매요청확정 화면을 묶음 확정 구조로 바꾼다.

## 확정 범위

### 업무 규칙 (2026-11-12 사용자 확정)

- 요청 상태의 구매요청을 여러 건 골라 한 번에 확정한다. 확정하면 확정번호 `MC-yyyyMMdd-NNNN`이
  발급된다(generator key `MATERIAL_CONFIRM_NO`, 테넌트 + 확정일 범위).
- 분할 확정은 없다. 구매요청 1건은 확정 1건에만 속하고, 요청의 모든 행을 함께 확정한다.
- 한 확정 묶음 안의 품목은 **통화가 같아야 한다**. 통화가 다르면 경고 메시지를 띄우고 저장하지 않는다
  (화면·서버 모두). 같은 통화 품목끼리 묶어서 확정한다.
- 확정 취소는 **확정번호 전체** 단위다. 묶인 요청은 모두 요청 상태로 돌아가고 확정 입력값과
  발주대기 마감이 지워진다. 일부 요청만 빼는 부분 취소는 없다.
- 취소한 확정은 지우지 않고 사용 안 함(`use_at = 'N'`)으로 표시해 번호 이력을 남긴다.
- 이미 확정한 번호에 요청을 추가하지 않는다. 추가 확정은 새 확정번호로 처리한다.
- 행별 확정 입력(확정수량 > 0, 확정납기일, 입고창고, 발주구분, 구매처, 단가, 통화, 확정비고),
  기본 매입 단가, 발주대기 마감 규칙은 20261112_004와 같다.

### 데이터베이스

- 신규 `tb_purchase_confirm_hd`(구매요청확정 메인): 확정번호, 확정일, 확정자, 통화, 합계금액, 비고,
  사용여부, 감사 컬럼.
- `tb_purchase_request_hd`: `purchase_confirm_id` 추가. `confirm_dt`, `confirmer_id`는 확정 메인으로
  옮기고 삭제한다. 상태 제약을 "요청이면 확정 ID 없음, 확정이면 확정 ID 있음"으로 바꾼다.
- `tb_purchase_request_dt`: 변경 없음.
- 기존 확정 데이터 이전: 확정 상태 요청마다 확정 메인 1건을 만든다. 통화가 섞인 확정 요청이 있으면
  스크립트가 중단된다(먼저 확정 취소 필요).
- SQL은 사용자가 직접 실행한다. 롤백 스크립트를 함께 제공한다.

### 백엔드

- `egovframework.let.materials.request.confirm`을 확정 메인 기준 API로 바꾼다.
  - 확정 대상 요청 목록, 선택한 요청들의 상세 조회, 확정 목록, 확정 단건 조회,
    묶음 확정(신규), 발주대기 마감 저장, 확정 취소, 기본 매입 단가.
- 구매요청등록 단건 조회는 확정일을 확정 메인에서 가져오도록 바꾼다.
- 여러 요청을 잠글 때 ID 순서로 `FOR UPDATE` 해서 교착을 피한다.

### 프론트엔드

- 구매요청확정 화면
  - 신규 확정: [요청 불러오기]에서 요청 상태 건을 체크해 여러 개 고른다. 고른 요청의 모든 품목이
    한 그리드에 구매요청번호와 함께 표시된다. 요청 불러오기는 항상 그리드를 비우고 이번에 고른 요청만 표시한다
    (2026-11-12 사용자 확정, 기존 목록에 누적하지 않음). 잘못 고른 요청은
    [선택 요청 빼기]로 뺀다.
  - [확정 불러오기]로 기존 확정번호를 열어 발주대기 마감 저장, 확정 취소를 한다. 취소된 확정은 읽기 전용이다.
  - [신규]로 화면을 비운다.
  - 통화가 섞이면 경고 메시지를 띄우고 확정하지 않는다.

## 제외 범위

- 부분 확정 취소, 기존 확정에 요청 추가, 분할 확정.
- 취소된 확정에 어떤 요청이 묶여 있었는지의 이력(요청 쪽 연결은 취소 시 해제된다). 필요하면 확정 이력
  테이블을 별도 작업으로 추가한다.
- 일괄적용, 기본 입고창고, 기본적용단가 설정, 확정현황 화면.

## 구현 절차

1. 계획서, 상세 사양서 작성
2. DDL·데이터 이전·롤백·변경 이력 스크립트(docs/database, backend/DATABASE 동일 사본), `db-schema.md` 갱신
3. 기존 확정 테스트 데이터 `MR-20261112-0005`(KRW·USD 혼합)는 새 규칙에 맞지 않으므로, 스크립트 실행 전에
   현재 API로 확정 취소한다.
4. 백엔드 실패 테스트 → 구현
5. 프론트 실패 테스트 → 구현
6. 검증: 집중 테스트, 빌드, JDK 8 컴파일, 브라우저 375/768/1280px
7. 사용자 스크립트 실행 후 MCP 확인, 실제 서버에서 묶음 확정·통화 혼합 차단·마감·확정 취소 확인(데이터는 남김)
8. 결과 문서와 스크린샷 (`docs/result/20261112/purchase-request-confirm-batch`)

## 완료 조건

- 요청 여러 건을 한 번에 확정하면 확정번호 1개가 발급되고, 묶인 요청 모두 확정 상태가 된다.
- 통화가 섞인 묶음은 화면과 서버에서 모두 거부된다.
- 확정 취소 시 확정 메인은 `use_at = 'N'`으로 남고 묶인 요청은 모두 요청 상태로 돌아간다.
- 구매요청등록·현황 화면이 바뀐 테이블에서 정상 동작한다.
- 결과 문서에 검증 결과, MCP 확인 근거, 커밋 제목·내용이 기록된다.
