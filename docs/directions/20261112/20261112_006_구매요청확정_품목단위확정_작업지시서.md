# 20261112_006 구매요청확정 품목 단위 확정 작업지시서

## 작업 목적

20261112_005는 구매요청 단위로 묶어 확정했다. 실제 업무(MES)는 구매요청의 **품목 행을 골라** 확정한다.
품목이 3개인 요청에서 2개만 먼저 확정하고 나머지 1개는 나중에 따로 확정하면 확정번호가 달라진다.
확정을 품목 행 단위로 바꾼다.

## 확정 범위

### 업무 규칙 (2026-11-12 사용자 확정)

- 요청 선택 창은 구매요청 헤더가 아니라 **품목 행**을 보여 주고 행별로 고른다.
  기본 컬럼은 구매요청번호, 요청일, 요청자, 품목코드, 품목명, 규격, 단위, 요청수량, 요청납기일, 사용용도, 비고.
  세부 항목(재고수량, 구매소요일 등)은 이후 조정한다.
- 한 요청의 품목을 여러 확정번호로 나눠 확정할 수 있다. 품목 행 1개는 확정 1건에만 속한다.
- **수량 분할은 없다.** 품목 행의 확정수량은 한 번에 정한다(한 행을 두 확정으로 나누지 않음).
- 구매요청 상태: `REQUESTED`(요청, 확정된 품목 없음) / `PARTIALLY_CONFIRMED`(부분확정) /
  `CONFIRMED`(확정, 모든 품목 확정). 확정·확정 취소 때 서버가 다시 계산한다.
- 구매요청등록의 수정·삭제는 `REQUESTED`일 때만 가능하다(부분확정도 불가).
- 확정 취소는 확정번호 단위다. 그 확정에 들어간 품목만 요청 상태로 돌아가고, 요청 상태를 다시 계산한다.
- 통화 동일, 확정번호 MC, 취소 이력 보존, 행별 입력 규칙은 20261112_005와 같다.

### 데이터베이스

- `tb_purchase_request_dt`에 `purchase_confirm_id` 추가(확정 메인 복합 FK). 확정 연결은 상세 행이 가진다.
- `tb_purchase_request_hd`의 `purchase_confirm_id`와 관련 제약 삭제, 상태 CHECK에 `PARTIALLY_CONFIRMED` 추가.
- 상세 제약: 확정 ID가 있으면 확정수량이 있고, 없으면 확정수량도 없다.
- 기존 데이터 이전: 확정 요청의 헤더 확정 ID를 그 요청의 모든 상세 행으로 옮긴다.
- SQL은 사용자가 직접 실행한다. 롤백 스크립트를 함께 제공한다.

### 백엔드·프론트엔드

- 확정 API: 후보 목록을 품목 행 단위로, 상세 불러오기·확정 요청을 상세 행 ID 기준으로 바꾼다.
- 요청 상태 라벨에 "부분확정"을 추가한다(구매요청등록·현황·확정 화면).
- 확정 화면의 [선택 요청 빼기]는 [선택 행 빼기]로 바꾼다(체크한 품목 행만 뺀다).

## 제외 범위

- 수량 분할 확정, 재고수량·구매소요일 등 선택 창 세부 항목, 요청일 기간 검색.

## 구현 절차

1. 계획서, 상세 사양서
2. DB 스크립트 `20261112_006`(적용·롤백·변경 이력, 두 경로 사본), `db-schema.md`, 정적 테스트
3. 백엔드 실패 테스트 → 구현
4. 프론트 실패 테스트 → 구현
5. 검증: 집중 테스트, 빌드, JDK 8 컴파일, PGlite, 브라우저
6. 사용자 스크립트 실행 후 MCP 확인, 실제 서버에서 부분확정·나머지 품목 별도 확정·확정 취소 확인(데이터 남김)
7. 결과 문서 `docs/result/20261112/purchase-request-confirm-item`

## 완료 조건

- 한 요청의 품목 일부만 확정하면 요청이 부분확정이 되고, 나머지 품목을 다른 확정번호로 확정하면 확정이 된다.
- 확정 취소 시 그 확정의 품목만 요청 상태로 돌아가고 요청 상태가 다시 계산된다.
- 이미 확정된 품목은 선택 창에 나오지 않고, 서버도 다시 확정하지 못하게 막는다.
