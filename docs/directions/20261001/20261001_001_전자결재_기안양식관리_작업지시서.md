# 20261001_001 전자결재 기안양식관리 페이지 작업지시서

## 작업 분류

- 경로: bounded
- 대상: S-ERP 프론트엔드, 백엔드/API 및 HACCP 원본 테이블 스키마 이관
- 메뉴: 기준정보 > 전자결재관리 > 기안양식관리
- 메뉴 코드/경로: `CO_WF_FORM` / `/co/workflow/form` (사용자 첨부 이미지 기준)
- 목적: HACCP의 기안양식 기준정보 테이블 구조와 관리 흐름을 S-ERP로 가져오되, 화면은 S-ERP 공통 페이지 규격과 F1-Grid를 사용한다.

## 확인한 현재 상태

- S-ERP는 React, TypeScript, Vite, MUI, F1-Grid를 사용하며 메뉴 페이지는 `DashboardContent`에서 모듈과 페이지 키로 연결한다.
- `/co/*` 경로는 대시보드 셸에 연결되어 있다. 첨부된 메뉴 경로의 페이지 키는 마지막 경로 세그먼트인 `form`이다.
- S-ERP 프론트엔드와 백엔드 코드 검색에서 기안양식 관리 화면/API 계약을 확인하지 못했다.
- PostgreSQL MCP에서 S-ERP `public` 스키마를 확인했을 때 HACCP의 `tb_drafting_work_category_group`, `tb_drafting_work_category`, `tb_drafting_work_category_authority`는 존재하지 않았다. 업무 데이터 행은 조회하지 않았다.
- HACCP 원본 migration에서 위 세 테이블의 컬럼, 제약 및 인덱스와 `tb_drafting_work_category.drafting_work_template_json/jsonb`, `drafting_work_template_html/text` 컬럼을 확인했다.
- HACCP 원본 구조에서는 분류가 전용 그룹 테이블에 저장되지만, S-ERP 이관 후 분류와 등록주기는 모두 S-ERP 공통코드 그룹/항목으로 관리한다. 양식 행은 공통코드 ID를 `category_item_id`, `reg_term_id`에 저장한다. `code_name`은 원본 양식명으로 보존하고, 등록주기 표시명은 호환을 위해 `reg_term`에 동기화한다.
- S-ERP에는 인증 테넌트/계정 테이블(`tb_tenant`, `tb_login_account`)이 존재한다. 상세 사양에서는 원본 테이블명·업무 컬럼을 보존하면서 S-ERP 기준 테넌트/사용자 참조 FK 호환성을 확인한다.
- 프론트엔드 기준선 빌드/테스트는 승인 전 실행 금지로 인해 아직 확인하지 않았다.

## 작업 목적 및 문제

DB에 등록된 `CO_WF_FORM` 메뉴가 연결할 S-ERP 기안양식관리 화면이 필요하다. HACCP 원본의 `tb_drafting_work_category_group`, `tb_drafting_work_category`, `tb_drafting_work_category_authority` 테이블과 업무 컬럼을 보존해 이관한다. 분류와 등록주기는 S-ERP 공통코드로 관리하고 양식 행에는 각각의 공통코드 ID를 저장한다. 분류 표시명은 `category_item_id`로 공통코드 항목을 조회하고, 원본 `code_name`은 양식명으로 보존한다. 등록주기 표시명은 하위 호환을 위해 기존 `reg_term`에 동기화한다. 분류 공통코드는 기안양식 페이지의 상세코드 도움창에서 관리해 사용자가 공통코드 관리 화면으로 이동하지 않도록 한다. 신규 `tb_electronic_approval_form`은 생성하지 않는다.

## 접근 방식 비교

### 대안 A: HACCP 기준정보 테이블 구조를 S-ERP에 그대로 이관

- 장점: 사용자가 지정한 원본 테이블명·업무 컬럼·도메인 관계를 유지하고 기존 문자열 값 호환성을 보존한다.
- 단점: 분류/등록주기 공통코드 ID 컬럼을 추가하고 기존 문자열 컬럼과 동기화해야 하며, 분류 등록용 공통 도움창이 필요하다.
- 판정: HACCP 저장 테이블 구조를 유지하면서 S-ERP 공통코드 운영 요구도 충족하므로 권장한다. 신규 `tb_electronic_approval_form`은 만들지 않는다.

### 대안 B: S-ERP용 신규 단일 양식 테이블로 재설계

- 장점: S-ERP 도메인에 맞춘 단순한 테이블을 설계할 수 있다.
- 단점: HACCP 기존 테이블을 그대로 가져오라는 지시를 충족하지 못하고 기존 도메인 필드/관계가 손실된다.
- 판정: 채택하지 않는다.

### 대안 C: HACCP 원본 서비스/API를 외부 연동

- 장점: 원본 DB 구조를 별도로 관리하지 않는다.
- 단점: S-ERP 테넌트/권한 및 단일 서비스 운영 방식과 결합하지 않으며 별도 시스템/API 의존성이 생긴다.
- 판정: 채택하지 않는다.

## 구현 범위

- `/co/workflow/form` 메뉴 경로에서 기안양식관리 페이지를 표시한다. DB 메뉴 데이터 자체는 변경하지 않는다.
- 화면 구조와 컴포넌트 조립은 S-ERP 관리 페이지 패턴을 우선한다. `CommonCodeManagementPage`와 `WarehouseManagementPage`를 기준으로 `PageHeader`, `PageSearchArea`, `PageMessageArea`, 기존 권한별 액션 그룹 및 F1-Grid를 재사용하고, 대시보드의 메뉴 경로·breadcrumb 전달 규칙을 따른다.
- S-ERP 테마 토큰, 간격, 로딩·오류·빈 상태, 저장 피드백 및 반응형 규칙을 기존 관리 화면과 일관되게 적용한다. HACCP 원본의 레이아웃이나 독립 디자인 체계를 그대로 복사하지 않는다.
- 검색 영역에는 다른 S-ERP 관리 페이지와 동일하게 통합 검색 필드 하나만 제공한다. 별도의 기본 검색 입력을 여러 개 나열하지 않는다.
- 상세 검색은 `PageSearchArea`의 기존 접이식 상세검색 패턴을 사용한다. 검색 항목은 F1-Grid 컬럼의 `search` 메타데이터에서 생성하고, 상세검색 조건과 통합 검색어를 동일한 조회 흐름에 반영해 F1-Grid에 표시되는 행을 갱신한다.
- 다른 시스템의 그리드 동작은 기존 F1-Grid 기능으로 대체한다. 페이지에서 직접 HTML/MUI 테이블을 구현하지 않으며, 필요한 기능이 F1-Grid에 없는 경우 코어 변경 전에 범위 승인을 받는다.
- 목록은 F1-Grid를 사용하며, 조회와 행 선택·등록·수정 등 승인된 양식 메타데이터 관리 동작을 제공한다.
- 분류와 등록주기 옵션은 기존 S-ERP 공통코드 API에서 각각 활성 `WF_FORM_CATEGORY`, `WF_FORM_CYCLE` 항목을 조회한다.
- 페이지에 `분류 설정` 액션을 제공하고, 별도 공통코드 관리 화면으로 이동하지 않는 공통 상세코드 도움창에서 현재 테넌트의 `WF_FORM_CATEGORY` 항목을 추가/수정한다. 공통코드 그룹 자체는 이 도움창에서 생성/수정하지 않는다.
- 상세코드 도움창은 공통코드 상세 목록, 추가/수정 폼, 사용여부 및 정렬순서를 다루며 기존 공통코드 상세 등록/수정 API를 재사용한다. 기존 API/권한 계약과 맞지 않는 경우 별도 권한/API 설계를 사양서에서 확정한다.
- HACCP 원본 테이블 `tb_drafting_work_category_group`, `tb_drafting_work_category`, `tb_drafting_work_category_authority`를 S-ERP에 동일한 테이블명과 업무 컬럼/타입으로 생성한다. 원본의 템플릿 JSONB/HTML 컬럼도 포함한다.
- 원본 업무 컬럼/테이블명은 유지한다. S-ERP 테넌트/사용자 FK 호환을 위해 참조 대상만 확인하고, 원본 컬럼 의미는 바꾸지 않는다.
- 원본 `drafting_work_category_group_id`와 그룹 테이블은 그대로 보존한다. 공통코드 분류 연결용 `category_item_id BIGINT`를 추가해 `tb_common_code_item.common_code_item_id`를 참조한다.
- 기존 `code_name`과 `reg_term` 문자열 컬럼은 보존한다. 새 `category_item_id`와 `reg_term_id`가 각각 참조하는 공통코드 항목의 `item_nm`을 동일 트랜잭션에서 해당 원본 표시명 컬럼에 동기화한다.
- `code_name`은 HACCP 원본의 양식명으로 유지하고 분류명으로 덮어쓰지 않는다. `category_item_id`는 공통코드 항목을 조인해 분류명을 표시한다. `reg_term_id`가 참조하는 항목의 `item_nm`만 `reg_term`에 같은 트랜잭션으로 동기화한다.
- `WF_FORM_CATEGORY`, `WF_FORM_CYCLE` 공통코드 그룹을 테넌트별로 멱등 seed한다. `WF_FORM_CYCLE`에는 `DAY=일`, `WEEK=주`, `MONTH=월`, `EVENT=발생시` 항목을 seed하고, 분류 항목은 기안양식 페이지의 상세코드 도움창에서 추가한다.
- HACCP 원본 호환용 `tb_drafting_work_category_group`은 구조/관계 보존을 위해 이관하되, 신규 화면의 분류 옵션과 분류 설정은 공통코드 `WF_FORM_CATEGORY`를 기준으로 한다.
- 기존 원본 테이블 기준 목록/등록/수정 API를 S-ERP 백엔드 패턴으로 구현하고, 테넌트/사용자 보안 경계를 유지한다. S-ERP 메뉴 경로, 권한, 공통 화면 및 F1-Grid 요건은 그대로 적용한다.
- 원본 테이블 DDL, `reg_term_id` 추가, 등록주기 공통코드 seed 및 변경 이력/롤백 파일을 `backend/DATABASE/20261001`과 `docs/database/20261001`에 동일하게 작성하고 `docs/database/db-schema.md`를 갱신한다.
- 원본 테이블 DDL, 분류/주기 공통코드 그룹 seed, `category_item_id`/`reg_term_id` 컬럼과 FK, 주기 항목 seed 및 변경 이력/롤백 파일을 `backend/DATABASE/20261001`과 `docs/database/20261001`에 동일하게 작성하고 `docs/database/db-schema.md`를 갱신한다.
- 원본 테넌트의 분류/양식/사용자 행 데이터는 임의 복사하지 않는다. 적용 테넌트에 생성할 초기 데이터가 필요하면 별도 seed 범위를 사양서 승인 전에 명시한다.
- 20261001 DB 이력 폴더의 기존 사용자 변경 파일은 수정·대체하지 않고, 새 파일 번호를 확인해 추가한다.
- 프론트엔드 테스트, 빌드 및 실제 브라우저 확인을 수행한다. 화면 변경 검증은 375px, 768px, 1280px 뷰포트를 포함하고 스크린샷을 결과 폴더에 보관한다.

- HACCP 테이블 이관, 두 코드 그룹 seed, `category_item_id`/`reg_term_id` FK, 주기 항목 seed SQL과 변경 이력/롤백 파일이 양쪽 날짜별 DB 폴더에 동일하게 존재한다.

## 승인 게이트

이 문서는 HACCP 원본 테이블 유지와 등록주기 공통코드 ID/표시명 병행 저장 요구를 반영한 개정안이다. 사용자는 2026-10-01 작업지시서·계획서·상세 사양서를 승인하고 Inline Execution을 선택했으며, 승인된 범위에서 구현과 검증을 진행했다. DB SQL은 초안 상태이며 배포 승인 전까지 실행하지 않는다.
