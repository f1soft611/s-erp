# 20260918_003 공지사항 첨부파일 목록 조회 불일치 작업지시서

## 작업 목적

공지사항 첨부 파일 업로드는 정상적으로 성공(HTTP 200, MinIO 저장, DB insert)하지만, 이후 목록(`GET /api/v1/groupware/boards/notice/posts`) 및 상세 조회 응답의 `attachments`가 항상 빈 배열(`[]`)로 내려오고 `attachmentCount`도 0으로 고정되는 문제를 수정한다.

## 증상 재현

- `POST /api/v1/groupware/boards/notice/posts/{postId}/attachments`로 파일 업로드 시 200 응답.
- 이후 `GET /api/v1/groupware/boards/notice/posts?page=1&size=20&keyword=` 조회 시 해당 게시글의 `attachments: []`, `attachmentCount: 0`으로 표시됨.

## 원인 분석 (MCP 읽기 전용 확인 완료)

- `NoticeBoardServiceImpl.uploadAttachment()`는 `20260916_003` 공통화 작업 이후 `CommonFileService.uploadFile(tenantId, "NOTICE", postId, file, uploaderId)`을 호출하여 파일을 **`tb_common_file`** 테이블(`owner_type='NOTICE'`, `owner_id=postId`)에 저장한다.
- 반면 목록/상세 조회 경로(`NoticeBoardServiceImpl.hydratePost()` → `NoticeBoardDAO.selectNoticeAttachmentList`, 그리고 `NoticeBoard_SQL_postgresql.xml`의 `selectNoticePostList`/`selectNoticePostById`의 `attachment_count` 서브쿼리)는 여전히 레거시 테이블 **`tb_board_file`**만 조회한다.
- 공통화 리팩터링이 업로드/삭제/다운로드 경로만 `tb_common_file`로 이전되고, 조회(hydrate) 경로는 이전되지 않아 두 테이블이 어긋난 상태다.
- MCP(`s-erp-postgresql-readonly`)로 postId=54 기준 확인 결과: `tb_common_file`에는 업로드된 레코드가 1건 존재하고, `tb_board_file`에는 0건이었다. 이는 위 분석과 일치한다.

## 요구사항

1. `NoticeBoardServiceImpl.hydratePost()`가 첨부파일 목록을 `tb_board_file`(`NoticeBoardDAO.selectNoticeAttachmentList`)이 아니라 `CommonFileService.listFiles(tenantId, "NOTICE", postId)` 기준(`tb_common_file`)으로 조회하도록 수정한다.
2. `NoticeBoard_SQL_postgresql.xml`의 `selectNoticePostList`, `selectNoticePostById`에서 계산하는 `attachment_count`를 `tb_common_file` 기준(같은 조건: `owner_type='NOTICE'`, `owner_id=post_id`, `deleted_yn='N'`)으로 맞추거나, Java 계층에서 `commonFileService.listFiles()` 결과 크기로 `attachmentCount`를 계산하도록 변경한다. (SQL과 Java 로직 중 팀 기존 패턴에 맞는 방식을 사양서 단계에서 확정)
3. 응답 JSON의 필드명(`attachments`, `attachmentCount`)과 각 첨부파일 항목의 필드 구조는 기존 프론트 계약을 유지한다. `CommonFileVO` → `NoticeBoardFileVO` 매핑이 필요하면 기존 필드명을 그대로 보존한다.
4. 더 이상 사용되지 않게 되는 `tb_board_file` 기반 DAO 메서드(`selectNoticeAttachmentList`, `selectNoticeAttachmentById`, `insertNoticeAttachment`, `softDeleteNoticeAttachment`)는 삭제 여부를 사양서에서 판단한다(즉시 삭제보다는 사용처 재확인 후 결정).
5. 첨부파일 삭제(`deleteAttachment`)와 다운로드(`downloadAttachment`) 경로가 이미 `commonFileService` 기준으로 동작 중인지 함께 재확인하여 조회 경로와 일관성을 보장한다.
6. 기존 목록/상세 조회의 다른 필드(댓글, 페이지네이션 등) 동작에는 영향을 주지 않는다.
