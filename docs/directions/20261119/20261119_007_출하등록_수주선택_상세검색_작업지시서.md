# 출하등록 수주 선택 상세검색 작업지시서

## 목표

출하등록의 수주 선택 모달에 현황 화면과 같은 통합검색·상세검색 흐름을 적용하고, 필수 기준일과 기존 빠른 날짜 설정을 제공한다.

## 범위

- 통합검색은 기존 수주번호·거래처·품목 검색을 유지한다.
- 상세검색은 수주일자 기간을 필수 기준일로 제공하고 기존 빠른 날짜 버튼(오늘, 이번주, 이번달, 전월, 최근 30일)을 그대로 사용한다.
- 수주번호, 거래처, 품목, 계획번호 및 선택 계획일자 조건을 제공한다.
- 검색 조건은 기존 미납 계획 상세 조회에 서버 측으로 적용한다.
- 기존 F1-Grid 결과, 체크 선택, 같은 거래처 검증, 선택/닫기 흐름을 유지한다.

## 작업 절차

1. 계획서와 상세사양서를 확인한다.
2. 프론트엔드와 백엔드의 검색 조건 테스트를 먼저 추가하고 실패를 확인한다.
3. 검색 폼, 조회 API/서비스/Mapper 조건을 구현한다.
4. 관련 Vitest, Maven 테스트 및 프론트엔드 빌드를 실행한다.
5. 375px, 768px, 1280px 브라우저에서 상세검색과 결과 그리드를 확인한다.
6. 결과 문서와 화면 캡처를 `docs/result/20261119/delivery-order-picker-detailed-search/`에 기록한다.

## 완료 조건

- 필수 수주일자 범위가 없거나 잘못된 경우 검색을 실행하지 않는다.
- 빠른 날짜 버튼이 서버 기준일로 기존과 동일하게 날짜 범위를 설정한다.
- 통합검색과 상세검색의 여러 조건이 실제 API 조회에 반영된다.
- 필터링 후에도 tenant 조건, 미납 잔량 조건, 200건 제한 및 기존 선택 검증이 유지된다.
- DB 스키마 변경 없이 관련 테스트와 빌드가 통과한다.

## 확인된 데이터 계약

- `s-erp-postgresql-readonly`에서 `list_tables`로 출하/수주/계획 관련 테이블을 확인했다.
- `tb_sales_order_hd`, `tb_sales_order_dt`, `tb_sales_delivery_plan_hd`, `tb_sales_delivery_plan_dt`, `tb_customer_info`, `tb_material_info`의 컬럼 메타데이터를 읽기 전용 MCP로 확인했다.
- 수주일자(`order_dt`)는 필수이고 계획일자(`plan_dt`)는 nullable이다. 업무 데이터 행은 조회하지 않았다.
- 신규 테이블/컬럼/FK 및 데이터 마이그레이션은 없다.
