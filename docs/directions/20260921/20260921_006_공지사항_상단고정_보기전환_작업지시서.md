# 20260921_006 공지사항 상단 고정 영역 및 보기 전환 작업지시서

## 작업 분류

- 경로: `architectural`
- 대상: 프론트엔드
- 관련 화면: `/groupware/community/notice`
- 관련 컴포넌트: `CommunityNoticePage`, `frontend/src/shared/components` 공통 보기 컴포넌트, 도메인별 어댑터

## 작업 목적

공지사항을 시작점으로 게시판·자료실·그룹웨어 업무 화면에서 재사용할 수 있는 좌우 분할 콘텐츠 셸과 피드형·리스트형 공통 보기 기반을 마련한다. 콘텐츠 영역은 좌측 목록과 우측 요약 영역으로 나누고, 좌측 목록이 길어져 세로 스크롤이 발생해도 우측 요약 영역은 화면 상단 기준으로 고정되어 계속 표시되도록 한다.

## 요구사항

1. 콘텐츠 영역을 좌측 목록 영역과 우측 요약 영역으로 나눈다.
2. 좌측 영역 최상단에는 상단 고정 공지 개수와 피드형·리스트형 보기 선택 버튼을 같은 행에 배치한다.
3. 상단 고정 개수는 현재 조회 목록에서 상단 고정 대상으로 판별되는 항목 수를 표시한다.
4. 상단 도구 행 아래에는 상단 고정 기능을 위한 별도 영역을 배치하고, 고정 공지가 없으면 빈 상태를 표시한다.
5. 상단 고정 영역 아래에는 선택된 모드의 피드 또는 리스트를 표시한다.
6. 우측 영역에는 공지 요약과 최근 이슈를 배치한다.
7. 좌측 목록이 길어질 때 페이지 또는 콘텐츠 외부에 세로 스크롤이 발생하도록 하되, 우측 요약·최근 이슈 영역은 `position: sticky` 기반으로 고정한다. 우측 영역 안에는 별도 세로 스크롤을 만들지 않는다.
8. 최초 진입 시 피드형을 기본 선택한다.
9. 리스트형 선택 시 첨부 이미지와 같은 문서형 행 목록을 표시한다.
10. 리스트형 각 행은 좌측 문서 아이콘, 중앙 제목, 제목 옆 사용자 아이콘, 아래 작성자·작성일시 메타정보로 구성한다.
11. 상단 고정 공지 행은 연한 강조 배경과 강조 색상의 제목으로 표시하고, 일반 공지 행은 기본 배경으로 표시한다.
12. 리스트형은 고정된 표 형태의 다중 컬럼 대신 제목 영역이 넓게 보이는 단일 행 카드형 목록으로 표시한다.
13. 피드형 선택 시 현재 카드 기반 피드 표시와 기존 피드 상호작용을 유지한다.
14. 보기 모드 전환 버튼을 클릭하면 해당 모드로 목록을 다시 조회한다.
15. 리스트형 항목 클릭 후 우측 요약 영역을 상세 현황으로 대체하는 기능은 이번 작업에서 구현하지 않는다.
16. 피드형 전환 중에는 좌측 목록에 피드형 스켈레톤을, 리스트형 전환 중에는 좌측 목록에 리스트형 스켈레톤을 표시한다.
17. 모드 전환으로 목록을 재조회하는 동안 우측 영역에는 공지 요약·최근 이슈 전용 요약 스켈레톤을 표시한다.
18. 재조회 실패 시 좌측 목록 영역과 우측 요약 영역에 선택 모드에 맞는 오류 또는 대체 상태를 표시하고 기존 재시도 흐름을 유지한다.
19. 좌우 분할 셸, 좌측 상단 도구 영역, 상단 고정 영역, 피드형·리스트형 목록, 좌측 모드별 스켈레톤, 우측 요약 스켈레톤을 책임별 공통 컴포넌트로 분리한다.
20. 페이지 조립부는 모드·재조회·로딩·오류 상태와 도메인 데이터를 관리하고 공통 셸에는 슬롯과 콜백만 전달한다.
21. 공통 컴포넌트는 공지사항 API 타입이나 도메인 액션을 직접 참조하지 않고 제네릭 데이터와 슬롯·렌더러·콜백을 전달받는다.
22. 게시판·자료실·그룹웨어 업무 화면은 동일한 좌우 셸을 사용하고 도메인별 필드·요약·동작은 어댑터와 슬롯으로 주입한다.
23. 기존 필터, 새 공지 작성, 새로고침, 오류·로딩·빈 상태 동작은 변경하지 않는다.
24. 375px, 768px, 1280px에서 영역이 겹치거나 잘리지 않고 불필요한 중첩 세로 스크롤이 생기지 않아야 한다.

## 현재 확인 결과

- `CommunityNoticePage`가 필터, 공지 목록, 요약 패널을 조립하고 있다.
- 현재 콘텐츠 그리드는 목록과 요약을 나누지만, 상단 도구가 좌측 목록에 속하지 않고 상단 고정 영역이 별도 행으로 렌더링되어 목표 레이아웃과 다르다.
- 현재 요약 패널은 목록과 같은 그리드 행에 있지만 sticky 고정 규칙이 없어 목록 스크롤 시 우측 영역 고정 요구를 충족하지 않는다.
- `NoticeFeedList`가 `FeedList`와 카드 렌더러를 통해 피드형 공지 항목을 직접 표시하고 있다.
- `NoticeFeedItem.highlight`와 API의 `isNotice === 'Y'` 매핑이 이미 존재하므로 상단 고정 대상 판별에 재사용할 수 있다.
- 기존 화면에는 피드형·리스트형 보기 상태나 상단 고정 전용 표시 영역이 없다.
- 현재 공지 재조회 함수가 필터 변경·재시도 흐름에서 사용되고 있으므로 보기 모드 전환 시에도 같은 조회 경로를 재사용할 수 있다.
- 피드형은 댓글·첨부·상세 확장 등 기존 상호작용이 많으므로 현재 `NoticeFeedList`를 피드 렌더러로 유지하고, 리스트형은 별도 전용 컴포넌트로 분리한다.
- `frontend/src/shared/components/feed/FeedList.tsx`와 현재 `view-mode` 컴포넌트가 공통 목록 렌더링 기반이다. 좌우 셸은 별도 공통 레이아웃으로 승격해 게시판·자료실에서도 사용해야 한다.
- 기존 테스트에는 공지 목록 및 피드 상호작용 회귀 케이스가 있어 보기 모드별 테스트를 추가할 수 있다.

## 접근 방식 비교

### 대안 A: 페이지에서 별도 상단 고정 목록과 보기 모드별 컴포넌트를 모두 분리

- 장점: 모드별 마크업과 상단 영역의 책임이 명확하다.
- 단점: 상세·댓글·첨부 이벤트 연결이 중복되고 기존 동작 회귀 범위가 커진다.
- 판정: 동작 중복이 커서 채택하지 않는다.

### 대안 B: 공통 좌우 콘텐츠 셸과 모드별 목록 컴포넌트를 조합

- 장점: 게시판·자료실·업무 화면이 동일한 좌우 구조를 재사용하고 피드·리스트·요약을 슬롯으로 교체할 수 있다.
- 단점: 셸의 슬롯 계약과 단일 스크롤 책임을 먼저 정의해야 한다.
- 판정: 공통 화면 구조와 모드별 소스 분리를 함께 만족하므로 채택한다.

### 대안 C: 하나의 목록 컴포넌트 내부에서 조건부로 피드형·리스트형을 렌더링

- 장점: 파일 수와 초기 연결 지점이 적다.
- 단점: 피드·리스트 마크업과 스켈레톤 조건이 한 파일에 섞여 변경 영향과 테스트 범위가 커진다.
- 판정: 소스 분리 요구에 맞지 않아 채택하지 않는다.

### 대안 D: 보기 모드를 전역 사용자 설정 또는 서버 설정으로 저장

- 장점: 재방문 시 사용자의 선택을 유지할 수 있다.
- 단점: 이번 요구사항에 없는 저장 계약과 초기화 정책이 필요하다.
- 판정: 범위를 벗어나므로 채택하지 않는다.

### 대안 E: 공지사항 폴더 안에 전체 레이아웃을 두고 다른 도메인에서 복사

- 장점: 공지사항 구현을 빠르게 끝낼 수 있다.
- 단점: 게시판·자료실·업무 화면마다 마크업과 스켈레톤이 복제되어 동작·접근성·반응형 수정이 분산된다.
- 판정: 공통 사용 요구와 유지보수 목적에 맞지 않아 채택하지 않는다.

## 구현 범위

- `frontend/src/shared/components` 아래에 도메인 중립적인 좌우 콘텐츠 셸, 보기 모드 타입, 피드형 렌더러, 리스트형 렌더러, 좌측 상단 도구 영역, 모드별 스켈레톤을 분리한다.
- 좌측 상단 도구 영역은 상단 고정 카운터와 피드형·리스트형 버튼을 담당하고, 상단 고정 영역은 별도 컴포넌트로 분리한다.
- 공통 피드·리스트·셸 컴포넌트는 제네릭 표시 모델과 슬롯/render prop/콜백을 사용하며 공지사항 타입·서비스를 import하지 않는다.
- `CommunityNoticePage`는 공지사항 데이터를 공통 표시 모델로 변환하는 어댑터와 공지 전용 상호작용 콜백을 제공한다.
- 기존 `NoticeFeedList`의 복잡한 피드 상호작용은 공통 좌우 셸의 좌측 슬롯에 주입하고, 리스트형은 공통 리스트 렌더러에 공지 표시 모델을 주입한다.
- 공통 리스트 렌더러는 문서 아이콘·제목·사용자 아이콘·작성자·작성일시 메타정보를 표시하는 문서형 행 레이아웃을 제공한다.
- 공통 리스트 렌더러는 `isPinned` 또는 강조 상태를 받아 고정 공지 행의 배경과 제목 색상을 구분한다.
- 게시판·자료실·그룹웨어 업무 화면이 동일한 공통 컴포넌트를 사용할 수 있도록 최소 계약과 사용 예시를 문서화한다.
- 페이지 조립부는 좌우 셸의 좌측 슬롯에 선택된 목록·스켈레톤을, 우측 슬롯에 공지 요약·최근 이슈를 렌더링한다.
- 좌측 슬롯은 상단 도구 행, 상단 고정 영역, 일반 목록 순서로 조립한다.
- 공통 좌우 셸은 좌측 콘텐츠의 세로 길이와 무관하게 우측 슬롯을 `position: sticky`로 고정하고, 우측 슬롯 내부에는 별도 스크롤을 두지 않는다.
- 상단 고정 공지는 기존 `highlight`/중요 공지 판별 결과를 이용해 표시한다.
- 보기 모드 전환 시 선택 모드를 먼저 반영하고 해당 모드의 공지 목록을 다시 조회한다.
- 재조회 중에는 좌측에 선택한 모드에 맞는 피드형 또는 리스트형 스켈레톤을 표시하고, 우측에는 요약 스켈레톤을 표시한다.
- 피드형의 기존 제목 클릭, 확장·상세 조회, 첨부파일·댓글 등 동작은 유지한다.
- 리스트형은 제목·작성자·작성일시 중심의 표시만 구현하고, 항목 클릭에 따른 우측 상세 현황 패널은 후속 작업으로 남긴다.
- 관련 Vitest 회귀 테스트를 추가하고 프론트 빌드 및 375px·768px·1280px 브라우저 검증을 수행한다.
- `docs/result/20260921/notice-pinned-view-toggle/`에 결과 문서와 스크린샷을 기록한다.

## 완료 기준

- 공지 콘텐츠가 좌측 목록과 우측 공지 요약·최근 이슈의 2열 구조로 표시된다.
- 좌측 최상단 한 행에 상단 고정 개수와 피드형·리스트형 전환 컨트롤이 표시된다.
- 상단 도구 행 아래에 별도 상단 고정 영역이 표시된다.
- 좌측 목록이 길어져 세로 스크롤이 발생해도 우측 공지 요약·최근 이슈가 화면 상단 기준으로 고정된다.
- 우측 요약 영역 내부에는 별도 세로 스크롤이 생기지 않는다.
- 최초 진입 시 피드형이 선택되고 기존 카드형 화면이 보인다.
- 리스트형 선택 시 첨부 이미지와 같은 문서형 행 목록으로 변경된다.
- 리스트형 행에는 좌측 문서 아이콘, 제목, 제목 옆 사용자 아이콘, 작성자·작성일시 메타정보가 표시된다.
- 상단 고정 공지 행은 연한 강조 배경과 강조 제목 색상으로 표시된다.
- 피드형과 리스트형의 목록 렌더링 소스가 별도 컴포넌트로 분리되어 있다.
- 피드형과 리스트형의 스켈레톤 소스가 별도 컴포넌트로 분리되어 있다.
- 공통 보기 컴포넌트가 공지사항 API 타입과 분리되어 있다.
- 게시판·자료실·그룹웨어 업무에서 재사용할 수 있는 제네릭 props/표시 모델 계약이 정의되어 있다.
- 공지사항은 도메인 어댑터를 통해 공통 컴포넌트를 사용한다.
- 피드형·리스트형 전환 시 목록을 다시 조회한다.
- 피드형 전환 중에는 좌측에 피드형 스켈레톤, 리스트형 전환 중에는 좌측에 리스트형 스켈레톤이 표시된다.
- 모드 전환 재조회 중 우측에는 공지 요약·최근 이슈 스켈레톤이 표시된다.
- 상단 고정 개수가 현재 목록의 고정 항목 수와 일치한다.
- 피드형의 기존 상세 조회·확장, 첨부, 댓글, 수정·삭제 동작이 정상 동작한다.
- 리스트형 클릭 후 우측 상세 현황 패널은 표시되지 않으며, 해당 기능이 범위에서 제외되어 있음이 유지된다.
- 좌우 셸과 상단 도구가 375px, 768px, 1280px 뷰포트에서 겹침·잘림 없이 표시되고, 데스크톱에서는 우측 영역 sticky 고정이 동작한다.
- 관련 테스트와 빌드, 브라우저 검증 결과가 결과 문서에 기록된다.

## DB 영향

- 신규 테이블·컬럼·인덱스·마이그레이션 없음
- SQL 및 rollback 스크립트: 해당 없음

## 승인 게이트

작업지시서 작성 완료. 사용자가 목표와 범위를 승인하기 전에는 계획서·상세 사양서 작성, 테스트 작성·실행, 코드 수정, 빌드, 브라우저 검증을 수행하지 않는다.
