# 20260921_003 공지사항 조회수 등록 작업지시서

## 작업 분류

- 경로: `bounded`
- 대상: 프론트엔드 및 백엔드
- 관련 화면: `/groupware/community/notice`
- 관련 API: `GET /api/v1/groupware/boards/notice/posts/{postId}`

## 작업 목적

공지사항 피드에서 게시글 상세 내용을 조회할 때 인증된 사용자별로 공지글당 최초 1회만 기존 게시글의 조회수(`view_count`)를 증가시키고, 증가된 조회수가 목록·상세 응답에 표시되도록 한다.

## 현재 확인 결과

- `tb_board_post.view_count` 컬럼은 이미 존재한다.
- 타입은 `integer`, `NOT NULL`, 기본값은 `0`이다.
- 공지사항 응답 VO와 MyBatis resultMap에도 `viewCount` 매핑이 이미 존재한다.
- 공지사항 상세 조회 서비스는 게시글 조회와 첨부파일·댓글 보강만 수행하고, 조회수 증가 UPDATE는 호출하지 않는다.
- 사용자별 중복 조회를 서버 간 재시작 이후에도 보장하려면 조회 이력을 영속화해야 한다.
- 따라서 기존 `view_count`는 재사용하되, 사용자별 최초 조회를 기록하는 신규 조회 이력 테이블과 DDL이 필요하다.

## 요구사항

1. 인증된 사용자가 존재하는 공지사항 상세 조회를 성공하면 `(tenant_id, post_id, login_id)` 조합으로 최초 조회 여부를 확인한다.
2. 해당 조합의 조회 이력이 없을 때만 조회 이력을 등록하고 게시글의 `view_count`를 1 증가시킨다.
3. 동일 사용자의 새로고침·반복 상세 조회·동시 요청은 조회수에 추가 영향을 주지 않는다.
4. 삭제된 게시글 또는 존재하지 않는 게시글은 조회 이력과 조회수 증가 대상에서 제외한다.
5. 동시 상세 조회에서도 중복 등록과 증가값 유실이 발생하지 않도록 DB 유니크 제약과 원자적 처리를 사용한다.
6. 상세 조회 응답의 `item.viewCount`는 사용자별 최초 조회 처리 후 값을 반환한다.
7. 목록 조회는 목록을 불러오는 행위만으로 조회수를 증가시키지 않는다.
8. 공지사항 작성·수정·삭제, 첨부파일, 댓글, 좋아요·북마크 동작은 변경하지 않는다.
9. 프론트엔드는 상세 응답의 `viewCount`를 현재 피드 조회수 표시 위치에 연결하며, 이미 연결되어 있다면 필요한 최소 변경만 적용한다.

## 조회수 집계 정책

- 기본 정책: 인증된 사용자 1명당 공지글 1개에 대해 최초 상세 조회 1회만 증가한다.
- 중복 기준: `tenant_id + post_id + login_id` 조합
- 브라우저 새로고침·같은 상세 조회 API 재호출·동시 재호출은 최초 1회 이후 증가하지 않는다.
- 사용자 식별은 인증 컨텍스트의 로그인 계정 ID를 사용하며 IP나 브라우저 식별자는 사용하지 않는다.

## 권장 설계

- 조회 이력 테이블을 추가하고 `tenant_id`, `post_id`, `login_id`, 최초 조회 시각을 저장한다.
- 조회 이력 테이블에 `(tenant_id, post_id, login_id)` 유니크 제약을 둔다.
- `NoticeBoardDAO`에 조회 이력 최초 등록과 공지 게시글 조회수 원자 증가 메서드를 추가한다.
- `NoticeBoard_SQL_postgresql.xml`에서 중복 등록 결과를 판별한 뒤 최초 등록일 때만 `tb_board_post.view_count = view_count + 1`을 수행한다.
- `NoticeBoardServiceImpl.getPost`에서 인증된 로그인 ID를 전달받아 게시글 존재 여부 확인, 조회 이력 등록, 조건부 증가, 상세 보강 순서를 트랜잭션으로 처리한다.
- 조회 이력 유니크 충돌은 정상적인 중복 조회로 처리하고 오류 응답으로 노출하지 않는다.
- 서비스 단위 테스트에서 최초 조회 증가, 동일 사용자 재조회 미증가, 다른 사용자 증가, 삭제·미존재 게시글 미증가를 검증한다.
- 구현 전 MCP와 기존 스키마 이력을 재확인하고, `backend/DATABASE/20260921/` 및 `docs/database/20260921/`에 SQL·변경 이력·rollback을 동일하게 작성한다.

## 완료 기준

- 사용자별 공지 최초 상세 조회 1회에서만 해당 공지의 조회수가 정확히 1 증가한다.
- 동일 사용자의 반복·동시 조회는 조회수가 추가 증가하지 않는다.
- 다른 사용자의 최초 조회는 각각 1회 증가한다.
- 존재하지 않거나 삭제된 공지의 조회 이력과 조회수는 변경되지 않는다.
- 동시 요청에서도 중복 이력과 증가분 유실이 발생하지 않는다.
- 상세 응답과 피드 표시에서 증가된 조회수가 확인된다.
- 목록 조회만으로 조회수가 증가하지 않는다.
- 관련 테스트와 빌드 검증 결과가 결과 문서에 기록된다.
- 조회 이력 테이블 DDL, rollback, 스키마 문서와 MCP·매퍼 확인 근거가 결과 문서에 기록된다.
