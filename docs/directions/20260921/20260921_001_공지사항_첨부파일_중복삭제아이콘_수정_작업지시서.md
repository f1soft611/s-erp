# 20260921_001 공지사항 첨부파일 중복·삭제 오류 및 확장자 아이콘 수정 작업지시서

## 작업 분류

- 경로: `bounded`
- 대상: 프론트엔드 + 백엔드
- 관련 화면: `/groupware/community/notice`

## 작업 목적

공지사항 첨부파일의 저장 후 재조회, 수정 삭제, 표시 UI를 실제 공통 첨부파일 계약과 일치시킨다.

## 확인된 현상

1. 첨부파일 1개를 등록하고 저장한 뒤 목록을 재조회하면 동일 파일이 2건으로 표시된다.
2. 공지 수정 화면에서 기존 첨부파일을 삭제하고 저장하면 `공지사항 첨부파일을 찾을 수 없습니다.` 404가 발생한다.
3. 첨부 영역에서 `xlsx` 같은 확장자 텍스트가 파일 아이콘 대신 표시된다.

## 현재 코드 기준 원인 가설

- `NoticeBoardServiceImpl.hydratePost()`가 `commonFileService.listFiles(tenantId, "NOTICE", postId)`로 첨부 목록을 채운 뒤, 같은 `tb_common_file`을 조회하는 `selectNoticeAttachmentList()` 결과를 다시 추가한다.
- 수정 시 삭제 요청은 `boardFileId`를 사용하므로 조회 응답의 첨부 ID가 실제 `tb_common_file.file_id`와 일치하고, 삭제 대상이 `ATTACHMENT`와 `EMBEDDED`로 혼합되지 않는지 계약을 보강해야 한다.
- 공통 `AttachmentList`는 확장자별 색상 배지와 확장자 라벨을 직접 렌더링하므로, 파일 종류를 나타내는 아이콘 컴포넌트와 라벨 표시 정책을 조정해야 한다.

## 요구사항

1. 공지 첨부파일을 등록한 뒤 목록·상세 재조회에서 동일 파일이 한 번만 표시되도록 한다.
2. 수정 화면에서 기존 첨부파일을 삭제하고 저장해도 404가 발생하지 않도록 한다.
3. 삭제 검증은 테넌트, 공지 게시글 소유자, 실제 파일 ID를 기준으로 유지하며 본문 임시 이미지(`EMBEDDED`)가 일반 첨부 삭제 대상에 섞이지 않도록 한다.
4. 업로드·목록·상세·수정 삭제·다운로드가 동일한 `tb_common_file`/공통 파일 서비스 계약을 사용하도록 정합성을 맞춘다.
5. 첨부 영역에서 `xlsx`, `pdf`, `docx`, `pptx`, 이미지, 압축파일 등 확장자에 맞는 파일 아이콘을 표시한다. 파일명과 다운로드/삭제 동작은 유지한다.
6. 기존 공지 본문, 댓글 첨부, 권한, API 경로와 응답 필드명은 변경하지 않는다.
7. 신규 테이블·컬럼·DB 마이그레이션은 추가하지 않는다.

## 권장 설계

- 백엔드 `hydratePost()`에서 일반 첨부는 `CommonFileService.listFiles()` 한 경로로만 구성하고, 본문 이미지 조회가 필요할 때만 `EMBEDDED` 파일을 별도로 사용한다.
- 일반 첨부 응답은 `CommonFileVO.fileId`를 `NoticeBoardFileVO.boardFileId`로 변환해 프론트 삭제·다운로드 키로 일관되게 사용한다.
- 삭제 전 소유자 검증은 일반 첨부 목록 기준으로 수행하고, 삭제 후 재조회 결과에 삭제 파일이 남지 않는지 확인한다.
- 공통 `AttachmentList`의 확장자 매핑을 파일 아이콘 중심으로 바꾸되, 지원하지 않는 확장자는 기본 파일 아이콘을 사용한다.

## 대안 및 트레이드오프

- 프론트에서 중복 ID를 제거하고 404 삭제를 무시하는 방식은 화면 증상만 완화하고 서버 조회 경로의 중복 원인을 남기므로 채택하지 않는다.
- 백엔드에서 SQL 조회와 공통 서비스 조회를 모두 유지하면서 Java에서 중복 제거하는 방식은 레거시 호환성은 높지만, 일반 첨부와 본문 이미지의 의미가 다시 섞일 위험이 있어 채택하지 않는다.

## 완료 기준

- 첨부 1개 저장 후 목록과 상세에서 1개만 표시된다.
- 기존 첨부를 수정 화면에서 삭제한 뒤 저장하면 성공하고, 재조회 시 삭제 파일이 표시되지 않는다.
- 다운로드와 일반 첨부 삭제가 실제 파일 ID 기준으로 정상 동작한다.
- 본문 이미지 첨부는 일반 첨부 목록에 중복 표시되지 않고 본문 이미지 렌더링은 유지된다.
- 확장자별 파일 아이콘이 데스크톱과 모바일에서 잘리지 않고 표시된다.
- 관련 테스트와 프론트 빌드, 백엔드 테스트 및 실제 브라우저 검증 결과를 결과 문서에 기록한다.

## 검증 계획

- 구현 전 승인된 계획·사양서에 따라 관련 테스트를 먼저 확인한다.
- 프론트: 첨부 목록 컴포넌트 및 공지 수정 흐름의 Vitest, `npm run build`.

- 브라우저: 첨부 업로드 후 재조회, 수정 삭제 저장, 확장자 아이콘 표시를 375px 및 1280px 이상에서 확인한다.
