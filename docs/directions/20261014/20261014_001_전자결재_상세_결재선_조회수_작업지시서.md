# 20261014_001 전자결재 상세 작성자 헤더·결재선·조회수 작업지시서

## 작업 분류

- 대상: 프론트엔드, 백엔드, PostgreSQL 스키마
- 화면: 전자결재 우측 상세 피드
- API: `GET /api/v1/groupware/approvals/documents/{electronicApprovalId}`
- 기준 설계: [전자결재 상세 헤더·결재선 설계](../../superpowers/specs/2026-10-14-document-approval-line-view-count-design.md)

## 작업 목적

공유된 두 참조 이미지와 일치하도록 전자결재 상세의 작성자 메타 행과 읽기 전용 결재선을 정돈한다. 현재 결재 상세 응답에는 조회수가 없으므로, 공지사항과 같은 인증 사용자별 최초 상세 조회 정책을 추가하고 서버가 반환하는 실제 조회수를 작성자 메타 행에 표시한다.

## 현재 확인 결과

- `tb_electronic_approval_main`에는 `view_count` 컬럼이 없다.
- `tb_electronic_approval_view_history` 테이블이 없다.
- `DocumentApprovalDetailVO` 및 전자결재 상세 MyBatis resultMap에 `viewCount`가 없다.
- 상세 API는 로그인 사용자 정보를 받고, 결재 문서의 tenant 및 기안자/참여자 조건으로 상세 접근을 확인한다.
- `LoginVO.id`는 로그인 코드이며, 기존 공지사항 조회수 구현은 tenant와 로그인 코드를 사용해 `tb_login_account.login_id`를 해석한다.
- 기존 결재선 패널은 작성자 Avatar/이름 행을 제거하고, 순번 이름 중앙 정렬, 선형 화살표, 합의·참조 chip으로 표시한다.
- 읽기 전용 PostgreSQL MCP 확인:
  - `list_tables`: 전자결재 본문·결재선 테이블은 확인했고 결재 조회 이력 테이블은 확인되지 않았다.
  - `describe_table(tb_electronic_approval_main)`: 조회수 컬럼 없음.
  - `describe_table(tb_board_post)`: 공지사항은 `view_count integer NOT NULL DEFAULT 0`을 사용.
  - `describe_table(tb_board_post_view_history)`: 공지사항의 사용자별 최초 조회 이력을 저장.

## 요구사항

### 상세 작성자 행

1. 결재선 패널 위에 기존 형식의 작성자 Avatar와 작성자 이름을 복원한다.
2. 이름 아래 한 줄에 `기안자 · YYYY.MM.DD · 조회 N` 메타 정보를 표시한다.
3. `조회 N`은 상세 API가 반환한 실제 누적값만 표시하며 프론트엔드에서 임의 증가·기본 숫자 대입을 하지 않는다.
4. 기존 문서 더보기, 문서 상태, 삭제/수정 동작은 유지한다.

### 결재선 패널

1. 작성자 행과 분리된 둥근 배경 패널을 유지하고, 패널 헤더는 `결재선` 및 `기안자 {이름} · {기안일}`을 표시한다.
2. 결재자는 `stageOrder`, `participantOrder` 오름차순으로 현재 카드 형태와 상태 도장을 유지해 표시한다.
3. 카드 사이 연결은 선이 없는 작은 오른쪽 꺾쇠 화살표로 표시한다. 마지막 카드 뒤에는 화살표를 표시하지 않는다.
4. 카드 하단 순번과 이름은 하나의 묶음으로 가로·세로 중앙에 배치한다. 긴 이름은 한 줄 말줄임 처리한다.
5. `AGREEMENT`, `REFERENCE`는 chip 대신 각각 `합의`, `참조` 제목이 있는 별도 행으로 표시한다. 각 사람의 실제 `stageOrder` 순번과 이름을 보존한다.
6. 결재선은 읽기 전용으로 유지하고 문서 전체 가로 넘침 없이 좁은 화면에서는 결재 카드 흐름 안에서만 가로 스크롤한다.

### 조회수 계약

1. 조회 기준은 `(tenant_id, electronic_approval_id, login_id)`로 한다.
2. 인증 사용자가 접근 권한이 확인된 상세 문서를 처음 조회할 때만 이력을 저장하고 조회수를 1 증가시킨다.
3. 같은 사용자의 반복 상세 조회, 새로고침, 재시도, 동시 요청은 중복 증가하지 않는다.
4. 목록 조회는 조회수를 증가시키지 않는다.
5. 기존 상세 API 경로와 응답 envelope를 유지하고 `item.viewCount`에 증가 처리 이후의 값을 반환한다.
6. 조회 이력 insert 충돌 여부와 무관하게 마지막에 상세 행을 다시 읽어 동시 요청에서도 최신 카운트를 반환한다.
7. 존재하지 않는 문서, 삭제 문서, 접근 불가 문서는 이력 또는 카운트를 변경하지 않는다.

## DB 변경 및 이력

- `tb_electronic_approval_main.view_count`: `integer NOT NULL DEFAULT 0`, 음수 금지.
- 신규 `tb_electronic_approval_view_history`: tenant, 전자결재 문서, 로그인 계정, 최초 조회 일시 보관.
- unique 제약 `(tenant_id, electronic_approval_id, login_id)`.
- 문서 삭제 시 조회 이력도 정리되도록 tenant·문서 복합 FK를 구성한다.
- 동일 날짜·작업번호 기준으로 다음 파일을 `docs/database/20261014/`와 `backend/DATABASE/20261014/`에 동일하게 추가한다.
  - SQL migration
  - 변경 이력 Markdown
  - rollback SQL
- `docs/database/db-schema.md`의 전자결재 본문 및 새 이력 테이블 설명을 갱신한다.
- 조회 전용 MCP는 확인 근거이며 DDL 실행에 사용하지 않는다.

## 완료 기준

- 이름 아래 작성자/기안일/실제 조회수가 표시되고 기존 작성자 행의 형태가 유지된다.
- 승인 카드 화살표, 중앙 순번+이름, 긴 이름 말줄임, 합의/참조 별도 번호 행이 참조 이미지 기준으로 동작한다.
- 최초/반복/다른 사용자/권한 없음 조회의 서비스 동작이 테스트된다.
- 중복 방지 unique key, insert 충돌 처리, 원자 카운터 증가, detail 응답 매핑이 mapper 테스트로 검증된다.
- 프론트 집중 테스트 및 build, 백엔드 집중 테스트가 통과한다.
- 375px, 768px, 1280px 브라우저 확인과 개인정보를 포함하지 않는 캡처가 결과 문서에 남는다.
- 날짜별 migration·변경 이력·rollback이 두 스키마 폴더에 일치하게 저장되고 `db-schema.md`가 최신화된다.
