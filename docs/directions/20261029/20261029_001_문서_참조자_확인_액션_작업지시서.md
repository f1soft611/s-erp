# 문서 참조자 확인 액션 작업지시서

## 목적

기안서 및 업무연락의 참조자가 문서를 명시적으로 확인할 수 있도록 하고, 미확인 문서를 종합현황과 문서작성 결재요약에서 결재 업무와 구분해 안내한다. 확인 액션은 기존 결재 처리와 동일한 공통 SYSTEM 타임라인에 기록한다.

## 승인 요구사항

- 기안서는 상신 후, 업무연락은 발송 후 참조자에게만 확인 액션을 제공한다. 임시저장 문서는 확인 대상이 아니다.
- 확인은 참조자별 1회이며, 결재 상태·결재선 진행·결재 대기 수에는 영향을 주지 않는다.
- 확인 상태와 확인자/시각을 기록하고, 같은 트랜잭션에서 `REFERENCE_CONFIRMED` SYSTEM 이력을 남긴다. 이력은 기존 결재 액션과 같은 타임라인/표시 형식을 사용한다.
- 이미 확인한 참조자의 재요청은 이력 중복 없이 기존 완료 상태를 반환한다.
- 미확인 문서는 문서 상태가 완료/반려된 뒤에도 확인될 때까지 대기 대상으로 남는다.
- 종합현황에 별도 `내가 확인할 문서` 건수와 목록을 제공한다.
- 문서작성 우측 결재요약에 별도 `내가 확인할 문서` 건수를 추가하고, 선택하면 미확인 참조 문서만 조회한다.
- 확인 완료 후 종합현황 및 문서작성 대기 건수/목록을 갱신한다. 일반 문서 목록/상세 접근은 유지한다.
- 사용자/tenant 권한은 서버에서 검증한다. 클라이언트가 확인자 ID나 확인 시각을 지정하지 않는다.

## 구현 및 검증 절차

1. 승인된 설계, 본 작업지시서, 날짜별 계획 및 상세 사양을 확인한다.
2. 구현 전 `s-erp-postgresql-readonly` MCP로 테이블 목록과 결재 참여/시스템 이력 테이블 메타데이터 및 관련 제약을 확인한다. 행 데이터는 조회하지 않는다.
3. 현재 결재/참조 상태 제약과 migration 이력을 확인한다. 스키마 변경이 필요한 경우 날짜별 SQL, 변경 이력, 롤백을 `backend/DATABASE`와 `docs/database`에 동일하게 추가하고 `db-schema.md`를 갱신한다.
4. 확인 API/서비스/조회 쿼리 및 각 화면의 실패 테스트를 먼저 작성한다.
5. 확인 상태 변경과 SYSTEM 이력 추가를 원자적으로 구현하고 권한/멱등성을 검증한다.
6. 문서작성 결재요약 및 종합현황에 별도 미확인 목록/건수를 연결한다.
7. 관련 백엔드 테스트, 프론트엔드 테스트 및 빌드를 수행한다.
8. 실제 브라우저에서 375px, 768px, 1280px 화면을 확인하고 결과 문서와 영문 경로의 스크린샷을 저장한다.

## 제외 범위

- 열람만으로 확인 처리, 이메일/푸시, 확인 취소/수정
- 결재/합의 상태 전이 변경 또는 업무연락 완료 상태 변경
- 기존 데이터 자동 확인 처리
- 별도 확인 테이블 도입(현행 참여자 행과 제약 검토로 처리 가능성이 확인되는 경우)

## 완료 조건

- 참조자 권한 확인, 임시저장 제외, 완료/반려 문서의 대기 유지, 확인 멱등성 및 시스템 이력 원자성이 서버 테스트로 검증된다.
- 미확인 참조 건수/목록이 문서작성 결재요약과 종합현황에서 일치하며 결재 수치와 분리된다.
- 확인 완료 후 두 화면의 미확인 영역에서 제거되고 일반 문서 조회 권한은 유지된다.
- 변경된 프론트/백엔드 테스트 및 빌드가 통과한다.
- DB MCP 확인 근거 또는 연결 실패와 대체 근거, 결과 문서 및 브라우저 스크린샷이 포함된다.
