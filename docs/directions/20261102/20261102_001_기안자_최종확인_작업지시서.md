## 목표

최종 승인 또는 반려 후 기안자가 문서를 최종 확인할 수 있도록 서버 생성 내부 `FINAL_CONFIRMATION` 참여 행과 별도 대기 목록/확인 이력을 구현한다. 문서 상태는 승인 시 `COMPLETED`, 반려 시 `REJECTED`로 즉시 확정하며 기안자 확인은 상태를 변경하지 않는다.

## 작업 범위

- 문서 최초 상신 및 보완요청 후 재상신 시 사용자 편집 결재선 뒤에 기안자 대상 `FINAL_CONFIRMATION` 행을 서버가 자동 생성한다. 요청 본문 또는 결재선 편집 UI에는 이 행을 요구하거나 표시하지 않는다.
- 해당 행은 일반 결재 단계 전이에서 제외한다. 최종 승인 또는 반려 시에만 `PENDING`으로 활성화하고 `pending_at`을 기록한다. 보완요청 시 확인 대상을 활성화하지 않는다.
- 기안자만 확인할 수 있는 확인 처리 API와 멱등 처리를 제공한다. 확인 시 행을 `CONFIRMED`로 바꾸고 SYSTEM 이벤트 `FINAL_CONFIRMATION_CONFIRMED`를 `기안자가 최종 확인을 완료했습니다.` 내용으로 추가한다.
- 기존 최종 승인 시 추가로 생성하던 `COMPLETED` SYSTEM 이력은 신규 결재처리에서 생성하지 않는다. 최종 승인자의 `APPROVED` 처리, 문서 상태 변경 및 과거 `COMPLETED` 이력은 유지한다.
- 문서작성 및 종합현황에 기존 참조확인과 구별되는 `내가 최종 확인할 문서` 건수/목록을 제공하고 상세에서 전용 확인 액션을 제공한다.
- 기존 참조확인, 일반 승인·반려·보완, 재상신, 상세 이력 표시 동작을 회귀 검증한다.
- DB 제약, 날짜별 변경/롤백 스크립트 양쪽 사본 및 `docs/database/db-schema.md`를 관리한다.

## 상태 및 권한 조건

| 처리 결과 | 문서 상태 | 최종확인 행 |
|---|---|---|
| 최종 승인 완료 | `COMPLETED` | `PENDING` |
| 반려 | `REJECTED` | `PENDING` |
| 보완요청 | `REVISION_REQUESTED` | `WAITING` 유지 |
| 기안자 확인 | 기존 상태 유지 | `CONFIRMED` |

- 확인 대상은 기안자 1명이며 현재 인증 사용자 및 tenant로 식별한다. 요청 본문에서 사용자 ID 또는 확인 시각을 받지 않는다.
- 앱 내 전용 대기 목록을 이번에 구현한다. 이메일/푸시 등 외부 발송은 범위에서 제외한다.
- 일반 참조확인 대기 및 처리 건수와 최종확인 대기/처리 건수를 섞지 않는다.
- `FINAL_CONFIRMATION`은 일반 결재/합의 처리, 참조확인, 다음 결재 단계 탐색에 포함하지 않는다.

## 필수 순서

1. 이 작업지시서 및 승인 설계를 바탕으로 날짜별 구현 계획서를 작성한다.
2. 계획서에 따라 `docs/spec/20261102`에 API, 저장상태, UI, DB, 테스트 계약을 상세화한다.
3. 실제 구현 직전에 `s-erp-postgresql-readonly` MCP로 결재선/공통 이력 테이블의 현재 컬럼과 CHECK 제약을 확인한다. MCP 확인에 실패하면 미확인 사실과 Mapper/날짜별 스키마 이력 대체 근거를 기록하고 현재 DB 계약을 확인한 것처럼 표현하지 않는다.
4. RED-GREEN-REFACTOR 흐름으로 백엔드와 프런트엔드 테스트를 먼저 추가하고 구현한다.
5. 실제 최종승인/반려/확인과 관련 목록을 검증하고 결과 문서 및 필요한 스크린샷을 `docs/result/20261102/drafter-final-confirmation/`에 기록한다.
6. DB 변경이 필요한 경우 동일한 변경 번호의 SQL/변경이력/롤백 파일을 `backend/DATABASE/20261102`와 `docs/database/20261102`에 만들고 전체 스키마 문서를 갱신한다.

## 완료 조건

- 승인/반려 직후 문서의 최종 상태가 각각 `COMPLETED`/`REJECTED`이며 기안자 확인 대기 항목이 생성된다.
- 신규 최종승인 처리에서 추가 `COMPLETED` SYSTEM 이벤트는 만들어지지 않고, 승인자 `APPROVED` 이벤트 및 반려 `REJECTED` 이벤트가 유지된다.
- 확인 성공은 문서 상태를 바꾸지 않고 전용 참여 행과 확인 이벤트를 한 트랜잭션에서 기록한다. 실패 시 부분 반영이 없다.
- 최종확인 행은 편집 결재선 및 일반 결재선 표시에서 숨고, 일반 참조확인/결재 처리와 구분된다.
- 문서작성/종합현황의 전용 대기 목록 및 건수가 문서 상세 확인 성공 후 갱신된다.
- 관련 백엔드 테스트, 프런트엔드 테스트/build 및 실제 브라우저 375px/768px/1280px 확인을 수행한다.
- 승인 설계, 상세사양, 코드, migration, 결과 문서가 서로 일치한다.
