# 20261022_008 거래처 관리 페이지 작업지시서

## 작업 목적

`/co/master/customers` 메뉴에 `tb_customer_info`를 사용하는 거래처 관리 화면을 추가한다. 화면은 기안양식관리 페이지의 기본 검색/상세검색 흐름과 F1-Grid 행 폼 패턴을 따른다.

## 승인된 범위

### 2026-10-22 백엔드 패턴 정정

- 사용자 확인에 따라 공통코드의 Controller → Service/Impl → DAO → Mapper 구조, 검색 조건의 Map 변환 및 서비스의 404 예외 처리 패턴을 따른다.
- 공통코드처럼 별도 BatchService의 `save-batch`에서 신규/수정 변경 집합을 한 트랜잭션으로 저장한다. 프론트 저장 버튼도 단일 배치 요청을 사용한다.
- 채번은 공통코드의 현재 `IdSequenceService`로 변경하지 않고 기존 승인대로 eGov `IDS`를 유지한다.
- 기존 거래처 감사 사용자 기록과 물리 삭제 금지 정책은 유지한다.

- 대상 화면: 기준정보 > 거래처 관리, `/co/master/customers`
- 프론트엔드: 검색, 상세검색, F1-Grid 목록, 등록, 수정, 사용여부 변경
- 백엔드: 인증된 테넌트 범위의 목록/검색/등록/수정 API
- 삭제: 물리 삭제 API를 추가하지 않는다. `use_at`의 `Y`/`N`으로 사용 상태를 관리한다.
- 저장 테이블: 기존 `public.tb_customer_info`; 테이블 컬럼과 기존 제약은 변경하지 않는다.
- 거래처 ID: 기존 `customer_id` 기본 시퀀스를 사용한다.
- 거래처 코드: 입력값이 있으면 그대로 저장하고 테넌트 내 중복을 거부한다. 비어 있으면 eGov ID Generator의 기존 `IDS` 관리 테이블에서 정확히 6자리 코드를 생성한다. 999999를 초과하면 등록을 거부하고 오류를 표시한다.
- 코드 채번: 신규 PostgreSQL sequence/table을 만들지 않는다. `EgovConfigAppIdGen`에 `tb_customer_info` 전용 eGov generator bean을 추가하고, 날짜별 SQL에서 기존 `ids` 카운터를 숫자형 1~6자리 거래처 코드 최댓값 기준으로 초기화한다. `docs/database`와 `backend/DATABASE`에 변경 이력 및 rollback 사본을 동일하게 보관한다. rollback 시 발급된 코드 재사용을 막기 위해 counter를 낮추거나 삭제하지 않는다.
- 권한: 조회는 메뉴 조회 권한을 사용한다. 등록/수정은 테넌트 관리자이며 해당 메뉴의 생성/수정 권한도 가진 경우에만 제공한다.

## DB 확인 근거

2026-10-22 지정 tenant PostgreSQL MCP에서 `list_tables`, `describe_table('public.tb_customer_info')`, `describe_table('public.ids')`, 제약 메타데이터 조회를 수행했다. 확인한 거래처 테이블은 거래처 ID, 테넌트 ID, 거래처 코드/명, 약칭, 대표자, 사업자/법인번호, 업태/종목, 우편번호/주소, 전화/팩스, 메모, 사용여부, 감사 컬럼을 가진다. `customer_id` 기본 시퀀스, 테넌트 FK, `use_at` Y/N 검사, `(tenant_id, customer_code)` 유니크 제약과 기존 eGov `ids`의 `(table_name)` PK/카운터 컬럼을 확인했다. tenant 업무 행과 ID 카운터 행은 조회하지 않았다.

## 검색 및 화면 요구사항

- 기본 검색 입력은 하나만 둔다. 거래처 코드, 거래처명, 약칭을 부분 검색하며 Enter 또는 조회 액션으로 적용한다.
- 상세검색은 `PageSearchArea`의 접이식 상세검색을 사용한다. F1-Grid 컬럼의 검색 메타데이터와 `toPageSearchFields()`로 생성한다.
- 상세검색 항목은 대표자명, 사업자번호, 법인등록번호, 업태, 종목, 사용여부다. 기본 검색어와 상세 조건을 같은 목록 조회에 전달한다.
- 초기 목록은 사용/미사용 거래처를 모두 포함한다. 사용여부는 상세검색으로 좁힌다.
- 페이지는 `PageHeader`, `PageSearchArea`, `PageMessageArea`, F1-Grid를 사용하고, breadcrumb와 페이지 권한은 대시보드에서 전달받는다.
- F1-Grid 첫 컬럼은 행 번호다. 목록에는 거래처 코드/명/약칭/대표자/사업자번호/업태/종목/전화/주소/사용여부를 표시한다.
- 등록/수정은 F1-Grid 행 폼을 사용한다. 거래처명은 필수다. `tenant_id`, `customer_id`, 등록/수정자 및 시각은 클라이언트가 입력하지 않는다.
- 사업자번호, 법인등록번호, 우편번호, 전화번호, 팩스번호는 공통 F1-Grid `inputFormat` 옵션으로 행 폼·인라인 입력·TSV 붙여넣기 시 포맷한다. 사업자번호는 `000-00-00000`, 법인등록번호는 `000000-0000000`, 전화·팩스는 국내 번호 규칙으로 자동 하이픈을 삽입하고 우편번호는 숫자만 허용한다. 사업자번호·법인등록번호 상세검색에도 같은 포맷을 적용한다. 입력 길이 검증 및 API/DB 계약 변경은 하지 않으며, 기존 값은 사용자가 편집할 때까지 보존한다.
- 로딩, 빈 목록, 입력 검증, 서버 오류, 저장 성공 상태를 기존 공통 컴포넌트와 알림 패턴으로 표시한다.
- 375px, 768px, 1280px에서 확인한다. 좁은 화면의 표 가로 스크롤은 그리드 내부에서 처리하고 페이지 자체의 불필요한 가로 스크롤을 만들지 않는다.

## 작업 절차

1. 본 작업지시서를 바탕으로 [계획서](../../plan/20261022/20261022_008_거래처_관리_페이지_계획서.md)를 작성한다.
2. 계획서에 따라 [상세 사양서](../../spec/20261022/20261022_008_거래처_관리_페이지_상세사양서.md)를 작성하고 API, 필드, 권한, 검색, 채번, 오류 계약을 확정한다.
3. 승인 설계와 사양서가 일치하는지 검토한 후에만 코드 변경을 시작한다.
4. 관련 테스트를 먼저 작성하고 실패를 확인한 뒤, 최소 구현으로 통과시킨다.
5. 백엔드 API와 MyBatis 매퍼, eGov ID Generator 설정 및 `ids` counter 이력, 프론트 서비스/상태/화면/라우트, F1-Grid 사용 문서를 단계별로 적용한다.
6. 변경된 DB 스크립트는 읽기 전용 MCP로 실행하지 않는다. 실행 가능한 데이터베이스에 적용되었다고 보고하지 않는다.
7. 결과 문서와 브라우저 스크린샷을 `docs/result/20261022/customer-management/` 아래에 기록한다.

## 완료 조건

- 사용자 추가 지시에 따라 모든 거래처 domain model의 클래스와 업무 필드에 공통코드와 같은 OpenAPI `@Schema` 정보를 제공한다. 검색·저장 요청·배치 변경 집합·응답 모델과 상속 필드까지 누락 없이 확인한다.
- 번호/연락처 입력은 공통 옵션으로 자동 포맷하며, 폼·인라인·붙여넣기·상세검색, caret 유지, 기존 값 보존을 프론트엔드 테스트로 확인한다.

- `/co/master/customers`에서 지정한 테넌트의 거래처 목록을 조회하고 기본/상세 검색을 함께 적용할 수 있다.
- 테넌트 관리자가 메뉴 권한에 따라 거래처를 등록/수정하고 사용여부를 바꿀 수 있다. 다른 테넌트 행은 조회/수정할 수 없다.
- 코드 미입력 등록은 eGov ID Generator가 생성한 6자리 코드를 사용하며, 테넌트 내 중복 및 채번 소진 오류가 화면에 명시된다.
- 프론트엔드 집중 테스트와 빌드, 백엔드 집중 테스트, 3개 뷰포트 브라우저 확인이 완료된다.
- eGov `ids` counter 초기화 SQL/변경 기록/롤백본과 `db-schema.md`가 갱신되고, `F1-GRID.md`에 해당 사용 흐름이 문서화된다.
- 결과 보고서와 375px/768px/1280px 스크린샷이 저장된다.
