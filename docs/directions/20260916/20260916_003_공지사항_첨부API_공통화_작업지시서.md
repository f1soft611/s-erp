# 20260916_003 공지사항 첨부 파일 API 공통화 작업지시서

## 작업 목적

공지사항 화면의 첨부 파일 업로드/다운로드/삭제 로직이 현재 `groupware/notice` 도메인에 강하게 결합되어 있어, 공지사항 외 다른 기능에서도 동일한 첨부 API를 재사용하기 어렵다.

이 작업은 첨부 파일 기능을 그룹웨어 전용 구현이 아니라 공통 첨부 모듈로 분리하여, 공지사항, 게시판, 자료실, 또는 향후 다른 피드형 화면에서 동일한 API 계약으로 재사용할 수 있도록 만든다.

핵심은 경로와 구현체를 공통화하되, 기존 공지사항 API 동작은 유지하는 것이다. 즉, 공지사항은 별도 로직을 유지하되 내부적으로 공통 첨부 서비스/컨트롤러/VO를 호출하도록 구조를 정리한다.

## 명명 원칙

- 공지사항 전용 이름은 공통 모듈에 사용하지 않는다.
- 첨부 기능은 `Attachment*` 또는 `BoardAttachment*` 계열의 범용 네이밍으로 분리한다.
- `groupware` 또는 `notice` 모듈에 묶이지 않는 공통 경로를 우선한다.
- 기존 공지사항 API는 기존 소비자 호환성을 유지한 채 내부적으로 공통 로직을 재사용하도록 구성한다.

## 수정 범위

1. 첨부 업로드 API를 공통화한다.
   - 공지사항 전용 경로(`/api/v1/groupware/boards/notice/...`) 외에, 범용 경로를 추가하거나 내부 공통 서비스로 추출한다.
   - 파일 업로드, 메타 저장, MinIO 저장 키 생성, 권한 체크를 공통 로직으로 분리한다.
   - `tenantId`, `ownerType`, `ownerId`, `fileMeta`, `uploadedBy` 와 같은 범용 값이 전달되도록 정리한다.

2. 첨부 삭제 API를 공통화한다.
   - 삭제 대상 파일 식별을 공지사항 전용 `boardFileId` 중심에서 범용 `attachmentId`/`fileId` 기반으로 확장 가능한 구조로 정리한다.
   - 기존 공지사항 DB/조회 로직은 유지하면서, 삭제 호출이 공통 서비스에서 처리되도록 추상화한다.

3. 첨부 다운로드 API를 공통화한다.
   - 파일의 저장 경로, 버킷, 오브젝트 키, MIME 타입을 공통 서비스에서 일관되게 관리한다.
   - 공지사항 호출뿐 아니라 다른 기능에서 동일한 다운로드 엔드포인트를 재사용 가능하게 만든다.

4. 공지사항 구현을 공통 로직에 연결한다.
   - 공지사항 API는 실제로는 공통 첨부 서비스에 위임하고, 필요한 전용 메서드만 남긴다.
   - 기존 `NoticeBoardServiceImpl`의 첨부 관련 코드 일부를 공통 서비스로 이전한다.
   - 기존 클라이언트 및 백엔드 응답 포맷은 가능하면 유지한다.

5. 기존 공지사항 기능 호환성을 유지한다.
   - 목록/상세/등록/수정/삭제 동작은 기존과 같아야 한다.
   - 첨부 업로드 응답의 필드명과 오류 메시지는 기존 호출부에 문제가 없도록 보존한다.
   - 공통화 과정에서 API 시그니처가 갑자기 바뀌지 않도록 점검한다.

6. 구현 범위를 분리한다.
   - 공통 첨부 모듈은 그룹웨어/공지사항 의존을 제거한다.
   - 기존 공지사항 소스는 공통 모듈을 활용하는 어댑터 역할만 맡는다.

## 제외 범위

- 신규 DB 테이블 생성
- 첨부 파일 관련 전체 데이터 모델 대대적 재설계
- 공지사항 목록/상세 기능 전면 리팩터링
- 다른 모듈의 비즈니스 로직 변경
- 불필요한 전역 설정/리듀서/캐시 구조 추가

## 완료 기준

- 첨부 파일 업로드/다운로드/삭제 로직이 공지사항 전용 의존성을 제거하고 범용 구조로 분리되어 있다.
- 공지사항 API는 동일한 동작을 유지하면서 공통 첨부 서비스/모듈을 사용한다.
- `groupware` 또는 `notice` 의존성이 강한 코드가 공통 계층으로 이동되었거나, 최소한 어댑터 역할로 정리되어 있다.
- 기존 첨부 동작이 정상적으로 유지된다.
- 관련 테스트와 빌드 검증이 통과한다.

## 검증 계획

- `cd backend`
- `mvn test`
- 필요한 경우 `mvn -q -DskipTests compile` 또는 컨트롤러 단위 검증을 수행한다.

## 문서 관리

- 구현 전, 계획서와 상세 사양서를 작성한다.
- 구현 후, 결과 문서와 필요한 로그를 `docs/result/YYYYMMDD/` 경로에 정리한다.
- 본 작업은 백엔드 구조 정리와 API 공통화에 집중하므로 문서와 코드가 동일 범위에서 동기화되어야 한다.
