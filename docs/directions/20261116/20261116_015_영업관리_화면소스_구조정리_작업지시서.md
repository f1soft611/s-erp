# 영업관리 화면 소스 구조 정리 작업지시서

## 요청

영업관리 메뉴의 업무 구분에 맞춰 프론트엔드 소스 디렉터리를 구성한다.

## 목표 구조

```text
frontend/src/pages/sales/
  order/
    create/
    status/
  delivery/
    plan/
      create/
      status/
      components/
      services/
      types/
    create/
    status/
    statement/
```

수주등록·현황은 `order` 아래에 유지한다. 출하계획의 기존 `delivery-plan` 폴더와 거래명세서의 기존 `statement` 폴더는 `delivery` 하위로 이동한다. 견적 등 이번 요청에 포함되지 않은 메뉴는 이동하지 않는다.

## 범위와 보존 항목

- 디렉터리 이동에 필요한 import 경로를 프런트엔드 소스, 테스트, 브라우저 테스트에서 함께 갱신한다.
- 메뉴 페이지 연결은 실제 이동된 위치를 import하도록 수정하며, 다른 미커밋 기능(견적관리)의 변경은 보존한다.
- URL, API 경로, page key, 메뉴명, 동작, 권한, 데이터 계약 및 화면을 변경하지 않는다.
- 백엔드와 DB는 수정하지 않는다.

## 완료 조건

1. 출하계획 페이지 파일이 `sales/delivery/plan` 아래에 있다.
2. 거래명세서 페이지 파일이 `sales/delivery/statement` 아래에 있다.
3. `DashboardContent`와 모든 기존 테스트/브라우저 테스트가 새 위치를 사용한다.
4. 이전 위치를 참조하는 활성 프런트 소스가 없다.
5. 관련 테스트, 전체 프런트 빌드 및 변경 영역 lint가 통과한다.
6. 결과 문서에 실제 변경 범위와 검증 결과를 기록한다.

## 추가 요청: 기능 내부 책임 분리

메뉴 디렉터리 이동뿐 아니라 기존 프론트엔드의 컴포넌트·서비스·타입·data 구조까지 맞춘다.
평면으로 배치된 거래명세서를 수주관리의 `create`·`status` 구조를 기준으로 정리한다.
등록/현황 페이지는 화면 조립을 맡고, 복합 상태는 `hooks`, UI는 `components`,
API 호출은 `services`, 타입은 `types`, 컬럼·검색조건·출력 계산은 `data`에 둔다.
등록/현황이 공유하는 출력 컴포넌트와 API·타입은 거래명세서 기능 루트에서 공유한다.
화면·권한·URL·API 계약을 바꾸거나 다른 미커밋 기능을 정리하지 않는다.
