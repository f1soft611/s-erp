# 출하관리 프론트·백엔드 공통 소스 구조 작업지시서

## 요청과 목표

출하를 뜻하는 상위 폴더 `shipment`를 만들고 프론트·백엔드 모두 그 안에
`delivery`, `deliveryplan`, `statement`를 같은 깊이로 배치한다.
이 구조가 이전 015 작업의 `sales/delivery/plan` 및 `sales/delivery/statement` 구조를 대체한다.

## 범위

- 프론트: `frontend/src/pages/sales/shipment/{delivery,deliveryplan,statement}`.
- 백엔드 운영 코드·테스트: `egovframework/let/sales/shipment/{delivery,deliveryplan,statement}`.
- MyBatis XML: `egovframework/mapper/let/sales/shipment/{delivery,deliveryplan,statement}`.
- 이동에 필요한 Java package/import, Mapper resultType, 테스트 리소스 경로, 프론트 import와 브라우저 동적 import를 갱신한다.
- 기능 내부 `create`, `status`, `components`, `hooks`, `services`, `types`, `data` 등 역할별 구조는 유지한다.
- 수주·견적 등 다른 기능은 이동하지 않는다. 수주의 출하계획 의존 import만 갱신한다.

## 보존 사항과 완료 조건

1. API 주소, 메뉴 경로/page key, 권한, Bean 이름, MyBatis namespace 및 SQL은 바꾸지 않는다.
2. 스키마나 데이터를 변경하지 않으므로 신규 마이그레이션은 만들지 않는다.
3. Mapper 이동 전에 읽기 전용 DB MCP로 관련 테이블 메타데이터를 확인한다.
4. 관련 프론트 테스트·빌드·lint, 백엔드 Controller/Service/Mapper 테스트와 Java 8 API 호환 컴파일을 확인한다.
5. 실제 브라우저 흐름과 결과 문서·스크린샷을 남긴다. 기존 서버·사용자 미커밋 작업은 보존한다.

## 추가 요청: 이후 에이전트용 지침

루트 `AGENTS.md`, `frontend/AGENTS.md`, `backend/AGENTS.md`에 공통 메뉴/업무 분류와
출하관리의 고정 디렉터리 구조를 기록한다.
프론트 책임별 폴더와 백엔드 계층별 패키지는 각 영역 지침에 명시하고,
패키지/Mapper/테스트 참조를 함께 변경하되 소스 위치 때문에 API 주소를 변경하지 않도록 한다.
