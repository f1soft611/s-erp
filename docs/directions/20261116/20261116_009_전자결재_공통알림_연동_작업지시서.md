# 전자결재 공통 알림 연동 작업지시서

## 목적

전자결재의 결재 요청, 단계 전환, 최종 처리 및 업무연락을 기존 공통 알림함과 웹 푸시 경로에 연결한다. 알림 수신자는 서버가 현재 결재선에서 결정하고, 알림 선택 시 해당 문서로 이동한다.

## 현재 상태

- 공통 헤더 알림과 알림함은 `APPROVAL_COMMENT_MENTION`, `DIRECT_MESSAGE_RECEIVED`를 지원한다.
- 웹 푸시는 공통 알림 저장 후 동일 알림을 추가 전달하는 선택 채널이다.
- 전자결재 문서 멘션은 공통 알림에 연결되어 있으나 결재 상태 전이는 아직 연결되지 않았다.
- 이메일은 현재 프로필의 이메일 주소와 SMTP 설정, Spring Mail 의존성이 있으나 실제 발송 서비스는 확인되지 않았다.

## 범위

### 포함

- 결재 상신/재상신 시 현재 처리 대기 중인 결재자에게 알림을 생성한다.
- 한 결재 단계가 끝나 다음 단계가 활성화되면 새 결재자에게 알림을 생성한다.
- 승인 완료, 반려, 보완요청 시 기안자에게 결과를 알린다. 기안자 최종확인이 대기 상태가 되면 기안자에게 확인 요청을 알린다.
- 업무연락 전송 시 지정된 참조자에게 알림을 생성한다.
- 결재 시스템 이력 ID를 알림 발생원 ID로 사용하고, 알림의 이동 대상은 전자결재 문서로 한다.
- 공통 알림함의 유형 검증/표시/필터와 PostgreSQL 제약을 확장하고, 날짜별 변경 SQL·롤백·이력을 관리한다.
- 메일 발송 가능성과 후속 발송 조건을 검토 결과 문서에 기록한다. 이번 구현에서는 이메일을 발송하지 않는다.

### 제외

- 모든 결재 단계의 개별 승인 행위마다 기안자에게 중간 알림 발송
- 참조자의 열람 여부를 알림 상태와 동기화
- 이메일 발송, 이메일 설정 UI, 이메일 outbox 또는 SMTP 운영 변경
- 알림 저장 실패를 이메일 발송으로 대체
- 일반 저장/수정 성공 토스트를 공통 알림함에 복제
- 수주·출하·재고 등 전자결재 외 업무 이벤트의 공통 알림 연동

## 수신자 및 발행 정책

- 상신/재상신: 상신 후 `PENDING` 상태이며 `APPROVAL`/`AGREEMENT` 결재선의 현재 대기자에게 보낸다.
- 단계 전환: 승인 완료로 다음 단계가 활성화된 경우 새로 `PENDING`이 된 결재자에게만 보낸다. 현재 단계에 대기자가 남아 있으면 추가 발송하지 않는다.
- 최종 승인: 일반 결재 문서는 기안자에게 보낸다. 기안자 최종확인이 필요한 문서는 확인 요청으로 알린다.
- 반려/보완요청: 기안자에게 결과를 보낸다.
- 업무연락: 문서에 지정된 `REFERENCE` 참여자에게 보낸다.
- 행위자가 실제 수신 대상에 포함되는 경우에는 자기 자신에게 발송하지 않는다.
- 수신자와 테넌트는 저장된 결재선 및 활성 사용자 계약을 이용해 서버에서 검증한다. 요청 본문에서 수신자를 받지 않는다.
- 이벤트마다 새 시스템 이력 ID를 발생원 ID로 사용해 동일 문서의 재상신/반복 처리도 별도 알림으로 식별한다. 알림과 이력 생성은 기존 업무 트랜잭션에 포함한다.

## 이메일 후속 조치 검토

- 이메일은 중요한 결재 이벤트에 한해 푸시가 최종 실패했거나 등록된 푸시 기기가 없는 경우의 대체 채널로 검토한다.
- 수신 주소는 실제 알림 수신자 본인의 유효한 이메일 주소이며, 발신 주소는 시스템 발신 주소다. 결재를 수행한 사람을 메일 발신자로 가장하지 않는다.
- 미읽음 상태만으로 미수신을 판단하지 않는다. 알림 저장 실패는 업무 트랜잭션 실패로 처리하고 이메일로 우회하지 않는다.
- 이메일을 구현할 때는 명시적 수신 동의, 이메일 검증, 비동기 outbox/재시도, 중복 억제 및 운영 실패 추적을 별도 사양으로 확정한다. 메일 전송 실패는 업무 트랜잭션을 되돌리지 않는다.
- 현재 소스에는 Spring Mail 의존성과 SMTP 설정이 있으나 실제 발송 서비스는 확인되지 않았다. 설정의 기본 자격정보는 운영 전 제거하고 secret 관리로 이전해야 한다.

## DB 확인 근거 및 제한

- 기본 PostgreSQL MCP의 `list_tables`와 `describe_table`로 `tb_notification`, `tb_electronic_approval_main`, `tb_electronic_approval_line_info`의 테이블 및 컬럼을 확인했다.
- `tb_notification` CHECK 제약을 확인하려는 제한 메타데이터 조회는 실패했다. 따라서 라이브 제약 확인은 완료되지 않았다.
- 저장소의 `docs/database/20261030/20261030_005_create_notification_message_schema.sql`에는 기존 두 이벤트/발생원 조합만 허용하는 `chk_notification_event_source`가 있다. 현재 MCP 조회에서 컬럼 구조는 DDL과 일치했으나 CHECK 제약의 실제 현재 값은 미확인이다.
- 이 DDL을 대체 근거로 변경 이력 초안을 작성하되, 실제 DB에는 SQL을 적용하지 않는다. 미확인 사실을 결과 문서에도 기록한다.

## 절차 및 완료 기준

1. 이 작업지시서에 맞춘 날짜별 계획서와 상세사양서를 확인한다.
2. 백엔드 테스트에서 이벤트/발생원 검증, 수신자 결정, 반복 재상신 알림, 잘못된 테넌트 및 자기 알림 제외를 검증한다.
3. `tb_notification` 이벤트/발생원 CHECK 제약을 확장하는 migration, 변경 이력, rollback을 `docs/database/20261116` 및 `backend/DATABASE/20261116`에 동일하게 작성하고 `docs/database/db-schema.md`를 갱신한다.
4. 결재 상태 전이와 시스템 이력 ID를 기존 공통 알림 서비스에 연결하고 공통 푸시 전달을 재사용한다.
5. 프런트엔드 알림 유형 검증, 이동 경로, 알림함 표시/필터를 확장한다.
6. 관련 백엔드/프런트엔드 테스트와 빌드를 수행한다. 실제 DB에는 migration을 실행하지 않는다.
7. 알림함 및 결재 흐름을 실제 브라우저에서 확인하고 `docs/result/20261116/approval-workflow-notifications/`에 결과와 스크린샷을 보관한다.

## 완료 조건

- 상신/재상신, 단계 활성화, 최종 처리, 보완요청, 업무연락에서 정의된 수신자에게만 공통 알림이 생성된다.
- 각 결재 알림이 전자결재 문서 상세로 이동하고 공통 알림 읽음/보관/필터 및 실시간 갱신이 유지된다.
- 알림 이력 저장과 발행은 기존 트랜잭션을 따르며 결재 상태 변경 실패 시 알림이 남지 않는다.
- 공통 푸시는 동일한 알림 행에서만 enqueue되고, 푸시 실패가 인앱 알림 저장이나 결재 처리에 영향을 주지 않는다.
- DB migration/rollback/이력/누적 스키마 문서, 테스트, 결과 문서 및 브라우저 스크린샷을 작성한다.
- 이메일 발송은 구현하지 않으며, 수신자/발신자/실패 조건 및 후속 요구사항을 결과 문서에 분리해 기록한다.
