# 거래명세서 헤더 합계 소수점 계약 적용 작업 결과

## 원인과 해결

- 원인: 명세서 생성 SQL이 헤더 `total_amt`를 `SUM(d.total_amt)` 서브쿼리로 저장해, 출하 헤더 합계에 적용되는 `deliveryTotal` 규칙(정책 + 컬럼 예외)이 적용되지 않았다. 예외가 없으면 값이 같고, `deliveryTotal`이 상세 `totalAmt`보다 적은 자릿수이거나 다른 반올림일 때만 어긋난다.
- 해결: `lockDeliveryDetails`가 `totalAmt`를 반환하고, `SalesStatementServiceImpl.createGrouped`가 거래처 그룹별로 합산한 뒤 `SalesDecimalPolicy.amount("deliveryTotal", …)`를 적용해 `insertHeader`에 `totalAmt`로 넘긴다. 출하 서비스의 `sumTotals`와 같은 규칙이다.
- 생성자에 `SystemPolicyService`를 추가했다. 정책 조회·계약 오류는 예외로 전파되어 트랜잭션이 롤백된다.
- 상세 행은 출하 상세 값을 그대로 복사하는 기존 동작을 유지한다.

## DB

- DB MCP `describe_table`로 `tb_sales_statement_hd.total_amt`, `tb_sales_delivery_dt.total_amt`가 `numeric`임을 확인했다. 스키마 변경과 DB 스크립트는 없다.

## 검증 결과

- 신규 서비스 테스트 2건: 정책 규칙(`currency` 1자리 DOWN)으로 `1.29 + 1.29`가 `2.5`로 저장 파라미터에 전달됨, 정책 조회 실패 시 헤더를 저장하지 않음.
- 매퍼 테스트: 헤더가 SQL 합산을 쓰지 않고 `totalAmt`를 바인딩하며 잠금 조회가 `d.total_amt`를 반환함을 확인하도록 갱신.
- 백엔드 전체 테스트 1642건 통과(실패 0, 건너뜀 9).

## 확인하지 못한 것

- 변경한 SQL(`insertHeader`의 `totalAmt` 바인딩, `lockDeliveryDetails`의 `d.total_amt`)을 실제 PostgreSQL에서 실행하지는 않았다. 매퍼 XML 파싱·바인딩 테스트와 모의 DAO 서비스 테스트까지 확인했다. 격리 테스트 DB 통합 테스트를 실행하려면 `SALES_DECIMAL_TEST_URL`과 `SALES_DECIMAL_TEST_PASSWORD`가 필요하다.
- `deliveryTotal` 예외를 넣은 상태의 실제 명세서 발행은 확인하지 않았다(현재 계약에 예외 없음).

## 커밋 제목·내용 (복사용)

제목: `fix(sales): 거래명세서 헤더 합계를 출하합계 소수점 규칙으로 계산`

내용: `명세서 헤더 합계를 SQL 합산 대신 서비스에서 deliveryTotal 규칙으로 계산해 저장하고, 매퍼와 서비스 테스트를 갱신한다.`
