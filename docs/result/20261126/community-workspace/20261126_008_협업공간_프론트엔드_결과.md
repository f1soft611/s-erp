## 구현 내용

- 그룹웨어 > 커뮤니티 > 협업공간 화면(`frontend/src/pages/groupware/community/workspace/`): 방 목록, 칸반/피드 보기 전환, 글 작성, 댓글·답글, 카드 상세, 방 설정(이름·기본 보기·컬럼·권한 그룹).
- 칸반: 드래그 이동과 카드별 "이동" 메뉴(키보드·모바일), 컬럼 숨김·접기·순서 변경(사용자별 저장), "내가 쓴 글"·검색 필터.
- 권한: 방별 권한 그룹(읽기/저장/방 설정, 누적). 읽기 전용 사용자는 새 글, 드래그, 이동 메뉴, 방 설정이 보이지 않는다.
- 서비스 계층(`services/workspace.service.ts`) 뒤에 localStorage 가짜 저장소를 두었다. 백엔드가 생기면 이 파일만 API 호출로 교체한다.
- 연결: `dashboardPages.ts`(lazy 등록), `DashboardContent.tsx`(`groupware` + `workspace` 분기), `dashboardData.ts`(페이지 콘텐츠).
- 메뉴 등록 seed: `backend/DATABASE/20261126/20261126_001_seed_workspace_menu.sql`(+ rollback, 변경 이력, `docs/database` 사본). 실제 DB에는 적용하지 않았다.

### 전체 테스트 스위트에 대한 기록

- `npx vitest run` 전체를 한 번에 돌렸을 때 39개 파일이 실패했고 대부분(111/127)은 5초 제한 시간 초과였다. 같은 시간에 Playwright·타입 검사 등을 함께 돌린 부하의 영향이 컸다.
- 실패 파일만 워커 2개로 다시 돌리니 `workspace-screen` 1개(제 테스트의 타이밍 문제, 수정함)와 `purchase-request-confirm` 1개만 남았다. `purchase-request-confirm`은 협업공간 수정 3개 파일을 되돌린 기준선에서도, 수정 상태에서도 단독 실행하면 통과한다(11/11, 수정 상태 2회 반복). 앞선 실패는 동시 실행 부하로 판단한다.
- 전체 스위트를 부하 없이 한 번에 끝까지 통과시킨 실행은 이 작업에서 확보하지 못했다. 이 점은 미확인 사실이다.

### 재현·원인·회귀 기록 (작업 중 발견한 결함)

- 글 목록 정렬 오류: 샘플 날짜(시간대 없음)와 새 글의 `toISOString`(UTC)을 문자열로 비교해 순서가 어긋났다. `Date.parse` 비교로 고쳤고 `workspace-service` 테스트가 회귀를 막는다.
- 타입 오류: MUI 9의 `Stack`, `Typography`는 `alignItems`·`flexWrap`·`fontWeight` 시스템 props를 직접 받지 않는다. 모두 `sx`로 옮겼다(vitest는 타입을 검사하지 않아 `tsc -b`로 확인).
- UX: 사용자 전환 선택기가 앱 테마의 `fullWidth` 기본값 때문에 화면 폭 전체로 늘어났다(`fullWidth={false}`, 고정 폭). 모바일에서 방 목록이 세로로 길어 칸반을 밀어내서 가로 스크롤 목록으로 바꿨다. "내가 쓴 글" 라벨 글자 크기를 다른 컨트롤과 맞췄다.

## DB 관련 확인 (메뉴 seed)

- 읽기 전용 MCP `s-erp-postgresql-readonly`의 `describe_table`로 `tb_menu`, `tb_menu_permission`, `tb_role_menu_permission` 구조를 확인했고, `query_readonly`(구조성 컬럼만, 테넌트 ID·사용자 데이터 제외)로 그룹웨어 모듈(`/groupware`)의 메뉴 코드·URL·정렬을 확인했다(`GW_INFO_CENTER` 아래 공지 11, 게시판 22, 자료실 33).
- 새 메뉴는 `GW_WORKSPACE`(`/groupware/community/workspace`, 정렬 44). 페이지 키는 URL의 마지막 구간 `workspace`이며 프론트 분기와 일치한다.
- 역할별 권한(`tb_role_menu_permission`)은 seed에 넣지 않았다. 메뉴 등록 후 관리자 화면에서 부여해야 사이드바에 나타난다(기존 공정관리 seed와 같은 방식).
- 적용 상태: 이 작업에서는 DB에 적용하지 않았다(읽기 전용 MCP만 사용). 최종 검토 중 읽기 전용 조회로 `GW_WORKSPACE` 행이 이미 존재함을 확인했다(`use_at = 'Y'`, 생성 2026-11-26 05:09 UTC, 메뉴 권한 4행, 역할 권한 3행). 적용 주체와 사용한 스크립트는 확인하지 못했다. 같은 seed를 다시 실행해도 `ON CONFLICT DO NOTHING`이라 중복되지 않는다. 다른 테넌트에 적용하려면 `v_tenant_id`를 지정해야 한다(미지정 시 예외).

## 최종 검토와 수정

별도 검토 에이전트가 전체 변경분을 읽고 중요 결함 7건, 경미한 결함 5건을 보고했다. 중요 결함은 각각 실패하는 테스트를 먼저 만들고 수정했다(수정 후 협업공간 테스트 7개 파일 71개 통과, `tsc -b` 오류 없음, 브라우저 21/21).

| 결함 | 수정 | 회귀 테스트 |
|---|---|---|
| 권한 그룹 구성원을 비우거나 본인 권한을 제거해 아무도 관리할 수 없는 방이 만들어짐 | `saveRoom`이 구성원 있는 방 설정 그룹과 본인의 방 설정 권한 유지를 요구 | `workspace-service` 3건 |
| 컬럼 없이 쓴 글이 방에 컬럼이 생기면 칸반에서 사라짐 | 첫 컬럼이 생길 때 컬럼 없는 글을 첫 컬럼으로 이동 | `workspace-service` 1건 |
| 저장소 쓰기 실패 시 성공 알림 직후 변경이 사라짐 | 쓰기 실패 후에는 메모리 상태를 기준으로 동작 | `workspace-service` 1건 |
| 칸반 카드를 키보드로 열 수 없음 | 제목을 버튼(span 기반)으로 변경, Enter/Space로 열기. 드래그가 막히지 않음을 브라우저에서 재확인 | `workspace-page` 1건 |
| 메뉴 권한이 쓰기·방 설정의 바깥 관문으로 적용되지 않음 | 쓰기는 메뉴 `create` 또는 `update`, 방 설정은 `update` 필요 | `workspace-screen` 1건 |
| 답글이 계속 깊어져 모바일에서 본문이 좁아짐 | 답글은 최상위 댓글에만 허용(공지 댓글과 같은 2단계) | `workspace-page` 1건 |
| 방·사용자 전환 중 끝난 요청이 이전 방·사용자의 목록을 덮어씀 | 변경 후 재조회는 항상 최신 방·사용자 기준 | `workspace-hooks` 2건 |

수정 중 정한 사항(원장 Ruling): 메뉴 `create`·`update` 둘 중 하나가 있으면 쓰기, `update`가 있어야 방 설정으로 해석했다. 사양에는 메뉴 권한 항목별 매핑이 없어 정한 값이며, 틀렸다면 `WorkspacePage.tsx`의 `menuCanWrite`·`menuCanAdmin` 두 줄만 바꾸면 된다.

### 미룬 경미한 결함 (수정하지 않음)

- 다른 곳에서 끌어온 텍스트(`text/plain`)를 컬럼에 놓으면 "글을 찾을 수 없습니다" 오류가 뜬다(전용 MIME 타입 사용 권장).
- 드래그 중 하위 요소 위를 지날 때 컬럼 강조가 깜박일 수 있다.
- 저장된 데이터가 옛 형태이면(방에 `groups` 없음 등) 화면이 오류에서 복구되지 않는다(`isStore`의 검증이 얕다).
- 컬럼 이름·그룹 이름을 비워 저장할 수 있다.
- 다른 댓글의 "답글"을 누르면 쓰던 답글 초안이 묻지 않고 사라진다.

## 한계와 미확인 사항

- 실제 메뉴 항목으로 사이드바에서 진입하는 흐름은 확인하지 못했다. 최종 검토 중 `GW_WORKSPACE` 메뉴 행이 DB에 이미 있음을 알게 되었지만(역할 권한 3행 포함), 로그인이 필요해 그 경로로는 확인하지 않았다. 브라우저 검증은 앱의 테마·알림 프로바이더를 쓰는 임시 하네스(검증 후 삭제)로 협업공간 화면을 직접 렌더링해 수행했다. 메뉴로 진입해 권한별 노출을 확인하는 단계가 남아 있다.
- 공지·자료실과 나란히 비교한 화면 검증은 수행하지 못했다. 같은 이유로 로그인 화면 흐름을 쓰지 않았고, `PageHeader`·본문 여백 규칙(`px: xs 1/sm 2`, `pt 1`, `pb 2`)은 공통 컴포넌트와 프로젝트 규칙 기준으로 맞췄다.
- "사용자 전환(개발용)"은 백엔드 연동 전 확인용이며 연동 시 로그인 사용자로 교체하고 제거해야 한다.
- 첨부는 파일명·크기·형식만 저장하며 내려받기를 지원하지 않는다.
- 구성원은 개별 사용자만 지원한다(부서 단위는 백엔드 사양 단계).
