# 대시보드 업무화면 청크 분할 결과

- 작업지시서: [작업지시서](../../../directions/20261126/20261126_002_대시보드_업무화면_청크분할_작업지시서.md)
- 계획서·사양서: [계획서](../../../plan/20261126/20261126_002_대시보드_업무화면_청크분할_계획서.md), [상세사양서](../../../spec/20261126/20261126_002_대시보드_업무화면_청크분할_상세사양서.md)
- 작업 위치: 같은 브랜치(`socra710`)를 다른 세션이 동시에 사용하고 있어 별도 worktree(`.worktrees/chunk-dashboard-lazy`, 브랜치 `chunk-dashboard-lazy`, 기준 `6d918e07`)에서 작업했다.

## 결론

- `npm run build`의 1,000 kB 초과 청크 경고가 사라졌다. `chunkSizeWarningLimit`(1,000)은 바꾸지 않았다.
- `DashboardPage` 청크: **1,778,872 → 131,058 bytes**. 업무 화면 48개가 각각 별도 청크(예: 문서작성 25 kB, 수주등록 27 kB)로 분리됐고, 편집기(tiptap/prosemirror)는 편집기를 쓰는 화면만 불러오는 공유 청크(396 kB)로 자동 분리됐다.
- 메뉴 선택 조건, props, URL, API는 바꾸지 않았다.

## 원인

`DashboardContent.tsx`가 업무 화면 48개를 정적 import해 모든 화면과 편집기가 `DashboardPage` 청크 하나에 합쳐졌다. [2026-10-26 조치](../../20261026/frontend-large-chunk-code-splitting/20261026_009_frontend_large_chunk_code_splitting_결과.md) 때는 476 kB여서 업무 화면 분리를 제외했는데, 이후 화면이 늘어 한도를 넘었다.

| 검토한 방법 | 측정 결과 | 판단 |
|---|---|---|
| 설정만 변경(tiptap/prosemirror를 vendor 청크로 분리) | `DashboardPage` 1,330,130 bytes | 여전히 한도 초과, 미채택 |
| 경고 한도 상향 | 번들 크기 그대로 | 사용자 결정으로 미채택 |
| 업무 화면 lazy 로딩 | `DashboardPage` 131,058 bytes | **채택**(사용자 결정) |

## 변경 내용

| 파일 | 내용 |
|---|---|
| `frontend/src/pages/dashboard/components/dashboardPages.ts` (신규) | 업무 화면 48개 지연 로딩 등록부. 이미 로드된 화면은 바로 렌더링하고, 아직이면 `React.lazy`로 기다린다. 마운트 중에는 컴포넌트 타입을 유지해 다시 마운트되지 않는다. `preloadDashboardPages()` 제공 |
| `frontend/src/pages/dashboard/components/DashboardContent.tsx` | 정적 import 48개를 등록부 import로 교체. 본문을 `DashboardContentView`로 옮기고 `DashboardContent`는 `<Suspense fallback={null}>`로 감쌈. 분기 코드는 그대로 |
| 테스트 13개 파일 + 문서작성 공용 harness | 최상위에 `beforeAll(() => preloadDashboardPages(), 60_000)` 추가. 테스트 본문·단언은 그대로 |
| `frontend/tests/dashboard-pages-lazy.test.tsx` (신규) | 등록부 동작 3건: 첫 사용 시 대기 후 같은 props로 렌더링, 로드 후 재렌더링 시 다시 마운트되지 않음, preload 후 대기 없이 렌더링 |

- 지연 로딩 중 본문 영역은 비어 있고 사이드바·헤더는 그대로 보인다. 앱 진입 정책([20261026_009 스피너 제거](../../../directions/20261026/20261026_009_app_initial_loading_spinner_removal_작업지시서.md))과 같은 `fallback={null}`이다. 각 화면을 처음 열 때만 해당되고, 한 번 불러온 화면은 다시 기다리지 않는다.

### 테스트 보정 방식

처음 적용했을 때 기준선 대비 51건이 새로 실패했다. 모두 렌더링 직후 화면을 동기로 조회(`getBy*`)하다가 지연 로딩 fallback을 만난 경우다. 약 130곳의 조회를 비동기로 바꾸는 대신, 해당 파일에서 화면 모듈을 미리 불러와 변경 전과 같은 조건(모든 화면 로드 완료)으로 실행했다.

- 제한 시간 60초: 변경 전에는 이 로드가 시간 제한 없는 import 단계에서 일어났다. 기본 hook 제한(10초)은 병렬 실행 부하에서 넘을 수 있다.
- `push-login-navigation`, `theme-settings`는 대시보드를 mock으로 대체하는 파일이어서 preload를 넣지 않았다. `push-login-navigation`에 넣었을 때 불완전한 auth mock으로 실제 화면을 불러오다 실패했다.

## 실제 브라우저 확인

- 환경: 포트 4173을 메인 작업 트리의 개발 서버가 사용 중이어서, 사용자 승인(워크트리에서는 다른 포트 허용)에 따라 worktree 개발 서버를 `127.0.0.1:4175`(`--strictPort`)로 실행했다. 백엔드는 로컬 8080. 로그인은 개발 모드 로그인 화면에 표시되는 개발용 테스트 계정을 사용했다. 확인 후 4175 서버를 종료하고 포트 해제를 확인했다.
- Playwright(headless Chromium)로 로그인 → 수주등록 URL 진입 → 사이드바 `수주현황` 메뉴 클릭(클라이언트 라우팅)을 수행했다.

| 확인 | 결과 |
|---|---|
| 로그인 직후 불러온 업무 화면 모듈 | 첫 화면 `OverviewPage`만(업무 화면 48개 일괄 로드 없음) |
| 수주등록 화면 표시 | 표시됨 |
| 메뉴 전환 시 추가로 불러온 모듈 | `SalesOrderStatusPage` 1개, URL `/sales/order/status` |
| 수주현황 화면 표시(조회 결과 8건, 그리드) | 표시됨 |
| 콘솔 오류·페이지 오류 | 0건 |
| 375·768·1280px 가로 넘침(`scrollWidth`) | 없음(375/768/1280) |

- 스크린샷: [375px](./screenshots/sales-status-375px.png), [768px](./screenshots/sales-status-768px.png), [1280px](./screenshots/sales-status-1280px.png)

## 미확인 사항

- 배포 후 열려 있던 탭에서 구 청크 해시를 요청하면 화면 로드가 실패할 수 있다. 기존 라우트 lazy 로딩과 같은 조건이며 이번 범위에서 새로 다루지 않았다.
- 프론트 전체 테스트(약 270개 파일)는 실행하지 않았다. 대시보드를 import하지 않는 파일은 이번 변경의 영향을 받지 않는다.
