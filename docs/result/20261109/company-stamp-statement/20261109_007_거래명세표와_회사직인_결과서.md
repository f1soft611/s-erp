# 거래명세표와 회사 직인 작업 결과

## 변경 내용

- 사용자의 최종 요청에 따라 제공받은 PDF처럼 같은 명세서 두 부를 A4 한 장의 상하에 출력한다. 품목 수와 품명 길이에 따라 여러 장으로 나누고 각 부에 동일한 품목과 전체 합계를 표시한다.
- 회사정보 화면을 기본정보, 주소·연락처, 회사 직인으로 나눴다. PNG·JPEG 직인을 선택·미리보기·삭제하고 회사정보와 함께 저장한다.
- 회사정보 세로 스크롤을 전체 콘텐츠 오른쪽으로 옮기고 필드 간 세로 간격을 줄였다. 미리보기 용지는 가운데 정렬하고 좁은 화면에서는 내부 가로 스크롤을 제공한다.
- 회사정보 저장 성공 시 공통 성공 토스트를 표시한다. 저장 실패는 기존 오류 영역에 표시하며 성공 토스트는 표시하지 않는다.
- 명세서 발행 시 직인을 함께 저장한다. 저장된 직인이 있으면 이후 회사 직인을 바꿔도 해당 명세서의 직인은 유지된다. 저장된 직인이 없는 명세서는 같은 테넌트의 현재 회사 직인을 표시하므로 회사 직인을 변경하거나 삭제하면 출력도 바뀐다.
- `20261109_009` SQL·변경 이력·롤백을 두 스키마 폴더에 동일하게 작성했다. 이 작업에서 SQL을 DB에 적용하지 않았다.

## 검증과 제한

- 기본 읽기 전용 DB MCP의 `list_tables`와 `describe_table`로 `tb_tenant.stamp_image`와 `tb_sales_statement_hd.supplier_stamp_image`가 현재 존재함을 확인했다. 업무 데이터 행은 조회하지 않았다.
- 프론트 집중 테스트 12건과 빌드, 백엔드 집중 테스트 23건 및 회사정보·명세서 운영 Java 8개 파일의 `javac --release 8` 검증을 수행했다. 변경 영역 린트는 오류 없이 실행됐으며 상태 동기화 경고가 있다.
- 합성 회사·직인 데이터로 375·768·1280px에서 스크롤 위치, 필드 간격, 미리보기와 출력에 직인 두 개를 확인했다. 일반 품목 80개는 A4 7장, 긴 품목 4개와 긴 주소 조합은 A4 4장으로 출력되고 사본 영역과 제목·금액란이 겹치지 않음을 확인했다.
- 저장 성공·실패 회귀 테스트와 프론트 빌드·변경 파일 린트를 실행했다. 합성 API 응답으로 375·768·1280px에서 저장 성공 토스트가 표시되는 것을 확인했다.
- 실제 사용자 데이터의 직인 저장부터 기존 명세서 조회·출력까지의 전체 연동은 확인하지 못했다. DB 컬럼이 존재한다는 사실은 이 작업에서 SQL을 적용했다는 뜻이 아니다.
- 전체 프론트 린트에는 기존 `tests/common-code-management-page.test.tsx:53` 조건부 Hook 오류가 있다.
