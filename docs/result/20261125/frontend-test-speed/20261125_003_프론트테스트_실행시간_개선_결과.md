- 작업지시서: [작업지시서](../../../directions/20261125/20261125_003_프론트테스트_실행시간_개선_작업지시서.md)
- 계획서·사양서: [계획서](../../../plan/20261125/20261125_003_프론트테스트_실행시간_개선_계획서.md), [상세사양서](../../../spec/20261125/20261125_003_프론트테스트_실행시간_개선_상세사양서.md)

## 결론

- `document-write-page` 테스트(156건)를 공용 모듈 1개와 테스트 파일 6개로 나눴다. 이 테스트들의 실행 시간은 **211초(단일 파일 직렬) → 86초(6개 파일 병렬)**로 줄었다. 파일별 시간은 54~65초로 고르게 맞췄다.
- 다만 **로컬 전체 실행 시간은 이 분할만으로 크게 줄지 않는다.** 이 파일을 제외하고 전체를 돌려도 570초(포함 시 629초)였다. 전체 시간의 대부분은 파일마다 반복되는 고정 비용(jsdom 로드, import)과 PC의 다른 프로세스 부하다.
- 운영 소스, Vitest 설정, 다른 테스트 파일은 변경하지 않았다.

## 원인 분석

| 측정 | 결과 |
|---|---|
| 전체 실행 누적 시간(629초, 255파일) | 테스트 본문 3,314초 · 환경 생성 2,483초 · import 1,978초 · setup 442초 |
| 순수 로직 테스트 1개 파일 | 테스트 0.03초, 환경 생성 3.2~4.9초 |
| 환경 생성 CPU 프로파일 | 약 71%가 `jsdom` 모듈 로드(대부분 파일 stat/read) |
| 워커 1개로 4개 파일 실행 | `forks` 환경 생성 11.1초, `vmForks` 2.7초 |
| `document-write-page` 단일 테스트 프로파일 | React 개발 모드 렌더링 약 18%, `getByRole` 접근성 이름 계산·`getComputedStyle` 약 10% |

1. **긴 파일의 직렬 실행:** Vitest는 파일 단위로만 워커에 나눠 실행한다. 156건이 한 파일에 있어 한 워커에서 직렬로 돌았고 전체 실행 끝부분을 이 파일이 차지했다. → 이번 작업에서 해결.
2. **파일마다 jsdom을 새로 로드:** 기본 `forks` pool은 파일마다 새 환경을 만들며 jsdom 모듈(수백 개 파일)을 매번 다시 읽는다. 파일당 약 3초 × 270여 개 파일. → 미해결(아래 제안).
3. **PC 부하:** 측정 중 다른 에이전트·IDE·백엔드 프로세스가 CPU를 45~100% 사용했다. 같은 조건의 반복 측정이 불가능해 워커 수 비교 결과는 신뢰할 수 없었다(워커 8개 실행이 1,056초로 오히려 느림).

## 변경 내용

```text
frontend/tests/document-write-page.test.tsx              (삭제)
frontend/tests/document-write-page/
  documentWritePage.harness.tsx                          mock 객체·vi.mock·픽스처·헬퍼·전역 beforeEach/afterEach
  document-write-page.part1~6.test.tsx                   원본 최상위 테스트 블록을 순서대로 배분
```

- 테스트 본문(단언, mock 설정, 개별 timeout)은 원본 텍스트 그대로 옮겼다. 유일한 변경은 모듈 변수를 직접 대입하던 한 줄을 `setRestoreImagePreloader(...)` 호출로 바꾼 것이다. ES 모듈의 import 바인딩은 밖에서 대입할 수 없기 때문이다.
- `vi.hoisted` 결과는 직접 `export`할 수 없어(Vitest 제약) 파일 끝에서 따로 export했다.
- 분배는 테스트별 실측 시간 기준이다. 처음에 줄 수 기준으로 나눴을 때는 파일별 시간이 25~102초로 차이가 컸다.
- `describe('Document write page')` 이름을 유지해 전체 테스트 이름이 바뀌지 않는다.

## 검증

- 테스트 이름: `vitest list` 결과 156건이 분할 전 실행 결과의 이름 목록과 정확히 일치한다.
- 실행: 6개 파일 156건 중 155건이 통과했고, 1건(part4)은 5초 시간 초과였다. 해당 파일을 단독으로 다시 실행하자 20/20 통과했다. 줄 수 기준 분할 때도 6개 파일 156건이 모두 통과했다.
- lint: `oxlint tests/document-write-page/` 경고·오류 0건.
- 타입: tests 폴더는 tsconfig 검사 범위가 아니어서 임시 설정으로 검사했다. 원본 파일 43건과 분할 파일 43건의 오류 코드 구성이 같다. 모두 원본에 있던 기존 오류이고 새로 생긴 오류는 없다.

## 검토 후 채택하지 않은 방법

| 방법 | 결과 |
|---|---|
| `deps.optimizer.client` | import 11.0초 → 12.6~12.9초로 느려짐 |
| `threads`/`vmThreads` pool | 30파일 표본에서 이득 없음 |
| **`vmForks` pool** | 파일당 환경 비용은 크게 줄었다. 그러나 전체 실행 중 워커 메모리가 계속 늘어(워커당 0.4~0.9GB 이상, 15개 합계 약 10GB) **시스템 메모리 부족으로 실행이 강제 중단**됐다. 남은 고아 프로세스는 직접 종료했다. |
| 워커 수 조정 | 부하 변동으로 측정 결론을 낼 수 없음 |

## 후속 조치: 수주현황 테스트 실패 수정

- 증상: `tests/sales-order-status-page.test.tsx`의 상세 패널 테스트 8건이 `SO-20261027-0001 상세 보기` 버튼을 찾지 못해 약 1.2~1.4초 만에 실패했다.
- 원인: 8건이 공통 헬퍼 `openOrderDetailPanel`에서 `findByRole`의 기본 대기 시간 1초 안에 목록 첫 렌더링을 기다린다. 첫 렌더링까지 걸리는 시간을 직접 측정했다(파일 1개 실행, 8회씩).

  | 소스 | 버튼 표시까지(ms) |
  |---|---|
  | 현재(`b3b85899` + 작업 트리) | 1차 379~433, 2차 624~963 |
  | 영업 소수점 커밋 이전(`8b13af07`) | 1차 358~622, 2차 518~1036 |

  두 소스의 차이는 없고 PC 부하에 따라 1초 경계를 넘나든다. **회귀가 아니라 부하 의존 실패**이며, 앞서 회귀로 추정한 판단은 틀렸다.
- 수정: 헬퍼의 첫 대기에 `{ timeout: 5000 }`을 지정했다. 기존 `app-router-not-found.test.tsx`의 초기 화면 대기와 같은 방식이다. 조건이 충족되면 바로 진행하므로 통과 시간은 늘지 않는다. 단언은 바꾸지 않았다.
- 검증: 단독 실행 26/26 통과. 무거운 테스트 9개 파일과 동시에 실행한 부하 상태에서도 이 파일은 실패 없음(함께 실행한 다른 파일은 기존과 같은 유형의 시간 초과 14건 발생). `oxlint` 경고 0건.
- 커밋 제목·내용: `test: 수주현황 상세 테스트 초기 목록 대기 시간 보정` / `목록 첫 렌더링 대기를 5초로 지정해 병렬 실행 부하에서의 시간 초과 실패를 막는다.`
