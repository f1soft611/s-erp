# 영업 소수점 후속 검증 인수인계

## 상태

구현·부분 검증 상태이며 전체 배포 완료로 판단하지 않는다. 이 문서는 미검증 항목을 이어서 수행하기 위한 목록이다.

- 적용 범위: 모듈별 `number`(수량), `decimal`(단가), `currency`(금액) 정책과 프론트·서버 공통 컬럼 계약.
- 사용자 확인: 출하등록 저장, 재조회, 거래명세서를 확인했다. 해당 확인에서 소수점 입력값과 재조회값이 일치하는지는 별도로 보고되지 않았다.
- 직접 확인: 수주와 견적은 현재 정책으로 저장 후 수량·단가·금액을 재조회했고, 출하계획은 수정 저장 후 수량을 재조회했다.
- 테스트용 컬럼 예외와 격리 PostgreSQL을 사용한 수주 서비스·Mapper 저장 및 재조회는 확인했다. 견적·출하의 컬럼 예외 검증은 모의 DAO이며 실제 DB 저장이 아니다.
- 영업 소수점 확장 SQL은 사용자가 적용했고 읽기 전용 DB MCP로 대상 27개 컬럼의 `numeric(19,6)` 메타데이터를 확인했다. 추가 컬럼 생성 SQL은 필요하지 않다.
- 2026-11-25 커밋 전 관련 백엔드 테스트와 프론트 11개 파일 386개 테스트, 프론트 빌드를 확인했다. 프론트 병렬 실행은 시간 초과 등으로 실패해 단일 작업자로 재실행했다. 변경 파일 린트는 오류 없이 종료했으나 React 관련 경고가 있고, 빌드에는 번들 크기 경고가 있다.
- 상세 근거와 시점별 기록: [중간 결과](../../20261124/sales-decimal-policy/20261124_004_영업관리_타입별소수점_중간결과.md). 오래된 미완료 문장은 당시 상태이며 위 사용자 확인과 구분한다.

## 남은 검증

1. **컬럼별 예외의 전체 저장 경로**: 격리 환경에 테스트 계약의 `places` 또는 `rounding` 예외를 지정하고 프론트와 서버에 동일하게 배포한다. 수주·견적·출하·출하계획에서 입력, 계산, 저장, 재조회가 해당 필드별 규칙에 일치하는지 확인한다. 특히 행 금액과 헤더 합계가 다른 규칙인 경우 각각 검증한다. 서로 다른 계약을 배포한 경우 저장이 HTTP 409로 거부되는지도 확인한다.
2. **실제 정책관리 흐름**: 테스트 환경에서 `number`·`decimal`·`currency`를 다르게 설정해 저장하고 재조회한다. 정책 이력의 변경 전후, 저장 성공·실패, 재시도, 정책 갱신 후 열린 영업 화면의 입력 제한과 계산을 확인한다. 전역 정책 변경은 공유 사용자에게 영향을 줄 수 있으므로 격리 환경을 사용하거나 사전 협의한다.
3. **출하 소수점 값 일치**: 정책 자릿수에 맞는 수량·단가·금액을 입력하고 저장 전 표시, 출하현황 상세·수정 재조회, 자동 거래명세서 상세·인쇄를 비교한다. 입력값과 저장값이 바뀌지 않는지, 금액 계산은 적용된 `currency` 규칙을 따르는지 확인한다.
4. **연계 화면·반응형**: 수주·견적·출하·출하계획의 현황 및 거래명세서·매출마감 등에서 필드 의미와 2자리 제한 잔존 여부를 조사한다. 실제 로그인 화면에서 375·768·1280px 레이아웃과 저장 진행·성공·실패·dirty 초기화·저장 후 갱신을 확인하고 결과와 스크린샷을 남긴다.
5. **호환성과 경계값**: 컬럼별 예외가 없는 계약에 대해 구버전 스냅샷 미전송 호출과 타입만 바뀐 구버전 호출의 안전성을 검증한다. JSON 숫자 토큰 파서의 큰 지수 등 미검증 경계와 F1-Grid 정밀 모드 경계 사례를 확인한다.
6. **배포 계약**: `frontend/src/shared/config/decimal-column-contract.json`과 서버 WAR의 포함 파일이 일치하는지 확인한다. 백엔드 단독 소스 빌드에는 같은 상대 경로의 계약 파일이 필요하므로 누락 시 기능 실패 가능성을 확인하고 프론트·서버를 함께 배포한다.
   - 2026-11-25 확인(로컬 기존 빌드 산출물 기준): `backend/pom.xml`의 resource 설정이 프론트 계약 파일을 복사하며, `target/classes`와 `target/s-erp-backend.war`의 `WEB-INF/classes/decimal-column-contract.json`이 프론트 원본과 바이트 단위로 일치한다. 계약 파일(11-24 21:14)이 WAR(11-24 21:42)보다 이전이다. 실제 배포 서버의 WAR와 백엔드 단독 빌드 환경의 누락 시 동작은 미확인이다.

## 2026-11-25 후속 진행 기록

- **5번(부분 완료)**
  - 서버: `SalesDecimalColumnPolicyTest`에 두 케이스를 추가해 통과했다. 컬럼 계약에 타입만 바뀌거나 필드가 누락·추가된 구버전 스냅샷은 예외 없는 계약에서도 HTTP 409로 거부된다. 전역 정책 스냅샷(`verifySnapshot`)도 타입 규칙이 바뀌면 409로 거부하며, 스냅샷이 없으면 허용한다.
  - JSON 파서: `exact-decimal-json.test.ts`에 지수 경계 테스트를 추가해 통과했다. 지수 ±256까지는 평문으로 풀고, 그보다 큰 지수나 300자리 토큰은 풀지 않은 문자열로 둔다. 서버 응답의 `numeric(19,6)` 값에는 지수 표기가 없으므로 실제 영향은 작다. 관찰만 하고 수정하지 않았다: `-0e5`는 `-000000`으로 풀린다.
  - F1-Grid 정밀 표시 결함 수정: 읽기 전용 정밀 컬럼에서 `-0.004` 같은 값이 `-0.00`으로 표시됐다(서버 저장값은 `0.00`). 실패 테스트를 먼저 추가한 뒤 `grid.utils.ts`의 `formatExactNumericValue`에서 반올림 결과가 0이면 음수 부호를 붙이지 않도록 수정했고 관련 테스트 41개가 통과했다. 재현: 정밀 컬럼(`decimalPlaces: 2`)에 `-0.004` 표시. 회귀 검증: `tests/f1-grid-exact-display.test.ts`.
  - 미확인: 프론트 `max`는 경계값을 포함하고 서버 `MAX_INTEGER`(1e13)는 미만만 허용한다. 영업 컬럼에 `max`가 실제로 지정되는지는 확인하지 못했다.
- **셀 편집 시 자릿수 불일치 수정**: 셀은 `3.22`로 표시되는데 편집하면 `3.220000`이 나왔다. 원인은 `startEdit`이 서버 원문 문자열을 그대로 편집기 값으로 사용한 것이다. 실패 테스트(`tests/f1-grid.test.tsx`의 "opens an exact decimal editor...")를 먼저 추가해 재현한 뒤, 편집 시작 값을 셀 표시 자릿수로 맞추는 `getExactEditValue`를 추가했다. 편집값을 바꾸지 않고 확정하면 원래 문자열을 유지해 변경(dirty)으로 처리하지 않는다. 회귀 검증: `f1-grid.test.tsx` 217개와 관련 4개 파일 통과, `tsc` 통과. 실제 브라우저 확인과 폼 모달(`GridFormField`) 편집은 미확인이다.
- **1번(실제 DB 저장 확인, 부분 완료)**: 로컬 PostgreSQL의 빈 격리 DB `sales_decimal_isolated_test`에서 `SalesDecimalPostgresIntegrationTest`를 실행했다. 테스트는 `SALES_DECIMAL_TEST_PASSWORD` 환경변수를 읽도록 수정했고, 재실행을 위해 시작 시(DB 이름 검증 후) 이전 테스트 테이블을 `DROP TABLE IF EXISTS`로 정리한다. 비밀번호는 문서·코드에 기록하지 않았다.
  - 실제 계약에는 컬럼별 예외가 없어 픽스처 테스트가 기대하는 `places`가 `null`이었다. 실제 계약 파일은 변경하지 않고, 빌드 산출물(`target/classes`)의 계약만 임시로 `sales.order.supplyAmount`(places 2, HALF_UP)·`orderTotal`(places 1, DOWN) 예외를 가진 픽스처로 바꿔 `mvn surefire:test`로 실행한 뒤 원본으로 복원했다(프론트 원본과 `cmp` 일치 확인).
  - 결과: 컬럼별 예외 픽스처 테스트 통과. 수주 서비스→Mapper→PostgreSQL 저장·재조회에서 행 공급가 `1.24`(2자리 HALF_UP), 행 합계 `1.340`(타입 정책 3자리), 헤더 합계 `1.3`(1자리 DOWN)로 행과 헤더가 서로 다른 규칙으로 처리됐다. 같은 실행에서 스냅샷을 보내지 않는 나머지 2개 테스트는 서버 계약에 예외가 있을 때 의도대로 HTTP 409로 거부됐다.
  - 미확인: 견적·출하·출하계획의 실제 DB 저장(해당 서비스의 컬럼 예외 검증은 모의 DAO 기준), 프론트와 서버가 서로 다른 계약을 배포한 실제 화면 흐름의 409 처리.
- **2번(서버 저장 흐름 확인, 화면 반영은 미확인)**: 정책 API는 로그인 인증이 필요해 호출하지 못했고, 공유 데이터와 실행 중인 서버(8080)는 건드리지 않았다. 대신 `SystemPolicyGridDecimalPostgresIntegrationTest`를 추가해 격리 DB에 기존 DDL(`20261105_004`, `20261117_010`)로 정책 테이블을 만들고 `SystemPolicyServiceImpl`과 실제 Mapper로 `GRID_DECIMAL_SALES`를 확인했다. 통과했다.
  - 저장·재조회: `number` 0자리, `decimal` 3자리 DOWN, `currency` 2자리 HALF_UP FIXED를 각각 저장하고 타입별로 다르게 조회됐다. `SalesDecimalPolicy.from`에 넘기면 서버 계산에 그대로 반영된다(예: 금액 `1.239`→`1.24`).
  - 수정과 이력: `currency`를 4자리 UP AUTO로 수정하면 버전이 2가 되고 이력에 UPDATE가 변경 전(2자리)·후(4자리) 값과 변경자 이름으로 기록된다. 이후 계산은 새 규칙을 따른다(`1.23001`→`1.2301`).
  - 실패: 오래된 버전은 409, 자릿수 7·잘못된 반올림 방식·타입 누락·정수가 아닌 자릿수는 400이다. 실패 뒤에도 값·버전·이력 건수는 그대로다.
  - 재시도: 최신 버전으로 다시 저장하면 성공하고 버전 3, 이력 3건이 된다.
  - 미확인: 정책 갱신 후 이미 열린 영업 화면의 입력 제한·계산 반영(프론트 구독·재조회), 실제 정책관리 화면 조작, HTTP 계층(권한·직렬화), `@Transactional` 롤백(테스트는 트랜잭션 프록시 없이 서비스를 직접 생성).
- **3·4번(사용자 확인)**: 이 세션에는 브라우저 제어 도구가 없어 직접 조작하지 못했다. 사용자가 실제 화면에서 값 일치를 확인했다고 알려 왔다. 확인한 화면 범위, 375·768·1280px 레이아웃, 저장 진행·성공·실패·dirty 초기화, 스크린샷은 전달받지 못해 미확인으로 남긴다.
- **1·2번 진행 준비**: `SalesDecimalPostgresIntegrationTest`가 `SALES_DECIMAL_TEST_PASSWORD` 환경변수(기본 빈 문자열)를 읽도록 수정했다. 격리 DB `sales_decimal_isolated_test`와 비밀번호는 사용자가 제공해야 하며 실행 결과는 아직 없다.

- **견적·출하·출하계획 실제 저장, 정책 갱신 후 열린 화면 반영(사용자 확인)**: 사용자가 두 항목을 직접 확인했다고 알려 왔다. 이 세션에서는 자동화 테스트나 화면으로 재현하지 않았고, 확인한 화면·값·환경과 증빙(스크린샷)은 전달받지 못했다.
- **정책 API HTTP 계층과 `@Transactional` 롤백(확인)**: `SystemPolicyHttpTransactionPostgresIntegrationTest`를 추가했고 격리 DB에서 통과했다. 스프링 트랜잭션 프록시와 실제 Mapper·PostgreSQL을 쓰고, 컨트롤러는 standalone MockMvc에 인증 주체를 주입했다. 실제 보안 필터 체인과 JWT는 포함하지 않는다.
  - 권한: `grid-decimals` 조회는 로그인 사용자(`TENANT_USER` 포함)에게 200, 인증 없음은 403. 저장·이력 조회는 `PLATFORM_ADMIN`만 허용하고 일반 사용자와 인증 없음은 403이다.
  - 응답: 저장 성공은 200·`resultCode` 200·메시지 "정책이 저장되었습니다."·새 버전과 값을 반환한다. 오래된 버전은 409, 범위를 벗어난 자릿수(9)는 400이며 실패 뒤에도 저장값은 유지된다. 이력 조회는 UPDATE(변경 전 2자리·후 4자리)와 CREATE 순으로 반환한다.
  - 롤백: 테스트 DB에 특정 정책의 UPDATE 이력 INSERT만 실패시키는 트리거를 두고 저장하면, 정책 UPDATE가 성공한 뒤 이력 단계에서 오류가 나도 값·버전·이력 건수가 모두 저장 전 상태로 유지된다. 트랜잭션 어노테이션을 제거했을 때 이 테스트가 실패하는지는 확인하지 않았다.
- **배포 계약 파일(WAR)**: 8080에서 실행 중인 서버는 WAR가 아니라 `backend/target/classes`에서 직접 실행하는 개발 서버(`spring-boot-devtools` 포함)이며 해당 디렉터리의 계약 파일은 프론트 원본과 일치한다. 실제 배포 서버의 WAR는 이 환경에서 접근할 수 없어 확인하지 못했다. 배포 담당자가 `unzip -p <war> WEB-INF/classes/decimal-column-contract.json | sha256sum`과 `sha256sum frontend/src/shared/config/decimal-column-contract.json`을 비교한다.
- **실제 보안 필터를 포함한 정책 API 호출(확인)**: `SystemPolicySecurityApiPostgresIntegrationTest`를 추가했고 격리 DB에서 통과했다. 실제 `SecurityConfig` 필터 체인과 `JwtAuthenticationFilter`를 쓰고, 토큰은 실제 `EgovJwtTokenUtil`로 서명한다(시크릿은 코드에서 읽지 않는다).
  - 토큰이 없거나 변조·형식 오류이면 컨트롤러에 도달하기 전에 401이고 정책 값은 바뀌지 않는다.
  - 서명된 `TENANT_USER` 토큰은 소수점 정책 조회는 200, 정책 목록·저장은 403이다. `PLATFORM_ADMIN` 토큰은 저장 200(버전 2), 오래된 버전 409, 이력의 변경자 이름·변경 후 값 조회가 된다. 토큰의 테넌트·사용자 ID가 저장 요청에 반영된다.
  - 비밀번호 변경 필요(`pcr`) 토큰은 조회와 저장 모두 403이며 응답 코드 `PASSWORD_CHANGE_REQUIRED`다.
  - 미확인: 만료된 토큰, 리프레시 토큰으로의 접근, CORS, 실제 로그인 API로 발급한 토큰.
- **저장 진행·성공·실패 표시(자동화 테스트로 확인)**: 이 세션에서는 실제 브라우저를 조작하지 못해 jsdom 테스트로 확인했다. 수주등록(진행 중 버튼 비활성·중복 제출 방지·성공 시 수주번호·실패 시 입력 유지·저장 후 이탈 경고 없음), 출하등록(실패 시 입력 유지·중복 저장 방지·서버 금액 재조회), 출하계획(저장 실패 시 편집 유지)은 기존 테스트가 있었다. 견적등록은 없어서 `tests/quotation-create-page.test.tsx`의 "saving a loaded quotation"에 두 케이스를 추가했고 통과했다.
  - 진행: 저장 중 입력 영역 `aria-busy`가 true이고 저장 버튼이 비활성이며, 다시 눌러도 요청은 1번이다. 입력값은 유지된다.
  - 성공: "견적이 수정되었습니다. 견적번호: QT-OLD" 알림이 뜨고 `aria-busy`가 해제된다. 저장된 값을 다시 불러오며 저장 버튼은 비활성(변경 없음)이고 `beforeunload` 경고가 없다(dirty 초기화).
  - 실패: 서버 오류 메시지가 표시되고 성공 알림은 없다. 입력값 유지, 저장 버튼 재활성, `beforeunload` 경고 유지, 재시도하면 성공하고 오류 알림이 사라진다.
  - 미확인: 거래명세서 등록·견적 신규 등록(수정 모드만 추가)·각 현황 상세 수정 화면의 저장 표시를 이번에 새로 확인하지 않았다. 실제 브라우저의 표시(스크린샷, 375·768·1280px)는 확인하지 못했다.
- **남은 미확인**: 375·768·1280px 레이아웃과 스크린샷, 실제 배포 서버 WAR의 계약 파일, 만료·리프레시 토큰과 CORS를 포함한 인증 경계.

- **회귀 실행(2026-11-25)**: 프론트 전체를 병렬 실행하면 3,186개 중 154개(39개 파일)가 실패했다. 대부분 5초 안팎의 시간 초과였다. 같은 39개 파일을 단일 작업자로 재실행하자 1,165개 중 1,164개가 통과했다. 남은 1개(`tests/page-initial-errors.test.tsx`의 "replaces the full sales/status body...")는 이번 변경을 임시로 빼고 실행해도 똑같이 실패해 기존 실패로 확인했다. 원인은 조사하지 않았다. 백엔드 `DecimalColumnRuleTest`, `SalesDecimalColumnPolicyTest`, `DecimalColumnContractTest`와 격리 DB 통합 테스트 2종은 통과했다. 프론트 빌드와 변경 영역 lint는 이번 후속 작업 후 다시 실행하지 않았다(`tsc`만 통과).
