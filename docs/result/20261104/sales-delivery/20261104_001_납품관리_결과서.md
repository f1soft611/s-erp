# 납품등록·납품현황 결과서

## 구현 범위

- 영업관리 > 납품관리 > 납품등록, 납품현황.
- 등록 경로: `/sales/delivery/delivery-create`.
- 현황 경로: `/sales/delivery/delivery-status`.
- 직납품: 거래처·품목 도움창 선택 후 수량/단가/VAT 입력.
- 수주납품: 미납 수주 검색·선택, 거래처·품목·잔량 자동 반영, 부분납품.
- 저장 후 재조회, 수정/삭제, 오류 시 입력 보존, 미저장 이탈 확인.
- 현황은 납품일 필수 기간, 통합/상세검색, F1-Grid 및 문서 상세 편집 제공.
- F1-Grid는 기존 기능을 소비하며 공통 그리드 자체 동작은 변경하지 않음.
- 재고수불·회계·반품은 이번 범위에 포함하지 않음.

## DB·메뉴 적용

**실제 DB에 적용하지 않았다.** 다음 스크립트는 실행자가 승인된 DB/테넌트를 확인하고 적용해야 한다.

| 순서 | 파일 | 내용 |
|---|---|---|
| 1 | [create_sales_delivery_schema.sql](../../../database/20261104/20261104_001_create_sales_delivery_schema.sql) | 납품 헤더/상세 및 수주상세 복합 UNIQUE |
| 2 | [seed_sales_delivery_menu.sql](../../../database/20261104/20261104_001_seed_sales_delivery_menu.sql) | 대상 tenant 지정 후 메뉴/지원 권한/기존 수주 역할 권한 복제 |
| 참고 | [change_sales_delivery_schema.md](../../../database/20261104/20261104_001_change_sales_delivery_schema.md) | 적용 전제·영향·롤백 절차 |

- 동일 파일을 `backend/DATABASE/20261104`에도 보관하며 내용 일치 확인.
- 메뉴 SQL의 `v_tenant_id := NULL`은 승인된 대상 ID로 변경해야 한다. 미지정 시 명시적으로 실패한다.
- 메뉴·스키마 롤백 스크립트를 각각 제공한다. 납품 이력이 있으면 스키마 롤백을 거부한다.
- 삭제된 납품도 상세 참조 이력을 유지하므로 연결 수주의 상세 재생성/삭제는 차단한다.
- 수주/납품 번호가 이미 발급되었으면 채번 상태를 자동 초기화하지 않는다.

## DB MCP 근거

- 기본 `s-erp-postgresql-readonly`의 `list_tables`를 먼저 호출.
- `tb_sales_order_hd`, `tb_sales_order_dt`, `tb_menu`, `tb_module`, `tb_customer_info`, `tb_material_info`의 `describe_table` 확인.
- 제한된 `pg_constraint` 조회로 수주/마스터 tenant 복합 FK 대상키 및 메뉴 권한 PK/FK 확인.
- `pg_attribute`/`pg_get_serial_sequence` 조회로 메뉴·모듈 ID의 identity 계약 확인.
- 신규 납품 테이블은 현재 목록에 없었음. 업무/테넌트/계정 행 데이터는 조회하거나 복사하지 않음.
- MCP는 읽기 전용 근거로만 사용했고 DDL 또는 데이터 변경에는 사용하지 않음.

## 검증

### PostgreSQL 스크립트

PGlite 임베디드 PostgreSQL의 독립 메모리 DB에 합성 선행 스키마/데이터만 생성하여 **19개 확인 통과**.

- 생성 DDL 및 메뉴 PL/pgSQL 실행.
- 직납품/수주납품 정상 입력.
- 부모와 다른 납품구분, 다른 수주·품목·tenant 참조, 중복 상세, 0/NaN 수량, 잘못된 합계 거부.
- 대상 tenant 미지정 거부, 메뉴 반복 seed 중복 방지, 대응 수주 역할 권한만 복사.
- 새 메뉴의 자식/손자 노드가 추가된 경우 메뉴 롤백 거부.
- 납품 이력이 있으면 스키마 롤백 거부, 빈 테이블이면 정상 롤백.
- docs/backend 스크립트 사본 일치.

이는 실제 운영 DB 적용이나 JDBC/MyBatis 통합검증이 아니다.

### 프론트엔드

- `npm run test -- tests/sales-delivery-api.test.ts tests/sales-delivery-page.test.tsx`: **15개 통과**.
- `npm run build`: 통과.
- 변경 파일 대상 oxlint: 오류 없음(경고 존재).
- `npm run lint`: 기존 `tests/common-code-management-page.test.tsx:53`의 조건부 `useImperativeHandle` 오류로 실패. 이번 납품 변경과 무관한 기존 파일은 수정하지 않음.

### 실제 브라우저

Playwright Chromium, `http://127.0.0.1:4173`, 모든 API는 합성 응답으로 격리.

- 거래처/품목 선택 → 직납품 저장 → 번호/서버 금액 재조회.
- 409 실패 후 비고/상세 입력 보존 및 재저장.
- 수주 잔량 6 확인 → 부분납품 3 저장 → 수량 4 수정.
- 현황에서 문서 상세 조회 → 삭제 확인 → 삭제 후 목록 재조회.
- 납품일 시작일을 비우면 필수 오류가 표시되고 새 조회 요청이 발생하지 않음.
- 필수 납품일 기간 칩의 제거 버튼 비활성화 확인.
- 등록/수주납품/현황 모두 375/768/1280px에서 문서 전체 가로 overflow 없음.
- 375px에서도 내부 세로 스크롤로 상세 그리드에 도달 가능.
- 브라우저 runtime error 0건. 검증용으로 시작한 서버를 종료하고 4173 포트 해제를 확인했다.

### 백엔드

- `mvn -q "-Dtest=SalesDelivery*,SalesOrderServiceImplTest,SalesOrderTenantScopeMapperTest" test`: **39개 통과**, 실패/오류/skip 0건. 최종 구현 후 별도 재실행하여 확인.
- 전체 `mvn -q test`: **881개**, 실패/오류 0건, 2개 skip.
- 첫 전체 실행에서 관련 없는 `StandardWebPushTransportTest`의 타이밍 민감 실패가 있었음. 해당 테스트 단독 재실행 및 전체 재실행은 통과했으며 무관한 코드는 수정하지 않음.
- 변경된 운영 Java **14개 파일**을 `javac --release 8`로 별도 컴파일하여 Java 8 표준 API/문법 호환성 확인.
- Controller 인증/응답, tenant 범위, 직접/수주납품, 잔량/중복/참조 위변조, 수정 시 기존 수량 제외, 삭제 수량 복원, 수주 편집 잠금/이력 참조 차단, 날짜 필수조건과 Mapper 계약 검증.
- 실제 DB의 트랜잭션 잠금·롤백을 통합 검증했다고 주장하지 않음.

### 리뷰 보완

- 최초 리뷰에서 현황 READ-only 사용자가 등록 메뉴 READ가 없으면 문서 상세를 열지 못하는 문제를 확인.
- 현황 상세 열기는 현황 READ를 따르도록 수정하고, 수정/삭제는 등록 메뉴 UPDATE/DELETE만 유지.
- 등록 메뉴 없음/READ 거부/등록 메뉴의 수정·삭제 권한 유지에 대한 3개 회귀 사례 추가. 수정 전 실패, 수정 후 통과 확인.
- 사양 준수 및 주요 로직·품질 검토에서 그 외 확정 결함은 보고되지 않았으며 권한 수정 재검토도 통과.

## 미확인 범위

- 승인된 실제 DB에 스키마·메뉴를 적용한 뒤의 JDBC/API 통합 동작.
- 실제 역할 설정에 따른 메뉴 노출은 메뉴 SQL 적용 및 권한 설정 후 확인 필요.
- 동시 트랜잭션의 실제 DB 잠금/롤백은 단위/계약 검증과 구분한다.
