# 20261027_001 품목·거래처 분류설정 구현 검토

## 검토 요청

`C:\Users\socra\Downloads\smart_haccp_schema_2.sql`의 품목분류·거래처분류를 등록할 수 있도록 품목관리와 거래처관리 우측 상단에 설정 버튼을 두고, 버튼에서 분류를 관리하는 화면을 여는 방안을 검토한다.

## 결론

페이지 이동보다 **각 관리 페이지에서 여는 분류 설정 다이얼로그**를 권장한다. 현재 목록 업무 흐름을 벗어나지 않고, 화면마다 품목분류/거래처분류 설정을 명확히 구분할 수 있다. 다만 외부 SQL의 분류 테이블은 현재 S-ERP DB와 모델이 다르므로, SQL을 그대로 적용하거나 프론트엔드만 먼저 연결해서는 안 된다. 테넌트 범위와 기존 분류값 처리 등 데이터 계약을 정한 뒤 작업지시서·계획서·상세사양서를 작성해야 한다.

## 확인한 근거

### 전달된 SQL

- `tb_cls_item`: 자체 참조 계층형 분류. 레벨은 대/중/소(1~3)이며 `upper_item_cls_cd`가 부모 분류를 가리킨다.
- `tb_cls_partner`: 자체 참조 계층형 분류. 레벨은 대/소(1~2)이다.
- 양쪽 모두 코드 PK(`VARCHAR(10)`), 이름(`VARCHAR(50)`), 정렬순서, 사용여부(`Y/N`)와 등록/수정 감사 필드를 가진다.
- 품목마스터는 `item_cls_cd`로 품목 소분류를, 거래처마스터는 `partner_cls_cd`로 거래처분류를 참조하도록 정의되어 있다.
- 분류 테이블에는 `tenant_id`가 없고, 코드 생성 규칙도 정의되어 있지 않다.

### 현재 S-ERP

- 기본 `s-erp-postgresql-readonly` MCP의 최신 조회에서 `tb_customer_info.business_kind1`, `business_kind2`, `business_kind3`를 확인했다. 세 컬럼은 nullable `character varying`이며 기본값은 없다. 제한된 집계에서 `business_kind1/2` 값이 비어 있음을 확인했으며, 개별 업무 행은 조회하지 않았다. 이는 사용자가 말한 central DB에 기존 분류 후보 컬럼이 있음을 뒷받침한다.
- tenant `1110011111` MCP의 `tb_customer_info` 메타데이터에는 `business_kind1/2/3`가 없다. tenant DB와 기본 central DB 메타데이터는 서로 다르므로 혼용하지 않는다.
- 현재 확인한 두 MCP의 테이블 목록에는 `tb_cls_item`, `tb_cls_partner`, `tb_item_master`, `tb_partner_master`가 없다. 이 사실은 조회한 두 DB에 한정한다.
- 현재 `tb_material_info`에는 `mat_cata_type`이 있지만 별도 분류 FK인 `item_cls_cd`는 없다. 최신 품목 작업지시서(`docs/directions/20261023/20261023_010_품목관리_공통코드_컬럼정비_작업지시서.md`)는 품목분류를 화면 목록·폼·상세검색에서 제외하고 DB/API 저장값은 보존하도록 정했다.
- 현재 `tb_customer_info`에는 `folder_type_code`가 있으나, 이를 거래처분류로 사용한다는 계약은 확인하지 못했다. 의미를 확인하지 않고 재사용하면 안 된다.
- 현재 관리 화면은 각각 `MaterialManagementPage.tsx`, `CustomerManagementPage.tsx`이며 `PageHeader`에 권한별 `actionGroups`를 전달한다. 설정 진입 버튼은 이 기존 헤더 액션 구조에 놓는 것이 자연스럽다.

## 화면 접근 방식 비교

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 설정 다이얼로그(권장) | 목록에서 바로 열고 닫을 수 있어 작업 맥락을 유지한다. 품목/거래처 페이지의 기존 헤더 액션 패턴과 맞는다. | 계층 편집과 좁은 화면 대응을 위해 충분한 다이얼로그 너비·내부 스크롤이 필요하다. |
| 별도 설정 페이지 | 계층이 크거나 추가 관리 기능이 생겼을 때 화면 공간을 확보하기 쉽다. | 메뉴/라우팅·뒤로가기·목록 복귀 상태까지 관리해야 하고, 현재 요청보다 범위가 커진다. |

설정 기능이 분류 CRUD와 계층 탐색에 한정되는 동안은 다이얼로그가 적합하다. 기능이 여러 관리 정책으로 커질 때 별도 페이지로 전환하는 것이 낫다.

## 권장 화면과 동작

1. 품목관리 헤더에는 `품목분류 설정`, 거래처관리 헤더에는 `거래처분류 설정` 버튼을 둔다. 기존 헤더 action group을 사용하고 저장 중에는 비활성화한다. 쓰기 권한은 우선 각 메뉴의 기존 생성/수정 권한 및 tenant-admin 제한과 일치시키되, 최종 권한 정책은 사양서에서 확정한다.
2. 버튼을 누르면 해당 분류만 관리하는 다이얼로그를 연다. 데스크톱에서는 계층 목록과 선택 항목 편집 영역을 나란히 배치하고, 모바일에서는 세로 배치와 내부 스크롤을 사용한다. 화면 폭 375/768/1280px에서 페이지 전체 가로 넘침이 없어야 한다.
3. 계층 구조에 따라 상위/하위 분류를 추가하고 선택 항목의 이름·정렬순서·사용여부를 편집한다. 품목은 3단계, 거래처는 2단계로 제한한다. 자식이 있는 부모의 레벨 변경이나 잘못된 부모 선택은 허용하지 않는다.
4. 저장은 백엔드 API를 통해 수행하고 성공하면 분류 목록을 재조회한다. 목록이 열려 있다면 분류 옵션도 갱신한다. 오류는 기존 페이지 메시지/다이얼로그 오류 표시 패턴으로 사용자에게 알린다.
5. 참조될 수 있는 분류는 물리 삭제하지 말고 `use_yn = 'N'`으로 비활성화하는 방안을 권장한다. 기존 품목·거래처에 이미 연결된 비활성 분류는 표시를 보존하되 신규 선택에서는 제외할지 정책을 확정해야 한다.

## 먼저 결정해야 할 데이터/API 사항

1. **분류 소유 범위:** 현재 앱의 관리 API는 인증된 tenant로 데이터를 제한한다. 하지만 전달 SQL의 분류 테이블에는 `tenant_id`가 없다. tenant별로 독립 관리한다면 테이블에 tenant 범위 및 유일성/FK 설계가 필요하다. 전체 tenant 공통 분류라면 공통 편집 권한과 전역 변경 영향 범위를 별도로 정의해야 한다. 현 구조에 맞춰 tenant별 관리를 기본 권고한다.
2. **실제 테이블 및 품목·거래처 연결:** 현재 S-ERP의 `tb_material_info`/`tb_customer_info`를 기준으로 분류를 연결한다. 기본 central DB에는 nullable varchar인 `business_kind1/2/3`가 이미 있으므로 거래처 분류 코드를 저장할 후보로 활용할 수 있다. 다만 `business_kind1/2`를 대·소분류 코드로 사용할지와 기존 저장값의 의미·호환성은 DDL 확정 전에 추가 확인해야 한다. 품목에는 새 분류 ID 컬럼이 필요하다는 요청을 반영하되, 현재 `mat_cata_type` 값과 신규 코드의 매핑은 별도 조사 없이 자동 변환하지 않는다.
3. **코드 발급과 중복 정책:** SQL은 코드 PK만 정하고 발급 방식을 정의하지 않는다. 사용자가 코드를 입력할지, 서버가 자동 발급할지와 이름 중복 허용 여부를 확정해야 한다.
4. **삭제/비활성 정책:** 참조 중인 분류의 삭제 차단, 비활성화 허용 조건, 하위 분류 및 연결 품목·거래처의 표시와 신규 선택 규칙을 정해야 한다.
5. **업무 화면 적용 범위:** 설정 팝업만 만들면 분류를 등록할 수는 있지만 품목/거래처에 지정할 수는 없다. 실제 사용을 원한다면 목록·등록/수정 폼·검색·저장 API에 분류 선택을 연결하는 후속 범위를 함께 정의해야 한다.

## 권장 작업 분리

- **1단계 — 데이터 계약 확정:** tenant 범위, 현재 테이블과의 연결, 기존값 매핑, 코드 발급, 비활성 정책을 정한다. 전달 SQL 전체에는 재실행 시 `DROP TABLE ... CASCADE`가 포함되어 있으므로 운영 또는 기존 데이터가 있는 DB에 그대로 실행하지 않는다.
- **2단계 — 분류 관리 기능:** 날짜별 작업지시서·계획서·상세사양서를 작성한 뒤 필요한 날짜별 SQL/롤백/스키마 문서, 백엔드 계층 API, 설정 다이얼로그를 구현한다.
- **3단계 — 마스터 화면 연결:** 1단계에서 정한 계약에 따라 품목/거래처의 분류 표시·선택·검색과 데이터 변환을 적용한다. 기존 품목분류 UI 제외 사양도 이 단계의 새 요구사항으로 명시적으로 갱신한다.

- 대/중/소 및 대/소 계층 제한, 부모 변경, 코드/이름 검증, 정렬, 비활성/참조 중 상태를 테스트한다.
- tenant별 데이터 격리와 저장 권한을 백엔드 테스트로 확인한다.
- 설정 저장 후 재조회 및 기존 연결값 표시가 동작하는지 확인한다.
- 375/768/1280px 실제 브라우저에서 다이얼로그와 페이지 가로 넘침을 확인한다.
- DB 변경이 있으면 날짜별 SQL·변경 이력·롤백 및 `docs/database/db-schema.md`를 함께 갱신한다.

## 확인 한계

이번 문서는 구현 검토다. 코드·DB 변경은 하지 않았다. 기본 MCP에서 central DB의 `tb_customer_info`를 다시 설명해 `business_kind1/2/3`가 nullable `character varying`임을 확인했고, tenant `1110011111` MCP 메타데이터와 차이도 확인했다. 테이블 메타데이터만 조회했으며 개인정보나 업무 데이터 행은 조회하지 않았다. 다운로드 SQL은 설계안으로 읽었고 실제 DB 적용 상태를 의미하지 않는다.

## 스키마 초안 작성 결과

후속 작업으로 승인된 데이터 모델에 따른 migration, guarded rollback, 변경 이력 초안을 작성했다. 파일은 [DDL](../../../database/20261027/20261027_002_create_item_partner_classification_schema.sql), [rollback](../../../database/20261027/20261027_002_rollback_item_partner_classification_schema.sql), [변경 이력](../../../database/20261027/20261027_002_change_item_partner_classification_schema.md)에 있으며, `backend/DATABASE/20261027`에도 동일 사본을 보관한다. [누적 스키마 문서](../../../database/db-schema.md)에는 현행 적용 스키마와 분리된 “미적용 설계안”으로 표시했다.

DDL은 central DB MCP에서 확인한 tenant/master 키 및 컬럼 메타데이터를 사전조건으로 검사하며, `business_kind1/2`에 적용 시점의 공백 외 데이터가 있으면 중단하도록 했다. rollback은 분류 row나 마스터 참조가 있으면 중단하고 `CASCADE`를 사용하지 않는다. SQL 문법 및 제약 연결은 정적으로 검토했으며, 이 환경에 `psql`/`pg_format` 실행 파일이 없어 PostgreSQL 파서/실행 검증은 하지 않았다. 실제 DB DDL 적용, 백엔드 API 및 화면 구현은 수행하지 않았다.
