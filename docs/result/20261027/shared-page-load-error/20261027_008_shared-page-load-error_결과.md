# 공통 최초 조회 실패 화면 결과

근거: [작업지시서](../../../directions/20261027/20261027_008_shared-page-load-error_작업지시서.md), [계획서](../../../plan/20261027/20261027_008_shared-page-load-error_계획서.md), [상세 사양서](../../../spec/20261027/20261027_008_shared-page-load-error_상세사양서.md).

## 적용 동작

- 필수 초기 조회가 실패하면 앱 탐색과 페이지 헤더는 유지하고, 검색·그리드·폼 본문은 공통 오류 안내와 재시도 버튼으로 대체한다.
- 재시도 중에는 오류 안내를 유지하며 버튼을 비활성화한다. 성공하면 정상 본문을 복구한다. 성공 응답이 0건이어도 정상 빈 목록으로 처리한다.
- 한 번 성공한 이후의 조회 실패와 저장 실패는 전체 본문을 가리지 않는다. 기존 데이터와 작성 내용을 유지하고 해당 화면의 기존 오류 표시를 사용한다.
- 연결 실패, 인증 필요(401), 권한 없음(403), 그 밖의 서버/응답 오류를 구분한다. 서버 내부 예외는 공통 본문에 노출하지 않는다.
- 취소 요청은 연결 오류로 처리하지 않으며, 최신 요청의 결과만 반영한다. 독립적인 필수 자원은 각각 최초 성공 여부를 관리한다.

연결 실패는 fetch 또는 응답 본문 수신 실패를 뜻한다. 인터넷 단절뿐 아니라 서버 중단·DNS·CORS 등의 가능성이 있으므로 물리적 네트워크 단절로 단정하지 않는다. HTTP 오류 응답을 받은 경우에는 네트워크 안내 대신 상태에 맞는 안내를 표시한다. 무한 대기 요청의 타임아웃 정책은 이번 변경에 추가하지 않았다.

## 적용 범위

| 영역 | 적용 화면 및 필수 자원 |
|---|---|
| 시스템 | 모듈, 역할, 창고, 메뉴관리의 초기 목록/필수 옵션 |
| 기준정보 | 공통코드, 거래처, 품목의 초기 목록/필수 옵션 |
| 기안양식 | 목록과 분류·주기·사용자 옵션 각각 |
| 그룹웨어 | 공지사항, 자료실의 기본 날짜/분류/파일 목록 |
| 전자결재 | 문서현황 기본 날짜/목록, 작성 화면 목록/요약 |
| 영업관리 | 병행 작업에서 추가된 수주현황의 기본 날짜/목록 |
| 공통 진입 | 앱 초기 메뉴/모듈, 내 정보 프로필 |

필수 초기 조회가 없는 정적 화면, 보안 설정, 로그인, 수주 신규 작성, 문서·Grid 예제, 준비 중/404에는 인위적인 요청이나 오류 화면을 추가하지 않았다. 편집창·상세·도우미의 실패는 해당 영역의 처리 방식을 유지한다. 모든 API 오류를 전역 차단하는 방식이 아니므로 새 데이터 페이지도 필수 초기 조회에 아래 공통 계약을 연결해야 한다.

## 구현 및 회귀 수정

`apiErrors.ts`의 오류 타입, `useInitialLoadState`의 최초 성공 상태, `PageLoadBoundary`의 표시 책임을 분리했다. 기존 `apiClient` 오류 타입 import는 재수출로 호환된다. HTTP 오류의 비 JSON 본문은 상태 코드를 보존하고, 정상 응답의 잘못된 JSON은 일반 조회 오류로 분류한다.

실제 페이지 회귀 테스트로 기안양식의 검색 영역만 감싸거나 프로필 이미지 편집 영역이 남는 불완전한 경계를 발견해 전체 본문 경계로 수정했다.

역할관리에서는 저장 성공 후 재조회 실패 → 확인 후 다시 조회 실패 → 저장 재시도 시, 편집 기준을 미리 초기화하면 과거 행 값으로 추가 PUT이 발생했다. 역할 편집 기준과 실패한 저장의 표시 상태를 실제 목록 적용 성공 후에만 초기화하도록 수정했다. 기존 재시도 기록 테스트에서 PUT 2회 실패를 확인한 뒤 1회로 유지되는 것을 검증했다. 매핑 재조회와 역할 전환 동작은 기존 계약을 유지한다.

### 이후 페이지 연결 예

```tsx
const { start, succeed, fail, ...initialLoad } = useInitialLoadState();

// 해당 자원의 기존 최신 요청/취소 검사와 함께 사용한다.
start();
try {
  const rows = await fetchRows();
  setRows(rows);
  succeed();
} catch (cause) {
  fail(cause);
  setError(cause instanceof Error ? cause.message : '조회 실패');
}

// PageHeader 아래의 전체 본문을 감싼다.
<PageLoadBoundary {...initialLoad} label="목록" onRetry={retry}>
  {body}
</PageLoadBoundary>
```

안정적인 `start/succeed/fail`을 effect/callback 의존성으로 사용한다. 목록 길이로 성공 여부를 추정하거나 저장 요청을 초기 조회 상태에 연결하지 않는다.

### 기존 관리 화면 테스트의 한계

전체 테스트가 모두 통과했다고 판단하지 않는다. 확장 관리 화면 10개 파일 실행은 수정 전 기대값과 기존 mock 문제 등을 포함해 195개 통과/49개 실패 및 19개 미처리 오류였다. 이 실행 뒤 공통 초기 오류 문구 기대값, 메뉴 역할 fixture, 위 역할 재조회 중복 저장 회귀를 수정하고 각각 집중 검증했다. 확장 10개 파일 전체는 다시 실행하지 않았다.

기존 실패와의 분리는 저장소 파일을 되돌리지 않고 세션 전용 설정으로 공통 초기 오류 상태를 비활성화해 확인했다. 거래처/품목/메뉴 Grid 3개 파일은 이 조건에서도 25개 실패/78개 통과였으며, 공통 상태 활성 실행과의 추가 차이는 역할 응답 fixture가 빠진 메뉴 정렬 테스트 1개였다. 해당 fixture는 보완 후 통과했다.

공통코드의 Tree mock `setSelectedRowIds` 누락, 기안양식의 기존 편집/컨텍스트 메뉴 기대값, 메뉴·역할의 기존 Grid skeleton/레이아웃 기대값은 이전 공통 이탈 보호 작업의 기준 실행에서도 재현됐다. 거래처/품목 분류 및 메뉴 선택/권한 관련 기존 실패는 초기 오류 상태를 비활성화한 진단에서도 유지됐다. 무관한 Grid/분류/선택 동작까지 변경하지 않았다. 역할 기존 테스트의 일부 비동기 act 경고도 남아 있다.
