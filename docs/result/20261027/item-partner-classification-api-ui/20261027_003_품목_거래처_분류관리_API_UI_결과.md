## API 및 데이터 보호

| API | 권한 | 응답 |
|---|---|---|
| `GET /api/v1/co/master/classifications/items` | 품목 메뉴 READ/CREATE/UPDATE 중 하나 | `result.resultList` |
| `POST /api/v1/co/master/classifications/items` | 품목 메뉴 CREATE | HTTP 201, `result.item` |
| `PUT /api/v1/co/master/classifications/items/{id}` | 품목 메뉴 UPDATE | `result.item` |
| `GET /api/v1/co/master/classifications/partners` | 거래처 메뉴 READ/CREATE/UPDATE 중 하나 | `result.resultList` |
| `POST /api/v1/co/master/classifications/partners` | 거래처 메뉴 CREATE | HTTP 201, `result.item` |
| `PUT /api/v1/co/master/classifications/partners/{id}` | 거래처 메뉴 UPDATE | `result.item` |

- 서버는 `SystemMenuService.getMyMenuTree`에서 `co` 모듈과 `materials`/`customers` 페이지의 유효 메뉴 권한을 확인한다. 다른 업무/모듈의 권한은 대체할 수 없다.
- tenant는 인증 `LoginVO.tenantId`, 감사 사용자는 `LoginVO.uniqId`에서 결정한다. 요청에 tenant·레벨·감사 필드를 받지 않으며 응답에도 tenant·감사 필드를 노출하지 않는다.
- 등록자/등록일시는 INSERT에서, 수정자/수정일시는 UPDATE에서 기록한다. 시각은 DB `CURRENT_TIMESTAMP`를 사용한다.
- 이름은 trim 후 1~50자, 정렬순서는 0 이상의 정수, 사용여부는 Y/N으로 검증한다.
- 같은 tenant의 활성 부모만 하위 등록을 허용한다. 활성 자식이 있으면 부모 비활성화를 거부하고 재활성화 시 부모 활성 상태를 확인한다.
- 모든 조회/수정에 tenant 조건을 적용하고 부모/대상 행 잠금을 트랜잭션 안에서 사용한다. 동적 SQL 식별자는 요청 문자열 대신 서버 내부 enum에 고정한다.
- 입력 및 비정수 ID는 표준 HTTP 400/INPUT_CHECK_ERROR, 권한 부족은 403, 인증 tenant 부재는 401, 없는/다른 tenant의 대상은 404다. 예상 밖 오류를 성공으로 변환하지 않는다.

## UI 및 검토 보완

- 열 때 로딩을 표시하고 실패 시 원인 메시지와 재조회 버튼을 제공한다. 부모 우선 목록, 단계별 들여쓰기, 최대 깊이/미사용 부모의 하위 추가 제한을 적용했다.
- 저장 오류는 입력을 유지한다. 저장 성공 뒤 목록 재조회만 실패하면 저장을 차단하고 재조회로 복구해 중복 등록을 방지한다.
- 검토에서 발견한 **다른 분류 선택/추가 시 미저장 편집값 유실**을 보완했다. 선택 변경·추가·닫기 시 기존 공통 확인창에서 폐기를 확인하고 취소하면 값을 보존한다.
- 초기 비동기 조회는 다이얼로그 해제 뒤 결과를 반영하지 않는다. 600px 미만은 전체 화면·세로 배치, 그 이상은 최대 900px의 두 영역 배치다.

### 실제 브라우저 확인

기존 `http://127.0.0.1:4173` S-ERP 서버를 재사용했다. 다른 작업을 방해하지 않도록 worktree의 실제 페이지·다이얼로그를 임시 Vite bundle로 빌드하고 Playwright의 격리 페이지에 공급했다. 마스터 목록과 분류 API는 **합성 데이터로 전부 가로채기**했으며, 실제 인증/업무 데이터나 DB를 사용하지 않았다. 이는 실제 Chromium 렌더링 및 서비스 요청/응답 흐름 확인이지, 운영 라우팅·DB 통합 검증이 아니다.

- 각 폭에서 비관리자의 메뉴 권한 기반 설정 열기, 최대 레벨/비활성 부모의 하위 추가 차단, 미저장 편집 취소 시 값 보존, 수정, 등록, 저장 후 재조회 실패, 재시도 및 중복 등록 방지, 닫기를 확인했다.
- 문서/본문의 가로 overflow 없음, 375px 전체 화면 및 768/1280px 일반 다이얼로그를 확인했다. 각 조합의 page error는 0건이다. 오류 복구 시나리오의 HTTP 503은 의도한 합성 응답이다.
- 측정값: 375px에서는 다이얼로그 375px, 768px에서는 704px, 1280px에서는 900px. 본문 `scrollWidth`와 `clientWidth`가 각 조합에서 일치한다.

## DB MCP 및 배포 제한

- 구현 전에 기본 읽기 전용 `s-erp-postgresql-readonly`의 `list_tables` → `describe_table(tb_tenant)`/`describe_table(tb_menu)`로 tenant key 및 메뉴 경로 메타데이터를 확인했다. 업무 데이터 행이나 자격 증명을 기록하지 않았다.
- 해당 시점에 분류 테이블은 없었다. 분류 컬럼 계약은 현행 DB 조회 결과로 가장하지 않고 **미적용 `20261027_002` 스키마 사양**을 근거로 사용했다.
- **이번 작업은 DDL·migration·DB 쓰기를 실행하지 않았다.** Mapper 검증은 SQL 파싱/렌더링이며 실제 PostgreSQL 트랜잭션·동시성·FK 적용을 검증하지 않았다.
- `docs/database/db-schema.md`의 분류 정의는 이미 미적용으로 표시되어 있어 변경하지 않았다. 기존 날짜별 SQL/rollback 및 `backend/DATABASE` 사본은 유지한다.
- 실사용 전 별도로 승인된 migration 적용과 실제 DB API 검증이 필요하다. 마스터의 분류 선택/저장 연결은 후속 범위다.

## 컴파일 호환 보완

- 재현: Java 8 API 기준에서 컨트롤러 135행의 `List.of()`를 찾을 수 없었다. 같은 메서드의 `Stream.toList()`도 Java 8에서 지원하지 않는다.
- 원인: `backend/pom.xml`의 source/target은 1.8인데 새 컨트롤러가 Java 9/16 이후 API를 사용했다. 앞선 Maven 검증은 JDK 19에서 실행되어 source/target만으로 최신 JDK API 사용을 차단하지 못했다.
- 해결: 해당 메서드만 `Collections.emptyList()`와 `collect(Collectors.toList())`로 교체했다. 기존 메뉴 경로 분리·권한 동작, API/DB 계약, Maven/JDK 설정은 변경하지 않았다.
- 검증: 원래 메서드를 추출한 최소 재현에서 `javac --release 8`의 두 API 오류를 확인했다. 수정 후 같은 컴파일과 null/빈 경로/슬래시 중복/품목·거래처 경로 동작 검증이 통과했다. 백엔드 Maven 컴파일 및 분류 Controller 28 + Service 26 + Mapper 6, 총 60건도 통과했다.
- 범위: 전체 프로젝트의 Java 8 호환성을 보증한 것이 아니라 이번 컨트롤러의 두 API 불일치를 보완했다. 화면 변경 및 DB 관련 변경은 없어 추가 스크린샷·DDL·DB MCP 조회는 해당하지 않는다.

### 분류 테스트 컴파일 호환 추가 보완

- 재현: `ClassificationApiControllerTest.java` 73행을 포함한 `List.of()` 9곳에서 같은 Java 8 API 오류가 발생했다. 앞선 수정은 운영 컨트롤러에 한정해 테스트 코드의 동일 문제를 놓쳤다.
- 해결: 단일 원소는 `Collections.singletonList()`, 여러 원소는 `Arrays.asList()`로 교체했다. 테스트의 입력값·검증 내용과 운영 동작은 변경하지 않았다.
- 회귀 검증: 실제 분류 Controller/Service/Mapper 테스트 소스 3개를 기존 컴파일된 운영 클래스 및 테스트 의존성과 함께 `javac --release 8 -encoding UTF-8 -proc:none`으로 컴파일했다. 수정 전 9개 오류를 재현했고 수정 후 성공했다. Maven의 동일 분류 테스트 60건도 실패·오류·누락 없이 통과했다.
- 한계: Java 8 API 기준의 해당 테스트 소스 컴파일과 현재 JDK의 Maven 실행을 확인한 것이며, 전체 프로젝트나 의존 라이브러리의 Java 8 런타임 호환성을 보증하지 않는다. DB 계약 및 화면 변경은 없다.

## F1Tree 직접 편집 전환

### 요청 및 변경

- 기존 분류 목록과 별도 입력 폼을 제거하고 F1Tree 하나에서 분류명·정렬순서·사용여부를 직접 편집하도록 변경했다. 기존 품목·거래처 관리 페이지의 설정 버튼과 팝업 진입점은 유지했다.
- 최상위/하위 추가 후 여러 행을 계속 편집할 수 있고 저장 버튼으로 변경 행들을 저장한다. 새 부모 아래에 새 자식을 작성하면 부모부터 생성하고 반환된 실제 ID로 자식을 연결한다.
- 품목 3단계·거래처 2단계, 비활성 부모 아래 추가 금지, 기존 메뉴 CREATE/UPDATE 권한, 변경 취소/닫기 및 새로고침의 미저장 보호를 유지했다.
- 공통 F1Tree 자체는 수정하지 않았다. 화면에서 우클릭 추가/복제/삭제와 Insert/Delete/Ctrl+D 행 작업을 차단하여 단계·권한·물리 삭제 정책을 우회하지 못하게 했다. 입력창 안의 일반 Delete 편집은 허용한다.

### 저장 및 오류 처리

- 기존 API의 단건 저장 계약을 유지하며 활성화/수정은 상위부터, 신규 생성은 부모부터, 비활성화는 자식부터 처리한다.
- 중간 실패 시 성공한 행을 저장 기준값으로 반영하고 미처리 행의 임시 부모 ID도 실제 ID로 갱신한다. 실패한 행과 미처리 행의 입력은 유지하며 재시도 시 이미 성공한 행을 중복 생성/수정하지 않는다.
- 모든 행 저장 성공 후 재조회만 실패한 경우 재조회 전까지 편집/저장을 차단한다.
- 여러 단건 API를 호출하므로 전체 변경의 원자적 저장은 보장하지 않는다. DB/백엔드 API 계약, 스키마 및 DDL은 이 전환에서 변경하지 않았으므로 추가 DB MCP 조회 대상은 아니다. 실제 DB 통합 실행은 검증하지 않았다.

### 검증 결과

- 기존 목록/입력 폼 구현에서 새 F1Tree 테스트가 실패함을 확인한 뒤 전환했다. 직접 편집, 접기/펼치기, 다중 행 저장, 임시 부모 연결, 부분 실패 재시도, 검증/권한/최대 깊이, 미저장 보호를 검증했다.
- 키보드 Delete의 선택 행 삭제 우회와 편집 중인 셀의 새로고침 보호 누락을 별도 실패 테스트로 확인하고 이 화면에서 차단/보완했다.
- Vitest 관련 5파일 92건 통과: 분류 다이얼로그 13건, 분류 서비스 4건, 품목관리 26건, 거래처관리 22건, 공통 F1Tree 27건. runner를 직접 실행하여 `--maxWorkers=2`를 적용했다.
- `npm run build` 통과. `npm run lint`는 기존 경고를 출력하고 종료 코드 0, 변경한 컴포넌트/테스트만 대상으로 한 lint는 경고 없이 통과했다.
- 기존 S-ERP Vite 서버 `http://127.0.0.1:4173`를 확인 후 재사용했다. 직접 실행한 서버가 아니므로 종료하지 않았다. 합성 API 응답만 사용한 Chromium에서 두 분류 종류 × 375/768/1280px의 직접 편집/저장 및 오류 복구를 모두 확인했고 브라우저 pageerror는 0건이었다.
- 375px 팝업은 전체 화면, 768px은 704px, 1280px은 900px 너비다. 페이지와 팝업 내용 영역에 의도하지 않은 가로 넘침이 없고 좁은 화면은 그리드 내부 가로 스크롤을 사용한다.

## 공통 다이얼로그 헤더 및 추가 버튼 배치

- 분류 팝업의 직접 MUI Dialog 구성을 기존 `CommonDialog` 사용으로 변경했다. 공통 컴포넌트 자체는 수정하지 않았다.
- 타이틀 바로 아래 공통 description에 안내 문구를 배치했다. 거래처는 `최대 2단계`, 품목은 기존 규칙대로 `최대 3단계`로 표시한다.
- 공통 헤더 우측 상단 X를 제공하고 하단 닫기와 같은 미저장 변경 확인 경로를 사용한다. 저장 중 X는 닫기 요청을 무시하고 하단 닫기는 비활성화한다.
- `최상위 추가`, `하위 추가` 버튼은 그리드 위 우측 정렬하며 모바일 줄바꿈을 허용한다. 팝업은 공통 md 크기(820px 기준, 테두리 별도)를 따르고 모바일 전체 화면은 유지한다.
- 새 헤더 요구사항이 기존 구현에서 실패함을 확인했다. 분류 다이얼로그 16건, frontend build, 변경 컴포넌트/테스트 lint가 통과했다.
- 기존 4173 Vite 서버를 재사용해 Chromium에서 품목/거래처 각각 375/768/1280px을 확인했다. 안내 문구가 타이틀 아래·본문 위에 있고 추가 버튼이 우측에 정렬되며 X가 헤더에 있음을 실제 좌표로 확인했다. X 닫기/미저장 취소, 편집/저장 및 오류 복구를 모두 확인했고 pageerror는 없었다.
- 실제 DB 호출 없이 합성 응답만 사용했다. 백엔드/API/DB 계약은 변경하지 않았다. 기존 서버는 종료하지 않았고 임시 harness는 저장소에서 제거했다.
