같은 테넌트의 사용/미사용 거래처를 모두 포함해 앞뒤 공백 제거 후 같은 이름을 중복으로 판단한다. 대소문자를 구분하고 수정 중 자기 행은 제외한다.

이전 작업에서 제거한 것은 저장 훅의 중복된 **필수 입력 검사**였다. 기존 거래처명 고유성 검사를 제거한 것이 아니며, 기존 백엔드/DB는 거래처코드만 중복 방지하고 있었다. 이번에 이름 고유성 정책을 추가했다.

## 구현

### F1-Grid 공통 옵션

```typescript
{
  field: 'customerName',
  headerName: '거래처명',
  required: true,
  validation: { unique: true },
}
```

- `createGridValidationContext`로 고유값 인덱스를 한 번 구성하고 기존 `validateGridRow`에서 검사한다.
- 폼 draft 적용과 그리드 `validate()`가 같은 helper를 사용한다.
- 비교 대상은 로드된 전체 활성 행과 신규/수정 행이다. 그리드 필터/row projection으로 숨긴 행도 비교에 포함하고 삭제 표시 행은 제외한다.
- null/undefined/빈 문자열/공백은 고유성 검사에서 제외해 기존 필수 검사에 맡긴다. 0/false는 고유값 비교 대상이다.
- 폼 적용 차단, 첫 오류 포커스, 오류 설명, 상단 실제 메시지, 빨간 입력/셀 테두리와 저장 차단을 기존 공통 오류 경로로 처리한다.
- 서버 검색으로 로드되지 않은 거래처는 클라이언트 검사 범위 밖이며 서버가 최종 확인한다.
- F1-Grid 마크다운·화면 가이드·API 참조를 함께 갱신했다.

### 백엔드

- 등록/수정 모두 이름 trim 후 tenant 범위에서 사전 검사한다. 사용여부 조건은 없으며 수정은 자기 ID를 제외한다.
- 이름 충돌은 `이미 사용 중인 거래처명입니다.`로 기존 입력 오류 흐름을 사용한다.
- 신규 name unique index의 PostgreSQL 충돌은 이름 오류로 분류하고 기존 코드 충돌 메시지는 유지한다.
- 배치의 두 번째 등록이 첫 번째 이름과 충돌하면 전체 트랜잭션이 rollback하는 테스트를 추가했다.
- OpenAPI 저장 요청의 거래처명 설명에도 고유성 정책을 반영했다.

### DB 변경 및 적용 상태

- [인덱스 SQL](../../../database/20261023/20261023_001_customer_name_unique.sql): `uq_tb_customer_info_tenant_name` on `(tenant_id, btrim(customer_name))`.
- [변경 이력/배포 절차](../../../database/20261023/20261023_001_change_customer_name_unique.md), [롤백](../../../database/20261023/20261023_001_rollback.sql).
- `docs/database`와 `backend/DATABASE`에 SQL/이력/롤백 사본을 동일하게 보관하고 누적 스키마에 적용 예정 상태로 기록했다.
- 기존 중복이 있으면 migration은 값 출력 없이 명시적 오류로 중단한다. 데이터 자동 삭제/수정 없음.
- **실제 DB에는 적용하지 않았다.** 인덱스 적용 전에는 백엔드 사전 조회만으로 동시 저장의 중복을 완전히 방어할 수 없다.
- 배포 전에 담당자의 기존 중복 확인·정리 승인 → SQL 적용 → 앱 배포가 필요하다. 이름 맞교환처럼 순차 배치의 중간 상태가 중복인 작업은 이번 범위에 포함하지 않았다.

## DB MCP 확인 근거

2026-10-23 기본 `s-erp-postgresql-readonly`에서 다음 순서로 직접 확인했다.

1. `list_tables`: 거래처 테이블 존재 확인.
2. `describe_table(tb_customer_info)`: 필드 metadata 확인.
3. `query_readonly`: `pg_indexes`에서 해당 테이블의 인덱스 정의만 조회, 최대 30개.

이 기본 DB에는 이름 unique index가 없고 코드 unique index 이름은 `uq_tb_customer_info_factory_customer_code`였다. 기본 DB의 `customer_name`은 nullable이며 이전 tenant 전용 문서와 다르므로 구분 기록했다. 실제 tenant를 추정하거나 다른 tenant DB를 조회하지 않았다. 업무 행·계정·인증 정보·연결 문자열은 조회하지 않았고 현재 데이터의 중복 유무는 미확인이다.

기존 모달 크기 테스트는 이전 작업에서 구현 전부터 실패한 `renders fixed modal regions, responsive grid span contracts, and final-save guidance`이며 변경하지 않았다. 이번 최종 실행은 이 테스트만 이름 필터로 제외했다. Maven과 Vitest를 동시에 실행했을 때 폼 테스트가 5초 기본 제한을 초과했으나, CPU 경합을 피한 단일 worker 재실행과 최종 통합 실행에서 통과했다.

검증 명령:

```powershell
# frontend
& .\node_modules\.bin\vitest.cmd run tests\f1-grid-unique-validation.test.tsx tests\customer-management-page.test.tsx tests\f1-grid-input-format-validation.test.ts tests\customer-number-input.test.ts tests\customer-management-service.test.ts tests\f1-grid-form-modal.test.tsx tests\f1-grid-docs.test.tsx '--testNamePattern=^(?!.*renders fixed modal regions)' --maxWorkers=1
npm run build

# backend
mvn '-Dtest=CustomerInfoServiceImplTest,CustomerInfoBatchServiceImplTest,CustomerInfoApiControllerTest,CustomerInfoSchemaTest' test
```

기존 4173 S-ERP Vite 서버를 재사용했다. 실제 계정 대신 독립 브라우저 컨텍스트와 가상 API fixture를 사용했고 실제 업무 데이터 저장은 수행하지 않았다. 브라우저는 검증 후 종료했고 기존 서버는 종료하지 않았다.
