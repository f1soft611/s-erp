## 반영 내용

- 업무 컬럼을 품목계정코드 → 품목코드 → 품목명 순서로 배치하고 No와 함께 왼쪽 고정했다.
- 품목계정코드는 `ITEM_TYPE`, 단위는 `ITEM_UNIT`, 품목유형은 `MATERIAL_TYPE`, 보관방법은 `STORE_METHOD`, 소비기한기준은 `EXPIRY_STATUS`를 사용한다.
- 목록 편집과 행 폼은 공통코드 이름을 표시하고 코드값을 저장한다. 기존 미등록 코드값은 보존한다.
- 품목분류는 컬럼 생성에서 제외하여 목록·행 폼·상세검색·컬럼 표시 메뉴에 노출하지 않는다. 기존 API/DB 값은 유지한다.
- 품목코드·품목유형·보관방법·소비기한기준은 가운데, 안전재고는 오른쪽 정렬했다.
- 소비기한 옵션은 조회된 허용 공통코드만 사용하고 기준별 숫자 검증과 단위 표시를 유지했다.
- 기존 저장 레이아웃이 새 기본 순서·고정을 덮어쓰므로 품목관리의 저장 키를 `co-master-material-grid-v2`로 변경했다. 기존 컬럼 너비/표시/고정 사용자 설정은 한 번 초기화된다.
- F1-Grid 문서의 품목관리 사용 설명을 갱신했다.

## 단위 미표시 원인과 실제 반영 확인

초기 실행 중인 백엔드는 이전 Mapper를 사용해 기존 세 그룹만 반환했다. 변경 소스에는 `ITEM_TYPE`, `ITEM_UNIT`을 추가했지만 Java 서버의 Mapper가 재로딩되지 않아 실제 단위 목록이 비어 있었다.

사용자가 직접 백엔드를 재시작한 후, 샘플 옵션 응답 없이 실제 `GET /api/v1/co/master/materials/options`에서 다섯 그룹과 `ITEM_UNIT` 상세 항목 2개가 반환됨을 확인했다. 실제 등록 폼의 단위 select에는 빈 선택 1개와 상세 항목 2개가 표시되었다. 폼에서 품목분류가 제외된 것도 확인했다. 실제 업무 데이터의 저장은 실행하지 않았다.

## 스크린샷과 검증 한계

업무 데이터 노출을 방지하기 위해 캡처는 품목 목록 응답만 가상의 샘플 행으로 대체하고 공통코드는 실제 API를 사용했다. 실제 API/등록 폼 확인과 샘플 화면 캡처는 별도 검증이다. 캡처 후 모든 응답 대체를 해제하고 실제 화면으로 복원했다. 실제 데이터 행을 캡처 파일에 남기지 않았다.

통합 브라우저의 캡처 동작은 viewport를 축소하여 PNG의 실제 렌더링 크기가 요청한 viewport와 달라졌다. 따라서 아래 파일은 화면 구성 참고용이며 정확한 375/768/1280px 시각 검증의 완전한 증거로 간주하지 않는다. 해당 세 CSS 너비에서의 페이지 가로 넘침은 캡처 전에 DOM 치수로 별도 확인했다. 캡처 과정에서는 좁아진 화면의 검색/헤더 줄바꿈이 관찰되었으며, 이번 변경 범위를 벗어나는 공통 레이아웃 수정은 하지 않았다.

## DB 및 변경 범위

기본 읽기 전용 MCP에서 `list_tables` → `describe_table(tb_common_code_group/tb_common_code_item)` → 제한된 그룹 코드/명칭 조회를 수행했다. 다섯 공통코드 그룹이 존재함을 확인했으며 tenant 업무 행·인증 정보를 조회하거나 기록하지 않았다.

DB 스키마/데이터 변경은 없다. SQL·스키마 이력·롤백 추가는 필요하지 않다. 백엔드는 기존 옵션 Mapper의 그룹 조건만 확장했다. 작업 시작 전 존재하던 거래처 채번 결과 및 기안양식 변경은 이 작업에서 수정·커밋하지 않았다.
