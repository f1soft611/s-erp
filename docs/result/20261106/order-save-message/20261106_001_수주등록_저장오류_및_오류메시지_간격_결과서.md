## 1. 변경 결과

- 수주등록 저장 오류 영역에 `PageMessageArea`의 compact 레이아웃을 적용했다.
- compact 메시지의 바깥 위·아래 패딩을 각각 8px로 통일하고, 오류가 있을 때 수주 입력 영역의 상단 패딩을 16px로 조정했다. 브라우저에서 오류와 인접 영역 사이 실제 공백이 세 화면 크기 모두 위·아래 24px로 동일함을 확인했다. 메시지 내용과 닫기 동작은 변경하지 않았다.

## 2. 저장 실패 조사

- 수주 저장은 트랜잭션 안에서 헤더와 상세를 저장한 뒤 AUTO 모드이면 자동 납품계획 생성 서비스를 호출한다.
- 제공된 stack trace는 계획 헤더/상세 INSERT 후 호출하는 `selectPlanByOrder`가 `null`을 반환해 예외가 난 것을 확인한다. 자동 계획 생성은 `void`이며 조회 결과를 호출자가 사용하지 않으므로, 이 사후 재조회는 저장 성공에 불필요한 의존이었다.
- 자동 계획 생성 경로를 공통 삽입/검증 로직으로 분리해 모든 헤더·상세 INSERT ID가 정상일 때 별도의 조회 없이 반환하도록 수정했다. 수동 납품계획 생성은 화면 응답에 계획 데이터를 써야 하므로 기존 재조회 및 상세 반환을 유지한다.
- 회귀 테스트는 자동 생성에서 초기 중복 확인용 조회만 수행되고, 사후 조회가 null이어도 생성이 정상 종료되는지 검증한다. 테스트는 수정 전에 제공된 예외와 동일한 `IllegalStateException`으로 실패했으며 수정 후 통과했다.
- 왜 해당 런타임에서 조인 조회가 비었는지까지는 미확정이다. tenant 전용 읽기 전용 MCP에서 `tb_sales_order_hd` 및 `tb_sales_delivery_plan_hd` 메타데이터를 찾지 못했고, 실제 서버 연결 DB를 확인할 수 없었다. DDL 또는 실제 업무 데이터를 조회/변경하지 않았다. 자동 생성 경로는 해당 표시용 재조회 결과에 더 이상 의존하지 않지만, 별도의 계획/현황 조회 문제가 발생하면 런타임 DB 메타데이터와 비민감 진단 로그가 필요하다.

## 3. 검증 및 산출물

- Vitest: 자동 계획 생성/수주 서비스/계획 Mapper 테스트 통과. 수주 저장 오류의 compact 적용 테스트와 공통 compact 여백 테스트 통과.
- Frontend build 통과.
- 브라우저에서 오류 표시를 합성 API 응답으로 재현해 375/768/1280px에서 측정했다. 세 폭 모두 위·아래 실제 공백 24px, 페이지 가로 넘침 없음.
- `shows save failure and retains all entered values` 테스트가 날짜를 고정해두던 기존 기대값을 화면 초기 날짜 비교로 바꿔 실행일과 무관하게 검증하도록 수정했다.
- 수주등록 및 알림 테스트 전체 파일을 함께 실행했을 때 23개 통과, 기존 저장 후 재조회/삭제 테스트 2개가 15초 제한으로 timeout됐다. 두 테스트는 각각 독립 실행해 통과했고, 오류 간격 변경 테스트도 포함 실행해 통과했다.
