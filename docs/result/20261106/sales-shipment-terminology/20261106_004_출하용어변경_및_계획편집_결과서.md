# 출하 용어 변경 및 출하계획 편집 결과서

## 구현 결과

- 영업관리 메뉴와 출하 등록/현황 및 출하계획 등록/현황의 화면 문구, 정책 안내, 백엔드 오류·성공 메시지를 출하 용어로 통일했다.
- `AUTO` 테넌트의 출하계획 메뉴를 권한 필터링 이후에도 노출하고, 인증 테넌트 기준 주문-계획 조회 API로 자동 계획을 불러와 기존 계획 ID와 상세를 유지한 채 `PUT` 수정한다. 자동 계획을 찾지 못하면 신규 `POST`로 대체하지 않는다.
- `MANUAL` 신규 계획 생성은 기존 `POST` 경로를 유지하며, 계획 조회·현황·수정은 두 운영 모드에서 가능하다.
- AUTO 수주 수정은 기존 계획 일자/수량을 보존하고 신규 수주 상세에만 초기 계획을 추가한다. 계획 합계보다 수주수량을 낮추는 수정은 HTTP 409로 거부한다.
- 메뉴 코드·URL·권한 구조, API/JSON 필드, DB 식별자와 정책 코드/값/타입은 유지했다.

- 실제 DB에는 SQL을 적용하지 않았다. MCP에서 테이블 목록과 `tb_menu`, `tb_system_policy` 컬럼 메타데이터만 확인했으며, 업무 데이터 행은 조회하지 않았다.

## 검증

| 검증 | 결과 |
|---|---|
| 프론트엔드 납품/계획 회귀 테스트 | 통과, 20 tests |
| 백엔드 계획·주문·출하·메뉴·SQL 계약 테스트 | 통과, 74 tests |
| 프론트엔드 `npm run build` | 통과 |
| 변경 영역 `oxlint` | 종료 코드 0. Fast Refresh 및 기존 effect set-state 경고 4건 |
| Java 8 API 호환 컴파일 | 통과, Maven `release 8` clean compile |
| 실제 브라우저 | 375/768/1280px 통과, 가로 overflow 및 런타임 오류 없음 |
| AUTO 계획 편집 브라우저 흐름 | 기존 계획 값/번호 로드 후 `PUT` 수정, 신규 `POST` 없음 |

브라우저 확인은 4173 포트에서 이미 실행 중이던 S-ERP Vite 서버를 재사용했고, API 응답은 합성 검증 데이터로 처리했다. 기존 서버는 종료하지 않았다.
