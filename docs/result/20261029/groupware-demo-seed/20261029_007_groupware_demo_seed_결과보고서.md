추가형 SQL과 보호 조건이 있는 롤백 SQL을 작성했다. 사용자 요청의 모호한 교체 범위는 기존 업무를 보존하는 데모 추가로 한정했다. **현재 연결 DB에는 적용하지 않았다.**

| 구분 | 생성 수 |
| --- | ---: |
| 공지사항 | 8 |
| 기안/업무연락/지출결의/근태신청 문서 | 12 |
| 결재/참조선 | 35 |
| 일반 댓글·대댓글 | 57 (대댓글 19 포함) |
| 시스템 이벤트 | 37 |

제목은 `[데모]`로 구분하며 본문에는 시연용 가상 정보임을 명시했다. 생산·구매·출하·재고·안전교육 등의 흐름에 맞는 본문과 대화를 구성했다. 문서 상태 6개, 문서 유형 4개를 포함한다. 완료 확인 댓글은 최종 승인 뒤에 생성된다.

계정·권한·비밀번호·거래처·품목·수주는 수정하지 않는다. 자료실 파일은 실제 저장소 업로드가 필요해 가짜 파일/빈 자료실 글을 만들지 않았다. UI/API/스키마 변경은 없으며 누적 스키마 문서의 구조 항목은 변경하지 않았다.

## 파일

`backend\DATABASE\20261029`와 `docs\database\20261029`에 동일한 다음 3개 파일을 보관했다.

- `20261029_003_seed_groupware_demo.sql`
- `20261029_003_rollback_groupware_demo.sql`
- `20261029_003_change_groupware_demo.md`

실행자는 psql에 대상 테넌트와 해당 테넌트의 활성 사용자 3명의 user ID를 전달한다. DB 접속 정보나 사용자 값은 문서에 저장하지 않았다. 최초 생성 이후 실제 상호작용이 있는 데이터의 일괄 교체는 지원하지 않는다.

## MCP 확인 근거

기본 `s-erp-postgresql-readonly`에서 `list_tables` → 대상 `describe_table` → 필요한 `pg_constraint` 메타데이터 조회 순서로 확인했다.

- `tb_board_type`, `tb_board_post`
- `tb_electronic_approval_main`, `tb_electronic_approval_line_info`
- `tb_common_comment`, 댓글 좋아요의 FK/유니크 제약
- `tb_user`, `tb_login_account`, `tb_id_sequence`, `tb_common_file`

테넌트/계정/업무 데이터 행은 조회하거나 출력하지 않았다. Mapper/Service를 대조해 기안자·댓글 작성자의 login code와 결재선 참여자의 user ID 차이, 업무연락의 참조 전용 발송 처리를 반영했다.

## 검증

Node 내장 테스트에서 PGlite를 별도 메모리 DB로 사용했다. 의존성은 세션 아티팩트 경로에만 설치했고 애플리케이션 manifest/lockfile은 변경하지 않았다.

```powershell
# PGLITE_MODULE_PATH에 임시 설치한 모듈의 절대 경로를 지정한 세션에서 실행
node --test tools\tests\test_groupware_demo_seed.cjs tools\tests\test_customer_material_sample_seed.cjs
```

최종 결과: **11개 테스트 통과, 실패/생략 0** (신규 5, 기존 시드 회귀 6).

- 기존 공지 보존, 대상별 생성 건수, 유형/상태/대기 결재선, 대댓글 부모/테넌트/시각 일치.
- 중복 재실행 차단, 다른 테넌트의 동일 시드 보존, 롤백 재실행 무변경.
- 없는/비활성 테넌트, 타 테넌트 사용자, 같은 사용자 중복, 비활성 사용자/계정, 누락 분류, 잘못된 날짜·인자 실패.
- 댓글 INSERT 강제 오류 후 부모 데이터/문서번호 카운터까지 원자적 롤백.
- 실제 댓글·좋아요·첨부·조회·문서 고정·문서/댓글 수정·마커 누락 시 자동 삭제 거부.
- 결재선 행 수를 유지한 수정도 최초 지문과 달라 롤백 거부.
- 기존 문서번호가 카운터보다 커도 충돌 회피, 롤백 후 카운터 유지.
- 최초 SQL 누락 실패를 먼저 확인했다. 추가 회귀 테스트에서 결재선 편집 보호와 완료 이전 확인 댓글 문제를 재현한 뒤 수정했다.
- 양쪽 SQL/변경 이력은 바이트 동일성 테스트로 확인했으며 SHA-256도 대조했다. `git diff --check`를 수행했다.

## 한계와 안전성

- 현재 환경에 psql/서버 PostgreSQL CLI가 없어 psql 메타명령은 정적으로 확인하고 SQL 본문만 격리 PostgreSQL 엔진에서 실행했다. 실제 psql 연결/운영 DB/API/브라우저 적용을 검증한 것은 아니다.
- 신규 계정·실제 개인정보·첨부파일 오브젝트는 생성하지 않았다.
- 화면 변경이나 실DB 적용이 없으므로 **화면 스크린샷은 해당 없음**이다. 테스트 화면을 실DB 적용 증거로 제시하지 않았다.
- 롤백은 보수적으로 실제 조회 이력만 있어도 중단한다. 관계 테이블 전체의 쓰기를 짧게 잠그므로 유지보수 시간에 실행해야 한다.
- 직접 SQL로 수정일·마커까지 조작한 변경을 완전히 탐지하는 백업/감사 도구는 아니다. 자동 롤백이 거부되면 강제 삭제하지 않고 별도 검토한다.
- 관련 없는 기존 스테이징/작업 파일을 변경·되돌리거나 커밋하지 않았다.
