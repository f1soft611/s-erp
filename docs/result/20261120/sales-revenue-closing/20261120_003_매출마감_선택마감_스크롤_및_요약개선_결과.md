# 매출마감 선택 마감 및 화면 개선 결과

## 작업 결과

- 매출마감관리 메뉴(`SALES_REVENUE_CLOSING`, `/sales/revenue/revenue-closing`)와 `READ`/`CREATE`/`EXCEL` 권한 seed 및 롤백 스크립트를 추가했다.
- 매출마감은 별도 테이블을 만들지 않고 출하 상세의 `revenue_closed_at`/`revenue_closed_by`로 기록한다. 같은 출하의 상세 행을 각각 선택·집계하고, 이미 마감된 행은 선택할 수 없다.
- `POST /api/v1/sales/revenue-closings/close`는 인증 tenant의 선택 상세 ID와 서버 기준일을 받아 원자적으로 처리한다. 이미 거래명세서가 있는 상세는 중복 발행하지 않고 마감하며, 새 발행 상세는 거래처별로 묶는다.
- 거래명세서 상세의 `sales_delivery_detail_id`로 원본 출하 상세를 연결한다. 일반 발행은 같은 거래처의 여러 출하 상세를 선택할 수 있고, 출하 등록 AUTO 발행은 기존처럼 출하 전체 상세를 대상으로 한다. 거래명세서 발행만으로 매출마감 상태를 변경하지 않는다.
- 요약 영역을 조밀한 거래처별 행으로 재구성하고, 데스크톱의 그리드와 요약 목록 및 좁은 화면의 요약 목록에 독립 스크롤을 적용했다. 요약 기준 라벨도 상세 행 기준으로 표시한다.

## DB 확인 및 적용 상태

- 읽기 전용 PostgreSQL MCP의 `list_tables`/`describe_table` 및 제한된 카탈로그 조회로 현재 계약을 확인했다. 현재 `tb_sales_delivery_dt`에는 매출마감 컬럼이, `tb_sales_statement_dt`에는 원본 출하 상세 ID 컬럼이 없으며, 활성 거래명세서의 기존 유일 인덱스는 `(tenant_id, sales_delivery_id) WHERE use_at='Y'`이다.
- `docs/database/20261120`과 `backend/DATABASE/20261120`의 001 메뉴 seed/rollback/change record 및 002 스키마 변경/rollback/change record는 모두 byte-identical이다.
- seed와 스키마 변경 SQL은 검토용으로만 작성했으며 실제 DB에는 실행하지 않았다. MCP 조회에서 tenant 데이터 행이나 식별자를 조회·기록하지 않았다.

## 검증

- Frontend 집중 테스트: 6개 파일, 246개 테스트 통과 (`sales-revenue-closing-page`, `revenue-closing-service`, `sales-statement-page`, statement print 2개, `f1-grid`).
- `npm run build`: 통과.
- `npm run lint`: 종료 코드 0. 비차단 React lint 경고가 출력되었으며 오류는 없었다.
- `npm run build`: 성공. 기존 대형 번들 크기 경고가 출력되었으나 빌드는 정상 완료했다.
- Backend 집중 테스트: 20개 테스트 통과 (`RevenueClosingApiControllerTest`, `RevenueClosingServiceTest`, `SalesStatementMapperTest`, `SalesStatementSchemaTest`, `SalesStatementServiceTest`).
- Java 8 API 호환성: `mvn clean -Dmaven.compiler.release=8 -DskipTests compile`로 운영 코드 637개 파일을 `javac --release 8`로 재컴파일해 통과했다.
- 브라우저 검증은 비민감 synthetic data(30개 상세, 15개 거래처)만 사용했다.
