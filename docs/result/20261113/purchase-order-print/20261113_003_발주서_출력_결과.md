# 20261113_003 발주서 출력 결과

## 커밋 제목·내용 (복사용, 커밋은 만들지 않음)

제목: `구매자재 발주서 출력(미리보기·인쇄·출력 기록) 추가`

내용:
- 발주서 미리보기·인쇄 화면 추가(사용자 제공 PDF 양식, A4 한 부, 행별 납기일, 한글 금액, VAT 표기)
- 발주 저장 시 회사·구매처·발주자 정보를 복사(스냅샷)하는 컬럼과 SQL 추가, 출력 데이터·출력 기록 API 추가
- 발주현황 상세 패널·수정 다이얼로그에 `출력`, 목록에 출력상태 추가, 취소된 발주는 출력 불가
- 한글 금액 변환을 공통 위치(`shared/utils`)에 추가

## 작업 범위

- DB: `20261113_006` 발주 헤더에 스냅샷·출력 컬럼 추가(적용·롤백·변경이력, 두 경로 사본), `db-schema.md`.
- 백엔드: 저장 시 스냅샷 복사(`insertOrderHeader`를 `INSERT … SELECT`로 변경), `GET /purchase-orders/{id}/print`, `POST /purchase-orders/{id}/print-mark`, 현황 목록 `printAt`.
- 프론트: `shared/utils/amountInKorean.ts`, `pages/materials/order/print`(미리보기·인쇄 컴포넌트, 인쇄 CSS, 서비스, 타입), 상세 패널 `출력` 메뉴, 수정 다이얼로그 `출력` 버튼, 목록 출력상태 컬럼.

## 영업(거래명세서) 규칙 적용 결과

사용자 확정: 스냅샷 보관 ○, 납기일은 행마다, 취소된 발주 출력 불가, 인쇄 버튼 클릭을 출력으로 기록, 한글 금액은 공통 위치.

- 영업과 같게: 상세 패널 더보기 `출력`, 수정 다이얼로그 하단 `출력`(저장하지 않은 변경이 있으면 비활성), 미리보기 → `인쇄`(브라우저 인쇄), 저장 시점 정보 스냅샷과 스냅샷이 없는 기존 건은 현재 정보로 출력, 저장된 금액을 그대로 출력(재계산 없음), 합계가 정수일 때만 한글 금액, 페이지 분할 시 매 페이지 같은 합계.
- 영업과 다르게: 한 장에 **한 부**, 납기일은 행마다, VAT 표기 4종(`VAT포함`/`VAT별도`/`영세`/`면세`), 출력 기록(`print_at`, `printed_at`, `printed_by`).

## 구현 요약

- 출력 양식: 사용자 제공 `발주서.PDF`와 같은 구성(제목, 일련번호·수신·참조·TEL·FAX, 회사 로고·사업자등록번호·회사명/대표(직인)·주소·담당/연락처, 금 액 줄, 품목 표 24줄, 하단 수량·공급가액·VAT·합계). 값이 없으면 `-`, 로고·직인은 있을 때만 이미지를 표시한다.
- 스냅샷: 발주 저장 시 서버가 같은 SQL 문장에서 `tb_tenant`·`tb_customer_info`·`tb_user` 값을 복사한다. 출력 조회는 `COALESCE(스냅샷, 현재 정보)`다. 발주 수정·취소는 스냅샷을 바꾸지 않는다.
- 출력 기록: `인쇄` 클릭 시 `window.print()` 후 `print-mark` 호출. 기록 실패는 인쇄를 막지 않고 화면에 안내한다. 성공하면 목록의 출력상태가 `출력`으로 바뀐다. 취소된 발주는 출력 데이터 조회와 기록이 모두 409다.

## 브라우저에서 찾아 고친 문제 (중요)

- **영업 인쇄 CSS와의 충돌**: 영업 `statement-print.css`는 앱 전체에 `body > :not(.statement-print-host) { display: none !important }`를 걸어 둔다(영업 파일이 대시보드 번들에 항상 포함되기 때문). 그대로 두면 **발주서 인쇄 시 내용이 전부 숨겨져 빈 페이지**가 나온다. 단위 테스트로는 잡히지 않았고 A4 PDF를 만들어 보니 빈 페이지(957바이트)여서 발견했다.
- 해결(영업 파일은 수정하지 않음): 미리보기가 열려 있는 동안만 `body`에 `order-printing` 클래스를 붙이고, 그때만 `html body.order-printing > .order-print-host { display: block !important }`로 영업 규칙을 이긴다. 발주서 인쇄가 아닐 때는 아무 규칙도 적용되지 않아 거래명세표 인쇄에는 영향이 없다. 수정 후 PDF는 한 건 1쪽, 30행은 2쪽으로 정상 출력된다.

## DB 확인

- `s-erp-postgresql-readonly` MCP로 `tb_tenant`(회사 정보·직인·로고), `tb_customer_info`(연락처·담당자), `tb_user`(이름·휴대폰번호), 영업 `tb_sales_statement_hd` 스냅샷 컬럼 구조를 확인했다.
- **`20261113_006`은 실제 DB에 적용하지 않았다. 사용자가 실행해야 한다.** 코드는 발주 저장 때 새 컬럼에 값을 넣으므로 **SQL을 실행하기 전에는 신규 발주 등록이 실패한다.** 적용 후 MCP로 컬럼을 다시 확인해야 한다(아직 미확인).

## 검증 결과

- 백엔드 `materials` 테스트 86개 통과(출력·기록 서비스 4, 스냅샷 복사·COALESCE·출력 기록 SQL 매퍼 2, 006 스크립트 정적 1 포함). 운영 코드 Java 8 컴파일 통과(JDK 1.8.0_201).
- 프론트 구매 관련 64개 통과(출력물 9, 현황 화면 출력 흐름 6 포함), 영업 거래명세서 테스트 5개 통과, `npm run build` 통과.
- 브라우저 `node tests/purchase-order-print.browser.mjs`: 합성 응답으로 375/768/1280px에서 미리보기(1페이지 / 2페이지), 한글 금액·VAT·행별 납기일, `인쇄` 클릭 시 인쇄 호출과 출력 기록 API 호출을 확인했고 페이지 오류가 없다. 1280px에서 인쇄 CSS로 A4 PDF를 생성해 페이지 수(1쪽 / 2쪽)와 인쇄 화면을 확인했다.

### 검증하지 못한 항목

- `mvn test` 전체는 JDK 8 환경 제약으로 돌리지 못했다(`materials` 테스트만 JDK 25로 직접 실행).
- 실제 서버·DB에서 스냅샷 복사와 출력 기록을 확인하지 못했다(006 미적용). 매퍼 SQL은 정적 테스트로만 검증했다.
- 실제 프린터 출력과 브라우저 인쇄 대화상자는 확인하지 못했다(헤드리스는 `window.print`를 호출만 기록).
- 회사 로고·직인 이미지가 있는 실제 데이터의 출력은 확인하지 못했다(합성 데이터는 이미지 없음, 이미지 표시는 단위 테스트로만 확인).

## 영업 담당자 전달 내용

1. **공통 한글 금액 함수**: `frontend/src/shared/utils/amountInKorean.ts`에 영업 `StatementPrint`와 같은 변환 규칙의 함수를 만들었다. 같은 입력에 같은 결과이므로 `StatementPrint.tsx`의 `amountInKorean`을 지우고 `import { amountInKorean } from '../../../shared/utils/amountInKorean'`로 바꾸면 된다(동작 변화 없음).
2. **인쇄 CSS 전역 규칙 주의**: `statement-print.css`의 `@media print { body > :not(.statement-print-host) { display: none !important; } }`는 앱 전체에 적용되어 다른 화면의 인쇄 영역도 숨긴다. 발주서는 `body.order-printing`과 더 구체적인 선택자로 우회했다. 다른 화면도 인쇄를 추가하려면 같은 충돌이 생기므로, 이 규칙을 `body.statement-printing` 같은 인쇄 중 전용 클래스 조건으로 바꾸는 것을 권한다(영업 담당자 판단).
