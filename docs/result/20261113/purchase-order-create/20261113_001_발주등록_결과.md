## 구현 요약

- 발주 1건 = 구매처 1곳 · 통화 1종. 확정 행의 잔량(확정수량 − 유효 발주 수량 합)을 기본 수량으로 불러오고, 마감(`order_close_at`)·취소된 확정은 후보에서 제외한다.
- 확정 선택 창: 첫 체크 행의 구매처를 칩으로 고정하고 다른 구매처를 체크하면 선택에서 자동 제외한다(F1Grid가 행 비활성을 지원하지 않아 사양과 다르게 구현). 칩 ✕로 초기화.
- 확정과 다른 행(구매처·단가·수량 초과·납기일·창고)은 "확정 대비" 열에 경고만 표시하고 저장은 막지 않는다.
- 직접 발주: 구매처를 먼저 고른 뒤 품목을 추가한다. 발주구분·사용용도를 헤더에서 선택하고, 저장 시 같은 트랜잭션에서 MR 1건 + MC 1건을 자동 생성해 행에 연결한다. 한 발주서는 한 가지 출처만 허용한다.
- 부가세: 과세/영세/면세(공통코드) + 포함/미포함(과세만 선택, 영세·면세는 미포함 고정). 행에 공급가·세액·합계를 저장하고 헤더는 행 합이다. 세액은 직접 수정할 수 있다(영세·면세 제외).
- 검사대상은 `tb_material_info.inspect_type`(`Y`만 검사)을 기본값으로 읽고 행에서 수정한다. 재고량은 응답·그리드 필드만 확보했고 값은 비어 있다. 출력상태(`print_at`)와 입고대기마감(`receipt_close_at`)은 컬럼만 확보했다.
- `PurchaseRequestConfirmService.cancelConfirm`: 유효한 발주 행이 있는 확정은 409로 취소를 막는다.

## DB 확인

- `s-erp-postgresql-readonly` MCP로 `list_tables`와 `describe_table`(구매요청 헤더/상세, 확정 헤더, 거래처, 창고, 단가)을 확인했다. 발주 테이블은 아직 없었고, 요청 상세에 `order_type`·`use_type`·`order_close_at`이 이미 있음을 확인했다. 기존 메뉴(`MATERIALS_*`) 정렬값도 조회했다. 행 데이터는 기록하지 않았다.
- **SQL은 실제 DB에 적용하지 않았다.** 사용자가 `20261113_001` → `_002` → `_003` 순서로 직접 실행해야 한다. 적용 후 MCP로 테이블·메뉴·공통코드를 다시 확인해야 한다(아직 미확인).

## 검증 결과

- 백엔드(구매요청·확정·발주 `materials` 59개): 모두 통과. 이번 추가분은 금액 계산 8, 서비스 9, 매퍼 5, 스키마 스크립트 정적 5, 확정 취소 보강 1이다.
- 운영 코드 Java 8 컴파일: JDK 1.8.0_201로 `mvn compile` 통과(Java 9+ API 미사용).
- 프론트 `tests/purchase-order-create.test.tsx` 14개, 기존 구매요청 테스트 포함 35개 통과, `npm run build` 통과.
- 브라우저 `node tests/purchase-order-create.browser.mjs`: 합성 응답으로 375/768/1280px에서 구매처 고정 → 불러오기 → 부가세 면세 전환(합계 30,360 → 27,600), 페이지 오류 없음. 4173 포트의 기존 개발 서버를 재사용했고 종료하지 않았다.

### 검증하지 못한 항목 (정직한 기록)

- 이 환경에는 JDK 8 외에 JDK 17이 없어 `mvn test` 전체를 돌릴 수 없었다. 대신 JDK 8로 운영 코드를 컴파일하고, JDK 25(VS Code 확장 번들)로 `materials` 테스트만 직접 컴파일해 실행했다. 전체 백엔드 테스트는 미실행이다.
- SQL을 PGlite 등으로 실제 실행해 보지 못했다(패키지 설치 권한 없음). 정적 테스트와 사양 대조만 했다. 사용자 적용 시 오류가 나면 알려 주길 바란다.
- 실제 서버·DB 연동(저장 후 MR/MC 생성, 확정 취소 거부)과 직접 발주 품목 추가 화면은 브라우저로 확인하지 못했다.
