## 작업 범위

- DB: `20261113_005` 발주현황 메뉴(`MATERIALS_ORDER_STATUS`, `/materials/order/order-status`, 발주관리 그룹 아래 정렬 20)와 `20261113_004` 메뉴 그룹 재구성(구매요청관리 / 발주관리) seed·롤백·변경이력(두 경로 사본). 스키마 변경은 없다.
- 백엔드: `materials/order/status`(목록), `materials/order/create`에 수정(`PUT /purchase-orders/{id}`)·취소(`POST /purchase-orders/{id}/cancel`) 추가, 단건 조회에 확정 기준값 추가.
- 프론트: `pages/materials/order/status`(목록·훅·서비스·상세 패널·편집 다이얼로그), `PurchaseOrderCreatePage` view/edit 모드, 대시보드 `order-status` 연결.

## 구현 요약

- 구매요청현황과 같은 구조: 빠른 검색 + 상세검색(발주일 기간 필수, 기본 최근 1개월), 같은 발주서 헤더 열 병합, 발주번호 링크 → 상세 패널 → 조회/수정 다이얼로그. 취소된 발주도 상태 컬럼으로 조회된다.
- 수정 가능 항목: 발주일, 부가세구분·여부, 비고, 행의 수량·단가·납기일·창고·검사대상·세액·비고. 구매처·통화·출처·품목은 고정이고 새 행 추가는 없다.
- **행 삭제**: 수정 다이얼로그에서 행을 체크해 [선택 행 빼기] 후 저장한다. 모든 행을 빼는 요청은 거부(발주 취소 사용). 삭제 후 행번호는 1부터 다시 매긴다.
  - 확정 불러오기 발주: 확정 행은 건드리지 않고, 잔량이 유효 발주 합으로 계산되어 자동 복원된다.
  - 직접 발주: 삭제한 행의 구매요청 상세도 함께 지우고, 수정한 행은 구매요청·확정 값을 맞추며, 확정 합계와 요청 상태를 다시 계산한다.
- **발주 취소**: 헤더 `use_at='N'`(이력 보존). 직접 발주는 자동 생성된 확정(MC)의 행을 초기화해 확정을 취소하고 구매요청(MR)을 삭제 처리한다. 취소된 발주는 수정·재취소가 409다.
- 수정·취소 권한은 발주등록 메뉴의 UPDATE 권한을 쓴다.

## DB 확인

- 이번 작업은 스키마 변경이 없고 메뉴만 추가한다. 이전 단계에서 `s-erp-postgresql-readonly` MCP로 테넌트 1의 `MATERIALS_*` 메뉴 정렬(10, 15, 20, 30)을 확인했고 `ORDER_STATUS` 역할 권한 복사 방식은 구매요청현황(`20261112_003`)과 같다.
- **`20261113_004`·`_005`는 실제 DB에 적용하지 않았다.** 사용자가 실행해야 하고, 적용 후 MCP로 메뉴·권한을 다시 확인해야 한다(아직 미확인).

## 검증 결과

- 백엔드 `materials` 테스트 74개 통과. 이번 추가분은 수정·취소 서비스 7, 현황 서비스·매퍼 3, 매퍼 수정·취소 SQL 1, 스키마 스크립트 004 정적 1이다.
- 운영 코드 Java 8 컴파일: JDK 1.8.0_201로 `mvn compile` 통과.
- 프론트 `tests/purchase-order-status.test.tsx` 7개, 등록 화면 포함 구매 관련 42개 통과, `npm run build` 통과.
- 브라우저 `node tests/purchase-order-status.browser.mjs`: 합성 응답으로 375/768/1280px에서 목록 → 상세 패널 → 수정 다이얼로그 → 행 빼기(공급가 12,000으로 재계산), 페이지 오류 없음. 4173 포트의 기존 개발 서버를 재사용했고 종료하지 않았다.
  - 병합 셀의 발주번호 링크는 Playwright 클릭 가능성 검사에 걸려 좌표 클릭으로 열었다. 사용자 동작과 같은 실제 마우스 클릭으로 패널이 열림을 확인했다.

## 추가 작업: 입고대기마감 (2026-11-13)

- 발주 행의 `receipt_close_at`을 바꾸는 **마감 전용** 기능을 발주현황에 추가했다(별도 메뉴·화면 없음). MES는 참고용이며 발주대기마감은 발주 화면에 두지 않는다.
- 상세 패널 더보기 메뉴: `자세히보기`, `수정`, `입고대기마감`(정상 발주 + 발주등록 UPDATE 권한). 마감 다이얼로그는 마감 체크박스 외 전부 읽기 전용이고 `저장`·`닫기`만 있다. 체크를 풀고 저장하면 마감이 취소된다. 마감과 수정은 분리되어 마감하면서 값을 고칠 수 없다.
- 저장은 `PUT /api/v1/materials/purchase-orders/{id}/receipt-close`로 마감 값만 갱신한다(수량·단가·금액·삭제·확정 동기화 경로를 타지 않음). 값이 같은 행은 건드리지 않고, 취소된 발주(409)·없는 행·중복·`Y/N` 외 값(400)은 거부한다.
- 발주현황 목록에 입고대기마감 컬럼(마감/-)을 조회용으로 추가했다. 수정 다이얼로그에서는 마감 컬럼이 읽기 전용이다.
- 저장된 발주를 보는 그리드는 컬럼 배치 저장 키를 등록 화면과 분리했다(`materials-purchase-order-detail-grid-v1`). 같은 키를 쓰면 등록 화면이 저장한 배치 때문에 새 컬럼이 숨겨지는 문제를 브라우저에서 확인해 고쳤다.
- 마감된 행을 가입고 후보에서 제외하는 처리는 가입고등록 작업에서 한다. 스키마 변경과 SQL 변경은 없다.

추가 검증: 백엔드 `materials` 테스트 79개 통과(마감 서비스 2, 매퍼 마감 SQL이 마감 컬럼만 바꾸는지 포함), 프론트 구매 관련 47개 통과, `npm run build` 통과, 브라우저 375/768/1280px 통과(768px 이상에서 체크·저장 활성 확인, 375px는 고정 컬럼이 폭을 차지해 마감 컬럼이 가로 스크롤 밖이므로 화면 확인만 했다).
