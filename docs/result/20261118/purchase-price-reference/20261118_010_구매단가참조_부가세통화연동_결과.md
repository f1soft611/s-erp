# 20261118_010 구매 단가 참조 시 부가세구분·부가세포함·통화 연동 결과

관련: [작업지시서](../../../directions/20261118/20261118_010_구매단가참조_부가세통화연동_작업지시서.md) · [계획서](../../../plan/20261118/20261118_010_구매단가참조_부가세통화연동_계획서.md) · [상세사양서](../../../spec/20261118/20261118_010_구매단가참조_부가세통화연동_상세사양서.md) · DB [20261118_002](../../../database/20261118/20261118_002_change_purchase_request_dt_tax_type.md), [20261118_003](../../../database/20261118/20261118_003_change_item_partner_price_unit_price_optional.md)

## 변경 내용
- **DB**: `20261118_002` 확정 상세 `tb_purchase_request_dt`에 `tax_type`·`vat_included_at`(NULL 허용, 기존 데이터는 과세·미포함 취급), `20261118_003` 단가 `unit_price` NOT NULL 해제와 원화·외화 단가 중 하나 이상 CHECK. 두 스크립트 모두 적용 확인(MCP).
- **단가 저장 규칙(007 보강)**: 원화단가 또는 외화단가 중 하나만 있으면 등록(외화만 허용), 둘 다 없으면 400, 부가세포함은 과세일 때만(서버·화면·엑셀 검증), 단가 입력 화면에서 과세 외 구분을 고르면 부가세포함을 미포함으로 되돌림. 품목 기준·거래처 기준·엑셀 변환 로직과 필수 표시(*, 원화·외화 모두 표시 전용)를 맞춤.
- **단가 조회 API(`…/purchase-request-confirms/unit-price`)**: `taxType`, `vatIncludedAt`, `foreignUnitPrice`, `foreignCurrency` 추가. 기본 설정은 원화단가가 있으면 KRW + 원화단가, **외화단가만 있으면 외화통화 + 외화단가**. 거래처 일치 단가 → 기본단가 폴백은 그대로.
- **구매요청확정**: 확정 행에 부가세구분·부가세포함·통화 컬럼(선택 가능)을 추가하고, 구매처를 고르면 단가·통화·부가세구분·포함을 함께 설정한다(수정 가능). 통화를 단가의 외화통화로 바꾸면 외화단가로, KRW로 되돌리면 원화단가로 바뀌고, 그 밖의 통화는 단가를 비운다(단가를 조회한 행만). 저장 API가 부가세구분·포함을 검증·저장하고 조회·발주 후보 응답에 포함한다.
- **발주**: 확정 불러오기는 후보의 부가세구분·포함·통화로 헤더를 설정하고, 서로 다른 설정의 확정 건은 한 발주서에 담을 수 없게 막는다(통화는 기존 규칙). 직접 등록은 첫 품목의 단가 정보로 헤더 부가세구분·포함·통화를 정하고, 이후 품목의 단가 정보가 다르면 경고만 한다.
- **공통 그리드 수정**: 선택(select) 칸을 셀에서 바꿀 때 `onValueChange`가 호출되지 않고 값만 덮어쓰던 문제를 수정했다(`GridRow.tsx`, 사용자 칸만 호출하던 분기를 모든 선택 칸으로 확대). 이 때문에 통화 변경 시 단가 전환, 부가세구분 변경 시 부가세포함 되돌리기가 셀 편집에서 동작하지 않았다. 기존 선택 칸의 `onValueChange`(창고 지정 등)는 같은 값을 돌려주는 정의라 동작이 바뀌지 않는다. 테스트 추가(`f1-grid-select-value-change.test.tsx`, 수정 없이는 실패 확인).

## 검증
- 백엔드: 단가 저장(외화만·둘 다 없음·과세 외 포함), 조회 응답 기본 설정 3가지, 확정 저장 검증·저장값, Mapper 포함 관련 테스트 통과.
- 프론트: 단가 변환·엑셀·화면, 확정 행 통화 전환·부가세 규칙, 발주 후보 혼합 판단, 공통 그리드 선택 칸 테스트 통과, `tsc` 통과. 전체 실행 시 기존 실패(feed·menu·notice 등, 이전 기준선과 같은 파일)만 남고 새 실패는 없다. 전체 실행 중 보인 구매자재·영업 테스트 몇 건은 개별 실행에서 모두 통과(부하로 인한 일시 실패)했고, `page-initial-errors` 영업현황 1건은 이번 수정과 무관하게 같은 실패가 재현되는 기존 문제다.
- **실서버 API(실제 단가 데이터 등록 후)**: 단가 등록 규칙(둘 다 없음 400, 과세 외 포함 400), 조회 5가지(기본단가 폴백 과세·포함 1,100 KRW / 특별단가 1,200 / 영세 500 / 외화만 USD 7.25 / 원화 1,000 + 외화 USD 0.9), 구매요청 → 확정(과세·포함 1,100, 영세 500 한 확정, 외화단가만 USD 7.25 확정) 저장 후 재조회 값 일치, 확정 저장의 과세 외 포함 400, 발주 후보 응답에 확정 시 설정한 부가세·통화가 따라옴.
- **실브라우저(구매요청확정)**: 구매처 선택만으로 단가 1,100.00 · KRW · 과세 · 포함이 채워지고, 원화+외화 단가 품목의 통화를 USD로 바꾸면 단가 0.90, 금액 9.00으로 전환(스크린샷 `confirm-after-supplier`, `confirm-currency-usd`).
- **실브라우저(발주)**: 서로 다른 부가세 설정의 확정 건을 함께 선택하면 "부가세구분·부가세포함이 다른 확정 품목은 한 발주서에 담을 수 없습니다"로 차단. 과세·포함 확정 건을 불러오면 헤더가 과세·부가세 포함·KRW, 합계 11,000(포함 계산), 영세 확정 건은 영세·미포함·KRW, 합계 5,000. 직접 발주는 첫 품목(과세·포함 단가)을 추가하면 헤더가 과세·부가세 포함·KRW가 되고(합계 1,100), 설정이 다른 두 번째 품목(영세)을 추가하면 "단가 정보(부가세구분·부가세포함)가 발주서 설정과 다릅니다. 단가를 직접 확인해 주세요." 경고만 보이고 헤더는 바뀌지 않는다(스크린샷 `order-mixed-blocked`, `order-from-confirm-taxable`, `order-from-confirm-zero-rated`, `order-direct-first-item`, `order-direct-second-item-warning`).

## 테스트 중 생긴 데이터(삭제 기능 정리 전, 필요하면 단가 삭제로 정리)
- 품목 000030·000036·000033 매입 기본단가(오늘 적용), 000032 매입 외화단가만(USD 7.25), 000030 거래처 213231 특별단가.
- 구매요청 몇 건과 확정 몇 건(MC-20261118-0001~0003 등).

## 후속
- 직접 발주 헤더의 통화는 읽기 전용이라 통화 변경으로 외화단가로 바꾸는 흐름은 구매요청확정에만 있다.
- 단가 노출 권한 분리, 외화 환율 연동은 범위 밖이다.
