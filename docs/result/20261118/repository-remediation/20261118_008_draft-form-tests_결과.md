# 기안양식 테스트와 사용 해제 경로 복구 결과

- [계획서](../../../plan/20261118/20261118_008_draft-form-tests_계획서.md), [상세사양서](../../../spec/20261118/20261118_008_draft-form-tests_상세사양서.md).
- 기존 실패 6개 중 4개는 현재 `양식명` 입력을 과거 `구분명`으로 찾았다. 분류·주기 ID, 선택 사용자, 저장 요청과 미저장 상태 단언은 유지했다.
- 나머지 2개는 실제 진입점 회귀였다. 승인된 사용 해제 사양과 관리 훅의 `deletedRows → PUT useAt=N` 처리는 존재하지만 Grid가 행 삭제를 무조건 숨겼다.
- `allowDeleteRowInContextMenu`만 `canUpdate && !saving`으로 연결했다. 물리 삭제, DELETE 권한·API, 백엔드·DB 계약 변경은 없다.

## 회귀 검증

`22bd60b8` 프론트 소스 오버레이와 복구 변경, 잠금 Vitest 4.1.12 기준:

| 검증 | 결과 |
|---|---|
| 수정 권한 없음 / 저장 중 / 수정 가능·대기 3개 회귀 | 수정 전 1 실패·2 통과, 수정 후 전부 통과 |
| `draft-form-management.test.tsx` 전체 | 32 통과 |
| 기존 문서작성 실패 사례 10개 선택 실행 | 10 통과, 소스 수정 없음 |
| 대상 타입 검사 | 종료 코드 0 |
| 대상 oxlint | 오류 0, 기존 컴포넌트 export 경고 3개 |

권한 없음과 저장 중에는 메뉴가 없으며 Delete 입력 후에도 삭제·수정 변경 집합이 비어 있음을 단위 회귀로 확인했다. 기존 PUT `useAt=N`, 저장 실패 보존, 저장 중·저장 후 조용한 조회의 잠금 단언도 유지했다. 선택 실행에서 제외된 다른 문서작성 사례를 통과로 집계하지 않았으며 시간 제한 상향이나 소스 skip 추가는 없다. 전체 저장소 통과를 주장하는 결과가 아니다.

## 실제 브라우저

실제 `DashboardContent`와 기안양식 페이지를 직접 마운트하고 합성 목록·공통코드·사용자 응답만 주입했다. 공유 서버의 현재 소스에서 수행한 브라우저 증거이며 고정 스냅샷 전체 테스트와 구분한다. 실제 인증·DB·API 접근 없이 임시 격리 프로필을 사용했다.

각 너비에서 실제 마우스 우클릭의 `행 삭제`와 저장 버튼으로 기존 PUT 요청을 발생시켰다. 응답을 보류하는 동안 저장 버튼 비활성화와 저장 진행 표시를 확인한 뒤 응답을 완료했다. 각 요청은 정확히 1회이며 `useAt=N`이었다. 수정 권한을 제거한 별도 진입에서는 실제 컨텍스트 메뉴에 행 삭제가 없고 행이 유지되며 저장할 수 없고 수정 요청도 0회였다.

| 뷰포트 | 문서 너비 | Grid 너비 | 사용 해제 저장·잠금 | 수정 권한 없는 메뉴 차단 |
|---|---:|---:|---|---|
| 375px | 375px | 359px | 확인 | 확인 |
| 768px | 768px | 752px | 확인 | 확인 |
| 1280px | 1280px | 1264px | 확인 | 확인 |

화면 밖 컬럼은 Grid 내부 가로 스크롤을 사용하며 문서 가로 넘침은 없다. 브라우저에서 Grid 루트의 직접 focus 시도가 성립하지 않아 네이티브 Delete 키 경로는 검증했다고 주장하지 않는다. 해당 차단은 위 단위 회귀의 범위다.

- [768px 저장 완료](screenshots/draft-soft-disable-768.png)

세 이미지의 합성 데이터와 저장 완료 알림을 직접 확인했다. 임시 HTML과 본인 탭·프로필을 정리했으며 공유 서버의 HTTP 200 응답도 확인했다.

DB·API 데이터 계약을 바꾸지 않은 기존 UI 진입점 복구이므로 DB MCP와 SQL 변경은 해당 없음이다.
