# 20261118_001 발주현황 가입고수량·입고잔량 컬럼 및 입고대기마감 검색 결과

관련: [작업지시서](../../../directions/20261118/20261118_001_발주현황_입고잔량_마감검색_작업지시서.md) · [계획서](../../../plan/20261118/20261118_001_발주현황_입고잔량_마감검색_계획서.md) · [상세사양서](../../../spec/20261118/20261118_001_발주현황_입고잔량_마감검색_상세사양서.md)

## 배경
입고대기마감(발주 상세 행 `receipt_close_at`)은 이미 구현되어 있다. 마감하면 가입고 대상 조회와 가입고 저장에서 제외된다. 다만 발주현황에서 가입고 진행량과 입고 잔량을 볼 수 없고 마감 여부로 거를 수 없어서 마감 대상을 고르기 어려웠다. 일괄 마감은 사용자 결정으로 이번 범위에서 제외했다.

## 변경 내용
- 백엔드(발주현황): 응답에 `arrivedQty`(가입고수량), `remainQty`(입고잔량) 추가, 검색 조건 `receiptCloseType`(OPEN/CLOSED, 없으면 전체) 추가.
  - 가입고수량 = 유효 가입고 합 − 유효 수입검사 불합격 합(가입고 대상 조회와 같은 정의), 입고잔량 = max(발주수량 − 가입고수량, 0).
  - 잘못된 `receiptCloseType`은 400.
- 프론트(발주현황): `발주수량` 뒤에 `가입고수량`, `입고잔량` 컬럼, 상세검색에 `입고대기마감`(전체/미마감/마감), 그리드 `storageKey`를 `-v2`로 변경(저장된 컬럼 구성 때문에 새 컬럼이 가려지지 않도록).
- DB 변경 없음. 일괄 마감, 마감 저장 로직, 가입고·입고 화면 변경 없음.

## 검증
- 백엔드 전체: 1288건, 오류 1(기존 `MinioStorageConfigTest`). 신규 테스트: 마감 조건 전달·거부, mapper의 수량 컬럼과 마감 필터 SQL.
- 프론트: 발주현황·검색 레이아웃·검색어 강조 테스트 42건 통과, `tsc -b` 통과. 레이아웃 테스트에 `입고대기마감` 선택 항목 반영.
- DB MCP(읽기 전용) 조회로 계산 확인: 예) 발주 15 → 가입고 6, 잔량 9 / 발주 1000 → 가입고 83, 잔량 917 / 발주 12 → 가입고 12, 잔량 0 / 가입고가 발주보다 많은 행(30 vs 35)은 잔량 0.
- 실행 중인 서버 API: 전체 24행 = 미마감 21 + 마감 3, 모든 행이 `remainQty = max(orderQty − arrivedQty, 0)`, `receiptCloseType=ALL`은 400.
- 브라우저(1920/768/375px): 헤더 순서(발주수량·가입고수량·입고잔량), 선택지(전체/미마감/마감), 마감 선택 후 조회 시 행 수 3건, 가로 스크롤 없음, 페이지 오류 없음.
- 스크린샷: [screenshots](screenshots/)
- Java 변경은 `BigDecimal` 필드와 문자열 검증뿐이며 Maven target 1.8로 컴파일했다(별도 `javac --release 8`은 하지 않음).

## 한계
- 가입고수량 계산이 테넌트 전체 가입고를 집계하는 서브쿼리다(가입고 대상 조회와 같은 방식). 데이터가 많이 커지면 발주일 범위로 좁히는 개선이 필요할 수 있다.
- 좁은 화면(768·375px)에서는 그리드가 가로 가상화되어 새 컬럼은 스크롤해야 보인다(기존 컬럼과 같은 동작).
- 조회조건 패널의 바깥 클릭 닫기와 재배치는 공용 컴포넌트 영향 범위를 영업 담당자와 협의한 뒤 정하기로 하고 이번에는 포함하지 않았다.
- 일괄 마감은 구현하지 않았다. 필요하면 현황에서 행을 선택해 마감하는 방식을 따로 설계한다.
