# 구매요청등록 화면 및 DDL 작업 결과

## 작업 내용

- 기존 MES TMA103(요청 메인)·TMA103A(확정 메인)·TMA104(요청 상세)를 S-ERP 기준으로 재설계해 `tb_purchase_request_hd`/`tb_purchase_request_dt` DDL을 작성했습니다. 확정 메인은 헤더에 합쳤고, 확정·발주대기 마감·수주 연계 컬럼은 테이블에만 미리 두었습니다.
- 상태는 영문 코드(`REQUESTED`/`CONFIRMED`)로 저장하고 화면에서 한글 라벨(요청/확정)로 표시합니다.
- 헤더와 상세 모두 감사 컬럼(`created_by/at`, `updated_by/at`)을 둡니다. 수정 시 값이 바뀐 상세 행만 수정자·수정일시를 갱신합니다.
- `MATERIALS` 모듈(구매자재)과 `구매관리 > 구매요청등록` 메뉴 seed를 작성했습니다(테넌트 1, 역할 권한은 수주등록에서 복사).
- 백엔드 `egovframework.let.materials.request.create`: 등록·단건 조회·수정·삭제 API(`/api/v1/materials/purchase-requests`). 번호는 `MR-yyyyMMdd-NNNN`, 요청자·요청부서는 로그인 사용자로 서버에서 설정합니다. `REQUESTED` 상태에서만 수정·삭제할 수 있습니다.
- 프론트 `pages/materials/request/create`: 수주등록과 같은 구조(기본정보 폼 + F1-Grid 상세). 사용용도는 공통코드 `PURCHASE_USE_TYPE`, 품목은 공통 품목 선택기를 씁니다. 현황 화면 다이얼로그에서 쓰도록 `embedded`/`mode` 모드를 지원합니다.

- SQL 정적 테스트 `node --test tools/tests/test_purchase_request_schema.cjs`: 6개 통과 (docs/backend 사본 동일성 포함)

  - 44개 파일 전부를 개별 확인하지는 않았습니다.
- 브라우저 `node tests/purchase-request.browser.mjs`: 합성 API 응답으로 375/768/1280px 확인 통과, 콘솔 오류 없음.

- 이 PC의 Maven 기본 JDK는 1.8이고, 기존 테스트 일부가 Java 9+ API를 써서 JDK 8에서는 테스트 컴파일이 실패합니다. 그래서 운영 코드는 JDK 8로 컴파일하고 테스트는 VS Code Java 확장에 포함된 JDK 25로 실행했습니다.

## 실제 서버 종단 확인 (2026-11-12)

실행 중인 개발 서버(백엔드 8080, 프론트 4173)에 `admin` 계정(테넌트 1, ADMIN 역할)으로 로그인해 API와 화면을 확인했습니다.

### 발견한 버그와 수정

- 증상: 부서가 없는 사용자가 저장하면 500 오류("데이터 처리 중 오류")가 나고 저장되지 않습니다.
- 원인: 요청부서 `request_dept_id`가 null로 들어가는데, 전역 MyBatis 설정 `jdbcTypeForNull=VARCHAR` 때문에 null이 문자열 타입으로 바인딩되어 BIGINT 컬럼에 거부됩니다. 서버 로그 파일이 없어 오류 원문은 보지 못했고, 수정 후 같은 조건의 저장이 성공하는 것으로 원인을 확인했습니다.
- 수정: `insertRequestHeader`의 `#{requestDeptId}`를 `#{requestDeptId, jdbcType=BIGINT}`로 바꿨습니다. 다른 숫자·날짜 파라미터는 항상 값이 있어 영향이 없습니다.
- 회귀 테스트: `PurchaseRequestMapperTest`에 `requestDeptId`의 jdbcType이 BIGINT인지 확인하는 검증을 추가했습니다. 구매요청 백엔드 테스트 20개 통과.

## 추가 변경: 구매 가능 품목계정 제한 (2026-11-12)

사용자 요청으로 구매요청 품목을 품목계정(`ITEM_TYPE`)이 원재료(`RAW`)·부재료(`SUB`)·소모품(`SUPPLY`)인 품목으로 제한했습니다. 작업지시서·계획서·사양서(4.3, 5.3, 5.7, 6장)에 같은 내용을 추가했습니다.

- 화면: `searchPurchaseMaterials`가 공통 품목 목록 API 결과를 세 계정으로 거르고, 선택 목록에 "품목계정: 원재료"처럼 계정 이름을 보여 줍니다. 공통 품목 목록 API는 바꾸지 않았습니다.
- 서버: 저장(등록·수정) 때 모든 행의 품목 계정을 확인합니다. 품목이 없거나 삭제됐으면 404, 다른 계정이면 400 "구매요청할 수 없는 품목계정입니다. 원재료, 부재료, 소모품만 선택할 수 있습니다."를 반환합니다. 품목 확인 쿼리는 삭제된 품목(`delete_status`, `deleted_at`)도 제외하도록 바꿨습니다(`existsMaterial` → `selectMaterialTypeCode`).
- 테스트: 백엔드 구매요청 테스트 21개 통과(허용 3개 계정 저장, 상품·제품·반제품 거부 추가), 프론트 구매요청 테스트 14개 통과(선택 목록 계정 필터 추가), `npm run build` 통과, JDK 8 컴파일 통과.

## 미확인 사항

- 부서가 있는 사용자 계정의 저장은 확인하지 않았습니다(요청부서가 채워지는 경우).
- 확정(`CONFIRMED`) 건의 수정·삭제 거부(409)는 확정 화면이 없어 실제 서버로는 확인하지 못했고, 단위 테스트로만 확인했습니다.
- 상세 그리드 일괄적용은 F1-Grid 공통 기능 결정 후 별도 작업으로 보류했습니다.
