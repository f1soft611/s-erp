- 원인: 60423e7a / 46cd5a4f 커밋에서 UTF-8 한글이 CP949로 잘못 디코딩되어 저장(`肄붾뱶`, `?占쎌씠` 등, 손실 치환 포함)되어 약 237행이 깨짐. 기계적 역변환 불가.

## 배치 3-C: 숫자 입력·조회 실패·테스트 지연

- 정수 입력 재현: `decimalPlaces: 0`에서 `12.34`가 `1234`가 됐다. 숫자가 아닌 문자를 모두 제거해 소수부 숫자를 정수부에 붙인 것이 원인이었다. 첫 소수점 이하를 버려 `12`, `-12.34`는 `-12`로 정규화한다.
- 키보드 입력 추가 재현: 정규화만 수정하면 브라우저 연속 입력 `12.34`가 `124`가 됐다. 셀 편집과 행 폼에서 편집 중 원문을 임시 표시하고 저장값은 정규화하며, 포커스를 잃으면 정수를 표시한다. 외부 값이 바뀌면 이전 입력 원문을 버린다.
- 문서 목록: 필터 등 조회 조건이 바뀐 조회가 실패하면 목록, 피드 및 고정 문서를 비워 이전 조건의 결과가 새 결과로 오인되지 않도록 했다. 같은 조건의 조용한 갱신 실패에서는 기존 결과와 오류를 함께 표시한다.
- 테스트 격리: `vi.clearAllMocks()`는 호출 이력만 지우므로 feed 표시 테스트가 사용하지 않은 `mockResolvedValueOnce`가 다음 테스트에 남았다. 해당 순서의 실패를 재현했고 대상 API 목의 일회성 응답과 구현을 테스트마다 초기화했다.
- 지연 분석: 문서 작성 파일의 단독 전체 실행은 157개, 총 324.30초(테스트 309.16초, import 11.87초)였다. 20개 테스트가 각각 4초 이상이었으며 가장 긴 결재선 설정 테스트는 11.289초였다. 대형 화면을 렌더링하고 여러 UI 상호작용·비동기 대기를 수행하는 통합 테스트가 실행 시간의 대부분을 차지한다. 이전 실행에서 두 테스트가 5초 제한시간에 걸렸으나, CPU·DOM 접근별 프로파일링 없이 특정 병목이나 시스템 부하를 단정할 수는 없다. 제한시간은 늘리지 않았다.
- 대표적인 `keeps the empty approval selector...` 테스트를 일시 계측한 결과 초기 렌더 448ms, 작성창 열기와 준비 대기 1,856ms, 네 번의 사용자 선택은 회당 약 0.4~0.5초, 마지막 버튼 클릭과 DOM 검증은 1,557ms였다. 한 번의 고정 대기보다 실제 화면 렌더·선택·검증이 누적되어 기본 5초를 넘는 사례다. 임시 계측 코드는 제거했다.
- 검증: F1Grid 및 행 폼 테스트 243개 전체 통과, `npm run build` 통과. 문서 작성 테스트는 목 격리 직후 157개 전체 통과했으나 공통 입력 변경 후 마지막 전체 실행에서는 152개 통과, 5개가 각각 기본 5초 제한시간 초과로 실패했다. 실패한 5개를 진단 목적으로 `--testTimeout=15000`을 지정해 재실행한 결과 모두 통과했다(2.05~5.23초). 프로젝트 설정의 제한시간은 변경하지 않았다. 변경 파일 oxlint는 오류 없이 기존 경고를 출력했다. 전체 프론트엔드 테스트는 이번 배치에서 재실행하지 않았다.
- 브라우저: 실제 컴포넌트를 임시 테스트 화면에 띄워 셀과 행 폼에서 `12.34` 입력 중 저장값 `12`, 포커스 이동 후 표시 `12`를 확인했다. 인증된 실제 업무 화면이나 문서 조회 실패 화면은 브라우저에서 검증하지 않았다. 375·768·1280px의 임시 화면은 가로 넘침이 없었다. 스크린샷: [375px](screenshots/number-editor-375.png), [768px](screenshots/number-editor-768.png), [1280px](screenshots/number-editor-1280.png).
- 다음 조치: 남은 다른 테스트 실패를 별도 배치로 확인하고, 문서 작성 통합 테스트의 대형 DOM과 접근성 쿼리 비용을 프로파일링한 뒤 범위를 보존하면서 분리·최적화한다.
