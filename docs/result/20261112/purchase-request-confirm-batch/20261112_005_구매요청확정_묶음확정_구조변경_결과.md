# 구매요청확정 묶음 확정 구조 변경 작업 결과

## 작업 내용

- 사용자 결정(2026-11-12): 여러 구매요청을 묶어 한 번에 확정하고 확정번호 `MC-yyyyMMdd-NNNN`을 발급한다.
  확정 취소는 확정번호 전체 단위, 취소한 확정은 `use_at = 'N'`으로 이력 보존, 기존 확정에 요청 추가 없음,
  한 확정 묶음은 같은 통화만 허용(다르면 경고 후 저장 차단).
- DB `20261112_005`: 확정 메인 `tb_purchase_confirm_hd` 신설, `tb_purchase_request_hd`에 `purchase_confirm_id` 추가,
  `confirm_dt`·`confirmer_id`를 확정 메인으로 옮기고 삭제, 상태 제약을 확정 ID 연결 기준으로 교체,
  기존 확정 데이터 이전(통화 혼합 시 중단)과 `MATERIAL_CONFIRM_NO` 채번값 맞춤. `db-schema.md` 갱신.
- 백엔드 `egovframework.let.materials.request.confirm` 재작성(`/api/v1/materials/purchase-request-confirms`)
  - `GET /candidates`, `GET /request-details?purchaseRequestIds=`, `GET /`(확정 목록), `GET /{id}`,
    `POST /`(묶음 확정, 201), `PUT /{id}/order-close`, `POST /{id}/cancel`, `GET /unit-price`
  - 요청은 ID 오름차순으로 `FOR UPDATE` 잠금 후 모두 요청 상태인지 확인, 행 집합이 정확히 같아야 확정,
    통화 2종 이상이면 400, 요청별 합계와 확정 합계를 함께 저장.
  - 구매요청등록 단건 조회는 확정일을 확정 메인에서 조인.
- 프론트 `pages/materials/request/confirm`
  - [신규] [요청 불러오기](다중 체크, 불러올 때마다 그리드를 비우고 고른 요청만 표시)
    [확정 불러오기](확정·확정 취소·전체) [확정] [저장](발주대기 마감) [확정 취소]
  - 기본정보: 확정번호, 확정일, 확정자, 상태(신규 작성/확정/확정 취소), 요청 건수, 통화(섞이면 "혼합"), 합계금액, 확정 비고
  - 상세 그리드 앞쪽에 구매요청번호·요청일·요청자를 두고 같은 요청끼리 병합, [선택 요청 빼기]
  - 통화가 섞이면 경고 문구를 보여 주고, [확정] 시 경고 대화상자 후 저장하지 않음
- 기존 테스트 데이터 `MR-20261112-0005`(KRW·USD 혼합 확정)는 스크립트 실행 전에 기존 API로 확정 취소했습니다.
- 20261112_004 작업지시서·사양서에 005로 변경되었다는 안내를 추가했습니다.

## 검증 결과

- SQL 정적 테스트 8개 통과(005 컬럼·제약·통화 혼합 중단·채번·롤백, docs/backend 사본 동일).
- 격리된 PGlite: 통화 혼합 확정 요청이 있으면 중단(테이블 생성 전체 롤백), 정상 이전(확정 메인 2건·번호·채번값 2),
  신규 제약 거부(확정인데 확정 ID 없음, 요청인데 확정 ID 있음, 잘못된 통화, 중복 확정번호, 잘못된 use_at),
  취소 흐름, 롤백 후 확정일·확정자 복원과 이전 제약 복원을 확인했습니다.
- 백엔드 구매요청 테스트 36개 통과(확정 Service 11: 여러 요청 번호 1개·요청별 합계·잠금 순서, 통화 혼합 거부,
  빈 통화 KRW 처리, 요청 상태 아님·행 집합 불일치 409, 선택 개수·필수값·참조 검증, 취소된 확정 409, 마감 대상 검증,
  확정 취소, 상세 불러오기, 목록 상태 / Mapper 4). JDK 8로 운영 코드 컴파일 통과.
- 프론트 구매요청 테스트 20개 통과(확정 6: API 경로, 초안 행·검증·payload, 통화 혼합 판정, 여러 요청 불러오기,
  확정 불러오기·확정번호 전체 취소, 권한). `npm run build` 통과.
- 브라우저 `node tests/purchase-request-confirm.browser.mjs`: 합성 응답으로 375/768/1280px에서
  요청 다중 선택 → 초안 필수값 검증 → 확정 불러오기 → 확정 화면, 콘솔 오류 없음.

## 사용자 확인 후 수정 (2026-11-12): 요청 불러오기 누적 → 교체

- 현상: 확정을 불러온 뒤(또는 작성 중에) [요청 불러오기]를 하면 그리드에 이전 행이 남고 새 요청 행이 이어 붙었습니다.
- 원인: 사양서에 "고른 요청을 현재 목록에 더한다"로 정했던 동작입니다(코드 오류가 아니라 요구사항과 다른 설계).
- 수정: 요청 불러오기는 항상 그리드를 비우고 이번에 고른 요청만 신규 확정으로 표시합니다. 작성 중 내용이나 미저장 변경이
  있으면 먼저 확인하고, 요청 선택 창은 요청 상태 건 전체를 보여 줍니다(제외 목록 없음). 작업지시서·사양서도 같이 고쳤습니다.
- 회귀 테스트: 확정 열기 → 요청 불러오기 → 다시 요청 불러오기에서 마지막에 고른 요청만 남는지 확인하는 프론트 테스트를 추가했습니다
  (구매요청 프론트 21개 통과, `npm run build` 통과).
- 실제 화면: `MC-20261112-0001`(0007·0008) 열기 → 0009 불러오기 → 그리드 0009만, 확정번호 "확정 시 자동 채번" →
  0006 불러오기 → 그리드 0006만, 요청 건수 1. API 오류 없음.

## 확인이 필요한 사항

- 취소된 확정에 어떤 요청이 묶여 있었는지는 남지 않습니다(취소 시 요청 쪽 연결 해제). 필요하면 확정 이력 테이블을 별도로 추가합니다.
- 경고 대화상자는 공통 확인 대화상자를 써서 [확인]/[닫기] 두 버튼이 보이며, 둘 다 저장하지 않고 닫습니다(공통 훅에 단일 버튼 옵션이 없음).
- 일괄적용(여러 행 같은 창고·구매처·발주구분)은 F1-Grid 공통 기능 결정 후 별도 작업으로 보류 중입니다.
