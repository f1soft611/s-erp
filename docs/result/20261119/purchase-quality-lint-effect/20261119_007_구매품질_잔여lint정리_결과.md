## 결과
- 구매·품질 영역 `set-state-in-effect` 14건 → 0건. 전체 프론트 진단은 63건 → 49건(나머지는 영업·그룹웨어·공통 그리드 등 구매·품질 밖). 린트 오류 0.

## 수정 범위(건별)
| 파일 | 건수 | 방식 |

| `usePurchaseArrivalStatus.ts` | 3 | 검색 초기화·목록·상세를 입고현황 훅과 같은 방식으로 이동(렌더 중 이전 요청 비교 후 시작 상태 보정, effect는 요청·응답만) |

| 구매요청·발주·가입고·입고·수입검사 등록 페이지 | 5 | 상세 로드 effect의 `setIsLoading(true)`를 "수정 대상 ID가 바뀐 렌더"에서 보정(마운트 시점 포함) |

보존한 동작: 목록 `filters` null 무요청, 필터 변경 시 이전 응답 무시·일반 로딩, `refreshQuietly`의 로딩·목록 유지와 quiet 판정(null 대기 중 quiet 요청은 재개 시 유지), 상세의 같은 ID 무요청·새로고침 시 항목 유지·닫기 초기화·오류 비움·늦은 응답 무시, 세션 키·버전·훅 반환 형태.

## 검증
- 신규 회귀 테스트 `tests/purchase-quality-status-hook-start.test.tsx`(3개 훅 × 4시나리오 = 12건): **변경 전 코드와 변경 후 코드 모두 통과**(동작 보존 확인).
- 관련 화면 테스트 18개 파일 263건 통과, `tsc` 통과, 전체 린트 오류 0.
- 브라우저(1280·375px): 가입고현황·발주현황·수입검사현황에서 번호 클릭 시 상세 표시, API·페이지 오류 없음. 스크린샷 [screenshots](screenshots/).

## 미해결·참고
- 발주현황 훅은 김기형 님이 로컬에 미커밋 후속 수정이 있다고 공유했습니다. 같은 파일을 수정했으므로 가져올 때 겹칠 수 있습니다.
- 등록 화면 5건은 마운트 시점 보정을 포함해 수정 모드 진입 시 로딩 표시를 동일하게 유지했습니다. 등록 화면 자체의 별도 신규 테스트는 추가하지 않았고 기존 화면 테스트로 확인했습니다.
