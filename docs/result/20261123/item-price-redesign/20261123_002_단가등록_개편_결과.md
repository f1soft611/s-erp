## 1. 구현 범위

### 규칙 변경
- **공통단가(거래처 없는 단가) 폐지**: 단가는 항상 거래처에 붙는다. `customer_id`는 NOT NULL이고 저장·수정·엑셀은 거래처가 필수다.
- **구매요청확정(매입) 구매처·단가 채우기**: 품목의 사용 중 매입 단가 거래처가 1곳이면 그 거래처, 2곳 이상이면 기본 거래처를 구매처로 하고 그 거래처의 기준일 유효 단가(부가세구분·부가세포함·통화·발주구분 포함)를 채운다. 구매처는 정해졌으나 기준일 유효 단가가 없으면 구매처만 채우고 단가는 비운다(기본 거래처로 체크되어 있어도 마찬가지). 거래처가 없거나, 2곳 이상인데 기본 거래처가 없으면 모두 비운다.
- **매입 기본 거래처 필수 검증**: 저장 후 매입 단가 거래처가 2곳 이상인 품목은 기본 거래처가 정확히 1개여야 한다(위반하면 400과 품목 안내, 저장 전체 되돌림). 1곳이면 지정은 선택이다. 매출은 기본 거래처 개념이 없다.
- **수주용 조회**: `ItemPriceLookupService.findPrice(테넌트, "매출", 품목, 수주처, 기준일)`가 수주처+품목의 유효 단가를 단가 행의 통화·부가세와 함께 돌려준다. 영업 소스는 수정하지 않았다(§5 연동 안내).

### 백엔드
- 조회: `/overview`는 품목 1줄(품목 정보·계정분류·단가 거래처 수·매입 기본 거래처)을 돌려주고 필터는 `ALL`/`NO_PRICE`/`NO_DEFAULT_SUPPLIER`(매입만). `itemTypes`(쉼표 구분, 6개 코드만 허용, 그 밖은 400)를 `/overview`·`/customer-overview`·목록에 추가했고, 목록에는 `materialId` 조건도 추가했다. 계정분류는 `tb_material_info.material_type_code`로 거른다.
- 저장: 거래처 필수, 매입 품목 단위 기본 거래처 검증(`ItemDefaultSupplierService.findMaterialsMissingDefaultSupplier`, 매입 단가가 바뀌는 품목만 대상이며 삭제·수정되는 기존 행은 DB의 거래구분으로 판단). 엑셀 검증은 거래처코드를 필수로 본다.
- 단가 조회 공통 서비스: 공통단가 대체 제거, `findDefaultSupplierPrices` → `findPurchasePrices`(구매요청확정 서비스 호출부 갱신). 쿼리는 `selectPurchasePrices`로 바뀌었다.
- 제거: `ItemPriceOverviewSideVO`, `selectOverviewPrices`.

### 프론트엔드
- **`PageSearchArea` select 필드 `multiple` 옵션**(공통 컴포넌트): 값은 쉼표로 이은 문자열, 선택 칩·체크박스 목록, 비우면 전체. 기존 select와 F1Grid 멀티선택은 바뀌지 않는다.
- **품목 계정분류 조회조건**: 세 탭 모두. 기본값은 매입 원재료·부재료·소모품(`RAW,SUB,SUPPLY`), 매출 제품·반제품·상품(`PRODUCT,SEMI,GOODS`).
- **품목 기준 탭 좌우 그리드**: 왼쪽 품목 목록(품목코드·품목·규격·단위 나란히, 계정분류, 거래처 수) → 오른쪽 선택 품목의 거래처별 단가. 품목이 고정되어 새 행 폼 상단에 품목이 비활성으로 보이고, 매입은 거래처 오른쪽에 기본 거래처 체크가 있다. 기본 거래처는 같은 품목의 한 행만 체크된다(변경이 반영된 뒤 다른 행 해제).
- **후속 조정(같은 날)**: 단가 그리드에서 최소주문수량 열·폼 칸을 뺐다(엑셀 양식·API의 최소주문수량 값은 그대로 두어 기존 값은 보존된다). 매입 단가 그리드의 기본 거래처 체크는 No 바로 다음 맨 앞 열로 옮기고 열 이름을 "기본"으로 했다(행 폼 칸 이름은 "기본 거래처" 유지). 매출 화면은 이 열을 숨긴다.
- **컬럼 순서**: 평면 단가 그리드(거래처 기준·이력)에서 단위를 규격 바로 뒤로 옮겨 품목코드·품목명·규격·단위가 나란하다.
- **엑셀 통합**: 품목 기준 전용 양식·파서·화면 흐름을 없애고 거래처별 단가 양식 하나만 쓴다(거래처코드 필수 안내).
- 제거: 품목 기준 트리(`ItemPriceOverviewTree`, `itemPriceOverviewGridModel`, `itemPriceOverviewChanges`, `itemPriceOverviewExcel`)와 단가 삭제 대화상자(`ItemPriceRemoveDialog`), 공통단가·특별단가 문구와 필터. 단가 삭제는 그리드 행 삭제 메뉴(적용 중·예정 단가)로 한다.
- 변경 집합 생성은 거래처 기준과 같은 함수로 일반화했다(`buildFixedKeyPriceBatch`: 거래처 또는 품목 고정).

## 5. 영업(수주) 연동 안내 (영업 담당자용)
수주 화면에서 수주처와 품목이 정해진 뒤 단가를 채우려면 공통 서비스를 호출한다. 영업 소스는 이번 작업에서 수정하지 않았다.
- 호출: `ItemPriceLookupService.findPrice(tenantId, "매출", materialId, customerId, baseDt)` (`egovframework.let.co.master.itempartnerprice.service`)
- 결과(`ItemPriceLookupVO`): `unitPrice`, `currency`(원화 단가가 있으면 KRW, 외화 단가만 있으면 그 통화), `taxType`, `vatIncludedAt`. 일치하는 유효 단가가 없으면 `null`이다(그때는 단가를 비워 두고 직접 입력).
- 수주 화면에는 통화가 없으므로 단가 행의 통화를 그대로 적용한다(통화로 단가를 거르지 않는다). 품목정보와 거래처정보에 있는 통화 정보를 같이 넘기면 된다.
- 단가 테이블과 기본 거래처 테이블은 이 서비스만 조회한다.

## 6. 미확인·후속
- 실서버에서 단가 저장·구매요청확정 채우기 동작은 실데이터를 바꾸거나 요청 데이터가 필요해 확인하지 않았다(조회 API·화면 로딩만 실계정으로 확인). 그 밖의 브라우저 확인은 합성 API 데이터다.
- 구매요청확정이 새 규칙대로 채우는 동작은 SQL 쿼리를 PGlite 샘플 데이터(거래처 1곳 유효/만료, 2곳 이상 기본 유효/만료, 기본 없음, 거래처 없음, 비활성 거래처, 부가세 전달)로 확인했고 서비스·화면 단위 테스트가 있다. 실서버 구매요청확정 화면 확인은 SQL 적용 뒤 사용자가 해야 한다.
- 계정분류 옵션은 정적 목록이다. 공통코드 `ITEM_TYPE` 이름이 바뀌면 화면 목록도 같이 바꿔야 한다.
- 품목 8처럼 기존 다거래처 품목은 SQL이 기본 거래처를 지정한다. 다른 환경에서는 같은 SQL을 실행하면 된다.
