## 1. 구현 범위

### 백엔드
- `ItemPriceAccessService`(신규): 내 메뉴 트리에서 거래구분의 화면 키(`item-purchase-prices` / `item-sales-prices`) 권한을 확인한다(분류관리와 같은 방식). READ는 읽기·등록·수정 권한 중 하나면 허용, CREATE/UPDATE/DELETE는 각 권한. 인증 없음 401, 권한 없음 403, 거래구분 값 오류 400.
- 컨트롤러 적용: 품목 기준·거래처 기준·목록 조회는 `tradeType` 필수 + READ. 엑셀 검증은 행에 나온 거래구분별 CREATE. 일괄 저장은 신규=CREATE, 수정=UPDATE(요청 값과 DB의 기존 행 거래구분 모두), 삭제=DELETE(DB의 기존 행 거래구분)를 모두 확인한 뒤에만 저장을 시작한다. 클라이언트가 삭제·수정 행의 거래구분을 속여도 DB 값으로 판단한다(신규 쿼리 `selectTradeTypesByPriceIds`).
- 조회: 품목 기준·거래처 기준 쿼리가 선택 구분의 단가만 조회·집계한다. 필터는 `ALL`/`NO_COMMON_PRICE`/`HAS_SPECIAL`/`NO_DEFAULT_SUPPLIER`(매입 전용, 매출에 보내면 400)로 정리하고 `NO_PURCHASE`/`NO_SALES`는 제거했다. 기본 거래처는 매입일 때만 내려준다.
- 구매요청확정·`ItemPriceLookupService` 등 내부 서비스 호출에는 메뉴 권한 검사를 걸지 않았다.

### 프론트엔드
- 화면 컴포넌트(`ItemPartnerPriceManagementPage`와 세 탭)가 `tradeType`을 받는다. `DashboardContent`가 `item-purchase-prices`→매입, `item-sales-prices`→매출로 연결하고 기존 `item-partner-prices` 키는 제거했다.
- 품목 기준 트리: 선택 구분의 열만 만든다. 매입에서만 "매입 기본 거래처", 발주구분, 기본 거래처가 있다. 변경 집합·삭제 창도 선택 구분 한쪽만 다룬다.
- 거래처 기준·이력 조회: 거래구분 열·행 폼 칸을 숨기고 신규 행 거래구분을 고정, 매입 전용 열은 매입에서만 만든다. 조회 필터 "거래구분"은 검색 조건에서 뺐다.
- 검색 필터: "단가 상태"는 거래구분별로 "공통단가 미등록 / 특별단가 있는 품목 / [매입] 매입 기본 거래처 미지정".
- 엑셀: 거래처별 단가 양식은 매입 14열·매출 12열(안내 시트도 구분별), 화면과 다른 거래구분 행은 오류. 품목 기준 양식도 선택 구분 한쪽 열만 쓴다.
- 그리드 `storageKey`와 이력 검색 세션 키를 구분별로 분리했다.
- 대시보드 설명 문구(매입단가등록/매출단가등록)와 F1-Grid 문서를 갱신했다.

### 메뉴 DB (사용자가 2026-11-23 실행 완료)
- [스크립트](../../../database/20261123/20261123_001_split_item_price_menu.sql) / [롤백](../../../database/20261123/20261123_001_rollback_split_item_price_menu.sql) / [변경 이력](../../../database/20261123/20261123_001_change_split_item_price_menu.md), `backend/DATABASE` 동일 복사.
- 기존 메뉴 `CO_UPRICE` → 매입단가등록(`/co/master/item-purchase-prices`), 신규 `CO_UPRICE_SALES` 매출단가등록(`/co/master/item-sales-prices`), 역할 권한 복제. 테이블 구조 변경은 없어 `db-schema.md`는 갱신하지 않았다.
- **적용 순서**: 이 코드(백엔드·프론트)가 배포된 뒤에 SQL을 실행한다. 코드 배포 전에 실행하면 새 주소의 화면이 열리지 않고, 기존 메뉴 주소(`/co/master/item-partner-prices`)는 더 이상 화면과 연결되지 않는다(북마크는 지원하지 않기로 결정).
- **적용 결과(읽기 전용 DB 조회, 실행 후)**: `CO_UPRICE`(ID 29)는 매입단가등록·`/co/master/item-purchase-prices`로 바뀌었고, `CO_UPRICE_SALES`(ID 73)는 매출단가등록·`/co/master/item-sales-prices`, 부모 13, 정렬 51, 사용 중으로 추가되었다. 두 메뉴 모두 역할 1에 READ·CREATE·UPDATE·DELETE·EXCEL이 있다(기존 권한이 그대로 복제됨).

## 2. DB MCP 확인 근거 (읽기 전용, 2026-11-23)
- `tb_menu` 단가 메뉴 1건(ID 29, `CO_UPRICE`, 부모 13, 정렬 50, 테넌트 1), 최대 menu_id 72, 즐겨찾기 0건, 역할 1의 권한 5건(READ·CREATE·UPDATE·DELETE·EXCEL).
- `tb_menu`는 `(tenant_id, menu_code)` 유일, `menu_id` 자동 증가, `tb_role_menu_permission`은 `(role_id, menu_id, permission_id)` 기본키임을 확인.
- 메뉴 SQL은 실DB가 아니라 PGlite(임시 PostgreSQL 호환 DB)에서 실행해 확인했다: 메뉴 이름·주소 변경, 신규 메뉴 추가, 권한 복제(5→10건), 재실행 시 변화 없음, 롤백 시 원상 복구(2개 테넌트 가정).

## 5. 미확인·후속
- SQL 적용은 DB 조회로 확인했다. 실제 계정으로 두 메뉴가 보이고 단가 조회·저장이 되는지는 사용자가 확인해야 한다(로그인 정보가 없어 미수행).
- 매출 메뉴 권한만 있는 계정이 매입 단가 API를 호출하면 403인지는 단위·컨트롤러 테스트로만 확인했다. 현재 DB에는 두 메뉴를 모두 가진 역할 1뿐이라 실서버에서 이 확인을 하려면 매출 권한만 가진 테스트 역할·계정이 필요하다.
- 다른 테넌트가 생기면 `CO_UPRICE` 메뉴가 있는 모든 테넌트에 같은 SQL이 적용된다.
- 이력 조회 탭·품목 기준 엑셀 업로드의 매출 화면 실사용 확인은 합성 데이터 수준이다.
