# 출하 상세 발행 제한 결과

## 변경

- 기존 100건 상한과 HTTP 400을 유지하고 초과 오류에 상한을 명시했다. AUTO 발행 실패 시 출하도 저장되지 않는다는 내용을 안내한다.
- 일반 발행과 매출마감은 중복을 제거한 선택 상세가 101건 이상이면 요청을 차단한다. 자동 분할이나 MANUAL 출하 제한은 추가하지 않았다.
- 서버의 기존 검사 기준은 중복 제거 전 요청 목록 길이이며, 상세 ID가 생략된 발행과 AUTO 발행에도 상한을 적용한다.

## 검증

- 백엔드 관련 서비스 테스트 44건 통과. 101건 거부와 AUTO 발행 실패 시 트랜잭션 매니저의 rollback 호출을 검증했다. 100건은 DAO 조회 단계에 도달하는 것까지 검증했으며 DB에 실제 저장·롤백한 통합 검증은 수행하지 않았다.
- 프론트 관련 8개 테스트 파일 99건 통과 후, 추가한 AUTO 오류 표시와 100/101건 화면 경계 테스트 3건도 통과했다. 서비스 경계 테스트에서 100건 요청 허용과 101건 요청 차단을 확인했다.
- 프론트 typecheck, lint, build 성공. lint 경고와 번들 크기 경고가 남아 있다. 빌드와 테스트 동시 실행 시 일부 테스트가 시간 초과되었으나 분리 실행에서 통과했다.
- 변경된 운영 Java 2개 파일을 별도 출력 디렉터리에 `javac --release 8`로 컴파일했다. 의존성 전체의 Java 8 런타임 호환성까지 보증하는 검증은 아니다.
- 매출마감 화면에 격리 브라우저와 합성 데이터 101건을 사용하여 375, 768, 1280px에서 오류 문구 표시를 확인했다. 일반 명세서와 AUTO 출하는 브라우저 캡처 대신 컴포넌트 테스트로 확인했다.
  - [375px](screenshots/revenue-limit-375.png)
  - [768px](screenshots/revenue-limit-768.png)
  - [1280px](screenshots/revenue-limit-1280.png)
- 읽기 전용 DB MCP의 `list_tables`, `describe_table`로 `tb_sales_delivery_dt`, `tb_sales_statement_dt`, `tb_login_account` 메타데이터를 확인했다. 데이터 행 조회와 DB 변경은 하지 않았고 스키마 스크립트는 필요하지 않았다.
- Windows 격리 복사본에 Node 22와 `npm ci`로 lockfile 의존성을 설치해 lint, typecheck, build 및 관련 테스트 8개 파일 100건을 확인했다. 전체 테스트는 사용자 요청에 따라 중단했으며 GitHub Actions Ubuntu에서 미커밋 변경을 검증한 것은 아니다.
