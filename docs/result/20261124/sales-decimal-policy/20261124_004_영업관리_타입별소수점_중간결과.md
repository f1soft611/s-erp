# 영업관리 타입별 소수점 중간 결과

## 상태: 미완료

- 2026-11-25: 출하 저장 시 자동 거래명세서 조회가 존재하지 않는 `tb_sales_statement_hd.customer_id`를 참조해 실패했다. 읽기 전용 DB MCP의 테이블·컬럼 확인 결과 명세서 헤더에는 해당 컬럼이 없고 대표 출하 헤더에는 존재한다. 기존 insert도 명세서에 고객 ID를 쓰지 않으므로 컬럼만 추가하는 SQL은 사용하지 않는다.
- 명세서 조회를 대표 출하 ID와 테넌트 ID로 출하 헤더에 연결해 고객 ID를 반환하도록 수정했다. 여러 출하를 묶는 경우에도 기존 발행 검증은 같은 거래처만 허용한다. 스키마 변경과 DB 쓰기는 없다.
- Mapper 회귀 테스트가 수정 전 실패하고 수정 후 통과했으며 거래명세서 API·서비스·스키마 및 출하 서비스 집중 테스트가 통과했다. 읽기 전용 MCP에서 실제 테이블에 대한 조인 SQL의 컬럼 해석을 빈 결과로 확인했다. 이는 실제 출하 저장 검증을 대체하지 않는다.
- PGlite 격리 합성 스키마에서 실제 Mapper의 `selectHeader` SQL 전체를 실행해 대표 출하의 거래처 ID 반환, 다른 테넌트의 출하 제외, 비활성화된 대표 출하의 기존 명세서 조회를 확인했다. 실제 DB 저장이나 로그인 브라우저 검증은 아니다.
- 사용자가 직접 출하등록의 오류 없는 저장과 재조회, 거래명세서 확인을 보고했다. 구체적인 소수점 값 일치 여부는 별도로 보고되지 않았다.
- 커밋 제목: `fix(sales): 거래명세서 거래처 조회 오류 수정`
- 커밋 내용: `대표 출하에서 테넌트 범위로 거래처 ID를 조회하고 Mapper 회귀 검증을 추가한다.`

- 컬럼별 설정 공통화 작업을 진행 중이다. `decimal-column-contract.json`을 프론트와 서버가 함께 사용하며 수주·견적·출하·출하계획의 입력과 계산, 저장 시 계약 비교를 연결했다. 실제 계약에는 현재 별도 자릿수 예외를 지정하지 않았다.
- 화면의 저장 요청은 타입 정책과 업무별 전체 컬럼 계약을 보내고, 서버는 배포된 계약과 비교해 다르면 409로 거부한다. 예외가 없는 계약에 한해 구버전 스냅샷 미전송을 허용하므로 타입 변경 시 구버전 API 호출의 호환성은 별도 확인이 필요하다.
- 출하의 컬럼별 규칙을 그리드 입력·금액 계산·저장 검증 및 헤더 합계 표시에도 연결했다. 출하계획 수량의 컬럼 예외는 입력·저장과 현황 상세 표시에서 적용한다. 공통 사용 방법과 서버 동시 배포 주의사항은 F1-Grid 문서에 추가했다.
- 수주·견적·출하 현황의 저장 필드 컬럼과 상세 표시에도 해당 업무 필드 계약을 연결했다. 수주·출하의 헤더 합계와 행 합계는 각각 별도 계약을 사용한다. 연계 업무와 인쇄의 컬럼별 예외 적용 범위는 아직 전체 검증하지 않았다.
- 백엔드 Maven은 프론트 소스의 계약 파일을 리소스로 복사하므로 백엔드 단독 소스 빌드에는 해당 파일을 같은 상대 경로로 제공해야 한다. 계약이 없으면 서버의 해당 계약 로딩이 실패하지만 Maven 빌드 자체가 누락을 보장해 감지하지는 않는다.
- 계약 예외의 수주 서버·격리 DB 저장·재조회와 로그인한 수주 화면의 현재 정책 저장·재조회는 확인했다. 계약 예외를 적용한 프론트부터 실제 서버와 DB까지의 검증과 나머지 화면의 로그인 저장·재조회는 미완료이므로 배포 완료로 판단하지 않는다.
- `number`, `decimal`, `currency`별 정책의 저장·조회와 그리드 적용, 정책관리 편집 및 캐시 무효화를 부분 구현했다.
- 기존 단일 소수점 정책은 그대로 읽으며, 정책관리에서 편집할 때 기존 값을 세 타입에 복사한다.
- 변경 전 읽기 전용 DB MCP에서 관련 숫자 컬럼이 `numeric(15,2)`인 것을 확인했다. 사용자가 스크립트를 적용한 후 같은 MCP의 메타데이터에서 대상 27개 컬럼이 `numeric(19,6)`인 것을 확인했다. 데이터 행은 조회하지 않았다.
- 영업 화면의 수량 컬럼을 `number`, 단가 컬럼을 `decimal`, 금액 컬럼을 `currency`로 분류하는 후속 작업이 진행 중이다. 검증 완료 전에는 배포하지 않는다.
- 정책 변경 이력에 변경 전·후의 타입별 자릿수, 0 표시, 반올림 방식과 기존 단일 규칙을 읽기 쉽게 표시했다.
- 그리드 표시 반올림이 큰 숫자를 무조건 유효숫자 12자리로 줄이던 문제를 수정했다. JavaScript `number`로 변환할 때 이미 잃은 정밀도는 복구되지 않는다.
- 영업 숫자 컬럼을 `numeric(19,6)`으로 확장하는 SQL과 손실 방지 롤백 및 변경 이력을 작성했다. 실제 DB 스크립트는 사용자가 적용했다.
- 영업 기본 정책은 정책이 없을 때 0/3/3으로 해석한다. 기존 단일 정책의 변환이나 정책 레코드 생성은 수행하지 않았다.
- 수주·견적·출하 서버의 입력 검증과 계산 및 출하계획 서버 수량 검증을 정책에 부분 연결했다. 프론트 수주·견적·출하 계산과 저장 전 검증, 출하계획 저장 전 수량 검증도 부분 연결했다.
- 출하계획 분할 수량의 저장 전 합계와 화면 표시는 십진 계산과 수량 정책을 따른다.
- 숫자 셀 붙여넣기는 `onValueChange`를 순서대로 적용하여 수량·단가 변경에 따른 계산값도 갱신한다. `exactDecimal`을 지정한 컬럼은 붙여넣은 원문을 유지하며 영업 전 화면 적용은 아직 점검 중이다.
- 수주·견적·출하·거래명세서 현황 상세와 거래명세서 인쇄의 수량·금액에 타입별 표시를 부분 적용했다.
- 영업 모듈 컨텍스트에서 수주·견적·출하·출하계획의 정책 조회 실패와 미등록을 구분하고 조회 실패·대기 중 편집과 저장을 막는다.
- 수주·견적·출하의 표시된 공급가·견적금액 및 합계가 현재 클라이언트 정책의 계산과 다르면 저장 전 재계산을 요청한다. 수동 부가세는 그대로 비교에 사용하며 자동 재계산은 아직 구현되지 않았다.
- 화면 저장 요청에 선택적인 소수점 정책 스냅샷을 포함하고 서버가 적용할 수량·금액 정책의 자릿수와 반올림 방식이 다르면 HTTP 409로 저장을 거부한다. 스냅샷이 없는 기존 호출은 기존대로 처리한다.
- 후속 금액 `currency` 전환에서 서버·화면의 단가 검증과 금액 계산을 분리하고 `currency` 스냅샷도 비교한다. 단일 규칙과 스냅샷 미전송은 유지하며 `currency`가 빠진 타입별 스냅샷은 안전을 위해 409로 거부한다. 실 로그인 화면 검증은 미완료다.
- 자동 출하계획의 수정 가능 수량 합산과 현황 상세의 수량 차이에 십진 계산을 적용하고 상세 수량 표시는 정책을 따른다.
- 자동 순번은 사용자의 후속 지시에 따라 기존 `rownumber`를 유지한다.
- 정밀 십진 문자열을 사용하는 F1-Grid 입력·붙여넣기·표시·정렬·필터·집계와 선택 필드의 API JSON 숫자 원문 보존 기능을 추가했다. 수주·견적 입력 및 상세 응답과 수주·견적 현황 목록에 부분 연결했다.
- 견적은 문자열 수량·단가의 계산값을 검증하고 합계 범위 초과 시 저장을 막는다. 편집 중 합계 계산 오류가 발생하면 이전 합계 대신 `-`를 표시한다.
- 출하 원천 수주의 잔량·단가 응답과 선택 후 출하 계산, 출하 그리드 입력·저장 요청·저장 응답·상세 재조회·현황 목록에 문자열 정밀도를 부분 적용했다. 나머지 연계 화면은 아직 미완료다.
- 거래명세서 출하 선택·상세·현황 응답과 그리드·인쇄, 출하 선택 합계에 문자열 정밀도를 부분 적용했다. 다른 연계 화면은 별도 점검이 필요하다.
- 출하계획의 원천 수주·저장 응답·상세 재조회, 입력 그리드, 저장 전 분할 수량·잔량 비교와 현황 상세 수량 차이에 십진 문자열 처리를 부분 적용했다.
- 매출마감 조회의 수량·금액 JSON 원문과 그리드 표시, 출하계획 수주 선택 및 입력 화면의 수주수량·계획잔량 표시에 십진 문자열 처리를 추가했다. 매출마감 요청은 기존처럼 출하 상세 ID만 전달한다.
- 일부 연계 화면 및 실제 로그인 저장·재조회는 확인되지 않아 전체 입력·저장·재조회 일치를 보장할 수 없다.
- 실제 정책관리 화면의 저장 흐름과 수주 이외 영업 화면의 로그인 저장·재조회는 수행하지 않았다. 사용자 허용에 따라 로그인된 화면에서 테스트 수주 1건을 생성했다.

## 부분 검증

- 2026-11-25 로그인된 수주등록 화면에서 수량 0자리 정책은 소수점을 차단했고 단가 3자리 정책은 `1.2345`를 `1.234`까지만 허용했다. 사용자가 모든 데이터가 테스트 데이터라고 확인한 후 수량 `12`, 단가 `1.234`로 실제 수주를 저장했다. 저장 성공 및 저장 버튼 비활성화를 확인했고, 수주현황 상세와 수정 화면에서 재조회한 수량 `12`, 단가 `1.234`, 공급가 `15`, 부가세 `2`, 합계 `17`이 저장 전 표시와 같았다. 테스트 수주는 비고로 구분하여 남겼다.
- 같은 로그인 환경에서 테스트 견적의 수량 `12`, 단가 `1.234`, 견적금액 `15`를 저장하고 현황 상세에서 재조회했다. 공급가 `15`, 부가세 `2`, 총액 `17`도 확인했다.
- 위 테스트 수주에서 자동 생성된 출하계획을 수량 `12`에서 `11`로 수정 저장하고 현황 상세에서 수주수량 `12`, 계획수량 `11`을 재조회했다.
- 테스트 직출하는 수량 `12`, 단가 `1.234`, 공급가 `15`, VAT `2`, 합계 `17`로 표시됐으나 저장 API가 HTTP 500을 반환했다. 서버 로그의 원인은 자동 거래명세서 발행 중 `tb_sales_statement_hd.customer_id`가 없다는 PostgreSQL 오류다. 기본 읽기 전용 DB MCP의 `list_tables`, `describe_table`로 해당 컬럼이 없는 것을 확인했다. 따라서 출하 저장·재조회와 실제 거래명세서 검증은 미완료이며, 공유 정책이나 DB 스키마는 변경하지 않았다.
- 서버 공통 `DecimalColumnRule`이 업무에서 제공한 타입 기본값과 컬럼별 부분 예외를 해석하도록 분리했다. 정책 조회, 업무 계산 및 스냅샷 검증 연결은 각 업무 책임이며 F1-Grid 개발자 문서에 예시와 동시 배포 주의사항을 기록했다. 공통 규칙과 영업 서비스 테스트 및 해당 운영 Java의 `javac --release 8` 검증을 통과했다.
- 테스트 전용 계약과 빈 격리 PostgreSQL에서 실제 수주 서비스·Mapper 저장 후 수량 `1`, 단가 `1.235`, 공급가 `1.24`, 수동 VAT `0.1`, 행 합계 `1.340`, 헤더 합계 `1.3`을 재조회했다. 견적·출하는 동일한 테스트 계약으로 서비스 계산과 모의 DAO 전달을 확인했으며 실제 DB 저장 검증은 아니다. 격리 서버는 종료했다.

- 실제 DB의 대상 컬럼 메타데이터 확인 결과를 누적 스키마 문서와 양쪽 변경 이력에 반영했다.

## 후속 작업

나머지 영업 연계 화면의 2자리 제한 및 필드 의미를 점검하고, 작업지시서·계획서·상세사양서의 실제 로그인 저장·재조회와 반응형 검증을 수행해야 한다. 프론트·서버 계약 동시 배포와 구버전 API 호출 호환성도 확인해야 한다. JSON 토큰 파서와 그리드 정밀 모드의 추가 경계 사례는 별도 검증이 필요하다.

사용자가 실제 DB 스크립트를 직접 적용했으며 읽기 전용 MCP에서 대상 컬럼의 타입을 확인했다. 에이전트는 공유 DB에 SQL을 직접 적용하지 않았다. 로그인된 화면에서 수주 1건을 저장·재조회했으나 다른 업무의 저장·재조회와 실 화면 반응형 검증은 미완료다. 앞의 모의 API·합성 스키마의 격리 PostgreSQL·PGlite·컴포넌트 검증은 이를 대체하지 않는다.
