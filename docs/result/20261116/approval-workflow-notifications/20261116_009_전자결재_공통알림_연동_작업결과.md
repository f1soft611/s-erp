# 전자결재 공통 알림 연동 작업 결과

## 작업 내용

- 결재 시스템 이력 생성 결과인 `comment_id`를 반환해 알림 `sourceId`로 사용한다. 알림 이동 대상 `targetId`는 이력의 `owner_id`인 결재 문서 ID로 해석한다.
- 상신/재상신은 현재 `PENDING`인 결재자, 다음 단계 전환은 활성화된 단계의 대기자에게 알린다. 최종 승인·반려·보완요청·기안자 최종확인 요청은 기안자에게, 업무연락은 활성 `REFERENCE` 참여자에게 알린다.
- 결재선의 tenant 및 활성 계정을 조회하고 행위자 본인과 중복 수신자를 제외한다. 같은 단계에 `PENDING` 결재자가 남으면 알림을 발행하지 않는다.
- 공통 알림의 `APPROVAL_WORKFLOW` / `APPROVAL_STATUS_EVENT` 조합을 허용하고, 알림함 검증·분류·필터·전자결재 문서 이동을 확장했다. 기존 Web Push 및 실시간 알림 흐름을 재사용한다.
- migration/rollback/변경 이력과 스키마 요약을 갱신했다. SQL은 참고 초안으로 작성했으며 실제 DB에는 적용하지 않았다.

## DB 확인 제한

기본 PostgreSQL MCP의 테이블 목록과 `tb_notification`, `tb_electronic_approval_main`, `tb_electronic_approval_line_info` 컬럼 메타데이터 조회는 성공했다. `tb_notification` CHECK 제약을 확인하는 제한 metadata 조회는 실패해 라이브 CHECK 정의는 확인하지 못했다. 저장소의 `20261030_005` DDL을 대체 근거로 삼아 `chk_notification_event_source` 확장 초안을 작성했으며 실제 DB에는 적용하지 않았다.

## 이메일 후속 정책

이번 변경에서는 이메일을 발송하지 않았다. 저장소에 Spring Mail 의존성과 SMTP 설정은 있지만 실제 발송 서비스는 확인되지 않았다. 향후 중요 결재 알림에 대해 푸시가 모든 활성 기기에서 최종 실패했거나 활성 푸시 기기가 없는 경우에만 대체 메일을 검토한다. 수신자는 해당 알림의 수신자 본인이고 발신자는 시스템 주소다. 단순 미읽음은 미수신 근거로 보지 않으며, 인앱 알림 저장 실패를 이메일로 우회하지 않는다. 실제 메일 구현 전 명시적 수신 동의, 이메일 검증, 비밀정보 관리, 중복 억제, 별도 outbox/재시도 및 메일 실패 운영 추적을 별도 승인해야 한다.
