# 출하계획 API 호환성 검토 결과

## 범위와 결론

2026-11-12 품목 기준 연계 전후의 출하계획 계약과 저장소 내 호출자를 대조했다. 동일한 `/api/v1/sales/delivery-plans` 경로에서 요청·응답과 목록 단위가 변경되어 구버전 클라이언트와 호환되지 않는다. 현재 프론트엔드는 행별 수주 ID 계약을 사용한다. 저장소 밖의 소비자와 실제 배포 버전은 확인하지 못했다.

새 사양은 다중수주 계획을 허용하므로 단일 수주 대표값을 임의로 복원하면 출처가 잘못 표현되거나 구버전 수정 시 다른 상세가 삭제될 위험이 있다. 이번 검토에서는 API·DB 변경과 배포를 수행하지 않았다.

## 확인된 변경

| 구분 | 이전 계약 | 현재 계약 및 영향 |
|---|---|---|
| POST·PUT 요청 | 헤더 `salesOrderId`, 각 상세 `salesOrderDetailId` | 각 상세에 `salesOrderId`가 필요하다. 이전 요청은 현재 MANUAL 생성 경로에서 400으로 거부된다. PUT도 행별 ID를 요구한다. |
| 단건·생성·수정 응답 | 헤더에 수주 ID·번호·일자 및 거래처 ID·코드·명 | 이 헤더 필드가 제거되었다. 상세의 수주·거래처 정보를 확인해야 한다. 구버전 상세 화면은 헤더 필드를 참조한다. |
| 현황 | 계획 헤더 단위 행 | 계획 상세 단위 행. 동일 계획이 여러 행으로 나타날 수 있고 날짜 필터도 상세 행에 적용된다. |
| 수주별 단일 계획 조회 | 수주별 조회 경로 사용 | `/by-order/{salesOrderId}`는 AUTO만 허용하며 MANUAL은 409로 거부한다. MANUAL은 한 수주가 여러 계획에 포함될 수 있다. |
| DB | 계획 헤더가 `sales_order_id`를 보유 | 헤더 컬럼이 제거되고 상세가 수주를 참조한다. 구버전 Mapper는 제거된 헤더 컬럼을 참조하므로 기존 서버와 변경 스키마를 함께 운영할 수 없다. |

기준 이력: `578a828c^`와 `578a828c`의 요청·응답 모델, `cead60bc`의 현황 변경, `a259b627`의 MANUAL 조회 제한. 로컬에 마지막으로 가져온 `origin/main`과 `origin/socra710` 참조는 `578a828c`를 포함한다. 실제 배포 여부를 뜻하지 않는다.

저장소 내 직접 HTTP 호출은 `frontend/src/pages/sales/delivery-plan/services/salesDeliveryPlan.service.ts`와 등록·현황 화면에서 확인했다. 외부 연동, 오래 열린 브라우저 탭, 캐시된 배포본의 사용 여부는 확인하지 못했다.

## 재현과 확인 근거

- 격리된 커밋 스냅샷에서 Spring의 Jackson 빌더와 모의 DAO를 사용하는 임시 단위 검사 2건을 오프라인으로 실행했다. 기존 형태 `{"salesOrderId":1,"details":[{"salesOrderDetailId":2,"plannedQty":1}]}`는 상세 수주 ID가 비어 있고 MANUAL 생성 서비스에서 400으로 거부되며 헤더 저장을 호출하지 않았다. 현재 응답 모델에는 기존 헤더 수주 ID·수주번호·거래처명이 없다.
- 검사는 서비스·직렬화 수준이며 실제 HTTP 서버, 인증, 운영 데이터, 배포본은 검증하지 않았다. 임시 검사에서 Spring 컨텍스트와 실제 DB를 시작하지 않았다.
- 기본 읽기 전용 DB MCP의 `list_tables`, `describe_table` 및 `information_schema` 제약 메타데이터 조회에서 계획 헤더에 `sales_order_id`가 없고 상세에는 필수 `sales_order_id`가 있음을 확인했다. 확인 대상은 MCP가 연결한 DB뿐이며 운영 DB와 동일하다고 가정하지 않는다. 업무 행은 조회하지 않았다.
- 기존 화면 참고: [품목 기준 출하 선택 화면](screenshots/historical-item-flow.png). 기존 작업 캡처이며 이번 호환성 시험 화면이 아니다.

## 권장 전환 절차

1. 배포 담당자가 실제 배포 버전과 외부 API 소비자, 열린 구버전 탭 및 캐시를 확인한다. 구버전 유지가 필요하면 별도 버전 계약과 다중수주 계획의 조회·수정 제한을 먼저 설계하고 검증한다.
2. 동시 전환을 선택하면 승인된 점검 시간에 관련 쓰기를 중지하고 기존 요청을 배출한다. 대상 DB 백업 및 현재 스키마를 확인하고, 필요한 경우에만 승인된 `20261112_009_allow_multi_order_sales_delivery_plan.sql`을 적용한다. 이미 적용된 DB에 재적용하지 않는다.
3. 호환되는 백엔드와 프론트엔드를 함께 배포하고 구버전 탭·캐시를 갱신시킨다. 혼합 버전으로 쓰기가 재개되지 않도록 제어한 후 격리된 합성 데이터로 MANUAL 다중수주 등록·수정, AUTO 수주별 조회, 상세별 현황과 출하 연계를 확인한다.
4. 롤백 전 기존 [롤백 스크립트](../../../database/20261112/20261112_009_rollback_multi_order_sales_delivery_plan.sql)의 가드를 확인한다. 빈 계획, 다중수주 계획 또는 동일 수주를 공유하는 복수 계획이 있으면 구 스키마로 자동 복구할 수 없다. 이 경우 임의 데이터 변환이나 롤백을 실행하지 않는다.

## 미해결

- 실제 소비자 목록, 캐시 정책, 배포 상태 및 대상별 DB 스키마 확인이 필요하다.
- 구버전 동시 운영이 필요한지에 따라 별도 API 버전·쓰기 보호·마이그레이션 정책을 확정해야 한다. 현재 코드의 호환성 문제는 수정되지 않았다.
