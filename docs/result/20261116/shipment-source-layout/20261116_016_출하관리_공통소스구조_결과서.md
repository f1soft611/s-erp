# 출하관리 프론트·백엔드 공통 소스 구조 결과서

## 구현 결과

출하관리 상위 폴더를 `shipment`로 통일하고 `delivery`, `deliveryplan`, `statement`를 같은 깊이에 배치했다.

```text
frontend/src/pages/sales/shipment/
  delivery/
  deliveryplan/
  statement/

backend/src/main/java/egovframework/let/sales/shipment/
  delivery/
  deliveryplan/
  statement/

backend/src/main/resources/egovframework/mapper/let/sales/shipment/
  delivery/
  deliveryplan/
  statement/

backend/src/test/java/egovframework/let/sales/shipment/
  delivery/
  deliveryplan/
  statement/
```

- 기능 내부의 등록·현황, 컴포넌트·훅·서비스·타입·data 및 백엔드 계층 구조를 유지했다.
- Java package/import/FQCN, 수주의 출하계획 의존 import, Mapper 모델 참조와 테스트 리소스 경로를 갱신했다.
- 프론트 대시보드·테스트·mock·브라우저 동적 import를 최종 위치로 갱신했다.
- 이동 직전 소스와 비교해 프론트 운영 모듈 31개는 import만, 백엔드 운영 모듈 30개는 package/FQCN만 달라졌음을 확인했다.
- Mapper 3개의 SQL 본문, API·메뉴 경로, page key, Bean/Mapper 이름, 권한 및 JSON 계약은 유지했다.
- 기존 견적관리 등 미커밋 작업을 보존했다. 커밋·푸시·서버 재시작은 수행하지 않았다.

## 이후 에이전트 지침

다음 지침서에 공통 메뉴/업무 계층과 출하관리의 고정 구조를 기록했다.

- [루트 AGENTS.md](../../../../AGENTS.md): 프론트·백엔드·Mapper·테스트의 업무 계층과 이름 일치, 과거 구조 재사용 금지, 참조 동시 갱신.
- [프론트 AGENTS.md](../../../../frontend/AGENTS.md): 등록·현황과 `components`, `hooks`, `services`, `types`, `data` 책임 분리 및 공유 범위.
- [백엔드 AGENTS.md](../../../../backend/AGENTS.md): 출하 패키지·Mapper·테스트 경로, 내부 계층, 이전 빌드 중복 방지와 Java 8 검증.

실제 역할이 없는 빈 폴더나 형식적인 계층을 만들지 않으며 소스 위치 때문에 API·SQL을 임의 변경하지 않도록 명시했다.

### 명령과 검증 중 조정

```powershell
cd backend
mvn test '-Dtest=SalesDelivery*Test,SalesStatement*Test,SalesOrderServiceImplTest' '-Dmaven.compiler.release=8' '-Dmaven.compiler.testRelease=17'

cd ..\frontend
npm run test -- tests\sales-delivery-api.test.ts tests\sales-delivery-page.test.tsx tests\sales-delivery-plan-api.test.ts tests\sales-delivery-plan-page.test.tsx tests\sales-statement-page.test.tsx tests\sales-statement-routing.test.tsx tests\statement-print-layout.test.tsx
npm run build
npm run lint -- src\pages\sales\shipment src\pages\dashboard\components\DashboardContent.tsx
```

- 이동 전에 새 프론트 모듈·Mapper 경로를 테스트에 먼저 적용해 파일/리소스 부재로 실패함을 확인했다.
- 백엔드는 Maven clean 후 운영 코드를 `release=8`로 컴파일했다. 처음에는 이 옵션이 기존 전체 테스트 소스에도 적용되어 Java 9+ API 사용 테스트의 컴파일이 실패했다. 운영 `release=8`, 개발·테스트 `testRelease=17`로 분리해 95개 테스트를 통과시켰으며 POM이나 무관한 테스트 코드는 변경하지 않았다.
- 프론트 첫 동시 검증에서는 2개 UI 테스트가 기존 5초 제한에 도달했다. 운영 코드나 테스트 제한 시간을 변경하지 않고 빌드 후 재실행해 65개가 통과했다.
- 브라우저 테스트는 격리된 컨텍스트의 합성 API 응답만 사용했고 미등록 API 요청을 차단했다. 4173의 기존 프로젝트 서버를 재사용했으며 종료하지 않았다.
- 브라우저 스크린샷 저장 위치는 각 테스트의 선택적 `SALES_DELIVERY_ITEM_FLOW_SCREENSHOT_DIRECTORY`, `SALES_STATEMENT_FLOW_SCREENSHOT_DIRECTORY` 환경변수로 이번 결과 폴더를 지정해 과거 결과를 덮어쓰지 않았다.
- Java 8 검증은 운영 소스 API 호환 컴파일 범위다. 기존 제3자 의존성을 포함한 전체 Java 8 배포 환경의 실행 검증을 새로 수행한 것은 아니다.

## DB MCP와 스키마

기본 `s-erp-postgresql-readonly`의 `list_tables`를 호출한 뒤
`tb_sales_delivery_hd`, `tb_sales_delivery_plan_hd`, `tb_sales_statement_hd`에 `describe_table`을 호출해 현재 메타데이터를 확인했다.
데이터 행, 인증 정보, 연결 문자열은 조회하거나 기록하지 않았다.

테이블·컬럼·SQL·데이터 변경이 없으므로 신규 마이그레이션/롤백 스크립트와 스키마 문서 변경은 없다.
Mapper는 기존 재귀 리소스 검색 설정을 그대로 사용한다.
