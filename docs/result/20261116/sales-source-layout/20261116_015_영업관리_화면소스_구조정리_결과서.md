# 영업관리 화면 소스 구조 정리 결과서

## 작업 내용

- 출하계획 화면 폴더를 `frontend/src/pages/sales/delivery-plan/`에서 `frontend/src/pages/sales/delivery/plan/`으로 이동했다.
- 거래명세서 화면 폴더를 `frontend/src/pages/sales/statement/`에서 `frontend/src/pages/sales/delivery/statement/`으로 이동했다.
- 이동에 따라 화면·테스트·브라우저 테스트의 import 경로와 내부 상대 경로를 갱신했다.
- 메뉴/API 경로, 화면 동작, 데이터 계약은 변경하지 않았다. 수주 화면과 견적관리 등 범위 밖 기능은 유지했다.

- 출하 품목 브라우저 흐름: 375px, 768px, 1280px에서 통과.

## 추가 요청 반영: 기능 내부 책임 분리

메뉴 폴더만 이동했던 1차 정리에 이어 거래명세서의 평면 구조도 수주관리 기준으로 정리했다.

| 역할 | 최종 위치 |
|---|---|
| 등록 페이지 | `statement/create/SalesStatementCreatePage.tsx` |
| 등록 UI | `statement/create/components/` |
| 등록 상태·저장 처리 | `statement/create/hooks/useSalesStatementCreate.ts` |
| 등록·출하선택 컬럼 | `statement/create/data/` |
| 등록 전용 props·액션 타입 | `statement/create/types/` |
| 현황 페이지 | `statement/status/SalesStatementStatusPage.tsx` |
| 현황 상세·편집 UI | `statement/status/components/` |
| 현황 조회·상세 상태 | `statement/status/hooks/useSalesStatementStatus.ts` |
| 현황 컬럼·검색조건 | `statement/status/data/` |
| 공유 출력 UI·CSS | `statement/components/` |
| 출력 금액·페이지 계산 | `statement/data/statementPrint.ts` |
| 공유 API | `statement/services/salesStatement.service.ts` |
| 공유 타입 | `statement/types/salesStatement.types.ts` |

기존 파일의 상태 초기값, effect 의존성, 권한, 이벤트 순서, 출력 계산 및 그리드 옵션을 유지했다.
대시보드와 테스트는 최종 경로를 참조하며, 이전 평면 경로를 호환용 재수출 파일로 남기지 않았다.
백엔드·DB·API 계약은 변경하지 않았다. 기존 견적관리 등 미커밋 작업은 보존했다.

### 추가 검증

- 경로 변경을 테스트에 먼저 적용한 후 두 테스트 파일이 새 모듈 부재로 실패함을 확인했다.
- `npm run test -- tests/sales-statement-page.test.tsx tests/statement-print-layout.test.tsx tests/sales-statement-routing.test.tsx`: 3개 파일, 5개 테스트 통과.
- `npm run build`: 통과.
- 거래명세서 폴더, 대시보드 연결 및 변경 테스트 lint: 오류 없이 종료. 기존 effect 경고 3건은 등록/현황 hook으로 이동한 동일 코드에 남아 있다.
- `node tests/sales-statement-flow.browser.mjs`: 375px, 768px, 1280px에서 출하 선택→신규 저장→현황 상세→수정 저장→출력 미리보기 통과.
- 브라우저 검증은 새 격리 컨텍스트의 합성 API 응답만 사용했다. 실제 API 요청은 차단했으며 기존 4173 서버를 재사용하고 종료하지 않았다.
- 각 폭에서 페이지 수준 가로 넘침과 uncaught page error가 없음을 확인했다.
- 이전 평면 모듈 경로 참조가 없고 `git diff --check`가 통과함을 확인했다.
