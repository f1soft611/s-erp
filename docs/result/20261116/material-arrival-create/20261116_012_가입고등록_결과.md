# 20261116_012 가입고등록 결과

기준: [작업지시서](../../../directions/20261116/20261116_012_가입고등록_화면_작업지시서.md), [계획서](../../../plan/20261116/20261116_012_가입고등록_화면_계획서.md), [사양서](../../../spec/20261116/20261116_012_가입고등록_화면_상세사양서.md)
가입고현황과 함께 진행했다: [가입고현황 결과](../material-arrival-status/20261116_013_가입고현황_결과.md)

## 구현 범위
- DB: 가입고 테이블 2개(`tb_material_arrival_hd/dt`), 입고관리 그룹과 가입고등록·가입고현황 메뉴. 스크립트는 사용자가 실행했다.
- 백엔드: 후보 조회, 가입고 저장·조회·수정·취소, 발주 쪽 가입고 연동 검증.
- 프론트: 가입고등록 화면(발주 불러오기 창 포함), 메뉴 라우팅 연결.

## 기준 화면
발주등록(`materials/order/create`)과 같은 구조다: 헤더 폼 + F1Grid, 선택 창에서 구매처를 칩으로 고정, `embedded` 모드 재사용. 등록 화면 안에는 기존 건 조회·검색을 두지 않았다(현황 화면에서 처리). MES 화면은 검토용으로만 참고했다.

## 사양과 구현의 차이
- 창고 검증은 발주와 같이 `disuse_at='N'`만 확인한다(사양서 초안의 `stock_io_at='Y'`는 발주에서 선택한 창고가 막힐 수 있어 적용하지 않았다). 사양서 3.3을 이에 맞게 읽는다.
- 동시 저장 방지를 위해 발주 행을 잠근 뒤 같은 행을 새 문장으로 다시 읽어 잔량을 확인한다(잠금 대기 중 커밋된 가입고 반영).
- 불러오기 창에 발주일 기간(시작·종료)과 검색어 입력을 두었고, 구매처 검색은 검색어에 포함된다.

## DB 근거 (MCP 확인)
- 구현 전: `s-erp-postgresql-readonly`로 `tb_purchase_order_hd/dt`(`inspect_at`, `warehouse_id`, `receipt_close_at`, `unit_price`), `tb_customer_info`, `tb_warehouse`, 메뉴 구조를 확인했다. 재고 테이블은 없음.
- 스크립트 실행 후: `describe_table`과 `pg_constraint`, `pg_indexes`, `tb_menu` 조회로 테이블 2개, 제약(체크·FK·유일), 인덱스 4개, 메뉴 3종과 권한(`READ,UPDATE` / `EXCEL,READ`)·역할 권한(각 4건)이 사양과 일치함을 확인했다. 행 데이터는 조회하지 않았다.
- 스크립트: [20261116_002](../../../database/20261116/20261116_002_create_material_arrival_schema.sql), [20261116_003](../../../database/20261116/20261116_003_seed_material_arrival_menu.sql), [20261116_004](../../../database/20261116/20261116_004_seed_material_arrival_status_menu.sql). `db-schema.md` 갱신 완료.

## 실서버 종단 확인 (2026-11-16)
8080 백엔드를 `mvn clean spring-boot:run`(dev 프로필)으로 새 코드로 재기동하고, 개발 DB(테넌트 1)에 실제로 호출해 확인했다. 계정 정보는 문서에 남기지 않았다.
- 후보 조회 → 거절 3종(잔량 초과 400, 단가 누락 400, 구매처 불일치 400) — 잔량 초과 거절은 2026-11-17에 허용으로 변경됨(아래 추가 변경 참고)
- 가입고 A 등록(`MP-20261116-0001`): 발주 2행(수량 5·8, 단가 1,000·2,000, 제조일·소비기한 입력) → 공급가 21,000, 세액 2,100, 합계 23,100, 번호 채번, 담당자·등록자 저장
- 등록 후 발주 잔량 감소(15→10, 20→12), 현황 목록·단건 조회(수정 상한 잔량 = 발주수량 − 다른 가입고)
- 발주 연동 차단 4종 모두 409: 가입고 있는 행 삭제, 수량 축소, 검사대상 변경, 발주 취소(차단 메시지 확인)
- 수정: 행 2 삭제 + 행 1 수량 6 → 공급가 6,000, 행번호 재정렬, 삭제된 행의 잔량 복원(20), 수정 시 잔량 초과 400(2026-11-17 허용으로 변경)
- 가입고 B 등록(`MP-20261116-0002`) → 취소 → 잔량 복원, 재취소 409
- 입고대기마감: 발주 행 마감 시 후보에서 제외되고 해제하면 다시 나타남(발주 4번 행 9를 임시 마감했다가 `N`으로 원상 복구)
- MCP로 저장 상태 재확인: 헤더·상세 금액, `use_at`(A=Y, B=N), `created_by=admin`/`updated_by` 기록, `lot_no` 빈값, 제조일 2026-11-10·소비기한 2027-11-09, 발주 5번 원본 수량(15·20) 불변, 마감 행은 기존 1건(11/13 작업)뿐
- 실서버 연결 브라우저(1920/1280px): 발주 불러오기에서 면세 발주 2행 선택 → 세액 0·포함 스위치 비활성, 현황에서 정상·취소 건 조회 → 상세 패널 → 수정 다이얼로그. 페이지 오류 0건, 실패한 API 호출 0건. 저장·취소는 브라우저에서 하지 않았다.
- 남긴 테스트 데이터: 가입고 A(정상), 가입고 B(취소). 삭제하지 않았다.

## 추가 변경 (2026-11-17): 발주 잔량 초과 허용 + 확인창
- 요구: 가입고수량이 발주 잔량을 넘어도 등록할 수 있어야 하고, 등록 전에 예/아니오로 묻는다.
- 서버: 잔량 초과 400 검사 삭제(등록·수정 공통). 수량 0 이하 거부, 발주 행 잠금·재조회는 유지. 별도 확인 플래그는 두지 않았다(합의).
- 화면: 셀 검증과 `validateArrivalInput`의 잔량 초과 오류 삭제. 저장 시 잔량 초과 행이 있으면 확인창("발주 잔량을 초과한 품목이 N건 있습니다. 그대로 등록(수정)하시겠습니까?") → 확인이면 저장, 취소면 저장하지 않고 화면 유지. 가입고현황 수정 다이얼로그도 같은 폼이라 동일 적용.
- 영향: 초과 가입고가 있으면 발주 잔량이 음수가 되어 불러오기 목록에서 해당 발주 행이 빠진다. 발주 쪽 수량 축소·행 삭제·취소 차단(409)은 그대로다.
- 검증: 서버 서비스 테스트 `allowsQuantityOverTheOrderRemainingButStillRejectsZero`·`updateAllowsQuantityOverTheRemaining`(관련 `MaterialArrival*`·`PurchaseOrderArrivalGuardTest` 통과), 프론트 `material-arrival-create`(11)·`material-arrival-status`(6) 통과, `tsc --noEmit` 통과, 합성 API 브라우저 1280px에서 수량 12 입력 → 확인창 → 취소(저장 안 됨) → 확인(수량 12로 저장) 확인: [over-remaining-confirm-1280](screenshots/over-remaining-confirm-1280.png).
- 실서버(8080, 2026-11-17 재기동) API 확인: 발주 행(발주 30·기가입고 0) 잔량 30에 33 등록 성공(`MP-20261117-0001`), 수량 0은 400, 35로 수정 성공, 초과 후 불러오기 목록에서 해당 발주 행 제외, 현황 조회 정상. 테스트 데이터는 남겼다. 확인창은 합성 API 브라우저로만 확인했다(실서버 브라우저 저장 클릭은 미확인).
- 커밋 메시지(복사용): 제목 `가입고 발주 잔량 초과 허용 및 저장 전 확인창 추가` / 내용: 서버 잔량 초과 거부 제거, 초과 시 예/아니오 확인 후 등록·수정, 테스트·문서 갱신.

## 확인하지 못한 것
- 합성 API가 아닌 실서버 브라우저에서 "저장 버튼 클릭" 흐름은 하지 않았다(저장 API는 위 종단 시나리오에서 직접 호출해 확인).
