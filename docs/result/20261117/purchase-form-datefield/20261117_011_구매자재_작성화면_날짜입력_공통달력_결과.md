## 결과 요약
구매자재 작성 화면 여섯 곳(구매요청등록·구매요청확정·발주등록·가입고등록·입고등록·자재수입검사등록)의 날짜 입력을 브라우저 기본 날짜 입력(`type="date"`)에서 공통 달력 `DateEditor` 기반 입력으로 바꿨다. 한국어 달력과 축약 입력(`1118`, `20261118`)을 쓰고, blur에서 `YYYY-MM-DD`로 확정하며, 무효 날짜는 입력을 보존한 채 필드 오류를 보인다. 저장 직전에 다시 정규화해서 blur 없이 저장해도 payload 날짜는 항상 ISO이고, 무효 날짜는 요청을 보내지 않는다. API·DB 변경 없음.

## 변경
- 신규 공통 컴포넌트 [FormDateField](../../../../frontend/src/shared/components/FormDateField.tsx): `DateEditor`(outlined) + blur 정규화 + 오류 표시 + 외부 오류 지원, `normalizeFormDate()`(저장 직전 검증용). 영업은 같은 동작을 페이지마다 직접 구현했지만 구매자재는 여섯 화면이라 한 곳에 두었다(영업 파일은 수정하지 않음).
- 화면: [구매요청등록](../../../../frontend/src/pages/materials/request/create/PurchaseRequestCreatePage.tsx), [구매요청확정](../../../../frontend/src/pages/materials/request/confirm/PurchaseRequestConfirmPage.tsx), [발주등록](../../../../frontend/src/pages/materials/order/create/PurchaseOrderCreatePage.tsx), [가입고등록](../../../../frontend/src/pages/materials/arrival/create/MaterialArrivalCreatePage.tsx), [입고등록](../../../../frontend/src/pages/materials/receipt/create/MaterialReceiptCreatePage.tsx), [자재수입검사등록](../../../../frontend/src/pages/quality/inspect/create/MaterialInspectionCreatePage.tsx). 날짜 입력 교체와 저장 직전 정규화(`올바른 ○○일을 입력해 주세요.`)를 적용했다. 서버 날짜 기본값(`20261117_010`)과 사용자 입력 우선 규칙은 그대로다.
- 편집 불가 상태(조회 전용, 취소된 문서, 입고대기마감 모드 등)에서는 입력과 달력 버튼이 모두 비활성이고 달력이 열리지 않는다.

## 확인하지 못한 것
- 저장 직전 정규화는 입고등록 화면 테스트로만 payload까지 확인했다. 나머지 다섯 화면은 같은 패턴의 코드를 적용했고 브라우저에서 입력·정규화·달력을 확인했지만, 각 화면의 저장 payload 날짜는 개별 테스트하지 않았다.
- 구매요청확정·발주등록에서 날짜를 가격 조회(`fetchDefaultUnitPrice`)에 쓰는 경로는 입력값 그대로이므로, blur 전에 담기 단추를 누르면 정규화 전 값이 갈 수 있다(기존 동작, 이번 범위에서 변경하지 않음).
