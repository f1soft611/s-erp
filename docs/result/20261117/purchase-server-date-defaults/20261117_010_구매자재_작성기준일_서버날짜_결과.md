요청 출처: Flow 글 [영업관리 작성 기준일을 서버날짜로 통일](https://flow.team/l/QzqMr)(88346262)과 댓글의 지침서 세 개(저장소 `AGENTS.md`, 팀 개발 규칙, `frontend/AGENTS.md` — 확인함).

## 결과 요약
구매자재 작성 화면 여섯 곳의 오늘 날짜 기본값이 브라우저 시계(`new Date()`)에서 서버 날짜(`GET /api/v1/common/system-date`)로 바뀌었다. 서버 날짜를 못 가져오면 브라우저 날짜로 대체하지 않고 날짜를 비운 채 오류를 표시한다. 저장된 자료를 열면 저장된 날짜가 유지되고, 서버 날짜가 기본값으로 들어오는 것만으로는 저장하지 않은 변경으로 보지 않는다. 서버·DB 변경 없음.

## 변경
- 신규 공통 훅 [useServerDateDefault](../../../../frontend/src/shared/hooks/useServerDateDefault.ts): 신규 화면에서만 서버 날짜를 한 번 조회, 사용자가 먼저 날짜를 바꾸면 늦은 응답 무시, 초기화용 `reload`, 실패 시 오류 콜백(로컬 날짜 대체 없음), 언마운트 후 응답 폐기. 영업은 페이지마다 같은 코드를 넣었지만 구매자재는 여섯 화면이라 훅으로 만들었다(영업 파일은 수정하지 않음).
- 적용 화면: [구매요청등록](../../../../frontend/src/pages/materials/request/create/PurchaseRequestCreatePage.tsx)(요청일, 변경감지 baseline도 함께 갱신), [구매요청확정](../../../../frontend/src/pages/materials/request/confirm/PurchaseRequestConfirmPage.tsx)(확정일, 요청 불러오기 시 재조회), [발주등록](../../../../frontend/src/pages/materials/order/create/PurchaseOrderCreatePage.tsx), [가입고등록](../../../../frontend/src/pages/materials/arrival/create/MaterialArrivalCreatePage.tsx), [입고등록](../../../../frontend/src/pages/materials/receipt/create/MaterialReceiptCreatePage.tsx), [자재수입검사등록](../../../../frontend/src/pages/quality/inspect/create/MaterialInspectionCreatePage.tsx).
- 초기 날짜는 빈 값이고, 초기화(신규 단추 등)는 서버 날짜를 다시 조회한다. 날짜를 직접 입력하면 늦게 도착한 서버 날짜가 덮어쓰지 않는다.

## 참고(범위 밖으로 둔 것)
- 구매자재 작성 화면의 날짜 입력은 브라우저 기본 `type="date"` 입력이라 이번에 만든 공통 달력(`DateEditor`)을 쓰지 않는다. 입력 방식 교체는 별도 작업이다(영업은 별도 작업으로 `DateEditor`를 적용했다).
- 새로 들어온 빠른 날짜 세팅(`quickDates.ts`, 영업 담당자 구현)은 오늘·이번주·이번달 등을 `dayjs()`(브라우저 시계)로 계산한다. 검색 조건의 편의 단추이고 작성 기준일이 아니라 이번 범위에서 제외했다. 서버 날짜 기준으로 맞출지는 영업 담당자와 정해야 한다.

## 확인하지 못한 것
- 구매요청확정에서 "요청 불러오기" 후 확정일 재조회, 각 화면의 "신규" 단추 초기화는 단위 테스트 수준으로 확인하지 못했고 훅의 `reload` 테스트로 갈음했다(브라우저로도 클릭 확인은 하지 않음).
- 서버 날짜 도착 전에 저장하면 기존 필수 검증 메시지가 나간다(별도 처리 없음).
