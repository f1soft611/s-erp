# 20261117_001 입고등록 결과

입고현황과 함께 진행했다: [입고현황 결과](../material-receipt-status/20261117_002_입고현황_결과.md)

## 구현 범위
- DB: 입고 테이블 2개(`tb_material_receipt_hd/dt`), 입고등록·입고현황 메뉴. 스크립트는 사용자가 실행했다.
- 백엔드:
  - 입고 조회·수정·취소 API(`/api/v1/materials/material-receipts`), 번호 `MI-YYYYMMDD-NNNN`.
  - 가입고 저장 시 무검사(`inspect_at='N'`) 행으로 입고 자동 생성(같은 트랜잭션).
  - 입고 수정·취소가 연결된 가입고 행·헤더에 반영.
  - 가입고 쪽 행 단위 잠금(`validateEditable` 자리를 실제 검증으로 교체).
- 프론트: 입고등록 화면(edit/view는 현황에서 사용, create는 안내와 수입검사 불러오기 창 틀), 가입고 화면의 잠금 표시·자동 입고 안내·입고번호 열.

## 기준 화면
가입고등록(`materials/arrival/create`)과 같은 구조다: 헤더 폼 + F1Grid, `embedded` 모드, 같은 확인창(`useCommonConfirmDialog`). 구매처 고정·발주 불러오기는 없다. MES 입고등록은 검토용으로만 참고했고 불필요한 컬럼(사용용도, 수주·생산 연계, 도면, 위치, 실입고량, 매입마감 등)은 가져오지 않았다.

## 동작 요약
- 무검사 가입고 저장 → 입고 자동 등록. 저장 응답에 `autoReceiptNo`, `autoReceiptCount`가 있고 화면은 "무검사 품목 N건은 입고 MI-…에 자동 등록되었습니다"를 알린다.
- 입고 수정: 수량·단가·세액·창고·제조일·소비기한은 연결된 무검사 가입고 행에도 반영, 가입고 헤더 금액 재계산. 부가세 설정을 바꾸면 같은 가입고의 검사 대상 행 금액도 새 설정으로 다시 계산한다.
- 입고 행 빼기·취소: 무검사 행의 가입고 행을 삭제하고 행번호·금액을 다시 매긴다. 가입고 행이 하나도 남지 않으면 행은 이력으로 남기고 가입고 헤더만 취소한다. 확인창이 먼저 결과를 안내한다.
- 가입고 잠금: 입고가 생긴 행은 가입고에서 수정·삭제 불가, 가입고 취소·가입고일·부가세 변경 불가(비고와 입고 없는 행은 수정 가능). 서버는 409와 입고번호를 돌려주고 화면은 해당 행 읽기 전용, 취소 버튼 비활성, 안내문, 입고번호 열을 보여 준다.
- 수량이 발주 잔량을 넘으면 서버는 거부하지 않고 화면 확인창(예/아니오)이 맡는다(가입고와 같은 규칙).

## 사양과 구현의 차이
- 가입고 행이 전부 사라질 때는 행을 지우지 않고 가입고 헤더만 취소한다(사양서 4.2·4.3과 작업지시서에 반영). 지우면 취소된 가입고가 가입고현황에서 조회되지 않기 때문이다.
- 입고 INSERT는 `RETURNING`을 쓰는 `select` 문장이라 MyBatis 1차 캐시가 비워지지 않아, 같은 트랜잭션에서 가입고 행을 다시 읽으면 입고번호가 비어 있었다. 실서버 확인 중 발견했고 입고 INSERT 두 문장에 `flushCache="true"`를 지정했다(매퍼 테스트로 고정).
- 입고 수정 사양서의 응답 필드 목록은 구현 VO 기준으로 맞췄다.

## DB 근거 (MCP 확인)
- 구현 전: `list_tables`로 입고·수입검사·재고 테이블이 없음을 확인했다. 가입고·발주 구조는 `20261116` 사양과 같다.
- 스크립트 실행 후: `describe_table`, `pg_constraint`, `pg_indexes`, `tb_menu` 조회로 테이블 2개, 제약(체크·FK·유일, 가입고 행 FK `ON DELETE SET NULL`), 인덱스 5개, 메뉴 2종과 권한(`READ,UPDATE` / `EXCEL,READ`)·역할 권한(각 4건)이 사양과 일치함을 확인했다.
- 현황 목록의 등록자 조인은 `tb_user`에 `login_cd`가 없어서 `tb_login_account`를 거치도록 MCP로 구조를 확인한 뒤 작성했다. 행 데이터는 조회하지 않았다.
- 스크립트: [20261117_001](../../../database/20261117/20261117_001_create_material_receipt_schema.sql), [20261117_002](../../../database/20261117/20261117_002_seed_material_receipt_menu.sql), [20261117_003](../../../database/20261117/20261117_003_seed_material_receipt_status_menu.sql). `db-schema.md` 갱신 완료.

### 전체 테스트
- 백엔드 전체 `mvn test`(캐시 수정 이후 재실행): 1,177개 중 1건 오류, `MinioStorageConfigTest`(`application-prod.properties`가 `.gitignore` 대상이라 이 PC에 없음, 이번 변경과 무관한 기존 문제).
- 프론트 전체 `npm run test`는 돌리지 않았다. 변경 범위의 4개 테스트 파일만 실행했다(이전 작업에서 확인한 기존 실패 14건과 가입고 외 파일은 영향 범위 밖).

### 실서버 API 종단 (2026-11-17, 사용자가 재구동한 8080, 개발 DB 테넌트 1)
계정 정보는 문서에 남기지 않았다.
- 무검사 발주 행 가입고 저장 → 자동 입고 생성(`autoReceiptNo`, 건수 1), 가입고 행 응답에 입고번호 연결.
- 가입고 수정·취소 시도 → 둘 다 409, 메시지에 입고번호 포함.
- 입고 수정(수량 2→3, 단가 +100) → 가입고 행·헤더 합계 반영 확인.
- 입고 취소 → 가입고(행이 하나뿐인 경우) 헤더 취소, 입고 재취소 409.
- 입고현황 상태 3종: 기본(정상)에서는 취소건 제외, `CANCELED`·`ALL`에서 조회됨.
- 남긴 테스트 데이터: 가입고 `MP-20261117-0002`·입고 `MI-20261117-0001`(정상, 입고 연동 확인용), 가입고 `MP-20261117-0003`·입고 `MI-20261117-0002`(취소). 삭제하지 않았다.

## 확인하지 못한 것
- 무검사와 검사 대상이 섞인 가입고의 실서버 확인: 개발 DB에 같은 구매처·통화·부가세의 검사 대상 후보가 없어 서비스 단위 테스트(행 번호 재정렬, 부가세 변경 시 검사 대상 행 재계산)로만 확인했다.
- 실서버 브라우저에서 "저장·취소 버튼 클릭" 흐름은 하지 않았다(API 종단에서 직접 호출로 확인).
- 입고등록 create 모드의 수입검사 불러오기·수동 저장은 수입검사 작업에서 연결한다(이번에는 창의 틀과 안내만).
- 가입고현황 목록 자체는 입고번호를 보여 주지 않는다(상세·수정 화면에서만 보여 준다).
