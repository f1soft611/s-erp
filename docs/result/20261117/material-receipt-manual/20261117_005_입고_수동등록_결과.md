# 20261117_005 입고 수동 등록(수입검사 합격분 불러오기) 결과

기준: [작업지시서](../../../directions/20261117/20261117_005_입고_수동등록_수입검사합격분_작업지시서.md), [계획서](../../../plan/20261117/20261117_005_입고_수동등록_수입검사합격분_계획서.md), [상세 사양서](../../../spec/20261117/20261117_005_입고_수동등록_수입검사합격분_상세사양서.md)

## 결과 요약
입고등록 화면의 `수입검사 불러오기`를 실제로 연결했다. 입고 가능량(합격량 − 유효 입고 합)이 남은 수입검사 행을 여러 건 불러와(구매처 1곳·통화 1종 고정) 한 입고(`MI-…`)로 등록하고, 입고수량은 입고 가능량을 넘을 수 없다. 입고를 취소하면 가입고·검사는 그대로 두고 입고 가능량만 복구된다. 합격분이 입고된 수입검사는 취소·행 빼기·합격량 축소가 제한되고 입고번호가 안내된다. 입고 행·입고현황에는 검사번호가 보인다. 실서버 API 종단(여러 건)과 실제 브라우저(1280/768/375px) 확인을 통과했다.

## DB (MCP 확인 근거)
- 스크립트: [20261117_006 적용](../../../../backend/DATABASE/20261117/20261117_006_add_receipt_inspection_link.sql), [롤백](../../../../backend/DATABASE/20261117/20261117_006_rollback_receipt_inspection_link.sql), [변경이력](../../../../backend/DATABASE/20261117/20261117_006_change_receipt_inspection_link.md), [db-schema.md](../../../database/db-schema.md) 갱신. `docs/database`와 `backend/DATABASE` 사본은 같다(스키마 스크립트 테스트가 비교).
- 구현 전 MCP로 `tb_material_receipt_dt`에 두 컬럼이 없음, `tb_material_inspection_dt`의 PK를 확인했다. 사용자가 실행한 뒤 MCP로 컬럼 `material_inspection_detail_id`(bigint NULL)·`inspection_no`(varchar(30) NULL), FK `ON DELETE SET NULL`, 인덱스, 주석이 스크립트와 일치하고 기존 입고 2행의 연결 값이 NULL임을 확인했다.
- 새 SELECT 쿼리(후보, 입고 가능량, 검사 행의 기입고량)는 읽기 전용 MCP로 실제 DB에서 문법 오류 없이 실행됨을 확인했다. `FOR UPDATE OF idt, ih`는 실서버 종단 확인에서 검증했다.

## 구현
- 백엔드: 합격분 후보 조회(`GET /material-receipts/candidates`, 전체 건수 포함), 입고 수동 등록(`POST /material-receipts`: 구매처·통화 혼합 400, 중복 400, 입고 가능량 초과 409, 요청 전체 롤백), 입고 수정 시 검사 연결 행의 상한 = 입고 가능량 + 자기 수량, 입고 취소는 헤더만(가입고·검사 불변). 수입검사 서비스는 입고된 합격분이 있는 행의 취소·행 빼기·합격량 축소를 409로 막고 입고번호를 안내한다. 입고현황 응답에 검사번호. 검사 행과 검사 헤더를 ID 순서로 잠근 뒤 다시 읽어 입고 가능량을 계산하므로 입고 등록·수정과 검사 수정·취소가 직렬화된다.
- 프론트: 입고등록 create 모드(합격분 불러오기 창의 구매처 고정 칩·통화 혼합 안내·이미 담은 행 제외, 신규·저장, 검사번호·입고 가능량 열, 가능량 초과 오류, 발주 잔량 확인창은 무검사 행에만), 입고현황 검사번호 열과 상세 패널, 수입검사 화면의 입고된 행 안내·뺄 수 없음·검사 취소 비활성·입고량 열·합격량 최소값 검증.
- 그리드 `storageKey`는 기존 키를 그대로 쓴다(컬럼만 추가).

## 구현 중 보정과 사양서와의 차이
- 가입고 행에도 입고번호가 조회된다(입고 행이 가입고 행을 참조하므로). 가입고 행이 검사번호와 입고번호를 모두 가지면 잠금 안내는 **검사번호를 우선** 보여 준다(검사에서 먼저 처리해야 하므로). 이 안내 순서 변경은 서버 재구동 전 확인이어서 단위 테스트로만 확인했다.
- 실서버 확인 중 검사 대상 발주 행(PO-20261113-0002)의 잔량이 소진되어 테스트용 직접 발주 `PO-20261117-0001`(검사 대상, 1000개)을 새로 만들었다.
- 브라우저 확인 스크립트 보강: 취소 확인창이 뜨면 아래 대화상자가 접근성 트리에서 숨겨져 "닫힘"으로 오인되던 타이밍 문제를 취소 API 응답 대기로 고쳤다(제품 결함이 아니라 스크립트 문제).

## 확인하지 못한 것
- 서로 다른 구매처의 검사 행이 한 입고에 섞이는 경우의 실서버 확인은 개발 DB에 구매처가 하나뿐이어서 하지 못했다(서비스·화면 테스트로 확인).
- 재고·LOT 연결, 매입마감, 입고 가능량 마감은 범위 밖이다.
- `app-router-not-found.test.tsx`의 "keeps the dashboard root path valid while the menu list is loading"는 이번 변경 전에도 3번 중 2번 실패하는 기존 불안정 테스트다. 전체 프론트 테스트(205개 파일) 실행은 별도로 하기로 했다.
- 개발 DB에는 확인 과정에서 만든 가입고·검사·입고가 남아 있다(성공한 데이터는 정리하지 않았고, 취소 확인에 쓴 데이터만 취소 이력으로 남아 있다).
