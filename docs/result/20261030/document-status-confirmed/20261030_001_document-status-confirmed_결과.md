# 문서현황 참조 확인 상태 조회 장애 수정 결과

## 원인 및 해결

- 참조 확인 완료 시 서버가 반환하는 `myActionStatus=CONFIRMED`가 문서현황의 정상 처리상태 목록에서 빠져 있었다.
- 응답의 각 행을 모두 검증하므로 확인 완료 참조 문서가 하나라도 섞이면 `전자결재 문서 검색 응답을 확인할 수 없습니다.` 오류로 전체 목록을 차단했다. 권한이나 조회 대상 부재가 원인은 아니었다.
- 기존 상태 옵션에 `CONFIRMED / 확인완료`를 추가하여 응답 검증·단일/복합 상태 표시·상세검색을 함께 일치시켰다.
- 프론트엔드 검색 타입 및 백엔드 문서현황 검색 허용 상태를 같은 계약으로 맞췄다. 기존 SQL, 사용자/테넌트 범위, 승인/합의 처리, 문서 상태 전이, 레이아웃은 변경하지 않았다.

## 검증

| 항목 | 결과 |
|---|---|
| 수정 전 회귀 | 단일·복합 `CONFIRMED` 응답 거부, 검색값 누락, 서버 필터 400 오류를 재현 |
| 문서현황 프론트엔드 관련 4개 파일 | 56개 통과, 기존 테스트 불일치 1개 실패 |
| 신규 확인 상태 검색 테스트 단독 | 1개 통과 |
| 백엔드 서비스·컨트롤러·Mapper | 34개 통과 |
| `npm run build` | 통과 |
| 변경 TypeScript 파일 oxlint | 통과 |
| Playwright Chromium, 375/768/1280px | 각 2개 합성 문서 정상 조회, `확인완료` 표시, 페이지 전체 가로 넘침 없음 |
| 변경분 직접 검토 및 `git diff --check` | 문제 없음 |

기존 실패는 `frontend/tests/document-status-search.test.ts`의 `maps trimmed inputs and date ranges to the existing filter names`다. 문서번호 검색으로 변경된 코드에 대해 이전 `electronicApprovalId` 변환을 기대한다. 수정 전 실패 실행에서도 동일하게 확인되었으며 이번 상태 수정과 무관하므로 변경하지 않았다. 전체 테스트가 모두 통과했다고 판단하지 않는다.

## DB MCP 및 범위

- 기본 `s-erp-postgresql-readonly`에서 `list_tables`와 문서·결재선·사용자 연결 테이블의 `describe_table`을 직접 호출했다.
- 제한된 `COUNT` 집계만으로 조회 대상 및 확인 완료 참조 문서가 존재함을 확인했다. 계정 정보, 인증 정보, 개별 업무 행은 문서/스크린샷에 저장하지 않았다.
- 데이터 및 스키마 변경 없음. 마이그레이션, 롤백 스크립트, 누적 스키마 변경 대상 아님.
- 기존 S-ERP `127.0.0.1:4173` 서버를 확인해 재사용했다. 기존 서버는 종료하지 않았다. 테스트 브라우저는 종료했다.
- 브라우저는 실제 문서현황 컴포넌트와 검증 경로에 합성 응답을 공급한 회귀 확인이다. 실제 사용자 로그인, 해당 인증 세션의 HTTP 요청, 실행 중 백엔드 재시작/배포는 수행하지 않았다.
- 커밋/푸시/병합 없이 현재 작업 트리에 수정 사항을 유지한다.
