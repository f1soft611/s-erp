# F1-Grid 상세검색 연동 가이드 개편 설계

## 목적

F1-Grid 문서 포털에서 상세검색을 처음 연결하는 개발자가 컬럼 설정부터 검색 UI, 조회 조건, API 요청까지 순서대로 따라 할 수 있도록 기존 안내를 실용적인 단계별 가이드로 개편한다.

현재 안내는 설명이 한 문단에 길게 모여 있고, 코드 예제는 설정과 상태/API 연결을 생략한 조각 수준이다. 이 때문에 `search` 메타데이터가 화면에 어떻게 반영되는지, 어떤 코드를 페이지에서 작성해야 하는지, 실제 API 조회는 누가 담당하는지 한눈에 파악하기 어렵다.

## 범위

- 기존 F1-Grid 포털의 `필터와 정렬` 문서 안에 있는 `PageSearchArea 상세검색 연동` 안내를 단계별 구성으로 재작성한다.
- 기존 메뉴 ID, 그룹, 포털 라우팅, 검색 기능, F1-Grid 및 `PageSearchArea` 런타임 동작은 변경하지 않는다.
- 문서 콘텐츠, 직접 관련된 문서 검색/표현 테스트, 지속 문서와 날짜별 작업 결과만 변경한다.
- 포털의 기존 `prose`, `code`, `api` 문서 섹션 렌더러를 사용한다. 전용 단계 UI나 새로운 콘텐츠 렌더러/컴포넌트는 추가하지 않는다.
- 저장소의 다른 업무 기능 또는 실제 업무 페이지는 수정하지 않는다.

## 대상 독자와 사례

- 대상은 F1-Grid 컬럼과 공통 페이지 검색 영역을 사용해 보려는 화면 개발자다. 상세검색 메타데이터나 콜백의 의미를 이미 안다고 가정하지 않는다.
- 전체 예제는 실제 기안양식 관리 화면에서 사용 중인 검색 항목과 책임 흐름을 따른다.
- 현재 기안양식 상세검색 항목은 분류(`categoryItemId`), 등록주기(`regTermId`), 사용여부(`useAt`)다. 분류와 등록주기 옵션은 코드 항목에서, 사용여부 옵션은 `Y`/`N` 값으로 정의된다. 자유 키워드는 별도 기본 검색 입력으로 유지된다.
- 현재 기안양식 화면은 등록일 상세검색을 제공하지 않는다. 날짜 범위는 현재 사례와 분리된 일반 확장 예제로만 소개하고, 실제 화면 계약이 아님을 명시한다.
- 현재 화면은 양식코드와 양식명 컬럼을 상세검색에서 숨기지만, 양식명은 별도의 기본 키워드 검색으로 지원한다. 예제에서 이 둘을 `search.hidden: true`로 설명해 검색 대상 제외와 기본 키워드 검색을 혼동하지 않게 한다.

## 제안된 정보 구조

하나의 연속된 긴 설명 대신 다음 읽기 순서를 사용한다.

1. **먼저 전체 흐름:** `Grid 컬럼의 search 설정 → toPageSearchFields 변환 → PageSearchArea 표시/입력 → 페이지의 조회조건 변환 → 목록/API 갱신`을 간단한 흐름으로 제시한다. Grid 헤더 필터와 페이지 상세검색의 차이를 구분한다.
2. **1단계 — 검색 필드 고르기:** 컬럼에서 검색할 필드만 `search`로 설정하고, 표시하지 않을 필드는 `search.hidden`으로 제외한다. 실제 기안양식 필드인 분류, 등록주기, 사용여부를 예로 든다.
3. **2단계 — 검색 UI 필드 만들기:** `toPageSearchFields(columns)`를 사용하고, 변환 결과의 `field`, `label`, `type`, `searchSpan`, `group`, `options`가 원본 컬럼의 어떤 설정에서 오는지 짧은 표로 설명한다.
4. **3단계 — PageSearchArea에 연결:** `detailFields`, `detailValues`, `onDetailValuesChange`, `onDetailSearch`가 각각 무엇을 책임지는지 설명하고, 검색 입력의 상태 보관과 검색 버튼 실행 순서를 작은 예시로 보여준다. 기본 키워드는 `searchField` / `onDefaultSearch` 흐름으로 상세검색과 구분한다.
5. **4단계 — 입력값을 실제 조회 조건으로 변환:** 상세검색 값의 예시를 `categoryItemId`, `regTermId`, `useAt` 조회조건으로 바꾸고, 기본 키워드를 포함해 페이지의 목록 로드 함수로 전달하는 책임 경계를 보여준다. 화면 저장 상태가 있을 때 검색 요청을 확인하는 것처럼 예제에서 생략한 실제 화면 정책은 임의로 꾸며내지 않는다.
6. **전체 예제 — 기안양식 검색:** 앞의 단계를 연결하는 일관된 TSX 예제를 제공한다. 컬럼/코드 옵션에서 검색 필드 정의, `useMemo` 변환, 기본 키워드와 controlled 상세검색 상태, `PageSearchArea` 연결, 상세값을 `DraftFormFilters`로 변환, 페이지의 조회 요청과 오류/로딩 전달까지 실제 화면 계약에 맞춰 보여준다. 기존 화면은 수정되지 않은 행에 대해서만 검색을 즉시 적용하고, 미저장 변경이 있으면 확인 절차를 거친다. 이를 안내해 예제가 현재 화면의 모든 편집 보호 동작을 포함하는 완전한 구현이라고 오해되지 않도록 한다.
7. **별도 예제 — 날짜 범위 추가:** `type: 'date'` 컬럼의 `{ from, to }` 입력값과 `search.span` 설정을 별도로 보여준다. 이는 일반 기능 예제이며 실제 기안양식 화면의 필터가 아니라고 표시하고, API에 전달할 기간 파라미터는 실제 API 계약 확인 없이 임의로 지정하지 않는다.
8. **빠른 참조 / 주의할 점:** 지원 타입 및 미지원 타입의 `text` fallback, `column.hidden`과 `search.hidden`의 차이, 옵션이 컬럼 `options`에서 전달되는 점, `search.span`과 행 폼 `form.span`의 구분, 정렬 기본 동작, 조회/API 책임이 페이지에 있음을 짧게 정리한다.

각 단계 설명은 짧은 문장과 명확한 소제목을 사용한다. API/옵션 계약 전체를 한 문단에 몰아넣지 않는다. 코드 식별자는 backtick으로 구분하고 한국어 용어를 먼저 써서 동작을 말한 뒤 코드 이름을 대응시킨다.

## 코드 예제 및 정확성 조건

- 상세검색 필드 metadata의 실제 타입/변환 구현 및 `PageSearchAreaProps` 정의를 따른다.
- `toPageSearchFields`는 검색 폼 정의를 생성할 뿐, 검색 조건을 조합하거나 Grid 데이터/API를 조회하지 않는다고 설명한다.
- `PageSearchArea`는 controlled `detailValues`를 읽고 `onDetailValuesChange`로 입력 변경을 알리며, 사용자가 상세검색을 실행하면 `onDetailSearch(values)`를 호출한다.
- 기본 검색어는 별도 상태이며 상세 검색 시 함께 조회하려면 페이지가 직접 결합한다. 기본 검색 실행 또한 페이지 callback/조회 흐름이다.
- 페이지는 입력값을 현재 화면 API가 받는 조회조건으로 변환하고 요청을 실행한다. API 오류 및 로딩 상태 역시 업무 페이지 책임이다.
- 기안양식 실제 흐름을 설명할 때 `handleDetailSearch`가 분류·등록주기 값은 숫자로 변환하고 `useAt`은 `'Y' | 'N'`만 허용하는 현재 코드를 반영한다. 이 조건을 실제 화면에서 검색하지 않는 `codeName` 같은 필드로 바꾸지 않는다.
- 기안양식 페이지의 `requestSearch`는 미저장 Grid 변경이 있으면 검색 전 확인을 요청한다. 문서 예제는 상세검색의 최소 흐름을 보여주되, 이 편집 보호 절차를 축약했다는 설명을 포함한다.
- `date` 값은 `{ from?: string; to?: string }` 범위이며 검색 폼 입력일 뿐, 날짜 범위에 대한 서버 필터 의미/파라미터 이름을 임의로 만들지 않는다.
- `select` 입력 옵션은 컬럼의 `options`에서 가져온다. 예제에서 실제 업무의 코드 값은 `categoryItemId`, `regTermId`, `useAt` 계약과 일치하게 쓴다.
- 코드 블록은 단계별 발췌문과 전체 예제를 구분한다. 전체 예제는 선언되지 않은 상태/상수/함수를 이용해 마치 붙여넣기 가능한 완결 코드인 것처럼 보이지 않도록, 동일 블록에서 선언하거나 명확한 주변 맥락 설명을 둔다.

## 포털 표현 및 상호작용

- `DocSection`의 기존 `prose`, `code`, `api` 유형 안에서 콘텐츠를 나눈다.
- `filtering-sorting` 문서의 검색/목차 기능이 새 소제목과 전체 본문을 계속 검색할 수 있어야 한다.
- 렌더러가 `prose`를 단일 Typography 본문으로 출력하므로, 여러 소제목·문단·표가 실제 화면에 제대로 구분되어 보이는지 브라우저에서 확인한다. 현재 렌더러 기능으로 그 계층이 표현되지 않는다면 콘텐츠 문자열에 마크다운 기호를 섞어 임시 스타일링하지 않는다. 승인 범위 안에서 문서 섹션을 나누고 기존 렌더러가 지원하는 API 표를 활용한다. 콘텐츠 구조만으로 충분히 읽기 좋은 위계를 만들 수 없는 경우 구현 전에 설계를 다시 확인한다.
- 실제 화면 캡처에서 제목, 설명, 코드 블록 사이의 간격/가독성을 확인한다. 데스크톱 및 375px 모바일 레이아웃을 점검하고 모바일 페이지 전체의 의도치 않은 가로 overflow가 없는지 확인한다.

## 테스트 및 수용 기준

1. 포털 문서 데이터 테스트가 단계별 제목, 전체 흐름, 기안양식 실제 필드, 메타데이터 표, controlled values/callback 흐름 및 조회 책임을 확인한다.
2. 예제 테스트가 분류·등록주기·사용여부 필드, 실제 `DraftFormFilters` 키/값 변환, 기본 키워드 결합, 편집 보호 절차 설명 및 API 요청 책임 경계를 검증한다.
3. 일반 날짜 범위 예제가 `{ from, to }`를 보여주며 실제 기안양식 필터와 분리되어 있음을 테스트로 확인한다.
4. 기존 `F1GridColumn.search` API 검색 및 해당 API 행 이동, 공개 API inventory 회귀가 유지된다.
5. `npm run test -- tests/f1-grid-docs.test.tsx`와 `npm run build`가 통과한다.
6. 브라우저에서 단계별 제목/코드/표가 각각 올바르게 렌더링되며, 상세검색 guide 및 기존 API 이름 검색으로 해당 콘텐츠에 도달할 수 있다.
7. 지속 문서 `F1-GRID.md`, 날짜별 작업 결과 문서, 데스크톱/모바일 스크린샷이 실제 최종 콘텐츠 및 검증과 일치한다.

## 하지 않는 일

- 상세검색 UX, `PageSearchArea`, `toPageSearchFields`, 업무 페이지/API/서버 코드 변경
- 실제 기안양식 검색 계약에 존재하지 않는 등록일 필터 추가
- 별도의 포털 메뉴나 신규 문서 경로 생성
- 별도 스타일 시스템이나 전용 콘텐츠 컴포넌트 구현
- 성능/번들, 백엔드, 데이터베이스 관련 변경
