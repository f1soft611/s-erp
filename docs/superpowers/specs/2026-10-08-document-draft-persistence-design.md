# 문서 임시저장 및 첨부 저장 설계

## 목적

S-ERP 문서작성 화면의 임시저장을 실제 영속 저장으로 연결한다. 문서 본문, 결재선, 결재 시스템 메시지는 공통 결재 처리 경계에서 저장하고, 첨부파일은 공통 파일 저장소를 재사용한다. 상신·승인·반려와 사용자 댓글은 후속 작업으로 분리한다.

## 확인한 현재 상태

- 문서작성 화면은 제목, 본문, 결재·합의 단계, 참조자, 첨부파일을 화면 상태로 보유하며 저장 API는 아직 연결되지 않았다.
- S-ERP의 날짜별 저장 스키마 초안은 문서 본문에 `tb_electronic_approval_main`, 참여자별 결재선에 `tb_electronic_approval_line_info`를 사용하고, 일반 댓글과 결재 시스템 메시지는 `tb_common_comment`를 공유하도록 정의한다.
- 사용자는 `tb_common_comment`의 `comment_type`, `event_type` 컬럼이 `s-erp_central`에 이미 적용됐다고 확인했다. 실제 타입, 기본값, 제약조건은 구현 전에 읽기 전용 DB 메타데이터로 재확인한다.
- 공지사항 작성 화면은 첨부 선택, 파일별 아이콘, 선택 파일 목록, 개별 제거 UX를 제공한다. 업로드는 문서 저장 후 수행하며, 업로드 일부 실패를 위한 정리·재시도 동작은 보완할 필요가 있다.
- 공통 파일 API는 tenant 인증을 확인하지만 결재 문서별 접근 권한을 확인하지 않는 경로가 있으므로, `APPROVAL` 첨부에 직접 노출하지 않는다.

## 승인된 설계

### 저장 경계

- 하나의 결재 도메인 서비스가 문서 임시저장과 결재선 저장을 책임진다. 이후 상신·승인·반려도 같은 서비스 경계 안에서 처리하되, 상태 전이와 권한 검증은 후속 사양으로 추가한다.
- `tb_electronic_approval_main`에는 문서 유형, 제목, 본문 JSON/HTML/평문, 작성자 스냅샷 및 `DRAFT` 상태를 저장한다.
- `tb_electronic_approval_line_info`에는 결재·합의·참조 참여자를 한 명당 한 행으로 저장하며 단계 순서와 단계 내 참여자 순서를 보존한다.
- `tb_common_comment`에는 시스템 저장 이력을 `comment_type='SYSTEM'`, `event_type='DRAFT_SAVED'`로 추가한다. 시스템 이벤트의 행위자와 문서 소유 정보는 인증 및 저장된 문서에서 서버가 설정한다.
- 문서 저장, 결재선 저장, 시스템 메시지 추가는 동일한 DB 트랜잭션으로 수행한다. 어느 저장이라도 실패하면 모두 rollback한다.
- 임시저장 메시지는 사용자의 명시적 저장마다 추가한다. 자동저장과 사용자 일반 댓글은 이번 범위에 포함하지 않는다.
- 최초 저장 후 현재 작성 세션이 문서 ID를 보유하여 재저장 시 새 문서를 중복 생성하지 않고 같은 초안을 갱신한다. 기존 문서함에서 초안을 검색·열고 수정하는 기능은 범위에 포함하지 않는다.

### 시스템 이벤트 계약

- 이번 구현에서 생성하는 이벤트는 `DRAFT_SAVED`뿐이다. `SUBMITTED`, `APPROVED`, `REJECTED`, `RETURNED` 및 추가 이벤트는 후속 결재 작업에서 추가한다.
- DB는 USER/SYSTEM 유형과 이벤트 값의 비어 있지 않음 등 구조적 조건을 보장한다. 이벤트 코드와 허용 행위는 백엔드 공통 이벤트 정의에서 검증하여 이벤트가 추가될 때마다 DB 제약을 변경하지 않도록 한다.
- 구현 전에 현재 DB의 check 제약을 확인한다. 기존 고정 이벤트 제약이 `DRAFT_SAVED`를 거부하면 그 제약을 조정하는 날짜별 forward/rollback migration과 누적 스키마 문서를 함께 관리한다. 컬럼을 중복 추가하지 않는다.
- 시스템 행은 일반 댓글의 수정·삭제·답글·좋아요 경로로 변경할 수 없어야 한다. 시스템 이벤트 생성은 결재 서비스의 내부 경로만 허용한다.

### 첨부파일

- 화면은 공지사항 작성 첨부 UI와 같은 파일 선택, 확장자별 아이콘, 목록, 개별 제거 동작을 제공한다. 컴포넌트/스타일을 그대로 복제하기보다 기존 공통 파일 저장 계약과 재사용 가능한 표시 패턴을 확인한다.
- 실제 파일과 메타데이터는 기존 MinIO/`tb_common_file` 저장소를 사용하고 `owner_type='APPROVAL'`, `owner_id=<전자결재 ID>`로 연결한다.
- 승인 전용 첨부 API가 문서 ID, 인증 tenant, 작성자 또는 문서 접근 권한을 확인한 다음 공통 파일 서비스를 호출한다. 업로더 ID는 요청 본문/폼 값이 아니라 인증 principal에서 설정한다.
- 문서/결재선/SYSTEM 메시지 저장 후 첨부를 업로드한다. DB와 MinIO는 하나의 원자적 트랜잭션이 아니므로 문서 저장 성공과 첨부 업로드 실패를 구분해 알린다.
- 업로드된 파일은 성공 상태로 유지하고 실패한 파일만 재시도한다. 재시도로 기존 문서 저장을 다시 생성하지 않는다. 첨부 전체의 성공을 확인하기 전에는 저장 완료 UX로 모달을 닫지 않는다.
- 허용 파일 크기/확장자/콘텐츠 검사 기준은 기존 공지사항 및 서버 공통 업로드 정책을 확인해 재사용한다. 서버 검증을 프론트의 `accept` 속성만으로 대체하지 않는다.

## 보안 및 검증 요구사항

- 서버는 인증 principal에서 tenant, 작성자 ID/이름, 업로더 ID를 설정하며 클라이언트가 보낸 감사 주체 값을 신뢰하지 않는다.
- 문서 조회·저장·첨부 업로드/목록/다운로드/삭제는 tenant 및 문서 접근 권한을 확인한다. 클라이언트의 `ownerType`/`ownerId`만으로 접근을 허용하지 않는다.
- 결재선 사용자들이 인증 tenant의 유효한 사용자임을 검증하고 중복 참여자, 잘못된 단계 순서, 지원하지 않는 문서 유형 및 잘못된 상태를 거부한다.
- DB 저장 중 문서·결재선·SYSTEM 댓글 어느 하나가 실패하면 세 변경이 모두 rollback되는지 서비스 테스트로 확인한다.
- 첨부 업로드의 부분 실패, 재시도 시 문서 중복/파일 중복 방지, 업로드 응답 누락 및 정리 실패를 검증하고 사용자에게 실제 완료 범위를 명확히 표시한다.
- 프론트엔드 테스트와 백엔드 테스트/빌드, 문서작성 첨부 UI의 브라우저 검증을 수행한다. 화면 변경 결과와 스크린샷은 날짜별 결과 폴더에 기록한다.

## 범위 제외

- 결재 신청, 승인, 합의 처리, 반려/반송, 회수 및 기타 상태 전이 API/화면
- 사용자 댓글·답글·댓글 수정/삭제, 좋아요
- 자동저장, 기존 문서함에서 초안 검색·재진입·수정
- 결재선 즐겨찾기, 결재 양식 관리 변경
- 기존 공지사항/공통 파일의 무관한 리팩터링
- 실제 DB DDL 적용. 별도 승인된 migration 실행 절차 없이는 개발/공유/운영 DB를 변경하지 않는다.

## 작업 문서 후속 절차

이 설계를 검토·확정한 뒤 20261008 날짜 문서 절차에 따라 문서 임시저장/첨부 저장 작업지시서, 계획서, 상세 사양서를 순서대로 작성한다. 구현 전 `s-erp_central`의 관련 테이블·컬럼·제약을 읽기 전용 MCP로 확인하고, 적용된 컬럼과 저장소 migration 이력을 대조한다. DB MCP를 사용할 수 없으면 스키마 이력과 코드에서 확인한 대체 근거 및 미확인 사항을 결과 문서에 기록한다.
