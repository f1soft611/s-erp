# 목록 조회 배치 처리 설계

## 목표

공지사항 목록과 전자결재 피드에서 목록 항목별 상세·첨부·댓글 조회가 반복되는 N+1 흐름을 제거한다. 브라우저의 기존 API 요청/응답 계약은 유지하면서, 각 페이지의 결과 행 수가 늘어도 DB 조회 횟수가 항목마다 증가하지 않도록 한다.

## 승인된 접근

종류별 set-based 배치 쿼리를 사용한다. 목록 결과의 식별자를 모아 첨부파일, 댓글, 댓글 수, 결재선, 시스템 이벤트, 상세 본문을 각각 한 번씩 조회하고, 서비스에서 owner ID 기준으로 응답 DTO를 구성한다. 하나의 큰 JOIN/JSON 집계 쿼리로 모든 관계를 펼치지 않는다. 단일 SQL 숫자보다 쿼리 수가 결과 행 수에 비례하지 않고 관계별 매핑을 명확하게 유지하는 것을 우선한다.

기존 전자결재 피드 API는 이미 한 번의 HTTP 요청으로 목록과 상세 데이터를 가져온다. 이 작업은 HTTP 요청 수를 늘리지 않으며, 서비스 내부의 문서별 DB 조회를 배치 조회로 바꾼다. 공지 목록 API의 응답 구조도 변경하지 않는다.

## 데이터 흐름

### 공지사항 목록

1. 기존 공지 목록과 전체 건수 조회를 유지한다.
2. 해당 페이지의 post ID를 기준으로 게시글 첨부파일과 댓글 트리를 배치 조회한다.
3. 댓글 수는 기존 계약과 동일하게 삭제되지 않은 최상위 댓글만 센다. 답글을 댓글 수에 포함하지 않는다.
4. 댓글 조회는 각 게시글의 최신 최상위 댓글 3개와 그 답글을 반환한다. 추가 최상위 댓글 존재 여부를 위해 1개를 더 확인하고, 이를 응답 댓글에 포함하지 않은 채 `hasPreviousComments`와 `nextBeforeCommentId`를 계산한다.
5. 페이지 내 댓글 ID를 전부 모아 댓글 첨부파일을 한 번에 조회한다. 개별 게시글 hydrate 안에서 배치 서비스가 반복 호출되지 않게 한다.

공지 목록 한 페이지의 DB 조회는 목록/전체 건수와 각 데이터 종류의 배치 조회로 구성하며, 게시글 수 또는 댓글 수에 따라 쿼리를 한 건씩 추가하지 않는다.

### 전자결재 피드

1. 기존 목록 범위·참여자 필터가 적용된 문서 목록을 조회한다.
2. 조회된 허용 문서 ID를 기준으로 전체 본문 상세, 결재선, 문서 첨부파일, 시스템 이벤트, 사용자 댓글 페이지와 댓글 수를 배치 조회한다.
3. 사용자 댓글은 문서별 최신 최상위 댓글 3개와 답글을 반환한다. `hasPreviousComments`, `nextBeforeCommentId`, `commentCount`는 기존 단일 문서 댓글 API와 같은 의미를 유지한다.
4. 댓글 ID 전체의 `APPROVAL_COMMENT` 첨부파일을 한 번에 조회한다.
5. 문서별 `requireRelatedDocument` 확인을 반복하지 않는다. 상세 조회도 tenant, 문서 ID, 기안자 또는 결재 참여자 조건을 적용하고, 보조 관계 조회에는 이 권한 확인을 통과한 문서 ID만 사용한다.

피드 데이터 조회는 목록 외에 데이터 종류별 배치 조회를 사용한다. 두 개 이상의 문서가 있을 때에도 목록 항목마다 상세/결재선/댓글/댓글 수/첨부 조회가 반복되지 않아야 한다.

## 계약 및 안전성

- 기존 API 경로, 응답 필드, 목록 범위/정렬, 문서 상세 본문, 첨부파일 필터, 삭제된 댓글 표현을 유지한다.
- tenant ID는 모든 배치 조회 조건에 포함한다.
- 전자결재 보조 데이터는 인증된 목록 결과에서 얻은 전자결재 ID만 대상으로 한다. 상세 조회는 목록과 같은 기안자/참여자 접근 조건을 적용한다.
- 댓글 수는 최상위의 삭제되지 않은 댓글 기준이다. 답글은 트리에는 포함하되 수에는 포함하지 않는다.
- 댓글 페이지의 기준은 최상위 댓글이다. 답글 수가 페이지 크기에 영향을 주지 않으며, 다음 페이지 cursor는 가장 오래된 반환 최상위 댓글 ID를 유지한다.
- DB 스키마나 데이터는 변경하지 않는다.
- pinned 목록, 요약 API, 상세 패널의 개별 상세/댓글 요청, 개발 모드 React StrictMode 재실행은 별도 요청/용도이므로 이 변경에서 합치거나 제거하지 않는다.

## 검증 기준

1. 서비스 테스트에서 여러 공지 게시글 및 여러 전자결재 문서를 넣었을 때 데이터 종류별 bulk 메서드가 한 번 호출되고, 항목별 개별 조회 메서드는 호출되지 않는지 확인한다.
2. 공지 및 전자결재의 댓글 수가 최상위 댓글만 계산하고 답글은 제외하는지 확인한다.
3. 댓글 트리, 최신 3개 최상위 댓글, 추가 댓글 여부, `nextBeforeCommentId`, 삭제된 댓글 및 댓글 첨부파일 매핑이 단일 항목 조회와 일치하는지 확인한다.
4. 기존 권한 조건과 tenant 범위, 응답 필드 및 목록 정렬이 유지되는지 확인한다.
5. 백엔드 집중 테스트와 전체 테스트를 수행하고, XML/Java 컴파일 및 `git diff --check`를 확인한다.
6. UI를 변경하지 않으므로 브라우저 캡처는 불필요하다. 결과 문서에는 DB MCP 스키마 확인 근거와 브라우저 검증 비대상 사유를 기록한다.
