# 문서 결재 취소 및 상태·구분 표시 통일 설계

## 목표

문서작성 `/groupware/doc/write`에서 기안자가 상신한 문서를 첫 결재 처리 전에 취소할 수 있게 하고, 결재자는 자신의 승인 처리를 다음 결재 단계가 처리되기 전에 취소할 수 있게 한다. 최종 승인이 완료된 문서는 취소하지 않는다.

리스트, 피드, 상세의 결재 상태와 문서 구분 표시를 하나의 표시 규칙으로 통일한다. 본문이 접힌 동안 결재선을 감추고 본문 확장 상태와 함께 표시한다.

## 범위 및 기준

- 프론트엔드: `frontend/src/pages/groupware/documents/write/` 및 필요한 공통 리스트 표시 타입/컴포넌트
- 백엔드: 기존 문서결재 API, `DocumentApprovalService` 및 관련 DAO/Mapper
- 데이터베이스: 새 컬럼은 추가하지 않는다. 취소 이력 이벤트를 허용하도록 `tb_common_comment.event_type` CHECK 제약을 날짜별 마이그레이션으로 갱신한다.
- 화면에 노출되는 결재처리 취소 버튼은 리스트에서 연 상세 패널에만 둔다. 피드 카드의 기존 결재 처리 컨트롤 부재는 유지한다.
- 이 설계는 `2026-10-12-document-approval-workflow-design.md`의 상태 전이, 단계별 처리, 병렬 합의 규칙을 따른다.

## 승인된 취소 정책

### 기안자 상신 취소

- 기안자는 문서가 `PENDING`일 때만 상신 취소를 할 수 있다. 현재 워크플로에서 `PENDING`은 기안자 외 결재/합의 참여자가 아직 아무도 처리하지 않은 상태다.
- 상세 패널의 결재상태 옆에 `결재신청 취소` 버튼을 표시하고, 실행 전에 확인 대화상자를 표시한다.
- 성공하면 문서 상태를 `DRAFT`로 되돌리고, 제출 시각을 초기화하며, 기안자에게 본문과 결재선을 보존해 임시저장 문서로 다시 편집할 수 있게 한다.
- 비참조 결재선은 `WAITING`으로 초기화하고 처리 시각/의견을 비운다. 참조선의 처리 상태는 계속 `null`이다.
- 취소 사실은 시스템 이력 `SUBMISSION_CANCELED`로 추가한다. 기존 `SUBMITTED` 이력은 삭제하거나 수정하지 않는다.
- `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `REVISION_REQUESTED`에서는 기안자 취소를 허용하지 않는다.

### 결재자 승인 취소

- 결재자/합의자는 현재 사용자가 처리한 `APPROVED` 결재선이 있고 문서가 완료되지 않았을 때만 자신의 승인을 취소할 수 있다.
- 자신의 단계보다 뒤인 단계에서 결재/합의 참여자가 이미 처리한 항목이 하나라도 있으면 취소할 수 없다. 뒤 단계가 활성 `PENDING` 상태더라도 아무도 처리하지 않았다면 취소할 수 있다.
- 같은 병렬 합의 단계 동료의 처리는 뒤 단계 처리로 보지 않는다. 병렬 단계의 다른 참여자 승인 여부만으로 본인의 취소를 막지 않는다.
- `COMPLETED`로 전환된 최종 승인은 취소 불가다. `REJECTED` 및 `RETURNED` 처리도 이 취소 기능의 대상이 아니다.
- 상세 패널의 결재상태 옆에 `승인 취소` 버튼을 표시하고, 실행 전에 뒤 단계와 문서 진행을 되돌린다는 확인 대화상자를 표시한다.
- 성공하면 본인의 결재선을 `PENDING`으로 되돌리고 `action_at` 및 `action_comment`를 비운다. 처리되지 않은 뒤 단계의 `PENDING` 결재선은 `WAITING`으로 되돌리고 `pending_at`을 비운다. 같은 단계 동료의 상태는 변경하지 않는다.
- 다른 결재선의 승인 처리가 남아 있으면 문서는 `IN_PROGRESS`, 취소한 승인만 처리 이력이었던 경우는 `PENDING`으로 둔다.
- 취소 사실은 시스템 이력 `APPROVAL_CANCELED`로 추가한다. 기존 승인 이벤트는 보존한다.

### 서버 검증 및 오류 처리

- 프런트엔드는 상세 응답으로 버튼 표시 조건을 계산할 수 있지만, 허용 여부의 최종 판단은 서버에서 수행한다.
- 각 취소 동작은 인증 사용자, 테넌트, 문서 상태, 기안자/결재선 소유자, 뒤 단계 상태를 검증한다. 문서 행 잠금 및 단일 트랜잭션 안에서 결재선/문서 상태/이력을 갱신한다.
- 동시 요청이나 상태 경합으로 조건이 달라졌으면 서버는 충돌 오류를 반환한다. 프런트엔드는 성공으로 간주하지 않고 오류를 표시한다.
- 성공 뒤 상세, 목록, 요약을 갱신한다. 실패 시 현재 화면을 유지하고 확인할 수 있는 오류 메시지를 표시한다.

## API 방향

현재 `/api/v1/groupware/approvals` 리소스에 역할과 의미가 분명한 두 동작을 추가한다.

- `POST /{electronicApprovalId}/submission-cancellation`: 기안자의 결재신청 취소
- `POST /{electronicApprovalId}/approval-cancellation`: 현재 사용자의 승인 취소

각 endpoint는 인증 사용자와 현재 상태를 서버에서 검증한다. 정상 응답은 기존 `ResultVO` envelope를 따르고 취소 후 문서 상태를 반환한다. 신규 클라이언트 서비스 함수는 성공 후 기존 상세/목록 조회를 이용해 화면을 갱신한다. 기존 상신·승인·반려·보완요청 API 계약은 변경하지 않는다.

## 상태 및 문서구분 표시

화면별 로컬 변환표를 두지 않고 공통 프론트 표시 메타데이터를 사용한다. API의 내부 코드와 상태 전이는 그대로 유지한다.

| 내부 문서 상태 | 공통 표시명 | 상태 배지 색상 |
|---|---|---|
| `DRAFT` | 임시저장 | 중립 |
| `PENDING`, `IN_PROGRESS` | 결재진행중 | 파랑 계열 |
| `COMPLETED` | 승인 | 초록 계열 |
| `REJECTED` | 반려 | 빨강 계열 |
| `REVISION_REQUESTED` | 보완요청 | 주황 계열 |

문서구분은 짧은 공통 라벨과 고정 색상을 사용한다. 색상만으로 의미를 구분하지 않으며 배지 텍스트를 항상 함께 표시한다.

| API 문서 유형 | 공통 구분명 | 구분 배지 색상 |
|---|---|---|
| `DRAFTING` | 기안 | 파랑 계열 |
| `BUSINESS_CONTACT` | 업무 | 청록 계열 |
| `EXPENSE_RESOLUTION` | 지출 | 주황 계열 |
| `ATTENDANCE_APPLICATION` | 근태 | 보라 계열 |

- 리스트 항목, 피드 배지, 상세 패널의 상태 표시가 같은 메타데이터와 색상을 사용한다.
- 상세 패널의 상태 옆에 문서구분 배지를 추가한다.
- 기존 문서 작성/필터 입력에서 사용하는 정식 양식명은 변경하지 않고, 위 짧은 구분명은 문서 표시 배지에 적용한다.
- 공통 리스트 표시 타입에 구분 색상 지원을 추가해 리스트 전용 고정 색상과 피드 전용 `primary` 색상 불일치를 제거한다.

## 본문 및 결재선 접기 동작

- 현재 본문 확장 상태를 결재선 표시에도 공유한다.
- 본문이 접혀 있고 더보기 동작이 가능한 문서는 결재선을 숨긴다.
- `더보기`를 누르면 본문과 결재선을 함께 표시하고, `접기`를 누르면 함께 감춘다.
- 본문이 짧거나 비어 있어 접기/확장이 필요하지 않은 문서는 결재선을 항상 표시한다.
- 공통 `FeedBodyContent`의 공지사항 등 다른 사용처 동작은 변경하지 않는다.

## 대안 검토

1. **취소 동작 2개를 별도 API로 추가하고 공통 UI 표시 메타데이터를 사용한다 — 선택.** 기안 취소와 결재자 승인 취소의 행위자/전이/검증을 서버에서 분리하고 감사 이력을 명시적으로 보존한다. 상태·구분 표현은 프런트 표시 책임으로 유지한다.
2. **기존 결재 처리 API에 취소 action을 합친다.** endpoint 수는 줄지만 기안자 취소와 결재자 승인 취소의 권한 및 상태 전이가 서로 다른데 요청 모델이 하나로 섞인다.
3. **문서 목록/상세 API가 표시명·색상까지 반환한다.** 표시 규칙을 한 곳에서 관리할 수 있으나 UI 테마 값이 서버 응답 계약에 결합되고 API가 표현 계층에 의존한다.
4. **프런트에서 기존 임시저장/승인 API를 조합해 취소한다.** 원자적 검증과 감사 이력을 보장할 수 없으므로 선택하지 않는다.

## 데이터베이스 이력

- 현재 승인 문서/결재선/시스템 댓글 테이블의 기존 컬럼을 재사용한다. 읽기 전용 PostgreSQL MCP에서 `tb_electronic_approval_main`, `tb_electronic_approval_line_info`, `tb_common_comment` 테이블과 주요 컬럼을 확인했다.
- `tb_common_comment.event_type` 허용 목록에 `SUBMISSION_CANCELED`, `APPROVAL_CANCELED`를 추가하는 SQL 변경본과 변경 이력, 롤백을 `docs/database/20261014/` 및 `backend/DATABASE/20261014/`에 동일하게 기록한다.
- 스키마 CHECK 제약 변경을 포함해 [db-schema.md](../../database/db-schema.md)를 최신화한다. 신규 컬럼이나 테이블은 추가하지 않는다.

## 검증 기준

### 백엔드

- 기안자 본인, 상태 `PENDING`인 결재신청 취소만 허용하고 문서/결재선이 `DRAFT` 기준으로 복구되는지 검증한다.
- 기안자가 아니거나 첫 참여자가 처리했거나 종료 상태인 경우 취소가 거부되는지 검증한다.
- 사용자는 자신이 승인한 결재선만 취소할 수 있고, 뒤 단계 처리 여부를 검증하는지 확인한다.
- 같은 병렬 단계 동료의 승인만으로는 취소가 막히지 않고, 뒤 단계가 처리됐거나 문서가 `COMPLETED`면 취소가 거부되는지 검증한다.
- 취소된 단계/문서 상태, 기존 이력 보존, 신규 시스템 이벤트, 트랜잭션 실패 롤백을 검증한다.
- controller/service/mapper 테스트와 스키마 변경본을 확인한다.

### 프런트엔드 및 브라우저

- 리스트·피드·상세에서 같은 내부 상태와 구분이 같은 라벨 및 배지 색으로 렌더링되는지 확인한다.
- 짧은 문서명, 상세 구분 배지, 상세의 역할/상태별 취소 버튼 노출을 검증한다.
- 확인 취소, 서버 성공, 충돌 오류, 성공 뒤 목록/상세/요약 갱신을 검증한다.
- 본문 접기 시 결재선이 숨고, 더보기 시 함께 열리며, 짧은 본문에서는 결재선이 계속 보이는지 검증한다.
- 실제 문서작성 화면을 375px, 768px, 1280px에서 확인하고 비민감정보 스크린샷을 결과 문서에 첨부한다.

- 양쪽 날짜별 DB 변경 스크립트, 이력, 롤백 및 `db-schema.md` 갱신
