# 전자결재 문서번호 설계

## 배경

문서현황의 “문서번호” 컬럼과 문서 상세 부제목은 현재 내부 `electronicApprovalId`를 노출한다. `eabusNo`는 DB의 문서유형 구분 코드이므로 사람이 사용하는 문서번호와는 다르다. 내부 ID는 조회와 수정 경로에 계속 필요하므로 별도의 업무 문서번호 필드를 둔다.

## 선택한 접근

문서가 최초 임시저장될 때 서버가 tenant 및 날짜 단위 sequence로 `EA-YYYYMMDD-NNNN` 문서번호를 발급하고 저장한다. 저장된 초안, 수정, 결재신청, 재상신, 업무연락 발송에 걸쳐 번호는 유지한다. 네 자리 숫자는 최소 폭이며 초과값은 잘라내지 않는다. 클라이언트는 번호를 전달하거나 생성하지 않는다.

다른 선택지는 (1) 결재신청/발송 시점 발급으로, 임시저장 문서에는 안정된 번호가 없어 현황 목록의 번호 요구를 충족하지 못하고, (2) 브라우저 발급으로, 동시 사용자 간 유일성·서버 권위를 보장할 수 없어 제외한다.

## 데이터 및 API

- DB: `tb_electronic_approval_main.document_no VARCHAR(40)`를 추가하고 tenant별 유일성을 보장한다.
- 기존 데이터: `created_at`의 날짜와 `created_at`, 내부 ID 정렬 순서로 일관된 번호를 채운다. backfill 후 `tb_id_sequence`의 `ELECTRONIC_APPROVAL_NO` 값을 각 tenant/날짜의 최댓값으로 맞춘다.
- API: 문서 생성/임시저장 응답, 문서 목록/현황 행, 상세 응답에 `documentNo`를 포함한다. 내부 `electronicApprovalId`는 PK 및 API 식별자로 보존하고 `eabusNo`의 의미도 보존한다.
- 현황: 번호 셀, 번호 상세검색, 빠른검색 및 정렬은 실제 `documentNo`를 사용한다. 정확 일치 검색을 유지한다.
- 화면: 상세 패널 부제목을 `문서번호: {documentNo}`로 바꾼다. 수주현황 상세 부제목은 `수주번호: {orderNo}`로 표시한다.

## 안전성 및 오류 처리

번호 발급과 최초 문서 insert는 기존 트랜잭션 안에서 수행한다. 시퀀스 또는 DB 저장 실패는 정상 오류 경로로 전파하고, 번호 없는 성공 응답을 만들지 않는다. 문서의 tenant 접근 검증과 기존 내부 ID 기반 동작은 변경하지 않는다.

마이그레이션은 트랜잭션으로 컬럼 추가, backfill, sequence 초기화, NOT NULL 및 tenant별 UNIQUE 제약을 적용한다. 같은 변경 번호로 rollback을 제공하며, 운영 적용/실제 데이터 변경은 이 작업에서 수행하지 않는다.

## 검증

- 백엔드: 날짜/tenant 범위 발급, 최소 4자리 및 4자리 초과, 최초 생성과 기존 번호 보존, 저장 실패 전파, 목록/상세 결과 매핑.
- 프론트엔드: 실제 번호가 현황 컬럼·검색·상세에 표시되고, 내부 ID는 상세 요청에 계속 사용되며, 수주번호 라벨이 표시되는지 검증.
- SQL: 기존 문서 번호 backfill의 안정적 순서, sequence 최댓값 보정, tenant 유일성, docs/backend SQL 사본 동등성 검증.
- 브라우저: 375px, 768px, 1280px에서 번호가 읽히고 페이지 전체 가로 overflow가 없는지 확인한다.
