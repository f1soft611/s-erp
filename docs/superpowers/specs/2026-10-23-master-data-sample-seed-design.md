# 품목·거래처 샘플 데이터 시드 설계

## 목표

수동으로 지정한 tenant에 품목 100건과 거래처 100건을 안전하게 추가할 수 있는 PostgreSQL 시드 SQL을 제공한다. 생성물은 저장소 내 SQL 파일이며, 에이전트는 MCP나 다른 수단으로 실제 DB에 실행하지 않는다.

## 확인된 구조와 제약

- `public.tb_customer_info`와 `public.tb_material_info`는 `tenant_id`를 필수로 사용한다.
- 두 테이블의 업무 코드(`customer_code`, `material_code`)는 테넌트 내 고유하며, 기존 eGov ID Generator는 각각 `public.ids`의 카운터를 사용해 6자리 코드를 생성한다.
- 기본 키는 각각 테이블 시퀀스가 생성한다.
- 품목 계정 코드와 단위는 tenant별 활성 `ITEM_TYPE`, `ITEM_UNIT` 공통코드에서 가져온다. 해당 tenant에서 필요한 활성 공통코드가 없으면 일부 값만 임의로 만들어 넣지 않고 전체 실행을 중단한다.
- 거래처명과 사업자번호 중복 검증이 적용될 수 있다. 샘플 거래처의 이름과 숫자 사업자번호는 각각 100개 안에서 고유해야 한다.
- 현재 세션은 읽기 전용 `s-erp-postgresql-readonly` MCP로 테이블 목록 및 `tb_customer_info`, `tb_material_info`, `ids` 컬럼 메타데이터를 확인했다. 실제 업무 행과 카운터 값은 조회하지 않았다.

## 승인된 설계

### 대상 파일과 실행

- 날짜별 작업지시서, 계획서, 상세사양서, 결과 문서를 `docs/directions/20261023`, `docs/plan/20261023`, `docs/spec/20261023`, `docs/result/20261023/master-data-sample-seed`에 둔다.
- 데이터 시드는 `docs/database/20261023` 및 `backend/DATABASE/20261023`에 동일한 SQL 사본으로 둔다.
- `target_tenant_id`는 파일에 고정하지 않는다. 실행자는 psql 변수로 반드시 지정한다. 변수 누락, 잘못된 tenant, 필요한 공통코드 부재, 코드 범위 초과 또는 충돌은 명시적 SQL 오류로 전체 트랜잭션을 중단한다.
- 시드는 DB 스키마를 변경하지 않는다. 기존 ID Generator 카운터 행이 이미 있어야 하며, 없으면 초기화 SQL을 먼저 적용하도록 안내하고 시드 자체는 카운터 행을 새로 만들지 않는다. 카운터를 업무 행 생성과 같은 트랜잭션에서 안전하게 예약해 6자리 업무 코드 범위를 배정하고, 이후 앱 등록 코드와 충돌하지 않도록 카운터를 유지한다.
- 생성 코드는 기존 ID Generator의 6자리 양수 범위를 따르며, 허용 범위를 예약할 수 없으면 어떤 업무 행도 커밋하지 않는다.
- 코드 카운터 행을 먼저 잠근 다음 거래처·품목 테이블을 `SHARE ROW EXCLUSIVE`로 잠근다. 이 순서는 앱이 카운터를 예약한 뒤 업무 테이블에 쓰는 흐름과 맞추어 교착 위험을 줄인다. 시드의 중복 검사와 쓰기가 끝날 때까지 해당 두 테이블의 INSERT/UPDATE/DELETE는 대기하지만 일반 조회는 가능하다.

### 데이터와 연결

- 지정한 tenant에 거래처 100건과 품목 100건을 생성한다.
- 모든 이름·사업자번호 등은 실재 인물·회사 정보를 사용하지 않는 가상 샘플 값으로 만든다. 번호는 10자리 형식과 중복 방지에 필요한 유일성만 갖춘 명시적 테스트 값이며 실제 사업자번호로 취급하지 않는다.
- 품목의 계정 코드와 단위는 해당 tenant의 활성 공통코드에서 선택한다. 재고/품목 분류 등의 선택 코드는 유효한 활성 코드가 확인되는 경우에만 반영하고, 유효하지 않은 코드를 임의로 하드코딩하지 않는다.
- 품목 100건의 제조사 코드는 같은 시드에서 생성한 거래처 100건 코드 중 하나와 연결한다. 소비기한은 스키마 허용값을 지키며 미관리(`NONE`)인 경우 숫자는 NULL로 둔다.
- 기본 필드 외에 불필요한 연락처·계좌·실제 주소 같은 민감하거나 오해를 부를 수 있는 값을 만들지 않는다.

### 안전성 및 충돌

- 시드는 하나의 트랜잭션으로 수행한다. 기존 업무 행을 갱신하거나 삭제하지 않는다.
- 동시 쓰기 중복을 막기 위해 기존 IDS 카운터 행을 잠근 다음 두 업무 테이블에 쓰기 잠금을 잡는다. 잠금은 샘플 실행 중에만 유지하며 커밋/롤백으로 해제한다.
- 생성될 샘플 식별값, 대상 tenant, 공통코드, 코드 카운터 범위를 사전 검사한다. 충돌이 발견되면 사용자가 선택한 대로 일부 건너뛰지 않고 전체를 롤백한다.
- 같은 스크립트를 재실행해 기존 샘플 이름/식별값과 충돌하면 전체를 중단한다. 데이터는 자동으로 덮어쓰거나 재생성하지 않는다.
- 사전에 업무 행을 조회하거나 SQL을 실행해 결과를 가장하지 않는다. 실행 후 확인은 실행자가 지정한 tenant 범위에서만 수행한다.

## 대안과 선택 근거

1. **고정 코드 범위 직접 INSERT:** 구현은 단순하지만 기존 업무 코드 및 다음 자동 채번 값과 충돌할 수 있어 제외한다.
2. **기존 IDS 카운터를 예약하는 트랜잭션형 SQL 시드:** SQL만으로 6자리 코드 계약을 유지하고, 업무 행과 카운터 변경을 원자적으로 처리할 수 있어 선택한다.
3. **애플리케이션 API를 통해 생성:** 서비스 검증과 자동채번을 자연스럽게 재사용하지만 SQL 시드 파일 요청에 부합하지 않아 제외한다.

## 데이터 흐름 및 검증

1. `target_tenant_id`를 검증하고 대상 tenant 및 필요한 활성 공통코드를 확인한다.
2. 기존 코드 최댓값과 이미 존재하는 `public.ids` 카운터 중 더 큰 다음 값을 기준으로 거래처·품목 코드 100개씩을 예약한다. 카운터 행이 없거나 6자리 코드 한계를 넘거나 카운터 행을 안전하게 예약하지 못하면 트랜잭션을 중단한다.
3. 고객 샘플 코드를 매핑한 뒤 거래처 100건과 이에 연결되는 품목 100건을 삽입한다.
4. 파일 사본이 동일한지, SQL 정적 검증에서 필수 tenant 변수, 트랜잭션, 오류 중단, 두 종류 각각 100건 생성, 코드 범위와 기존 행 비갱신/비삭제를 확인한다.
5. 결과 문서에 MCP가 읽기 전용으로 사용되었고 SQL 및 실제 DB 변경을 수행하지 않았음을 분명히 기록한다. 화면 변경이 없으므로 UI 스크린샷은 범위에 포함하지 않는다.

## 승인

- 2026-10-23: 사용자는 tenant 입력형 SQL 시드, 품목 100건과 거래처 100건, 충돌 시 전체 중단, 기존 ID Generator 코드 계약 유지, 실제 DB 미실행 설계를 승인했다.
- 2026-10-23: 사용자는 중복 검사와 삽입 사이의 경쟁을 막기 위해 시드 트랜잭션 동안 두 관리 테이블의 쓰기를 잠시 대기시키는 방식을 승인했다.
- 구현 착수 전 사용자는 이 문서 내용을 검토하고 승인해야 한다.
