# 협업공간(그룹웨어 > 커뮤니티) 프론트엔드 설계

- 작성일: 2026-11-26
- 범위: 프론트엔드만 (백엔드·DB 없음)
- 상태: 승인됨 (2026-11-26, 사용자 확인)

## 1. 의도와 이유

사용자가 스스로 "방"을 만들어 소통하는 공간을 제공한다. 방의 용도는 업무, 파일 공유, 자유 소통 등 사용자가 정한다. 그래서 용도를 코드에 고정하지 않고, 같은 글 구조를 여러 보기로 보여준다.

- 방 1개는 칸반 보드 1개로도, 피드(스레드)로도 볼 수 있다.
- 글에는 댓글, 답글, 첨부가 붙는다.
- 방마다 권한 그룹을 두어 저장 권한이 있는 사람만 글·댓글을 쓰고 카드를 옮긴다.

## 2. 목표 / 비목표 / 안티골

목표
- 방 목록, 방 만들기, 방 설정(이름, 기본 보기, 컬럼, 권한 그룹)
- 칸반 보기: 컬럼별 카드, 카드 드래그 이동, 컬럼 숨김·접기·순서 변경(사용자별 저장)
- 피드 보기: 글 목록, 댓글·답글, 첨부 표시, 칸반 상태 배지
- 글 작성/수정, 댓글 작성
- 권한 그룹에 따라 읽기/저장/방 설정 버튼 표시 제어
- 미리보기 화면(브라우저에서 확인한 3화면)과 같은 동작

비목표 (이번 범위 아님)
- 백엔드 API, DB, 실제 권한 판정
- 파일 보기 탭 (2차)
- 사용자별로 컬럼 자체를 따로 정의하는 기능 (카드 상태가 공유 데이터이므로 제외)
- 알림, 멘션, 실시간 동기화

안티골
- 사람마다 같은 카드가 다른 컬럼에 있는 상태가 생기면 실패다.
- 기존 공지/자료실 화면과 레이아웃이 어긋나면 실패다.

## 3. 제약

- `frontend/src`만 수정한다. 기존 구조와 규칙은 `AGENTS.md`, `frontend/AGENTS.md`를 따른다.
- 모달은 `CommonDialog`, 확인창은 `useCommonConfirmDialog`를 쓴다. 브라우저 기본 alert/confirm은 쓰지 않는다.
- 화면 연결은 기존 방식을 따른다: `DashboardContent.tsx`의 `groupware` + `currentPageKey` 분기, `dashboardPages.ts`의 lazy 등록.
- 375/768/1280px에서 가로 스크롤과 겹침이 없어야 한다.
- 기준 화면: 공지(`community/notice`)의 피드·댓글 패턴, 자료실(`community/archive`)의 페이지 헤더·권한 처리 패턴.

## 4. 접근 방법

| 방법 | 내용 | 장단점 |
|---|---|---|
| A. 서비스 계층 뒤에 가짜 데이터 (선택) | 화면은 `services/`만 호출하고, 서비스는 메모리+localStorage 샘플을 반환 | 드래그·댓글·권한까지 실제처럼 동작하고, 나중에 서비스만 API로 교체하면 된다. 타입은 이번에 정한 안이라 백엔드 사양에서 재확정이 필요하다. |
| B. 정적 화면만 | 동작 없이 레이아웃만 | 빠르지만 확인할 것이 없어 미리보기와 차이가 없다. |

선택: A. 사용자가 승인했다.

## 5. 사용자가 정한 것

- 구조: 방 1개 = 칸반/피드로 보는 글 모음. 글 구조는 공통, 상태(컬럼)는 선택 항목.
- 보기: 1차는 칸반과 피드. 파일 보기는 나중.
- 권한: 방마다 권한 그룹을 만들고, 저장 권한이 있는 사람에게 부여한다.
- 개인 설정: 컬럼 구성은 방 공통이고, 컬럼 숨김·접기·순서와 필터만 사용자별로 저장한다.
- 메뉴명: 협업공간. 위치는 그룹웨어 > 커뮤니티.
- 폴더: `frontend/src/pages/groupware/community/workspace`.

## 5.1 UI/UX 요구사항 (사용자 지시)

- 사용자 UI/UX를 최우선으로 하고, 디자인은 기존 ERP 화면의 테마·공통 컴포넌트와 일관되게 한다. 임의의 새 스타일을 만들지 않는다.
- 기준 화면(공지, 자료실)과 나란히 놓고 헤더, 여백, 버튼 위치, 메시지 영역, 색상을 비교한다.
- 칸반은 드래그 중 놓을 위치 표시, 빈 컬럼 안내, 로딩·오류·빈 상태, 키보드 접근(카드 이동 대안)을 갖춘다.
- 저장·변경 흐름은 진행 표시, 성공 알림, 실패 표시, 변경 취소 확인(`useCommonConfirmDialog`)을 갖춘다.
- 권한이 없는 동작은 숨기거나 비활성화하고 이유를 알려준다.

## 5.2 권한 그룹 구성원 (사용자 확정)

- 1차는 개별 사용자만 구성원으로 한다. 샘플 사용자 몇 명과 "사용자 전환" 개발용 스위치를 두어 권한별 화면을 브라우저에서 확인한다.
- 부서 단위 지정은 백엔드 사양 단계에서 추가한다(데이터 모델은 이를 막지 않게 구성원 종류 필드를 둔다).

## 6. 제가 정한 것 (사용자가 확인함)

- 권한 단계는 읽기, 저장(글·댓글·카드 이동), 방 설정 세 가지이고, 방마다 설정한다.
- 기존 메뉴 권한(`selectedMenuPermissions`)은 바깥 관문으로 유지한다. 방 권한은 그 안쪽에서만 판단한다.
- page key는 `workspace`로 한다. 메뉴 항목 자체의 등록 방식은 구현 시 확인한다(메뉴 데이터가 서버/설정에서 오는지 미확인).
- 샘플 데이터는 영업팀 협업, 설계도면 공유, 전사 자유게시 3개 방으로 한다.
- 사용자별 설정과 가짜 데이터는 localStorage 키 `s-erp:workspace:*`에 저장한다.
- 컬럼 숨김·접기 사용자 설정은 화면 이동 후에도 유지한다.
- 글 필드: 제목, 본문(일반 텍스트), 작성자, 작성일시, 상태(컬럼, 선택), 첨부. 담당자·마감일은 이번에 넣지 않는다.
- 첨부: 작성창에서 파일을 선택할 수 있지만 백엔드가 없으므로 파일명·크기·형식만 저장하고 내려받기는 지원하지 않는다.
- 댓글: 공지 화면의 댓글 구조(`noticeCommentTree`)와 같은 깊이를 따른다. 새로 깊이를 정하지 않는다.
- 방 설정의 컬럼: 추가, 이름 변경, 순서 변경, 삭제를 지원한다. 카드가 있는 컬럼은 삭제할 수 없고 먼저 카드를 옮겨야 한다.
- 컬럼이 없는 방: 칸반 탭을 비활성화하고 피드로만 보여준다. 컬럼이 있으면 글 작성 시 상태를 고른다.
- 권한 그룹 표: 그룹마다 읽기/저장/방 설정을 체크한다. 그룹 추가·삭제·이름 변경이 가능하며, 방 설정 권한을 가진 그룹은 최소 1개 있어야 한다.
- localStorage 키에는 사용자 ID를 포함한다(`s-erp:workspace:<userId>:...`). 가짜 방·글·댓글은 같은 브라우저의 모든 사용자가 공유한다. 그래야 "같은 카드는 모두에게 같은 컬럼"을 확인할 수 있다.
- 개인 설정과 방 컬럼이 어긋날 때: 새 컬럼은 기본으로 보이고 순서 맨 뒤에 붙는다. 삭제된 컬럼의 개인 설정은 무시한다.
- 숨긴 컬럼에는 카드를 드롭할 수 없다(보이지 않으므로).
- 필터는 "내가 쓴 글", 검색어 두 가지만 둔다.
- 미리보기 3화면(브라우저에서 확인함): ① 방 목록 + 칸반 보기, ② 피드 보기(댓글 포함, 상태 배지), ③ 방 설정(기본 정보, 컬럼, 권한 그룹 표). 구현 전에 이 화면을 `docs/result/20261126/` 아래 영문 폴더에 스크린샷으로 보관해 기준으로 삼는다.
- 메뉴 등록: 메뉴 항목이 서버 데이터라면 `workspace` 메뉴 행이 필요하다. 구현 첫 단계에서 확인하고, 행이 없으면 임의로 DB를 바꾸지 않고 먼저 사용자에게 알린다.
