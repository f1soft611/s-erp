# S-ERP 공통 웹 푸시 서비스 설계

## 목표

현재 공통 알림으로 발행되는 업무 알림과 쪽지 도착 알림을 하나의 백엔드 웹 푸시 서비스로 전달한다. 알림별 업무 서비스가 Push API, 브라우저 구독, 재시도 로직을 직접 구현하지 않게 하고, 사용자가 명시적으로 동의한 브라우저 기기에만 알림을 전달한다.

웹 푸시는 기존 인앱 알림과 쪽지를 대체하지 않는 선택적 전달 채널이다. 인앱 알림의 저장·읽음·보관과 쪽지의 저장·읽음은 현재 계약을 유지한다.

## 범위

### 포함

- 현재 공통 알림 유형인 `APPROVAL_COMMENT_MENTION`과 `DIRECT_MESSAGE_RECEIVED`의 공통 웹 푸시 전달
- 사용자의 명시적 동의, 브라우저 권한 확인, 기기별 구독 등록·중복 방지·해제
- 기존 공통 알림 생성 트랜잭션과 원자적으로 기록하는 전달 대기 항목
- 비동기 전송, 중복 억제, 제한된 재시도 및 만료/해지 구독 비활성화
- 푸시 알림 선택 시 앱 열기와 인증·테넌트·원본 접근권한 재검증
- VAPID 키와 구독 비밀 자료의 안전한 운영·저장 정책
- 미지원 브라우저, 권한 거부, 오프라인, 전송 실패 시 기존 인앱 흐름 유지

### 제외

- 아직 공통 알림으로 발행되지 않는 결재 요청·승인·반려 등 새 업무 이벤트의 발행
- 이메일, SMS, 모바일 네이티브 푸시 및 외부 관리형 푸시 사업자 도입
- 알림 유형별 푸시 설정 및 사용자별 세부 전달 규칙
- 푸시에서 알림/쪽지 본문, 이름 등 업무 내용을 노출
- 인앱 알림·쪽지의 읽음, 보관, 삭제 정책 변경

새 업무 이벤트 추가는 로드맵 3단계에서 이벤트·수신자 정책을 합의한다. 해당 이벤트가 공통 알림으로 발행되면 이후 이 서비스의 공통 전달 계약을 재사용할 수 있다.

## 현재 구조와 확인 근거

- `NotificationServiceImpl.createEvent`는 테넌트·수신자별 공통 알림을 저장하고 현재 `APPROVAL_COMMENT_MENTION` 및 `DIRECT_MESSAGE_RECEIVED` 유형만 허용한다.
- `DirectMessageServiceImpl.saveMessage`는 쪽지 저장과 같은 트랜잭션 안에서 `NotificationService.createEvent`를 호출해 수신자용 `DIRECT_MESSAGE_RECEIVED` 알림을 만든다.
- 현재 공통 알림과 쪽지는 기존 DB 테이블 및 권한 API를 사용한다. 푸시 구독·전달 상태는 그 데이터와 별개로 관리한다.
- 읽기 전용 `s-erp-postgresql-readonly` MCP의 `list_tables`에서 `tb_notification`, `tb_direct_message`, `tb_direct_message_thread`가 존재하고 푸시 구독/전달 전용 테이블은 없음을 확인했다.
- 같은 MCP의 `describe_table`에서 `tb_notification`의 식별자, 테넌트, 수신자, 이벤트/원본 유형 및 ID, 제목·요약, 읽음·보관·생성 시각을 확인했다. 쪽지 테이블에서는 메시지·대화·발신자·수신자·본문·읽음 정보를 확인했다. 개인정보가 포함될 수 있는 행 데이터는 조회하지 않았다.

## 권장 아키텍처

### 공통 전달 경계

각 업무 서비스는 기존 공통 알림 발행 계약만 사용한다. 웹 푸시 전송은 알림 유형별 서비스에 넣지 않는다. `NotificationService.createEvent`가 알림 행과 푸시 전달 대기 항목을 같은 DB 트랜잭션에서 기록하고, 트랜잭션이 커밋된 뒤 공통 푸시 워커가 대기 항목을 처리한다.

대기 항목을 알림 저장과 같은 트랜잭션에 기록하므로 프로세스가 커밋 직후 종료되어도 푸시 요청이 유실되지 않는다. 워커는 알림 ID를 기준으로 유효한 수신자 구독을 찾아 보내며 업무 서비스나 쪽지 서비스가 브라우저 Push API, VAPID, 재시도 정책에 의존하지 않는다.

1. 업무 발생원 또는 쪽지 서비스가 기존 공통 알림 계약을 호출한다.
2. 공통 알림 서비스가 수신자 알림과 푸시 대기 항목을 하나의 트랜잭션으로 저장한다.
3. 커밋된 대기 항목만 워커가 가져온다. 보류 작업은 잠금/임대 방식으로 한 워커만 처리하며, 다중 애플리케이션 인스턴스에서도 중복 실행을 억제한다.
4. 워커는 해당 알림 수신자의 활성 기기 구독을 읽고, 각 알림·구독 쌍을 중복 없이 처리한다.
5. 푸시 서비스가 성공 또는 영구 실패를 반환하면 결과를 기록한다. 일시 실패는 제한된 횟수와 지수형 지연으로 재시도한다.

전송은 외부 브라우저 벤더 Push Service를 표준 Web Push 경로로 사용한다. S-ERP는 구독 수명주기, 발송 큐, 정책과 관측 기능을 소유하며 관리형 푸시 중계 사업자에는 의존하지 않는다.

### 저장 개념

상세 DDL은 이 설계 단계에서 고정하지 않는다. 다음 논리 정보를 별도 저장하는 것을 기준으로 구현 계획과 상세 사양에서 확정한다.

- **기기 구독:** 테넌트, 사용자, 브라우저 Push endpoint, 암호화된 구독 키 자료, 활성/비활성 상태, 생성·갱신 시각. 한 사용자는 여러 기기를 등록할 수 있고, 동일 endpoint의 반복 등록은 한 구독으로 수렴한다.
- **푸시 대기/전달 상태:** 공통 알림 ID, 처리 상태, 시도 횟수, 다음 시도 시각, 마지막 오류 분류, 생성·완료 시각. 같은 공통 알림은 재시도나 여러 워커 실행에도 중복으로 발행되지 않는다.
- **기기별 전달 결과:** 알림·구독 조합별 성공/영구 실패 상태를 기록해 하나의 기기 실패가 다른 기기 전달을 막지 않도록 한다.

기존 `tb_notification`은 인앱 알림의 권위 있는 원본으로 남긴다. 쪽지 본문을 푸시 전용 저장소에 복사하지 않는다. 대기 상태와 전달 상태의 보존/정리 기간은 운영 용량과 재시도 정책을 정하는 상세 사양에서 확정한다.

## 구독 및 동의 흐름

- 사용자가 설정에서 웹 푸시 켜기를 직접 선택할 때만 브라우저 알림 권한을 확인하거나 요청한다. 페이지 진입만으로 권한 팝업을 자동 표시하지 않는다.
- 권한이 허용되고 브라우저가 Service Worker, Push API, 필요한 암호화 기능을 지원할 때만 구독을 생성해 인증된 백엔드에 등록한다.
- 백엔드는 인증 principal과 테넌트로 구독 소유자를 결정한다. 요청의 사용자 ID를 신뢰하지 않는다.
- 동일 endpoint의 반복 등록은 멱등하게 갱신한다. 같은 브라우저 기기에서 계정이 바뀌어 등록되면 기존 소유자 연결이 남지 않도록 원자적으로 소유권을 재할당하거나 기존 연결을 비활성화한다.
- 사용자는 현재 브라우저 기기의 구독을 해제할 수 있다. 앱 차원의 푸시 동의 상태와 브라우저 권한은 별개이며, 브라우저 설정에서 권한이 취소된 경우에도 서버 응답과 이후 페이지 방문 시 상태를 동기화한다.
- 미지원/거부 상태는 구체적으로 안내하고 인앱 알림 접근은 그대로 제공한다. 브라우저 권한을 앱이 임의로 다시 허용할 수 있다고 표시하지 않는다.

## 푸시 내용과 선택 동작

- 서비스 워커는 사용자에게 의미 있는 일반 문구(예: “새 알림이 도착했습니다”)를 표시한다. 업무 제목, 쪽지 내용, 사용자 이름, 그 밖의 민감한 내용은 push payload나 OS 알림에 넣지 않는다.
- payload에는 공통 알림 ID와 제한된 앱 내부 식별 정보만 둔다. 임의 URL을 수용하거나 외부 링크로 이동하지 않는다.
- 사용자가 푸시를 선택하면 앱을 열고 기존 인증 절차를 거친다. 인증된 앱이 알림 ID를 이용해 현재 사용자 소유인지 조회하고, 원본 리소스의 현재 접근권한을 다시 검사한 뒤 허용된 화면으로 이동한다.
- 원본이 삭제되었거나 현재 접근권한이 없으면 상세 내용을 표시하지 않고 안전한 알림함 화면으로 이동한다.
- 푸시 선택만으로 쪽지 읽음 상태를 변경하지 않는다. 쪽지 읽음은 기존 대화 진입/읽음 처리 흐름을 따른다.
- 선택 시 브라우저의 현재 권한 상태를 재확인한다. 권한이 취소된 경우 앱은 이를 상태 화면에 반영하며 다시 표시할 수 있다고 가정하지 않는다.

## API 및 보안 경계

구체 URL과 DTO는 구현 계획 및 상세 사양에서 기존 인증·응답 패턴을 확인해 확정한다. 최소한 다음 서버 책임이 필요하다.

| 계약 | 책임 |
|---|---|
| 현재 기기 구독 등록/갱신 | 로그인 principal과 테넌트를 사용해 구독을 저장하고 endpoint 중복 등록을 멱등 처리 |
| 현재 기기 구독 해제 | 인증 사용자 소유의 endpoint만 비활성화 |
| 구독 상태 조회 | 현재 사용자의 활성 등록 여부만 반환하며 endpoint/암호화 키는 노출하지 않음 |
| 공통 알림 푸시 enqueue | 알림 생성과 같은 트랜잭션에 전달 작업을 기록하고 중복 생성을 방지 |
| 푸시 처리 | 인증 사용자별 활성 구독에 최소 payload 전송, 결과 기록, 재시도/만료 처리 |
| 원본 재검증 | 알림 조회와 상세 이동 때 현재 로그인 사용자·테넌트·원본 권한을 다시 검증 |

- VAPID 개인키는 DB, 코드, frontend bundle에 넣지 않고 운영 secret 설정으로 주입한다. 공개 키만 클라이언트 구독 생성에 제공한다. 키 회전 절차와 무중단 전환 범위는 운영 상세 사양에서 정한다.
- endpoint와 subscription key는 구독을 악용할 수 있는 민감한 자격자료로 취급한다. API 응답·로그·예외 메시지에 원문을 기록하지 않고 저장 시 암호화한다.
- 클라이언트가 보낸 endpoint는 서버의 outbound 요청 대상이 되므로 검증한다. HTTPS만 허용하고 loopback, 사설/링크 로컬 주소 및 허용되지 않은 Push Service 도메인으로의 발신을 차단한다. DNS 해석 후에도 사설 주소로 우회하지 못하도록 네트워크 egress 정책을 함께 적용한다.
- API는 인증, 테넌트 격리, endpoint당 사용자 소유권, 크기/요청 빈도 제한을 적용한다. 구독 키와 사용자 식별 정보가 포함된 원본 요청을 로그로 남기지 않는다.
- 표준 암호화 및 VAPID 처리는 검증된 Java 라이브러리를 사용한다. 후보 라이브러리의 Java 8 호환성과 보안 유지 상태는 dependency 선정 시 확인하고, 직접 암호화 프로토콜을 구현하지 않는다.
- 전송 성공은 인앱 알림 읽음이나 쪽지 수신/읽음을 의미하지 않는다. 권한/API 확인 후 브라우저가 OS 알림 표시를 보장한다고 가정하지 않는다.

## 오류 및 운영 동작

- 푸시 발송 실패는 이미 커밋된 인앱 알림 또는 쪽지 저장을 rollback하지 않는다.
- 일시적 네트워크 오류와 서비스 일시 제한 응답은 최대 시도 횟수와 최대 보류 시간 내에서 재시도한다. 그 이후에는 실패 상태와 원인 분류를 보존하고 계속 무한 재시도하지 않는다.
- endpoint 만료/해지 응답(HTTP 404 또는 410)은 해당 기기 구독을 비활성화하고 그 구독으로 추가 요청을 보내지 않는다.
- 구독이 없거나 사용자가 opt-in 하지 않은 경우 전달 작업을 완료 가능한 no-recipient 상태로 마감하며 인앱 알림은 유지한다.
- 다중 인스턴스 운영에서 작업 임대 만료, 워커 재시작 및 동시 dequeue를 고려한다. 알림·기기별 중복 키와 완료 상태를 이용해 at-least-once 작업 처리에서도 실질적인 중복 표시를 억제한다.
- 구조화 로그와 지표에는 알림/작업 식별자, 유형, 결과 분류, 시도 횟수, 처리 지연만 남긴다. endpoint, subscription key, 제목·요약·쪽지 본문은 기록하지 않는다.
- 대기 건수, 오래된 작업, 재시도 및 영구 실패, 만료 구독 정리, 외부 Push Service 응답을 운영 지표로 제공한다. 알림 본문이나 개인별 payload를 로그/분석 도구로 수집하지 않는다.

## 검증 기준

- 기존 댓글 멘션과 쪽지 수신이 동일한 공통 전달 경로로 enqueue되고, 새로운 결재 이벤트 발행이 추가되지 않는다.
- 알림 insert와 enqueue는 원자적이다. rollback 시 푸시 작업이 남지 않고, commit 이후 발송 실패가 알림/쪽지 저장 실패로 바뀌지 않는다.
- 동의하지 않은 사용자나 다른 사용자/테넌트의 구독에는 발송하지 않는다. endpoint 재등록·계정 전환·기기 해제는 멱등하고 소유권을 격리한다.
- 동일 알림과 기기 조합의 재시도/워커 중복 처리로 중복 작업 또는 반복 푸시가 생기지 않는다. 한 기기 오류가 다른 활성 기기의 발송을 중단시키지 않는다.
- 404/410, 일시 오류, 제한 초과, 재시도 한도, 워커 재시작 및 작업 임대 만료를 검증한다.
- push payload와 화면 캡처/로그에서 업무 제목, 쪽지 본문, endpoint, 구독 키와 인증정보가 노출되지 않는다.
- Service Worker 클릭 후 앱은 로그인·테넌트·알림 소유자·원본 접근권한을 재검증하며 쪽지 읽음 의미를 바꾸지 않는다.
- 권한 허용/거부/미지원, 브라우저 권한 취소, 명시적 등록·해제 및 인앱 알림 유지 흐름을 검증한다.
- 백엔드 테스트, 프런트엔드 테스트/빌드 및 실제 브라우저의 375px, 768px, 1280px 확인을 구현 결과 문서에 기록한다.
- DB 스키마 변경이 필요한 경우 구현 전에 읽기 전용 DB MCP로 현재 계약을 확인하고 날짜별 SQL, 변경 이력, rollback 및 누적 스키마 문서를 갱신한다. 실제 DB에는 migration을 자동 적용하지 않는다.

## 다음 단계

사용자가 이 설계 문서를 검토·승인한 뒤 `writing-plans` 절차로 날짜별 구현 계획을 작성한다. 그 계획에서는 구독·대기/전달 저장 구조, 동시 워커 정책, API DTO와 브라우저 UI 흐름을 기존 코드·확인된 DB 계약에 맞춰 상세 사양으로 구체화한다. 구현은 상세 사양 승인과 해당 계획의 절차를 따른다.
