# 품목 공통코드 시드 및 소비기한 입력 설계

## 목표

지정 tenant의 품목관리 공통코드를 S-ERP 대상 tenant에 안전하게 넣을 수 있는 SQL을 준비하고, 품목의 소비기한 기준과 계산 숫자를 한 쌍으로 입력·검증한다. 실제 DB에는 적용하지 않는다.

## 확인된 현행 구조

- 품목관리 사양의 공통코드 그룹은 `MATERIAL_TYPE`, `STORE_METHOD`, `EXPIRY_STATUS`다. 현재 화면과 API에서 사용하는 그룹에 한정하고 다른 필드는 임의로 공통코드화하지 않는다.
- `tb_material_info.expiryed_status`와 `expiryed_count` 컬럼 및 API/화면 타입은 이미 존재한다. `expiryed_count`는 양의 정수 또는 NULL이다. 새 컬럼은 만들지 않는다.
- 현재 행 폼에는 기준 선택과 숫자 입력이 별도 필드로 있으나, 단위 표기와 기준-숫자 연동 검증은 없다.
- 두 DB 모두 소비기한 기준 허용값 및 양수 체크를 보유한다. 제한 집계 결과는 기준과 숫자가 맞지 않는 기존 행이 없음을 확인했다.
- 기본 S-ERP DB에서는 위 세 그룹의 코드가 조회되지 않았다. 실제 적용 테넌트 ID는 SQL 실행자가 지정한다.

## 공통코드 원본

세 그룹과 12개 상세코드만 복사한다. 원본에서 그룹·항목은 모두 활성 상태였다. 설명과 정렬 순서도 원본 값을 유지한다.

| 그룹 코드 | 그룹명 | 설명 | 정렬 |
| --- | --- | --- | ---: |
| `MATERIAL_TYPE` | 품목 유형 | NULL | 40 |
| `STORE_METHOD` | 보관 방법 | NULL | 50 |
| `EXPIRY_STATUS` | 소비기한 기준 | 소비기한 계산 단위 | 80 |

| 그룹 코드 | 항목 코드 | 항목명 | 설명 | 정렬 |
| --- | --- | --- | --- | ---: |
| `MATERIAL_TYPE` | `TYPE_01` | 초콜릿 | NULL | 10 |
| `MATERIAL_TYPE` | `TYPE_02` | 준초콜릿 | NULL | 20 |
| `MATERIAL_TYPE` | `TYPE_03` | 초콜릿가공품 | NULL | 30 |
| `STORE_METHOD` | `ROOM` | 실온 | 1~35℃ | 10 |
| `STORE_METHOD` | `AMBIENT` | 상온 | 15~25℃ | 20 |
| `STORE_METHOD` | `REFRIG` | 냉장 | 0~10℃ | 30 |
| `STORE_METHOD` | `FROZEN` | 냉동 | -18℃ 이하 | 40 |
| `STORE_METHOD` | `ROOM_OPEN_REFRIG` | 실온(개봉후냉장보관) | NULL | 50 |
| `EXPIRY_STATUS` | `NONE` | 없음 | 소비기한 미관리 | 10 |
| `EXPIRY_STATUS` | `DAY` | 일 | 제조일 + N일 | 20 |
| `EXPIRY_STATUS` | `MONTH` | 개월 | 제조일 + N개월 | 30 |
| `EXPIRY_STATUS` | `YEAR` | 년 | 제조일 + N년 | 40 |

## 설계 결정

### 코드 시드 SQL

- `target_tenant_id`는 psql 변수로 실행 시 지정하며, 특정 tenant ID를 파일에 고정하지 않는다. `psql -v ON_ERROR_STOP=1 -v target_tenant_id=<tenant_id> -f <script.sql>` 형태로 실행하고 SQL에서는 값에 안전한 변수 인용을 사용한다.
- 그룹은 `(tenant_id, group_code)`로 찾고, 상세코드는 해당 그룹의 생성된 `group_id`를 사용한다. 자동 생성 PK를 미리 가정하지 않는다.
- SQL은 하나의 트랜잭션으로 그룹과 항목을 입력한다.
- `(tenant_id, group_code)` 또는 `(group_id, item_code)` 충돌은 `ON CONFLICT DO NOTHING`으로 처리한다. 재실행은 안전하고 기존 테넌트별 명칭·설명·상태를 덮어쓰지 않는다.
- 원본의 NULL 설명, 정렬 순서, 활성 상태를 보존한다. FK 오류를 포함한 실행 오류는 트랜잭션 전체를 중단시킨다.
- `docs/database/20261023`와 `backend/DATABASE/20261023`에 시드 SQL을 동일하게 보관한다. 기존 값을 지우는 시드 롤백은 제공하지 않는다. 충돌로 건너뛴 기존 코드까지 삭제할 위험이 있기 때문이다. 읽기 전용 MCP로는 적용하지 않는다.

### 소비기한 입력

- 기존 `expiryedStatus` 선택 옆에 `expiryedCount` 정수 입력을 둔다. 선택값에 따라 숫자 입력에 `일`, `개월`, `년` 단위를 표시한다.
- `NONE`은 소비기한 숫자를 NULL로 비우고 입력을 비활성화한다.
- `DAY`, `MONTH`, `YEAR`는 1 이상의 정수를 필수로 한다. 소수, 0, 음수 및 정수 범위 초과는 프론트엔드와 백엔드에서 명시적으로 거부한다.
- 기준을 `NONE`으로 변경하면 숫자를 지운다. 단위 기준을 서로 바꾸면 숫자는 보존하고 표시 단위만 바꾼다.
- 저장 요청은 기존 API 필드명을 유지한다. `expiryedStatus`와 `expiryedCount`를 함께 저장하고, 새 API나 신규 컬럼은 만들지 않는다.
- DB에는 `NONE`일 때 count가 NULL이고, 그 외 허용 기준일 때 count가 양수여야 한다는 CHECK를 추가한다. 기존 두 CHECK는 유지한다. 변경 및 롤백 SQL은 날짜별 DB 이력에 기록하고 `docs/database/db-schema.md`를 갱신한다.

## 대안 및 선택 근거

1. 대상 tenant 변수와 충돌 시 기존 값을 유지하는 멱등 시드: 명시적으로 선택했다. 반복 실행이 가능하고 기존 테넌트별 사용자 정의 코드를 보존한다.
2. 충돌 시 원본 값을 갱신하는 UPSERT: 원본과 정확히 동기화할 수 있지만 대상 tenant의 커스텀 명칭·설명을 덮을 수 있어 제외한다.
3. ID를 고정한 단순 INSERT: 실행이 간단하지만 다른 환경의 시퀀스와 충돌할 수 있고 재실행이 불가능해 제외한다.
4. 소비기한 숫자를 선택 입력으로 유지: 기준만 선택된 불완전한 값을 저장할 수 있어 제외한다. `NONE`은 빈 값, 다른 기준은 양수 필수로 승인했다.

## 구현 범위 및 데이터 흐름

1. `docs/directions/20261023` 작업지시서를 작성하고 계획서와 상세사양서를 날짜별 문서 위치에 작성한다.
2. 공통코드 시드 SQL을 `docs/database/20261023`와 `backend/DATABASE/20261023`에 동일하게 둔다. 소비기한 CHECK 변경에는 별도 변경 이력과 CHECK만 제거하는 롤백 SQL을 함께 보관한다.
3. 품목 행 폼에서 기준 변경에 따라 숫자 입력을 초기화/비활성화하고 단위를 표시한다. 프론트엔드 저장 검증과 백엔드 서비스 검증은 같은 규칙을 사용한다.
4. DB CHECK가 저장 경계에서 동일한 기준-숫자 규칙을 보장한다. MCP는 스키마/코드 확인 전용으로 유지한다.
5. `docs/database/db-schema.md`, 품목관리 관련 F1-Grid 안내 및 날짜별 결과 문서를 갱신한다. 결과 문서에는 검증 결과와 화면 스크린샷을 포함한다.

## 오류 처리 및 검증

- tenant 변수가 없거나 대상 tenant가 유효하지 않으면 SQL 실행이 실패해야 하며, 일부 그룹만 입력된 채 커밋되지 않아야 한다.
- 기존 그룹/상세코드는 수정하지 않는다. 실행 후 대상 tenant에 그룹 3개와 필요한 상세코드 12개가 존재하는지 제한 조회로 확인한다.
- 프론트엔드 테스트는 각 기준의 단위 표시, `NONE` 전환 시 값 비움·비활성화, 활성 기준의 필수 양수 검증, 잘못된 정수 거부를 확인한다.
- 백엔드 서비스 테스트는 네 가지 기준과 count의 허용/거부 조합을 확인한다.
- DB 스크립트 검증은 CHECK/롤백/두 SQL 사본의 일치를 확인한다. 실제 DB에는 시드 또는 스키마 SQL을 적용하지 않는다.
- 품목 집중 프론트엔드 테스트·빌드와 백엔드 집중 테스트를 실행한다. 브라우저에서 375px, 768px, 1280px의 입력 배치를 확인하고 결과 스크린샷을 보관한다.

## 사용자 승인

- 공통코드 시드 방식: 실행 시 target tenant 지정, 충돌 시 기존 값 유지.
- 소비기한 동작: `NONE`이면 숫자 NULL 및 비활성, `DAY`/`MONTH`/`YEAR`이면 양의 정수 필수.
- 소비기한 조합을 프론트엔드·백엔드·DB CHECK에서 모두 강제.
- 전체 설계 승인 후 이 문서를 작성했다. 상세 설계 문서 검토 승인을 받은 뒤 계획 및 구현 단계로 진행한다.
