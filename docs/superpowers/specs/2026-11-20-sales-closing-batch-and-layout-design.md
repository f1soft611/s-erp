# 매출마감 선택 마감 및 화면 개선 설계

## 문제와 근거

현재 화면은 출하 상세 행을 보여주지만 F1Grid 체크박스를 숨겨 마감 대상을 선택할 수 없다. 최초 구현은 출하 ID 기준으로 선택 행을 합쳤으나, 사용자는 동일 출하의 품목 행도 각각 선택·마감되어야 한다고 명확히 요청했다. 거래명세서 발행 화면도 현재 출하 전체 snapshot만 저장하므로 상세별 선택을 추가한다. 원본 상세 연결은 헤더가 아닌 `tb_sales_statement_dt`에 저장하고, 서로 다른 출하번호의 상세도 거래처가 같으면 한 거래명세서로 묶는다.

## 고려한 접근

1. **권장: 상세 링크 기반 발행 + 원자적 batch API.** 거래명세서 상세마다 원본 `sales_delivery_detail_id`를 기록한다. UI는 같은 거래처의 여러 출하에서 미발행 상세를 선택하고, batch 마감도 미발행 상세를 고객별 문서로 생성한다. 일부만 발행되는 실패 상태를 방지한다.
2. 기존 단건 생성 API를 브라우저에서 순차 호출. 새 API가 적지만 중간 오류 시 부분 마감이 남아 결과가 불명확하므로 채택하지 않는다.
3. 선택 UI만 추가하거나 거래명세서 입력 화면으로 이동. 다중 선택에서 문서별 작업이 반복되고 요청한 마감 기능을 직접 제공하지 않으므로 채택하지 않는다.

## 확정 설계

- F1Grid의 다중 체크박스로 상세 행을 선택한다. `rowId`(sales_delivery_detail_id)가 마감 단위이므로 같은 `salesDeliveryId` 행도 각각 처리한다. 마감된 행은 체크박스를 비활성화하고 API에서도 재검증한다.
- 마감 버튼은 CREATE 권한이 있을 때 표시하고 실제 미마감 상세가 있을 때만 활성화한다. 확인창에서 상세 건수를 알리고 취소는 무변경이다.
- 거래명세일은 서버 기준일을 사용한다. batch API는 상세와 출하 헤더를 tenant 범위에서 잠그고, 선택한 라인 snapshot을 고객별 한 문서로 저장하며 하나라도 실패하면 transaction 전체를 rollback한다.
- `tb_sales_statement_dt.sales_delivery_detail_id`가 원본 출하 상세를 가리키고, `tb_sales_delivery_dt.revenue_closed_at/revenue_closed_by`가 사용자의 명시적 마감을 기록한다. 조회 상태는 거래명세서 존재가 아니라 마감 필드로 판정한다. 기존 활성 문서는 상세 `line_no`로 ID를 backfill하지만 기존 행을 자동으로 마감 처리하지 않는다.
- 기존 출하 단위 unique index를 제거하고 원본 상세 ID unique index로 중복 거래명세서 상세를 막는다. 문서 삭제 때 원본 링크는 해제하되 매출마감 기록은 유지한다.
- 매출마감 batch는 이미 활성 거래명세서가 있는 선택 행을 허용하고 중복 문서를 만들지 않는다. 발행 문서가 없는 선택 행만 고객별 한 문서에 묶어 만들고, 모든 선택 행에 마감 시각/사용자를 기록한다.
- 거래명세서 발행 화면은 같은 거래처의 여러 출하를 함께 선택하고, 그중 미발행 상세만 골라 저장한다. 이미 발행된 상세는 대상에 나타나지 않는다. 출하등록 AUTO 자동 발행은 전체 출하 상세를 그대로 포함하지만 매출마감 상태는 OPEN으로 유지한다. 그룹 문서의 상세 목록/인쇄물은 각 행에 원본 출하번호와 출하일을 표시한다.
- 별도 endpoint `POST /api/v1/sales/revenue-closings/close`는 `revenue-closing` CREATE 권한으로 보호한다. 신규 메뉴 권한과 동일 tenant의 거래명세서 생성 권한에 기초한 역할 grant를 seed에 추가한다.
- 데스크톱은 상세/요약의 고정 2열 레이아웃이다. 상세 그리드와 고객 목록은 각자 스크롤할 수 있다. 모바일은 페이지 스크롤과 요약 목록 내부 스크롤을 함께 사용하고 상세 영역에 최소 높이를 둔다.
- 요약은 반복되는 큰 카드를 제거하고 전체 KPI + compact 행 목록으로 재구성한다. 선택 상태와 마감/미마감 색상 구분을 유지한다.

## 오류 처리 및 검증

서버 기준일을 가져오지 못하거나 batch API가 실패하면 명시적인 오류를 표시하고 데이터/선택을 성공 상태로 바꾸지 않는다. 성공 시 선택을 비우고 동일 필터로 조회를 갱신한다. 검증은 프론트 컴포넌트/API 테스트, F1Grid의 비선택 행 처리, 선택 상세 snapshot 및 AUTO 전체 상세 발행 테스트, backend 권한/원자성/tenant 테스트, build/lint, 375/768/1280px 브라우저 확인으로 수행한다. 스키마와 메뉴 SQL 변경 이력은 paired 날짜 폴더에 기록하고 SQL은 실제 DB에 적용하지 않는다.
