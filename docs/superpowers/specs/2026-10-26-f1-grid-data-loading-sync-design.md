# F1-Grid 조회 데이터 표시 시점 설계

## 배경과 원인

품목관리와 거래처 관리의 최초 목록 조회는 API 응답을 받은 뒤 부모 상태의 `rows`와 `loading`을 함께 갱신한다. 공통 F1-Grid는 새 `rows`를 내부 편집 모델에 반영하는 작업을 passive `useEffect`에서 수행한다. 이에 따라 `loading=false`인 부모 렌더가 먼저 페인트되고, 자식 effect의 `setData`가 뒤따르는 사이 빈 그리드가 잠깐 나타날 수 있다. 같은 prop 동기화 경로를 사용하는 검색/재조회에도 같은 시점 차이가 생길 수 있다.

## 검토한 접근

1. **권장 — 외부 행 동기화를 `useLayoutEffect`로 수행.** 기존 내부 데이터 동기화 전에 브라우저가 페인트하지 않게 한다. 변경 지점이 공통 F1-Grid 한 곳이고, 페이지 로딩/API 계약과 오버레이 표시 조건은 그대로 유지한다. 행 모델을 동기화하는 작업은 페인트 직전에 실행되므로 큰 데이터셋 검증이 필요하다.
2. **그리드 준비 상태 동안 오버레이 유지.** passive effect는 유지하면서 입력 `rows`와 내부 데이터가 동기화될 때까지 로딩 표시를 유지한다. 새 준비 상태와 일치 여부 관리가 추가된다.
3. **그리드 반영 완료 콜백으로 페이지 로딩을 종료.** 준비 완료 경계는 명시적이지만 공통 그리드 API와 각 사용 페이지를 함께 변경해야 한다.

## 승인된 설계

- F1-Grid가 외부 `rows` prop을 내부 편집 상태로 동기화하는 기존 effect를 `useLayoutEffect`로 옮긴다.
- 행 데이터 변환, 로컬 편집 변경 처리, 데이터 소스 재기준화, 선택·포커스 초기화 조건 등 기존 동기화 로직은 유지한다.
- 페이지의 API 요청, `loading` 생성/전달, 공통 로딩 오버레이 및 저장 상태 정책은 변경하지 않는다.
- 공통 컴포넌트 변경으로 품목·거래처의 최초 조회와 이후 검색/재조회, 그 밖의 F1-Grid 사용 화면에 동일한 페인트 전 동기화가 적용된다.

## 동작 및 예외

- 조회 중에는 기존 로딩 오버레이와 접근성 상태를 유지한다.
- 조회 성공 시 행이 내부 모델에 반영되기 전까지 새 빈 그리드 프레임이 표시되지 않으며, 로딩 오버레이가 사라지는 프레임에는 새 데이터가 표시된다.
- 빈 배열은 기존 빈 그리드 동작을 유지한다.
- 조회 오류 처리 및 이전 행 유지 여부는 페이지의 기존 책임을 유지한다.
- 편집 변경이 존재하는 경우 기존의 변경 행 보존/데이터 소스 리베이스 분기를 변경하지 않는다.
- 동기화를 layout phase에서 실행하면 페인트가 데이터 반영 완료까지 대기한다. 일반/대량 데이터셋 회귀 및 실제 화면에서 과도한 프레임 정체가 없는지 확인한다.

## 검증

- F1-Grid에서 새 행 prop과 `loading=false`가 함께 전달될 때 오버레이가 제거된 화면에는 새 행이 존재하는지 검증한다.
- 기존 편집, 선택/포커스, 데이터 소스, 저장 행 확정 및 대량 행 렌더링 회귀를 실행한다.
- 프론트엔드 빌드를 실행한다.
- 가능한 실제 브라우저 환경에서 품목관리·거래처 관리의 최초 조회를 확인하고 결과 문서에 재현/해결 내용과 캡처를 기록한다.

## 범위 제외

- 품목·거래처 API 또는 백엔드/DB 변경
- 페이지별 로딩 상태 정책 및 저장 처리 변경
- 그리드 스켈레톤, 스피너 디자인, 행 가상화 및 그리드 렌더 구조 변경
