# 2026-11-17 회의 안건 설계안 (작업장·소수점·수주현황·거래명세서·공통코드·품목분류)

상태: 설계 초안 (사용자 승인 전, 구현 미착수). 6개 안건은 서로 독립이므로 각각 별도 작업지시서 → 계획서 → 사양서 → 구현 사이클로 진행한다.
DB 근거: 현재 코드/스키마 이력(Mapper XML, `backend/DATABASE/20261027`) 기준. 구현 착수 전 `s-erp-postgresql-readonly` MCP로 `describe_table` 재확인 필요(이번 설계에서는 미수행).

## 권장 진행 순서

| 순서 | 안건 | 규모 | 근거 |
| --- | --- | --- | --- |
| 1 | 수주현황 컬럼 조정 | 소 | 프론트만, 의존 없음 |
| 2 | 공통코드 모듈 구분 | 소~중 | 컬럼 1개 + 필터 |
| 3 | 소수점 정책 (1단계: 화면별) | 중 | F1Grid 옵션 이미 존재 |
| 4 | 거래명세서 발행 + 정책 | 중~대 | 기존 출하계획 정책 패턴 재사용 |
| 5 | 작업장/공정 구조 개편 | 대 | 스키마 변경·데이터 이관 |
| 6 | 품목 동적 분류 | 대 | 설계 결정 필요, 별도 브레인스토밍 |

## 1. 작업장(공정그룹) 개편

현황: `tb_process_group(group_id)` 1 : N `tb_process(process_id, group_id)`. 공정이 그룹 하위에 종속되어 같은 공정도 그룹마다 다른 ID로 중복 생성된다. 화면은 `pr/process` 트리 하나로 그룹+공정을 함께 편집한다.

변경안 (권장: 공정 마스터 + 작업장-공정 매핑)
- `tb_process_group` → 개념상 **작업장**. 테이블 리네임은 위험(참조·API)이 크므로 1차에서는 테이블/API 유지, 화면·문구만 "작업장"으로 변경. 리네임은 별도 판단.
- `tb_process`: `group_id` 종속 제거, 테넌트 단위 **공정 마스터**(이름·설정 플래그)로 독립.
- 신규 `tb_process_group_process(tenant_id, group_id, process_id, sort_seq, …)`: 작업장이 어떤 공정을 갖는지 관리. UNIQUE(tenant_id, group_id, process_id), 복합 FK로 테넌트 정합성 보장.
- 이관: 기존 `(group_id, 같은 이름·설정)` 공정을 이름+설정 기준으로 병합해 마스터로 통합하고 매핑 행 생성. 병합 규칙(이름만 동일 vs 플래그까지 동일)은 구현 전 확정 필요. 외부에서 `process_id`를 참조하는 테이블이 있으면 함께 재매핑.
- 화면
  - 공정관리: 문구 "공정그룹"→"작업장". **공정 설정** 버튼 → `CommonDialog` 모달에서 공정 마스터 등록/수정/삭제.
  - 작업장 안 공정 추가: 공정 설정에서 등록된 공정을 조회·선택하여 매핑 추가(직접 신규 입력 금지).
  - 공정 마스터 삭제 시 매핑 존재하면 차단.
- 위치: 기존 `pr/process` 구조 유지(`frontend/src/pages/pr/process`, `backend/.../let/pr/process`). 공정 설정 모달은 `components/`로 분리.
- DB: 날짜별 SQL + 변경 이력 + 롤백(`docs/database`, `backend/DATABASE` 동일 유지).

## 2. 그리드 소수점 관리

1단계 (화면별): `F1Grid`의 숫자 컬럼 소수점 옵션(2026-10-26 number-decimal-precision 설계)을 화면 컬럼 정의에서 지정. 신규 기능 없이 각 화면 컬럼에 `decimals` 명시.

2단계 (모듈별 정책): 정책 관리(`SystemPolicy`, 값 유형 NUMBER/SELECT 지원, 이력·버전 관리 포함)를 활용.
- 정책 코드 예: `DECIMAL_PLACES_SALES`, `_PURCHASE`, `_PRODUCTION`, 각 NUMBER 값. 수량/단가/금액 구분이 필요하면 `DECIMAL_QTY_SALES`처럼 세분화(필요 시점에 결정).
- 기존 정책 테이블이 값 유형을 이미 확장 가능하게 지원하므로 **테이블 확장 없이** 정책 행 추가로 시작. 내장 정책(`BUILT_IN_CODES`)이 아닌 사용자 정의 정책으로 시드.
- 적용 방식: 프론트에 `useModuleDecimals(moduleKey)` 훅(정책 조회+캐시) → 화면 컬럼의 `decimals` 기본값으로 주입. 화면별 명시 값이 있으면 그것이 우선. 정책이 없으면 현재 기본값 유지(무중단).
- 검토 필요: 저장 시 서버 반올림/검증 일치(서버가 정책 자릿수를 초과한 값을 거부/반올림할지), 이미 저장된 데이터의 표시 vs 저장 정밀도(DB 컬럼 scale 확인).

## 3. 수주현황

- 수주상태(헤더) 컬럼 숨김, 행상태 컬럼을 앞쪽으로 이동하고 헤더명을 "업무상태"로 변경.
- 프론트 컬럼 정의만 변경(`pages/sales/order` 현황 화면). API·데이터 계약 불변. 컬럼 사용자 설정(로컬스토리지) 저장 키 충돌 여부 확인.

## 4. 거래명세서 발행

- 명칭: "거래명세서등록" → "거래명세서 발행"(메뉴/화면/문구만, URL·page key·API는 변경하지 않음. 지침 준수).
- 정책: 정책 관리에 **거래명세서 발행 방식** 추가 (`STATEMENT_ISSUE_MODE`: `AUTO`/`MANUAL`). 출하계획 정책(`DELIVERY_PLAN_MODE`)과 동일 패턴.
  - 기존 정책은 테넌트 컬럼 + 내장 코드(`BUILT_IN_CODES`)로 구현되어 있다. 동일 방식(테넌트 컬럼 추가)이 일관적이나 DB 변경이 필요. 대안으로 사용자 정의 정책 행 사용(스키마 불변). **권장: 출하계획 정책과 동일한 내장 방식** (서비스에서 즉시 읽고 변경 가드 필요하므로).
- AUTO: 출하등록 저장 트랜잭션 내에서 출하 등록 묶음 단위 1건당 거래명세서를 자동 생성(실패 시 출하 저장 롤백할지, 별도 보정할지는 구현 전 결정 — 권장: 같은 트랜잭션).
- MANUAL: 발행 화면에서 동일 거래처의 출하건을 여러 건 선택해 하나의 명세서로 묶어 발행. 이미 발행된 출하건은 제외(중복 발행 방지).
- 모드 변경 가드: 출하계획 정책처럼 기존 데이터가 있을 때 변경 제한 여부 확인 필요.
- 위치: `sales/shipment/statement`.

## 5. 공통코드 모듈 구분

- 상위 그룹 코드 테이블에 `module_cd`(공통/영업/생산/구매/품질…) 컬럼 추가. 값은 공통코드 자체(예: `MODULE_CATEGORY` 그룹)로 관리해 하드코딩 회피. 기본값 `COMMON`.
- 화면: 목록 상단 모듈 필터(전체 포함), 그룹 등록/수정 폼에 모듈 선택. 트리 그리드 구조 유지.
- 기존 데이터: 마이그레이션에서 `COMMON`으로 일괄 설정 후, 화면 코드 접두 규칙 등으로 점진 재분류.

## 6. 품목 테넌트별 동적 분류

현황: `tb_cls_item`(테넌트, 레벨 1~3 고정 트리)과 `tb_material_info.item_cls_id`가 이미 설계되어 있다(2026-10-27). 즉 "분류 트리"는 있으나 "분류 **축(항목) 개수**를 테넌트가 정의"하는 요구는 별개다.

접근안
- A. **분류 축 정의 + 값 트리** (권장): `tb_cls_item_axis(tenant_id, axis_id, name, sort_seq, use_at)`로 테넌트가 축(예: 대분류·소분류·브랜드)을 N개 정의, `tb_cls_item_value(axis_id, value_id, name, …)`로 값, `tb_material_cls(material_id, axis_id, value_id)`로 품목별 선택값 저장. 관계형 정합성·검색/필터 유리. 품목 화면은 축 목록을 읽어 동적 폼/컬럼 생성.
- B. JSONB 컬럼에 분류값 저장: 구현이 빠르나 FK 무결성·조회 성능·통계가 약함.
- C. 고정 컬럼(분류1~5) 사용 + 라벨만 테넌트 설정: 단순하나 최대 개수 제한, 값 관리 어려움.

결정 필요(착수 전 확인): ① 축 간 상하관계(계층)가 필요한지 독립 다중 분류인지, ② 축 최대 개수, ③ 기존 `item_cls_id` 트리를 축 1로 이관할지.
이 안건은 구현 전에 별도 브레인스토밍으로 요구를 확정한다.
