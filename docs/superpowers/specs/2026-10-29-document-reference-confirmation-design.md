# 문서 참조자 확인 처리 설계

## 목표

업무연락 및 기안서의 참조자가 문서를 단순 열람하는 데 그치지 않고, 문서 상세에서 명시적으로 `확인`할 수 있게 한다. 미확인 문서는 종합현황과 문서작성 결재요약에 각각 결재 업무와 구분해 표시한다.

## 현재 구조와 근거

- 업무연락 작업지시서는 참조자에게 발송하면 완료되며 수신자의 확인을 요구하지 않는다고 정한다. 이 동작은 이번 요구사항으로 변경한다.
- 기존 결재 요약은 `내가 처리할 결재`, `결재 진행 중`, `작성 중 문서`를 표시하고, 문서 상태 요약은 별도 패널에 표시한다.
- 종합현황의 현재 결재 업무 목록은 결재 대기 및 보완요청을 표시한다.
- 결재선의 `REFERENCE` 참여자는 현재 결재 액션 대상이 아니며, 문서 조회 권한만 가진다.
- 상세 타임라인은 공통 SYSTEM 이력을 사용한다. 확인 액션과 이력 추가는 원자적으로 처리한다.

## 승인된 동작

### 참조 확인 대상

- 대상은 기안서와 업무연락의 `REFERENCE` 참여자다.
- 임시저장(`DRAFT`) 중에는 확인할 수 없다. 기안서는 상신 후, 업무연락은 발송 후부터 확인할 수 있다.
- 참조자로 지정된 로그인 사용자만 해당 문서를 확인할 수 있다. 결재자, 기안자 또는 다른 문서 참여자에게 참조 확인 액션을 노출하지 않는다.
- 문서가 `COMPLETED`, `REJECTED` 등 최종 상태가 되더라도 해당 참조자가 확인하지 않았다면 확인 대상에 남는다.
- 확인은 참조자별 1회 처리다. 문서 결재 상태, 결재선 순서, 결재 대기 건수에는 영향을 주지 않는다.
- 확인된 문서는 대기 목록과 건수에서 제외하되 기존 관련 문서 목록, 상세, 첨부 및 이력 접근은 유지한다.

### 상세 화면과 시스템 이력

- 미확인 참조자에게 문서 상세에서 `확인` 액션을 제공한다. 처리 중에는 중복 입력을 막는다.
- 확인 성공 시 참조 참여자의 상태와 확인 시각을 저장하고, 기존 결재 액션과 동일한 공통 SYSTEM 이력 기록 경로로 같은 트랜잭션에서 `REFERENCE_CONFIRMED` 이벤트를 추가한다. 별도 로그나 사용자 댓글로 기록하지 않는다.
- 이력은 기존 결재 액션 시스템 메시지와 같은 타임라인 및 표시 형식으로 노출한다. 확인자 이름과 기록 시각을 기존 작성자/생성시각 표시 규칙으로 보여주고, 메시지는 `문서를 확인했습니다.`로 기록한다. 결재자/참조자를 포함한 문서 열람 권한이 있는 참여자는 이력을 조회할 수 있다.
- 중복 또는 재시도 요청은 확인 상태를 되돌리거나 시스템 이력을 중복 추가하지 않는다. 이미 확인된 상태라면 기존 성공 상태를 반환한다.
- 상태 저장이나 시스템 이력 저장 중 하나라도 실패하면 모두 롤백하고 확인 완료로 표시하지 않는다. 실패는 기존 문서 상세 오류 표시 패턴으로 사용자에게 알린다.

### 종합현황

- 기존 `내가 처리할 결재`와 구분되는 `내가 확인할 문서` 영역을 추가한다.
- 영역은 미확인 참조 문서의 건수와 문서 목록을 보여준다. 목록은 문서 제목과 문서 종류 등 기존 요약 카드 수준의 정보를 재사용한다.
- 항목을 선택하면 기존 문서 상세 화면을 열고, 확인 완료 후 목록 및 건수를 새로고침한다.
- 결재 대기/보완요청 영역과 결재 건수의 의미는 그대로 유지한다. 참조 확인 문서를 결재 notice로 섞지 않는다.

### 문서작성 결재요약

- 우측 `결재 요약` 패널에 결재 항목과 별개의 `내가 확인할 문서` 건수를 추가한다.
- 해당 행을 선택하면 미확인 참조 문서만 조회한다. 이 범위는 결재 대기와 별도의 조회 조건으로 처리하며, 기존 문서 상태 필터와 보기 모드는 유지한다.
- 확인 완료 후 문서작성 목록과 결재요약을 갱신한다. 이미 제공하는 `문서 상태` 및 `놓치지 마세요` 패널의 기존 의미와 구성은 유지한다.

## 데이터와 API 설계

- 참조자별 상태는 기존 전자결재 참여자 행에서 관리한다. 확인된 `REFERENCE` 행은 `action_status=CONFIRMED`, `action_at`은 확인 시각으로 기록하고 `action_comment`는 비워 둔다. 미확인 참조 행은 기존 초기 상태를 유지한다.
- 결재 처리 상태와 구별되도록 `CONFIRMED`는 `REFERENCE`에서만 유효하게 서버 검증 및 DB 제약으로 제한한다. 실제 현행 CHECK 제약 및 인덱스는 구현 전에 기본 DB MCP의 read-only metadata 조회로 확인한다.
- SYSTEM 이벤트 허용 제약에는 `REFERENCE_CONFIRMED`를 추가한다. 신규 테이블은 만들지 않는다.
- 확인 API는 문서 ID로 요청자를 식별하며, 서버가 인증 사용자·tenant·문서 참여 행·문서 상태를 검증한다. 요청에서 사용자 ID 또는 확인 시각을 받지 않는다.
- 문서 목록은 새 조회 범위 `MY_REFERENCE_PENDING`을 지원해 로그인 사용자의 미확인 REFERENCE 행이 있는 문서만 반환한다. `DRAFT` 문서는 제외한다.
- 결재요약 응답에는 참조 확인 대기 건수와 미확인 문서 목록을 결재 notice와 분리해 제공한다. 종합현황도 같은 사용자 범위에 한정된 대기 건수/목록을 제공한다.
- 신규 상태 및 이벤트 제약에 migration이 필요하면 날짜별 SQL, 변경 이력, 롤백 파일을 `backend/DATABASE`와 `docs/database`에 동일하게 추가하고 `docs/database/db-schema.md`를 갱신한다. DB 변경 여부와 제약의 구체적인 전제는 MCP 메타데이터와 현재 이력 확인 뒤 확정한다.

## 대안과 선택

1. **기존 참여자 행에 확인 상태를 기록하고 SYSTEM 이벤트를 추가한다 — 선택.** 사용자별 확인 상태를 직접 조회할 수 있고 기존 결재선 및 타임라인을 재사용한다. 결재 상태와 충돌하지 않도록 `CONFIRMED`는 `REFERENCE`에만 허용한다.
2. 확인 전용 테이블을 추가한다. 상태와 참여자 모델을 완전히 분리할 수 있지만 현재 참여자 행과 중복 관계를 유지해야 한다.
3. SYSTEM 이벤트만으로 확인 상태를 추론한다. 별도 참여자 상태는 없지만 대기 건수·미확인 문서 조회와 중복 처리의 무결성이 복잡해진다.

## 오류 및 권한 경계

- 비참조자, 다른 tenant 사용자, 임시저장 문서 또는 접근할 수 없는 문서의 확인 요청은 거부한다.
- 활성 참조 참여 행은 서버가 인증 사용자 기준으로 찾아야 하며, 클라이언트가 임의의 참여자 ID를 지정하지 못한다.
- 목록과 건수는 현재 인증 사용자 및 tenant 범위로 제한하고 문서별로 중복 집계하지 않는다.
- 목록/상세/확인 API 오류는 성공처럼 처리하거나 빈 결과로 감추지 않는다.

## 제외 범위

- 열람(open)만으로 자동 확인 처리
- 이메일/푸시 알림, 수신 여부 추적, 확인 취소 또는 확인 이력 수정
- 결재선 순서, 승인/반려/보완요청, 업무연락 완료 상태 변경
- 기존 완료·반려 문서의 자동 확인 또는 과거 확인 데이터 backfill
- 참조자가 아닌 사용자에게 확인 액션을 부여하는 것

## 검증 기준

- 업무연락 발송 후 참조자에게만 확인 액션과 대기 항목이 보이고, 기안서도 상신 후 같은 규칙이 적용된다.
- 임시저장, 비참조자, 다른 tenant, 접근 불가 문서는 확인 및 대기 목록에서 거부/제외된다.
- 확인 성공은 참여자 행과 SYSTEM 이력을 원자적으로 저장하며, 실패 시 어느 쪽도 부분 반영하지 않는다.
- 동일 사용자 재요청은 이력을 중복 생성하지 않고 확인 완료 상태를 유지한다.
- 결재 완료/반려 등 최종 상태인 미확인 문서도 참조자가 확인할 때까지 표시된다.
- 확인 건수 및 목록은 문서작성 결재요약과 종합현황에서 일치하며, 결재 대기 count/notice에는 섞이지 않는다.
- 확인 완료 후 두 화면의 미확인 목록/건수에서 빠지고 일반 문서 목록과 상세 접근은 유지된다.
- 관련 회귀 테스트와 백엔드 테스트, 프론트엔드 빌드/테스트를 수행한다. UI 변경은 실제 브라우저 375px, 768px, 1280px에서 확인하고 결과 스크린샷을 저장한다.
