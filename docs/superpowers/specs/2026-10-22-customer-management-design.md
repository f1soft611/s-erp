# Customer Management Page Design

## Status

- Design approved in conversation on 2026-10-22 and updated to use the existing eGov ID Generator after user clarification.
- Visual layout: option A, full-width F1-Grid with a grid row form.
- Scope: tenant-scoped listing/search, create, update, and use-status changes.

## Context

The requested page is `/co/master/customers`, using the existing S-ERP `co` dashboard module. The selected reference is the draft form management page, especially its single keyword search, metadata-driven detailed search, permission-aware actions, and F1-Grid row form.

The tenant PostgreSQL MCP confirmed the `public.tb_customer_info` table has these business fields:

| Column | Type | Nullability / default |
| --- | --- | --- |
| `customer_id` | `bigint` | not null; generated by `tb_customer_info_customer_id_seq` |
| `tenant_id` | `bigint` | not null |
| `customer_code` | `varchar` | not null |
| `customer_name` | `varchar` | not null |
| `cust_name_abbr` | `varchar` | nullable |
| `president_name` | `varchar` | nullable |
| `business_no` | `varchar` | nullable |
| `jurid_no` | `varchar` | nullable |
| `business_status_1` | `varchar` | nullable |
| `business_item_1` | `varchar` | nullable |
| `post_code` | `varchar` | nullable |
| `address` | `varchar` | nullable |
| `telephone_no` | `varchar` | nullable |
| `facsimile_no` | `varchar` | nullable |
| `cust_memo` | `varchar` | nullable; defaults to empty string |
| `use_at` | `char(1)` | not null; defaults to `Y` |
| `created_by`, `updated_by` | `bigint` | nullable |
| `created_at`, `updated_at` | `timestamp` | not null; default to current timestamp |

Metadata also confirmed a primary key on `customer_id`, a foreign key from `tenant_id` to `tb_tenant`, a `Y`/`N` check on `use_at`, and a unique constraint on `(tenant_id, customer_code)`. No tenant data rows were queried.

The tenant MCP also confirmed the existing `public.ids` generator table and its `(table_name)` primary key. The project config already uses `EgovTableIdGnrServiceImpl` with table `IDS`, a configured `tableName`, and zero-padded output for other master-data codes. No business or generator-counter rows were queried.

## Approaches Considered

1. **Tenant-scoped API and F1-Grid (selected).** Add frontend page behavior and backend APIs over the existing table. This supports the requested persistence and CRUD scope while preserving tenant isolation and existing UI patterns.
2. **Frontend-only mock or static data.** Faster to render, but does not load or persist `tb_customer_info`, so it does not meet the requested management behavior.
3. **Frontend direct database access or a generic unrestricted CRUD endpoint.** Rejected because it bypasses backend tenant authorization and the established service/DAO boundary.

## Approved Design

### Page and data flow

- Connect the `co` module page key `customers` to the `/co/master/customers` menu in `DashboardContent`.
- Follow the established page structure: `PageHeader`, `PageSearchArea`, `PageMessageArea`, and F1-Grid. Reuse the dashboard-provided breadcrumb and menu permissions.
- Add a tenant-scoped backend API under `/api/v1/co/master/customers` for list/search, create, and update.
- Derive `tenant_id` from the authenticated backend principal, never from a caller-supplied tenant identifier. Scope list, duplicate-code checks, and update targets to that tenant.
- Do not implement physical delete. Change `use_at` between `Y` and `N`.
- Keep `customer_id`, `tenant_id`, and audit columns server-managed.

### Search

- Provide one integrated keyword field, matching `customer_code`, `customer_name`, and `cust_name_abbr` by partial match. Enter and the standard search action apply it.
- Generate detailed-search fields from F1-Grid column metadata using the existing `toPageSearchFields()` and `PageSearchArea` pattern.
- Detailed fields: `president_name`, `business_no`, `jurid_no`, `business_status_1`, `business_item_1`, and `use_at`.
- Apply detailed search only when the user submits the detail search. Search conditions combine with the keyword in the same list request.
- Initial results include both active and inactive rows; `use_at` is an optional detailed-search filter.

### F1-Grid and row form

- Use a full-width F1-Grid with columns for row number, customer code, name, abbreviation, president, business number, business status, business item, telephone, address, and use status.
- Register and edit rows through the F1-Grid row form. Expose the table's business fields: customer code, customer name, abbreviation, president, business/registration numbers, business status/item, postcode/address, telephone/fax, memo, and use status.
- A blank customer code is generated by the backend as exactly six digits. A provided code is retained and checked for duplicates within the authenticated tenant.
- `customer_name` is required. `use_at` accepts only `Y` or `N`.
- Registration and update provide clear loading, validation, success, and request-error feedback. Preserve existing F1-Grid behavior and use the grid's internal horizontal scrolling on narrow viewports.

### Code generation and database change

- Leave the existing `customer_id` default sequence responsible for `customer_id`.
- Use the existing eGov ID Generator table `IDS` through a dedicated `customerCodeIdGnrService` bean configured with `tableName = "tb_customer_info"`, no prefix, six digits, and block size 1. Do not create a customer-specific sequence or table.
- Initialize the existing `ids` counter row from the largest existing 1–6 digit numeric customer code plus one. If the row already has a larger counter, preserve it. This aggregate initialization does not copy or publish business rows.
- Reject generated values outside the six-digit range, including values above `999999`, with an explicit exhaustion error.
- Preserve the existing tenant-scoped unique constraint as the final duplicate guard.
- No `tb_customer_info` columns or constraints are changed. Record the existing `ids` counter initialization in the date-based SQL change/rollback history and keep the `docs/database` and `backend/DATABASE` copies identical. A rollback must not reduce or delete the counter, since generated codes may already be saved.

### Responsive layout and validation

- Respect the 375px, 768px, and 1280px viewport guidance. Keep search controls and action buttons usable without page-level horizontal overflow; allow the grid to scroll internally.
- Add focused frontend tests for keyword/detail search, row-form create/update, permissions, loading/error states, and code display behavior.
- Add backend tests for tenant-scoped list/update, code generation (including exhaustion), required fields, `use_at` validation, and tenant-scoped duplicate rejection.
- Run the focused tests and frontend build, then perform browser checks at the required viewport widths and include screenshots in the dated result directory.

## Out of Scope

- Physical deletion.
- Any changes to the existing `tb_customer_info` table shape.
- Cross-tenant lookup or caller-selected tenant IDs.
- F1-Grid core changes.
- New search criteria not backed by `tb_customer_info`.
