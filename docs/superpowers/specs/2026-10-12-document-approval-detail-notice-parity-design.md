# 전자결재 상세 패널 공지사항 UI 정합성 설계

## 목적

전자결재 문서 상세 패널의 표현과 상호작용을 공지사항 피드 수준으로 통일한다. 전자결재의 기존 결재 흐름과 문서 참여 권한은 유지하며, 문서 이력은 별도 섹션 대신 댓글 타임라인에 통합한다. 기안자에게 허용되는 문서 수정·삭제 메뉴를 제공하고, 삭제는 감사 자료를 보존하는 논리 삭제로 처리한다.

## 승인된 접근 방식

전자결재 전용 상세 패널을 유지하고 공지사항의 표시 패턴과 기존 공통 피드 컴포넌트를 재사용한다. `PostDetailPanel`, `AttachmentList`, `CommentThread`를 계속 사용하며, 공지사항 상세 전체를 범용화하거나 공지사항 컴포넌트에 전자결재 도메인 로직을 넣지 않는다.

이 방식은 댓글·첨부와 상세 패널의 기존 공통 UI를 재사용하면서, approval 전용 권한과 API 경계를 보존하고 변경 범위를 제한한다.

## 사용자 흐름 및 UI

### 상단 헤더와 본문

- 패널 자체의 상단 타이틀은 문서 제목이 아니라 고정 문구 `문서 상세`로 표시한다. 이 타이틀과 함께 `electronicApprovalId`를 `문서 ID`로 표시하고 기존 닫기 동작을 유지한다.
- 패널 콘텐츠 첫 카드의 헤더를 공지사항 피드처럼 구성한다. 기안자 아바타/이름과 기안일을 표시하고, 우측에는 핀 UI, 더보기, 결재 상태 배지를 둔다.
- 카드 본문은 다음 순서로 구성한다.
  1. 상단 헤더의 기안일·기안자 등 읽기 전용 문서 메타정보
  2. 작성 화면과 같은 결재선 단계·참여자 표현. 이름, 부서, 단계/유형, 처리 상태와 처리 의견은 읽기 전용이고 편집 컨트롤은 노출하지 않는다.
  3. 문서 제목
  4. 본문 내용
  5. 본문에 포함된 이미지 미리보기 목록
  6. 문서 첨부파일 목록
  7. 좋아요·북마크 UI
  8. 댓글 타임라인
- 작성 모달이 현재 `electronicApprovalId`를 임시저장 문서 ID로 표시하고, `eabusNo`는 `001`, `008`, `004`, `031` 같은 문서 종류 코드이므로, 문서 ID 표시는 `electronicApprovalId`를 사용한다.
- 본문 이미지는 기존 인증 경로에서 blob URL로 가져와 공지사항의 썸네일 목록과 같은 순서·미리보기 상호작용으로 표시한다. 저장된 본문 데이터는 변경하지 않으며, 본문 내 원래 위치에는 번호/대체 텍스트 참조를 남기고 실제 이미지 미리보기는 별도 목록에서 한 번만 렌더링한다.
- 문서 첨부 목록은 공지사항과 같은 `AttachmentList` 표시 패턴을 사용하고 파일명, 이미지 미리보기(지원되는 경우), 다운로드 동작을 유지한다.
- 기존 활성 처리자의 승인/반려/보완요청, 기안자의 보완 수정/재상신 동작을 유지한다.

### 좋아요·북마크 및 핀

- 좋아요·북마크 버튼과 수치/상태 표현은 공지사항 피드와 같은 위치와 스타일로 표시한다.
- 현재 approval 백엔드에는 좋아요·북마크 API/저장 계약이 없으므로 서버 요청을 추가하지 않는다. 사용자가 누르면 현재 화면에서만 선택 상태와 표시 수치를 갱신하는 임시 프런트엔드 상호작용으로 둔다. 새로고침 또는 상세 패널을 다시 열면 초기 표시 상태로 돌아간다.
- 핀은 아이콘만 표시하고 클릭 동작 및 저장을 추가하지 않는다.

### 더보기·수정·삭제

- 문서 소유자인 기안자에게 권한 상태에 맞는 `수정` 및 `삭제` 메뉴를 제공한다. 다른 참여자에게 기안자 전용 메뉴를 노출하지 않는다.
- 수정은 기존 규칙을 유지해 소유 기안자의 `DRAFT` 또는 `REVISION_REQUESTED` 문서에만 허용한다.
- 삭제 전 확인 다이얼로그를 표시한다. 성공하면 상세 패널을 닫고 문서 목록·요약을 갱신한다. 실패하면 상세를 유지하고 오류를 명시한다.
- 삭제 허용 상태:
  - 기안자 소유의 `DRAFT`
  - 기안자 소유의 `PENDING` 문서 중 결재신청 시 기안자 자동 승인 이외에 다른 결재 참여자가 처리한 이력이 전혀 없는 상태
- `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `REVISION_REQUESTED` 또는 다른 결재자가 이미 처리한 문서는 삭제할 수 없다.
- 백엔드는 로그인 주체, tenant, 문서 소유자, 상태와 결재선의 처리 이력을 검증한다. 삭제 요청과 결재 액션은 동일 문서 행을 잠그고 상태를 다시 확인해 경쟁 요청이 잘못된 결과를 만들지 않게 한다.

### 댓글 및 시스템 이력 통합

- 별도 `문서 이력` 섹션을 제거하고, 시스템 이벤트와 사용자 댓글을 하나의 `댓글` 타임라인에 표시한다.
- 승인/반려/보완요청/상신/재상신/완료 등의 SYSTEM 이벤트는 시각을 기준으로 USER 댓글 스레드와 시간순 배치한다. SYSTEM 행은 읽기 전용이며 답글·수정·삭제 대상이 아니다.
- USER 댓글, 대댓글, 작성자 수정/삭제, 이전 댓글 조회 및 댓글 첨부 조작은 기존 승인 전용 API와 공통 `CommentThread` 동작을 유지한다. 대댓글은 부모 USER 댓글 아래에 둔다.
- 기존 SYSTEM 이벤트 조회와 USER 댓글 페이지 API를 유지하고 화면에서 결합한다. 페이지네이션은 USER 댓글에 적용하며, SYSTEM 이벤트가 로드된 사용자 댓글을 중복시키거나 댓글 개수를 바꾸지 않게 한다.

## API 및 권한

- 신규 삭제 API: `DELETE /api/v1/groupware/approvals/{electronicApprovalId}`. 요청 본문의 사용자/tenant 식별자는 신뢰하지 않는다.
- 삭제 API는 로그인한 문서 기안자만 호출할 수 있으며, 잠금된 문서의 현재 상태와 결재선 행을 기준으로 위 삭제 조건을 다시 검증한다. 조건 불일치 또는 이미 삭제된 문서는 기존 상태 충돌/존재 은닉 응답 규칙에 맞춰 실패한다.
- `DRAFT` 및 미처리 `PENDING` 문서는 논리 삭제하고, 동일 트랜잭션에서 `DELETED` SYSTEM 이벤트를 추가한다. 처리 실패 시 삭제 표시와 이벤트 기록 모두 롤백한다.
- 삭제된 문서는 정상 사용자 경로에서 목록, 요약, 알림, 상세, 참여자 검증, 댓글, 첨부 및 본문 이미지 조회/다운로드에 포함하지 않는다. 기존 문서 행, 결재선, `tb_common_comment` 이력, 첨부 메타데이터와 본문 이미지 파일은 물리적으로 삭제하지 않는다.
- 좋아요/북마크/핀에는 API, DB 저장, 권한 우회 경로를 추가하지 않는다. 댓글·첨부·결재 처리는 기존 approval 전용 권한 검증을 계속 사용한다.

## DB 변경 및 이력 보존

구현 전 `s-erp-postgresql-readonly`의 현재 계약을 확인했다. 행 데이터는 조회하지 않았다.

- `tb_electronic_approval_main`에 `deleted_yn` 논리 삭제 표시가 없고, 현재 `document_status` CHECK 목록에도 `DELETED` 상태가 없다.
- `tb_electronic_approval_line_info`는 `(tenant_id, electronic_approval_id)` FK로 문서 삭제 시 cascade 된다. `tb_common_comment`의 parent FK만 확인되었고 approval 문서와 comment/file 간 FK는 없다.
- 논리 삭제는 문서 상태를 새 값으로 바꾸지 않고 `deleted_yn`을 추가해 표현한다. 따라서 기존 상태 전이 계약을 바꾸지 않는다.
- `tb_common_comment`의 SYSTEM event CHECK에 `DELETED`를 추가해 삭제 이벤트를 append-only로 기록한다.
- 날짜별 migration, 변경 이력, 롤백 스크립트를 `docs/database/20261012`와 `backend/DATABASE/20261012`에 동일하게 추가하고 `docs/database/db-schema.md`를 갱신한다.
- 기존 문서 삭제 표시 컬럼을 추가하는 migration과 SYSTEM 이벤트 CHECK 확장은 한 변경 번호를 사용하고, 롤백에서 기본 미삭제 값/기존 이벤트 허용 목록을 복구한다. 적용 후의 삭제 표시 데이터 복구 가능 여부와 CHECK 원복 전제는 변경 이력에 명시한다.

## 컴포넌트 및 책임

- `DocumentApprovalDetailFeed`: 공지사항형 문서 헤더/상태/제목/문서번호, 읽기 전용 결재선, 본문·첨부, 임시 좋아요/북마크, 통합 댓글 타임라인과 결재 액션을 조립한다.
- approval 서비스/컨트롤러: 기안자 전용 삭제 API와 서버 측 삭제 가능 상태 검증을 제공한다. 문서 행 잠금 및 트랜잭션은 기존 결재 액션과 같은 일관성 경계를 따른다.
- approval Mapper: 삭제 표시 조건을 목록·요약·알림·상세·참여자·첨부/댓글 연계 경로에 반영한다. 삭제 자체는 상태/라인을 잠금 검증한 뒤 `deleted_yn`을 갱신한다.
- 공통 피드 UI: 기존 `PostDetailPanel`, `AttachmentList`, `CommentThread`의 공통 계약은 변경하지 않는다. SYSTEM 항목 렌더링은 approval 상세의 전용 읽기 전용 항목으로 구현한다.

## 오류 처리

- 접근 불가 문서의 존재 여부를 노출하지 않고 기존 tenant/문서 권한 패턴을 따른다.
- 권한 부족, 삭제 불가 상태, 이미 삭제된 문서, 동시 결재 처리 등은 성공형 fallback 없이 명시적인 API 오류와 화면 메시지로 처리한다.
- 논리 삭제와 `DELETED` 이벤트는 원자적이다. 이벤트 기록이나 표시 갱신 실패 시 일부만 성공한 응답을 만들지 않는다.
- 댓글/첨부 조회 실패는 빈 목록으로 숨기지 않고 기존 오류 및 재시도 흐름을 유지한다.

## 검증 기준

### 프런트엔드

- 공지사항과 동일한 헤더 배치, 기안자/일자, 상태 칩, 제목 아래 문서번호 및 읽기 전용 결재선이 렌더링된다.
- 작성자에게만 적합한 수정/삭제 메뉴가 표시되고, 수정 상태 조건과 삭제 확인/성공 후 목록 갱신이 적용된다.
- 별도 문서 이력 섹션이 없고 SYSTEM 이벤트와 USER 댓글이 시간순으로 표시된다. SYSTEM 항목은 수정/삭제/답글을 제공하지 않으며 USER 댓글 스레드/첨부는 유지된다.
- 문서 첨부 및 댓글 첨부가 공지사항 공통 컴포넌트와 같은 모양·다운로드 흐름을 사용한다.
- 좋아요/북마크는 프런트엔드 내 임시 상호작용만 가지며 approval API 호출을 발생시키지 않는다. 핀은 시각 요소만 가진다.
- 관련 Vitest와 production build를 실행한다.

### 백엔드/DB

- `DRAFT`는 기안자만 삭제되고, 승인 후 `PENDING`은 기안자 자동 승인만 있고 다른 결재자의 action이 없는 경우에만 삭제된다.
- 타 사용자/tenant/결재 참여자의 삭제, 이미 처리된 결재 문서 삭제, 이미 삭제된 문서의 반복 요청은 차단된다.
- 문서 잠금으로 삭제와 결재 처리 경쟁에서 한 요청만 유효하게 진행된다.
- 삭제와 `DELETED` SYSTEM 이벤트가 함께 성공하거나 함께 롤백된다.
- 삭제 문서는 일반 목록·요약·알림·상세·댓글·파일·이미지 API에서 보이지 않는다. 보존 대상 데이터는 물리 삭제되지 않는다.
- 관련 Maven 서비스/Mapper/컨트롤러 테스트를 실행하고, 문서 논리 삭제 플래그와 이벤트 제약 migration을 양쪽 스키마 경로에서 대조한다.

### 브라우저

- `frontend/AGENTS.md` 기준으로 `375px`, `768px`, `1280px`에서 상세 패널, 헤더 도구, 결재선, 첨부 및 댓글 배치를 확인한다.
- UI 결과 스크린샷과 검증 명령/결과를 날짜별 결과 보고서에 기록한다.

## 범위 제외

- 좋아요/북마크/핀의 백엔드 저장, API, 재접속 후 상태 보존.
- 삭제 문서 복원 UI, 보관 기간 정책, 완전 삭제/첨부 객체 정리 작업.
- 결재선 정책, 승인 단계, 댓글 저장 구조와 기존 사용자 댓글 API 변경.
- 공지사항 상세 컴포넌트 전체의 공통화 또는 무관한 피드 화면 변경.
