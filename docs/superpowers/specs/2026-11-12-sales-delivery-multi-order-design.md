# 출하등록 다중 수주 선택 설계

## 선택한 접근

같은 거래처의 여러 수주를 하나의 출하 문서로 처리한다. 도움창은 계획 상세 단위 행과 별도 체크박스 선택 열을 유지하고, 같은 수주번호는 행 사이에서 병합하며 각 행에 계획번호를 표시한다. 계획번호는 표시 전용이다. 체크된 행에서 수주 ID를 추출해 해당 수주의 모든 검색결과 상세를 선택한다. 선택한 수주의 거래처가 다르면 하나의 헤더 거래처에 결합할 수 없으므로 도움창에 오류를 표시하고 선택을 거부한다.

## 데이터 흐름

선택된 상세행은 각각 `salesOrderId`, `salesOrderDetailId`, `salesDeliveryPlanDetailId`를 출하 폼에 보존한다. 헤더의 기존 `salesOrderId`는 첫 선택 수주를 대표값으로 유지하고, 각 상세행은 실제 원 수주 ID를 기록한다. 조회 API의 `orderNo`는 상세행에서 고유 수주번호를 모아 표시하고 현황 행은 해당 상세의 원 수주번호를 표시한다.

DB MCP에서 헤더와 상세 테이블의 현재 컬럼을 확인했다. 상세 테이블에는 이미 행별 `sales_order_id`가 있고, 현재 상세→헤더 복합 FK가 이를 헤더의 단일 수주 ID로 제한한다. 이 FK 하나를 제거하고 수주상세 및 계획상세의 tenant 복합 FK를 유지한다. rollback은 헤더와 다른 상세 수주가 있으면 실행을 거부한다.

## 대안과 판단

- 수주별 별도 출하문서를 자동 생성하는 방식은 저장 후 여러 문서의 식별/실패 부분처리 UI가 필요하므로 요청 범위를 크게 확장한다.
- 도움창만 다중 체크를 허용하는 방식은 기존 API가 나머지 수주를 저장하지 않으므로 데이터 손실을 만든다.
- 따라서 상세별 원 수주를 보존하고 한 거래처 문서로 합치는 방식을 선택한다.

## 오류 및 검증

다른 거래처, 취소/완료 수주, 수주/계획 잔량 충돌은 기존 검증 및 트랜잭션 오류로 처리한다. 수주 잠금은 ID 오름차순으로 획득해 다중 선택 간 잠금 순서를 일관되게 한다. 기존 단일 수주출하와 직출하 payload 동작을 회귀 검증한다.

## 승인

사용자가 “그렇게 해야지..여러개 출하할 수 있는거자나”라고 답해 한 출하 문서에서 여러 수주를 처리하는 방향을 승인했다. 동일 거래처 제한은 기존 단일 헤더 거래처 제약을 보존하기 위한 구현 규칙이다.
