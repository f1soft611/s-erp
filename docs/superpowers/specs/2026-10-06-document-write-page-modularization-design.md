# 문서 작성 페이지 소스 분리 설계

## 목적

913줄로 커진 문서 작성 페이지의 화면, 상태, 작성 모달, 타입, 샘플 데이터를 책임에 따라 분리한다. 기안양식관리 페이지의 기능별 디렉터리 구조와 공지사항 페이지의 페이지 조립 및 모달 컴포넌트 패턴을 따른다.

이번 작업은 문서 작성 기능을 확장하는 것이 아니라 다음 단계의 기능 구현을 위한 구조 정리다. 기존 화면과 동작은 유지한다.

## 현재 구조와 확인 근거

- `DocumentWritePage.tsx` 한 파일이 페이지 조립, 샘플 문서와 타입, 피드 항목, 결재 요약, 빈 상태, 목록 필터/보기 상태, Tiptap 편집기, 첨부 파일, 작성 다이얼로그를 함께 소유한다.
- 페이지 테스트는 기본 리스트 보기, 피드 전환, 샘플 상태와 업무 구분, 작성 모달의 탭·제목·본문·툴바를 확인한다.
- 기안양식관리 기능은 `components`, `hooks`, `services`, `types`를 기능 폴더에 두고 페이지에서 조립한다.
- 공지사항 페이지는 목록과 작성 다이얼로그를 별도 컴포넌트로 조립하며, 작성 다이얼로그는 공용 모달 셸을 사용한다.
- 문서 작성 페이지에는 현재 서버/API 호출이 없고 저장 버튼도 비활성화되어 있다.

## 대안과 선택

### 대안 A: 역할별로 페이지 전반을 분리 (권장)

페이지는 화면 조립을 담당하고, 작성 모달·피드 항목·요약 패널·빈 상태를 각각 컴포넌트로 둔다. 페이지 목록/필터/보기 상태와 작성 편집기 상태를 훅으로 분리하며, 도메인 타입과 샘플 데이터를 별도 파일로 옮긴다. 실제 API가 없으므로 서비스 계층은 만들지 않는다.

장점은 다음 단계에서 목록 조회나 문서 저장 기능을 구현할 때 확장 위치가 명확하고, 현재 동작을 그대로 분리할 수 있다는 점이다. 단점은 파일 수가 늘어난다.

### 대안 B: 모달만 분리

작성 다이얼로그만 별도 컴포넌트로 이동하고 나머지 상태·목록·요약은 페이지에 둔다. 파일 수는 적게 늘지만 페이지의 책임이 여전히 많고, 요청한 기안양식관리·공지사항 패턴과의 일관성이 낮다.

### 대안 C: 샘플 데이터용 mock service 추가

샘플 목록을 서비스처럼 감싼다. 실제 호출 계약이나 비동기 동작이 없는 현재 구조에 불필요한 서비스 계층을 만들고, 이후 API 구현 전에 임시 계약이 고정될 위험이 있다.

### 선택

대안 A를 채택한다. 현재 존재하지 않는 데이터 서비스는 가장하지 않으며, 실제 API 연결 작업에서 서비스와 필요한 로딩/오류 흐름을 함께 추가한다.

## 승인 설계

### 디렉터리와 책임

대상은 `frontend/src/pages/groupware/documents/write/` 내부로 제한한다.

- `DocumentWritePage.tsx`: 헤더, 레이아웃, 목록·요약 컴포넌트를 연결하고 페이지 훅의 값을 전달한다.
- `components/DocumentComposerDialog.tsx`: 문서 구분 탭, 제목, 본문 편집기, 첨부 목록과 푸터 액션을 렌더링한다. 기존 `CommonDialog`를 그대로 사용하며 공용 모달 구현은 수정하지 않는다.
- `components/DocumentFeedItem.tsx`: 피드 카드와 문서 상태 칩을 렌더링한다.
- `components/ApprovalSummaryPanel.tsx`: 결재 요약과 알림을 렌더링한다.
- `components/EmptyDocumentList.tsx`: 빈 목록 안내와 작성 진입 버튼을 렌더링한다.
- `hooks/useDocumentWritePage.ts`: 목록 보기 방식, 업무 구분 필터, 작성 다이얼로그 열기/닫기 상태를 관리한다.
- `hooks/useDocumentComposer.ts`: 작성 탭, 제목, Tiptap 편집기, 툴바 표시, 첨부 파일, 취소 시 초기화 동작을 관리한다.
- `types/documentWrite.types.ts`: 문서 종류, 결재 상태, 샘플 문서 및 페이지 속성 타입을 정의한다.
- `data/documentWriteData.ts`: 현재 샘플 문서와 문서 종류 데이터를 둔다.

기존 화면에 서비스 호출이나 서버 연동은 없으므로 `services/`는 이번 변경에서 만들지 않는다. 새 서비스는 실제 API 또는 의미 있는 업무 서비스 동작이 추가될 때 정의한다.

### 데이터와 사용자 흐름

샘플 목록은 현재와 동일한 정적 데이터에서 가져온다. 페이지 훅은 업무 구분 필터를 적용하고, 고정/비고정 목록과 공용 피드·리스트 뷰 입력값을 만든다. 페이지 액션이나 빈 상태의 작성 버튼은 작성 모달을 연다. 작성 모달은 작성 훅이 가진 편집 상태를 사용하고, 취소/닫기 동작은 제목·첨부·본문·툴바를 기존처럼 초기화한다.

### 유지할 동작과 범위 제외

- 기본 리스트 보기, 피드 전환, 필터, 상단 고정 문서, 결재 요약과 샘플 데이터는 동일하게 유지한다.
- 현재 활성/비활성 문서 구분, 제목·본문 입력, 서식 툴바, 첨부 선택과 삭제를 유지한다.
- 저장 버튼은 계속 비활성화한다. 문서 생성·수정 API, 임시저장, 유효성 검증, 권한, 백엔드 연동은 추가하지 않는다.
- `CommonDialog` 및 공지사항 작성 흐름은 수정하지 않는다.
- 라우팅, 메뉴 권한, 다른 그룹웨어 페이지는 변경하지 않는다.

### 오류와 상태 처리

현재 대상 기능에는 네트워크 호출이 없으므로 새로운 로딩·오류·성공 상태를 추가하지 않는다. 편집기와 첨부 파일의 현행 초기화 및 편집 동작을 유지한다.

## 검증 기준

- 기존 `document-write-page.test.tsx`를 실행해 라우트 렌더링, 보기 방식, 필터 대상 문서, 모달 탭/입력/툴바 동작이 유지되는지 확인한다.
- TypeScript/Vite 프론트엔드 빌드를 실행한다.
- 개발 서버의 실제 브라우저에서 375px, 768px, 1280px 화면을 확인해 분리 전후 레이아웃이 유지되는지 점검한다.
- 결과 문서와 확인 스크린샷을 `docs/result/20261006/document-write-page-modularization/`에 보관한다.
