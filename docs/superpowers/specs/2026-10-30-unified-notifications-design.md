# S-ERP 공통 알림 시스템 설계

## 목표

업무 기능에서 발생하는 사용자 알림을 공통 저장·조회·읽음 처리 흐름으로 통합한다. 첫 발생원은 전자결재 문서 댓글의 `@사용자`/`@ALL` 멘션과 새 쪽지 도착이다. 공통 알림과 쪽지는 서로 다른 데이터와 읽음 상태를 갖지만, 쪽지 도착 이벤트는 공통 알림함에도 수신자별 알림으로 연결한다.

로그인 사용자는 시스템 우측 상단 알림 아이콘에서 최근 알림과 미읽음 개수를 확인하고, 알림함에서 전체 알림을 조회한다. 웹 푸시는 추후 전달 채널로 확장하며 1차 범위에서는 제공하지 않는다.

## 현재 구조와 근거

- `App.tsx`는 인증 화면을 포함한 앱 라우팅을 `NotificationProvider`로 감싼다. 현재 Provider는 성공·경고·오류 토스트를 제공하며 저장되는 알림 목록이나 읽음 상태를 관리하지 않는다.
- `DashboardPage.tsx` 우측 상단에 `aria-label="notifications"`인 알림 아이콘이 있으나 아직 알림 동작과 연결되지 않았다.
- 문서작성의 사용자 댓글과 시스템 메시지는 공통 댓글 저장소 및 기존 조회 흐름을 사용한다. 시스템 메시지는 문서 이력이며 수신자별 읽음 알림과는 별도 개념이다.
- 최근 사용 메뉴는 세션 범위의 빠른 이동 기능이다. 사용자가 지정하는 메뉴 즐겨찾기 및 전역 통합검색과 혼합하지 않는다.

## 승인된 범위와 우선순위

### 1차 범위

1. 수신자별 알림을 저장하고 미읽음 상태를 조회·변경하는 공통 알림 기능을 구현한다.
2. 공통 헤더 알림 아이콘에 미읽음 뱃지와 최근 알림 팝오버를 연결한다.
3. 더보기로 전체 알림함을 열고, 알림 선택 시 원본 문서로 이동한다.
4. 전자결재 문서 댓글에서 `@사용자`와 `@ALL` 수신자를 결정해 알림을 생성한다.
5. 1:1 쪽지 작성, 받은함/보낸함, 대화 조회, 읽음 처리 및 답장을 제공한다.
6. 새 쪽지 메시지마다 공통 알림을 생성하고 공통 알림을 쪽지 대화로 연결한다.
7. 메뉴 즐겨찾기·통합검색·웹 푸시는 별도 후속 범위로 유지한다.

### 후속 작업

- 메뉴 즐겨찾기: 사용자별 메뉴 선택 및 탐색 UX로 별도 설계한다. 최근 사용 메뉴와 구별한다.
- 전역 통합검색: 메뉴 검색 및 업무 데이터 검색을 포함하는 별도 설계로 진행한다.
- 웹 푸시: 사용자 동의, 브라우저 구독 수명주기, 권한 거부, 만료 구독 정리 및 전달 실패 처리를 정의한 뒤 별도 채널로 추가한다.

즐겨찾기와 통합검색은 같은 상단 영역을 공유할 수 있지만 저장 모델과 동작 책임은 독립적으로 둔다. 알림과 쪽지는 각각 별도의 아이콘/미읽음 표시를 제공한다.

## 설계 원칙

### 알림과 기존 토스트의 분리

- `NotificationProvider`의 성공·경고·오류 토스트는 저장 결과나 일시적인 피드백 용도로 유지한다.
- 공통 알림함은 수신자별로 지속되는 알림 레코드와 읽음 상태를 관리한다. 토스트 메시지를 알림함 항목으로 자동 복제하지 않는다.
- 문서의 SYSTEM 댓글은 업무 이력으로 유지한다. 해당 이력에서 사용자에게 알림을 보낼 필요가 있을 때만 별도의 알림 발생 정책을 통해 알림을 생성한다.

### 발생원과 수신자 상태 분리

- 업무 발생원은 공통 알림 발행 계약을 사용해 tenant, 이벤트 종류, 원본 리소스 식별자, 표시용 제목/요약, 이동 대상 및 수신자 식별자를 전달한다.
- 공통 알림 기능은 수신자별 읽음 여부와 생성 시각을 소유한다. 발생원별 업무 권한과 수신자 결정은 해당 업무의 서버 측 책임으로 둔다.
- 저장 구조는 하나의 업무 이벤트가 여러 수신자에게 전달되더라도 각 수신자의 읽음 상태가 독립적으로 유지되도록 한다. 물리 테이블·컬럼·인덱스는 구현 전에 읽기 전용 DB MCP와 기존 스키마 관리 방식을 확인해 확정한다.
- 같은 이벤트 내 수신자는 중복 제거한다. 다른 tenant 사용자, 비활성 사용자, 발신자는 해당 이벤트 알림 대상에 포함하지 않는다.
- 댓글 저장과 해당 댓글에서 발생한 알림 생성은 원자적으로 처리한다. 댓글은 저장됐지만 알림은 일부만 생성되는 상태를 허용하지 않는다. 기존 트랜잭션 경계로 원자성을 보장할 수 없다면 알림 생성 요청을 내구성 있게 기록한 뒤 처리 완료를 보장하는 방식을 구현 상세 설계에서 선택한다.
- 멘션 알림은 댓글 최초 생성 시 한 번만 발생한다. 댓글 수정으로 멘션 대상이 바뀌더라도 기존 알림을 소급 변경하거나 같은 댓글 알림을 다시 발행하지 않는다.

### 문서 댓글 멘션 수신자

- 댓글 작성 UI에서 `@` 입력 후 사용자를 선택하면 문자열 표시와 별도로 선택된 사용자 ID를 명시적으로 전달한다. 서버는 표시 이름 문자열만 분석해 수신자를 추측하지 않는다.
- `@ALL`은 해당 댓글이 작성되는 시점에 문서를 볼 권한이 있는 사용자로 확장한다. tenant 경계를 넘지 않으며 작성자 본인은 제외한다.
- 대상 문서 댓글에는 최상위 댓글과 답글을 포함한다.
- 개별 멘션과 `@ALL` 대상이 겹치는 경우 수신자는 한 번만 알림을 받는다.
- 댓글 저장과 멘션 대상 검증을 서버에서 수행한다. 문서 접근 권한이 없는 사용자가 요청에 임의 사용자 ID를 넣어 알림을 발송할 수 없어야 한다.
- 알림에는 문서 식별 정보와 댓글 요약/작성자 등 필요한 최소 정보를 담고, 문서 이동 시점에도 서버가 현재 접근 권한을 다시 확인한다. 접근 권한이 없거나 문서가 더 이상 존재하지 않으면 알림 상세 정보를 노출하지 않는다.
- 댓글 작성자가 자신을 멘션하거나 `@ALL`에 포함되는 경우 자기 자신에게 알림을 만들지 않는다.

### 쪽지함과 공통 알림 연결

- 쪽지는 업무 알림과 구별되는 사용자 작성 메시지다. 공통 알림 행에 쪽지 본문을 복제하지 않는다.
- 1차 쪽지는 동일 tenant 안의 한 명에게 보내는 1:1 메시지다. 받은함/보낸함은 대화 목록으로 제공하고, 대화 안에는 양쪽 사용자가 주고받은 메시지를 시간순으로 표시한다.
- 새 쪽지는 제목(선택)과 일반 텍스트 본문으로 구성한다. 답장은 기존 대화 참여자인 두 사용자 사이에서만 가능하다. 첨부파일, 그룹 쪽지, 전달/삭제, 임시저장, 외부 이메일 발송은 제외한다.
- 쪽지의 읽음 상태는 수신 메시지별로 관리한다. 대화 진입 시 해당 사용자가 받은 미읽음 메시지를 읽음 처리하고, 보낸함에서는 상대방의 읽음 상태를 표시한다.
- 새 메시지를 저장할 때 수신자에게 공통 `DIRECT_MESSAGE_RECEIVED` 알림을 생성한다. 쪽지와 알림 생성은 원자적으로 처리한다.
- 알림에서 쪽지를 선택하면 해당 대화로 이동한다. 알림을 열기만 한 행위는 쪽지를 읽음 처리하지 않는다. 대화에 진입해 수신 메시지를 읽음 처리할 때 연결된 새 쪽지 알림도 읽음으로 동기화한다. 공통 알림을 읽음 처리하는 것만으로 쪽지 읽음 상태가 바뀌지는 않는다.
- 새 쪽지가 기존 스레드의 답장이라도 새 메시지별 알림을 만든다. 발신자는 자기 자신에게 알림을 받지 않는다.
- 쪽지함의 unread count와 공통 알림함의 unread count는 별도로 계산하고 각각 표시한다.

## 화면 및 사용자 흐름

### 우측 상단 알림 팝오버

- 인증된 업무·프로필·보안 화면의 우측 상단에 같은 알림 아이콘과 미읽음 뱃지를 제공한다. 현재 업무 라우트는 `DashboardPage`가 공통 셸이지만 프로필/보안 라우트는 독립 페이지이므로, 알림 컨트롤을 공통 컴포넌트로 재사용해 동작을 일치시킨다. 로그인과 공개 문서 화면에는 노출하지 않는다.
- 뱃지는 미읽음 개수를 표시하고, 긴 숫자는 `99+`로 축약한다. 미읽음이 없으면 숫자 뱃지를 숨긴다.
- 아이콘을 누르면 최신 알림 최대 5건을 팝오버로 보여준다. 항목은 읽음/미읽음 상태, 발생 시각, 제목 및 요약을 구별할 수 있어야 한다.
- `더보기`는 전체 알림함으로 이동한다. 팝오버를 열기만 한 경우 알림을 읽음 처리하지 않는다.
- 팝오버의 알림 항목을 선택하면 읽음 처리를 요청하고 원본 문서로 이동한다. 읽음 요청이 실패해도 원본 이동은 막지 않고, 항목은 미읽음 상태로 남기며 사용자에게 오류를 알린다.

### 알림함

- 최신순 목록과 전체/미읽음 보기 전환을 제공한다. 목록은 페이지 단위로 조회한다.
- 알림을 선택하면 원본 화면으로 이동하고 읽음 처리를 시도한다.
- 단일 읽음 처리 외의 일괄 읽음, 삭제, 보관/숨김, 알림 설정 화면은 1차 범위에서 제외한다.
- 1차 버전에서는 알림을 자동 만료하거나 사용자 삭제하지 않는다. 보존 기간과 정리 정책은 저장량 및 운영 요구를 확인한 후 별도 설계한다.
- 로딩, 빈 목록, 조회 오류 및 재시도 상태를 구분한다. API 오류를 빈 목록이나 읽음 상태로 대체하지 않는다.

### 쪽지함

- 인증된 업무 화면의 헤더에 쪽지함 아이콘과 받은 미읽음 쪽지 개수를 표시한다. 아이콘은 받은함으로 이동한다.
- 받은함/보낸함 전환, 최근 대화 목록, 대화 상세, 새 쪽지 작성 및 답장 입력을 제공한다.
- 미읽음 대화는 시각적으로 구분하고 최신 메시지 시각 및 상대 사용자명을 표시한다. 대화 진입은 서버에서 읽음 처리한 결과를 기준으로 상태와 개수를 갱신한다.
- 쪽지 본문은 일반 텍스트로 렌더링해 HTML을 실행하지 않는다. 선택적 제목은 최대 120자, 본문은 최대 5,000자로 제한하며 서버에서 검증한다.
- 대화 오류, 조회 실패, 빈 상태 및 발송 실패는 명시적으로 표시하고 재시도 가능하게 한다. 발송 실패를 성공 토스트/화면으로 처리하지 않는다.
- 공개 사용자 선택 목록은 기존 tenant 사용자 옵션 조회를 재사용하되, 발신 대상은 활성 로그인 계정이 연결된 활성 사용자로 제한한다.

### 상태 갱신

- 인증된 앱 시작 및 브라우저 탭이 다시 활성화될 때 미읽음 개수를 갱신한다.
- 팝오버를 열 때 미읽음 개수와 최근 목록을 다시 조회하고, 읽음 처리 후에는 해당 항목과 뱃지를 갱신한다.
- 1차 버전에는 WebSocket, Server-Sent Events, 웹 푸시를 사용하지 않는다. 실시간 전달은 별도 요구와 운영 기준을 확인한 뒤 추가한다.

## API 및 권한 경계

구체적인 URL, DTO 필드명, 페이지 크기, 인증 방식은 기존 컨트롤러·서비스·Mapper 패턴 및 DB MCP 확인 후 구현 계획과 상세 사양에서 확정한다. 필요한 계약은 다음 책임을 포함한다.

| 계약 | 책임 |
|---|---|
| 미읽음 요약 조회 | 인증 사용자·tenant 범위의 미읽음 개수 반환 |
| 알림 목록 조회 | 인증 사용자의 최신순 페이지 조회, 필요 시 미읽음 필터 적용 |
| 읽음 처리 | 현재 사용자의 알림만 읽음으로 전환하고 반복 요청에도 안전하게 동작 |
| 공통 알림 발행 | 업무 서버가 검증한 발생원 정보와 수신자 집합을 받아 수신자별 알림 생성 |
| 문서 댓글 저장 | 댓글 및 멘션 ID 검증, 문서 접근 확인, 중복 제거된 대상에 알림 생성 |
| 쪽지 작성/답장 | 현재 사용자의 tenant 및 대화 참여자를 검증하고 메시지와 수신자 알림을 함께 저장 |
| 쪽지함/대화 조회 | 현재 사용자가 참여자인 대화와 메시지만 반환하고 대화 진입 시 받은 미읽음 메시지를 처리 |

- 모든 읽기·변경 API는 요청 본문에서 받은 사용자 ID를 신뢰하지 않고 인증 principal과 tenant로 범위를 정한다.
- 다른 사용자의 알림 ID를 지정한 읽음 요청은 성공 처리하지 않는다.
- 쪽지의 송신자/수신자는 요청 본문으로 받되 서버가 현재 tenant의 활성 사용자 및 대화 참여자 여부를 검증한다. 응답이나 목록은 현재 사용자가 참여자인 대화만 반환한다.
- 원본 이동 경로는 서버가 허용한 리소스 종류/식별자 조합으로 만들며, 임의 외부 URL을 실행하지 않는다.
- 알림 목록과 요약의 실패는 공통 오류 피드백을 사용하고, 성공 모양의 기본값으로 숨기지 않는다.
- 알림 요약·목록·읽음 처리에서 tenant 격리와 인증 사용자 격리를 테스트한다.

## 대안과 선택

1. **수신자별 공통 알림 저장소와 업무 발행 계약 — 선택.** 읽음 상태와 뱃지를 일관되게 제공하고 새 업무 발생원을 추가하기 쉽다. 초기 DB/API 변경과 각 발생원의 수신자 검증은 필요하다.
2. **헤더가 업무별 API를 직접 집계.** 첫 화면은 빠르게 구성할 수 있지만 업무별 읽음 규칙, 오류, 뱃지 의미가 달라지고 전체 알림함이 업무 API 집계기에 종속된다.
3. **실시간 이벤트·웹 푸시까지 처음부터 구현.** 즉시 전달을 지원하지만 연결, 브라우저 권한/구독, 재시도와 운영 복잡도가 커진다. 현재 1차 요구를 넘어선다.

## 오류·보안·운영 고려사항

- 알림 본문에는 권한 없는 사용자가 내용을 추측할 수 있는 민감 데이터를 복제하지 않는다. 요약 정보 노출도 원본 리소스 접근권한과 함께 검토한다.
- 원본 리소스 접근권한은 알림 생성 시 수신자를 제한하고, 이동/상세 표시 시 다시 검사한다.
- 수신자 확장 및 알림 목록 조회에는 tenant, 페이지 크기, 알림 유형 등 서버 측 제한을 둔다. 대규모 `@ALL` 처리는 수신자 fan-out 성능과 트랜잭션 크기를 측정하고, 원자성을 보존하는 대량 처리 방식을 구현 사양에서 정한다.
- 재시도에도 같은 댓글·알림 유형·수신자 조합으로 중복 알림이 생기지 않도록 발행 식별 기준을 둔다.
- 사용자의 미읽음 건수는 서버 저장 상태를 기준으로 하며 클라이언트 캐시만으로 읽음 여부를 확정하지 않는다.
- 웹 푸시 추가 시 인앱 알림 저장/읽음 상태를 대체하지 않고, 같은 알림을 전달하는 선택적 채널로 둔다.

## 검증 기준

- 서로 다른 발생원이 같은 공통 계약으로 수신자별 알림을 생성할 수 있고, 한 알림의 읽음 처리가 다른 수신자 상태에 영향을 주지 않는다.
- `@사용자`, `@ALL`, 개별 멘션과 전체 대상의 중복, 작성자 자기 알림 제외가 서버 검증 기준과 일치한다.
- `@ALL`은 문서 접근 권한이 있는 현재 tenant 사용자만 대상으로 하며, 권한 없는 수신자나 임의 사용자 ID는 거부된다.
- 미읽음 요약·목록·읽음 API는 사용자/tenant 경계를 지키고 반복 읽음 요청에 안전하다.
- 알림 팝오버에는 최신 5건이 나타나고, 열기만으로는 읽음 처리되지 않으며 선택 후 문서 이동과 상태 갱신이 동작한다.
- 알림함의 전체/미읽음 목록, 페이지 전환, 빈 상태, 로딩, 오류 및 재시도 흐름이 검증된다.
- 토스트 메시지, 공통 댓글 SYSTEM 이력 및 기존 최근 사용 메뉴의 의미와 동작이 바뀌지 않는다.
- 알림을 읽어도 쪽지 메시지 읽음 상태가 자동 변경되지 않으며, 쪽지 대화를 열어 수신 메시지를 읽으면 관련 새 쪽지 알림도 읽음 처리된다.
- 보낸함/받은함 대화 목록과 쪽지 상세는 대화 참여자만 조회할 수 있고, 보낸 메시지의 상대 읽음 상태가 수신자 읽음 처리 결과와 일치한다.
- 프런트엔드 화면은 실제 브라우저에서 375px, 768px, 1280px 뷰포트로 확인한다. 백엔드/API 테스트, 프런트엔드 테스트와 빌드 결과는 작업 결과 문서에 남긴다.
- DB 스키마 변경이 확정되면 DB MCP 확인과 날짜별 SQL·변경 이력·롤백 기록을 완료한다. 이 설계 단계에서는 DB를 조회하거나 변경하지 않는다.
