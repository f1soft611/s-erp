# 전자결재 공통 알림 확장 설계

## 목표

전자결재의 처리 대기와 결과 상태를 기존 사용자별 공통 알림함 및 Web Push에 전달한다. 알림 발생원은 결재 시스템 이력 댓글이며 대상은 문서 ID이므로, 같은 문서의 반복 재상신도 각기 다른 알림 이벤트로 보존할 수 있다.

## 현황

- `NotificationServiceImpl`은 멘션과 쪽지 두 이벤트/발생원 쌍만 허용한다.
- 알림 API 응답의 `targetId`는 멘션 댓글의 문서 ID만 조회한다.
- 전자결재 `submit`과 `processAction`은 상태 변경과 시스템 이력을 같은 트랜잭션에서 기록한다.
- 현재 DB 컬럼은 공통 알림 및 결재선을 지원한다. 저장소 DDL의 `chk_notification_event_source`는 두 기존 쌍만 허용하므로 신규 조합용 migration이 필요하다.
- MCP `list_tables`/`describe_table`은 성공했으나 CHECK 제약 조회는 실패했다. 라이브 제약 확인이 완료되지 않은 상태이므로 저장소 DDL을 대체 근거로 사용하고 결과에 미확인 범위를 기록한다.

## 대안과 선택

1. **결재 이력 ID를 발생원으로 사용하는 공통 알림 — 선택.** 기존 notification uniqueness를 이용해 재상신마다 별도 이벤트를 보존하고, `owner_id`를 통해 문서 상세로 이동한다. 이벤트/발생원 조합을 DB 및 프런트엔드 허용 목록에 추가해야 한다.
2. **문서 ID를 직접 발생원으로 사용.** 스키마 변경은 적지만 `(event_type, source_type, source_id, recipient)` 중복 방지 키 때문에 같은 문서의 재상신을 새 알림으로 만들기 어렵다.
3. **결재 화면별 독립 배지/알림 API.** 기존 공통 알림과 읽음/푸시/필터 정책이 분리되어 사용자가 알림을 놓칠 수 있으므로 제외한다.

## 데이터 흐름

1. 결재 서비스가 기존 트랜잭션 안에서 상태 전이 및 시스템 이력을 저장한다.
2. 시스템 이력 ID와 이벤트 요약을 공통 `NotificationService.createEvent`에 넘긴다.
3. 공통 알림 서비스가 tenant, 수신 사용자, 이벤트/발생원 조합을 검증하고 알림 레코드를 저장한다.
4. 저장 성공 시 기존 Web Push outbox와 realtime notification 신호를 발행한다.
5. 프런트엔드는 `APPROVAL_STATUS_EVENT` 원본을 기존 알림함에서 표시하고 문서 상세로 이동한다.

## 이벤트 및 수신자

공통 알림 유형은 `APPROVAL_WORKFLOW`, 원본 유형은 `APPROVAL_STATUS_EVENT`로 통합한다. 제목은 행위별로 “결재 요청”, “최종 승인”, “반려”, “보완 요청”, “최종 확인 요청”, “업무연락 도착” 등을 사용하고, 요약에는 문서 제목 등 최소 정보만 표시한다.

- 상신/재상신: 현재 `PENDING` 결재선의 승인/합의자
- 단계 전환: 방금 활성화되어 `PENDING`이 된 다음 단계 승인/합의자
- 최종 승인: 기안자. 단, 기안자 최종확인 대기 상태면 “최종 확인 요청”으로 알림
- 반려/보완요청: 기안자
- 업무연락 전송: 해당 문서의 참조자
- 행위자가 수신자에 포함되면 제외한다. 알림 생성 시 사용자 ID는 요청 payload가 아니라 인증 principal 및 저장 결재선에서 결정한다.
- 중간 승인 동작은 같은 단계의 다른 결재 대기자가 남아 있으면 별도 알림을 생성하지 않는다.

시스템 이력의 `comment_id`를 notification `source_id`로 사용하고 `owner_id`를 `target_id`로 조회한다. 이 방식은 문서 한 건에서 반복되는 재상신/상태 변경을 서로 다른 source ID로 구분하며 기존 unique key와 맞는다.

## 실패·권한 정책

- 시스템 이력, 결재 상태 변경 및 인앱 알림 저장은 기존 결재 트랜잭션 경계 안에 둔다. 핵심 인앱 알림 저장이 실패하면 해당 업무 트랜잭션도 실패한다.
- Web Push는 이미 저장된 알림의 추가 전달 채널이다. 푸시 전송 실패는 인앱 알림/결재 처리에 영향을 주지 않는다.
- 사용자/tenant 범위는 저장된 결재선과 인증 principal로 정하고, 접근권한 없는 문서는 알림 경로에서 열리지 않게 기존 문서 권한 검증을 재사용한다.
- 저장소 DDL의 CHECK 제약, 서버 allowlist, 프런트엔드 event/source validation은 같은 단일 신규 조합을 지원해야 한다.

## 메일 알림 검토

메일은 이번 구현의 일부가 아니다. 저장소에 Spring Mail 의존성과 SMTP 프로파일 설정은 있으나 실제 발신 서비스는 확인되지 않았다. 따라서 “메일 알림이 이미 동작한다”고 볼 수 없다.

후속 이메일 대체는 다음 조건을 권장한다.

- 받는 사람: 해당 결재 이벤트의 정당한 알림 수신자 본인, 유효/검증된 이메일 주소이며 명시적으로 이메일 알림에 동의한 사용자
- 보내는 사람: 시스템 no-reply 발신 주소. 결재 행위자의 주소로 가장하지 않는다.
- 발송 조건: 중요한 결재 이벤트에 한해 푸시가 전체 기기에서 최종 실패하거나 활성 기기가 없는 경우
- 발송하지 않는 경우: 인앱 알림 저장 실패(업무 트랜잭션에서 rollback), 단순히 알림이 미읽음인 경우, 일반 저장 성공 메시지
- 메일 자체 실패: 별도 durable outbox에서 제한 재시도 및 운영 모니터링. 업무 트랜잭션은 rollback하지 않는다.
- 후속 구현 전 이메일 주소 검증/동의 설정, SMTP secret 외부 주입, 이메일별 중복 키, 재시도 상한, 메일 본문 최소화 및 보안 URL 정책을 별도 설계한다.

현재 프로필 화면의 이메일 주소 편집은 확인되었지만 별도 이메일 수신 동의 또는 발신 서비스는 확인되지 않았다. SMTP 설정의 자격정보 기본값은 운영 전 secret 관리로 이전하고 안전하지 않은 기본값을 제거해야 한다.

## 범위 제외

- Email 발송 코드/설정/DB outbox 추가
- 결재 외 ERP 모듈 알림, 이메일 미읽음 리마인더, 모든 결재자별 중간 상태 알림
- Web Push 프로토콜이나 기존 outbox 구조 변경

## 검증

- 서버 서비스 테스트: 이벤트별 수신자, 재상신 구별, 자기 알림 제외, 트랜잭션 실패 시 발행 억제
- MyBatis 계약 테스트: status-event source를 통해 전자결재 문서 ID가 `targetId`로 반환됨
- 프런트 테스트: 알림 응답 validation, 유형 필터/아이콘, 문서 상세 이동
- migration은 실행하지 않고 양쪽 날짜별 사본 및 `db-schema.md`를 검토한다.
- 브라우저에서 승인자 수신, 기안자 결과 수신, 알림 이동 및 반응형을 확인한다.
