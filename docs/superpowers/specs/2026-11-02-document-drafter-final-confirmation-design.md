# 기안자 최종확인 결재선 설계

## 목표

최종 승인 또는 반려된 문서를 기안자가 별도로 확인할 수 있게 한다. 확인 여부는 문서의 최종 상태와 분리해 기록한다. 결재선 작성 화면에는 최종확인 단계를 노출하지 않고, 서버가 상신 시 내부 최종확인 결재선 행을 생성한다.

## 현재 구조와 근거

- 문서 상태는 일반 결재 처리의 최종 결과를 나타낸다. 현재 최종 승인 시 `COMPLETED`, 반려 시 `REJECTED`, 보완요청 시 `REVISION_REQUESTED`로 전환한다.
- 최종 승인 처리 코드는 승인자의 `APPROVED` 시스템 이력과 별도로 `COMPLETED` 시스템 이력을 생성한다.
- 기존 `REFERENCE` 참여자는 일반 승인 처리 대상이 아니며, 확인 시 `action_status=CONFIRMED`와 `action_at`을 결재선 행에 기록한다. 확인은 문서 상태를 변경하지 않는다.
- 현재 상세 결재선은 `APPROVAL`, `AGREEMENT`, `REFERENCE` 유형을 순서대로 표시한다. 결재선 생성 시 기안자는 첫 단계의 고정 승인자로 저장된다.
- 이 설계는 기존 사양서, Mapper 및 서비스 코드를 바탕으로 작성한다. PostgreSQL의 현재 CHECK 제약 메타데이터는 이 설계 작성 중 MCP로 재확인하지 않았다. 구현 전 `s-erp-postgresql-readonly` MCP로 관련 테이블과 제약을 조회해야 한다.

## 확정된 동작

### 최종 상태와 확인의 분리

| 처리 | 처리 직후 문서 상태 | 기안자 최종확인 |
|---|---|---|
| 마지막 결재/합의 단계 승인 완료 | `COMPLETED` | 확인 대기 |
| 결재선의 반려 | `REJECTED` | 확인 대기 |
| 보완요청 | `REVISION_REQUESTED` | 확인 대상 아님 |
| 기안자 최종확인 | 기존 상태 유지 | 확인 완료 |

- 최종 승인 시 문서는 즉시 완료 상태가 된다. 기안자 확인은 완료 처리를 지연시키지 않는다.
- 반려 문서는 즉시 반려 상태가 된다. 기안자 확인은 반려를 승인이나 완료로 바꾸지 않는다.
- 어느 결재 단계에서 반려되더라도 해당 결재 처리는 종결 결과다. 기안자 확인 대상을 활성화한다.
- 보완요청은 종결 결과가 아니므로 확인 대상을 활성화하지 않는다. 보완 후 재상신한 문서는 그 회차의 최종 승인 또는 반려 시 확인 대상으로 만든다.
- 확인은 기안자만 1회 수행한다. 확인 처리로 문서 상태나 결재 상태를 변경하지 않는다.

### 내부 최종확인 결재선

- 사용자가 결재선을 저장하거나 편집할 때 최종확인 참여자를 요청하지 않는다.
- 최초 상신 및 보완요청 후 재상신의 서버 트랜잭션에서 기안자용 `FINAL_CONFIRMATION` 참여 행을 자동 생성한다.
- 자동 생성 행은 상신 요청에 포함된 사용자 결재선 및 참조자 행의 최대 `stage_order` 다음 순번에 둔다. 예를 들어 사용자 결재 단계가 5개이고 참조자가 없다면 최종확인 행은 6단계다. 참조자 행이 있으면 그 순번과 충돌하지 않도록 다음 순번을 사용한다. 이 순번은 표시/추적용이며 일반 결재 단계 활성화에는 참여하지 않는다.
- 생성 시 `action_status=WAITING`으로 둔다. 이 행은 일반 승인 단계 탐색 및 활성화 대상이 아니다.
- 최종 승인 또는 반려가 성공하면 해당 행만 `PENDING`으로 활성화한다. 활성화 시각은 `pending_at`에 기록한다. 문서 상태 갱신과 확인 행 활성화는 같은 트랜잭션에서 처리한다.
- 보완요청은 이 행을 활성화하지 않는다.
- 재상신 시 새 결재 회차의 사용자 결재선과 최종확인 행을 생성/초기화한다. 과거 회차의 시스템 이벤트는 기존 append-only 규칙에 따라 보존한다.
- `FINAL_CONFIRMATION`은 `REFERENCE`와 별도 참여 유형이다. 일반 참조자 대기 건수/목록에 포함하지 않는다.
- 일반 결재선 UI에는 이 내부 행을 렌더링하지 않는다. 기안자의 최종확인 전용 대기 목록과 문서 상세의 확인 동작으로만 노출한다.

## 확인 처리 및 시스템 이력

- 확인 API는 기존 문서확인 패턴을 따르되 `FINAL_CONFIRMATION`만을 대상으로 하는 별도 경로 또는 명시적으로 구분되는 요청 경로를 사용한다. 기존 참조확인 API의 권한 조건을 완화해 공유하지 않는다.
- 서버는 인증 사용자, tenant, 문서 상태(`COMPLETED` 또는 `REJECTED`), 내부 최종확인 행의 기안자 일치 여부, `PENDING` 상태를 검증한다. 클라이언트가 참여자 ID나 확인 시각을 전달하지 않는다.
- 성공 시 확인 행을 `CONFIRMED`로 바꾸고 `action_at`을 기록한다. `action_comment`는 비워 두며, `pending_at`은 확인 대기 시작 시각으로 보존한다.
- 동일 기안자의 중복 확인 요청은 성공 상태를 반환할 수 있지만 확인 이력을 중복 추가하지 않는다.
- 확인 상태 변경 및 SYSTEM 이력 추가는 한 트랜잭션이다. 이력 추가가 실패하면 확인 상태 변경도 롤백한다.
- 신규 확인 이벤트 코드는 `FINAL_CONFIRMATION_CONFIRMED`로 구분한다. 표시 문구는 **`기안자가 최종 확인을 완료했습니다.`**로 한다.
- 최종 승인 시 생성하던 추가 `COMPLETED` SYSTEM 이벤트는 신규 처리부터 생성하지 않는다. 승인자의 `APPROVED` 이벤트 및 문서 상태 `COMPLETED` 전환은 유지한다. `COMPLETED` 이벤트 허용 제약과 과거 이력은 하위 호환 및 append-only 원칙을 위해 유지한다.
- 반려자의 `REJECTED` 이벤트는 유지한다. 기안자가 확인한 뒤에도 `REJECTED` 상태와 반려 이력은 그대로 남는다.

## 조회 및 화면

### 전용 최종확인 대기 목록

- 문서작성 및 종합현황에 일반 참조확인과 구별되는 `내가 최종 확인할 문서` 항목을 제공한다.
- 신규 목록 범위는 `MY_FINAL_CONFIRMATION_PENDING`으로 분리한다. 현재 사용자와 tenant에 속하고 `FINAL_CONFIRMATION` 행이 `PENDING`인 문서만 반환한다.
- `COMPLETED`와 `REJECTED` 모두 최종확인 대기 목록에 포함한다. `DRAFT`, `PENDING`, `IN_PROGRESS`, `REVISION_REQUESTED`는 포함하지 않는다.
- 요약 건수와 목록은 기존 `MY_REFERENCE_PENDING` 및 참조확인 건수와 분리한다. 일반 결재 대기 건수에도 포함하지 않는다.
- 목록 선택 시 기존 문서 상세를 열며, 현재 기안자에게만 `최종확인` 액션을 표시한다. 확인 성공 후 목록/건수와 상세 이력을 새로고침한다.
- 기존 `REFERENCE` 확인 UX·목록 패턴은 재사용하되, 라벨, 범위, 참여 유형, 권한 검증, 확인 이벤트는 독립적으로 유지한다.
- “보내기”는 애플리케이션 내 전용 대기 목록 제공을 뜻한다. 이메일/푸시 등 외부 알림은 이번 범위에 포함하지 않는다.

### 상세 결재선 표시

- `FINAL_CONFIRMATION` 행은 통상적인 결재선 표시에서 숨긴다. 사용자가 편집한 승인·합의·참조 라인의 순서와 표현을 바꾸지 않는다.
- 문서 상세의 시스템 타임라인에는 확인 완료 이벤트를 표시한다.
- 기안자는 최종확인 대기 항목에서 문서를 열고 확인할 수 있다. 확인 완료 후에는 같은 액션을 다시 제공하지 않는다.

## 데이터 및 무결성

- 신규 테이블은 추가하지 않는다. 기존 `tb_electronic_approval_line_info`에 `FINAL_CONFIRMATION` 유형의 내부 참여 행을 저장한다.
- 기존 결재선 CHECK 제약을 확장해 `FINAL_CONFIRMATION` 행에 허용되는 상태를 명시한다.
  - `WAITING`: `pending_at`, `action_at`, `action_comment` 모두 NULL
  - `PENDING`: `pending_at` NOT NULL, `action_at`, `action_comment` NULL
  - `CONFIRMED`: `pending_at`, `action_at` NOT NULL, `action_comment` NULL
- `FINAL_CONFIRMATION` 행은 문서별 한 행이며 참여자는 문서의 기안자다. 서버 생성으로만 허용하고 클라이언트가 행을 삽입·수정·삭제할 수 없어야 한다.
- `tb_common_comment` SYSTEM 이벤트 CHECK에 `FINAL_CONFIRMATION_CONFIRMED`를 추가한다. 기존 SYSTEM 이벤트와 USER 이벤트의 `event_type IS NULL` 규칙을 보존한다.
- 날짜별 SQL, 변경 이력, 롤백 SQL을 `backend/DATABASE/YYYYMMDD`와 `docs/database/YYYYMMDD`에 같은 번호·내용으로 생성하고 `docs/database/db-schema.md`를 갱신한다. rollback은 새 유형/이벤트를 사용하는 기존 행이 있을 때 데이터 삭제 없이 중단하도록 가드한다.
- 구현 직전 PostgreSQL MCP에서 결재선·댓글 테이블의 실제 컬럼, CHECK 및 현재 적용 상태를 확인한다. 확인하지 못하면 그 사실과 Mapper/날짜별 스키마 이력 등 대체 근거를 결과 문서에 구분해 남긴다.

## 대안과 선택

1. **결재선의 마지막 단계 뒤에 내부 최종확인 행을 자동 생성한다 — 선택.** 기존 순번·참여자 저장 구조와 확인 처리 방식을 활용하면서 `FINAL_CONFIRMATION` 유형으로 참조 및 일반 결재와 구분한다. 일반 결재선 조회/전이에서 이를 제외하는 조건이 필요하다.
2. 별도 최종확인 테이블을 만든다. 승인 결재선과의 결합은 줄지만 확인 상태 조회, 사용자 요약, 문서 상세/타임라인 통합을 위한 별도 저장·조회 경로가 생긴다.
3. 마지막 결재 이벤트만으로 기안자의 확인 상태를 추론한다. 확인 대기 목록과 멱등 처리를 안정적으로 제공하기 어렵고, 참여자별 상태를 나타내지 못하므로 채택하지 않는다.

## 오류 및 권한 경계

- 타 사용자/타 tenant, 문서 기안자가 아닌 사용자, 최종 상태가 아닌 문서, `PENDING`이 아닌 확인 행은 확인할 수 없다.
- 최종확인 행은 일반 결재 액션, 참조확인, 결재 단계 활성화 쿼리의 대상에서 제외한다.
- 문서 상태 변경, 확인 행 갱신 또는 SYSTEM 이력 저장 중 하나라도 실패하면 트랜잭션 전체를 롤백한다.
- 목록/요약 실패는 0건 성공으로 변환하지 않는다. UI에서 기존 오류 및 재시도 패턴을 사용한다.

## 범위 제외

- 사용자 결재선 편집기에 최종확인 참여자를 표시하거나 선택·삭제하게 하는 것
- 최종확인으로 문서 상태 또는 결재 결과를 변경하는 것
- 보완요청 직후 기안자 확인을 요구하는 것
- 확인 취소, 확인 의견 입력, 대리 확인
- 이메일, 푸시 등 외부 알림
- 과거 문서 및 과거 `COMPLETED` 시스템 이력의 데이터 정리/삭제
- 별도 최종확인 이력 테이블 추가

## 검증 기준

- 상신 요청 payload에 최종확인 행이 없어도 서버가 기안자 대상 `WAITING` 행을 정확히 한 건 생성한다.
- 사용자 편집 결재선 및 참조자의 stage/participant 순서는 보존되고 일반 결재선 UI에는 최종확인 행이 표시되지 않는다.
- 마지막 단계 승인 시 문서가 `COMPLETED`가 되고 기안자 최종확인 행만 `PENDING`이 된다. 새 `COMPLETED` SYSTEM 이벤트는 추가되지 않고 최종 승인자의 `APPROVED` 이벤트는 보존된다.
- 승인과 무관한 단계의 반려 시 문서가 `REJECTED`가 되고 최종확인 행이 `PENDING`이 된다. 반려 SYSTEM 이벤트가 유지된다.
- 보완요청은 `REVISION_REQUESTED`이며 최종확인 행이 대기 중으로 노출되지 않는다. 재상신 후 최종 승인/반려 결과에 대해 새 최종확인 행이 활성화된다.
- 기안자 확인 후 승인 문서는 계속 `COMPLETED`, 반려 문서는 계속 `REJECTED`다. `FINAL_CONFIRMATION_CONFIRMED` 이력은 한 번만 추가된다.
- 비기안자, 다른 tenant, 비최종 상태, 비활성/미대기 확인 행의 요청은 거부되며 타 문서 존재 여부를 노출하지 않는다.
- 확인 행 업데이트와 이력 삽입은 원자적이며 이력 삽입 실패 시 두 변경 모두 롤백된다.
- `MY_FINAL_CONFIRMATION_PENDING` 목록/요약은 참조확인과 일반 결재 대기 건수에 섞이지 않고, 완료/반려의 대기 문서를 각각 반환한다.
- 기존 참조확인, 일반 승인·반려·보완, 재상신, 상세 타임라인 및 알림/요약 동작에 회귀가 없다.
- 날짜별 migration 두 사본 및 누적 스키마가 일치하며 최소 관련 백엔드 테스트, 프런트엔드 테스트/build, 지원되는 실제 브라우저 뷰포트 검증을 통과한다.
