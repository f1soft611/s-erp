# 20261013_001 공지사항·전자결재 피드 UI 공통화 구현 계획

## 목표 및 설계

공지사항을 시각 기준으로 삼아 좌측 피드 카드와 우측 상세 패널의 공통 표현을 구성요소화한다. 기존 `FeedView`, `PostDetailPanel`, `AttachmentList`, `CommentThread`를 우선 재사용·확장하고, 누락된 카드·반응·댓글 섹션만 추출한다. 공지사항과 전자결재의 API, 상태, 권한, 데이터 정규화는 기능별 컴포넌트/훅에 남긴다.

## 위험 및 완화

- `NoticeFeedList`는 매우 큰 컴포넌트이며 확장/페이지네이션 상태가 결합되어 있다. UI chrome만 추출하고 state machine/API 코드는 이동하지 않는다.
- Notice와 approval의 댓글 cursor 및 권한 계약은 다르다. 공통 컴포넌트는 presentational props/callbacks만 받고 feature adapter가 정책을 유지한다.
- 공유 카드의 클릭 가능 semantics는 버튼 또는 article에 올바르게 반영하여 키보드 동작과 nested controls를 보존한다.
- 반응 상태의 영속화/서버 계약은 변경하지 않는다.
- 첫 댓글 페이지를 작은 batch로 조정하되 service의 cursor, `hasPrevious`, 댓글 count 응답 계약은 변경하지 않는다.
- 공지사항 본문 컴포넌트 추출은 presentation only로 제한해 기존 API, sanitization, image hydration, interaction/state 흐름을 바꾸지 않는다.

## Task 5 — 상세 패널 UI 통일 후속 조정

이 단계는 기존 공통화 작업에 대한 2026-10-13 승인 후속 변경이며, 기존 API/권한/댓글 계약과 좌측 목록 동작을 보존한다.

### 변경 범위

- `PostDetailPanel`: 선택 상세 로딩 중 기존 콘텐츠 viewport 전체를 접근 가능한 상태 표시와 중앙 스피너로 교체한다.
- `useNoticeInteractions`: 선택된 공지의 상세 fetch 진행 여부를 선택 ID 기준으로 노출한다. 동일 공지에 이미 진행 중인 상세 요청이 있으면 그 요청을 공유하고, 오래된 요청의 종료가 새 선택의 로딩 상태를 지우지 않게 한다.
- `CommunityNoticePage`: 공지 상세 로딩 상태를 공통 패널에 연결한다.
- `DocumentApprovalDetailFeed`: 기존 상세 요청 상태를 공통 패널로 전달하고 상세를 열 때 본문 펼침 상태를 초기화한다.
- `TiptapCommentThread`: SYSTEM 텍스트 배지를 접근 가능한 아이콘으로 교체하며, 정상/삭제 USER 댓글의 답글 토글 모두에 접힘/펼침 아이콘과 `aria-expanded`를 제공한다.
- 공지사항 상세와 좌측 피드 카드, 전자결재 상세의 separator를 조정한다. 이전 댓글 앞 separator는 모두 제거하고, 전자결재 본문 직후 separator를 제거한다. 공지는 첨부가 없을 때에만 본문-반응 separator를 제거한다. 첨부-반응 및 결재선 구분선은 유지한다.
- 좌측 공지 피드 카드에도 반응-댓글 separator 제거를 적용한다. 첨부가 없을 때 본문-반응 separator를 제거하고, 첨부가 있으면 첨부-반응 separator를 유지한다. 좌측 목록 본문은 접힘 상태를 유지한다.
- `DocumentWritePage`의 좌측 로딩은 현재 view mode에 맞춰 `FeedViewSkeleton` 또는 `ListViewSkeleton`을 사용한다. 공지사항 skeleton은 변경하지 않는다.

### TDD 및 작업 순서

1. 날짜별 작업지시서·계획서·상세사양서에 본 후속 변경과 완료 기준을 먼저 반영한다.
2. 공통 패널 로딩 테스트, 공지/전자결재의 대기 중 상세 요청 테스트를 추가하고 실패를 확인한다. 테스트는 accessible `status`, 자식 콘텐츠의 대체, `post-detail-panel-content`의 양축 중앙 정렬을 검증한다.
3. 선택 상세의 기본 펼침 테스트를 추가하고, 공지의 선택 상세는 펼쳐지면서 좌측 카드 기본 접힘이 유지되는지 확인한다.
4. SYSTEM 아이콘/읽기 전용 및 답글 접힘·펼침 아이콘/`aria-expanded` 회귀 테스트를 추가하고 실패를 확인한다.
5. separator 테스트를 추가한다. 승인 상세는 본문 직후 구분선을 제거하고, 공지 피드 카드 및 상세는 본문/첨부 콘텐츠 뒤 반응 영역 앞 구분선을 제거한다. 두 기능 모두 반응 영역과 이전 댓글 사이 구분선을 제거하며, 결재선과 첨부/반응 separator는 유지한다.
6. 위 테스트를 먼저 통과시킨 뒤 최소한의 공통 패널, 기능 연결, 댓글 아이콘 및 상세 separator 변경을 구현한다.
7. 문서 목록 로딩 테스트를 추가한다. notice와 동일하게 feed mode는 `FeedViewSkeleton`, list mode는 `ListViewSkeleton`을 사용하도록 하고 view switch에 따라 변경되는지 확인한다.
8. `feed-components`, `notice-page`, `document-write-page` 관련 테스트와 `npm run build`를 실행하고, 375px/768px/1280px 브라우저 확인 및 결과 보고/스크린샷을 남긴다.
9. 후속 간격 조정에서 승인 상세의 첨부·반응·댓글 묶음을 하위 Box로 그룹화해 부모 Stack의 항목별 16px 간격을 차단하고, 첨부/반응 separator의 `my: 1.5` 여백을 공지사항과 맞춘다. 회귀 테스트에서 그룹 부모 관계, 반응/댓글의 computed top margin 0, 기존 구분선 수를 검증한다.

### 검증 조건

- 선택 상세에서만 로딩이 패널 콘텐츠 전체 중앙에 표시되며, 로드 완료 후 콘텐츠가 정상 표시된다.
- 두 기능 모두 상세 본문은 최초에 펼쳐져 있고, 공지 목록의 접힘 동작은 변하지 않는다.
- SYSTEM 아이콘은 접근 가능한 이름을 가지며 SYSTEM 행에는 답글/편집/삭제 조작이 없다.
- 답글 toggle의 아이콘이 상태에 따라 바뀌고 `aria-expanded` 값과 동기화된다.
- 지정된 separator는 좌측 공지 피드와 두 상세에서 사라지며, 첨부-반응 및 결재선 구분은 유지된다.
- 문서 좌측 로딩 skeleton은 notice의 활성 view-mode skeleton과 동일하고, 목록 본문은 기본 접힘을 유지한다.
- API 경로/데이터, 권한, 댓글 정렬 및 cursor/page size에는 변경이 없다.
