# 20261013_001 공지사항·전자결재 피드 UI 공통화 구현 계획

## 목표 및 설계

공지사항을 시각 기준으로 삼아 좌측 피드 카드와 우측 상세 패널의 공통 표현을 구성요소화한다. 기존 `FeedView`, `PostDetailPanel`, `AttachmentList`, `CommentThread`를 우선 재사용·확장하고, 누락된 카드·반응·댓글 섹션만 추출한다. 공지사항과 전자결재의 API, 상태, 권한, 데이터 정규화는 기능별 컴포넌트/훅에 남긴다.

## 파일 변경 지도

### 공통 프런트엔드

- 생성 `frontend/src/shared/components/feed/FeedCard.tsx`: 카드의 공통 chrome과 header/title/summary/content slots. API와 권한을 다루지 않는다.
- 생성 `frontend/src/shared/components/feed/FeedReactionBar.tsx`: 좋아요·북마크 버튼과 댓글 수를 받는 프레젠테이션 컴포넌트.
- 생성 `frontend/src/shared/components/feed/FeedCommentsSection.tsx`: 댓글 수, 이전 댓글 보기 상태/동작, 댓글 영역 배치. 댓글 API를 호출하지 않고 기존 `CommentThread`를 children/props로 조립한다.
- 수정 `frontend/src/shared/components/feed/PostDetailPanel.tsx`: 공통 상세 패널 shell을 유지·정리하고 전자결재 보조 정보 및 공통 본문 배치와 호환한다.
- 수정 `frontend/src/shared/components/feed/TiptapCommentThread.tsx`: SYSTEM 작성자에 `시스템` Chip/Badge를 렌더링하고 기존 immutable 동작을 보존한다.
- 수정 `frontend/tests/feed-components.test.tsx`: 카드, 반응/댓글 공통 영역, SYSTEM 배지와 공통 상세 패널 검증.

### 공지사항 소비자

## 순서 및 테스트 전략

### Task 1 — 공통 카드 presentation

1. `feed-components.test.tsx`에 `FeedCard`의 제목/메타/slot 및 click 동작 테스트를 먼저 추가한다.
2. `cd frontend; npm run test -- tests/feed-components.test.tsx`로 실패를 확인한다.
3. `FeedCard.tsx`를 구현하고 동일 명령으로 통과를 확인한다.
4. `DocumentFeedItem`을 공통 카드로 조립하고 `document-feed-item.test.tsx` 및 `document-write-page.test.tsx`를 실행한다.
5. `NoticeFeedList`의 카드 바깥 chrome을 공통 카드로 옮기되 내부 body/이미지/첨부/댓글 상태 처리는 보존하고 notice 테스트를 실행한다.

### Task 2 — 공통 상세 하단 섹션

1. `feed-components.test.tsx`에서 `FeedReactionBar`와 `FeedCommentsSection`의 label, count, callback, loading/disabled 렌더 테스트를 먼저 추가하고 실패를 확인한다.
2. 공통 섹션을 구현하고 테스트를 통과시킨다. API 호출이나 도메인 state는 구현하지 않는다.
3. `NoticeFeedList`에서 기존 반응/댓글 header 및 이전 댓글 버튼을 공통 섹션으로 교체한다. 댓글 merge, cursor, loading, error 흐름은 기존 소유 컴포넌트에 둔다.
4. 상세 화면의 기존 `PostDetailPanel` shell과 `AttachmentList`를 양 소비자가 사용하도록 확인한다.

### Task 3 — 전자결재 상세 조립 및 SYSTEM badge

1. SYSTEM badge와 `isSystemEvent` mutation 차단을 검증하는 실패 테스트를 작성·실행한다.
2. `TiptapCommentThread.tsx`에서 SYSTEM 행에 `시스템` badge만 추가하고 기존 mutation affordance가 없음을 검증한다.
3. 전자결재 상세 결재선을 그룹화하여 공통 상세 내 상단에 배치한다. 결재/합의 참여자는 단계·순서대로, 참조는 별도 칩 목록으로 표시한다. 서버 데이터의 실제 행만 렌더링한다.
4. 전자결재 상세 하단에서 공유 첨부/반응/댓글 섹션을 사용하고 기존 문서 첨부 다운로드, approval comment CRUD, pagination callback을 유지한다.
5. 대상 테스트 `document-write-page.test.tsx`, `document-approval-service.test.ts`, `feed-components.test.tsx`를 실행한다.
6. 후속 재현 결함을 회귀 테스트로 고정한다: deleted USER row의 null `writerId` 허용, 본문 접기/더보기, 이미지 미리보기/뷰어, 공지사항과 같은 카드 테두리, 삭제 댓글 포함 시 댓글 등록/이전 댓글 영역 보존.

### Task 4 — 회귀, 브라우저, 결과 문서

1. `cd frontend; npm run test -- tests/feed-components.test.tsx tests/notice-page.test.tsx tests/document-feed-item.test.tsx tests/document-write-page.test.tsx`를 실행한다.
2. `cd frontend; npm run build`를 실행한다.
3. S-ERP Vite 서버(4173)에서 notice/approval의 좌측 리스트 및 우측 상세를 375px, 768px, 1280px로 확인한다. 기존 4173 서비스가 있으면 S-ERP인지 확인 후 재사용하고, 이번 작업에서 시작한 서버는 종료한다.
4. 좌측 카드와 우측 상세의 overflow, 댓글 순서/기능, SYSTEM badge, 결재선 read-only를 확인하고 해당 뷰포트 스크린샷을 저장한다.
5. 실제 명령 결과와 제한사항을 결과보고서에 기재한다.
6. `git diff --check`를 실행하고 결과를 확인한다.

## 위험 및 완화

- `NoticeFeedList`는 매우 큰 컴포넌트이며 확장/페이지네이션 상태가 결합되어 있다. UI chrome만 추출하고 state machine/API 코드는 이동하지 않는다.
- Notice와 approval의 댓글 cursor 및 권한 계약은 다르다. 공통 컴포넌트는 presentational props/callbacks만 받고 feature adapter가 정책을 유지한다.
- 공유 카드의 클릭 가능 semantics는 버튼 또는 article에 올바르게 반영하여 키보드 동작과 nested controls를 보존한다.
- 반응 상태의 영속화/서버 계약은 변경하지 않는다.
