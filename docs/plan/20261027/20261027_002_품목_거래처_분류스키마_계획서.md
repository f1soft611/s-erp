## 목표

S-ERP central DB의 tenant 경계, 기존 master table, ID/audit 네이밍에 맞는 분류 구조 migration 초안을 만들고 실제 적용 없이 리뷰 가능하게 보관한다.

## 범위와 제외

포함:

- `tb_cls_item`, `tb_cls_partner` 테넌트 분류 테이블 생성
- `tb_material_info.item_cls_id` 추가 및 tenant 복합 FK
- `tb_customer_info.business_kind1/2`를 nullable BIGINT 분류 ID로 전환
- business_kind 컬럼 변환 전 guard, FK/index, COMMENT
- 데이터/참조 존재 시 거부하는 rollback
- DB schema summary 및 양쪽 DB 이력 사본

제외:

- 백엔드 API 및 프론트엔드
- 기존 `mat_cata_type`, `business_kind3` 이관/삭제
- business_kind의 비공백 데이터를 임의 변환
- tenant 전용 DB 적용
- MCP 통한 쓰기 또는 실제 DB DDL 실행

## 구현 순서

1. 작업지시서와 이 계획서를 기준으로 타입·제약·중단 조건을 상세사양에 고정한다.
2. 적용 DDL에서 tenant/parent, 레벨, 사용여부, 마스터 참조 제약을 먼저 설계한다.
3. conversion guard 이후 `business_kind1/2` 빈 값만 NULL로 정리하며 BIGINT로 변경한다.
4. 분류 테이블 생성, 품목 컬럼 추가 및 tenant 복합 FK/index, 거래처 FK/index를 같은 트랜잭션으로 처리한다.
5. COMMENT, 변경 이력, rollback을 작성하고 backend 날짜 폴더에 동일 복사한다.
6. schema summary에 적용 전임을 분명하게 표시한다.
7. SQL 사전조건/후조건을 정적 검토하고 사본 일치, `git diff --check`를 확인한다.

## 위험과 완화

- `business_kind1/2`는 central DB에서 nullable varchar로 확인됐다. 적용 시점에 nonblank 값이 들어오면 자동 casting 금지, migration guard로 중단한다.
- 기존 앱에 DB 적용 전후로 business_kind 타입이 달라지면 해당 컬럼을 참조하는 client/server가 영향을 받을 수 있다. 저장소 소스에서 직접 참조가 발견되지 않았으나 적용 전 배포 의존성 확인이 필요하다.
- 대/소분류 ID만으로 레벨과 활성 여부를 FK가 보장하지 못한다. 분류 API 구현 범위에서 레벨/활성/부모 조합을 검증한다. 소분류-부모 일치는 composite FK로 데이터베이스가 보장한다.
- 적용 이후 분류 레코드나 참조가 발생하면 rollback을 거부한다. 실제 rollback 전 별도 백업과 업무 승인 절차가 필요하다.

## 검증

- 기본 central DB MCP의 `tb_tenant`, `tb_material_info`, `tb_customer_info` metadata와 tenant 복합 unique target을 사용한다.
- 업무 행은 노출하지 않고 제한 집계로 conversion 선행 조건을 확인한다.
- DDL의 `LOCK`, `DO` guard, FK key 순서, type conversion, rollback 순서를 리뷰한다.
- docs/backend 사본의 바이트 동일성을 PowerShell `Get-FileHash` 또는 `Compare-Object`로 확인한다.
- 구문 확인용 실제 DB/테스트 DB가 이 작업 환경에 준비되지 않은 경우 실행을 가장하지 않고 정적 검토 한계로 기록한다.
- 실제 central DB에는 어떤 DDL도 적용하지 않는다.
