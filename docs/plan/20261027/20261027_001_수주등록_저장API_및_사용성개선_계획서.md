## 목표와 범위

현재 브라우저 상태만 편집 가능한 수주등록 화면에 create-only 저장 API를
연결한다. 구현은 eGovFrame 계층과 인증 tenant 경계를 유지하고, 사용자
직접 생성 예정인 수주 테이블의 승인된 컬럼 계약만 사용한다. 번호 생성과
저장 후 UX를 순차 진행하며 검색/수정/취소 및 DB 스키마 변경은 포함하지
않는다.

## 구현 순서

1. 날짜별 작업지시서/계획서/상세사양서와 API 계약을 동기화한다.
2. service 테스트를 먼저 작성해 검증, 번호 포맷, 계산, 테넌트 범위를
   확인한다.
3. `SalesOrderDAO`/PostgreSQL MyBatis mapper를 추가하고,
   `SalesOrderService`/구현에 단일 트랜잭션 저장을 작성한다.
4. 인증 `LoginVO`를 검증하는 `SalesOrderApiController`와 MockMvc 테스트를
   추가하고 HTTP 201 및 기존 `ResultVO` 응답 형식을 확인한다.
5. 프론트 API 타입/서비스/검증을 추가하고 저장 요청/성공/오류/중복 방지
   UX를 연결한다.
6. 저장 뒤 별도 테스트로 미저장 이탈 경고를 추가한다. React Router 7의
   `useBlocker` 사용을 위해 `frontend/src/App.tsx`에서 기존 경로를 data
   router로 제공하고, browser `beforeunload`도 함께 처리한다.
7. 상세 그리드 옆에 선택 행용 품목 도움 버튼을 제공하고 F1-Grid 안내를
   갱신한다. 좁은 화면은 브라우저에서 페이지 가로 overflow가 없는지,
   필요한 상세 열이 그리드 내부에서 스크롤되는지 확인한다.
8. 집중 테스트, build, 브라우저 3개 폭 검증과 결과 보고서를 완료한다.

## 검증 계획

- Backend 집중:
  `mvn -f backend/pom.xml -Dtest=SalesOrderApiControllerTest,SalesOrderServiceImplTest test`
- Frontend 집중: `cd frontend; npm run test -- tests/sales-order-create-page.test.tsx`
- Frontend build: `cd frontend; npm run build`
- API 관련 backend 테스트는 DAO mock 기반으로 작성한다. DB 목록에서 수주
  테이블 부재가 확인되었으므로 DB 통합 검증은 사용자 테이블 생성 후 별도
  수행한다.
- 실제 브라우저에서 입력/품목 선택/저장 흐름을 375px, 768px, 1280px에서
  확인한다. API는 성공/실패 시나리오를 테스트 대역으로 검증한다.
- 전체 frontend baseline에서 관련 없는 기존 테스트 실패가 확인될 경우,
  수주 변경과 분리해 결과 문서에 기록하며 무관한 코드는 수정하지 않는다.

## 제외 및 안전 조건

- 신규 테이블/컬럼, DDL, 롤백 또는 DB 데이터 삽입을 생성/실행하지 않는다.
- 요청에 포함된 tenant/user/orderNo/ID/status/계산 합계를 권위 있는 값으로
  사용하지 않는다.
- tenant는 인증 `LoginVO`에서 파생하고 DAO 쿼리/삽입 모두 tenant scope를
  명시한다.
- API 실패는 성공 envelope로 변환하지 않고 사용자 입력을 보존한다.
- 테이블이 생성되기 전까지 실제 DB 통합 완료를 주장하지 않는다.
