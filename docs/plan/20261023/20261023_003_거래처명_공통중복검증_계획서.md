# 거래처명 공통 중복 검증 구현 계획

**근거:** [사용자 승인 작업지시서](../../directions/20261023/20261023_003_거래처명_공통중복검증_작업지시서.md).

**목표:** 거래처명 중복을 컬럼 옵션으로 선언하고 폼·그리드·서버에서 차단한다.

**구조:** 기존 `validateGridRow`에 선택적 중복 비교 context를 추가한다. 그리드는 활성 행의 고유값 인덱스를 한 번 구성하고 폼도 같은 helper를 사용한다. 백엔드는 조회 사전 검사와 tenant/trimmed-name 유니크 인덱스를 병행한다.

## 작업 단위

1. 상세 사양 작성 및 DB MCP 메타데이터 확인. 기본 DB와 기존 tenant 문서의 차이를 구분 기록한다.
2. 실패 테스트 작성:
   - 공통 빈 값/공백 trim/다른 ID/자기 ID/숫자 0/옵션 미설정/필터 행 및 폼 검사.
   - 거래처 신규 폼·저장 중복 오류와 실제 상단 메시지·빨간 테두리·API 미호출.
   - 백엔드 등록/수정 이름 중복, tenant/ID 조건, 동시 충돌 분류, mapper SQL.
3. 최소 구현:
   - `grid.types.ts`: `validation?: { unique?: boolean }`.
   - `GridValidation.ts`: unique 값 인덱스와 선택 context, 공통 오류.
   - `F1Grid.tsx`/`F1GridFormModal.tsx`: 전체 활성 행을 같은 검증 helper에 전달.
   - `CustomerGrid.tsx`: 거래처명 unique 설정.
   - `CustomerInfoDAO`/Mapper/Service: 이름 사전 검사, PostgreSQL index 이름에 따른 오류 분류.
4. SQL 작성: `20261023_001` tenant/name unique index 및 rollback. 기존 중복은 값 출력 없이 명시적 사전 오류, 데이터 자동 정리 없음.
5. 검증: 집중 Vitest, Maven customer 테스트, 프론트 build, 3개 폭 실제 브라우저. 필요한 경우 기존 실패는 구현 전과 구분.
6. 사용 문서·누적 스키마·날짜별 변경 문서·결과와 스크린샷 갱신. DB 미적용 사실 명시.
