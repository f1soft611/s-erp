# 20260917_001 공지사항 실제 브라우저 테스트 계획서

## 1. 목적

공지사항 페이지의 실제 브라우저 동작을 검증하고, 발견된 오류를 즉시 수정해 최종적으로 저장·수정·삭제와 첨부파일/댓글 기능이 정상 동작하도록 한다.

본 작업은 UI 동작 검증을 중심으로 하며, 코드 작성보다는 실제 사용자 흐름 중심의 문제 재현과 수정이 핵심이다.

## 2. 작업 범위

### 2.1 검증 대상 기능

1. 공지사항 저장, 수정, 삭제
2. 첨부파일 포함 공지사항 저장, 수정, 삭제
3. 댓글 저장, 수정, 삭제
4. 답글 저장, 수정, 삭제
5. 브라우저 기반 에러 재현 및 즉시 수정

### 2.2 대상 화면

- `http://127.0.0.1:4173/groupware/community/notice`
- 관련 페이지 파일: `frontend/src/pages/groupware/community/notice/**`
- 관련 서비스 파일: `frontend/src/pages/groupware/community/notice/services/**`
- 관련 공통 API: `frontend/src/shared/services/commonContentApi.ts`

## 3. 현재 코드 구조와 영향 범위

### 3.1 공지사항 페이지 로직

- `CommunityNoticePage.tsx`는 목록 로딩, 생성, 수정, 삭제, 댓글 등록을 담당한다.
- `NoticeComposerDialog`는 공지 작성/수정 모달이며, 본문 HTML/첨부 파일 데이터를 전달한다.
- `NoticeFeedList`는 목록, 댓글, 첨부 영역의 UI를 렌더링한다.

### 3.2 API 연동 흐름

- 목록 조회: `fetchNoticePosts`
- 상세 조회: `fetchNoticePostDetail`
- 생성: `createNoticePost`
- 수정: `updateNoticePost`
- 삭제: `deleteNoticePost`
- 첨부 업로드: `uploadNoticeAttachment`
- 첨부 삭제: `deleteNoticeAttachment`
- 댓글 조회/생성: `fetchCommonComments`, `createCommonComment`

### 3.3 직접 영향 파일

- `frontend/src/pages/groupware/community/notice/CommunityNoticePage.tsx`
- `frontend/src/pages/groupware/community/notice/components/NoticeComposerDialog.tsx`
- `frontend/src/pages/groupware/community/notice/components/NoticeFeedList.tsx`
- `frontend/src/pages/groupware/community/notice/services/noticeBoardService.ts`
- `frontend/src/shared/services/commonContentApi.ts`

## 4. 검증 시나리오

### 4.1 공지사항 CRUD

1. 새 공지 작성 버튼으로 작성 모달을 연다.
2. 제목/본문을 입력하고 저장한다.
3. 목록에 새 글이 추가되었는지 확인한다.
4. 수정 버튼으로 기존 공지를 편집한다.
5. 제목 또는 본문을 변경하고 저장한다.
6. 수정된 내용이 재조회되었는지 확인한다.
7. 삭제 버튼으로 공지를 삭제한다.
8. 목록에서 사라졌는지 확인한다.

### 4.2 첨부파일 포함 CRUD

1. 첨부 파일을 포함한 공지를 저장한다.
2. 첨부 목록이 보이는지 확인한다.
3. 수정 시 첨부 추가 또는 삭제가 반영되는지 확인한다.
4. 삭제 시 첨부가 실제로 제거되고 목록 재조회가 정상인지 확인한다.
5. 첨부 다운로드 링크가 정상적으로 동작하는지 확인한다.

### 4.3 댓글/답글 CRUD

1. 공지 상세를 연다.
2. 댓글을 작성한다.
3. 목록에 즉시 반영되는지 확인한다.
4. 댓글 수정 기능이 정상인지 확인한다.
5. 댓글 삭제 기능이 정상인지 확인한다.
6. 답글을 작성한다.
7. 답글 수정/삭제가 정상인지 확인한다.
8. 답글 계층 구조가 올바르게 보이는지 확인한다.

## 5. 수정 전략

### 단계 1: 재현

- 실제 브라우저에서 저장/수정/삭제 경로를 순서대로 실행한다.
- 발생하는 에러 메시지, API 호출 실패, UI 상태 불일치를 기록한다.

### 단계 2: 원인 분석

- 해당 기능이 어디서 실패하는지 확인한다.
- 데이터 전달 값, 상태 갱신, 재조회 로직, 첨부 파일 업로드 요청 형식, 댓글 parentId 처리 등을 검토한다.

### 단계 3: 최소 수정

- 사용자 요구사항 범위에 맞는 코드 수정만 적용한다.
- 재조회 로직, 에러 처리, 기존 상태값 초기화, 댓글/답글 트리 변환 등을 정리한다.

### 단계 4: 재검증

- 동일 시나리오를 다시 실행해 정상 동작을 확인한다.
- 오류가 나오면 다시 원인 파악과 수정 루프를 반복한다.

## 6. 검증 계획

### 브라우저 검증

- 로컬 개발 서버에서 실제 페이지를 직접 여는 흐름으로 검증한다.
- 필요 시 네트워크 탭/개발자 도구를 사용해 API 응답과 에러 상태를 확인한다.

### 코드 검증

- TypeScript 빌드 검증: `cd frontend && npm run build`
- 관련 테스트 확인: `cd frontend && npm run test -- --run` 또는 필요한 테스트 파일 실행

### 예외 상황

- 백엔드 API가 미구현이거나 네트워크 차단 상태라면, 프론트 쪽에서 발생하는 예외 메시지와 재조회 흐름을 수정해 브라우저 동작을 안정화한다.
- 다른 화면에 영향이 큰 변경은 즉시 중단하고 범위를 좁힌다.

## 7. 리스크와 위험 요소

- 첨부파일 업로드/수정에서 기존 업로드 파일과 새 파일 구분이 잘못될 수 있다.
- 댓글/답글 트리에서 parent id 누락 또는 재조회 후 구조가 비정상일 수 있다.
- 수정 후 목록이 오래된 상태로 유지될 수 있어 재조회 로직을 확인해야 한다.
- 에러 메시지가 UI에 반영되지 않을 수 있어 사용자 피드백 상태를 확인해야 한다.

## 8. 완료 기준

- 공지사항 저장/수정/삭제가 실제 브라우저에서 정상 동작한다.
- 첨부파일 포함 시나리오가 정상 동작한다.
- 댓글 및 답글의 저장/수정/삭제가 정상 동작한다.
- 발견된 문제는 수정 및 재검증을 통해 해결된다.
- 결과 문서와 필요 시 스크린샷이 정리된다.

## 9. DB 영향 검토

- 본 작업은 프론트엔드 동작 검증 및 문제 수정에 집중한다.
- 백엔드 DB 스키마 변경 또는 신규 API 설계는 필요하지 않다.
- DB 스크립트: 해당 없음, 영향 검토 완료.
