# 20260921_001 공지사항 첨부파일 중복·삭제 오류 및 확장자 아이콘 수정 계획서

## 1. 작업 목적

공지사항 첨부파일의 저장 후 재조회 중복, 수정 삭제 시 404, 확장자 표시 UI 문제를 기존 공통 첨부파일 계약 안에서 수정한다. 신규 API나 DB 스키마 변경은 하지 않는다.

## 2. 원인 및 설계 결정

- `NoticeBoardServiceImpl.hydratePost()`는 공통 파일 서비스 결과를 첨부 목록에 넣은 뒤, 같은 `tb_common_file`을 조회하는 DAO 결과를 다시 추가한다.
- 일반 첨부와 본문 이미지가 같은 owner 아래 저장되므로 `EMBEDDED`를 일반 첨부 표시·삭제 대상으로 섞지 않는다.
- 첨부 항목의 프론트 삭제·다운로드 키는 `CommonFileVO.fileId`에서 변환된 `NoticeBoardFileVO.boardFileId`를 사용한다.
- 삭제는 테넌트·공지 게시글·파일 ID를 함께 검증한 뒤 공통 파일 서비스의 owner-scoped 삭제를 호출한다.
- `AttachmentList`는 확장자별 MUI 파일 아이콘과 색상을 사용하고, 파일명은 별도로 표시한다.

## 3. 변경 범위

### 백엔드

- 대상: `backend/src/main/java/egovframework/let/groupware/community/notice/service/impl/NoticeBoardServiceImpl.java`
- 대상: 공지 첨부 관련 VO/DAO/XML은 실제 계약 검토 후 필요한 최소 변경만 적용
- `hydratePost()`에서 일반 첨부와 본문 이미지 목록을 중복 합치지 않도록 분리
- 일반 첨부의 `attachmentCount`와 응답 항목을 실제 활성 공통 파일 기준으로 유지
- 삭제 검증이 일반 첨부 ID를 정확히 찾도록 보강
- 본문 이미지 재작성·스트리밍 동작은 유지

### 프론트엔드

- 대상: `frontend/src/shared/components/feed/AttachmentList.tsx`
- 대상: `frontend/src/pages/groupware/community/notice/CommunityNoticePage.tsx`
- 대상: `frontend/src/pages/groupware/community/notice/services/noticeBoardService.ts`
- 필요 시 `NoticeComposerDialog.tsx`의 기존 첨부 ID 계산을 최소 보정
- 일반 첨부 응답의 ID를 보존하고 삭제 API에 게시글 ID를 함께 전달
- 확장자별 아이콘 표시와 기본 아이콘 fallback 추가

### 문서·검증

- 대상: 관련 Vitest/백엔드 테스트
- 대상: `docs/result/20260921/notice-attachment-consistency/`
- 데스크톱·모바일 브라우저 검증 및 스크린샷 기록

## 4. 태스크 분해

1. 백엔드 첨부 조회 경로를 단일화하고 `EMBEDDED` 분리를 검증한다.
2. 백엔드 삭제 소유 검증과 첨부 ID 응답 계약을 검증·보강한다.
3. 프론트 첨부 매핑·수정 삭제 흐름의 ID 계약을 검증·보강한다.
4. 공통 첨부 목록의 확장자별 아이콘 UI를 구현한다.
5. 회귀 테스트를 작성·실행하고 프론트 빌드와 백엔드 테스트를 수행한다.
6. 실제 브라우저에서 저장 후 재조회, 수정 삭제, 아이콘 표시를 검증하고 결과 문서를 작성한다.

## 5. 영향 범위

- 공지사항 일반 첨부 목록·상세 응답
- 공지사항 첨부 삭제·다운로드
- 공통 피드 첨부 목록 UI를 사용하는 화면의 아이콘 표시
- 본문 이미지 및 댓글 첨부는 기존 동작을 유지

## 6. DB 영향

- 신규 테이블·컬럼·인덱스·데이터 마이그레이션 없음
- 기존 `tb_common_file` 조회/소프트 삭제 계약만 사용
- DB 스크립트 및 rollback 파일: 해당 없음

## 7. 검증 계획

- 프론트 관련 Vitest: 첨부 중복 제거, ID 전달, 확장자 아이콘 fallback
- 백엔드 관련 테스트: 일반 첨부 단일 응답, `EMBEDDED` 제외, owner-scoped 삭제 검증
- 프론트: `npm run build`
- 백엔드: `mvn test`
- 브라우저: 1280px 이상과 375px에서 업로드 후 재조회, 수정 삭제 저장, `xlsx`/기타 확장자 아이콘 표시
- 실패 시 원인과 재검증 결과를 결과 문서에 기록

## 8. 상세 실행 계획

### Step 1: 백엔드 첨부 집합 단일화

- 파일: `backend/src/main/java/egovframework/let/groupware/community/notice/service/impl/NoticeBoardServiceImpl.java`
- 작업: `hydratePost()`에서 공통 파일을 `ATTACHMENT`와 `EMBEDDED`로 분리하고, 일반 첨부는 한 번만 `attachments`에 넣는다. 본문 이미지 재작성은 `EMBEDDED` 집합만 사용한다.
- 검증: 관련 서비스 테스트 또는 백엔드 테스트 실행. 일반 첨부 1건의 응답 ID가 한 번만 존재하고 본문 이미지는 목록에 나오지 않는지 확인한다.
- 인터페이스: `NoticeBoardFileVO.boardFileId`는 `CommonFileVO.fileId`를 유지한다.

### Step 2: 백엔드 삭제·개수 계약 점검

- 파일: `backend/src/main/java/egovframework/let/groupware/community/notice/service/impl/NoticeBoardServiceImpl.java`, 필요 시 공지 DAO/XML
- 작업: owner-scoped 삭제 검증이 일반 첨부 ID를 찾도록 확인하고, `attachmentCount`가 일반 첨부 응답 수와 일치하도록 유지한다.
- 검증: 같은 공지의 파일 삭제 성공, 다른 공지의 파일 삭제 404, 삭제 후 재조회에서 파일 제외를 확인한다.
- 인터페이스: 삭제·다운로드 URL과 `postId` 쿼리 계약은 변경하지 않는다.

### Step 3: 프론트 첨부 ID 흐름 회귀 보강

- 파일: `frontend/src/pages/groupware/community/notice/CommunityNoticePage.tsx`, `frontend/src/pages/groupware/community/notice/services/noticeBoardService.ts`, 필요 시 `NoticeComposerDialog.tsx`
- 작업: 저장된 첨부의 `boardFileId` 보존, 제거 목록 생성, 삭제 요청의 `postId` 전달을 점검하고 필요한 최소 수정만 적용한다.
- 검증: 수정 화면에서 기존 첨부 제거 후 제출 시 올바른 ID와 게시글 ID가 전송되는 테스트를 실행한다.
- 인터페이스: 새 로컬 파일은 삭제 API에 전송하지 않는다.

### Step 4: 확장자별 파일 아이콘 표시

- 파일: `frontend/src/shared/components/feed/AttachmentList.tsx`
- 작업: 기존 확장자 매핑을 아이콘 컴포넌트 중심으로 정리하고 미지원 확장자 fallback과 좁은 화면 레이아웃을 유지한다.
- 검증: `xlsx` 및 미지원 확장자 렌더링 테스트와 브라우저 375px/1280px 캡처를 실행한다.
- 인터페이스: 파일명, 다운로드, 삭제 접근성 라벨과 동작은 유지한다.

### Step 5: 통합 검증 및 결과 문서

- 파일: `docs/result/20260921/notice-attachment-consistency/progress.md`, `docs/result/20260921/notice-attachment-consistency/result.md`
- 작업: 단계별 검증 로그, 실패 원인·수정·재검증, 브라우저 캡처 경로를 기록한다.
- 검증: 프론트 관련 Vitest, `npm run build`, 백엔드 `mvn test`, 실제 브라우저 시나리오를 순서대로 실행한다.

## 9. Global Constraints

- 승인된 상세 사양서 범위 밖의 API·권한·DB 스키마 변경을 추가하지 않는다.
- 사용자 변경사항과 기존 무관 변경을 되돌리지 않는다.
- 첫 구현 태스크는 실패 가능한 좁은 테스트 또는 최소 검증을 먼저 확보한 뒤 수정한다.
- 각 태스크는 자기검토, 사양 준수 리뷰, 코드 품질 리뷰를 거친 뒤 다음 태스크로 이동한다.
- 이 세션에서는 사용자의 별도 요청 없이는 커밋·병합·푸시·브랜치 삭제를 실행하지 않는다.
