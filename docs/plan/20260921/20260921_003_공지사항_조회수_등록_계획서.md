# 20260921_003 공지사항 조회수 등록 계획서

## 1. 작업 목적

공지사항 상세 조회 시 인증된 사용자별로 공지글당 최초 1회만 조회수를 증가시킨다. 기존 `tb_board_post.view_count`를 재사용하고, 영속 조회 이력으로 새로고침·반복·동시 요청의 중복 증가를 차단한다.

## 2. 설계 결정

- 조회 단위: `tenant_id + post_id + login_id`
- 조회 이력: 신규 `tb_board_post_view_history`
- 중복 방지: `(tenant_id, post_id, login_id)` 유니크 제약
- 증가 처리: 조회 이력 최초 등록이 성공한 경우에만 `tb_board_post.view_count = view_count + 1`
- 인증 식별자: `LoginVO.id`(로그인 코드)를 `tenant_id + login_code`로 `tb_login_account.login_id`에 해석한 뒤 이력에 저장
- 목록 조회: 조회수 증가 없음
- 외부 상세 API 경로·HTTP 응답 구조: 유지

## 3. 영향 범위

### 백엔드

- `NoticeBoardApiController`: 상세 조회에서 인증 사용자 식별자를 서비스에 전달
- `NoticeBoardService`: 사용자 식별자를 받는 상세 조회 계약 추가
- `NoticeBoardServiceImpl`: 게시글 존재 확인, 조회 이력 등록, 최초 조회 시 조회수 증가, 상세 보강 흐름 구현
- `NoticeBoardDAO`: 로그인 계정 식별자 해석, 조회 이력 등록, 조회수 증가 메서드 추가
- `NoticeBoard_SQL_postgresql.xml`: 조회 이력 INSERT 및 조회수 원자 UPDATE 추가
- `NoticeBoardServiceImplTest`: 최초 조회/중복 조회/다른 사용자/예외 회귀 검증

### 프론트엔드

- `noticeBoardService.ts`, `CommunityNoticePage.tsx`, `NoticeFeedList.tsx`의 `viewCount` 계약 연결을 점검한다.
- 이미 상세 응답의 조회수를 표시하면 코드 변경 없이 빌드·관련 테스트로 확인한다.
- 표시가 누락된 경우 해당 표시 연결만 최소 수정한다.

### 데이터베이스

- `tb_board_post_view_history` 신규 테이블 생성
- `tenant_id`, `post_id`, `login_id`, `viewed_at` 저장
- 게시글·로그인 계정 FK와 복합 유니크 제약 추가
- 날짜별 SQL, 변경 이력, rollback, 누적 스키마 문서 갱신

## 4. 트랜잭션 및 동시성

1. 상세 대상 게시글을 삭제되지 않은 상태로 조회한다.
2. `LoginVO.id`로 현재 테넌트의 로그인 계정 PK를 확인한다.
3. 조회 이력 INSERT를 시도한다.
4. 유니크 충돌 또는 이미 존재하는 이력이면 조회수 UPDATE를 수행하지 않는다.
5. 최초 INSERT가 성공한 경우에만 조회수 원자 UPDATE를 수행한다.
6. 증가된 값을 포함하도록 게시글을 재조회한 뒤 첨부파일·댓글을 보강한다.

서비스 메서드는 트랜잭션으로 묶고, 중복 요청은 DB 유니크 제약을 최종 기준으로 처리한다.

## 5. 검증 계획

- 백엔드: `mvn -Dtest=NoticeBoardServiceImplTest test`
