# 20261015_016 목록 조회 배치 처리 계획서

## 목표

공지사항 목록과 전자결재 피드 목록의 N+1 조회를 종류별 배치 조회로 바꾸고, 기존 댓글 카운트/페이지 응답 의미를 복원한다.

## 파일 범위

- `backend/src/main/java/egovframework/com/common/service/CommonCommentService.java`: 배치 댓글 페이지 서비스 계약.
- `backend/src/main/java/egovframework/com/common/service/impl/CommonCommentServiceImpl.java`: owner ID별 댓글 페이지/수/메타데이터 그룹화.
- `backend/src/main/java/egovframework/com/common/domain/repository/CommonCommentDAO.java`: 댓글/카운트 batch DAO 연결.
- `backend/src/main/resources/egovframework/mapper/com/common/CommonComment_SQL_postgresql.xml`: owner ID별 루트 댓글 트리 및 루트 카운트.
- `backend/src/main/java/egovframework/let/groupware/community/notice/service/impl/NoticeBoardServiceImpl.java`: 공지 페이지 수집과 댓글 파일 단일 배치 조회.
- `backend/src/main/java/egovframework/let/groupware/approval/domain/model/DocumentApprovalLineBatchVO.java`: bulk 결과를 전자결재 ID로 그룹화하기 위한 내부 결과 모델.
- `backend/src/main/java/egovframework/let/groupware/approval/domain/repository/DocumentApprovalDAO.java`: 상세 및 결재선 batch DAO.
- `backend/src/main/resources/egovframework/mapper/let/groupware/approval/DocumentApproval_SQL_postgresql.xml`: 권한 조건이 포함된 상세 batch 조회와 전자결재 ID별 결재선 조회.
- `backend/src/main/java/egovframework/let/groupware/approval/service/impl/DocumentApprovalServiceImpl.java`: 피드의 목록 ID 수집, batch hydration, 댓글 트리/카운트/첨부 조립.
- `backend/src/test/java/egovframework/com/common/service/CommonCommentServiceTest.java`: 공통 batch 댓글 페이지 grouping과 루트 count 테스트.
- `backend/src/test/java/egovframework/let/groupware/community/notice/service/impl/NoticeBoardServiceImplTest.java`: 공지 결과 및 고정 호출 수 회귀 테스트.
- `backend/src/test/java/egovframework/let/groupware/approval/service/impl/DocumentApprovalServiceImplTest.java`: 다중 문서 피드 batch 호출 및 권한/댓글 회귀 테스트.
- `backend/src/test/java/egovframework/let/groupware/approval/domain/repository/DocumentApprovalMapperTest.java`: bulk SQL의 tenant/권한/root count 조건 및 매퍼 등록 확인.
- `docs/result/20261015/list-query-batching/20261015_016_목록_조회_배치처리_결과.md`: 수행 결과.

## 실행 계획

### Task 1: 공지 목록 회귀 테스트

1. `NoticeBoardServiceImplTest`의 배치 hydration 케이스를 두 게시글, 최소 네 최상위 댓글, 답글 및 첨부 사례로 구성한다.
2. 댓글 수는 최상위 댓글만 센다는 assertion과 함께, 댓글은 최신 세 최상위 그룹만 포함하고 `hasPreviousComments=true`, `nextBeforeCommentId`가 가장 오래된 표시 루트를 가리키는지 검증한다.
3. 페이지 내 comment IDs를 하나의 `listFilesByOwnerIds(tenantId, "NOTICE_COMMENT", ids)`에 전달하며, 게시글별 댓글 첨부 호출이 없음을 verify한다.
4. 집중 테스트를 실행해 새 assertion이 실패하는 것을 확인한다.

### Task 2: 공통 댓글 배치 페이지 서비스

1. `CommonCommentService`에 `Map<Long, CommonCommentPageVO> listCommentPagesByOwnerIds(Long tenantId, String ownerType, List<Long> ownerIds, Integer limit)`을 추가한다. 기존 `listCommentsByOwnerIds`는 기존 소비자를 위해 보존한다.
2. batch SQL은 owner별 최신 `limit + 1`개의 루트 대화를 가져오고, 답글은 각 루트에 전부 연결한다. 서비스는 초과 한 루트를 제거하고 기존 단건 서비스와 동일하게 표시 그룹 순서를 구성한다.
3. `countCommentsByOwnerIds` SQL에 `parent_comment_id IS NULL`을 적용해 기존 `countCommonComments`와 일치시킨다. 페이지 서비스는 기존 bulk 카운트를 사용하여 각 `CommonCommentPageVO.resultCnt`를 설정한다.
4. 결과 페이지에는 현재 노출 가능한 최대 `limit`개의 루트 그룹만 담고, 초과 그룹이 있을 때 `hasPrevious=true`, `nextBeforeCommentId`에는 반환 댓글 중 가장 오래된 루트 ID를 설정한다.
5. `CommonCommentServiceTest`에서 empty IDs, 서로 다른 owner grouping, extra root sentinel, root-only count, 잘못된 limit을 검증한다.
6. 해당 테스트를 실행해 실패를 확인한 다음 서비스/SQL을 구현하고 다시 실행한다.

### Task 3: 공지 목록 단일 hydration

1. `NoticeBoardServiceImpl.listPosts()`는 post IDs에 대해 파일, `CommonCommentPageVO`, 댓글 수를 bulk service 호출로 얻는다.
2. 모든 페이지 댓글의 IDs를 먼저 수집하고 댓글 첨부파일을 한 번 조회해 `commentId -> files` map으로 만든다.
3. 각 post hydrate에는 준비된 페이지/파일 map을 전달하고, 단건 상세 `getPost()`의 기존 hydrate 흐름은 유지한다.
4. 공지 집중 테스트를 재실행해 목록 전체 ID당 bulk 호출 횟수가 한 번이고 응답 metadata가 단건 호출 계약과 일치하는지 확인한다.

### Task 4: 전자결재 피드 실패 테스트

1. `DocumentApprovalServiceImplTest.feedListHydratesDocumentWithoutRecordingView`를 두 문서로 확장한다.
2. batch 상세, 결재선, 첨부, 시스템 이벤트, 댓글 페이지/수, 댓글 첨부파일 응답을 ID별로 반환하도록 mock하고 각 문서 응답 매핑을 검증한다.
3. `selectDocumentApprovalDetail`, `selectApprovalLines`, `selectApprovalUserCommentPage`, `countApprovalUserComments`, `selectIsDocumentParticipant`, 단건 `listFiles`가 피드 처리에서 호출되지 않음을 verify한다.
4. 테스트를 실행해 새 batch DAO 메서드/응답 조립이 아직 없어 실패함을 확인한다.

### Task 5: 전자결재 batch DAO 및 SQL

1. `DocumentApprovalDAO`에 ID 목록 상세 조회 및 결재선 조회 메서드를 추가한다.
2. 상세 batch SQL은 `tenantId`, `ownerIds`, 그리고 기존 `selectDocumentApprovalDetail`의 기안자 또는 결재 참여자 조건을 유지한다.
3. 결재선 batch SQL은 `tenant_id`와 `electronic_approval_id IN (...)`로 제한하고 기존 단일 조회의 user/login join, 도장 조건, 순서(`stage_order`, `participant_order`)를 유지한다.
4. 내부 `DocumentApprovalLineBatchVO`는 기존 결재선 필드를 상속하고 `electronicApprovalId`만 추가해 결과를 문서 ID별로 그룹화한다. API 응답용 `DocumentApprovalLineVO`에 그룹화 전용 필드를 노출하지 않는다.
5. 공통 댓글 DAO 및 mapper에 `APPROVAL`의 `USER` 댓글 트리/루트 수를 owner ID 목록 기준으로 조회하는 쿼리를 추가한다. system 이벤트는 기존 owner ID bulk mapper를 재사용한다.
6. MyBatis mapper와 Java 소스가 컴파일되는지 `mvn -q -DskipTests compile`로 확인한다.

### Task 6: 전자결재 feed assembly

1. `listFeedDocuments()`에서 목록 문서 ID를 모아 상세, 결재선, 문서 파일, 시스템 이벤트, 사용자 댓글 페이지와 root count를 각각 batch 조회한다.
2. comment IDs를 전체 문서 기준으로 모아 `APPROVAL_COMMENT` 파일을 한 번 조회한다.
3. 각 feed item에 기존 목록 필드와 batch detail/관계 자료를 설정한다. 상세 batch query 자체에 권한 조건을 둬 문서별 `requireRelatedDocument()`를 호출하지 않는다.
4. 댓글은 삭제 표시 규칙을 지키고, 댓글 수는 삭제되지 않은 최상위 `USER` 댓글만 계산한다. 페이지 metadata는 최신 3개 루트 대화 기준으로 기존 단건 댓글 API와 맞춘다.
5. 문서가 비어 있으면 empty list를 반환하고 불필요한 빈 `IN` 쿼리를 실행하지 않는다.
6. Task 4 테스트를 실행해 다중 문서 결과 및 고정된 batch 호출 횟수가 통과하는지 확인한다.

### Task 7: 통합 검증 및 결과

1. 관련 서비스 및 매퍼 테스트를 실행한다:

   ```powershell
   cd backend
   mvn test -q "-Dtest=CommonCommentServiceTest,NoticeBoardServiceImplTest,DocumentApprovalServiceImplTest,DocumentApprovalMapperTest"
   ```

2. 전체 백엔드 테스트를 실행한다:

   ```powershell
   cd backend
   mvn test -q
   ```

3. `git diff --check`를 실행하고 mapper 변경/호출 수 회귀 테스트를 검토한다.
4. 결과 폴더에 집중/전체 테스트 결과, DB MCP 테이블 계약 확인 근거, schema 변경 없음 및 UI가 없어 스크린샷이 비대상인 점을 기록한다.
5. 기존의 unrelated staged/unstaged 파일은 수정하거나 포함하지 않는다.
