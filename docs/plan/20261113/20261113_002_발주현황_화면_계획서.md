# 20261113_002 발주현황 화면 계획서

기준: [작업지시서](../../directions/20261113/20261113_002_발주현황_화면_작업지시서.md)

## 구현 단위

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| 1 | 메뉴 SQL | `20261113_005` seed·롤백·변경이력(두 경로 사본), 정적 테스트 |
| 2 | 목록 API | `materials/order/status`(Controller·Service·DAO·Mapper·VO) |
| 3 | 수정 API | `PUT /purchase-orders/{id}`: 값 수정, 행 삭제, 직접 발주 시 자동 MR/MC 동기화 |
| 4 | 취소 API | `POST /purchase-orders/{id}/cancel`: 확정 불러오기는 잔량 복원, 직접 발주는 MC 취소·MR 삭제 처리 |
| 5 | 단건 조회 보강 | 상세 행에 확정 기준값(확정수량, 잔량, 확정 단가·납기·창고·구매처) 추가 |
| 6 | 등록 화면 view/edit 모드 | `PurchaseOrderCreatePage`에 mode·embedded·콜백 추가(구매요청등록과 같은 방식) |
| 7 | 현황 화면 | 검색·목록·상세 패널·편집 다이얼로그, 대시보드 `order-status` 연결 |
| 8 | 검증·결과 | 테스트, 빌드, JDK 8, 브라우저, 결과 문서 |

## 재사용
- 구매요청현황의 검색 훅·세션 보존·컬럼 정의 패턴, `PageAreaOverlay`/`PostDetailPanel`, `CommonDialog` 편집 다이얼로그.
- 발주등록의 금액 계산, 컬럼, 행 변환, `prepareRow` 검증을 수정에도 그대로 쓴다.
- 확정 취소·요청 상태 재계산은 기존 `PurchaseRequestConfirmDAO`, `PurchaseRequestDAO`를 재사용한다.

## 위험과 대응
- **직접 발주 정합성**: 행 삭제·값 수정 때 자동 생성된 MR/MC가 어긋나지 않게 같은 트랜잭션에서 동기화한다. 실패하면 전체 롤백한다.
- **행 번호 충돌**: `(발주, 행번호)` 유일 제약 때문에 삭제를 먼저 하고 남은 행을 기존 행번호 오름차순으로 다시 매긴다.
- **동시 수정·취소**: 헤더를 `FOR UPDATE`로 잠그고 취소된 발주는 409로 막는다.
- **가입고 연동 미구현**: 가입고 테이블이 없어 차단 검증을 넣지 않는다. 결과 문서와 사양서에 명시하고 가입고 작업에서 추가한다.

## 검증 계획
- 서비스 단위 테스트: 수정(값 변경·행 삭제·금액 재계산), 직접 발주 동기화, 모든 행 삭제 거부, 취소(확정 불러오기/직접), 취소된 발주 거부.
- 매퍼·SQL 정적 테스트, 프론트(검색·상세·편집·취소·읽기 전용), 브라우저 375/768/1280px.
