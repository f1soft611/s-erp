# 프론트 테스트 실행시간 개선 계획서

- 작업지시서: [작업지시서](../../directions/20261125/20261125_003_프론트테스트_실행시간_개선_작업지시서.md)

## 원인 조사 결과 (구현 전 측정)

| 항목 | 측정값 |
|---|---|
| 전체 실행(16 논리 코어, 기본 forks 15워커) | 629초, 255파일 3,056건 |
| 누적 시간 | 테스트 본문 3,314초 · 환경 생성 2,483초 · import 1,978초 · setup 442초 |
| `document-write-page` 전체 실행 중 | 592초 (156건) |
| `document-write-page` 단독 실행 | 211초, 평균 1.36초/건, 4초 이상 6건 |
| 두 번째로 긴 파일 | `sales-order-create-page` 202초(전체 실행 중) |

- Vitest는 **파일 단위로만** 워커에 분배한다. 156건이 한 파일에 있어 한 워커에서 직렬로 실행되며, 전체 실행이 끝나는 시점을 이 파일이 결정한다(임계 경로).
- 단일 테스트 CPU 프로파일: React 개발 모드 렌더링 약 18%, `getByRole` 접근성 이름 계산과 jsdom `getComputedStyle` 약 10%. 테스트 하나하나가 무거운 MUI 화면을 렌더링하는 것이 기본 비용이다.
- 테스트 순서가 뒤로 갈수록 느려지는 현상(스타일 누적)은 없었다(분기별 평균 1,305/895/2,280/941ms).

## 검토한 대안

| 대안 | 결과 | 판단 |
|---|---|---|
| `deps.optimizer.client` 사전 번들 | import 11.0초 → 12.6~12.9초 | 제외 |
| pool `threads`/`vmThreads`/`vmForks` | 30파일 표본에서 기본 `forks`(47초)보다 빠르지 않음(48~60초) | 제외 |
| 워커 수 조정 | 다른 프로세스 부하(CPU 약 45%)로 측정 편차가 커 결론 불가 | 제외(설정 변경 안 함) |
| `isolate: false` | 파일별 `vi.mock` 상태 공유 위험 | 제외 |
| `getByRole` 전역 `hidden` 설정 | 숨김 요소 매칭으로 단언 의미가 바뀔 위험 | 제외 |
| **`document-write-page` 파일 분할** | 임계 경로 제거, 단언 변경 없음 | **채택** |

## 구현 계획

1. 공용 영역(1~703행: mock 객체, `vi.mock`, 픽스처, 헬퍼, 전역 `beforeEach`/`afterEach`)을 `tests/document-write-page/documentWritePage.harness.tsx`로 옮긴다.
2. 최상위 테스트 138개 블록(`it` 127, `it.each` 11 → 156건)을 원래 순서대로 여러 파일로 나눈다. 단독 실행 시간 기준으로 균형을 맞춘다.
3. 각 분할 파일은 공용 모듈을 먼저 import해 mock 등록을 보장하고, 기존 `describe('Document write page')` 이름을 유지한다.
4. 기존 파일을 삭제한다. 참조하는 스크립트·CI 설정은 없음을 확인했다(CI는 `npm run test:ci`로 전체 실행).
5. 검증: 분할 파일만 실행해 156건 통과·테스트 이름 일치 확인, 전체 실행 시간 비교.

## 범위 제외

- 운영 소스 변경, 다른 테스트 파일 변경, Vitest 설정 변경.
- 장시간 파일 2위 이하(`sales-order-create-page` 등)는 이번 결과를 본 뒤 별도 판단한다.
