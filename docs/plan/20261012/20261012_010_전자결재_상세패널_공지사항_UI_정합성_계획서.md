# 전자결재 상세 패널 공지사항 UI 정합성 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 전자결재 문서 상세 패널을 공지사항형 구조로 통일하고, 문서 이력 통합·기안자 전용 수정/삭제·감사 가능한 논리 삭제를 제공한다.

**Architecture:** 전자결재 전용 상세 컴포넌트와 승인 전용 API 경계를 유지하면서 `PostDetailPanel`, `AttachmentList`, `CommentThread`를 재사용한다. 문서·결재선·SYSTEM 이벤트 데이터는 기존 모델을 유지하고, 삭제 표시는 문서 테이블의 `deleted_yn`으로 관리해 일반 API 경로에서 숨긴다. 상세 응답은 로그인 사용자의 소유 여부를 `isDrafter` boolean으로 제공하되, 삭제 권한은 서버 service에서 매번 다시 검증한다. SYSTEM 이벤트는 USER 댓글과 같은 시간순 댓글 타임라인에서 읽기 전용으로 표시한다.

**Tech Stack:** React, TypeScript, MUI, Vitest, Playwright, Java 17, Spring Boot/eGovFrame, MyBatis, PostgreSQL, JUnit 5, Mockito.

- 본문 순서는 기안일/기안자 메타정보 → 읽기 전용 결재선 → 문서 제목 → 본문 → 본문 이미지 목록 → 문서 첨부 목록 → 좋아요/북마크 UI → 댓글 타임라인이다. 본문 내 이미지는 원래 위치에 번호/대체 텍스트 참조를 남기고 실제 이미지 미리보기는 목록에서 한 번만 렌더링한다.
- 헤더 우측에는 핀 UI, 기안자에게만 보이는 더보기 메뉴, 결재 상태 배지를 둔다. 핀은 클릭 동작을 제공하지 않는다.
- 좋아요/북마크는 공지사항과 같은 프런트엔드 임시 상호작용까지만 제공한다. approval 백엔드 호출, DB 저장, 상세 재열기/새로고침 이후 상태 보존은 하지 않는다.
- SYSTEM 이벤트는 별도 문서 이력 섹션 없이 USER 댓글과 한 타임라인에서 시각순으로 보여주며, SYSTEM 이벤트는 답글/수정/삭제할 수 없다.
- 수정은 본인 문서의 `DRAFT`/`REVISION_REQUESTED`에 한해 기존 흐름을 유지한다.
- 삭제는 본인 문서의 `DRAFT`, 또는 `PENDING` 중 기안자 자동승인 외에 다른 결재 참여자의 처리 이력이 없는 경우만 허용한다. 논리 삭제와 `DELETED` SYSTEM 이벤트를 한 트랜잭션으로 기록한다.

### Task 3: 논리 삭제 migration과 스키마 문서

**파일:** 양쪽 `20261012_002` SQL/변경 이력/롤백 및 `docs/database/db-schema.md`

- [x] **Step 1: migration 선행 검증 조건을 정한다.** 실제 DB constraint 이름/허용값이 설계 확인 시점과 달라졌다면 기존 DB 변경 이력과 read-only MCP metadata를 재확인한다. 행 데이터와 자격 증명은 조회하지 않는다.
- [x] **Step 2: forward SQL을 작성한다.** 하나의 트랜잭션에서 `tb_electronic_approval_main.deleted_yn VARCHAR(1) NOT NULL DEFAULT 'N'`과 `Y/N` CHECK를 추가하고, `chk_tb_common_comment_event_type`의 기존 USER/SYSTEM 규칙 및 기존 이벤트 허용값을 유지하면서 SYSTEM `DELETED` 이벤트를 추가한다.

```sql
BEGIN;

ALTER TABLE public.tb_electronic_approval_main
    ADD COLUMN deleted_yn VARCHAR(1) NOT NULL DEFAULT 'N',
    ADD CONSTRAINT chk_electronic_approval_main_deleted_yn
        CHECK (deleted_yn IN ('Y', 'N'));

ALTER TABLE public.tb_common_comment
    DROP CONSTRAINT chk_tb_common_comment_event_type,
    ADD CONSTRAINT chk_tb_common_comment_event_type
        CHECK (
            (comment_type = 'USER' AND event_type IS NULL)
            OR
            (
                comment_type = 'SYSTEM'
                AND event_type IS NOT NULL
                AND LENGTH(BTRIM(event_type)) > 0
                AND event_type IN (
                    'APPROVED', 'REJECTED', 'RETURNED', 'DRAFT_SAVED',
                    'SUBMITTED', 'RESUBMITTED', 'COMPLETED', 'DELETED'
                )
            )
        );

COMMIT;
```

이 SQL은 파일로 작성하고 실행하지 않는다. 기존 허용 이벤트 목록은 현재 migration의 계약을 그대로 보존한다.
- [x] **Step 3: 롤백 SQL을 작성한다.** 아래처럼 `deleted_yn='Y'` 문서 또는 `event_type='DELETED'` 이벤트가 존재하면 데이터 손실 방지를 위해 예외로 중단한다. 그 외에는 기존 이벤트 허용 목록으로 제약을 복구하고 삭제 표시 컬럼/CHECK를 제거한다.

```sql
BEGIN;

LOCK TABLE public.tb_electronic_approval_main IN ACCESS EXCLUSIVE MODE;
LOCK TABLE public.tb_common_comment IN ACCESS EXCLUSIVE MODE;

DO $rollback$
BEGIN
    IF EXISTS (
        SELECT 1 FROM public.tb_electronic_approval_main
        WHERE deleted_yn = 'Y'
    ) OR EXISTS (
        SELECT 1 FROM public.tb_common_comment
        WHERE owner_type = 'APPROVAL'
          AND comment_type = 'SYSTEM'
          AND event_type = 'DELETED'
    ) THEN
        RAISE EXCEPTION 'Cannot roll back while deleted approval data exists';
    END IF;
END;
$rollback$;

ALTER TABLE public.tb_common_comment
    DROP CONSTRAINT chk_tb_common_comment_event_type,
    ADD CONSTRAINT chk_tb_common_comment_event_type
        CHECK (
            (comment_type = 'USER' AND event_type IS NULL)
            OR
            (
                comment_type = 'SYSTEM'
                AND event_type IS NOT NULL
                AND LENGTH(BTRIM(event_type)) > 0
                AND event_type IN (
                    'APPROVED', 'REJECTED', 'RETURNED', 'DRAFT_SAVED',
                    'SUBMITTED', 'RESUBMITTED', 'COMPLETED'
                )
            )
        );

ALTER TABLE public.tb_electronic_approval_main
    DROP CONSTRAINT chk_electronic_approval_main_deleted_yn,
    DROP COLUMN deleted_yn;

COMMIT;
```

이 롤백 SQL도 작성/검토만 한다. migration을 적용한 이후 롤백은 `DELETED` 이벤트/삭제 표시가 없는 경우에만 가능하다는 전제를 변경 이력에 기록한다.

```sql
UPDATE public.tb_electronic_approval_main

    updated_by = #{drafterId}

```

- [ ] **Step 6: service 삭제 트랜잭션을 구현한다.** interface 시그니처는 `void deleteDocumentApproval(LoginVO user, Long electronicApprovalId) throws Exception;`로 한다. 구현에는 `@Transactional(rollbackFor = Exception.class)`을 붙인다. service는 기존 인증 검증과 양수 ID 검증을 사용하고 `selectDocumentApprovalForUpdate`로 행을 잠근다. 소유자 ID가 일치하는지 확인하고 `PENDING`이면 `selectApprovalLines` 결과에서 stage 1 기안자 `APPROVAL` 자동승인 행을 식별한 뒤, 다른 `APPROVAL`/`AGREEMENT` 행 모두가 미처리임을 검증한다. 기존 `insertSystemEvent` helper에 `eventType='DELETED'`, 내용 `문서가 삭제되었습니다.`를 전달하고, 삭제 표시는 같은 transaction에서 갱신한다. 이벤트 insert 또는 update 실패는 예외로 전파해 두 작업을 함께 rollback한다. 결재 action도 동일한 문서 행 잠금을 사용하므로 두 요청은 직렬화되어야 한다.
