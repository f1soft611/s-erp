# 문서 본문 이미지 붙여넣기 복구 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 문서작성 본문에 붙여넣은 이미지를 공통 이미지 생명주기와 전자결재 임시저장 API에 연결해 draft 저장 뒤에도 안전하게 유지한다.

**Architecture:** 기존 `RichTextEditor`와 `useRichTextEditorSaveLifecycle`, `EmbeddedImageStorageService`, `EmbeddedImageDocumentProcessor`를 재사용한다. 전자결재 도메인은 임시 이미지 업로드/삭제 및 owner-authorized 이미지 조회 경로를 제공하고, draft 저장 요청의 HTML/JSON 및 이미지 session metadata를 같은 트랜잭션에서 검증·승격한다.

**Tech Stack:** React, TypeScript, Tiptap, Vitest, Spring Boot, MyBatis, JUnit 5, Mockito, MinIO.

## 작업 1: 날짜별 상세 사양 고정

**Files:** `docs/spec/20261012/20261012_002_문서본문이미지붙여넣기_복구_사양서.md`

- [x] **Step 1: 승인 설계의 API 및 ownership 계약을 날짜별 사양서로 옮긴다**

  사양서에 다음 경로와 계약을 고정한다.

  - `POST /api/v1/groupware/approvals/embedded-images/temp`: 인증 사용자의 tenant scope에서 공통 `EmbeddedImageStorageService.uploadTemporaryImage`를 호출하고 `{ item: { uploadToken, fileName, fileSize, mimeType, previewUrl, objectKey } }`를 반환한다.
  - `DELETE /api/v1/groupware/approvals/embedded-images/temp/{uploadToken}?fileName=...`: 인증 tenant의 공통 temporary object만 삭제한다.
  - `GET /api/v1/groupware/approvals/{electronicApprovalId}/embedded-images/{fileId}`: draft owner 확인 후 owner type `APPROVAL`로 `streamOwnedImage`를 호출한다.
  - Draft JSON은 `embeddedImages`에 `{ uploadToken, fileName, imageUrl, fileId, objectKey, fileSize, mimeType, width }` 목록을, `temporaryImages`에 `{ uploadToken, fileName }` session 목록을 포함한다. 두 목록은 빈 목록일 수 있다.
  - 저장 성공 시 HTML/JSON의 이미지 URL을 위 GET 경로로 rewrite하고, request token을 검증한다. 같은 owner 기존 이미지 참조는 보존하고 제거된 기존 이미지는 공통 cleanup에 전달한다.

- [x] **Step 2: DB 변경 전제와 현재 검증 한계를 기록한다**

  변경이 예정된 테이블/컬럼은 없다. 현재 도구에 `s-erp-postgresql-readonly`가 제공되지 않으므로 live MCP 조회는 수행할 수 없다. 기존 `CommonFile_SQL_postgresql.xml`, 날짜별 common-file schema history, 공통 processor/storage 구현과 테스트를 계약 확인 근거로 사용하고, 구현 중 스키마 변경이 필요하면 별도 작업으로 중단한다.

  공통 `EmbeddedImageDocumentProcessor`와 mocked `EmbeddedImageStorageService`를 사용해 테스트한다.

  - Create: insert로 발급된 approval ID를 processor owner ID로 사용하고, rewritten HTML/JSON을 해당 draft의 update params에 기록한다.
  - Update: owner type `APPROVAL` 및 기존 approval ID로 이미지를 처리한다.

  테스트 문서 JSON은 upload token을 가진 Tiptap image node로 구성한다. storage promotion fixture는 tenant, owner type/id, fileId, object key, filename을 반환한다.

  `DocumentApprovalEmbeddedImageVO`에 아래 필드를 둔다: `uploadToken`, `fileName`, `imageUrl`, `fileId`, `objectKey`, `fileSize`, `mimeType`, `width`. `DocumentApprovalDraftSaveRequestVO`에는 `List<DocumentApprovalEmbeddedImageVO> embeddedImages`와 `List<DocumentApprovalEmbeddedImageVO> temporaryImages`를 추가한다. image attributes가 없는 기존 request는 빈 목록으로 처리한다.

- [x] **Step 3: processor 입력 변환 및 stable URL resolver를 추가한다**

  승인 서비스는 domain DTO를 `EmbeddedImageUploadVO`로 변환한다. 공통 processor 호출은 tenant, `APPROVAL`, approval ID, request HTML/JSON, referenced metadata, temporary session, 인증 user ID와 approval stable URL resolver를 사용한다. Resolver는 `/api/v1/groupware/approvals/{approvalId}/embedded-images/{fileId}` 형태만 생성하고 approval 경로가 아닌 내부 API image URL은 거부한다.

- [x] **Step 4: create/update 저장 순서를 processor 기준으로 바꾼다**

  Create는 기존 insert가 발급한 ID로 processor를 실행한 다음 rewritten HTML/JSON/text를 `updateDocumentApprovalMain`으로 저장한다. Update는 owner 검증 뒤 processor 결과를 main update params에 담는다. 기존 transaction 안에서 결재선 교체와 SYSTEM 이벤트 추가를 유지하고, 저장 완료 뒤 `completeOwnerSave`를 호출한다. 기존 첨부 API는 수정하지 않는다.

  결과 문서에 원인(공유 에디터 adapter 누락), 해결 경로, API 계약, DB MCP 접근 여부와 대체 증거, 테스트/build/lint 결과, viewport 측정값, 캡처 링크, 미해결 제한사항을 기록한다. `git diff --check`와 `git status --short`로 변경 무결성을 확인한다.

## 위험 및 대응

- Create draft는 approval ID를 얻은 뒤 stable URL을 생성할 수 있으므로 insert 뒤 같은 트랜잭션에서 rewritten content update를 수행한다. 후속 update 실패 시 DB rollback과 common storage의 rollback cleanup이 실행되는지 테스트한다.
- 업로드가 완료되기 전에 저장하지 못하게 하고, upload error는 눈에 보이게 유지해 임시 URL이 본문에 저장되는 일을 막는다.
- URL resolver는 다른 internal API owner 경로를 승인 이미지로 취급하지 않는다. 이미지 read endpoint는 draft owner/tenant/file owner를 함께 확인한다.
- 공통 editor API나 notice/form 저장 경로를 변경하지 않는다.
