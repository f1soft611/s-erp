# 출하 용어 변경 및 출하계획 편집 계획서

## 목표

영업 업무 화면의 납품 용어를 출하로 통일하고, AUTO 테넌트에서도 자동 생성된 출하계획을 조회·편집하며 수주 수정이 사용자가 편집한 기존 계획을 덮어쓰지 않도록 한다.

## 구현 순서

1. **AUTO 계획 회귀 테스트 우선 작성**: 계획 조회/수정 모드 권한, source 주문 모드 필터, AUTO 수주 수정 시 계획값 보존, 수주수량 축소 제한을 실패 테스트로 고정한다.
2. **백엔드 계약 확장**: 인증 tenant 범위의 order-to-plan 조회 API를 추가하고, 계획 GET/status/PUT를 AUTO/MANUAL 모두 허용하되 POST 생성은 MANUAL로 제한한다. AUTO 수주 수정은 기존 계획행 값을 보존하고 신규 상세에만 초기 계획을 추가한다.
3. **프론트 계획 편집 연결**: AUTO 계획등록에서 기존 계획이 있는 수주만 선택할 수 있게 하며 선택 시 계획 ID·번호·상세 ID/일자/수량을 로드하고 PUT으로 저장한다. MANUAL 신규 POST 및 기존 수정 동작은 유지한다.
4. **용어 정리**: 납품등록/현황과 계획 화면, 정책 도움말, API 오류·성공 문구를 출하 용어로 변경한다. 기존 page key, 메뉴 코드/URL, API 필드/경로, DB와 정책 코드는 유지한다.
5. **표시 데이터 migration**: 메뉴와 시스템 기본 정책의 표시명/설명만 변경하는 날짜별 SQL 및 조건부 rollback을 작성하고 docs/backend 사본을 동일하게 둔다. 실제 DB에는 적용하지 않는다.
6. **검증 및 결과 문서화**: 관련 Maven/Vitest/build/lint, SQL 계약 테스트, 375/768/1280px 브라우저 확인과 캡처를 수행하고 결과서를 작성한다.

## 핵심 검증 항목

- AUTO는 기존 계획 조회·수정 허용, 수동 신규 생성 거부.
- MANUAL은 미계획 수주 신규 계획 등록 및 계획 조회·수정 허용.
- AUTO 계획 편집 후 수주 수정 시 기존 계획일/계획수량 보존.
- 신규 수주 상세는 현재 fallback 일자와 주문수량으로 계획 생성.
- 계획합 미만으로 수주수량을 줄이는 요청은 기존 업무 데이터 수정 전에 HTTP 409로 거부.
- 기존 tenant/수주/계획/출하 참조, delivered quantity, 잠금순서, 권한 및 직납품 동작 보존.
- 메뉴/정책 migration은 명칭/설명만 변경하고 값/권한/키/버전을 건드리지 않으며, rollback은 운영자 후속 편집을 덮어쓰지 않는다.
- 브라우저 모바일/태블릿/데스크톱에서 레이아웃 및 출하 명칭 표시를 확인한다.

## 제외

- API/DB/메뉴 코드/URL/정책 코드 이름 변경.
- 새로운 정책 값/테이블/컬럼 도입.
- 실제 데이터베이스에 SQL 실행.
- 재고·회계·세금계산서 등 주변 업무 연동.
