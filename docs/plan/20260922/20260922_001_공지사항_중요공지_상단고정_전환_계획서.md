# 20260922_001 공지사항 중요 공지 기능 상단 고정 전환 계획서

## 1. 목표

기존 공지사항의 `isNotice`/`is_notice` 기반 중요 공지 기능을 제거하고 `isPinned`/`is_pinned` 기반 상단 고정 기능으로 전환한다. 작성·수정 모달에는 고정 입력을 제공하지 않고, 게시글 더보기 옆 아이콘으로만 고정·해제를 수행한다. 일반 피드는 20건 단위 무한 스크롤로 과거 게시글을 누적하고, 상단 고정 영역은 같은 목록 API를 별도 조건으로 조회해 일반 피드와 중복 표시할 수 있도록 한다.

## 2. 작업 분류 및 범위

- 분류: `bounded`
- 대상: 프론트엔드, 백엔드, DB 계약
- 화면: `/groupware/community/notice`
- API: 기존 공지 목록/저장/수정 계약을 `isPinned`로 변경
- 페이징: 첨부 SHMT-MES의 `ComDefaultVO` + `PaginationInfo` 인덱스 계산과 `ListResult<T>` 목록/총 건수 응답 패턴을 적용
- 공지 API 공통 규칙: 공지 도메인의 모든 목록·검색·댓글 등 페이징 API는 동일한 `ComDefaultVO` + `PaginationInfo` + 목록/count 응답 패턴을 사용한다. 상세·단건 API는 페이징 대상에서 제외한다.
- DB: `tb_board_post.is_notice`를 `is_pinned`로 변경
- 페이지 조회: 일반 피드와 상단 고정 영역을 별도 요청
- 범위 제외: 다른 게시판 확장, 고정 순서·예약 고정, 보기 모드 영구 저장

## 3. 작업 분해

### 3.1 DB 및 백엔드 계약

- `tb_board_post.is_notice` 컬럼을 `is_pinned`로 변경해 기존 `Y/N` 상태를 보존한다.
- 공지 검색 VO는 `ComDefaultVO`를 상속하고 공통 `EgovPaginationSupport`가 레거시와 동일한 `PaginationInfo` 코드로 `firstIndex`, `lastIndex`, `recordCountPerPage`를 계산한다.
- 목록 Controller는 `@ModelAttribute` 검색 VO를 받고 `pageIndex`, `pageUnit`, `pageSize` 공통 필드를 사용한다.
- 백엔드 Request/Response VO의 `isNotice`를 `isPinned`로 변경한다.
- 목록 Controller/Service/Mapper의 선택 필터를 `isPinned`로 변경한다.
- 목록 응답에 `resultCnt`를 추가해 일반 목록과 상단 고정 목록의 전체 개수를 구분한다.
- 일반 목록은 `created_at DESC, post_id DESC`로 정렬하고, 고정 여부 때문에 피드 맨 위로 이동시키지 않는다. 고정 게시글은 별도 상단 고정 영역에서 표시한다.
- 기존 게시글 수정 API를 활용해 더보기 아이콘의 최소 고정 토글 payload를 처리한다.

### 3.2 프론트엔드 조회 상태

- 일반 피드 상태와 상단 고정 상태를 별도로 둔다.
- 일반 피드는 `page=1,size=20`으로 시작하고, 목록 끝에서 다음 페이지를 요청해 결과를 누적한다.
- 상단 고정은 `isPinned=Y` 조건으로 별도 조회하며 별도 `totalCount`를 카운터에 사용한다.
- 검색·구분 필터 변경·새로고침·재시도 시 일반 누적 페이지와 고정 조회 결과를 초기화한다.
- 추가 조회 중 요청 중복, 최신 필터와 이전 응답 혼입, 더 이상 조회할 데이터가 없는 상태를 관리한다.

### 3.3 화면 및 액션

- 작성/수정 모달에서 `중요 공지` 체크박스를 제거하고 `상단 고정` 체크박스도 제공하지 않는다.
- 중요 공지 필터, 중요 공지 색상, 중요 공지 요약을 제거한다.
- 게시글 더보기 옆에 고정/해제 아이콘을 표시한다.
- 고정 성공 후 일반 목록과 상단 고정 목록을 재조회하고 카운터를 갱신한다.
- 상단 고정 영역에는 별도 조회된 고정 게시글만 표시하며 일반 피드와 같은 게시글이 함께 나타날 수 있다.
- 기존 피드형·리스트형 보기, 상세·댓글·첨부·삭제·수정 흐름은 유지한다.

### 3.4 테스트 및 문서

- 백엔드 목록 필터, totalCount, VO/Mapper 계약 테스트를 추가 또는 갱신한다.
- 프론트 서비스의 `isPinned` query/payload, 일반 무한 스크롤, 상단 고정 별도 조회, 토글 액션 테스트를 추가한다.
- 중요 공지 문구·필터·색상·모달 체크박스 제거 회귀를 검증한다.
- 결과 문서와 375px·768px·1280px 브라우저 캡처를 작성한다.

## 4. 영향 범위

- Frontend: `CommunityNoticePage`, `NoticeComposerDialog`, 공지 데이터/서비스/어댑터, 더보기 메뉴 및 공통 고정 영역, 관련 Vitest
- Backend: 공지 Controller, Service, Request/Response VO, PostgreSQL Mapper, 서비스/컨트롤러 테스트
- Database: `tb_board_post.is_notice` 컬럼명 변경, 스키마 누적 문서, 변경/rollback 스크립트
- 문서: 기존 `isNotice` 의미를 중요 공지로 설명하는 관련 공지 문서 갱신
- 유지 규칙: 향후 공지 도메인에 추가되는 페이징 목록 API도 같은 공통 계약을 사용한다.

## 5. 검증 계획

- 백엔드: `cd backend; mvn test` 및 공지 관련 지정 테스트
- 프론트: 공지 관련 Vitest, `cd frontend; npm run build`, 전체 테스트
- 브라우저: 375px·768px·1280px에서 무한 스크롤, 상단 고정 영역, 더보기 아이콘, 중복 표시, 겹침·잘림·가로 스크롤을 확인
- DB: migration SQL은 `is_notice` 값 보존과 `is_pinned` 계약을 확인하고 rollback은 원래 컬럼명 복구를 확인

## 6. 완료 조건

- 코드와 API/DB 문서에서 공지 상태 계약이 `isPinned`/`is_pinned`로 통일된다.
- 작성/수정 모달에 고정 체크박스가 없고 더보기 옆 아이콘으로만 고정/해제가 가능하다.
- 일반 피드는 20건씩 끝에서 추가 조회되고 중복 요청 없이 누적된다.
- 상단 고정 목록은 별도 조회·카운트로 표시되고 일반 피드와의 중복이 허용된다.
- resultCnt가 일반 목록과 상단 고정 목록에 맞게 계산된다.
- 관련 테스트·빌드·브라우저 검증 및 결과 문서가 남는다.
