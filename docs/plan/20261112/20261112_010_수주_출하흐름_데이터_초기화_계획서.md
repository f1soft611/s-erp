# 수주·출하 흐름 데이터 초기화 계획서

## 목표

지정한 테넌트의 수주·출하계획·출하등록 흐름을 안전하게 초기화하여 다시 등록할 수 있는 PostgreSQL 스크립트를 제공한다.

## 근거 문서

- 작업지시서: [20261112_010 수주·출하 흐름 데이터 초기화 작업지시서](../../directions/20261112/20261112_010_수주_출하흐름_데이터_초기화_작업지시서.md)
- 승인 설계: [Sales Order and Delivery Data Reset Design](../../superpowers/specs/2026-11-12-sales-order-delivery-reset-design.md)

## 파일 구조

- `docs/spec/20261112/20261112_010_수주_출하흐름_데이터_초기화_상세사양서.md`: 초기화 범위, 테이블 관계, 삭제 순서 및 실행 안전 계약.
- `docs/database/20261112/20261112_010_reset_sales_order_delivery_flow.sql`: 운영자가 tenant ID를 지정해 실행할 SQL.
- `backend/DATABASE/20261112/20261112_010_reset_sales_order_delivery_flow.sql`: 위 SQL과 동일한 사본.
- `docs/database/20261112/20261112_010_change_sales_order_delivery_flow_reset.md` 및 `backend/DATABASE` 동일 사본: 삭제 범위와 되돌리기 한계를 기록하며, 스키마 변경이 없음을 명시.
- `docs/result/20261112/sales-flow-data-reset/20261112_010_수주_출하흐름_초기화_작업결과.md`: 변경 파일, MCP 메타데이터 근거, 검증 및 미적용 상태 기록.

스키마는 변경하지 않으므로 `docs/database/db-schema.md` 수정 및 스키마 롤백 스크립트는 만들지 않는다. 삭제 SQL은 기본 롤백 상태로 제공하고, 삭제 건수 검토 후 운영자가 커밋 절차를 명시적으로 바꿔 실행한다. 커밋 후 데이터 복구는 백업에서만 가능하다.

## 작업 순서

1. 작업지시서와 승인 설계를 바탕으로 상세사양서를 기록한다.
2. 확인된 FK를 기준으로 tenant ID 필수 입력, 삭제 대상 산정, 자식-부모 순서를 명세한다.
3. 트랜잭션 기본 롤백, 대상 테넌트 검증, 영향 행 수 출력, 참조 데이터 보호를 포함한 PostgreSQL SQL을 작성한다.
4. SQL 및 설명 문서를 두 데이터베이스 이력 위치에 바이트 동일하게 둔다.
5. 삭제 범위·순서·조건을 정적 검토하고, 두 사본 해시 및 `git diff --check`를 확인한다.
6. 결과 문서에 실행 전 백업 권고, 커밋 후 복구 한계, DB 미적용 사실을 기록한다.

## 검증 기준

- 모든 대상 테이블의 DELETE 경로가 `tenant_id`로 제한된다.
- 구매요청 연결은 `sales_order_id`와 `sales_order_detail_id` 두 참조를 모두 기준으로 찾는다.
- 삭제 순서는 거래명세서 상세/헤더 → 출하 상세/헤더 → 계획 상세/헤더 → 구매요청 문서/고아 구매확정 헤더 → 수주 헤더 순서다.
- 거래처/품목/창고/테넌트 및 타 테넌트의 행은 삭제되지 않는다.
- 존재하지 않거나 비양수인 tenant ID는 삭제 전에 실패한다.
- PK/문서번호 시퀀스는 수정하지 않는다.
- 전방 SQL의 두 사본 및 변경기록의 두 사본이 일치한다.
- DB MCP는 스키마 메타데이터만 확인했으며, 업무 데이터 조회와 스크립트 적용을 수행하지 않는다.
