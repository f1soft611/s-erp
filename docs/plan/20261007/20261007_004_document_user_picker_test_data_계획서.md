# 20261007_004 문서작성 사용자 선택 테스트 데이터 계획서

## 목표

현재 사용자 선택기 쿼리 계약을 만족하는 테스트 사용자 10명을 제공하는 안전한 데이터 시드와 롤백을 작성한다.

## 근거 문서

- 작업지시서: [20261007_004 문서작성 사용자 선택 테스트 데이터](../../directions/20261007/20261007_004_document_user_picker_test_data_작업지시서.md)
- 설계 사양: [Document User Picker Test Seed Design](../../superpowers/specs/2026-10-07-document-user-picker-seed-design.md)

## 변경 범위

- `docs/database/20261007` 및 `backend/DATABASE/20261007`에 동일한 시드, 롤백, 변경 이력 파일을 추가한다.
- 스키마와 프론트엔드/백엔드 동작 코드는 수정하지 않는다.
- 읽기 전용 MCP를 통한 스키마 메타데이터 확인은 수행했지만 제한된 집계 조회가 `Database request failed`로 실패했다. 테이블 생성 스크립트, 사용자 선택 Mapper SQL, 성공한 테이블 메타데이터를 대체 근거로 사용한다.
- MCP를 통해 데이터 쓰기나 DDL을 실행하지 않는다.

## 실행 순서

1. `DraftingWork_SQL_postgresql.xml`의 사용자 조회가 `tb_user`와 활성 `tb_login_account`를 같은 테넌트/로그인 ID로 내부 조인한다는 점을 반영한다.
2. 활성 계정 연결 사용자 중 가장 이른 `user_id`를 기준 프로필로 선택하고, 같은 테넌트/로그인 ID/부서/직급을 갖는 활성 테스트 프로필 10개를 추가한다.
3. 테스트 이메일의 `(tenant_id, email_addr)` 유일 충돌은 건너뛰어 재실행을 안전하게 한다. 기준 프로필이 없으면 SQL 예외로 중단한다.
4. 롤백은 10개 이름/이메일이 일치하고 기준 테넌트에 속한 행만 삭제한다.
5. `docs/database`와 `backend/DATABASE`의 세 파일을 비교해 동일성을 확인한다.
6. 사용자 데이터는 읽기 전용 MCP로 확인할 수 없으므로 수동 적용 여부와 화면 검증 여부를 결과 문서에서 분리해 기록한다.

## 검증 기준

- 응답과 프론트엔드 선택값이 `user_id`를 사용하므로 공유 `login_id`가 열 개의 서로 다른 프로필을 합치지 않는지 확인한다. 데이터는 선택기 UI 테스트에만 사용한다.
- 시드에 서로 다른 테스트 이름과 `.invalid` 이메일이 정확히 10쌍 있다.
- 시드가 `tb_user`만 삽입하고 기존 활성 `tb_login_account`의 동일 테넌트 및 로그인 ID를 참조한다.
- `use_at = 'Y'`이며 사용자 ID는 기존 identity 기본값으로 생성된다.
- 동일 SQL 재실행 시 같은 테넌트의 테스트 이메일에 중복 행이 생기지 않는다.
- 롤백은 테스트 이름과 이메일, 테넌트 조건을 모두 사용한다.
- 양쪽 SQL/변경 이력 파일의 내용이 일치한다.
- DB에 미적용이면 선택기에서의 실제 조회는 미검증으로 명시한다.
