# 20261120_010 인사명령 계획서

기준: [작업지시서](../../directions/20261120/20261120_010_hr-order_작업지시서.md)

## 구현 단위
1. **DB**(`20261120_006`): `tb_hr_order_hd`(명령 건)·`tb_hr_order_dt`(사원별 변경항목 명령 전/후) 생성, 메뉴 `HR_INFO_ORDER`(인사정보 > 인사명령) 등록과 권한. 날짜별 SQL·롤백·이력, `db-schema.md`.
2. **백엔드**(`let/hr/order`, 사원 서비스 연동):
   - 명령 유형 정의(상수), 발령 처리 서비스(대상별로 `EmployeeService.updateEmployee`를 호출하고 이력을 기록, 한 트랜잭션), 이력 조회.
   - 사원 서비스에 **이력 기록 연결**: 수정 시 추적 항목 변경분, 신규 등록 시 입사 이력.
3. **프론트**(`pages/hr/order`): 인사명령 페이지(탭 2개), 처리 탭(명령 입력 줄, 대상 사원 표, 발령 처리), 처리 내역 탭(조회조건·표). 라우팅 연결, 사원 선택 도움창(다중) 재사용.
4. **검증·문서**: 단위·통합 테스트, 실서버·브라우저, 결과 문서.

## 위험·결정 사항
- 부서·직위·입사일이 비어 있는 기존 사원 10명은 사원 서비스의 필수값 검증에 걸려 발령 대상이 될 수 없다(먼저 사원관리에서 채움). 오류 메시지에 사원명을 붙여 안내한다.
- 휴직은 새 휴직일을 쓰며 이전 복직일을 비운다(재휴직 시 재직 상태 계산 오류 방지). 이력에도 복직일 비움이 같이 남는다.
- 직접 수정과 명령 처리가 같은 경로라 이력이 중복되지 않는다(명령 처리는 출처 `ORDER`, 직접 수정은 `DIRECT`).
- DB 컬럼명·API 경로는 모듈 접두어 규칙(`tb_hr_...`, `/api/v1/hr/...`)을 따른다.
