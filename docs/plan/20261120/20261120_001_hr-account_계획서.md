# 20261120_001 인사관리 2-2단계 계정관리 계획서

기준: [작업지시서](../../directions/20261120/20261120_001_hr-account_작업지시서.md)

## 구현 단위
각 단계는 테스트를 먼저 쓰고 단계가 끝날 때 관련 단위 테스트와 `tsc`만 돌린다. 실서버·브라우저·전체 테스트는 마지막에 한 번 한다.

1. **DB**: `20261120_001` 계정 컬럼 추가(변경 강제 플래그·수정자)와 메뉴·권한, `20261120_002` 정책 시드(잠금 사용·기준 횟수, 사진 정책)와 사진 보정. 롤백·변경 이력·`db-schema.md`.
2. **A 계정 관리**: 백엔드 `let/system/accounts`(목록, 허용/미허용, 비밀번호 초기화, 역할 지정, 잠금 해제), 프론트 `pages/settings/system/accounts`, 퇴사자 로그인 차단(로그인·갱신 쿼리 공통).
3. **잠금 정책**: 정책값 읽기 메서드, 로그인 서비스의 실패 누적·잠금·해제, 잠금 상태 표시.
4. **B 변경 강제**: 로그인 응답·토큰에 변경 필요 표시, 변경 외 API 차단 필터, 변경 시 새 토큰 발급, 프론트 강제 변경 화면.
5. **C 사진·내 정보**: 사진 정책 적용, 내 정보 사진 변경 시 사원 마스터 동기화, 내 정보 화면에 사번·직위 표시.
6. **검증·문서**: 테스트, 실서버·브라우저, 결과 문서·스크린샷.

## 순서와 이유
- 계정 목록을 먼저 만들어야 이후 단계(잠금·변경 강제)의 상태 표시가 같은 화면에 붙는다.
- 잠금과 변경 강제는 둘 다 인증 흐름을 바꾸므로 서로 섞이지 않게 따로 구현하고 각각 로그인 테스트를 붙인다.
- DB 적용은 사용자가 하므로 스크립트는 코드 작업 전에 만들고, 적용 요청은 각 단계 코드가 끝난 뒤에 한다.

## 위험과 대응
- **로그인은 모든 사용자에게 영향**을 준다. 잠금 정책은 기본 미사용이고, 정책값을 못 읽거나 행이 없으면 미사용으로 동작해 시드 누락이 안전하다.
- **기존 계정 보호**: `password_changed_at` 비어 있는 계정이 2건이라 변경 강제는 새 플래그(`password_change_required`, 기본 N)로만 판단한다. 관리자 초기화와 사원등록 발급 때만 Y로 둔다.
- **자기 잠금 방지**: 자기 계정 미허용·마지막 테넌트 관리자 권한 제거는 서버가 막는다. 역할이 없으면 로그인 쿼리가 계정을 찾지 못하므로 역할 0개로 저장하지 못하게 한다.
- **퇴사자 차단**은 저장 상태가 아니라 `retire_dt`로 계산해 로그인·토큰 갱신에서 걸러 낸다. 퇴직일을 지우면 자동으로 풀리고 배치가 필요 없다. 현재 퇴직일이 지난 계정 2건이 영향을 받는다.
- **변경 강제 차단 필터**는 정상 사용자 요청을 잘못 막을 수 있어 허용 경로(비밀번호 변경, 로그아웃, 토큰 갱신)를 테스트로 고정한다.
- 임시 비밀번호는 응답에 한 번만 담고 서버 로그·감사 문서에 남기지 않는다.
