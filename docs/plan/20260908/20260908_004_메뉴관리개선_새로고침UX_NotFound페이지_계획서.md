## 요구사항 분석 및 목적

1. `MenuManagementPage`는 모듈만 선택해도 메뉴 조회/저장이 가능해 권한(Role) 컨텍스트 없이 메뉴/버튼 권한이 저장될 수 있다. 권한 관리 페이지처럼 스켈레톤 로딩도 없다.
2. `DashboardPage`는 `fetchMyMenus()` 응답을 기다리는 짧은 시간 동안 실제로는 로딩 중임에도 "접근 가능한 메뉴가 없습니다"를 보여줘 사용자가 오해할 수 있다.
3. `AppRouter`는 정의되지 않은 모든 경로를 `/dashboard` 또는 `/login`으로 리다이렉트해 실제 404 상황을 사용자가 인지할 수 없다.

목적은 프론트엔드 UX 일관성 확보와 오동작(권한 미지정 저장) 방지이며, 백엔드 API/DB 변경은 없다.

## 작업 범위 분해 (프론트엔드 전용)

### A. 메뉴관리 검색조건 필수화 + 스켈레톤

- 대상 파일:
  - [frontend/src/pages/settings/system/menus/MenuManagementPage.tsx](../../../frontend/src/pages/settings/system/menus/MenuManagementPage.tsx)
  - [frontend/src/pages/settings/system/menus/components/MenuManagementPanel.tsx](../../../frontend/src/pages/settings/system/menus/components/MenuManagementPanel.tsx)
- 변경 내용:
  - `selectedRoleId`가 빈 문자열이면 `loadMenus` 호출을 막고 안내 문구 상태를 노출한다.
  - `MenuManagementPanel`에 `menuGridLoading` prop을 추가하고 `F1Tree`의 `loading` prop(RoleManagementPanel의 `F1Grid loading` 패턴과 동일, F1Tree가 F1Grid props를 그대로 전달하므로 `GridLoadingSkeleton`이 자동 적용됨)으로 연결한다.
  - `MenuManagementPage`의 저장(`write`) 액션은 모듈/권한이 모두 선택된 경우에만 활성화되도록 `disabled` 조건에 `!selectedModuleId || !selectedRoleId`를 추가한다.
  - 모듈/권한 중 하나라도 비어있을 때 트리 대신 안내 메시지(`PageMessageArea` 또는 별도 안내 Box)를 표시한다.

### B. 새로고침 시 메뉴없음 UX 개선

- 대상 파일: [frontend/src/pages/dashboard/DashboardPage.tsx](../../../frontend/src/pages/dashboard/DashboardPage.tsx)
- 변경 내용:
  - `menusLoading` state(초기값 `true`)를 추가하고 `fetchMyMenus`/`fetchModuleRows` 완료 시 `false`로 변경한다.
  - 렌더링 분기를 `menusLoading` → 로딩 스피너/스켈레톤, `!menusLoading && !hasAccessibleMenu` → 기존 안내 문구, 그 외 → 기존 대시보드 콘텐츠 3단 분기로 변경한다.
  - 기존 인증/라우팅/모듈 계산 로직은 변경하지 않는다.

### C. NotFound 페이지 추가

- 신규 파일: `frontend/src/pages/errors/NotFoundPage.tsx`
- 대상 파일: [frontend/src/routes/AppRouter.tsx](../../../frontend/src/routes/AppRouter.tsx)
- 변경 내용:
  - 첨부 디자인을 반영한 `NotFoundPage` 컴포넌트를 작성한다(제목, 안내문, 돌아가기 버튼, 하단 카피라이트).
  - catch-all 라우트(`path="*"`)의 `element`를 `<NotFoundPage />`로 교체한다(리다이렉트 제거).
  - "돌아가기" 버튼 클릭 시 `isAuthenticated()` 여부에 따라 `/dashboard` 또는 `/login`으로 `navigate`한다.

## 영향 범위 검토

- 메뉴관리 변경은 `MenuManagementPage`/`MenuManagementPanel` 내부에 한정되며 API 계약(`fetchMenuRows`, `saveMenuChanges` 등)은 변경하지 않는다.
- 대시보드 변경은 렌더링 분기만 추가하며 기존 `moduleItems`, 라우팅, 메뉴 트리 구조는 그대로 유지한다.
- 라우터 변경은 `path="*"`의 리다이렉트 동작을 제거하는 것이므로, 기존에 이 경로를 의도적으로 사용하던 곳이 있는지 확인이 필요하다 (검토 결과: 별도 사용처 없음, 단순 fallback).
- 백엔드/DB 변경 없음.

## 검증 계획

- Vitest:
  - 메뉴관리: 모듈만 선택/권한만 선택 시 조회 API 미호출 및 안내 문구 노출, 모듈+권한 선택 시 스켈레톤 노출 후 정상 조회를 검증하는 테스트 추가.
  - 대시보드: 메뉴 로딩 중 스피너/스켈레톤 노출, 로딩 완료 후 메뉴 0건일 때만 안내 문구 노출을 검증하는 테스트 추가.
  - 라우터: 정의되지 않은 경로 접속 시 `NotFoundPage`가 렌더링되고, 버튼 클릭 시 인증 상태별 이동 경로를 검증하는 테스트 추가.
- Playwright(UI 캡처): 메뉴관리 필수 안내 문구, 대시보드 새로고침 스피너, NotFound 페이지 스크린샷을 `docs/result/20260908/<work-slug>/screenshots`에 저장한다.
- 명령: `npm run test`, 필요 시 `npm run test -- tests/<file>.test.tsx`.
