# 공통 기능 후속 확장 로드맵

근거: [작업지시서](../../directions/20261102/20261102_007_공통기능_후속확장_작업지시서.md).

## 확정 순서

1. **알림·쪽지 실시간 갱신** — 구현 완료. [결과·검증·운영 제약](../../result/20261102/notification-message-realtime/README.md).
2. **웹 푸시** — 1단계 완료 후 설계.
3. **업무 알림 확대** — 2단계 완료 후 대상 이벤트/수신자 합의.
4. **통합검색 대상 확대** — 3단계 완료 후 대상 업무/권한 합의.

이 문서는 순서와 단계 경계를 기록하는 로드맵이며, 각 단계의 상세 구현을 일괄 승인하는 사양이 아니다.

## 1단계 착수 당시 현황

- 헤더 알림/쪽지 배지는 최초 진입·화면 복귀 및 일부 로컬 읽음 이벤트로 갱신된다.
- 쪽지함은 visibilitychange/focus 시 목록과 선택 대화를 조용히 갱신한다.
- 현재 확인한 서버 Java 코드에는 SSE/WebSocket 전송 기반이 없다.
- API 클라이언트는 Authorization 헤더 기반이다. SSE 도입 시 기본 EventSource 대신 헤더 인증을 지원하는 전송 방법과 토큰 갱신 처리가 필요하다. 토큰을 URL에 넣지 않는다.

## 방식 비교 및 권장안

| 방식 | 장점 | 제약 |
|---|---|---|
| 주기 조회 | 기존 인증/API 재사용, 서버 변경 최소 | 주기만큼 지연, 사용자/탭 수에 따라 반복 조회 증가 |
| SSE | 서버 단방향 변경 신호에 적합, 이벤트 직후 갱신 | 연결 인증·재연결·heartbeat·프록시 및 다중 서버 전달 경계 필요 |
| WebSocket | 양방향 통신 확장 가능 | 현재 변경 알림 목적에는 연결/프로토콜 관리 범위가 큼 |

**권장: SSE 변경 신호 + 기존 REST 재조회.** 실시간 채널은 알림/쪽지 본문을 보내지 않고 변경 종류만 전달하며, 실제 목록/건수/대화는 기존 권한 API로 재조회한다. 웹 푸시의 브라우저 구독과는 분리한다.

1단계 전용 계획/사양에 반영한 항목:

- tenant/user별 인증된 구독, 로그아웃/계정 전환/만료 시 연결 정리.
- 저장 트랜잭션 성공 후에만 변경 신호 발행. 읽음·숨김·보관에 의한 건수 변경도 구분.
- 여러 수신 이벤트의 병합 재조회와 요청 경쟁 방지. 오류 시 기존 화면/작성 중 입력 유지.
- 재연결 후 기존 REST로 상태 재동기화. 연결 종료/heartbeat 및 retry 지연.
- 열린 알림 목록과 쪽지함/선택 대화만 필요한 조회 수행. 과거 메시지/스크롤/미전송 입력 보존.
- 단일 서버/다중 서버 배포 지원 범위 확인. 다중 서버에서 프로세스 메모리 연결만으로 전체 전달이 된다고 가정하지 않는다.
- 수신자 격리, rollback 비전송, 중복/재연결, 읽음 동기화 및 실제 두 사용자 흐름 검증.

## 후속 단계 착수 조건

1단계의 결과 문서/검증을 완료한 뒤 웹 푸시의 HTTPS·Service Worker·운영 키 관리·사용자 동의·기기별 구독 저장 정책을 설계한다. 이후 업무 알림과 검색은 대상을 명시적으로 확정한 단위로 확장한다.
