# 20261008_003 문서 결재 저장 스키마 계획서

## 목표

승인된 저장 구조 설계를 S-ERP의 날짜별 요구사항 문서, PostgreSQL forward/rollback 초안, 누적 스키마 및 검토 결과 문서로 남긴다.

## 작업 단계

### 1. 실제 계약 확인과 상세 사양 확정

- 문서작성 화면에서 제목, 본문, 양식, 결재 단계, 참조자 필드와 값 타입을 확인한다.
- `LoginVO.id`와 `tenantId`, 공통 댓글의 키 및 기존 soft-delete/수정 계약을 확인한다.
- 데이터베이스 MCP 메타데이터 확인 이력과 저장소 스키마/매퍼 근거를 구분해 기록한다. 현재 실행 맥락에서 MCP 도구를 사용할 수 없으면 그 사실과 대체 근거를 결과 문서에 명시한다.
- 테이블, 컬럼, 코드, null 규칙, FK/unique/check/index, 삭제 정책 및 마이그레이션 순서를 상세 사양에 고정한다.

### 2. 날짜별 요구사항 문서 작성

- 작업지시서에 승인 범위, 비목표, 완료 기준을 적는다.
- 계획서에 파일 범위와 순차 작업을 기록한다.
- 상세 사양서에 모든 DDL 계약과 후속 API 권한 요구사항을 적는다.

### 3. 스키마 forward/rollback 초안 작성

- `tb_electronic_approval_main` 및 `tb_electronic_approval_line_info`를 생성한다.
- `tb_common_comment`에 기본값 `USER`인 유형과 SYSTEM 이벤트 코드를 추가한다.
- 댓글 좋아요 관계 테이블을 만들고 tenant/comment/user 중복을 제한한다.
- 공통 댓글의 tenant/comment 복합키 제약을 추가해 좋아요의 tenant 일치 FK를 지원한다.
- rollback은 신규 좋아요 테이블, 이번에 추가한 댓글 제약/컬럼, 신규 결재 테이블만 되돌린다.

### 4. 스키마 참조 문서와 결과 기록

- backend와 docs 스키마 이력에 forward SQL, 변경 이력, rollback을 동일하게 보관한다.
- `docs/database/db-schema.md`에 변경된 테이블 구조를 반영한다.
- DDL 검토, 양쪽 사본 일치, diff 검증과 미적용 사실을 결과 문서에 기록한다.

## 검증 기준

1. 상세 사양과 forward SQL의 컬럼/코드/제약이 일치한다.
2. 모든 신규 객체와 변경 컬럼이 rollback에 정확히 대응한다.
3. docs/backend 이력 사본을 바이트 단위로 비교한다.
4. PostgreSQL 실행기가 있으면 격리된 로컬 환경에서만 구문 검증하고, 없으면 정적 검토로 제한한다.
5. `git diff --check`를 통과하고 작업 범위 밖의 변경이 없음을 확인한다.
6. 어떠한 공유/운영 DB에도 DDL을 실행하지 않는다.
