**Goal:** 문서작성 화면에서 초안을 저장하고 본문·결재선·시스템 저장 이력을 원자적으로 기록하며, 문서 권한을 확인하는 첨부 저장을 제공한다.

# 20261008_005 문서 임시저장 및 첨부 저장 계획서

## 목표

문서작성 화면의 명시적 임시저장을 실제 저장으로 연결하고, 본문·결재선·SYSTEM 저장 이력은 원자적으로 저장하며, 공지사항 작성과 동일한 첨부 UX를 결재 문서 권한 검증 아래에서 제공한다.

## 구조

- 백엔드의 결재 문서 서비스가 문서/결재선/System `DRAFT_SAVED` 기록을 한 트랜잭션으로 저장한다.
- 공통 댓글에 SYSTEM 이벤트를 기록하는 전용 DAO 경로를 두고, 일반 댓글 API는 SYSTEM 댓글을 수정·삭제·답글 대상으로 허용하지 않는다.
- 결재 전용 첨부 API가 문서 접근을 확인한 뒤 기존 `CommonFileService`에 `APPROVAL` 소유 유형으로 위임한다. 범용 파일 API로 권한 확인을 우회하지 못하게 한다.
- 프론트엔드는 현재 작성 중인 문서 ID를 보유해 재저장 시 같은 초안을 갱신하고, 첨부 업로드의 부분 실패를 성공 파일/실패 파일 단위로 보여주고 재시도한다.
- 초안 저장 후 발급된 문서 ID는 공통 다이얼로그의 제목 바로 아래 description 영역에 표시하고, 다이얼로그 본문에서는 중복 표시하지 않는다.
- 구현 전에 MCP로 실제 중앙 DB 제약 조회를 시도한다. 현재 세션에는 MCP 도구가 노출되지 않아 저장소 DDL을 대체 근거로 사용하고 실제 DB 미확인 상태를 기록한다. 저장소 DDL이 `DRAFT_SAVED`를 거부하므로 event constraint migration 초안은 작성하되 실행하지 않는다.

## 작업 단계

### 1. 실제 DB와 화면/인증 계약 확인

- 승인된 설계·작업지시서를 다시 대조하고 문서작성의 제목/본문/양식 ID/문서 유형/결재선 참여자 필드를 재확인한다.
- 읽기 전용 MCP의 `list_tables`/`describe_table`로 중앙 DB의 네 테이블과 `tb_common_comment` check 제약을 확인한다. `query_readonly`는 메타데이터만으로 컬럼 계약을 알 수 없을 때 비민감 `information_schema` 조회에 한정한다.
- 실제 컬럼과 저장소 SQL 이력을 비교해 이미 반영된 `comment_type`/`event_type`을 중복 migration하지 않는다.
- `LoginVO`에서 tenant/user identity를 확정하고, 첨부 정책은 공지사항 서비스의 검증과 `CommonFileService` 흐름에서 재사용 가능한 조건을 찾는다.
- MCP 도구/연결이 제공되지 않으면 데이터 행을 시도 조회하지 않는다. 대체 근거와 미확인 제약을 사양/결과 문서에 적고 구현 범위를 조정한다.

- 예외 케이스에서 DAO가 결재선/시스템 메시지 추가를 실패하면 예외를 전파하고 서비스 메서드에 `rollbackFor=Exception` 트랜잭션 경계가 있는지 검증한다.
- 잘못된 문서 유형, 공백 제목, tenant 밖/비활성 참여자, 중복 참여자, 요청 actor 위조를 거부하는 테스트를 추가한다.
- 새 테스트를 먼저 실행해 계약 미구현에 따른 실패를 확인한다.

### 3. 문서 저장 및 SYSTEM 이벤트 DAO/service/API 구현

- request VO에는 `documentType`, `draftingWorkCategoryId`, `title`, `contentsJson`, `contentsHtml`, `contentsText`, `approvalLines`를 두고 `tenantId`, `drafterId`, 작성자명, `eventType`은 클라이언트 입력으로 받지 않는다. 화면 참여자 `userId` 및 프로필 `employeeId`는 `tb_user.user_id`이며 `LoginVO.uniqId`와 일치한다. 감사 행위자와 문서 `drafter_id`는 기존 공통 API와 같이 로그인 코드인 `LoginVO.id`를 사용한다.
- approval line request 항목에는 `stageOrder`, `participantOrder`, `participantType`, `participantUserId`를 둔다. `participantName`과 부서명은 검증된 사용자 프로필에서 가져온다.
- 신규 문서는 `DRAFT`로 생성하고, 동일 tenant의 작성자 소유 `DRAFT` 문서만 update할 수 있도록 조건부 SQL을 사용한다.
- 서비스의 `@Transactional` 메서드에서 문서 생성/갱신 → 결재선 저장 → SYSTEM `DRAFT_SAVED` 댓글 삽입을 처리한다. 각 필수 DAO 변경 건수가 기대와 다르면 명시적 예외를 발생시킨다.
- SYSTEM 댓글 `content`는 서버가 관리하는 고정 문구를 사용한다. `owner_type='APPROVAL'`, `owner_id=전자결재 ID`, `comment_type='SYSTEM'`, `event_type='DRAFT_SAVED'`, `parent_comment_id=NULL`로 기록한다.
- API 응답은 최소한 `electronicApprovalId`와 `documentStatus='DRAFT'`를 반환한다. 서비스/컨트롤러 단위 테스트를 통과시킨다.

### 4. 일반 댓글 경로와 파일 권한 우회 차단

- 공통 댓글 mapper에 `comment_type`, `event_type` 조회 필드를 반영한다. 기존 일반 댓글 등록은 DB default `USER`를 유지한다.
- 일반 수정/삭제 SQL을 USER 행으로 제한하고, 서비스가 SYSTEM 행을 대댓글 부모로 받지 않도록 조회 결과 유형을 검증한다.
- 범용 댓글 목록/등록 API에서 `ownerType=APPROVAL`을 거부해 전자결재 문서 권한을 우회할 수 없게 한다.
- 회귀 테스트에서 일반 USER 댓글의 기존 등록/수정/soft-delete 동작은 유지되고, SYSTEM 댓글은 수정/삭제/답글 대상에서 거부되는지 확인한다.
- 결재 파일 목록/업로드/삭제/다운로드는 결재 전용 API에서 문서 소유권/접근권한을 검사하고 `CommonFileService`를 호출한다.
- 범용 `/common/files` API가 `ownerType=APPROVAL`로 우회 접근을 허용하지 않게 막고, owner 정보 없이 파일 ID만 전달하는 일반 다운로드/삭제도 `APPROVAL` 파일을 제외한다. 다른 owner type의 기존 동작은 변경하지 않는다.
- 파일 권한 테스트는 동일 tenant의 작성자와 권한 없는 사용자를 구분하고, tenant가 다른 문서/파일은 모두 거부되는지 검증한다.
- `CommonFileServiceImpl`에서 `tenant/ownerType/ownerId/originalName`을 MinIO object key로 직접 사용하지 않는다. 파일별 UUID 키를 사용하고, 메타데이터의 `fileName`은 사람이 올린 원래 표시 이름을 유지한다.
- `CommonFileServiceTest`에 동일 tenant/owner/name으로 파일 두 개 업로드 시 MinIO key가 다르고 각 DB 메타데이터가 해당 key를 보유하는 회귀 테스트를 먼저 추가한다. 공지·댓글 등 기존 owner type의 조회/다운로드 및 soft-delete 테스트도 그대로 통과해야 한다.
- storage/DAO 의존성이 없으면 MinIO 호출 전에 실패하는지 확인하고, 업로드 경로의 기존 storage-bucket 테스트는 실제 insert ID를 반환하는 DAO fixture를 사용하도록 정리한다. metadata insert가 null ID를 반환하거나 persisted row 확인이 실패하면 업로드한 해당 object key만 삭제하는 테스트를 추가한다. 삭제가 실패하는 경우에도 원래 metadata 예외가 최종 원인으로 유지되고 정리 실패가 로그/예외 보조정보로 관찰되는지 검증한다. metadata 저장 성공 객체나 동일 파일명의 다른 객체는 삭제하지 않는다.

### 5. 프론트 저장·첨부 UI 구현

- `documentApprovalService.ts`에서 API 오류를 누락하거나 성공 형태로 변환하지 않는다. 응답에 양수 문서 ID 또는 `fileId`가 없으면 실패로 처리한다.
- `useDocumentComposer`에 세션별 `electronicApprovalId`, 저장 진행 상태, 파일별 `pending/uploaded/failed/unknown` 상태를 둔다. 저장 중 중복 요청은 막고 첫 성공 후 문서 ID로 재저장한다.
- `DocumentComposerDialog`는 저장 전 description을 표시하지 않고, 저장 응답 후에는 공통 헤더 description으로 `임시저장 문서 ID`를 표시한다.
- 편집기 현재 JSON/HTML 및 plain text, 선택 양식 ID, 문서 유형, 단계 순서/사용자, 참조자, 작성 제목을 요청 DTO에 변환한다. actor ID/이름은 전송하지 않는다.
- 신규 파일은 문서 저장 응답 ID로 승인 전용 upload API에 업로드한다. 각 성공 응답의 ID를 상태에 보관하고 `failed` 파일만 개별 재업로드하며, `unknown` 결과는 목록 대조 전 자동 재업로드하지 않는다. 문서 ID가 발급된 뒤 재시도해도 신규 문서를 다시 만들지 않는다.
- `AttachmentList`를 `mode='edit'`로 사용해 공지사항과 동일한 파일 아이콘/목록/삭제 동작을 제공한다. 공지사항의 기존 test id와 동작은 유지한다.
- 저장 버튼은 전송 중 비활성/진행 상태를 보이고, DB 저장 실패와 첨부 부분 실패 메시지를 구분한다. 첨부가 모두 확인되기 전 성공 완료로 모달을 닫지 않는다.
- 프론트 테스트는 문서 DTO 변환, 저장 ID 유지, 첨부 성공/실패 파일 상태 보존, 재시도에서 중복 생성/기존 성공 파일 재업로드 없음, API 실패 시 입력 내용 보존을 확인한다.

### 6. 필요한 경우에 한해 DB migration과 문서 갱신

- 저장소 DDL의 정적 이벤트 목록을 USER/SYSTEM 조합 및 non-empty 조건은 유지하면서 `DRAFT_SAVED`까지 확장하는 migration 초안을 작성한다. 후속 이벤트를 이번 migration에 임의 추가하지 않는다.
- 이미 적용된 컬럼은 재생성하지 않는다. migration은 현재 DB와 저장소 이력에 실제 필요한 제약만 수정한다.
- 스크립트가 필요하면 `backend/DATABASE/20261008/`와 `docs/database/20261008/`에 같은 forward/change record/rollback을 두고 `docs/database/db-schema.md`를 갱신한다.
- 관련 SQL 사본을 바이트 비교하고 forward/rollback 대칭성을 확인한다. 스크립트를 실제 DB에 실행하지 않는다.

### 7. 회귀 검증 및 결과 기록

- 백엔드 대상 테스트: `cd backend; mvn "-Dtest=DocumentApprovalServiceImplTest,DocumentApprovalApiControllerTest,CommonCommentServiceTest,CommonFileServiceTest" test`
- 프론트엔드 대상 테스트: `cd frontend; npm run test -- tests/document-write-page.test.tsx`
- 프론트엔드 타입/번들 검증: `cd frontend; npm run build`
- 문서작성 대화상자를 실제 브라우저에서 열어 저장, 첨부 추가/제거, 업로드 부분 실패/재시도를 확인하고 375px/768px/1280px 화면을 캡처한다.
- `git diff --check`, 결과/화면 문서, migration이 필요한 경우 양쪽 사본을 확인한다.
- 결과 문서에 MCP 확인 근거 또는 연결 실패 및 대체 근거, 테스트 결과, 파일 실패 처리 확인, DB 미적용 상태를 기록한다.

## 위험 및 대응

- MinIO 업로드와 RDB 트랜잭션은 원자적이지 않다. 이를 하나의 commit처럼 표시하지 않고, 문서 저장 후 파일별 결과와 재시도 상태를 유지한다.
- 네트워크 timeout으로 업로드 응답만 유실될 가능성은 파일 ID/서버 응답 확인을 기준으로 처리하고, 확정되지 않은 성공을 새로 업로드하지 않는다. 구현 중 기존 업로드 계약으로 중복 여부를 판단할 수 없다면 상세 사양의 재시도 UX를 `상태 재조회` 후 재시도로 조정한다.
- 공통 파일 범용 API가 `APPROVAL`을 접근 권한 없이 노출할 수 있다. 전용 권한 가드 또는 owner-type 거부를 먼저 적용하고 테스트한다.
- object key의 파일명 충돌은 동일 owner의 기존 파일을 손상시킬 수 있다. 공통 object key 생성 개선과 같은 이름 파일 회귀 테스트를 결재 첨부 연결보다 먼저 완료한다.
- MinIO 업로드 후 metadata 저장이 실패하면 객체가 고아로 남을 수 있다. 이번 업로드로 생성한 고유 key에만 보상 삭제를 시도하고, 삭제 실패가 원본 DB 예외를 덮어쓰지 않도록 한다.
- 실제 DB의 check 제약이 저장소 초안과 다를 수 있다. MCP 도구가 현재 세션에 없어 실제 제약은 미확인 상태로 유지하며, 저장소 DDL 기준 migration 초안은 작성하지만 DB에는 적용하지 않는다.

## 의존 관계

- DB/인증 계약 확인은 API 및 migration 확정보다 선행한다.
- 문서/결재선/System 이벤트 백엔드 저장이 끝나야 첨부 업로드 및 프론트 저장 연결을 검증할 수 있다.
- 권한 우회 차단은 `APPROVAL` 첨부 엔드포인트를 프론트에 연결하기 전에 완료한다.
- DB check migration은 중앙 DB 제약 재확인 및 운영 승인 전까지 미적용 상태로 둔다. 코드/API 구현을 실제 DB에 적용하지 않는다.
