## 의존·재사용

- 입고 서비스(`MaterialReceiptServiceImpl`)의 수정·취소·금액 계산·번호 발급 경로를 그대로 쓰고, 등록(`createReceipt`)과 합격분 후보·잠금 조회를 추가한다. 무검사 자동 입고(`createFromArrival`)와 가입고 동기화(`isLinkedNoInspection`)는 바꾸지 않는다. 검사 연결 행은 `inspect_at='Y'`라 가입고 동기화 대상이 아니다.
- 화면은 `MaterialReceiptCreatePage`의 create 모드를 활성화하고, 불러오기 창은 가입고 불러오기(`MaterialArrivalOrderPicker`)의 구매처 고정 칩 UX를 따른다.
- 수입검사 서비스(`MaterialInspectionServiceImpl`)의 수정·취소에 제한을 추가한다. 입고 서비스 → 검사 서비스 호출은 두지 않고 DAO 조회(검사 DAO가 입고 테이블을 읽음)로 처리해 서비스 순환을 막는다.

## 위험과 대응

- **동시성**: 입고 등록·수정과 수입검사 수정·취소가 같은 검사 행을 동시에 건드릴 수 있다. 입고 등록·수정은 검사 헤더·행을 ID 순서로 `FOR UPDATE`한 뒤 다시 읽어 입고 가능량을 계산하고, 검사 수정·취소는 기존대로 검사 헤더를 잠근 뒤 연결 입고를 조회한다. 두 경로가 모두 검사 헤더를 잠그므로 직렬화된다.
- **입고 가능량 계산 지점**: 후보 조회, 등록·수정 검증, 입고 행 조회(상한), 검사 행 조회(기입고량) 4곳에서 같은 기준(합격량 − 유효 입고 합)을 쓴다. 지점별 테스트로 고정하고 취소된 입고는 합계에서 제외함을 확인한다.
- **연결 FK**: 입고 상세의 검사 행 FK는 `ON DELETE SET NULL`이고 검사번호를 복사해 둔다(이력·표시용). 검사 행이 삭제되려면 입고가 없어야 하므로(제한 규칙) 실제로 끊기는 경우는 취소된 입고뿐이다.
- **구매처·통화·부가세 혼합**: 한 입고는 구매처 1곳·통화 1종이므로 불러오기와 저장 양쪽에서 검증한다. 부가세 설정은 입고 헤더의 값 하나를 모든 행에 적용한다(행 금액을 다시 계산).
- **기존 입고 화면 회귀**: create 모드를 켜면서 수정·조회 모드(무검사 입고)의 동작이 바뀌지 않아야 한다. 기존 입고등록·입고현황 테스트를 그대로 유지하고 초과 확인창은 검사 연결 행에서 제외한다.

## 검증 계획

- 서비스 단위 테스트: 후보 조회(입고 가능량 > 0, 취소된 입고 제외), 등록(구매처·통화 혼합 거부, 중복 행 거부, 입고 가능량 초과 409, 번호 발급, 가입고 행 불변), 수정(상한 = 가능량 + 자기 수량, 행 빼기), 취소(헤더만, 가입고·검사 불변), 수입검사 제한(취소·행 빼기·합격량 축소 409와 입고번호 안내, 입고 취소 후 해제).
- 매퍼/스키마 정적 테스트와 실제 DB 쿼리 문법 확인(읽기 전용 MCP).
- 프론트 테스트: 불러오기 창(구매처 고정, 통화 혼합 안내), 저장 payload, 입고 가능량 초과 검증, 무검사 행 초과 확인창 유지, 수입검사 화면의 행 잠금·취소 비활성.
- 백엔드 `mvn test`, 프론트 집중 테스트·`tsc`·`npm run build`, JDK 8 `--release 8` 컴파일, 실서버 API 종단과 브라우저 375/768/1280px.
