# 20261117_013 구매자재·품질 API 모델 Swagger @Schema 보강 계획서

## 구현 단위

| 순서 | 단위 | 내용 |
| --- | --- | --- |
| 1 | 검증 테스트 | 구매자재·품질 `domain/model`의 모든 모델 클래스·필드에 `@Schema`와 비어 있지 않은 설명이 있는지 확인하는 테스트(리플렉션 + 클래스 탐색) |
| 2 | 설명 사전 | 필드 이름별 설명·예시 사전 171개, 클래스별 재정의(같은 이름이지만 뜻이 다른 필드, 오래된 주석) 작성 |
| 3 | 일괄 보강 | 사전과 기존 주석으로 54개 모델에 클래스·필드 `@Schema`를 추가하는 스크립트를 한 번 실행하고 결과를 검토. 줄바꿈 형식 유지 |
| 4 | 검토·검증 | 생성된 설명 전체를 목록으로 검토, Java 8 컴파일, 관련·전체 백엔드 테스트, Swagger 문서 확인 |
| 5 | 문서 | 결과 문서 |

## 결정과 이유
- **사전 기반 일괄 생성 + 전수 검토**: 필드가 약 900개라 손으로 쓰면 누락·불일치가 생기기 쉽다. 필드 이름별 사전을 먼저 정리해 같은 이름의 필드가 모델마다 같은 설명을 갖게 하고, 모델별로 뜻이 다른 필드(상태 검색 조건, 매입마감 행의 마감 값 등)만 클래스별 재정의로 바로잡는다. 생성 결과는 목록으로 전부 읽고 검토한다.
- **기준 모델을 따른다**: `required`·`allowableValues`는 쓰지 않고(구매요청 모델과 동일) 코드 값은 설명 문장에 적는다. 예시는 구매요청 모델처럼 값이 있는 필드에 넣는다.
- **오래된 주석 정정**: 상태 검색 필드의 주석이 "없으면 전체"로 남아 있었다. 현재 계약은 "없으면 ACTIVE, ALL로 전체(취소 포함)"이므로 설명을 현재 계약으로 쓴다.
- **동작 불변**: 어노테이션과 import만 추가하고 필드·타입·Lombok 어노테이션은 그대로 둔다.

## 위험과 대응
- **설명이 계약과 어긋남**: 코드·매퍼·서비스 검증과 대조해 사전을 작성하고, 모호한 필드는 클래스별 재정의로 구체화한다. 전수 검토 목록을 결과 문서에 근거로 남긴다.
- **줄바꿈 혼용(CRLF/LF)**: 저장소가 파일별로 다르다. 읽을 때 형식을 감지해 그대로 쓴다.
- **빌드·직렬화 영향**: 어노테이션만 추가하므로 JSON 직렬화(Jackson)와 MyBatis 매핑은 영향이 없다. 전체 `mvn test`와 Java 8 컴파일로 확인한다.

## 검증 계획
- 신규 테스트: 대상 패키지의 모든 모델 클래스에 클래스 `@Schema`, `serialVersionUID`를 제외한 모든 인스턴스 필드에 `@Schema(description≠"")`가 있어야 한다(모델 클래스는 `domain/model` 패키지 파일을 클래스패스에서 찾는다). 기준 모델(구매요청)과 같은 방식인지(`required`·`allowableValues` 미사용)도 확인한다.
- `javac --release 8`로 구매자재·품질 패키지 컴파일, 전체 `mvn test`(기존 `MinioStorageConfigTest` 1건 오류는 기존), 실행 중인 서버의 `/v3/api-docs`에서 모델 설명 노출 확인(서버는 사용자가 재구동).
