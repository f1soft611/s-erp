# 출하계획 API 전환 계획

> **For agentic workers:** 작업은 문서로 확정하며 운영 배포나 DB 변경을 수행하지 않는다.

**목표:** 구버전 호환성은 유지하지 않고 현재 출하계획 API 계약을 기준으로 단일 배포 절차를 확정한다.

**접근:** 저장소의 현재 컨트랙트, 호출자와 DB MCP 스키마를 비교한다. 동일 `/api/v1` 경로의 구버전 계약과 동시 운영을 만들지 않으며, 현재 프론트엔드·백엔드와 대상 DB를 하나의 변경 창에서 전환하도록 배포 게이트를 정의한다. 실제 운영 artifact 및 운영 DB 식별은 저장소와 기본 MCP만으로 증명할 수 없으므로 배포 전 담당자가 확정해야 한다.

**기술 범위:** 문서 변경만 수행. 애플리케이션 코드, SQL, 운영 데이터는 변경하지 않는다.

---

### 작업 1: 계약 및 현재 근거 확인

**대상:** `SalesDeliveryPlanApiController`, `SalesDeliveryPlanRequestVO`, 프론트엔드 `salesDeliveryPlan.service.ts`, `20261112_009` 스키마 변경 이력, 기본 읽기 전용 DB MCP

- [x] 동일 `/api/v1/sales/delivery-plans` 경로에서 현재 요청·응답 계약을 확인한다.
- [x] 저장소 내 직접 소비자가 프론트엔드 출하계획 서비스이며 관련 테스트가 있음을 확인한다.
- [x] 기본 MCP 계획 헤더에 수주 ID가 없고 계획 상세가 필수 수주 ID와 tenant 복합 FK를 보유하는 현재 스키마 형태를 확인한다.
- [x] GitHub Releases, Actions 실행 및 Git tag에서 배포 artifact 버전을 특정할 근거가 없음을 기록한다.

### 작업 2: 전환 및 안전 조건 확정

**대상:** 상세사양서

- [x] 구버전 유지 요구가 없으므로 API 버전 분리를 선택하지 않는다.
- [x] 현재 경로와 현재 계약을 유지하고 프론트·백엔드를 함께 배포한다.
- [x] 운영 대상 DB의 스키마 상태를 배포 직전 확인한다. 이미 현재 스키마면 009 SQL을 재실행하지 않고, 구 스키마면 승인·백업·선행조건 확인 후에만 적용한다.
- [x] 구버전 서버와 새 DB 스키마의 혼합 운영을 금지하고 롤백 가드를 기록한다.
