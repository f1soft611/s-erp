# 20261117_010 구매자재 작성 기준일 서버날짜 통일 계획서

기준: [작업지시서](../../directions/20261117/20261117_010_구매자재_작성기준일_서버날짜_작업지시서.md)

## 구현 단위

| 순서 | 단위 | 내용 |
| --- | --- | --- |
| 1 | 공통 훅 | `shared/hooks/useServerDateDefault.ts`: 신규 화면에서 서버 날짜를 한 번 조회해 콜백으로 전달, 사용자가 먼저 바꾸면 무시, 초기화용 `reload`, 실패 시 오류 콜백(로컬 날짜 대체 없음) |
| 2 | 가입고·입고·수입검사 등록 | 초기 날짜 빈 값, 훅 연결, 초기화에서 서버 날짜 재조회, 날짜 입력 시 `markTouched` |
| 3 | 구매요청등록 | 변경 감지가 `baseline`과의 비교라서 서버 날짜 도착 시 날짜와 baseline을 함께 갱신 |
| 4 | 구매요청확정 | 신규·초기화·요청 불러오기에서 서버 날짜 |
| 5 | 발주등록 | 훅 연결, 초기화에서 재조회 |
| 6 | 문서·검증 | 테스트, 브라우저, 결과 문서 |

## 결정과 이유
- **공통 훅**: 영업은 페이지마다 같은 코드를 직접 넣었다. 구매자재는 여섯 화면이라 중복을 피하려고 훅 하나로 만든다. 영업 파일은 건드리지 않는다.
- **날짜 입력 컴포넌트는 바꾸지 않는다**: 구매자재 작성 화면은 브라우저 기본 `type="date"` 입력이다. 이번 작업은 기본값 출처만 바꾸고 입력 방식 교체는 범위가 아니다(필요하면 별도 작업).
- **변경감지**: 서버 날짜 도착은 사용자 변경이 아니므로 dirty로 표시하지 않는다(`setDirty` 호출 없음, 요청등록은 baseline 갱신).

## 위험과 대응
- **기존 페이지 테스트**: `getSystemDate()`가 mock되지 않으면 오류 문구가 뜨거나 날짜가 비어 테스트가 깨진다 → 해당 테스트 파일에 `systemDateService` mock을 추가하고 서버 날짜 값으로 기대를 맞춘다.
- **저장 전 날짜 비어 있음**: 서버 날짜 도착 전 저장하면 기존 필수 검증 메시지가 나간다(별도 처리 없음).
- **StrictMode 중복 호출**: 개발 모드에서 효과가 두 번 실행되므로 `active` 플래그로 늦은 응답을 버린다.

## 검증 계획
- 훅: 도착 시 콜백 1회, 실패 시 오류 콜백·날짜 콜백 없음, `enabled=false`면 조회 안 함, `markTouched` 후 늦은 응답 무시, `reload`.
- 화면별: 서버 날짜가 브라우저 날짜와 다를 때 서버 날짜 표시, 실패 시 빈 값+오류, 초기화 후 재조회, 저장된 자료 열기 시 저장된 날짜 유지, 서버 날짜 적용이 dirty가 아님.
- 브라우저: 개발 서버 날짜(2026-11-17)와 브라우저 시계를 다르게 두고 확인.
