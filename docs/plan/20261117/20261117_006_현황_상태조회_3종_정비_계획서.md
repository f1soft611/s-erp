# 20261117_006 기존 현황 화면 상태 조회 3종 정비 계획서

기준: [작업지시서](../../directions/20261117/20261117_006_현황_상태조회_3종_정비_작업지시서.md)

## 구현 단위

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| 1 | 백엔드 발주현황 | 상태 없으면 `ACTIVE`, `ALL` 허용, 그 외 400 |
| 2 | 백엔드 가입고현황 | 위와 동일 |
| 3 | 프론트 발주현황 | 선택지에 전체 추가, 기본값 정상, 필터 변환·검색 기본값 주입 |
| 4 | 프론트 가입고현황 | 위와 동일 |
| 5 | 검증·결과 문서 | 테스트, 빌드, JDK 8 컴파일, 실서버·브라우저 확인, 결과 문서 |

## 재사용
입고현황(`MaterialReceiptStatusServiceImpl`, `materialReceiptStatus.service.ts`, `useMaterialReceiptStatus.ts`)의 구현을 그대로 따른다. 매퍼는 이미 `ACTIVE`/`CANCELED`는 필터하고 그 밖의 값(`ALL`)은 필터하지 않는 구조라 바꾸지 않는다.

## 위험과 대응
- **동작 변경**: 지금까지 기본 조회에 섞여 나오던 취소건이 사라진다. 의도한 변경이며 결과 문서에 기록한다. 취소 조회·전체 조회로 볼 수 있다.
- **저장된 검색 세션**: 사용자 브라우저에 상태 값이 없는 세션이 남아 있을 수 있다. 필터 변환에서 상태가 비어 있으면 정상으로 채우므로 복원 시에도 정상으로 조회한다.
- **검색 UI 기본값**: 검색 영역의 기본값(`usePageSearchDefaults`)은 날짜 범위만 지원하므로 상태 기본값은 훅에서 주입한다(입고현황과 같은 방식).
- **다른 호출자**: 두 상태 API를 쓰는 곳은 각 현황 화면의 훅뿐임을 확인했다(`grep`).

## 검증 계획
- 백엔드 단위 테스트: 상태 없음 → `ACTIVE`, `ALL` 통과, `CANCELED` 통과, 잘못된 값 400(두 서비스), 매퍼가 `ALL`에서 `use_at` 조건을 붙이지 않음.
- 프론트 테스트: 선택지가 정상·취소·전체, 필터 변환이 상태 없으면 `ACTIVE`, 기본 조회 요청에 `status=ACTIVE`, 기존 화면 테스트 회귀 없음.
- 실서버: 가입고·발주를 여러 건 만들고 일부를 취소한 뒤 API와 브라우저에서 정상·취소·전체 조회 결과를 확인한다(취소를 확인하려는 데이터는 취소 처리, 나머지는 남김).
