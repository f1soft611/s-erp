## 결정과 이유
- **공통 컴포넌트 `FormDateField`**: 여섯 화면이 같은 blur 정규화·오류 문구를 써야 해서 한 곳에 둔다. 컴포넌트는 `normalizeDateInput`(공통 `DateEditor`의 기존 함수)을 그대로 쓰므로 새 규칙을 만들지 않는다.
- **저장 직전 정규화**: 각 화면의 `handleSave`에서 날짜를 한 번 정규화한 값으로 검증·payload를 만든다. 무효 날짜는 기존 검증 메시지 영역에 "올바른 ○○일을 입력해 주세요."를 보낸다.
- **서버 날짜 훅과의 관계**: 훅은 날짜 문자열 setter만 호출하므로 입력 컴포넌트와 무관하다. 사용자가 입력하면 `markTouched`를 호출하는 지점만 `FormDateField`의 `onChange` 안으로 옮긴다.

## 위험과 대응
- **저장 전 날짜 형식**: 축약 입력(예 `1117`)을 blur 없이 저장 단추로 바로 누를 수 있다 → 저장 직전 정규화로 보장하고 테스트한다.
- **조회 전용 화면에서 달력 열림**: `disabled`를 `FormDateField`에서 `DateEditor`로 전달한다(`DateEditor`는 disabled이면 팝업을 열지 않는다).
- **기존 테스트**: 날짜 `<input type="date">`를 직접 다루던 테스트가 있으면 갱신한다(`getByLabelText(/^가입고일/)`는 그대로 입력 필드를 가리킨다).

## 검증 계획
- 공통 컴포넌트: blur 정규화, 무효 입력 오류, 외부 오류 표시, `disabled`에서 달력 불가.
- 화면별: 축약 입력 후 저장 시 payload 날짜 ISO, 무효 날짜는 요청 없음+오류, 필수 누락 차단.
- 회귀: 구매·품질 화면 테스트 전체. 브라우저로 여섯 화면 달력 열기·선택, 375px 겹침 확인.
