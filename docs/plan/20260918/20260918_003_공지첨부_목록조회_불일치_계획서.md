## 요구사항 분석

- 첨부 업로드는 `CommonFileService.uploadFile(tenantId, "NOTICE", postId, ...)`을 통해 `tb_common_file`에 저장된다.
- `NoticeBoardServiceImpl.deleteAttachment`, `downloadAttachment`, `deletePost`는 이미 `commonFileService.listFiles(tenantId, "NOTICE", postId)`(= `tb_common_file`) 기준으로 정상 동작한다.
- 유일하게 `hydratePost()`만 여전히 `noticeBoardDAO.selectNoticeAttachmentList(...)`(= `tb_board_file`, 항상 빈 결과)를 호출하여 목록/상세 응답의 `attachments`가 비어 보인다.
- `attachmentCount`는 `selectNoticePostList`/`selectNoticePostById` SQL의 서브쿼리(`tb_board_file` 기준)에서 채워지며 역시 항상 0이다. 기존 `commentCount`처럼 서비스 계층에서 재계산하는 패턴이 이미 존재하므로 동일 패턴을 적용한다.

## 작업 범위 분해 (백엔드 전용)

1. **매핑 헬퍼 추가**: `CommonFileVO` → `NoticeBoardFileVO` 변환 메서드를 `NoticeBoardServiceImpl`에 추가한다. `uploadAttachment()`에 이미 존재하는 수동 매핑 로직과 동일한 필드 대응을 재사용한다(중복 로직 통합, 범위 내 리팩터링).
2. **`hydratePost()` 수정**: `noticeBoardDAO.selectNoticeAttachmentList` 호출을 제거하고 `commonFileService.listFiles(tenantId, BOARD_TYPE_NOTICE, postId)` 결과를 매핑하여 `post.setAttachments(...)`에 설정한다.
3. **`attachmentCount` 재계산**: `hydratePost()`에서 매핑된 첨부파일 리스트 크기로 `post.setAttachmentCount(...)`를 설정해 SQL 서브쿼리 값을 덮어쓴다(commentCount와 동일 패턴).
4. **SQL/DAO 변경 없음**: `tb_board_file` 기반 DAO 메서드(`selectNoticeAttachmentList`, `selectNoticeAttachmentById`, `insertNoticeAttachment`, `softDeleteNoticeAttachment`)는 삭제하지 않고 유지한다(현재 다른 곳에서 호출되지 않아 즉시 삭제해도 무방하나, 이번 작업은 조회 경로 정합화에 집중하고 불필요한 삭제로 범위를 넓히지 않는다).
5. **테스트 갱신**: `NoticeBoardServiceImplTest`의 `listPostsHydratesAttachmentsCommentsAndPaginationMetadata`, `getPostHydratesAttachmentsForEachNoticeComment` 테스트가 `noticeBoardDAO.selectNoticeAttachmentList`를 모킹하던 부분을 `commonFileService.listFiles(tenantId, "NOTICE", postId)` 모킹으로 교체하고, 매핑된 `NoticeBoardFileVO` 필드(`boardFileId` 등)를 검증하도록 갱신한다. `attachmentCount` 검증 케이스를 추가한다.
