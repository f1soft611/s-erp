## 요구사항 분석 및 목적

메뉴 관리 페이지는 F1-Grid 기반으로 조회/검색/저장/삭제/엑셀 내보내기와 dirty 상태 관리까지 한 화면에서 처리하고 있다. 권한 관리 화면도 동일한 구조와 동작 흐름을 따라야 하며, 권한 마스터와 권한별 사용자 매핑을 함께 관리할 수 있어야 한다.

이번 작업의 목적은 다음과 같다.

1. 메뉴 관리 페이지와 동일한 페이지 레이아웃 구조를 유지하면서 권한 관리 화면을 구현한다.
2. 권한 관리 영역을 F1-Grid 기반으로 구성해 역할 목록을 조회하고 수정/생성/비활성화 흐름을 유지한다.
3. 권한별 사용자 매핑 영역을 별도 F1-Grid로 구성해 권한과 사용자 연결 상태를 쉽게 관리한다.
4. 프론트엔드와 백엔드가 기존 테이블 구조와 API 패턴에 맞게 연동되도록 한다.

## 작업 범위 분해

### A. 프론트엔드: 화면 구조 및 F1-Grid 구성

1. 권한 관리 페이지를 기존 설정 페이지 구조에 맞게 구성한다.
   - 상단 경로 영역
   - 상단 버튼 영역
   - 검색 영역
   - 메시지 영역
   - 권한관리 F1-Grid 영역
   - 권한별 사용자 매핑 F1-Grid 영역
2. 기존 메뉴 관리 페이지의 공통 패턴을 재사용해 `PageHeader`, `PageSearchArea`, `PageMessageArea` 구조를 유지한다.
3. 권한 관리용 `RoleManagementPage`/`RoleManagementPanel` 구조를 확장하거나 새 권한 관리 페이지를 추가해 화면을 구성한다.
4. F1-Grid 컬럼 정의, 검색 필터, row selection, dirty 상태 관리, 저장/취소 확인 흐름을 적용한다.
5. 권한별 사용자 매핑은 선택된 역할 기준으로 사용자를 검색하고, assign/unassign 상태를 관리하는 UI를 구성한다.

### B. 프론트엔드: 서비스 및 타입 정의

1. 역할 목록 조회 API 응답을 기존 `SystemRoleVO` 형식에 맞게 매핑한다.
2. 권한별 사용자 매핑 조회 API와 저장 API를 위한 타입/서비스를 추가한다.
3. 사용자 목록, 역할 내 사용자·미할당 사용자 분리 로직을 공통 서비스에 정리한다.
4. 에러, 로딩, 성공 메시지 처리와 dirty 상태를 기존 설정 페이지와 동일하게 유지한다.

### C. 백엔드: 권한/역할 API 정합성

1. 기존 `SystemRoleApiController`와 역할 서비스 로직을 재확인하여 역할 목록/생성/수정 동작이 그대로 유지되도록 한다.
2. 기존 `SystemPermissionApiController`를 활용해 활성 권한 코드 목록을 읽도록 한다.
3. 권한별 사용자 매핑 API를 추가하거나 기존 역할 API 확장으로 사용자-역할 연결 데이터를 조회/저장한다.
4. DB는 기존 `tb_role`, `tb_login_account`, `tb_login_account_role` 구조를 활용해 연동한다.
5. 관리자 권한 체크와 예외 응답은 기존 `EgovAccessControlHelper` 및 `ResponseCode` 패턴에 맞춘다.

### D. 검증

1. 프론트엔드: `npm run build`로 타입 안정성 확인
2. 프론트엔드: 권한 관리 관련 테스트 또는 회귀 테스트 수행
3. 백엔드: `cd backend && mvn test` 또는 관련 단위 테스트 검증
4. 브라우저 UI에서 상단 경로/버튼/검색/메시지/그리드 구조가 표시되는지 확인

## 기존 코드/아키텍처 영향 범위

- 프론트엔드 영향 범위: `frontend/src/pages/settings/system/roles/**`, 필요한 경우 `frontend/src/pages/dashboard/components/DashboardContent.tsx` 또는 공통 설정 구조 파일
- 백엔드 영향 범위: `backend/src/main/java/egovframework/let/system/roles/**`, `backend/src/main/java/egovframework/let/system/permissions/**`, 필요 시 사용자-역할 매핑 관련 로직
- 기존 구조 유지: 메뉴 관리 페이지와 동일한 페이지 구성, 공통 PageHeader/PageSearchArea/PageMessageArea, 기존 `SystemRole*` API 구조 활용
- DB 영향: 신규 테이블 생성은 불필요하며, 기존 역할/로그인계정/역할매핑 테이블을 재사용하는 방식을 우선한다.

## 검증 계획

- **프론트엔드 빌드**: `cd frontend && npm run build`
- **프론트엔드 테스트**: `cd frontend && npm run test` 또는 권한 관리 관련 테스트 파일 선택 실행
- **백엔드 검증**: `cd backend && mvn test`
- **브라우저 검증**: 설정 페이지에서 권한 관리 화면 진입 후 경로, 버튼, 검색, 메시지, 2개 F1-Grid 레이아웃 표시 확인
- **회귀 확인**: 기존 메뉴 관리 페이지 구조와 역할 관리 페이지 동작이 충돌하지 않는지 점검

## 기대 결과

- 메뉴 관리와 동일한 페이지 구조를 유지한 권한 관리 화면이 구현된다.
- 권한관리와 권한별 사용자 매핑이 분리된 2개 F1-Grid 영역으로 운영된다.
- 프론트와 백엔드의 데이터 흐름이 기존 ERP 아키텍처와 일관되게 맞물린다.
- 사용자에게는 같은 설정 페이지 패턴을 유지하면서 더 직관적인 권한 운영 화면이 제공된다.
