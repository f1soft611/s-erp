# 20261014_006 문서작성 상세 피드 및 재조회 계획서

## 목표

문서작성 피드/리스트 전환마다 데이터를 다시 조회하고 해당 보기의 스켈레톤을 표시한다. 피드형은 문서 목록 응답 한 번으로 본문, 결재선, 첨부, 초기 댓글을 준비한 뒤 필터 결과 전체를 상세 카드로 한 번에 표시한다. 문서 상세 수정 모달이 닫히거나 저장된 후 기존 우측 상세 패널은 유지하고 조용히 갱신한다.

## 파일 변경 지도

### 백엔드 응답 계약

- 수정 `backend/src/main/java/egovframework/let/groupware/approval/controller/DocumentApprovalApiController.java`: `GET /documents`에 기본값 false인 `includeDetails` 파라미터를 추가하고, true일 때만 상세 피드 서비스 분기를 호출한다.
- 수정 `backend/src/main/java/egovframework/let/groupware/approval/service/DocumentApprovalService.java`, `.../service/impl/DocumentApprovalServiceImpl.java`: 기존 scope/type/ID 권한 필터에 속한 문서만 상세·첨부·결재선·초기 댓글 페이지로 구성하며 상세 선조회 중 조회 이력/조회수를 변경하지 않는다.
- 생성 `backend/src/main/java/egovframework/let/groupware/approval/domain/model/DocumentApprovalFeedItemVO.java`: 기존 목록 필드를 상속하고 피드에서 필요한 상세 필드 및 댓글 cursor metadata를 추가한다. 기본 목록 및 summary notice DTO는 변경하지 않는다.
- 수정 서비스/컨트롤러 테스트에서 feed response 전체 구성, 인증 조건, view-history 미호출, 기본 목록 계약 유지를 검증한다.

### 프론트엔드

- 수정 `frontend/src/pages/groupware/documents/write/services/documentApproval.service.ts` 및 `types/documentWrite.types.ts`: 상세 포함 목록 옵션과 응답 필수 필드 타입/검증을 추가한다.
- 수정 `frontend/src/pages/groupware/documents/write/hooks/useDocumentWritePage.ts`: viewMode 전환마다 목록 재조회, feed일 때 상세 포함 옵션 지정, 오래된 응답 무시, 모드별 loading/error 처리를 관리한다.
- 수정 `frontend/src/pages/groupware/documents/write/DocumentWritePage.tsx`: feed/list 스켈레톤을 구분하고 완전한 feed 응답이 도착하기 전 부분 카드를 표시하지 않는다.
- 수정 `frontend/src/pages/groupware/documents/write/components/DocumentFeedItem.tsx`, `DocumentApprovalDetailFeed.tsx`: 피드 카드에 API 선조회 상세·댓글 데이터를 주입하고 카드별 초기 detail/comment 요청은 제거한다. 기존 댓글 추가/수정/삭제 및 이전 댓글 페이징, 첨부와 반응을 유지한다.
- 수정 `frontend/tests/document-feed-item.test.tsx`, `frontend/tests/document-write-page.test.tsx`: 응답 선주입, 보기 전환 재조회/스켈레톤, stale 응답 배제, 전체 카드 일괄 표시, 기존 상세 패널/quiet refresh를 검증한다.

## 구현 순서 및 검증

1. 백엔드 작업 전에 `s-erp-postgresql-readonly` MCP로 `list_tables` 후 관련 승인/댓글/파일 테이블을 `describe_table`로 확인한다. DB 스키마 변경은 없으며 조회 결과는 결과 보고서에 계약 근거로 기록한다.
2. 서비스/컨트롤러 테스트를 먼저 추가한다. `includeDetails=true`에서 모든 필수 피드 필드가 준비되고 조회 이력/조회수가 바뀌지 않는지, 기본 목록 branch에 detail 조회가 추가되지 않는지 검증한다.
3. `DocumentApprovalFeedItemVO`와 선택적 목록 API 분기를 구현한다. 권한/필터 범위는 현행 목록 메서드와 동일하게 적용하고 일부 문서 데이터가 누락되면 부분 성공으로 응답하지 않는다.
4. 프론트 서비스·타입 검증을 추가하고 mode switch에 맞춰 `includeDetails=true/false`를 사용한다. 요청 중 feed/list skeleton, 실패 시 명시적 오류, stale 응답 무시를 테스트한다.
5. `DocumentApprovalDetailFeed`가 feed의 선조회 데이터를 초기 상태로 사용하도록 변경한다. 초기 카드별 detail/comment API 요청은 발생하지 않아야 하며 이전 댓글 페이지 조회 및 조작은 기존 API를 유지한다.
6. 기존 편집/삭제 권한, 좋아요 로컬 토글, feed의 결재 처리 UI 제외, list 상세 패널, Composer close/save의 quiet refresh를 회귀 확인한다.
7. `Set-Location backend; mvn -Dtest=DocumentApprovalServiceImplTest,DocumentApprovalApiControllerTest test`, `Set-Location frontend; npx vitest run tests/document-feed-item.test.tsx tests/document-write-page.test.tsx`, `npm run build`를 실행한다.
8. `http://127.0.0.1:4173`의 S-ERP 서버를 확인 후 재사용하고 375px/768px/1280px에서 화면 전환, 스켈레톤, 데이터 일괄 표시, 댓글/첨부, quiet edit refresh를 확인한다. 캡처와 결과를 날짜별 결과 폴더에 기록한다.

## API 및 DB 범위

- 목록 경로와 기존 필터는 유지한다. `includeDetails`가 없거나 false일 때 기존 `resultList` 응답 형태를 유지한다.
- `includeDetails=true`일 때 목록 result row에 `contentsJson`, `contentsHtml`, `contentsText`, `viewCount`, `isDrafter`, `draftingWorkCategoryId`, `approvalLines`, `attachments`, `systemEvents`, `comments`, `commentCount`, `hasPreviousComments`, `nextBeforeCommentId`를 추가한다.
- 피드에는 댓글 최신 3개 root 페이지를 포함하고, 과거 댓글은 기존 cursor API로 조회한다.
- DB 테이블/컬럼/인덱스 및 공지사항 API는 변경하지 않는다.

## 완료 기준

- 보기 모드 전환은 재조회와 해당 보기의 스켈레톤을 표시한다.
- 피드 데이터는 상세 포함 목록 요청 1회로 모두 도착한 뒤 전체 카드로 표시된다. 개별 feed card의 최초 상세/댓글 요청은 없다.
- 기존 목록 응답/summary 응답, 문서 상세 조회수, 권한, 댓글 후속 조회 및 조작 동작이 보존된다.
- 집중 백엔드/프론트 테스트와 build가 통과하고, 3개 뷰포트 결과물과 MCP 계약 확인 근거가 보고서에 포함된다.
