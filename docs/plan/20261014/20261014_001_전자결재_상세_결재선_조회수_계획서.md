## 변경 범위

### 프론트엔드

- `DocumentApprovalDetailFeed.tsx`: 작성자 Avatar/이름/기안자·일자·조회수 행과 분리된 결재선 패널을 표시한다.
- 같은 파일에서 승인 카드 간 connector를 꺾쇠 아이콘으로 변경하고, 순번+이름을 중앙 정렬하며 긴 이름을 말줄임 처리한다.
- 합의와 참조를 각각 별도 행으로 렌더링하고 각 참여자의 실제 `stageOrder`를 표시한다.
- `documentWrite.types.ts` 및 `documentApproval.service.ts`: 상세 응답 `viewCount`를 필수 정수로 정의·검증한다.
- `document-write-page.test.tsx`: 실제 상세의 조회수, 작성자 행, 결재선 순서·말줄임·합의/참조를 회귀 검증한다.
- `document-approval-service.test.ts`: 상세 응답의 `viewCount` 유효성 검증을 회귀 검증한다.

### 백엔드 및 DB

- `DocumentApprovalDetailVO`, `DocumentApprovalDAO`, `DocumentApprovalServiceImpl`, `DocumentApproval_SQL_postgresql.xml`에서 상세 조회수 계약을 추가한다.
- `DocumentApprovalServiceImplTest`에서 최초/반복/다른 사용자/접근 불가 동작을 테스트한다.
- `DocumentApprovalMapperTest`에서 조회수 mapping, tenant-scoped lookup, 중복 방지 insert 및 원자 counter update SQL을 검증한다.
- `tb_electronic_approval_main.view_count`와 신규 `tb_electronic_approval_view_history`를 날짜별 SQL로 추가한다.
- SQL, 변경 이력, rollback을 `docs/database/20261014/`와 `backend/DATABASE/20261014/`에 동일하게 보관하고 `docs/database/db-schema.md`를 갱신한다.

## 집계와 응답 규칙

- 유니크 집계 키는 `(tenant_id, electronic_approval_id, login_id)`이다.
- 권한이 확인된 상세 진입에서만 조회 기록을 시도한다. 최초 history insert가 성공한 경우에 한해 `view_count`를 원자적으로 1 증가시킨다.
- insert 충돌 이후에도 상세 행을 다시 읽어 응답하며, 반복·동시 조회는 중복 증가하지 않는다.
- `GET /api/v1/groupware/approvals/documents/{electronicApprovalId}`의 기존 envelope에 `item.viewCount`를 추가한다. 목록 조회에는 조회수 증가 동작을 추가하지 않는다.

### 실행 검증 메모

- 반응형 화면 검증은 브라우저에서 합성 문서 데이터로 수행했다. 375px에서 결재 카드 흐름 내부에만 가로 스크롤이 생기고, 768px·1280px에서는 페이지 가로 넘침이 없었다.
- 현재 실행 중인 상세 API는 HTTP 200을 반환하지만 `result.item.viewCount`를 포함하지 않아 프론트 응답 검증이 실패한다. 브라우저 시각 검증에서는 API 응답을 브라우저 안에서만 합성 데이터로 대체했으며 서버 데이터는 변경하지 않았다.
- DB migration은 적용하지 않았다. 실제 API 연동 검증은 변경된 백엔드와 migration 배포 후 다시 수행해야 한다.
