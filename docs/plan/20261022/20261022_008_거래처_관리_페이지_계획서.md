## 구현 목표

`/co/master/customers`에서 `tb_customer_info` 기반 테넌트 거래처 조회/검색/등록/수정/사용여부 변경을 제공한다. 화면은 기존 `DraftFormManagementPage`의 단일 키워드 검색, 컬럼 메타데이터 기반 상세검색, F1-Grid 행 폼을 따른다. 백엔드는 인증 principal의 `tenant_id`만 사용하며, 등록/수정은 테넌트 관리자와 메뉴 생성/수정 권한을 요구한다.

## 구현 단위

### 1. 문서 및 DB 채번 구조

- 상세 사양에서 API 계약, 타입 변환, 검색 조건, 검증/권한, 오류 응답을 확정한다.
- 기존 전자정부 ID Generator를 재사용한다. `EgovConfigAppIdGen`에 `IDS`/`tb_customer_info` 키, 6자리, block size 1인 generator bean을 추가한다.
- `20261022_005` SQL에서 기존 거래처 코드 중 1~6자리 숫자 최댓값 다음 값으로 `ids.next_id`를 초기화하고, 기존 카운터가 더 크면 유지한다. 별도 sequence/table은 만들지 않는다.
- eGov 생성값이 999999를 넘으면 저장을 거부한다. rollback은 이미 발급된 코드를 재사용하지 않도록 `ids` 카운터를 보존한다.
- 기존 `customer_id` 기본 시퀀스와 거래처 테이블 구조는 변경하지 않는다.
- `docs/database/db-schema.md`에 MCP에서 확인한 거래처 테이블/제약과 기존 `ids` generator metadata를 기록한다.

### 2. 백엔드

- 공통코드 기준으로 검색 전용 `CustomerInfoSearchCondition`에서 tenant를 분리하고, 서비스가 인증 tenant와 검색값을 DAO용 Map으로 구성한다. 무조건 조회/조건 조회 overload를 제공한다.
- 조회 Controller는 `ResultVO`를 반환하고 등록/수정/배치 저장은 `ResponseEntity<ResultVO>`를 반환한다. 존재하지 않는 행은 서비스의 `findByIdOrThrow`에서 `ResponseStatusException(404)`로 처리한다.
- 별도 `CustomerInfoBatchService`/Impl과 변경 집합/요청/결과 VO를 추가한다. `saveBatch`는 기존 CustomerInfoService의 등록/수정을 재사용하고 전체 변경을 하나의 트랜잭션으로 처리한다.
- eGov IDS, 감사 사용자 ID 기록, Y/N 검증, 물리 삭제 금지를 유지한다. 배치에 삭제 행이 있으면 명시적으로 거부한다.
- Controller, Service, DAO, VO 및 PostgreSQL MyBatis Mapper를 `egovframework.let.co.master.customer` 아래에 추가한다.
- GET 목록은 키워드 및 상세 조건을 조합하고 인증된 tenant 범위로 제한한다.
- POST는 비어 있는 코드를 `customerCodeIdGnrService`로 생성하고 `customer_id`는 기존 DB default에 맡긴다.
- PUT은 tenant-scoped ID로만 갱신하며 identity/tenant/audit 입력을 무시한다.
- `customer_name`, `use_at`, 테넌트별 코드 중복, 다른 테넌트 ID 접근을 검증한다.

### 3. 프론트엔드

- 저장 훅은 개별 POST/PUT 반복 대신 `saveCustomerBatch`를 한 번 호출한다. 배치 오류 시 dirty 변경을 유지하고, 성공 시 현재 검색 조건으로 재조회한다.
- API 타입/서비스와 요청 상태 훅을 추가한 후 `CustomerManagementPage`와 F1-Grid 행 폼을 구성한다.
- `DashboardContent`의 `co/customers` 분기와 `dashboardData`의 페이지 설명을 추가한다.
- 키워드는 거래처코드/명/약칭, 상세검색은 대표자/사업자번호/법인번호/업태/종목/사용여부로 구성한다.
- 조회/추가/저장 액션을 메뉴 권한과 테넌트 관리자 여부에 따라 노출한다. 물리 삭제는 제공하지 않는다.
- 거래처 숫자/연락처 다섯 필드에 공통 F1-Grid `inputFormat` 설정을 적용한다. 사업자번호(10), 법인등록번호(13), 우편번호(5), 전화·팩스(최대 11, `02`는 10) 자리수 상한을 입력 단계에서 공통 적용하고, 저장 시 비어 있지 않은 값의 허용 자리수(사업자 10, 법인 13, 우편 5, 전화/팩스 `02` 9·10, 기타 10·11)를 검증한다. 입력은 폼·인라인·TSV 붙여넣기·사업자/법인번호 상세검색에 동일 적용하며 상세검색은 부분 값을 허용한다. 미변경 기존 값도 저장 검증 대상이고, 기존 값 및 앞자리 0은 사용자가 편집할 때까지 보존한다.
- `F1-GRID.md`에 새 화면이 사용하는 검색 메타데이터와 행 폼 흐름을 추가한다.

### 4. 검증 및 결과

- 거래처 domain model 7개 클래스의 `@Schema`와 필드 설명을 보완한다. 저장 필수값, 사용여부 허용값, 채번/배치 ID/삭제 금지 계약을 설명하고 상속된 저장 필드도 검증한다.
- 모델 metadata 회귀 테스트를 추가해 클래스와 모든 비정적 필드의 설명 및 필수값/허용값을 확인한다.

- Vitest에서 서비스 직렬화, 검색 조합, 권한, Grid 행 폼 저장/오류를 확인한다.
- Maven에서 Controller/Service tenant scoping, 입력 검증, eGov 자동채번 및 매퍼 SQL을 검증한다.
- `npm run build`를 수행하고 375px/768px/1280px 실제 브라우저 화면을 확인한다.
- 변경 결과와 스크린샷을 [결과 디렉터리](../../result/20261022/customer-management/)에 보관한다.

## 완료 기준

- 상세 사양서의 필드/API/검색/권한 계약이 백엔드와 프론트엔드에 일치하게 반영된다.
- 새 테스트와 빌드가 통과하며 기존 동작에 불필요한 변경이 없다.
- 날짜별 SQL/이력/롤백 사본이 같고, DB 변경 이력과 F1-Grid 사용 문서 및 결과물이 남는다.
