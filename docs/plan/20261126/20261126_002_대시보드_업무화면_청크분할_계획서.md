## 구현 단위

1. **DashboardContent 지연 로딩** (`frontend/src/pages/dashboard/components/DashboardContent.tsx`)
   - named export 화면을 `lazy()`로 감싸는 헬퍼 `lazyPage(load, exportName)`와 화면 48개를 등록부 `dashboardPages.ts`에 둔다. 컴포넌트 이름은 그대로 유지해 본문 분기 코드는 바꾸지 않는다.
   - 기존 함수 본문을 `DashboardContentView`로 옮기고, export되는 `DashboardContent`는 `<Suspense fallback={null}>`로 감싼다.
   - `ComingSoonPage`, 기본 현황 화면(카드 영역), `PageHeader`는 정적 import를 유지한다.
2. **테스트 보정**
   - 1차 적용 후 기준선 대비 51건이 새로 실패했다. 모두 렌더링 직후 동기 조회(`getBy*`)가 지연 로딩 fallback을 만난 경우다.
   - 약 130곳의 조회를 각각 비동기로 바꾸는 대신, 등록부를 `dashboardPages.ts`로 분리하고 `preloadDashboardPages()`를 제공한다. 해당 테스트 파일은 `beforeAll`에서 preload해 변경 전과 같은 조건(모든 화면 로드 완료)으로 실행한다. 단언은 바꾸지 않는다.
3. **검증**
   - `npm run build` 경고 없음과 청크 크기 표
   - 영향 테스트 21개 파일 전후 비교, `oxlint` 변경 파일
   - 브라우저(`127.0.0.1:4173`)에서 대시보드 → 업무 화면 전환, 375·768·1280px

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 메뉴 첫 진입 시 본문이 잠깐 비어 보임 | 청크는 화면별로 수십~수백 kB이며 사이드바·헤더는 유지된다. 앱 진입 정책과 같은 빈 fallback 사용 |
| 동기 렌더링 전제 테스트 실패 | 기준선 비교로 새 실패만 대기 보정 |
| 배포 후 구 청크 해시 요청 실패(재배포 직후 열린 탭) | 기존 라우트 lazy 로딩과 같은 조건이며 이번 범위에서 새로 다루지 않는다. 결과 문서에 기록 |
| 같은 브랜치를 쓰는 다른 세션과 충돌 | 별도 worktree(`chunk-dashboard-lazy` 브랜치)에서 작업 |
