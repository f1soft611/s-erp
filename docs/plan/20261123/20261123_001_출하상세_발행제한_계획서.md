# 출하 상세 발행 제한 계획

## 근거와 결정

- [매출마감 작업지시서](../../directions/20261120/20261120_003_매출마감_선택마감_스크롤_및_요약개선_작업지시서.md)
- 사용자 결정: 기존 100건 제한을 유지한다.
- 일반 발행과 매출마감은 100건 초과 선택을 화면에서 알리고 요청을 막는다. AUTO 출하에서는 기존 트랜잭션 거부를 유지하고 제한 이유를 명확히 표시한다.

## 순서

1. 상세사양에 건수 기준과 기존 API·트랜잭션을 기록한다.
2. 100건 허용, 101건 거부, AUTO 실패 시 롤백에 대한 회귀 테스트를 먼저 작성한다.
3. 기존 검증 범위 안에서 화면 안내와 서버 오류 메시지를 정비한다.
4. 관련 프론트·백엔드 테스트, 프론트 typecheck/build/lint, Java 8 호환성을 확인한다.
5. 가능한 브라우저 검증과 결과를 `docs/result/20261123/statement-detail-limit`에 기록한다.

스키마, API 경로, 권한 및 100건 상한은 변경하지 않는다. DB MCP는 관련 테이블 메타데이터만 확인한다.

## 구현 단위

- `SalesStatementServiceTest`, `RevenueClosingServiceTest`: 100건이 다음 DAO 단계에 도달하고 101건은 `BAD_REQUEST`와 `100` 안내를 반환함을 검증한다. 상세 생략 경로에도 동일하게 적용한다.
- `SalesStatementServiceImpl`, `RevenueClosingServiceImpl`: 빈 목록 오류와 초과 오류를 분리하고 초과 오류에 최대 100건을 명시한다.
- `salesStatement.service.ts`, `revenueClosing.service.ts`: 중복 제거 후 `ids.length > 100`이면 API를 호출하지 않고 최대 100건 오류를 던진다. 일반 발행 훅과 매출마감 페이지에서도 확인창/서버 날짜 조회 전에 같은 안내를 표시한다.
- `sales-delivery-page.test.tsx`: AUTO 저장 오류 메시지가 사용자에게 표시되는지 확인한다. 출하 화면은 서버 오류를 그대로 표시하므로 모든 출하에 임의 상한을 도입하지 않는다.
- 실행: `cd frontend; npm run test:ci -- tests/sales-statement-page.test.tsx tests/sales-revenue-closing-page.test.tsx tests/revenue-closing-service.test.ts tests/sales-delivery-page.test.tsx`; `cd backend; mvn -B -ntp '-Dtest=SalesStatementServiceTest,RevenueClosingServiceTest,SalesDeliveryServiceImplTest' test`.
