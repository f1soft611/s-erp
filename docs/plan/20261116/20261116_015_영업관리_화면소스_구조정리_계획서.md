# 영업관리 화면 소스 구조 정리 계획서

1. 현재 `sales/order`, `sales/delivery`, `sales/delivery-plan`, `sales/statement` 디렉터리와 활성 참조를 확인한다.
2. 테스트·브라우저 테스트의 출하계획 및 거래명세서 import를 목표 경로로 먼저 바꾸고, 관련 테스트를 실행해 새 파일이 없어 실패함을 확인한다.
3. `delivery-plan` 폴더를 `delivery/plan`으로, `statement` 폴더를 `delivery/statement`로 이동한다.
4. 이동된 파일의 상대 import와 `DashboardContent` import를 깊이에 맞게 수정한다. 견적관리 등 기존 미커밋 변경은 보존한다.
5. 집중 테스트, 브라우저 흐름 테스트, 프런트 빌드와 변경 영역 lint를 실행한다.
6. 활성 코드에서 이전 경로 참조가 남지 않았는지 확인하고 날짜별 결과 문서를 작성한다.

## 제약

- 이동은 파일 구조 정리로 한정하며 화면/API 동작을 변경하지 않는다.
- endpoint의 `/sales/delivery-plan` 및 `/api/v1/sales/delivery-plans` 문자열은 외부 계약이므로 변경하지 않는다.
- 과거 날짜별 계획·결과 문서는 당시 구현 경로를 기록한 이력이므로 불필요하게 일괄 수정하지 않는다.

## 추가 요청 실행 계획

1. 수주관리 등록·현황의 책임별 폴더와 거래명세서의 평면 구조를 비교한다.
2. 거래명세서 페이지 테스트와 출력 테스트의 import를 목표 경로로 바꾸고 실패를 확인한다.
3. 등록 페이지는 `statement/create`, 현황 페이지는 `statement/status`로 옮긴다.
4. 등록 전용 선택기·상세 그리드와 현황 전용 상세 패널·편집창을 각각 `components`로 분리한다.
5. 페이지의 상태·조회·저장 처리를 각각 `hooks`로 옮기되 effect 의존성과 처리 순서를 유지한다.
6. 컬럼 정의는 각 화면의 `data`로, API 모듈은 `services/salesStatement.service.ts`,
   공유 타입은 `types/salesStatement.types.ts`, 등록 전용 props는 `create/types`로 분리한다.
7. 공유 출력 컴포넌트와 CSS는 기능 루트의 `components`로 옮기고 순수 출력 계산은 `data/statementPrint.ts`로 분리한다.
8. 대시보드와 테스트의 import를 갱신하고 거래명세서 테스트·라우팅·출력, 빌드, 변경 영역 lint를 실행한다.
9. 합성 데이터로 실제 브라우저에서 등록·현황·수정·출력 흐름을 확인하고 결과 문서와 스크린샷을 갱신한다.
