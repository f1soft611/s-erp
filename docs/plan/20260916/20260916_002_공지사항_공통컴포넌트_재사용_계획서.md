# 20260916_002 공지사항 공통 컴포넌트 재사용 계획서

## 1. 목적

공지사항 화면의 피드/첨부/댓글 영역을 단일 페이지 전용 로직에서 분리하여, 공지사항 외 다른 게시판 또는 피드형 화면에서도 재사용할 수 있도록 구조를 정리한다.

이번 작업의 핵심은 3개 문맥별 공통 컴포넌트로 분리하는 것이다.

- `FeedList`: 게시글 카드/메타/본문/액션 영역을 담당
- `AttachmentList`: 파일 목록, 확장자 아이콘, 다운로드/삭제 액션을 담당
- `CommentThread`: 댓글/답글 트리와 입력 UI를 담당

기존에는 첨부 컴포넌트가 `Notice*` 네이밍으로 고정되어 있어 공통 컴포넌트로 보기 어렵고, 댓글/피드 영역은 페이지 내부에 남아 있어 재사용성이 제한적이다. 향후 다른 피드형 화면에서 같은 구조를 조립할 수 있도록 범용 UI 계층으로 이동하는 것을 목표로 한다.

## 2. 요구사항 분석

### 현재 문제점

- `NoticeFeedList` 내부에 댓글 트리 UI가 직접 포함되어 있어, 댓글 영역이 페이지 전용 로직으로 고착되어 있다.
- `NoticeAttachmentList`는 이름 자체가 공지사항 전용으로 보이므로 공통 컴포넌트라고 보기 어렵다.
- 공지사항 기능을 다른 게시판/피드 형식에 재사용하려면, 첨부/댓글/피드가 각각 독립된 조립 단위여야 한다.

### 설계 원칙

- 공통 컴포넌트는 기능 중심으로 구성한다.
- 공지사항 페이지는 공통 컴포넌트를 조립하는 화면으로 유지한다.
- 기존 화면 동작과 시각 구조는 그대로 유지하여 사용자 경험 변화가 없도록 한다.
- 서버 API 및 데이터 모델 구조는 기존 계약을 유지한다.

## 3. 작업 범위

### 3.1 프론트엔드 작업 범위

1. `NoticeFeedList`의 화면 조립 책임을 경량화한다.
2. 재사용 가능한 `FeedList` 컴포넌트를 공통 계층으로 분리한다.
3. 첨부 목록 UI를 범용 `AttachmentList`로 정리한다.
4. 댓글 트리 UI를 범용 `CommentThread`로 분리한다.
5. 공지사항 화면은 이 3개의 공통 컴포넌트를 조합하는 형태로 리팩터링한다.
6. 기존 스타일, 다크모드, 버튼/상태 뱃지 표현, 파일 아이콘 색상 체계를 유지한다.

### 3.2 제외 범위

- 백엔드 API 신규 설계
- 댓글/첨부 저장 로직 전면 재설계
- 다른 도메인 전체 화면 리팩터링
- 전역 상태 관리 도입
- DB 스키마 변경

## 5. 실행 계획

### 작업 단계 1: 구조 정리

- 기존 `NoticeFeedList`에서 댓글 트리와 첨부 렌더링 영역을 식별한다.
- 공통 UI가 될 수 있는 영역을 재사용 단위로 분리한다.
- 현재 공지사항 동작이 유지되는지 확인한다.

### 작업 단계 2: 공통 컴포넌트 추출

- `FeedList` 컴포넌트 생성
- `AttachmentList` 컴포넌트 생성 또는 이름 정리
- `CommentThread` 컴포넌트 생성
- 공통 props로 액션 콜백(다운로드/삭제/댓글 등록/답글 클릭) 정의

### 작업 단계 3: 공지사항 페이지 적용

- `NoticeFeedList`에서 공통 컴포넌트를 사용하도록 연결
- 기존 이벤트 핸들러와 데이터 구조를 유지
- extra props와 형태 변환 로직만 범용 인터페이스에 맞게 정리

### 작업 단계 4: 검증

- `cd frontend`

- 관련 Vitest 테스트 실행
- 필요 시 화면 검증을 위해 렌더링 기준을 점검한다.

## 6. 검증 계획

### 정적 검증

- TypeScript 타입 오류 없음
- JSX 구조와 props 계약 일치
- 불필요한 의존성/중복 로직 제거

### 기능 검증

- 공지사항 목록이 기존과 동일하게 표시된다.
- 첨부 파일 목록이 정상적으로 렌더링된다.
- 댓글 목록과 답글 트리가 기존 UX와 동일하게 보인다.
- 다크 모드와 공지 강조 배지 스타일이 유지된다.

### DB 영향 검토

- 본 작업은 프론트엔드 공통 컴포넌트 분리만 수행하며 서버/DB 계약 변경이 없다.
- DB 스크립트: 해당 없음, 영향 검토 완료.

## 7. 위험 요소 및 대응

### 위험 요소

- 공통 컴포넌트로 분리하면서 기존 notice 전용 스타일이 누락될 수 있다.
- 컴포넌트 이름이 `Notice*`로 남아 있어 재사용성 의도가 약해질 수 있다.
- props 인터페이스가 과하게 추상화되어 공지사항 화면이 복잡해질 수 있다.

### 대응

- 기존 디자인 스펙을 유지하고, 공통 props는 최소 범위로 정의한다.
- 컴포넌트 책임을 3개로 명확히 나눈다.
- 페이지별 데이터 변환 로직은 상위 화면에서 처리한다.

## 8. 완료 기준

- 3개의 재사용 컴포넌트가 각각 역할을 명확히 가진다.
- 공지사항 페이지는 이 컴포넌트를 조립하는 형태로 동작한다.
- 이름이 공지사항 전용이 아닌 기능 중심으로 정의된다.
- 기존 공지사항 UX가 유지된다.
- TypeScript 빌드 및 관련 테스트가 통과한다.
