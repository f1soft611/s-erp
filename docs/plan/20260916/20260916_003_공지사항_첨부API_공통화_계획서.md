# 20260916_003 공지사항 첨부 API 공통화 계획서

## 1. 작업 목적

공지사항 첨부 파일 로직은 현재 `NoticeBoardServiceImpl` 안에 업로드, 삭제, 다운로드, MinIO 저장, 메타 저장이 모두 강하게 결합되어 있다. 이 구조는 공지사항 전용 로직으로 보이기 때문에, 다른 게시판 또는 범용 피드 화면에서 동일한 첨부 기능을 재사용하기 어렵다.

이 작업은 첨부 파일 기능을 공통 모듈로 분리해서, 공지사항 화면은 기존 동작을 유지하면서도 내부적으로 공통 첨부 서비스를 사용하도록 정리한다.

## 2. 핵심 문제 정의

- 첨부 업로드/다운로드/삭제 로직이 `notice` 도메인에 고정되어 있음
- 파일 객체 키, 저장 버킷, 메타 관리, 삭제 처리 로직이 특정 게시글 경로에 묶여 있음
- 다른 기능에서 동일한 첨부 기능을 재사용하려면 같은 API/서비스 패턴을 공유해야 함
- 기존 공지사항 API는 그대로 유지해야 하므로, 공통화는 내부 구조 정리 위주로 진행해야 함

## 3. 아키텍처 방향

### 권장 방식

- 공통 첨부 기능을 `egovframework.com.attachment` 계열로 분리한다.
- 첨부 서비스는 `tenantId`, `ownerType`, `ownerId`, `fileName`, `bucketName`, `objectKey`, `uploadedBy` 등을 범용적으로 처리한다.
- 공지사항은 기존 엔드포인트를 유지하되, 내부적으로 공통 첨부 서비스를 호출하는 어댑터 역할을 맡는다.

### 기대 효과

- 첨부 API 재사용성 향상
- 공지사항/게시판/자료실/피드형 화면에서 동일한 API 계약으로 확장 가능
- 기존 공지사항 동작과 응답 체계 유지

## 5. 영향 범위

### 백엔드 영향

- 공통 첨부 서비스 신규 추가
- 공지사항 서비스 코드 일부 분리/위임
- 공지사항 API 응답 유지

### DB 영향

- 없음. 기존 첨부 메타 테이블/기존 스키마 재사용이 목적이므로 신규 테이블 생성 또는 컬럼 추가는 범위에서 제외한다.
- 따라서 SQL 스크립트와 DB 변경 이력은 이 작업에서 새로 만들지 않는다.

### 프론트엔드 영향

- 없음. 본 작업은 백엔드 API 구조 정리만 수행한다.

## 7. 위험 요소 및 대응

### 위험 1: 공지사항 기존 API가 깨지는 문제

- 대응: 기존 경로와 응답 형식을 유지하고, 공통 모듈은 내부 구현만 추상화한다.

### 위험 2: ownerType/ownerId 설계가 과도하게 일반화되어 복잡해지는 문제

- 대응: 첨부 기능의 공통 핵심만 유지하고, notice 전용 추가 로직은 어댑터에서 처리한다.

### 위험 3: 저장 경로와 삭제 로직 불일치

- 대응: MinIO object key와 bucket 관리를 공통 서비스에서 일관되게 관리한다.

## 8. 완료 기준

- 첨부 업로드/다운로드/삭제 로직이 공지사항 전용 의존성을 벗어나 공통 계층으로 정리되었다.
- 공지사항 API는 동작을 유지하면서 공통 첨부 모듈을 사용한다.
- 공통 서비스는 다른 기능에서도 동일한 경로와 계약으로 재사용 가능하다.
- 기존 테스트 및 Maven 빌드가 통과한다.
