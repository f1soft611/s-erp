# AGENTS

## 프론트엔드 작업 가이드

이 파일은 [frontend](../frontend) 영역에서 작업할 때 AI 에이전트가 따라야 할 규칙을 정리한 문서입니다.

## 기본 원칙

- 작업 전에 [docs](../docs) 의 요구사항 문서와 작업지시서를 먼저 확인합니다.
- 구현은 문서 기준으로 수행하고, 화면 동작을 추측하지 않습니다.
- 변경 범위는 [frontend/src](src) 와 관련 설정으로만 제한합니다.
- 기존 구조와 네이밍을 우선 따르며, 불필요한 리팩터링을 하지 않습니다.

## 작업 순서

1. 작업지시서와 요구사항 문서 확인
2. [docs/plan](../docs/plan) 에서 계획 수립
3. [docs/spec](../docs/spec) 에서 화면/기능/검증 기준 정의
4. 실제 구현
5. 결과 문서와 스크린샷 정리

## 프론트엔드 개발 규칙

### 공통 다이얼로그 및 확인

- 확인, 입력, 선택, 상세 보기 등 모달 UI는 `shared/components/CommonDialog.tsx`를 사용합니다. 기능 컴포넌트에서 MUI `Dialog`를 직접 렌더링하지 않습니다.
- 확인이 필요한 작업은 `shared/hooks/useCommonConfirmDialog.tsx`를 사용하고, 확인 결과가 `true`일 때만 원래 동작을 진행합니다.
- 확인창은 제목과 필요한 짧은 부가설명만 상단에 두고, 확인 사유와 전체 안내문은 본문 영역에 표시합니다. 긴 메시지를 제목 아래에만 두고 본문을 비워 두지 않습니다.
- 브라우저 기본 `window.alert`, `window.confirm`, `window.prompt`는 사용하지 않습니다. 단순 성공/오류/안내는 기존 알림 컨텍스트 또는 화면 내 `Alert` 패턴을 사용합니다.
- `beforeunload` 이벤트와 PWA 설치 이벤트의 `prompt()`는 브라우저가 제공하는 플랫폼 동작이므로 일반 확인 대화상자와 구분합니다.
- `CommonDialog` 크기와 접근성 props를 사용해 기존 콘텐츠 폭, 제목 연결 및 닫기 버튼 이름을 유지합니다.

### 기존 화면 레이아웃 일치

- 모든 화면의 상단 메시지 영역은 성공·오류·경고·안내·입력 검증·서버 오류 등 종류나 발생 원인에 관계없이 동일한 외부 여백을 사용합니다. 메시지 종류에 따라 본문 패딩을 바꾸거나 메시지 래퍼에 추가 패딩을 넣지 않습니다.
- 등록 화면의 기준은 수주등록의 입력 검증 메시지입니다. 메시지와 바로 아래 기본정보의 좌우 경계를 맞추고, 일반 본문은 모든 폭에서 좌우·상단·하단 `2`(16px), 메시지와 다음 영역의 `gap: 2`(MUI spacing)를 사용합니다(수주등록 `SalesOrderCreatePage`의 `px/pt/pb: 2`가 기준, 2026-11-26 확정). embedded 본문의 패딩은 0으로 유지합니다. 선택창·상세 대화상자는 `CommonDialog`가 자체 패딩을 관리하므로 이 기준에서 제외합니다.
- 메시지 여백 검증에서는 같은 오류 종류만 비교하지 않습니다. 성공·입력 검증·서버 오류를 실제로 각각 발생시키고 375/768/1280px에서 상단 위치, 좌우 경계, 다음 영역까지의 간격이 동일한지 확인합니다. 서버 오류만 비교하고 전체 메시지 여백이 통일되었다고 판단하지 않습니다.
- 신규 화면이나 기존 화면 변경 전 같은 업무의 등록·현황 등 동종 화면을 직접 확인하고 기준 화면을 작업 문서에 명시합니다.
- 제목과 버튼 위치, 검색 영역, 입력 폼, 그리드, 상세 영역, 여백과 반응형 동작을 기준 화면과 통일하고 기존 공통 컴포넌트를 우선 재사용합니다. 별도의 레이아웃이나 표를 임의로 새로 만들지 않습니다.
- 업무상 차이가 필요한 경우 요구사항에 근거해 그 차이를 사양과 결과 문서에 기록합니다. 완료 전에 기준 화면과 나란히 비교하고 실제 브라우저에서 확인합니다.
- 현황 상세의 보기·수정 폼은 같은 업무 등록 화면의 폼과 F1Grid를 실제 컴포넌트로 공유합니다. 비슷한 별도 그리드를 재작성하지 말고 컬럼, 분할·편집 동작, 권한 및 검증 차이를 비교합니다. 차이가 불가피하면 사양과 결과에 이유를 기록하고 등록·상세·수정 화면을 함께 회귀 검증합니다.
- F1Grid를 사용했다는 사실만으로 편집 방식이 같다고 판단하지 않습니다. 기준 화면이 셀 직접 편집을 사용하면 컬럼의 `type`·`editable`과 그리드 편집·확정·저장 흐름도 동일하게 적용하고, 셀마다 별도 입력 컴포넌트를 상시 렌더링하는 방식으로 대체하지 않습니다.
- 현황 상세의 작성자 이름·프로필·등록일, 요약 및 정보 그룹도 기준 화면과 비교합니다. 그리드 행 높이, 기본정보의 행·열 간격, 대화상자 내부 여백은 브라우저에서 기준 화면과 실제 치수를 대조하고, 표시 데이터가 빠졌다면 API 응답까지 확인합니다.

### 현황 페이지 기준일

- 신규 현황/상태 목록 페이지는 업무 기준일 검색조건을 제공하고 필수조건으로 지정합니다.
- 기준일이 기간 검색이면 시작일과 종료일을 모두 필수로 검증하고, 필수 조건은 상세검색 적용 칩에서 해제할 수 없게 합니다.
- 검색 기본값 유무와 관계없이 제출 검증을 유지하고, 이전 세션 복원에도 유효한 기준일을 보장합니다.

### 서버 연결 실패 화면 (모든 페이지 공통)

- 페이지가 열릴 때 서버에서 읽는 초기 데이터(목록, 기준일, 공통코드, 상세, 소수점 정책 등)의 조회가 서버에 연결하지 못해(`ApiNetworkError`) 실패하면 `shared/components/PageLoadBoundary.tsx`를 사용해 해당 페이지 본문 영역에만 "서버에 연결하지 못했습니다…" 문구와 다시 시도 아이콘을 표시합니다. 헤더와 사이드 메뉴는 유지하고, 전체 앱 화면으로 대체하지 않습니다.
- 상태는 `shared/hooks/useInitialLoadState.ts`로 관리합니다. 조회 시작 `start()`, 성공 `succeed()`, 실패 `fail(cause)`를 호출하고, 기존 화면 내 오류 메시지를 유지해야 하는 화면은 `useInitialLoadState({ networkOnly: true })`로 서버 연결 실패만 페이지 오류 화면으로 처리합니다. 오류 종류는 `toPageLoadError(cause)`로 구분하며, 모든 실패를 `'server'`로 고정하지 않습니다.
- 소수점 정책을 쓰는 화면은 `usePolicyDecimalStatus()`의 `network`를 `PageLoadBoundary`의 `error`(`'network'`)에 연결하고, 다시 시도에서 `resetGridDecimalPolicyCache()`를 호출합니다. `SalesDecimalPolicyError`에는 `network`를 넘겨 중복 표시를 막습니다.
- 페이지 오류 화면이 표시될 때는 다른 메시지(오류·성공 알림, 검색 결과 건수, 입력 검증 메시지)가 함께 보이면 안 됩니다. `PageMessageArea`, `Alert`, `SearchResultMessage` 등 모든 메시지 영역을 `PageLoadBoundary` 내부에 두고, 서버 연결 실패는 `isApiNetworkError(cause)`일 때 `setError`를 호출하지 않습니다(`shared/services/apiErrors.ts`).
- 등록·현황·관리·마감 등 새 페이지를 만들 때는 초기 조회가 하나도 없는 화면이 아니라면 이 규칙을 적용하고, 다시 시도는 실패한 조회를 다시 실행하도록 연결합니다. 영업관리의 모든 화면(견적·수주·출하계획·출하·거래명세서·매출마감·납품처관리)에 적용되어 있습니다.

## 반응형 브라우저 대응 규칙

- 화면 구현 전 모바일, 태블릿, 데스크톱 레이아웃을 함께 고려합니다.
- 최소 375px, 768px, 1280px 뷰포트에서 레이아웃을 확인합니다.
- 고정 너비로 인해 의도하지 않은 가로 스크롤이 발생하지 않도록 합니다.
- 테이블, 검색 영역, 필터, 버튼 그룹은 좁은 화면에서 줄바꿈, 내부 스크롤, 접힘 중 적절한 방식을 적용합니다.
- 텍스트, 버튼, 아이콘, 입력 요소가 겹치거나 잘리지 않도록 합니다.
- 기존 스타일 체계에 맞춰 유동적인 너비, 미디어 쿼리, `minmax` 등을 사용합니다.
- DOM 테스트만으로 반응형 검증을 끝내지 않고 실제 브라우저 렌더링을 확인합니다.
- 화면 변경 후 필요한 경우 모바일 및 데스크톱 스크린샷을 결과 문서에 포함합니다.

## 페이지 생성 시 구조 예시

페이지를 새로 만들 때는 아래와 같은 수준으로 정리하는 것을 원칙으로 합니다.

```text
src/
  pages/
    settings/
      system/
        menus/
          MenuManagementPage.tsx
          components/
          hooks/
          services/
          types/
          constants/
          data/
        roles/
          RoleManagementPage.tsx
          components/
          hooks/
          services/
          types/
          data/
    dashboard/
      DashboardPage.tsx
      components/
      hooks/
      services/
      types/
      data/
    groupware/
      DocumentsPage.tsx
      OverviewPage.tsx
  shared/
    components/
      f1-grid/
      layout/
      PageHeader.tsx
      PageSearchArea.tsx
    hooks/
      usePagination.ts
      useDebouncedSearch.ts
    services/
      apiClient.ts
      authService.ts
    context/
    types/
  routes/
  theme/
```

원칙:

- 페이지 파일(`XxxPage.tsx`)은 화면 조립과 주요 흐름을 담당하고, `pages/<도메인>/<기능>/` 폴더 바로 아래에 둡니다.
- 해당 기능 안에서만 쓰이는 UI, 훅, API 호출, 타입은 같은 기능 폴더 하위의 `components/`, `hooks/`, `services/`, `types/`로 분리합니다.
- 정적 목록, 옵션 데이터 등은 필요할 때 같은 위치에 `data/` 또는 `constants/`로 분리합니다.
- 신규·변경 관리 화면은 같은 업무의 기존 화면(예: 창고관리)의 파일 구조를 먼저 확인합니다. 조회·검색·선택·저장 등 상태와 로직이 복합적인 화면은 단일 페이지에 몰지 말고 `hooks/`, 그리드·컬럼은 `components/`, API·계약은 `services/`와 `types/`, 행 초기값·정적 데이터는 `data/`로 책임을 분리합니다.
- 여러 페이지/도메인에서 공통으로 재사용되는 컴포넌트, 훅, 서비스, 컨텍스트, 타입만 `src/shared` 아래로 승격합니다. 한 기능에서만 쓰이는 코드를 `shared`로 옮기지 않습니다.
- 한 페이지 안에서 단순한 UI만 있는 경우, 하위 폴더를 과도하게 만드는 대신 같은 파일에 두는 것이 더 적절할 수 있습니다.
- 너무 작은 파일 단위로 쪼개지 말고, 재사용 여부와 복잡도 기준으로 분리합니다.
- `hook`은 여러 컴포넌트에서 재사용되거나 로직이 복잡할 때 만들며, 단순한 페이지 전용 상태는 같은 파일에 둘 수 있습니다.

## 영업관리 출하 소스 구조 (필수)

출하관리의 세 기능은 `shipment` 아래의 형제 폴더로 구성합니다. 과거 `sales/delivery/plan`이나 `sales/delivery/statement` 아래에 새 파일을 만들지 않습니다.

```text
src/pages/sales/shipment/
  delivery/
    create/
    status/
  deliveryplan/
    create/
    status/
    components/
    services/
    types/
  statement/
    create/
      components/
      hooks/
      data/
      types/
    status/
      components/
      hooks/
      data/
    components/
    data/
    services/
    types/
```

- 등록·현황 페이지는 각각 `create`, `status`에 두고 화면 조립을 담당합니다. 복합 상태·조회·저장 흐름은 `hooks`, UI는 `components`, API는 `services`, 계약·props는 `types`, 컬럼·초기값·정적 옵션·순수 변환은 `data`로 분리합니다.
- 등록·현황이 함께 쓰는 코드는 해당 업무 폴더의 공통 역할별 폴더에 둡니다. 하나의 업무만 사용하는 코드를 `src/shared`로 올리거나 서로 같은 UI·로직을 복제하지 않습니다.
- 위 예시는 업무 계층과 책임을 설명합니다. 사용하지 않는 역할 폴더를 형식적으로 만들지 않습니다.
- 경로 변경 시 대시보드 연결, 전체 소비자의 import와 mock, 브라우저 테스트의 동적 import를 함께 갱신합니다. 메뉴 URL·page key·API 주소를 소스 디렉터리에 맞춰 변경하지 않습니다.
- 검증은 관련 등록·현황·서비스 테스트, 빌드, 변경 영역 lint와 필요한 실제 브라우저 흐름을 포함합니다.

## 검증 기준

```bash
cd frontend
npm install
npm run dev
npm run build
npm run test
```

- `npm run dev`: Vite 개발 서버 실행
- `npm run build`: TypeScript + Vite 빌드
- `npm run test`: Vitest 단일 실행

## 브라우저 테스트 포트

- 모든 실제 브라우저 테스트는 `http://127.0.0.1:4173`에서 수행합니다. 다른 포트로 변경하거나 Vite가 포트를 자동 변경한 상태에서 테스트하지 않습니다.
- 브라우저 테스트용 서버는 `npm run dev -- --strictPort`로 실행해 4173을 사용할 수 없을 때 다른 포트로 자동 전환되지 않도록 합니다.
- 4173에서 이미 실행 중인 서버가 있으면 iPlusMES 서버인지 확인한 뒤 재사용합니다. 다른 서버이거나 용도를 확인할 수 없으면 임의의 다른 포트로 테스트하지 말고 충돌을 먼저 해결합니다.

## 브라우저 테스트 서버 정리

- 브라우저 테스트를 위해 개발 서버를 직접 실행한 경우, 테스트 완료 여부와 관계없이 테스트 종료 후 해당 서버를 종료하고 사용한 포트가 해제되었는지 확인합니다.
- 테스트가 실패하거나 중단된 경우에도 동일하게 정리합니다. 자동화 스크립트에서는 성공·실패 경로 모두에서 종료 처리가 실행되도록 합니다.
- 기존에 실행 중이던 서버를 재사용한 경우에는 해당 서버를 종료하지 않습니다.

## 금지 사항

- 문서 없이 화면 동작을 임의로 추가하지 않습니다.
- 인접 기능과 무관한 수정이나 대규모 리팩터링을 하지 않습니다.
- 결과 문서와 스크린샷 없이 작업을 완료로 간주하지 않습니다.

## 소수점 계약 규칙 (서버 계산 문서)

- 소수점은 `src/shared/config/decimal-column-contract.json`에서만 정합니다. 계약 대상 문서의 컬럼에 `decimalPlaces`, `rounding`, `trailingZeros`, `decimal`이나 고정 `places`를 직접 쓰지 않습니다.
- 정책이 기본이고, 계약 컬럼에 `places`/`rounding`/`trailingZeros`가 있으면 그 항목만 정책보다 우선합니다.
- 예외 컬럼 설정 방법과 JSON 예시, 신규 모듈 적용 절차는 [공통 소수점 계약 가드레일 사양](../docs/spec/20261126/20261126_001_공통_소수점_계약_가드레일_상세사양서.md)을 따릅니다.
