# 20261104_001 납품관리 스키마 변경 이력

## 변경일·대상·영향

- 날짜: 2026-11-04.
- 신규: `tb_sales_delivery_hd`, `tb_sales_delivery_dt`.
- 기존: `tb_sales_order_dt`에 수주상세/수주/테넌트/품목 복합 유일키 추가.
- 메뉴: 지정 테넌트의 영업관리 모듈 아래 납품관리/납품등록/납품현황 및 버튼 권한.
- 수주 연계 저장/수정/삭제 시 기존 `shipped_qty` 보정. 직납품은 수주에 영향 없음.
- 재고수불·회계 테이블 변경 없음. 실제 DB에는 적용하지 않음.

## 현재 계약 확인

- 기본 `s-erp-postgresql-readonly` MCP의 `list_tables`, `describe_table`로 수주 헤더/상세, 거래처, 품목, 메뉴, 모듈 계약 확인.
- 제한된 `pg_constraint` 조회로 tenant 복합 FK 대상키와 메뉴 권한 PK/FK 확인.
- `pg_attribute` 메타데이터로 메뉴/모듈 ID가 BY DEFAULT identity임을 확인. 업무 행, 계정 행, 테넌트 행은 조회하지 않음.
- 원본 수주 DDL `20261026/20261026_008_create_sales_order_schema.sql`, 감사 컬럼 확장 `20261028/20261028_009_expand_sales_order_audit_columns.sql` 참고.

## 적용 순서

1. 대상 DB 백업 및 기존 수주 스키마/100자 감사 컬럼 적용 상태 확인.
2. `20261104_001_create_sales_delivery_schema.sql`을 해당 승인된 업무 DB에 한 번 실행.
3. 메뉴 SQL의 `v_tenant_id := NULL`을 명시적으로 승인된 대상 tenant ID로 수정.
4. `20261104_001_seed_sales_delivery_menu.sql`을 메뉴 저장 DB에서 실행. tenant ID 미지정·모듈 미존재/중복·기존 노드 충돌 시 실패하며 전체 롤백.
5. 수주등록/현황과 대응하는 기존 역할 권한만 복사됨. 수주 역할 권한이 없으면 권한관리에서 담당 역할에 명시적으로 부여.
6. 애플리케이션 배포 후 합성 테스트 데이터로 직납품, 부분납품, 초과 차단, 수정/삭제 및 현황 조회 확인.

메뉴 SQL은 충돌 없는 반복 실행을 허용하되 기존 노드/권한을 덮어쓰지 않는다. DDL은 재실행용 스크립트가 아니며 테이블이 없을 때만 적용한다.

## 무결성과 이력

- 부모/상세 delivery_type 복합 FK로 NULL source의 FK 우회 방지.
- 수주상세 복합 FK로 source 수주/품목/tenant 불일치 차단.
- 납품은 논리삭제하고 상세는 보존. 따라서 삭제된 납품의 수주 참조도 수주 상세 재생성/삭제를 막는다.
- API는 같은 수주 헤더를 잠가 수주 수정/납품 간 잔량 검사 경쟁을 방지한다.

## 롤백

- 제공: `20261104_001_rollback_sales_delivery_menu.sql`, `20261104_001_rollback_sales_delivery_schema.sql`.
- 메뉴 롤백은 이 작업에서 새로 만든 노드에만 적용. 기존 동일 코드 노드가 있었다면 백업 기준 수동 복원.
- 새 메뉴 아래 다른 노드가 추가되었으면 자동 롤백 거부.
- 스키마 롤백은 모든 납품 이력이 없는 경우만 허용. 이력이 있으면 출하수량 정합성·보관 정책을 확정한 별도 절차가 필요하며 자동 삭제하지 않는다.
- 채번 상태는 보존하여 이미 발급한 번호를 재사용하지 않는다.
